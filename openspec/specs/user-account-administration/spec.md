# user-account-administration Specification

## Purpose
管理員對使用者帳號的管理語義：email 唯一性衝突以友善訊息呈現、未知 email 以 NULL 表示，使用者更新採欄位級審計差異，帳號標註供應來源並管理外部身分綁定與解綁的失效語義，角色變更即時失效相關憑證。

## Requirements

### Requirement: Admin user email uniqueness conflict is friendly
When an administrator updates a user's `email` via `PUT /api/v1/users/:id` to a value already held by another live account, the system SHALL return `409 Conflict` with a machine-recognizable conflict code, not a generic `500` internal error. Email SHALL be trimmed and case-normalized before the uniqueness comparison.

#### Scenario: Duplicate email rejected with 409
- **WHEN** admin sets a user's email to one already used by another live account
- **THEN** the request fails with `409` and a machine-recognizable conflict (not a `500`)

#### Scenario: Case-insensitive uniqueness
- **WHEN** admin sets an email that differs from an existing one only by case or surrounding whitespace
- **THEN** it is treated as a conflict after trim/case normalization

### Requirement: Field-level audit diff for user updates
Administrative user updates SHALL record a field-level before/after diff in the audit log so that what changed is auditable. `full_name` MUST NOT be masked as `***MASKED***` in the audit body, as it is not a secret.

#### Scenario: Update records before and after
- **WHEN** admin changes a user's `full_name` or `email`
- **THEN** the audit entry records the previous and new values for the changed fields

#### Scenario: full_name not over-masked
- **WHEN** an admin user update touches `full_name`
- **THEN** the audit body shows the actual `full_name` value, not `***MASKED***`

### Requirement: Unknown email represented as NULL
The system SHALL represent an unknown or absent email as NULL rather than an empty string, and SHALL enforce email uniqueness only over non-NULL values. When LDAP provisioning encounters an email conflict, it SHALL store NULL, allowing multiple email-less shadow accounts to coexist.

#### Scenario: LDAP conflict stores NULL not empty string
- **WHEN** LDAP provisioning finds the incoming email already taken
- **THEN** the shadow account's email is stored as NULL, not as an empty string

#### Scenario: Multiple email-less accounts allowed
- **WHEN** more than one account has no email (NULL)
- **THEN** the unique index does not reject them, because uniqueness applies only to non-NULL emails

### Requirement: 供應來源標註與外部身分管理
使用者 SHALL 帶不可變的供應來源標註（local/ldap/oidc），SHALL 於建立時寫入且 SHALL NOT 因後續登入方式改寫。管理端列表 SHALL 呈現來源；OIDC 帳號 SHALL 可辨識至 provider 實例（顯示名），不得壓成籠統單一「oidc」標示。列表 SHALL 提供來源篩選。

使用者的外部身分關聯（provider、subject、最近登入）SHALL 可由超級管理者或持使用者管理權限點者（如身分管理員）檢視；上述管理者 SHALL 可為既有帳號顯式綁定外部身分，並 SHALL 可解除綁定（目標為超級管理者或系統安全管理員帳號時，另依「超級管理者與系統安全管理員帳號的身分控制權」）。**解除綁定 SHALL 連帶使該使用者的既有存取失效**——涵蓋刷新憑證、仍有效的存取憑證、進行中協議連線、唯讀訂閱，以及尚未兌換的交棒憑證、待驗證狀態憑證與連線授權憑證。失效粒度為**使用者級**：該使用者經其他身分提供者或本地密碼建立的工作階段亦一併失效，須重新登入。此為刻意的安全取捨——身分級粒度需在每類憑證各多帶一維狀態，漏接風險高於「使用者重新登入一次」的成本；管理介面 SHALL 於確認前明示「該使用者的所有工作階段將被登出」。解除綁定 SHALL 於介面明示後果（已外部化的帳號解除其最後一筆身分將使其無法登入，該操作 SHALL 被拒絕）。

密碼類管理操作（重設密碼、強制改密）SHALL 依帳號憑證是否已外部化而鎖定，並 SHALL 由後端強制。

憑證外部化狀態的轉移 SHALL 明確且受限：非外部化帳號 SHALL 可由超級管理者或持使用者管理權限點者顯式改為僅外部登入（同交易清除密碼雜湊，不留可比對殘值），且該操作 SHALL 要求該帳號至少已有一筆外部身分；該操作 SHALL 一併撤銷以本地密碼建立或啟動的一切存取（含刷新與存取憑證、連線授權憑證、進行中協議連線、監看訂閱，以及**尚在進行中的多因素待驗證狀態**——否則其可於轉換後完成驗證，並因帳號此時已外部化而跳過密碼相關檢查，取得新的正式會話）；已外部化的帳號 SHALL NOT 取得本地密碼。

SHALL NOT 使任何帳號失去全部可用登入途徑。判準為「操作後該帳號是否仍有可用登入途徑」：仍具本地密碼者解除最後一筆外部身分 SHALL 被允許；目錄供應帳號的登入不依賴外部身分記錄故不受此限；憑證已外部化且登入途徑僅剩外部身分者，解除最後一筆 SHALL 被拒絕，並 SHALL 提供原子的「解除綁定並停用帳號」操作作為正當出路。

任何操作（改為僅外部登入、停用、移除 admin 角色、刪除帳號）若將使「啟用中且未外部化的 admin 帳號」數量**自一以上降為零**，SHALL 被拒絕；該數量已為零的既有部署 SHALL NOT 因此被阻擋一切管理操作（此時系統 SHALL 持續警示需新增本地 admin 以保有解封能力）。此判定 SHALL 於序列化範圍內重讀後成立——各操作獨立檢查不足以維持此不變式（兩個並發操作可各自看見對方仍存在而同時成功）。同理，解除外部身分綁定的「仍有可用登入途徑」判定 SHALL 於使用者範圍的序列化範圍內重讀。——系統封印後的解封僅接受本地 admin 憑證，失去最後一個此類帳號將導致無人可解封。

#### Scenario: 列表呈現來源
- **WHEN** admin 檢視使用者列表
- **THEN** 每列可辨識該帳號為 local/ldap/oidc 來源；OIDC 帳號可辨識至 provider 實例（顯示名）

#### Scenario: 外部來源鎖定密碼操作
- **WHEN** admin 開啟一個 OIDC 供應帳號的編輯介面
- **THEN** 密碼重設類操作不可用，並標示密碼由外部身分提供者管理

#### Scenario: admin 綁定外部身分
- **WHEN** admin 為一個既有帳號綁定某 provider 的外部身分
- **THEN** 該使用者此後可經該 provider 登入至此帳號

#### Scenario: 解綁使該使用者既有存取全數失效
- **WHEN** 一個帳號綁有兩個 provider 的身分且各自建立過會話與協議連線，admin 解除其中一個身分的綁定
- **THEN** 該使用者的刷新憑證、既簽存取憑證、協議連線、唯讀訂閱與尚未兌換的能力憑證**全數失效**（含經另一 provider 建立者），須重新登入；管理介面於確認前已明示此後果

#### Scenario: 解綁提示後果
- **WHEN** admin 對一個已外部化帳號的多筆外部身分之一執行解綁
- **THEN** 介面於確認前明示該身分將無法再用於登入

#### Scenario: 來源不因登入改寫
- **WHEN** 一個 local 供應的帳號被綁定外部身分並以該身分登入
- **THEN** 其供應來源標註仍為 local

#### Scenario: 轉換撤銷本地密碼建立的存取
- **WHEN** 使用者以本地密碼取得會話並進入多因素待驗證狀態，admin 隨即將該帳號改為僅外部登入
- **THEN** 其既有會話與連線失效，該待驗證狀態亦失效（SHALL NOT 於轉換後完成驗證並取得正式會話）

#### Scenario: 帳號停用收線監看訂閱
- **WHEN** 一名以本地密碼登入的管理者正監看他人會話，admin 停用該管理者帳號
- **THEN** 其監看訂閱被收線（該訂閱不產生協議會話記錄，亦無外部身分關聯，仍 SHALL 被涵蓋）

#### Scenario: 改為僅外部登入後本地路徑關閉
- **WHEN** admin 對一個已綁外部身分且具本地密碼的帳號執行「改為僅外部登入」
- **THEN** 該帳號此後可經外部身分登入，以任何密碼進行本地登入皆失敗

#### Scenario: 不可製造不可登入的孤兒帳號
- **WHEN** admin 嘗試解除一個憑證已外部化、且登入途徑僅剩該筆外部身分之帳號的最後一筆外部身分
- **THEN** 操作被拒絕並回明確錯誤，並提示可改用「解除綁定並停用帳號」

#### Scenario: 仍有本地密碼者可解綁最後一筆
- **WHEN** admin 對一個仍具本地密碼的帳號解除其最後一筆外部身分
- **THEN** 操作成功，該帳號仍可以本地密碼登入

#### Scenario: 並發操作不得使本地 admin 歸零
- **WHEN** 系統僅有兩個啟用且未外部化的 admin，兩個請求並發分別對兩者執行停用（或改為僅外部登入）
- **THEN** 至多一個成功，系統仍存在至少一個啟用且未外部化的 admin

#### Scenario: 並發解綁不得使登入途徑歸零
- **WHEN** 一個憑證已外部化的帳號有兩筆外部身分，兩個請求並發各解綁其中一筆
- **THEN** 至多一個成功，該帳號仍保有至少一筆外部身分

#### Scenario: 已無本地 admin 時不阻擋管理操作
- **WHEN** 系統已不存在任何啟用且未外部化的 admin，admin 執行其他帳號管理操作
- **THEN** 操作不因該不變式被拒絕，但介面持續警示需新增本地 admin 以保有解封能力

#### Scenario: 不可移除最後一個本地 admin
- **WHEN** admin 嘗試將最後一個啟用且未外部化的 admin 帳號改為僅外部登入（或停用、移除 admin 角色、刪除）
- **THEN** 操作被拒絕並回明確錯誤，帳號狀態不變

### Requirement: 角色變更的憑證失效

管理端**替換**使用者角色集的操作，於「有效角色集有列被移除」時 SHALL 於**同一交易**內完成三件事：替換角色、推進該使用者的憑證世代、撤銷其全部刷新憑證。SHALL NOT 停在「角色已變更但世代未推進」的中間態——該中間態使降權在憑證層完全不生效。

**替換端點的作用範圍限於由管理者指派的角色列**。角色指派列帶有來源（僅管理者指派、僅由外部群組映射賦予、兩者並存），替換端點 SHALL 只增刪管理者指派的部分：讀取端 SHALL 分別回傳管理者指派集與映射集，寫入端 SHALL 只接受管理者指派集。以現行**有效**角色集重送替換 SHALL NOT 改變任何列的來源——否則任何「讀取後整包回寫」的用戶端（介面、既有腳本）都會把映射賦予的角色靜默升格為管理者指派，而審計上與正常指派無從區分。

請求主體含目前僅由映射賦予的角色時，該角色 SHALL 被忽略：SHALL NOT 因此建立管理者指派、SHALL NOT 使請求失敗。回應 SHALL 以可辨識的機器碼列出被忽略的角色，使用戶端得以呈現「這些角色來自映射」。把僅由映射賦予的角色轉為同時由管理者指派（釘住）SHALL 為獨立的顯式操作，SHALL NOT 是替換端點的副作用。

替換端點的舊請求形狀（以單一鍵描述整組有效角色者）SHALL 被拒絕並回可辨識的機器碼，SHALL NOT 靜默視為管理者指派集——靜默相容會使未更新的用戶端一次刪光該使用者的映射角色而無訊號。

**世代推進的判定 SHALL 以有效角色集（管理者指派集與映射集的聯集）是否有列被移除為準**，SHALL NOT 以集合是否相等為準、亦 SHALL NOT 以角色數量是否變少為準：角色集自一個特權角色換成另一個時數量不變，但確有撤除。

現行角色集 SHALL 於序列化範圍（使用者級憑證鎖）內重讀後比對；鎖外預讀 SHALL NOT 視為滿足本要求（兩個並發替換可各自看見舊集合而其一誤判為無變動）。同時需要系統級與使用者級鎖時 SHALL 依既定的 system → user 固定順序取用。

有效角色集**沒有任何列被移除**時 SHALL NOT 推進世代，其中包含兩種情形：新角色集與現行角色集相同（管理端重存同一組角色不得使該使用者的既有會話失效），以及新角色集為現行角色集的嚴格擴充（純追加不縮減任何權限，推進會使當事人於進行中的核准／代配流程被迫重新登入）。

**純追加角色的冪等端點**同受此判準約束，其對已由映射賦予的角色 SHALL 升為並存態而非新建列。替換端點與冪等追加端點於此 SHALL NOT 有不同的世代語義——同一件事在兩條路徑上得到相反的結果，會使「我的會話為什麼斷了」無法回答。

**非管理端的角色縮減同樣受本要求約束**：登入時依外部群組映射重算而使有效角色集有列被移除者，SHALL 於同一交易內推進世代並撤銷刷新憑證。本要求 SHALL NOT 被讀成「只有管理者的顯式動作才推進世代」。

本要求的動機是「管理面的權限判定以憑證所攜角色快照為準」這一既有事實：不使既簽憑證失效，被撤除 admin 的帳號在其存取憑證的剩餘壽命內仍以 admin 身分通過管理端判定，據以將自身角色改回——降權可被當事人自行復原。

#### Scenario: 撤除 admin 角色即失效既簽憑證

- **WHEN** admin 將某使用者的角色自 `admin` 替換為 `user`
- **THEN** 該使用者的憑證世代被推進、全部刷新憑證被撤銷；其在此之前簽出的存取憑證於下一次使用時 SHALL 被拒（世代不符），SHALL NOT 得以憑舊快照的 admin 身分再次變更角色

#### Scenario: 純追加角色不失效既簽憑證

- **WHEN** admin 將某使用者的角色自 `admin` 替換為 `admin` ＋ `user`（無任何角色被移除）
- **THEN** 憑證世代不推進、刷新憑證不被撤銷，該使用者的既有會話繼續有效

#### Scenario: 保留 admin 的角色變更同樣失效既簽憑證

- **WHEN** admin 將某使用者的角色自 `admin` ＋ `auditor` 替換為 `admin` ＋ `user`（新角色集仍含 admin，不觸發本地 admin 不變式的系統級鎖，但 `auditor` 被撤除）
- **THEN** 世代同樣被推進——本要求 SHALL NOT 僅覆蓋「移除 admin」那一條路徑

#### Scenario: 角色集未變動不推進世代

- **WHEN** admin 以與現行完全相同的角色集（順序不同亦視為相同）呼叫角色替換
- **THEN** 憑證世代不變、刷新憑證不被撤銷，該使用者的既有會話不受影響

#### Scenario: 角色變更不終斷進行中的協議會話

- **WHEN** 某使用者角色被變更時其有進行中的協議會話與唯讀訂閱
- **THEN** 該會話與訂閱不因角色變更而被終斷（角色縮減不等同「此帳號不應再有存取」；帳號停用、刪除、解除身分綁定才適用收線語義）

#### Scenario: 替換端點不動映射列

- **WHEN** admin 以某使用者的現行**有效**角色集（含由映射賦予者）呼叫角色替換
- **THEN** 沒有任何指派列的來源被改變、憑證世代不變；映射賦予的角色仍於下次登入依映射結果重算

#### Scenario: 登入時的映射縮減同樣推進世代

- **WHEN** 某使用者登入時依外部群組映射重算，其有效角色集有列被移除
- **THEN** 憑證世代於同一交易內被推進、刷新憑證被撤銷，其在其他裝置以舊憑證發出的下一個請求被拒

### Requirement: 使用者來源網段允許清單

每個使用者 SHALL 具備允許來源網段清單（`allowed_cidrs`），由超級管理者或持使用者管理權限點者（如身分管理員）於建立與更新使用者時設定。清單為空 SHALL 表示不限制來源。清單項目 SHALL 為 IPv4 或 IPv6 的 CIDR；裸位址 SHALL 視為 /32（IPv4）或 /128（IPv6）。每人項目上限為 32。

儲存前 SHALL 於伺服端驗證：任一項目無法解析 SHALL 整體拒絕（SHALL NOT 靜默丟棄不合法項目）；項目 SHALL 正規化（網段遮罩後的標準文字形式）並去重；超過上限 SHALL 拒絕。拒絕 SHALL 以 `VALIDATION_*` 機器碼回應（三語）。解析與比對 SHALL 使用系統唯一的來源位址與網段實作，SHALL NOT 另寫第二套解析。

**更新請求的欄位存在語義**：更新使用者時，`allowed_cidrs` 欄位**省略** SHALL 保留現值，JSON **`null`** SHALL 視同省略（保留現值），**空陣列** SHALL 清除為不限，非空陣列 SHALL 整體取代。既有形狀的更新請求（不帶該欄位）SHALL NOT 清空已設定的清單。建立使用者時省略 SHALL 表示不限。

**有效涵蓋狀態**：系統 SHALL 依清單的有效涵蓋（而非陣列是否為空）計算唯讀狀態並隨使用者回應回傳：不限（空）、等同不限（正規化後含 `0.0.0.0/0` 或 `::/0`，並指出放行的位址家族）、已限定。全域前綴 SHALL 允許儲存，但介面 SHALL 於表單與列表醒目警告「等同不限」，SHALL NOT 把含全域前綴的清單呈現為已受限。狀態 SHALL 由伺服端單一實作計算，介面 SHALL NOT 自行推算。

清單的變更 SHALL 沿使用者更新的欄位級審計差異記錄前後值（清單不是機密，SHALL NOT 遮罩）。使用者列表與回應 SHALL 以字串陣列呈現清單；列表 SHALL 以上述三態辨識使用者的來源限定狀態，不展開內容。

**清單判定端點**：系統 SHALL 提供 `POST /api/v1/users/source-policy/check`（與使用者管理同權限、純判定、不變更任何狀態），輸入清單草稿與選填的位址（省略即以本請求的來源判定），回覆逐項驗證結果與正規化清單、有效涵蓋狀態、判定所用的來源、以及該來源是否落入清單（清單非空而來源不可解析時為不落入，與強制點一致）。判定端點與強制點 SHALL 共用同一實作；前端 SHALL NOT 自行判定位址是否落入清單，只 SHALL 做格式層的就近提示，落入、正規化與狀態一律以端點回覆為準。前後端 SHALL 共用同一份測試向量（IPv6 縮寫與 zone、IPv4-mapped、遮罩正規化、裸位址補長、全域前綴、重複與上限、非法項），前端的格式提示 SHALL NOT 拒絕任何後端判為合法的向量。

管理介面 SHALL 於使用者表單提供多值輸入，格式與上限錯誤 SHALL 就近提示（三語）。**自鎖防呆**：管理者編輯自己的清單且儲存後其當前來源將不在清單內（以判定端點回覆為準）時，介面 SHALL 於儲存前就近警告，但 SHALL NOT 阻擋儲存（管理者可能刻意設定）；後端 SHALL NOT 以此理由拒絕。復原途徑 SHALL 於介面說明與營運文件載明：由另一位管理者修改清單；系統無其他管理者時，走營運文件所載的離線資料庫重設途徑（與 admin 密碼遺失的既有途徑相同），該途徑 SHALL 能清除清單，且文件 SHALL 載明它不經產品審計、由部署方變更管理留痕，產品側可見的痕跡為復原後的登入審計列與之後線上重設清單的欄位級差異。

**降版邊界**：本能力的資料庫變更以增量 migration 交付，其 Down 只還原結構、不保留亦不還原資料，僅供開發庫；生產環境的回退唯一手段為還原升級前備份（見升級程序）。Down 後再升級，所有使用者的清單為空（不限）。此邊界 SHALL 於營運文件載明，SHALL NOT 表述為可逆。

清單的強制點見 auth-session「登入來源位址限定」、「短效會話與活動刷新」與 connection-gating「簽發閘序」、「連線 token 兌換點授權與政策重查」；本要求只界定資料與管理面。

- **THEN** 回覆正規化清單 `["10.0.0.0/8", "2001:db8::1/128"]`、狀態為已限定、來源為 `10.9.9.9`（IPv4-mapped 已還原）且落入為真；端點未變更任何使用者

### Requirement: 主體種類與自動化主體的擁有者

使用者帳號 SHALL 帶主體種類（`human` 或 `agent`），預設 `human`，並 SHALL 於資料庫層以約束限制其值域。種類 SHALL 於建立時決定且 SHALL NOT 可經任何端點變更——兩個方向皆不可（human 不得轉 agent、agent 不得轉 human），否則「這個帳號受哪一套限制」會隨時間漂移而審計無從還原。

`kind=agent` 的帳號 SHALL 必填擁有者，擁有者 SHALL 為 `kind=human` 且啟用中的帳號；缺擁有者或指向不合格帳號的建立請求 SHALL 以可辨識機器碼拒絕。`kind=human` 的帳號 SHALL NOT 帶擁有者。

agent 主體 SHALL NOT 具備任何本地或外部登入能力：SHALL NOT 持有可用密碼、SHALL NOT 可經本地帳密、目錄服務或外部身分提供者登入、SHALL NOT 可註冊或驗證多因素、強制改密旗標 SHALL 恆為否。上述限制 SHALL 於服務層判定，SHALL NOT 僅依賴介面不提供入口。

自動化主體沿用同一使用者表，因此授權記錄、可視範圍與審核範圍 SHALL 以同一主體識別值綁定，SHALL NOT 另立平行主體表。

**自助建立**：系統 SHALL 提供一般使用者自助建立自己名下 agent 主體的端點，且該端點 SHALL NOT 與管理員的使用者管理端點共用路徑。是否開放 SHALL 由安全政策鍵決定（見本 capability 的自助建立政策鍵群），出廠 SHALL 為關閉。政策關閉時該端點 SHALL 回 403 並帶可辨識機器碼，SHALL NOT 建立任何帳號。此政策鍵 SHALL 只約束建立：列出自己名下 agent 主體的端點 SHALL NOT 受其限制。

自助建立的呼叫者 SHALL 為 `kind=human` 且啟用中的帳號。所建主體的擁有者 SHALL 固定為呼叫者本人，取自其認證身分；請求本體即使帶擁有者欄位亦 SHALL NOT 被採信，SHALL NOT 有任何參數可指定他人為擁有者。自助建立 SHALL 必填主體名稱與用途說明；用途說明 SHALL 隨該次建立的審計列保存。

自助建立的主體 SHALL 受與管理員建立完全相同的限制——不可登入、無可用密碼、角色守衛、不得成為審核者、建立審計與主體完整性登記列同交易——自助路徑 SHALL NOT 提供任何放寬上述限制的參數。

每位擁有者名下現存的 agent 主體數 SHALL 受安全政策鍵上限約束；達上限時自助建立 SHALL 回 403 並帶可辨識機器碼，SHALL NOT 建立帳號。計數 SHALL 以資料庫現查並於建立交易內判定，SHALL NOT 依賴行程記憶體。上限調小 SHALL NOT 追溯影響既有主體：超出上限者維持可用，僅不得再新建。管理員經使用者管理端點建立 agent 主體 SHALL NOT 受本上限約束。

agent 主體 SHALL NOT 得使用自助建立端點——自動化主體不得建立自動化主體。此判定 SHALL 由既有的 agent 路由範圍限縮承擔：該端點 SHALL NOT 列入 agent 允許清單。

自助建立的審計列 SHALL 可與管理員建立區分：其詳情 SHALL 標示來源為自助。系統 SHALL 提供呼叫者列出自己名下 agent 主體的端點，其結果 SHALL 只含該呼叫者擁有的主體；該端點 SHALL 對任何啟用中的 human 呼叫者可用，不論自助建立政策鍵為開或關——負責人對名下既有主體的責任不隨建立入口關閉而消失。該清單回應 SHALL 附帶一個布林值，指出自助建立目前是否開放。管理員使用者清單的預設行為 SHALL NOT 因自助建立而改變——預設仍只回 `kind=human`。

- **THEN** 請求被拒，無帳號被建立

- **THEN** 登入被拒，且 SHALL NOT 因此產生可用的會話憑證或待驗證的中繼憑證

#### Scenario: 自動化主體不可持有密碼路徑

- **WHEN** 自助建立政策鍵為關閉，啟用中的一般使用者呼叫名下 agent 清單端點
- **THEN** 回 200 與其本人名下的主體清單、計數與上限，並以布林值指出自助建立未開放；清單 SHALL NOT 含他人擁有的主體

#### Scenario: 政策開啟時建立成功且擁有者為本人

- **WHEN** 自助建立政策鍵為開啟，啟用中的一般使用者提交名稱與用途說明，並於請求本體帶入指向他人的擁有者欄位
- **THEN** 主體建立成功，其種類為 `agent`、擁有者為呼叫者本人（請求帶的擁有者欄位不生效）、無可用密碼且不可登入；建立審計列標示來源為自助並含用途說明；主體完整性登記涵蓋該列

- **THEN** 回 403 並帶可辨識機器碼，無帳號被建立；既有主體不受影響

#### Scenario: 自動化主體不得建立自動化主體

- **WHEN** 以 agent 憑證呼叫自助建立端點
- **THEN** 請求被拒（該端點不在 agent 允許清單內），無帳號被建立

#### Scenario: 自助建立不改變管理員清單預設

- **WHEN** 一般使用者自助建立 agent 主體後，管理員以預設參數讀取使用者清單
- **THEN** 該 agent 主體不出現於結果；呼叫者以自身的名下清單端點讀取時可見，且該端點只回其本人擁有的主體

### Requirement: 自動化主體的角色守衛

agent 主體 SHALL NOT 被指派 admin、auditor 或 approver 角色，亦 SHALL NOT 被指定為任何審核範圍的審核者。此判定 SHALL 於角色寫入的每一條路徑生效——替換管理者指派集、冪等追加單一角色、釘住映射角色，以及登入時依外部群組映射重算——SHALL NOT 只在其中一條路徑設防。違反 SHALL 以可辨識機器碼拒絕該次指派，SHALL NOT 靜默忽略。

agent 主體的有效角色集 SHALL 恆為無特權角色。既有的角色指派審計、憑證世代推進與完整性鏈語義 SHALL NOT 因本要求改變。

此判定 SHALL 依角色的能力類別，而非角色名稱：任何含管理、稽核或審核類權限點的角色（含自訂角色與新的內建管理範本），以及超級管理者、稽核員、審核者內建身分，SHALL NOT 成為 agent 主體的有效角色。經使用者群組取得角色的路徑同樣受此約束：agent 主體 SHALL NOT 被加入帶上述角色指派的群組，且已有 agent 成員的群組 SHALL NOT 新增上述角色指派；違反時整筆拒絕，群組成員與指派皆不變。

#### Scenario: 指派特權角色被拒

- **WHEN** 管理員把 admin 或 auditor 角色指派給 agent 主體
- **THEN** 請求被拒並帶可辨識機器碼，該主體的角色集不變

#### Scenario: 冪等追加路徑同樣受守衛

- **WHEN** 管理員經冪等追加端點對 agent 主體追加 approver 角色
- **THEN** 請求被拒；兩條寫入路徑的判定結果一致

#### Scenario: 一般角色可指派

- **WHEN** 管理員把無特權角色指派給 agent 主體
- **THEN** 指派成功，並留既有格式的角色指派審計列

#### Scenario: 不得成為審核者

- **WHEN** 管理員把某個審核範圍的審核者設為 agent 主體
- **THEN** 請求被拒，該審核範圍不變

#### Scenario: 含管理類權限的自訂角色被拒

- **WHEN** 持指派能力者把一個含資產管理權限點、名稱不屬於任何內建角色的自訂角色指派給 agent 主體
- **THEN** 請求被拒，該主體的角色集不變

#### Scenario: 經群組取得管理類角色被拒

- **WHEN** 持指派能力者把 agent 主體加入帶管理類角色指派的使用者群組，或對已有 agent 成員的群組新增管理類角色指派
- **THEN** 整筆被拒，群組成員與群組的角色指派均不變

### Requirement: 自動化主體的未處置事件旗標與發證閘

agent 主體 SHALL 帶「有未處置熔斷事件」的時刻旗標（未設即為無）。旗標非空時，該主體 SHALL NOT 得發放新的 agent token，請求 SHALL 回 409 並帶可辨識機器碼——重發 token SHALL NOT 成為繞過未處置事件的途徑。

旗標 SHALL 掛在主體上而非個別 token 上：撤銷或重建 token SHALL NOT 清除旗標。清除 SHALL 為顯式的處置動作，SHALL NOT 隨時間自動失效。本要求只定義旗標語義與發證閘；寫入旗標的偵測機制與清除該旗標的處置端點由後續變更定義。

發放與撤銷 agent token SHALL 限於管理員或該主體的擁有者，並 SHALL 留審計（含 token 名稱、到期時刻與操作者），審計內容 SHALL NOT 含明文或其雜湊。

#### Scenario: 有未處置事件時不得發新 token

- **WHEN** 某 agent 主體的未處置事件旗標非空，管理員為其建立新 token
- **THEN** 回 409 並帶可辨識機器碼，無 token 被建立

#### Scenario: 撤銷既有 token 不清除旗標

- **WHEN** 旗標非空的 agent 主體其全部既有 token 被撤銷後再次請求發證
- **THEN** 仍回 409；旗標維持非空

#### Scenario: 擁有者可發證與撤銷

- **WHEN** agent 主體的擁有者（非管理員）為該主體建立或撤銷 token
- **THEN** 操作成功並留審計；其他一般使用者對同一主體的相同操作被拒

#### Scenario: 審計不含憑證材料

- **WHEN** 檢視 token 建立與撤銷的審計列
- **THEN** 可見主體、token 名稱、到期時刻與操作者，SHALL NOT 見明文或其雜湊

### Requirement: 自動化主體自助建立政策鍵群

安全政策 SHALL 提供兩個自助建立政策鍵：`agent_self_create_enabled`（bool，出廠預設 `false`）決定一般使用者是否得自助建立自己名下的 agent 主體；`agent_self_create_max_per_owner`（int，出廠預設 3，值域 1 至 100）為每位擁有者名下現存 agent 主體數的上限。

兩鍵的設定 UI SHALL 由存取管控頁承載，並 SHALL 沿既有政策機制：政策值存於資料庫並於執行期生效、批次寫入為原子、非法值以可辨識機器碼拒絕、變更入審計。出廠值 SHALL 使升級後行為零變更——自助建立端點存在但一律拒絕。

`agent_self_create_max_per_owner` SHALL NOT 設下界：本鍵的危險方向是調大（配額放寬），調小只是更嚴格且狀態誠實，SHALL NOT 出現「介面上顯示開著而機制實質失效」的情形；0 SHALL 由既有的非零值域判定拒絕。

兩鍵 SHALL NOT 攜帶任何規範基準建議值：沒有一個基準對「自動化主體可否自助建立」與「每人可有幾個」給出建議值，兩者取決於部署方的管理形態。掛用假的建議值會使其被標示為基準要求並進入「套用本頁建議值」，違反政策鍵的合規標示誠實紀律。因此兩鍵 SHALL NOT 產生對任一生效政策組的判定，亦 SHALL NOT 計入偏離摘要與全系統偏離總數。

兩鍵的 label 與單位 SHALL 納入政策 i18n（三語）與鍵歸屬單一事實源，由既有完備性測試把關；鍵 SHALL 歸入單一設定域，SHALL NOT 落入母頁「其他」區塊。

#### Scenario: 出廠預設與行為零變更

- **WHEN** 既有部署升級後未調整任何政策
- **THEN** `agent_self_create_enabled` 讀出 `false`、`agent_self_create_max_per_owner` 讀出 3；自助建立端點一律拒絕，管理員建立 agent 主體的路徑行為不變

#### Scenario: 值域外的上限被拒

- **WHEN** 管理員把 `agent_self_create_max_per_owner` 設為 0 或大於 100 的值
- **THEN** 寫入被拒並帶可辨識機器碼，政策現值不變

#### Scenario: 政策變更入審計

- **WHEN** 管理員把 `agent_self_create_enabled` 由 `false` 改為 `true` 並儲存
- **THEN** 變更生效無須重啟，並留既有格式的政策變更審計列（含舊值與新值）

#### Scenario: 不計入合規偏離

- **WHEN** 檢視任一生效政策組的符合性判定與偏離摘要
- **THEN** 兩鍵不產生判定、不出現於偏離摘要，亦不計入全系統偏離總數

#### Scenario: 鍵歸屬單一設定域

- **WHEN** 檢視政策鍵的域歸屬
- **THEN** 兩鍵歸屬存取管控頁且不重複歸域，各設定域鍵集的聯集等於後端全鍵集

### Requirement: Agent 管理唯讀投影
系統 SHALL 在既有權限下提供種類 query 與本人自建政策資訊，SHALL NOT 擴張 agent token 路由權限或以 POST 探測政策。

#### Scenario: 管理者按種類查人員
- **WHEN** admin 查 GET /users?kind=human 或 kind=agent
- **THEN** 資料與 total 使用同一伺服器篩選，明示 kind 優先於 include_agents，未指定時保留原行為；未知種類回 400，非 admin 回 403

#### Scenario: 本人可取得自建政策與配額
- **WHEN** human 查 GET /my/agents
- **THEN** 依已認證 id 回 self_create 的 enabled、max_per_owner、current 與同值的布林旗標，不接受 client owner 參數
- **AND** 政策開或關皆回 200 與本人名下清單；受政策鍵限制的只有建立端點，清單範圍恆為呼叫者本人擁有的主體

### Requirement: 帳號 email 依主體種類區分

管理員經使用者管理端點建立帳號時，email 的要求 SHALL 依主體種類區分：

- `kind=human`（含省略種類）的建立請求 SHALL 帶 email，且 SHALL 為合法 email 格式；缺 email、空字串或格式不合法 SHALL 以 400 與可辨識機器碼拒絕，SHALL NOT 建立帳號。
- `kind=agent` 的建立請求 SHALL NOT 被要求 email。未帶 email 或帶空字串時 SHALL 以 NULL 儲存，SHALL NOT 以空字串儲存；多個無 email 的 agent 主體 SHALL 可並存。agent 帶非空 email 時 SHALL 驗證格式，不合法 SHALL 以 400 拒絕。
- 管理介面建立 agent 主體時實際送出的請求本體 SHALL 可被建立端點接受；前端送出的本體與後端驗收所用的請求本體 SHALL 取自同一份測試資料，任一側變動時另一側的測試 SHALL 失敗或以新形狀重新驗收。

管理介面編輯帳號時，email 的必填檢查 SHALL 依該帳號的主體種類：編輯 agent 主體時 email SHALL 可留空（留空不改動既有值），有填仍 SHALL 驗證格式；編輯 human 帳號時 email 維持必填。

#### Scenario: 管理介面原樣送出的 agent 建立請求成功

- **WHEN** 管理員以管理介面建立 agent 主體時送出的請求本體（名稱、負責人、角色、主體種類，不含 email）呼叫建立端點
- **THEN** 回 201，所建帳號種類為 `agent`，其 email 以 NULL 儲存

#### Scenario: 多個無 email 的 agent 並存

- **WHEN** 連續建立兩個不帶 email 的 agent 主體（其中一個帶空字串 email）
- **THEN** 兩者皆建立成功，email 皆為 NULL，唯一性約束不拒絕

#### Scenario: human 仍須帶合法 email

- **WHEN** 建立 human 帳號（省略種類、顯式 `human` 或 email 為空字串）而未帶有效 email
- **THEN** 回 400 並帶可辨識機器碼，無帳號被建立；同一請求補上合法 email 即建立成功

#### Scenario: agent 帶不合法 email 被拒

- **WHEN** 建立 agent 主體並帶格式不合法的 email
- **THEN** 回 400 並帶可辨識機器碼，無帳號被建立

#### Scenario: 前端送出本體變動時契約測試失敗

- **WHEN** 管理介面建立 agent 時送出的請求本體與共用測試資料不一致
- **THEN** 前端契約測試失敗，直到共用測試資料同步；共用測試資料更新後，後端以新形狀重新驗收建立結果

#### Scenario: 編輯無 email 的 agent 可送出

- **WHEN** 管理員在管理介面編輯一個 email 為 NULL 的 agent 主體，只修改全名後送出
- **THEN** 更新請求送出且 email 維持不變；同樣情境換成 email 為 NULL 的 human 帳號時，介面以 email 必填擋下送出

### Requirement: 目前使用者資訊附帶 agent 入口資格

登入成功回應中的使用者資訊與目前使用者資訊端點（`GET /auth/me`）SHALL 附帶兩個布林欄位：`owns_agents`（呼叫者名下至少有一個未刪除的 agent 主體）與 `can_self_create_agent`（自行建立 agent 的安全政策鍵目前為開啟）。兩欄 SHALL 在每次登入與每次呼叫目前使用者資訊端點時由資料庫現算，其值 SHALL 與名下 agent 清單端點回報的自建狀態及名下主體計數同源，SHALL NOT 依角色而異。

兩欄僅供介面決定入口顯示；計算失敗時兩欄 SHALL 為 `false`，SHALL NOT 使登入或目前使用者資訊端點失敗。名下 agent 清單、自助建立與鑰匙管理端點 SHALL 維持各自的授權判定，SHALL NOT 依這兩欄放行。

#### Scenario: 名下沒有 agent 且政策關閉

- **WHEN** 名下沒有 agent 主體的 human 帳號在自行建立政策關閉時登入並讀取目前使用者資訊
- **THEN** 登入回應與目前使用者資訊的 `owns_agents`、`can_self_create_agent` 皆為 `false`

#### Scenario: 名下有 agent，不論角色

- **WHEN** 名下有一個 agent 主體的帳號（含具系統管理者角色者）登入並讀取目前使用者資訊
- **THEN** 兩處的 `owns_agents` 皆為 `true`；該 agent 被刪除後再次讀取時為 `false`

#### Scenario: 政策開啟

- **WHEN** 自行建立政策開啟時，名下沒有 agent 主體的帳號登入並讀取目前使用者資訊
- **THEN** 兩處的 `can_self_create_agent` 皆為 `true`，`owns_agents` 為 `false`

### Requirement: 帳號刪除的外部身分處置與留痕
刪除帳號時，系統 SHALL 在與軟刪除同一個交易內作廢該帳號的全部外部身分綁定；交易失敗時帳號與綁定 SHALL 皆維持原狀。刪除完成後，SHALL NOT 留下任何指向已刪帳號的有效綁定。

刪除帳號的審計列 SHALL 帶被刪帳號的帳號名稱與本次作廢的外部身分綁定數；帳號名稱 SHALL 取自被刪除的那一筆帳號記錄，SHALL NOT 依賴刪除後另行查詢。

刪除不等於封鎖：經外部身分或目錄服務登入的人，在帳號刪除後若再次登入，系統可能依其登入方式重新建立帳號（規則見 `oidc-auth`「已刪除帳號的外部身分綁定」）。管理介面的刪除確認 SHALL 依帳號類型如實說明刪除後的結果，且 SHALL 引導替代操作：兩步驟驗證綁錯時改用停用兩步驟驗證；要阻止此人登入時改用停用帳號，或在外部身分提供者、目錄服務端停用此人。確認文案 SHALL 只描述系統實際會發生的事：

- 未綁定外部身分的本地帳號：刪除無法復原。
- 已綁定外部身分的帳號：刪除時一併解除綁定；之後此人再經該身分提供者登入時，允許自動建立帳號的登入方式會建立新帳號並依群組映射規則重新給予角色，原帳號直接指派的角色與授權不會帶回；只允許預先綁定的登入方式則無法登入，需管理者重新建立帳號並綁定。
- 目錄服務帳號：之後此人再以目錄帳號登入時，系統會建立新帳號並依群組映射規則重新給予角色，原帳號直接指派的角色與授權不會帶回。

#### Scenario: 刪除帳號同時作廢外部身分綁定
- **WHEN** admin 刪除一個綁有兩筆外部身分的帳號
- **THEN** 帳號被刪除，兩筆綁定在同一交易內作廢；之後以同一身分域與 subject 為其他帳號綁定時不回衝突

#### Scenario: 刪除失敗時綁定不變
- **WHEN** 刪除帳號因不變式（例如最後一個本地 admin）被拒
- **THEN** 帳號與其外部身分綁定皆維持原狀

#### Scenario: 刪除審計帶被刪帳號名稱
- **WHEN** admin 刪除帳號 `alice`（綁有一筆外部身分）
- **THEN** 該刪除操作的審計列帶出被刪帳號名稱 `alice` 與作廢綁定數 1，與操作者帳號分開記錄

#### Scenario: 外部身分帳號的刪除確認寫出後果與替代操作
- **WHEN** admin 對一個已綁定外部身分的帳號點選刪除
- **THEN** 確認框列出其綁定的身分提供者、說明刪除後再登入可能重新建立帳號或需重新綁定，並提示兩步驟驗證綁錯時改用停用兩步驟驗證、要阻止登入時改用停用帳號

#### Scenario: 本地帳號的刪除確認
- **WHEN** admin 對一個未綁定外部身分的本地帳號點選刪除
- **THEN** 確認框說明刪除無法復原，並提示停用兩步驟驗證與停用帳號兩種替代操作，不提及重新建立帳號

### Requirement: 角色指派的共用授權關卡

使用者直接指派（替換管理者指派集、冪等追加、建立帳號帶角色）、使用者群組的角色指派、以及使用者群組成員異動，SHALL 經同一個服務層授權關卡裁決；關卡 SHALL 在取得對象鎖之後，以交易內重讀的現值判定，SHALL NOT 採用處理器預查的結果。

關卡規則 SHALL 對所有路徑一致：
- 讓任何帳號取得或失去超級管理者或系統安全管理員內建角色的寫入，不論直接指派、外部映射或經使用者群組，只有超級管理者能執行：直接指派、映射規則與群組角色指派中被新增或移除的項目含這兩種角色時 SHALL 只限超級管理者；群組成員異動與刪除群組不改群組的角色集，SHALL 以群組目前帶的全部指派判定，群組帶這兩種角色時 SHALL 只限超級管理者。保護角色在寫入前後都不變、只增減其他角色時 SHALL NOT 要求超級管理者，不論對象是使用者或使用者群組，因為這種寫入不會讓任何人取得或失去保護身分。
- 權限集合含任一高風險權限點的自訂角色 SHALL 視為保護角色，適用上一項的全部規則。高風險權限點是能刪除證據、關閉或改道告警、放寬安全控制或管理金鑰的權限點：`recording:delete`、`systemalert:manage`、`alertrule:manage`、`notification_channel:manage`、`syslog:manage`、`securitypolicy:manage`、`policygroup:manage`、`key:manage`、`offsite:manage`。這個集合 SHALL 是系統安全管理員專屬權限點的子集；專屬權限點 SHALL 由內建範本推導（系統安全管理員範本持有、而超級管理者以外的其他內建範本都不持有的權限點），範本改動使任一高風險點不再專屬時 SHALL 由測試攔下。只含其餘專屬權限點（唯讀檢視、排程、清冊）或不含專屬權限點的自訂角色照一般角色規則。
- 其餘角色 SHALL 對持有「指派角色」權限點者放行，且 SHALL NOT 以指派者自身的其他權限或範圍作為上界；不持有者 SHALL 一律被拒。系統 SHALL NOT 提供只能發放部分角色或只能在部分範圍發放的設定。
- 節點範圍指派開放前，請求帶任何範圍或節點欄位、或範圍種類不是全域時，SHALL 整筆拒絕並回可辨識機器碼，SHALL NOT 改存為全域。
- 尚未開放的角色（新的內建管理範本與自訂角色）在開放前 SHALL 經所有指派入口被拒絕；可指派目標集合 SHALL 由系統組裝決定，SHALL NOT 是部署者或使用者可切換的設定。
- 最後本地超級管理者的保護 SHALL 照舊只計直接、全域、手動指派的超級管理者；經使用者群組取得的超級管理者 SHALL NOT 計入。

拒絕回應 SHALL 只帶可辨識機器碼，SHALL NOT 帶角色名稱或權限點名稱；被拒的規則 SHALL 以原因碼記入該次請求的審計列（只記原因碼，SHALL NOT 記角色名稱、權限點名稱或請求內容）。被拒絕的寫入 SHALL NOT 推進權限版本，也 SHALL NOT 產生成功審計或告警事件。

節點範圍指派開放後，整組替換使用者管理者指派集與整組替換使用者群組角色指派兩個入口 SHALL 接受逐角色的節點範圍，關卡對範圍的裁決 SHALL 依下列規則：
- 持有「指派角色」權限點者 SHALL 能把可限定節點的角色以任意節點範圍發放；SHALL NOT 比對指派者自身持有的範圍或節點，也 SHALL NOT 要求指派者具備所發角色的任何權限點。系統 SHALL NOT 提供只能在部分節點發放、或只能發放部分角色的權限點、欄位或端點；指派角色權限點 SHALL 只能經全域指派持有。
- 角色可限定節點，若且唯若其權限集合不含任何只能全域生效的權限點（含模型預留範圍、尚未實作範圍過濾者）。不能限定節點的角色以節點範圍指派時，SHALL 整筆拒絕並回可辨識機器碼。
- 可限定節點的角色若不含任何已實作範圍過濾的權限點，其節點範圍不會生效；以節點範圍指派這類角色時 SHALL 照常寫入，SHALL NOT 因此拒絕。內建角色只在全域指派時產生能力；可限定節點的內建角色（一般使用者、審核者）以節點範圍持有時不產生任何能力，其範圍同樣不會生效，以節點範圍指派時 SHALL 照常寫入，SHALL NOT 因此拒絕。寫入成功的回應 SHALL 列出寫入後以節點範圍持有、且範圍不會生效的全部角色（含本次未改動範圍者），每個角色 SHALL 附範圍不會生效的原因（權限不受節點限制，或內建角色只在全域指派時生效），供畫面提示範圍不會生效；沒有這類角色時，回應 SHALL NOT 帶此欄，因此只有全域指派的對象，寫入回應與開放前同形。能否限定節點與範圍是否生效 SHALL 由同一個伺服器判定得出，畫面 SHALL NOT 自行推算。
- 節點範圍為空，或含不存在、已刪除的節點時，SHALL 整筆拒絕並回可辨識機器碼；不存在與已刪除 SHALL 同形，回應 SHALL NOT 帶節點名稱。系統 SHALL NOT 略過無效節點後儲存其餘節點，也 SHALL NOT 改存為全域。
- 冪等追加、建立帳號帶角色與釘住映射角色三個入口 SHALL 仍只接受全域；請求帶任何範圍或節點欄位時，SHALL 以範圍不支援的機器碼整筆拒絕。冪等追加一個已以節點範圍持有的角色 SHALL NOT 改變其範圍。
- 對象可寫、保護目標與指派能力的判定 SHALL 先於範圍判定。對 agent 主體，或對含 agent 成員的使用者群組寫入節點範圍的角色指派，SHALL 整筆被拒；之後的群組成員異動不受此限。

#### Scenario: 非超管指派保護角色被拒

- **WHEN** 持指派能力但非超級管理者的主體，經替換、追加或建立帳號帶角色，把超級管理者或系統安全管理員角色給任何使用者
- **THEN** 每條路徑皆被拒並回同一個可辨識機器碼，對象的角色不變

#### Scenario: 與系統安全管理員能力等價的自訂角色同受保護

- **WHEN** 持指派能力但非超級管理者的主體，經替換、追加、建立帳號帶角色、群組角色指派或群組成員異動，把含高風險權限點的自訂角色給自己或他人
- **THEN** 每條路徑皆被拒並回與保護角色相同的可辨識機器碼，對象的角色與群組不變；超級管理者執行同樣的操作成功；只含其餘專屬權限點或不含專屬權限點的自訂角色，非超級管理者照常可指派

#### Scenario: 移除保護角色同樣受限

- **WHEN** 持指派能力但非超級管理者的主體替換某使用者的角色集，使原有的系統安全管理員角色被移除
- **THEN** 請求被拒，因為被移除的項目含保護角色

#### Scenario: 保護角色不變時增減其他角色不需超管

- **WHEN** 持指派能力但非超級管理者的主體，對持有系統安全管理員角色的使用者替換角色集或追加角色，寫入前後系統安全管理員角色都在，只增減其他角色
- **THEN** 寫入成功；若同一請求也移除或換掉系統安全管理員角色，則整筆被拒

#### Scenario: 經群組取得或失去保護角色同樣限超管

- **WHEN** 持指派能力但非超級管理者的主體，把超級管理者或系統安全管理員角色指派給使用者群組、把群組既有的這類指派移除或換掉、把使用者加入或移出帶這類指派的群組、或刪除帶這類指派的群組
- **THEN** 每條路徑皆被拒並回與直接指派相同的可辨識機器碼，群組的指派與成員不變；超級管理者執行同樣的操作成功（系統安全管理員角色開放指派前，經群組新增此指派仍一律被拒）

#### Scenario: 群組路徑保護角色不變時不需超管

- **WHEN** 持指派能力但非超級管理者的主體，對帶系統安全管理員指派的群組替換角色指派，寫入前後該指派都在、只增減其他角色；或對成員含超級管理者帳號、但不帶保護角色指派的群組增減一般角色或增減成員
- **THEN** 寫入成功

#### Scenario: 不比對指派者自身權限

- **WHEN** 只持指派能力、本身沒有任何資產管理權限的主體，把含資產管理權限的角色指派給他人
- **THEN** 指派成功

#### Scenario: 勾選指派能力的自訂角色與身分管理員一致

- **WHEN** 一個持有指派能力的自訂角色主體，與一個身分管理員主體，分別對同一類目標執行同一組指派
- **THEN** 兩者的放行與拒絕結果逐項相同

#### Scenario: 不持指派能力者被拒

- **WHEN** 持使用者管理能力但不持指派能力的主體指派任何角色
- **THEN** 請求被拒，對象的角色不變

#### Scenario: 節點範圍請求被拒

- **WHEN** 指派請求帶節點清單或空的節點範圍，而節點範圍為空、所指派的角色不能限定節點，或經只接受全域的入口送出
- **THEN** 整筆被拒，沒有任何指派以全域或節點範圍寫入

#### Scenario: 超級管理者可指派保護角色

- **WHEN** 超級管理者經替換、追加或建立帳號帶角色，指派超級管理者角色
- **THEN** 指派成功；系統安全管理員角色在開放前經這些入口仍一律被拒，不因操作者是超級管理者而例外

#### Scenario: 群組帶來的超級管理者不計入最後本地超管

- **WHEN** 系統只有一位直接手動指派的本地超級管理者，另一位使用者經群組取得超級管理者，超級管理者嘗試移除前者的直接指派
- **THEN** 請求被拒，帳號狀態不變

#### Scenario: 任意範圍發放不比對指派者自身範圍

- **WHEN** 一位只持指派能力、本身沒有任何節點範圍的身分管理員，與一位持指派能力且只在甲節點持有資產管理範圍的主體，分別把可限定節點的資產管理角色以乙節點範圍指派給他人
- **THEN** 兩次指派皆成功，指派以乙節點範圍寫入

#### Scenario: 只能全域生效的角色不能限定節點

- **WHEN** 持指派能力者把含稽核類權限點、或含使用者管理權限點的角色以節點範圍指派
- **THEN** 整筆被拒並回可辨識機器碼，對象的角色指派不變

#### Scenario: 權限不受節點限制的角色仍可以節點範圍指派

- **WHEN** 持指派能力者把權限集合為空的自訂角色以甲節點範圍指派給一位沒有其他節點範圍指派的他人
- **THEN** 指派以甲節點範圍寫入、沒有被拒，回應列出該角色為範圍不會生效的角色；同一請求若只含範圍會生效的角色，回應不帶此清單

#### Scenario: 未改動的範圍不會生效角色仍被列出

- **WHEN** 使用者以甲節點範圍持有權限集合為空的自訂角色，另持一個一般角色，操作者以只帶管理者指派集的請求移除該一般角色
- **THEN** 一般角色被移除，自訂角色仍為甲節點範圍，回應列出該自訂角色為範圍不會生效的角色

#### Scenario: 節點範圍的內建一般使用者角色如實標示不生效

- **WHEN** 持指派能力者把內建一般使用者角色以甲節點範圍指派給一位沒有其他角色指派的他人
- **THEN** 指派以甲節點範圍寫入、沒有被拒，回應列出該角色為範圍不會生效的角色，原因為內建角色只在全域指派時生效

#### Scenario: 含已刪除節點的範圍整筆被拒

- **WHEN** 指派請求的節點範圍含一個已刪除的節點與一個有效節點
- **THEN** 整筆被拒，回應與節點不存在時相同，沒有只以有效節點寫入的指派

#### Scenario: 沒有部分委派的入口

- **WHEN** 列舉權限點目錄與全部路由
- **THEN** 只有一個不帶參數、只能全域持有的指派角色權限點，沒有任何設定可發放角色子集或可發放節點的欄位或端點；把含此權限點的角色以節點範圍指派被拒

#### Scenario: agent 不能取得節點範圍指派

- **WHEN** 持指派能力者對 agent 主體，或對含 agent 成員的使用者群組，以節點範圍指派可限定節點的角色
- **THEN** 整筆被拒，指派與群組成員皆不變

#### Scenario: 只接受全域的入口拒絕範圍欄位

- **WHEN** 經冪等追加端點對使用者追加角色並在請求中帶節點清單
- **THEN** 請求以範圍不支援的機器碼被拒，該使用者的角色不變

### Requirement: 超級管理者與系統安全管理員帳號的身分控制權

目標帳號的內建身分 SHALL 以伺服器解析的有效指派判定，不論來自直接指派、使用者群組或外部映射。

非超級管理者 SHALL NOT 對超級管理者帳號執行下列操作：管理端設定密碼、停用多因素驗證（含管理端救援）、綁定外部身分、直接角色寫入（替換管理者指派集、追加單一角色、釘住映射角色）。違反 SHALL 以可辨識機器碼拒絕，帳號狀態不變。此保護 SHALL 置於服務邊界，所有對應入口共用；未列入的操作（例如解除外部身分綁定、編輯基本資料）照既有規則處理；啟用帳號另見下段。經使用者群組成員異動或群組角色指派而改變的角色由共用授權關卡裁決：會讓任何帳號取得或失去超級管理者或系統安全管理員角色的群組操作 SHALL 只限超級管理者；不帶這兩種角色指派的群組，其成員異動與一般角色的增減 SHALL NOT 因成員含超級管理者帳號而被擋。

停用帳號（含解除外部身分綁定並停用）與刪除帳號會讓該帳號的全部角色隨之失效，啟用已停用的帳號會讓該帳號重新取得全部角色，與取得或失去保護角色同一界線：目標帳號持有超級管理者或系統安全管理員身分（不論來源）時，這三項操作 SHALL 只限超級管理者執行。非超級管理者的請求 SHALL 以與上列操作相同的機器碼拒絕，帳號狀態、角色、外部身分綁定與憑證世代皆不變；拒絕 SHALL 記入該次請求的審計紀錄並帶拒絕原因，原因只寫類別，SHALL NOT 帶角色名稱。目標帳號不持這兩種身分時，停用、啟用與刪除照既有規則。解除登入鎖定只清除失敗計數與鎖定期限、不改變帳號的啟用狀態，不在此限。「啟用中且未外部化的 admin 帳號不得自一以上降為零」的規則 SHALL 照常適用，操作者是超級管理者也不例外。無操作者的系統路徑（例如閒置自動停用）不經此判定。這道判定 SHALL 在目標帳號的使用者級互斥內重讀其現行角色後再寫入狀態，凡改變該帳號有效角色集的寫入（含群組只新增角色）SHALL 持同一互斥，使判定與寫入之間不存在角色變動插隊；群組已先授出保護角色時，等待中的非超級管理者操作 SHALL 重驗並拒絕。

非超級管理者對系統安全管理員帳號執行管理端設定密碼、停用多因素驗證（含管理端救援）、綁定或解除外部身分綁定時，操作 SHALL 照常成功，且 SHALL 在同一交易寫入服務審計與一筆不可刪除的系統告警事件。審計或事件寫入失敗 SHALL 使該操作回滾。告警內容 SHALL 只含操作者、目標帳號識別與動作類別，SHALL NOT 含密碼、多因素秘密或外部身分的原始識別值。超級管理者執行同類操作 SHALL NOT 產生此告警。

#### Scenario: 非超管不能改超級管理者密碼

- **WHEN** 身分管理員對一個經使用者群組取得超級管理者的帳號設定新密碼
- **THEN** 請求被拒，密碼與憑證世代不變

#### Scenario: 非超管不能停用超級管理者的多因素驗證

- **WHEN** 身分管理員對超級管理者帳號執行管理端停用多因素驗證
- **THEN** 請求被拒，多因素設定不變

#### Scenario: 非超管不能為超級管理者綁定外部身分

- **WHEN** 身分管理員為超級管理者帳號綁定外部身分
- **THEN** 請求被拒，沒有新的外部身分綁定

#### Scenario: 非超管不能改超級管理者的角色

- **WHEN** 身分管理員對超級管理者帳號追加一般使用者角色
- **THEN** 請求被拒，該帳號的角色集不變

#### Scenario: 身分管理員對一般帳號的同類操作成功

- **WHEN** 身分管理員對一個非超級管理者帳號設定密碼、停用多因素驗證、綁定外部身分
- **THEN** 三項操作皆成功

#### Scenario: 非超管不能停用超級管理者帳號

- **WHEN** 系統另有其他啟用中的超級管理者，身分管理員停用一個經使用者群組取得超級管理者的帳號
- **THEN** 請求以帳號受保護的機器碼被拒，帳號維持啟用、憑證世代不變，該次請求的審計紀錄記為拒絕並帶拒絕原因

#### Scenario: 非超管不能刪除超級管理者或系統安全管理員帳號

- **WHEN** 身分管理員刪除一個超級管理者帳號，或刪除一個系統安全管理員帳號
- **THEN** 兩次請求皆被拒，帳號與其外部身分綁定都還在

#### Scenario: 非超管不能解除綁定並停用系統安全管理員帳號

- **WHEN** 身分管理員對系統安全管理員帳號執行解除外部身分綁定並停用
- **THEN** 請求被拒，綁定與啟用狀態不變，不產生系統告警事件

#### Scenario: 非超管不能重新啟用超級管理者或系統安全管理員帳號

- **WHEN** 一個超級管理者帳號與一個系統安全管理員帳號已被停用，身分管理員分別將其啟用
- **THEN** 兩次請求皆以帳號受保護的機器碼被拒，兩個帳號都維持停用，該次請求的審計紀錄記為拒絕並帶拒絕原因

#### Scenario: 超管可以重新啟用已停用的超級管理者

- **WHEN** 一個超級管理者帳號已被停用，另一位超級管理者將其啟用
- **THEN** 操作成功，帳號恢復啟用

#### Scenario: 超管可以停用或刪除另一位超級管理者

- **WHEN** 系統有兩位超級管理者，其中一位停用另一位，之後再將其刪除
- **THEN** 兩項操作皆成功

#### Scenario: 身分管理員停用與刪除一般帳號照常

- **WHEN** 身分管理員停用、重新啟用、再刪除一個不持超級管理者或系統安全管理員身分的帳號
- **THEN** 三項操作皆成功

#### Scenario: 最後一位超級管理者仍不可停用或刪除

- **WHEN** 系統只有一位啟用中的本地超級管理者，該超級管理者嘗試停用或刪除自己的帳號
- **THEN** 請求被拒，帳號狀態不變

#### Scenario: 系統安全管理員帳號的身分操作觸發告警

- **WHEN** 身分管理員對系統安全管理員帳號設定密碼
- **THEN** 操作成功，同一交易有服務審計與一筆系統告警事件，告警不含密碼

#### Scenario: 告警事件寫入失敗則回滾

- **WHEN** 身分管理員停用系統安全管理員帳號的多因素驗證，而系統告警事件寫入失敗
- **THEN** 多因素設定維持原狀，請求以錯誤結束

### Requirement: 授權變更的自我授權與管理類發放分類

每一筆經共用授權關卡放行的寫入，SHALL 在同一交易內比較寫入前後的授權摘要（有效角色指派與其範圍，以及經使用者群組帶來的授權規則）：直接指派與釘住比較被異動帳號；使用者群組的角色指派、成員異動、刪除與外部映射規則的寫入比較操作者本人，並另比較寫入前後新增的角色指派，用來判定管理類發放。

- 受影響主體是操作者本人（直接對象，或操作者是被異動群組的直接成員）時，SHALL 產生自我授權告警事件：有任何新增項為高分級（含同時有增有減的互換），只有移除項為低分級，兩者皆無則不產生。
- 受影響主體不是操作者本人、且新增的角色屬管理類時，SHALL 產生管理類發放告警事件，預設分級為中。管理類 SHALL 依角色權限集合是否含資產、授權規則、身分或系統設定任一群組的管理權限點判定，SHALL NOT 只看角色名稱；稽核群組內的管理權限點（例如告警管理）不使角色成為管理類，因此稽核員、一般使用者與只帶授權規則的群組不屬之。
- 同一寫入可同時產生兩類事件。命中者的審計列 SHALL 分別帶「自我授權」「管理類發放」標記；未命中者只寫一般審計。
- 告警事件、審計與資料變更 SHALL 同一交易提交；任一寫入失敗 SHALL 全部回滾。自我授權告警摘要 SHALL 列出寫入路徑與變更前後的角色名稱；管理類發放告警摘要 SHALL 列出寫入路徑、受發放對象、新增的角色名稱與範圍；兩者 SHALL NOT 含秘密。

節點範圍納入授權摘要時，範圍的新增項與移除項 SHALL 以涵蓋比較計算：變更後涵蓋而變更前未涵蓋的節點為新增項，變更前涵蓋而變更後未涵蓋的節點為移除項；全域涵蓋所有節點；涵蓋判定 SHALL 與管理範圍判定使用同一子樹定義，已刪除的節點不計。據此，對自己把指派範圍由一個節點改為不相涵蓋的另一個節點 SHALL 為高分級；由全域改為節點範圍、或縮小節點範圍 SHALL 為低分級；擴大自己的節點範圍 SHALL 為高分級。

對他人既有管理類角色的範圍出現新增項時，SHALL 視同對他人發放管理類角色，產生中分級的管理類發放事件；經使用者群組的角色指派擴大範圍時，事件 SHALL 與新增群組指派相同，以該群組為目標、不逐成員展開。只有移除項時 SHALL NOT 產生管理類發放事件，只寫一般審計。管理類發放告警摘要中的範圍 SHALL 以全域或節點識別碼與數量表示。

#### Scenario: 替自己追加角色為高分級

- **WHEN** 身分管理員替自己追加一個目前沒有的角色
- **THEN** 同一交易有標記自我授權的審計列與一筆高分級自我授權事件

#### Scenario: 移除自己的角色一定告警

- **WHEN** 持指派能力者移除自己的一個角色，或把自己移出帶角色指派的群組
- **THEN** 產生一筆低分級自我授權事件

#### Scenario: 對自己所屬群組新增指派

- **WHEN** 操作者對自己是直接成員的群組新增角色指派
- **THEN** 對操作者產生高分級自我授權事件；若該角色屬管理類，另產生一筆以該群組為目標的管理類發放事件，不逐成員展開，受影響成員由審計與群組成員關係查得

#### Scenario: 同樣操作施於他人不產生自我授權事件

- **WHEN** 持指派能力者把同一個非管理類角色指派給他人
- **THEN** 不產生自我授權事件，也不產生管理類發放事件，只有一般審計

#### Scenario: 對他人發放管理類角色

- **WHEN** 超級管理者或身分管理員把含資產管理權限點的角色經直接指派或群組指派給他人
- **THEN** 產生標記管理類發放的審計列與一筆中分級事件

#### Scenario: 加入一般群組不告警

- **WHEN** 把他人加入只帶授權規則、不帶任何角色指派的使用者群組
- **THEN** 不產生管理類發放事件

#### Scenario: 事件寫入失敗則指派回滾

- **WHEN** 一次觸發自我授權事件的角色替換，其事件寫入失敗
- **THEN** 角色集、權限版本與審計列均維持交易前狀態

#### Scenario: 自己的範圍互換為高分級

- **WHEN** 持指派能力者把自己的一筆資產管理指派由甲節點改為不在甲節點子樹內的乙節點
- **THEN** 同一交易有標記自我授權的審計列與一筆高分級自我授權事件

#### Scenario: 由全域改為節點範圍為低分級

- **WHEN** 持指派能力者把自己一筆全域的可限定節點角色改為只限甲節點
- **THEN** 產生一筆低分級自我授權事件

#### Scenario: 擴大他人管理類角色的範圍

- **WHEN** 持指派能力者把他人的資產管理指派由甲節點擴為甲、乙兩個節點
- **THEN** 產生標記管理類發放的審計列與一筆中分級事件

#### Scenario: 擴大群組管理類角色的範圍

- **WHEN** 不是群組 G 成員的持指派能力者，把 G 的資產管理指派由甲節點擴為甲、乙兩個節點
- **THEN** 產生一筆以 G 為目標的管理類發放事件，不逐成員展開

#### Scenario: 只縮小他人範圍不產生管理類發放

- **WHEN** 持指派能力者把他人的資產管理指派由甲、乙兩個節點縮為甲節點
- **THEN** 不產生管理類發放事件，只有一般審計

### Requirement: 有效能力的危險組合預覽

系統 SHALL 提供唯讀的預覽端點，輸入一筆提議中的角色定義修改、直接指派、使用者群組角色指派或群組成員異動，回傳受影響主體總數，以及每位列出主體的入口增減、變更後命中的危險組合、是否為操作者本人與這筆寫入將觸發的告警分類。呼叫者 SHALL 具備被預覽的那種寫入所需的能力。

危險組合 SHALL 依主體的有效能力類別計算，SHALL NOT 只看單一角色定義或角色名稱；涵蓋：授權規則管理與資產或憑證管理並存、系統安全設定與資產或授權規則管理並存、資產管理與連線授權並存、身分管理與系統安全設定並存、身分管理與任一業務角色或連線授權並存。持指派能力的主體本人 SHALL 被標示為可替自己取得超級管理者、系統安全管理員與含高風險權限點的自訂角色以外角色的人。

預覽 SHALL 唯讀：SHALL NOT 改變指派、群組成員、權限版本或其他業務資料，也 SHALL NOT 產生授權變更的審計標記或告警事件；系統對每個請求既有的請求紀錄照常保留。對應的寫入 SHALL NOT 以先完成預覽作為條件；危險組合只是提示，SHALL NOT 阻擋寫入。列出的主體 SHALL 限於操作者本人與變更後新命中危險組合者，並有數量上限；其餘只計入總數。

回應 SHALL 另附不受列出條件與數量上限影響的整筆彙總：這筆寫入將觸發的告警分類（含以使用者群組、映射規則或角色為目標者）、實際求值的主體數，以及已求值主體整體新增與失去的頁面入口。整筆彙總的分類 SHALL 與對應寫入使用同一判定；受影響主體為零時，以群組、映射規則或角色為目標的分類仍 SHALL 回報。頁面入口 SHALL 依介面導覽所用的同一份入口規則判定；依本人資格呈現的入口不列入增減。既有欄位的意義 SHALL 不變。

群組成員異動的預覽 SHALL 可接受與寫入相同的手動成員集合，由伺服器依寫入的來源規則求得變更後的成員，仍受映射支持的成員 SHALL 視為保留；加入的判定 SHALL 與寫入相同，把已經經映射加入的成員改列為手動成員也算加入。預覽 SHALL 另接受一筆外部群組映射規則變更作為輸入，呼叫者同樣 SHALL 具備該寫入所需的能力。外部群組映射規則變更的預覽 SHALL 以規則識別讀取既有規則，接受新的群組值、目標與啟用狀態或刪除；受影響者 SHALL 由伺服器依最近一次已知群組觀測與目前的映射支持求得，SHALL NOT 接受客戶端提供的主體清單，帶有主體清單的請求 SHALL 被拒絕。停用、刪除或修改既有規則時，變更後的狀態 SHALL 依寫入的保留規則求得：帳號仍有其他規則、其他來源或手動成員身分支持的角色與群組成員身分 SHALL 視為保留；對操作者本人的分類 SHALL 依變更前後的授權比較，SHALL NOT 只因操作者目前受該規則支持就回報減少。沒有實際變動的存檔 SHALL 回報不觸發任何分類。求值有數量上限時，操作者本人 SHALL 優先求值，回應 SHALL 分別標示總數、求值數與是否截斷。

預覽的輸入 SHALL 可帶與對應寫入相同形狀的節點範圍。以「範圍有交集」為成立條件的組合 SHALL 依實際範圍計算：授權規則管理與資產或憑證管理並存，須兩筆指派的範圍有交集；資產管理與連線授權並存，須主體經授權規則可連線的資產中至少一台落在其資產管理指派的範圍內。兩筆範圍有交集，指下列任一成立：任一方為全域而另一方非空；一方的某個節點落在另一方某個節點的子樹內；有一台未刪除的資產同時在兩方範圍內，一台資產掛在多個節點時，任一掛載節點在範圍內即算在範圍內；對憑證管理那一方，另有一份憑證依其歸屬同時在兩方範圍內。子樹、資產與憑證是否在範圍內的判定 SHALL 與管理範圍判定使用同一定義。不以範圍為條件的組合照舊計算。

預覽的請求 SHALL 可另要求可管理資產台數；此項只對直接指派與使用者群組角色指派兩種輸入提供，其他輸入種類（含外部群組映射規則變更）帶此要求時 SHALL 不回此項，也 SHALL NOT 因此要求而拒絕請求，其餘輸入驗證照舊；未要求時，回應 SHALL 與不提供此項時同形。可管理資產 SHALL 與資產列表的管理範圍同一定義：具全量資產檢視身分（超級管理者、稽核員）的主體涵蓋全部未刪除資產；其他主體只計管理範圍判定實際認列為資產檢視來源的節點範圍指派、在其有效節點子樹內的未刪除資產，經全域指派持有的資產檢視權限點（例如內建一般使用者）SHALL NOT 計入，也 SHALL NOT 使台數成為全部資產。已刪除的範圍節點不計，同一台資產只計一次，SHALL NOT 計入只經授權規則可連線的資產；涵蓋判定 SHALL 與管理範圍判定使用同一子樹定義。寫入前、寫入後、逐角色與群組的台數 SHALL 都由對應的指派集合經同一管理範圍判定計算，SHALL NOT 以角色名稱、角色定義是否含資產檢視權限點或範圍是否會生效代替計算。
- 直接指派：SHALL 回該使用者寫入前與寫入後的可管理資產台數；並就請求後每個以節點範圍持有（管理者指派或經使用者群組）的角色，回管理者指派範圍中被判定認列者涵蓋的台數、同一角色經使用者群組另外涵蓋的台數，以及兩者合計；某筆節點範圍指派未被判定認列為資產檢視來源時（例如角色不含資產檢視權限點，或只以節點範圍持有的內建一般使用者角色），它不貢獻台數；以全系統持有的範圍不列台數。
- 使用者群組角色指派：SHALL 回該群組的角色指派在寫入前與寫入後涵蓋的資產台數，以該群組自己的指派集合經同一判定計算（群組帶全量資產檢視身分的角色時為全部未刪除資產），並就請求後每個以節點範圍持有的角色回其被判定認列的範圍涵蓋的台數。
- 台數 SHALL 只以數字回傳，SHALL NOT 附資產名稱、位址或識別碼；要求台數 SHALL NOT 改變預覽所需的能力或其他輸出。

#### Scenario: 跨角色組合依有效能力出現

- **WHEN** 預覽把含授權規則管理的角色加給一位已經由群組持有資產管理角色的使用者
- **THEN** 回應列出該使用者並標示授權規則管理與資產管理並存的組合

#### Scenario: 預覽不寫資料

- **WHEN** 呼叫預覽端點後比對資料庫與權限版本
- **THEN** 角色指派、群組成員與權限版本皆不變，也沒有授權變更的審計標記或告警事件

#### Scenario: 不預覽也能寫入

- **WHEN** 有權者直接送出一筆會命中危險組合的指派而未先呼叫預覽
- **THEN** 指派依共用關卡裁決，不因未預覽或命中組合而被拒

#### Scenario: 無權者不能預覽

- **WHEN** 不持指派能力的主體預覽一筆直接指派
- **THEN** 請求被拒，不回傳任何主體資料

#### Scenario: 沒有組合的管理類發放出現在整筆彙總

- **WHEN** 預覽把含資產管理能力的角色直接指派給一位沒有其他管理或連線能力的他人
- **THEN** 列出的主體為空，整筆彙總標示將產生管理類發放並列出新增的頁面入口，與實際寫入產生的事件相同

#### Scenario: 空群組的管理類發放

- **WHEN** 預覽為一個沒有成員的群組新增管理類角色
- **THEN** 受影響主體總數為零，整筆彙總仍標示將產生以該群組為目標的管理類發放

#### Scenario: 手動成員預覽保留映射成員

- **WHEN** 群組有一位手動成員與一位經映射加入且就是操作者本人的成員，以清空手動成員的集合預覽
- **THEN** 只有手動成員被算為移出，操作者本人不被回報為失去授權

#### Scenario: 映射規則無變動存檔不觸發分類

- **WHEN** 以一條既有規則的識別與完全相同的新值預覽
- **THEN** 整筆彙總沒有任何分類，受影響總數為零

#### Scenario: 停用最後一份支持的規則預報收回

- **WHEN** 操作者只經某條規則取得一個使用者群組的成員身分，沒有其他規則支持，也不是該群組的手動成員，以該規則識別與停用預覽
- **THEN** 整筆彙總標示對操作者本人的授權減少，受影響者含目前受該規則支持的帳號，與實際停用後產生的自我授權事件相同

#### Scenario: 仍有其他支持時停用不報減少

- **WHEN** 操作者同時經兩條規則取得同一個使用者群組的成員身分，或另是該群組的手動成員，以其中一條規則的識別與停用預覽
- **THEN** 受影響者含操作者，整筆彙總沒有對操作者本人的分類；實際停用後操作者仍是該群組成員，也沒有自我授權事件

#### Scenario: 映射成員改列手動仍算加入

- **WHEN** 一個帶管理類角色的群組有一位經映射加入的他人，以把該成員列入手動成員的集合預覽
- **THEN** 群組的有效成員不變，整筆彙總仍標示將產生以該群組為目標的管理類發放，與實際寫入相同

#### Scenario: 映射規則預覽拒絕主體清單

- **WHEN** 映射規則變更的預覽請求另外夾帶一份主體清單
- **THEN** 請求被拒，不回傳任何主體資料

#### Scenario: 超量時本人優先求值

- **WHEN** 一條規則的受影響帳號超過求值上限，而操作者本人排在最後
- **THEN** 操作者本人仍被求值並列出，回應的總數為全部受影響帳號數，求值數不超過上限且標示截斷

#### Scenario: 範圍不相交不列組合

- **WHEN** 預覽把甲節點範圍的授權規則管理角色加給一位只在乙節點持有資產管理指派的使用者，甲、乙互不在對方子樹內，也沒有任何資產同時掛在兩者之下
- **THEN** 回應不列授權規則管理與資產管理並存的組合

#### Scenario: 範圍相交列出組合

- **WHEN** 同一預覽改為把授權規則管理角色限在乙節點的父節點
- **THEN** 回應列出該使用者並標示授權規則管理與資產管理並存的組合

#### Scenario: 同掛兩個節點的資產使範圍相交

- **WHEN** 甲、乙互不在對方子樹內，有一台資產同時掛在甲、乙之下，預覽把甲節點範圍的授權規則管理角色加給一位只在乙節點持有資產管理指派的使用者
- **THEN** 回應列出該使用者並標示授權規則管理與資產管理並存的組合

#### Scenario: 管理範圍外的連線授權不構成組合

- **WHEN** 預覽把甲節點範圍的資產管理角色加給一位只能連線乙節點下資產的使用者
- **THEN** 回應不列資產管理與連線授權並存的組合；若改為乙節點範圍則列出

#### Scenario: 預覽回可管理資產前後台數

- **WHEN** 預覽把使用者的資產管理角色由甲節點改為甲、乙兩個節點並要求台數，乙節點子樹內有三台不在甲節點子樹內的資產
- **THEN** 回應的寫入後台數比寫入前多三，並附該角色的管理者指派台數、經群組另外涵蓋的台數與合計

#### Scenario: 同一台資產只計一次

- **WHEN** 一台資產同時掛在甲、乙兩個節點下，預覽以甲、乙兩個節點為範圍並要求台數
- **THEN** 該資產在合計中只計一次

#### Scenario: 全域的資產檢視不使台數成為全部

- **WHEN** 一位持內建一般使用者角色（全域資產檢視）、沒有其他指派的使用者，預覽為其加入甲節點範圍的資產管理角色並要求台數
- **THEN** 寫入前台數為零，寫入後台數等於甲節點子樹內的資產數，不是全部資產

#### Scenario: 全量檢視身分涵蓋全部資產

- **WHEN** 預覽一位稽核員的直接指派變更並要求台數
- **THEN** 寫入前與寫入後的可管理資產台數皆為全部未刪除資產數

#### Scenario: 未要求台數時回應不變

- **WHEN** 預覽請求沒有要求台數
- **THEN** 回應不含任何台數欄位，其餘欄位與同一輸入要求台數時相同

#### Scenario: 台數不帶資產識別

- **WHEN** 具指派角色與使用者管理能力、本身沒有任何資產權限的主體預覽一筆節點範圍的直接指派並要求台數
- **THEN** 回應只含台數，不含任何資產名稱、位址或識別碼

#### Scenario: 只以節點範圍持有內建一般使用者時台數為零

- **WHEN** 預覽為一位沒有其他指派的使用者以甲節點範圍加入內建一般使用者角色並要求台數
- **THEN** 寫入後的可管理資產台數與該角色的三個台數皆為零，與該使用者寫入後在資產列表的管理範圍相同

#### Scenario: 其他輸入種類要求台數不回也不拒絕

- **WHEN** 外部群組映射規則變更的預覽請求另要求可管理資產台數
- **THEN** 回應不含台數，其餘結果與未要求時相同；同一請求另夾帶主體清單時仍被拒絕

### Requirement: 使用者詳情頁

管理介面 SHALL 提供單一使用者的詳情頁，分為基本資料與角色與範圍兩個分頁。進入詳情頁 SHALL 需要與使用者列表相同的入口能力；不具此能力者不論由列表或直接網址進入，SHALL 被拒絕進入。使用者列表 SHALL 由使用者名稱與分配角色操作連到詳情頁的對應分頁。詳情頁 SHALL 沿用使用者管理既有的入口，SHALL NOT 新增入口。

除上述兩個分頁外，詳情頁 SHALL 另提供第三個分頁「權限一覽」，唯讀呈現該使用者的有效權限、各自的範圍與來源，以及其可連線的資產；進入條件與上述兩個分頁相同，SHALL NOT 因權限一覽而新增入口。

基本資料分頁的修改與帳號動作（設定密碼、停用多因素驗證、外部身分綁定與解除、解除綁定並停用、解鎖、停用、啟用、刪除）SHALL 與列表頁使用同一實作與同一組端點。使用者單筆讀取 SHALL 對目前操作者回傳設定密碼、停用多因素驗證、綁定外部身分、解除外部身分綁定、解除綁定並停用、停用、啟用與刪除各自的保護分類：沒有保護身分的限制、照常執行且會通知安全人員、只有超級管理者能執行；此分類 SHALL 以伺服器解析的有效指派判定目標身分（不論來自直接指派、使用者群組或外部映射），並 SHALL 與帳號身分控制權的裁決取自同一判定。保護分類 SHALL NOT 被當作該動作可執行的保證：主體種類、外部帳號、多因素驗證是否啟用、帳號狀態與可用登入途徑等既有條件 SHALL 照舊決定動作是否出現或可按，保護分類只在既有條件允許的動作上再疊加一層。基本資料分頁 SHALL 依此呈現：

- 只有超級管理者能執行的操作 SHALL 停用，並說明原因是目標帳號持有的身分；
- 會通知安全人員的操作 SHALL 維持既有狀態，並在執行前提示操作後會通知安全人員；
- 停用、啟用、刪除與解除綁定並停用的限制 SHALL 與設定密碼、停用多因素驗證、綁定外部身分的限制分開呈現：目標持有系統安全管理員身分時，前者停用、後者可用並提示通知。

解鎖與基本資料編輯 SHALL 照既有規則呈現，解鎖 SHALL NOT 被當作啟用。列表頁沒有保護分類時，每個動作 SHALL 維持原有的呈現。畫面狀態只供呈現，伺服器 SHALL 仍以其身分控制規則與既有限制裁決。

#### Scenario: 無使用者入口能力不能進入

- **WHEN** 不具使用者列表入口能力的已登入者直接開啟某使用者的詳情頁網址
- **THEN** 進入被拒絕，畫面不呈現該使用者的資料

#### Scenario: 超級管理者帳號的受限操作

- **WHEN** 非超級管理者的身分管理員開啟一位經使用者群組取得超級管理者、已啟用多因素驗證的本地帳號的基本資料分頁
- **THEN** 設定密碼、停用多因素驗證、綁定外部身分、停用、刪除與解除綁定並停用皆為停用並附說明，解除外部身分綁定照既有規則

#### Scenario: 系統安全管理員帳號的通知提示與生命週期限制

- **WHEN** 非超級管理者的身分管理員開啟一位已啟用多因素驗證的本地系統安全管理員帳號的基本資料分頁
- **THEN** 設定密碼、停用多因素驗證、綁定與解除外部身分綁定可用且執行前提示會通知安全人員，停用、刪除與解除綁定並停用為停用並附說明

#### Scenario: 已停用的受保護帳號不能由非超管啟用

- **WHEN** 非超級管理者的身分管理員開啟一位已停用、持有超級管理者身分的帳號
- **THEN** 啟用為停用並附說明，解鎖照既有規則呈現

#### Scenario: 超級管理者操作不受保護限制但既有條件照舊

- **WHEN** 超級管理者開啟另一位超級管理者帳號的基本資料分頁，該帳號是外部身分來源的帳號且未啟用多因素驗證
- **THEN** 各項動作沒有保護限制也不提示通知，但設定密碼依外部帳號規則停用、停用多因素驗證不出現；伺服器仍保有最後一位本地超級管理者的限制

#### Scenario: 列表頁維持原有呈現

- **WHEN** 列表頁顯示一個自動化主體帳號與一個外部人類帳號的帳號動作
- **THEN** 自動化主體不出現密碼與外部身分動作，外部帳號的設定密碼為停用，與改版前相同

#### Scenario: 權限一覽是第三個分頁

- **WHEN** 具使用者檢視能力者開啟某使用者的詳情頁並切到權限一覽
- **THEN** 頁面呈現基本資料、角色與範圍、權限一覽三個分頁，權限一覽的內容取自該使用者的權限一覽端點，側欄入口數不變

### Requirement: 角色與範圍分頁的三種來源

角色與範圍分頁 SHALL 分三區呈現使用者的角色來源：管理者指派的角色、來自使用者群組的角色、來自外部群組映射的角色。

- 管理者指派的角色 SHALL 可新增與移除；送出 SHALL 只帶管理者指派集，SHALL NOT 把映射或群組帶來的角色併入，請求本文 SHALL NOT 含任何範圍或節點欄位，節點範圍指派開放後本次編輯改動了範圍的角色依下段明示其範圍者除外。可分配的角色 SHALL 取自伺服器的角色列表；受保護的角色 SHALL 停用並說明只有超級管理者能指派，尚未開放指派的角色 SHALL 停用並說明。
- 來自使用者群組的角色 SHALL 唯讀，並 SHALL 提供前往該群組角色設定的連結；操作者無權讀取使用者群組時，該區 SHALL 說明無法列出，SHALL NOT 影響其他兩區。
- 來自映射的角色 SHALL 列出並提供釘住為管理者指派的操作；受保護角色的釘住在操作者不能指派時 SHALL 停用。該區 SHALL 分別說明兩種時效：停用或刪除規則、停用來源與修改規則的群組值或目標，於管理操作儲存時即收回該規則的支持，其他來源給的同一角色不受影響；外部來源的群組成員變動於該使用者下次成功登入時重算，並依重新驗證時限的現值、設為不設限，或檢視者無法讀取現值三種情形說明其上界。

分頁 SHALL 顯示儲存後新增與失去的頁面入口，取自伺服器預覽的整筆彙總，並說明一般管理能力不會自動帶來連線權、能連哪些主機由資產授權決定，超級管理者另依既有的保留身分。節點範圍指派開放前 SHALL NOT 提供節點或範圍選擇。伺服器拒絕時，畫面 SHALL 以該錯誤的機器碼訊息呈現，使用者的角色 SHALL 與直接呼叫端點的結果相同。

節點範圍指派開放後，分頁 SHALL 依下列規則呈現與送出管理者指派角色的節點範圍：
- 每個管理者指派的角色 SHALL 標示能否限定節點，判定 SHALL 取自伺服器，SHALL NOT 由畫面依角色名稱或權限推算。能限定節點的角色 SHALL 顯示其範圍：全系統，或所選節點的路徑與這些節點涵蓋的資產台數；不能限定節點的角色 SHALL 標示不需要選範圍，SHALL NOT 提供節點選擇。
- 能限定節點的角色 SHALL 可在全系統與指定節點之間切換；新加入的角色 SHALL 預設為全系統。指定節點時以節點樹選擇：樹 SHALL 提供依名稱搜尋，每個節點 SHALL 顯示其子樹（含子節點）內的資產台數；勾選一個節點 SHALL 表示其底下的子節點與日後新增的子節點一併納入，其子節點 SHALL 顯示為已涵蓋。
- 同一角色經使用者群組取得的範圍節點 SHALL 在樹上標示來自群組，且 SHALL NOT 因此不能再以管理者指派選取。樹的底部 SHALL 顯示管理者指派的節點數與其涵蓋台數、來自群組另外涵蓋的台數與合計台數。
- 「儲存後的變化」SHALL 另顯示這位使用者儲存前與儲存後的可管理資產台數，口徑與這位使用者在資產列表看到的管理範圍相同。上述台數 SHALL 由伺服器計算，多個節點涵蓋同一台資產時只計一次；畫面 SHALL NOT 以加總各節點台數代替。
- 送出時，本次改動了範圍的角色 SHALL 明示其範圍（全系統或節點清單）；範圍未改動的角色，以及新加入且維持全系統的角色，SHALL NOT 帶範圍欄位：前者保留現有範圍，後者依伺服器規則以全系統寫入。
- 對能指派角色的操作者，管理者指派或來自群組的指派含已不存在的節點時，該角色 SHALL 標示節點已不存在（SHALL NOT 顯示該節點的名稱），並說明那部分不生效、也不會變成全系統、其餘節點照常。管理者指派的角色 SHALL 提供「移除失效的節點」，只從本次編輯移除失效的節點，儲存後才寫入；移除後沒有剩下任何節點時，SHALL 提示至少選擇一個節點或改為全系統。
- 以節點範圍持有、但其角色目前不能限定節點的指派，SHALL 標示該角色含只能套用到全系統的權限、那部分在這個範圍內不生效，並 SHALL 仍可改為全系統或移除。
- 能限定節點、但節點範圍不會生效的角色，有兩種原因：權限集合不含任何已實作範圍過濾的權限點；或為只在全系統指派時生效的內建角色（一般使用者、審核者），以節點範圍持有時不產生任何權限。這類角色 SHALL 與其他能限定節點的角色一樣可切換全系統與指定節點、選擇節點並照常送出，畫面 SHALL NOT 因此停用選擇或儲存，也 SHALL NOT 只提供改為全系統與移除。這類角色以指定節點持有或在本次編輯選擇節點時，畫面 SHALL 依原因提示：前者提示這個角色的權限不受節點限制、範圍不會生效；後者提示內建角色只在指派到全系統時生效、限定節點後不會產生權限。是否不會生效與其原因 SHALL 取自伺服器，SHALL NOT 由畫面依角色名稱或權限推算；台數 SHALL 照伺服器計算的結果呈現，SHALL NOT 因範圍不會生效而由畫面改寫。
- 範圍含已不存在的節點、或角色目前不能限定節點的指派，在本次編輯沒有改動其範圍時 SHALL 照常保留，SHALL NOT 因此使其他角色的增減無法儲存。
- 節點的名稱與台數 SHALL 只對能指派角色的操作者呈現；其他能檢視此分頁的人 SHALL 只看到每個角色限定的節點數。
- 畫面狀態只供呈現；節點範圍的寫入 SHALL 仍以伺服器的共用指派關卡裁決，伺服器拒絕時 SHALL 以該錯誤的機器碼訊息呈現。

#### Scenario: 指派受保護角色被拒與端點一致

- **WHEN** 非超級管理者經此分頁送出包含系統安全管理員的管理者指派集（例如以過時畫面送出）
- **THEN** 畫面呈現與直接呼叫指派端點相同的拒絕機器碼，使用者的角色不變

#### Scenario: 指派一般角色成功並提示通知

- **WHEN** 身分管理員經此分頁為一位沒有其他危險組合的他人分配含資產管理能力的角色並確認儲存
- **THEN** 指派成功，儲存前的確認說明這次儲存會通知安全人員

#### Scenario: 儲存後的變化列出頁面入口

- **WHEN** 操作者為他人新增一個只含憑證秘密設定能力的自訂角色
- **THEN** 變化面板列出新增憑證庫頁面，與導覽列對同一組能力的判定相同

#### Scenario: 指派請求不帶範圍欄位

- **WHEN** 操作者在此分頁新增一個角色後儲存，該角色維持預設的全系統，且本次編輯沒有改動任何角色的範圍
- **THEN** 送出的請求本文只有管理者指派集一個欄位，沒有任何範圍或節點欄位

#### Scenario: 映射角色與釘住可操作

- **WHEN** 使用者持有一個只由外部群組映射賦予的稽核員角色，操作者在此分頁勾選釘住
- **THEN** 釘住送出成功，該角色顯示為已固定為管理者指派

#### Scenario: 映射時效分兩種說明

- **WHEN** 操作者檢視一位持有映射角色的使用者，且無法讀取重新驗證時限的現值
- **THEN** 該區說明停用、刪除或修改規則於儲存時收回該規則的支持，外部群組變動於下次登入重算，並以不帶數值的通則說明時限，不以出廠預設冒充現值

#### Scenario: 群組帶來的角色唯讀

- **WHEN** 使用者經某使用者群組取得角色
- **THEN** 該角色出現在來自群組區且不能在此移除，並有前往該群組角色設定的連結

#### Scenario: 不帶映射角色送出

- **WHEN** 使用者同時有管理者指派與映射賦予的角色，操作者移除一個管理者指派的角色後儲存
- **THEN** 送出的指派集只含剩餘的管理者指派角色，映射賦予的角色不受影響

#### Scenario: 以節點範圍指派可限定節點的角色

- **WHEN** 能指派角色的操作者為使用者新加入一個能限定節點的角色，切到指定節點並勾選甲節點後儲存
- **THEN** 送出的請求只為該角色帶甲節點，指派以甲節點範圍寫入，角色卡片顯示甲節點的路徑與其涵蓋的資產台數

#### Scenario: 新加入的角色預設為全系統

- **WHEN** 操作者為使用者新加入一個能限定節點的角色，未改動其範圍即儲存
- **THEN** 送出的請求不帶該角色的範圍欄位，該角色以全系統寫入，卡片顯示全系統

#### Scenario: 未改動範圍的角色保留現有範圍

- **WHEN** 使用者以甲節點範圍持有一個角色，操作者只移除另一個角色後儲存
- **THEN** 送出的請求不帶甲節點那個角色的範圍欄位，該角色儲存後仍為甲節點範圍

#### Scenario: 新增角色時另改動既有角色的範圍

- **WHEN** 使用者以乙節點範圍持有角色 A，操作者新加入一個維持全系統的角色，並把 A 改為丙節點後儲存
- **THEN** 送出的請求除管理者指派集外，範圍欄位只帶 A 的丙節點、不帶新加入角色的鍵；新加入的角色以全系統寫入，A 儲存後為丙節點範圍

#### Scenario: 失效或目前不能限定節點的範圍不阻擋其他修改

- **WHEN** 使用者持有一個範圍含已不存在節點的角色，與一個以節點範圍持有、但目前不能限定節點的角色，操作者只移除第三個角色後儲存
- **THEN** 送出的請求不帶這兩個角色的範圍欄位，儲存成功，兩者的範圍維持原狀

#### Scenario: 不能限定節點的角色不提供節點選擇

- **WHEN** 操作者檢視使用者持有的一個角色，伺服器判定該角色不能限定節點
- **THEN** 卡片標示不需要選範圍，畫面沒有該角色的節點樹

#### Scenario: 一般使用者角色可限定節點時提供節點選擇

- **WHEN** 操作者檢視使用者持有的一般使用者角色，伺服器判定該角色可限定節點、範圍不會生效，原因為內建角色只在全系統指派時生效
- **THEN** 卡片提供全系統與指定節點的切換，選指定節點時可開啟節點樹選擇並照常儲存，畫面不因角色名稱而隱藏節點樹，並提示內建角色只在指派到全系統時生效、限定節點後不會產生權限

#### Scenario: 勾選節點涵蓋子節點並可搜尋

- **WHEN** 操作者在節點樹勾選一個有兩個子節點的節點，再以其中一個子節點的名稱搜尋
- **THEN** 兩個子節點顯示為已涵蓋，搜尋結果列出該子節點與其上層路徑，每個節點旁顯示其子樹的資產台數

#### Scenario: 來自群組的範圍標示與去重合計

- **WHEN** 管理者指派的範圍是甲節點，使用者所屬群組的同一角色範圍是乙節點，有一台資產同時掛在甲、乙兩個節點下
- **THEN** 樹上乙節點標示來自群組且仍可勾選，底部合計台數等於伺服器回傳的去重台數，小於甲、乙台數相加

#### Scenario: 儲存後的變化顯示可管理資產台數

- **WHEN** 操作者把使用者的資產管理角色由甲節點改為甲節點的上層節點
- **THEN** 「儲存後的變化」顯示可管理資產儲存後與儲存前的台數，兩個數字取自伺服器預覽

#### Scenario: 失效節點的標示與移除

- **WHEN** 使用者的資產管理角色範圍含一個有效節點與一個已不存在的節點，操作者開啟角色與範圍分頁並按「移除失效的節點」後儲存
- **THEN** 儲存前該角色標示節點已不存在且不顯示其名稱，並說明那部分不生效、不會變成全系統；儲存的請求只帶有效節點，失效節點自指派中移除

#### Scenario: 全部節點失效時提示重新選擇

- **WHEN** 使用者某個角色的範圍節點全部已不存在，操作者按「移除失效的節點」
- **THEN** 畫面提示至少選擇一個節點或改為全系統，該角色沒有在本次編輯中被改成全系統

#### Scenario: 角色目前不能限定節點的標示

- **WHEN** 使用者以甲節點範圍持有一個角色，該角色之後被加入只能套用到全系統的權限
- **THEN** 該角色卡片標示含只能套用到全系統的權限、那部分在這個範圍內不生效，並仍提供改為全系統與移除

#### Scenario: 權限不受節點限制的角色可選節點並提示

- **WHEN** 操作者為使用者加入一個權限集合為空的自訂角色，切到指定節點並勾選甲節點後儲存
- **THEN** 畫面在選擇與儲存時都不阻擋，並提示這個角色的權限不受節點限制、範圍不會生效；送出的請求為該角色帶甲節點，指派以甲節點範圍寫入

#### Scenario: 不能指派角色者只看到節點數

- **WHEN** 具使用者入口能力但不持指派角色權限點的主體開啟一位以兩個節點持有資產管理角色的使用者的角色與範圍分頁
- **THEN** 該角色只顯示限定兩個節點，畫面不顯示節點名稱或台數，也沒有節點樹

### Requirement: 使用者群組與外部映射畫面的指派呈現

使用者群組 SHALL 有詳情頁，分為成員與角色與範圍兩個分頁。畫面對受保護角色的限制 SHALL 依動作分別呈現，SHALL NOT 因群組帶受保護角色就停用整個分頁：

- 角色與範圍分頁 SHALL 讀寫群組的角色指派，說明群組的角色會給每一位成員，並以伺服器預覽呈現影響成員數與新增的頁面入口。受保護角色在操作者不能指派時 SHALL 不可移除也不可新增並說明原因；不能指派給群組的角色 SHALL 在選單中停用並說明；其他角色 SHALL 照常可增減。
- 群組帶有操作者不能指派的受保護角色時，成員維護 SHALL 停用並說明只有超級管理者能加入或移除成員；否則成員異動儲存前 SHALL 以與寫入相同的手動成員集合預覽並依結果確認。

群組有啟用中的外部映射規則時，標頭 SHALL 寫出依設定由哪個身分來源的哪個外部群組映射進此群組，並說明於下次登入時依該來源更新；來源已停用時 SHALL 加註；多個來源或外部群組時 SHALL 列出前幾個並以總數表示其餘。此資料 SHALL 來自具使用者群組管理入口能力即可讀取的唯讀端點，只列啟用中的映射規則，SHALL NOT 回傳成員名單。標頭 SHALL NOT 把設定中的外部群組說成某位成員已驗證的來源。沒有啟用中的規則或取不到時 SHALL 改以不指名的說明呈現，不阻擋頁面，且 SHALL NOT 把它說成規則停用後尚未收回。群組頁的說明 SHALL NOT 再宣稱群組與角色無關。

外部群組映射頁 SHALL 在使用者群組規則的目標旁列出該群組的角色。規則目前的目標為受保護角色、或為帶受保護角色之群組時，在操作者不能指派該角色時 SHALL 標示只有超級管理者能修改，並停用修改群組值或目標、啟用與停用以及刪除。新增與編輯規則時，受保護的目標與尚未開放指派的角色 SHALL 在選單中停用並說明；角色規則的目標選單 SHALL 只列可直接映射的角色，並提示其他角色改經使用者群組取得；目標屬管理類時 SHALL 提示儲存後會通知安全人員；目標為受保護或管理類時 SHALL 提示該外部群組的成員由外部目錄的管理者決定。映射頁 SHALL 說明兩種時效（管理操作儲存時收回、外部群組變動於下次登入重算及其時限上界），每頁只呈現一次。

身分來源設定頁在會觸發身分來源設定變更告警的連線設定被修改且尚未儲存時，SHALL 提示儲存後會通知安全人員。上述標示只供呈現，伺服器 SHALL 仍以其守衛裁決。

節點範圍指派開放後，群組的角色與範圍分頁 SHALL 以與使用者角色與範圍分頁相同的規則呈現、選擇與送出群組角色指派的節點範圍：能否限定節點取自伺服器、全系統與指定節點的切換與新加入角色預設全系統、節點樹的搜尋與子樹台數、勾選節點涵蓋子節點、只為改動範圍的角色明示範圍（範圍未改動與新加入且維持全系統的角色不帶範圍欄位）、失效節點的標示與「移除失效的節點」、角色目前不能限定節點的標示、未改動的失效範圍不阻擋其他修改，以及節點名稱與台數只對能指派角色者呈現。樹的底部 SHALL 顯示已選的節點數與其涵蓋的資產台數；「儲存後的變化」SHALL 另顯示這個群組的角色指派在儲存前與儲存後涵蓋的資產台數，並說明這些資產會成為每一位成員的管理範圍。台數 SHALL 由伺服器計算並對多個節點涵蓋的同一台資產只計一次。

以全系統持有可限定節點且範圍會生效之角色時，「儲存後的變化」的可管理資產 SHALL 寫「全部資產」，SHALL NOT 顯示台數。

節點範圍不會生效的角色（權限不受節點限制的角色，或內建一般使用者角色），在群組的角色與範圍分頁 SHALL 同樣可選節點並照常送出，並 SHALL 依伺服器給的原因提示範圍不會生效；SHALL NOT 停用選擇或儲存。

外部群組映射規則本身 SHALL NOT 帶範圍：映射頁新增與編輯規則的對話框 SHALL NOT 提供節點或範圍選擇，送出的映射規則 SHALL NOT 帶範圍欄位。節點範圍只寫在使用者群組或帳號的角色指派上，經映射加入群組的成員取得該群組指派的範圍。映射頁可以提供建立使用者群組並設定其角色與管理範圍的流程；該流程寫入的是使用者群組與該群組的角色指派，SHALL 經與使用者群組頁相同的伺服器關卡裁決，SHALL NOT 把範圍寫進映射規則，也 SHALL NOT 因此為映射規則增加欄位。

外部群組映射頁在使用者群組規則的目標旁列出群組的角色時，可限定節點且範圍會生效的角色 SHALL 一併寫出管理範圍：以全系統持有者寫出全系統，以節點範圍持有者寫出範圍節點的路徑，超過三個節點時列出前三個並以總數表示其餘；其他角色以全系統持有時只列名稱。任何角色以節點範圍持有時 SHALL 寫出其範圍節點，SHALL NOT 呈現為全系統。範圍中已不存在的節點 SHALL 標示節點已不存在而不顯示其名稱。範圍 SHALL 取自群組角色指派的讀取結果，以讀取結果的範圍種類判斷全系統或節點範圍，畫面 SHALL NOT 自行推算；節點範圍的範圍節點為空或全數已不存在者 SHALL NOT 呈現為全系統。角色能否限定節點與範圍是否會生效 SHALL 取自伺服器，SHALL NOT 由畫面依角色名稱或權限推算。節點路徑 SHALL 只對能指派角色者呈現；不能指派角色者 SHALL 只看到限定的節點數，沒有路徑。節點清單取不到時 SHALL 改以限定的節點數呈現，不阻擋頁面。新增與編輯規則對話框的目標使用者群組選單 SHALL 在每個群組旁列出其角色，可限定節點且範圍會生效的角色另附其管理範圍（全系統、單一節點的路徑或節點數）；操作者能進入使用者群組頁時，選單末尾 SHALL 提供前往使用者群組新增群組的連結；映射頁另提供建立使用者群組的流程時，此連結 SHALL 照常保留。選定目標群組後，對話框 SHALL 說明經這條規則加入的人會取得的角色與管理範圍，並說明一般管理能力不會自動帶來連線權、能連線到哪些主機另由資產授權決定、超級管理者另依既有的保留身分，以及該群組目前的資產授權筆數。資產授權筆數 SHALL 只在取得目前選定群組的用途讀取結果後呈現：讀取中 SHALL 說明正在讀取，讀取失敗 SHALL 說明暫時無法取得，這兩種情形 SHALL NOT 呈現為沒有資產授權；先前選定的群組較晚回來的讀取結果 SHALL NOT 呈現在目前選定的群組上。操作者能進入對應頁面時 SHALL 附查看或修改該群組角色與範圍的連結，以及預先帶入該群組的前往資產授權連結。上述呈現 SHALL NOT 新增讀取端點或回應欄位，也 SHALL NOT 改變規則新增、編輯、停用與刪除的條件。

角色規則分頁 SHALL 說明這裡只能對應不需要指定範圍的內建角色，點名可限定管理範圍的內建角色（資產管理員、授權管理員）與自訂角色要經使用者群組取得，並以編號步驟寫出路徑：開啟或新增使用者群組、在其角色與範圍分頁分配角色並選全系統或指定節點、回映射頁以使用者群組規則對應該群組；另說明要讓這些人連線到主機，須以資產授權把主機授權給該群組。操作者能進入使用者群組頁時 SHALL 附前往的連結，不能進入者 SHALL NOT 看到該連結；映射頁另提供建立使用者群組的流程時，此連結與上述步驟說明 SHALL 照常保留。角色規則對話框的目標角色選單 SHALL 在選項之後固定說明找不到的角色如何經使用者群組取得，SHALL NOT 因此把不可直接映射的角色列為選項。

#### Scenario: 受保護群組的成員維護停用

- **WHEN** 非超級管理者開啟一個帶系統安全管理員角色的群組的成員分頁
- **THEN** 成員維護為停用，並說明只有超級管理者能加入或移除成員

#### Scenario: 受保護角色不變時其他角色可增減

- **WHEN** 非超級管理者開啟一個帶系統安全管理員角色的群組的角色與範圍分頁
- **THEN** 系統安全管理員角色不可移除並附說明，操作者仍可新增或移除其他一般角色並儲存

#### Scenario: 群組標頭寫出映射設定

- **WHEN** 一個群組有一條啟用中的規則，把某目錄來源的一個外部群組映射進來，操作者開啟該群組
- **THEN** 標頭寫出依設定由該來源與外部群組映射，並說明於下次登入時依該來源更新

#### Scenario: 映射目標選單停用尚未開放的角色

- **WHEN** 超級管理者在外部群組映射頁新增規則並開啟目標角色選單
- **THEN** 尚未開放指派的角色與受保護角色顯示為停用並說明原因，其他可直接映射的角色可選

#### Scenario: 來源停用時標頭加註

- **WHEN** 映射進群組的啟用規則所屬的身分來源已停用
- **THEN** 標頭在該來源後加註來源已停用

#### Scenario: 多個外部群組以總數收尾

- **WHEN** 一個群組有四條啟用中的映射規則
- **THEN** 標頭列出前三個外部群組並以「另有 1 個群組」表示其餘

#### Scenario: 群組角色指派顯示影響成員

- **WHEN** 操作者為一個有八位成員的群組新增角色
- **THEN** 角色與範圍分頁顯示影響八位成員與新增的頁面入口，儲存前依預覽結果確認

#### Scenario: 空群組新增管理角色仍提示通知

- **WHEN** 操作者為一個沒有成員的群組新增含資產管理能力的角色
- **THEN** 儲存前的確認說明這次儲存會通知安全人員

#### Scenario: 映射頁保護列不可操作

- **WHEN** 非超級管理者檢視一條目標為帶系統安全管理員角色群組的使用者群組映射規則
- **THEN** 該列標示只有超級管理者能修改，修改、啟用或停用與刪除為停用

#### Scenario: 管理類目標提示會通知

- **WHEN** 操作者新增一條目標群組帶資產管理角色的規則
- **THEN** 對話框提示儲存後會通知安全人員，並說明該外部群組的成員由外部目錄的管理者決定

#### Scenario: 角色規則只列可直接映射的角色

- **WHEN** 操作者在角色規則的目標選單中尋找一個自訂角色
- **THEN** 該角色不在選單中，畫面提示改經使用者群組取得

#### Scenario: 映射頁的時效說明

- **WHEN** 可讀取安全政策的操作者開啟映射頁，而重新驗證時限設為不設限
- **THEN** 頁面說明一次：停用、刪除或修改規則於儲存時收回，外部群組變動的權限保留到下次登入

#### Scenario: 身分來源設定變更提示

- **WHEN** 操作者修改目錄的連線位址但尚未儲存
- **THEN** 畫面提示儲存後會通知安全人員

#### Scenario: 群組以節點範圍指派角色

- **WHEN** 操作者在群組的角色與範圍分頁為能限定節點的角色勾選甲節點並儲存
- **THEN** 送出的群組角色指派請求只為該角色帶甲節點，樹底部顯示已選 1 個節點與其涵蓋的資產台數

#### Scenario: 群組儲存後的變化顯示涵蓋台數

- **WHEN** 操作者把群組某角色的範圍由甲節點擴為甲、乙兩個節點
- **THEN** 「儲存後的變化」顯示影響成員數，以及群組指派涵蓋的資產台數儲存後與儲存前的值，兩者取自伺服器預覽

#### Scenario: 群組的失效節點可移除

- **WHEN** 群組某角色的範圍含一個已不存在的節點，操作者按「移除失效的節點」後儲存
- **THEN** 儲存前標示節點已不存在且不顯示其名稱，儲存的請求只帶其餘有效節點

#### Scenario: 映射規則不選節點

- **WHEN** 操作者開啟新增或編輯外部群組映射規則的對話框，目標是一個以節點範圍持有角色的使用者群組
- **THEN** 對話框沒有節點或範圍欄位，送出的規則不帶範圍欄位

#### Scenario: 映射目標列寫出節點範圍

- **WHEN** 能指派角色的操作者開啟外部群組映射頁，一條使用者群組規則的目標群組以一個節點持有資產管理角色、另以全系統持有一般使用者角色
- **THEN** 目標欄寫出兩個角色名稱，資產管理角色附管理範圍與該節點的路徑，一般使用者角色只列名稱、不附範圍文字

#### Scenario: 映射目標列寫出全系統管理範圍

- **WHEN** 一條使用者群組規則的目標群組以全系統持有資產管理角色，另一條的目標群組以全系統持有系統安全管理員角色
- **THEN** 前者的目標欄寫出資產管理角色與管理範圍全系統，後者只寫出系統安全管理員角色名稱、不附範圍文字

#### Scenario: 多個範圍節點以總數收尾

- **WHEN** 目標群組的某角色以五個節點持有，操作者開啟映射頁
- **THEN** 該角色列出前三個節點的路徑，並以「等 2 個」表示其餘

#### Scenario: 不能指派角色者只看到節點數

- **WHEN** 能檢視映射頁但不能指派角色的操作者，檢視一條目標群組以兩個節點持有資產管理角色的規則
- **THEN** 該角色只顯示限定 2 個節點，不顯示節點名稱或路徑

#### Scenario: 映射目標的失效節點只標示

- **WHEN** 目標群組某角色的範圍含一個已不存在的節點與一個仍存在的節點
- **THEN** 目標欄寫出仍存在節點的路徑，另一個標示節點已不存在，不顯示其名稱

#### Scenario: 目標群組選單列出角色

- **WHEN** 能進入使用者群組頁的操作者在新增規則對話框展開目標使用者群組選單
- **THEN** 每個群組旁列出其角色，可限定節點且範圍會生效的角色附管理範圍（含全系統），沒有角色者標示沒有角色；受保護的群組仍為停用並說明；選單末尾有前往使用者群組新增群組的連結

#### Scenario: 選定目標後說明加入者取得什麼

- **WHEN** 操作者在新增規則對話框選定一個以全系統持有資產管理角色、目前沒有資產授權的使用者群組
- **THEN** 對話框說明經這條規則加入的人會取得資產管理角色、管理範圍為全系統，能連線到哪些主機另由資產授權決定且這個群組目前沒有資產授權，並附查看或修改群組角色與範圍、前往資產授權的連結

#### Scenario: 用途讀取失敗時不說沒有資產授權

- **WHEN** 操作者在新增規則對話框選定一個使用者群組，而該群組的用途讀取失敗
- **THEN** 對話框說明暫時無法取得這個群組的資產授權筆數，不寫這個群組目前沒有資產授權；角色與管理範圍的說明與連結照常呈現

#### Scenario: 角色規則分頁寫出經群組取得的步驟

- **WHEN** 能進入使用者群組頁的操作者開啟映射頁的角色規則分頁
- **THEN** 說明點名資產管理員、授權管理員與自訂角色要經使用者群組取得，以編號步驟寫出路徑並說明連線另需資產授權，附前往使用者群組的連結；不能進入使用者群組頁的操作者看到同樣的說明但沒有該連結

#### Scenario: 角色規則選單底部說明找不到的角色

- **WHEN** 操作者在角色規則對話框展開目標角色選單
- **THEN** 選項只有可直接映射的角色，選項之後固定說明資產管理員、授權管理員與自訂角色要先連同範圍給一個使用者群組，再以使用者群組規則對應

### Requirement: 使用者直接指派的節點範圍

整組替換使用者管理者指派集的請求 SHALL 可為其中的角色逐一指定節點範圍，指定值為節點識別碼清單或「全域」。未指定範圍時，使用者已持有的角色 SHALL 保留現有範圍，新增的角色 SHALL 為全域；只有明示改為全域時才改為全域。指定範圍的角色不在該次的管理者指派集內時，SHALL 整筆拒絕。只帶管理者指派集、不帶任何範圍欄位的既有請求形狀 SHALL 照舊有效，且 SHALL NOT 改變任何既有的節點範圍。欄位與路徑 SHALL NOT 使用既有的範圍字樣。

系統 SHALL 提供讀取單一使用者直接指派的端點，每筆列出角色與來源；節點範圍的指派 SHALL 附節點識別碼（含已刪除節點的識別碼，照實回傳），全域指派 SHALL NOT 帶節點欄位。讀取 SHALL 需要與使用者管理頁相同的使用者入口能力。既有的使用者列表與詳情回應形狀 SHALL 不變。

#### Scenario: 以節點範圍直接指派

- **WHEN** 持指派能力者整組替換某使用者的管理者指派集，加入可限定節點的資產管理角色並指定甲節點
- **THEN** 指派以甲節點範圍寫入，讀取該使用者的直接指派時該列附甲節點的識別碼

#### Scenario: 舊請求形狀不改變節點範圍

- **WHEN** 使用者以甲節點範圍持有資產管理角色，操作者以只帶管理者指派集的請求重送同一組角色並移除另一個一般角色
- **THEN** 一般角色被移除，資產管理角色仍為甲節點範圍，沒有改為全域

#### Scenario: 明示改回全域

- **WHEN** 操作者對以甲節點範圍持有的角色明示改為全域
- **THEN** 該指派改為全域，讀取時該列不帶節點欄位

#### Scenario: 範圍指向未列入的角色

- **WHEN** 請求為一個不在本次管理者指派集內的角色指定節點範圍
- **THEN** 整筆被拒，使用者的指派不變

#### Scenario: 管理者與外部群組映射同時給予同一角色時的範圍

- **WHEN** 使用者以甲節點範圍持有某角色，外部群組映射之後也給了同一角色；管理者其後把該角色移出自己的管理者指派集；或映射不再命中而只剩管理者指派
- **THEN** 映射命中時該指派升為並存、保留甲節點範圍；管理者移出自己那份而降為僅映射時，指派改回全域並清除節點範圍，視為擴大，推進權限版本、不推進憑證世代並留下範圍變更審計；映射不再命中而降為僅管理者時，指派不變，保留甲節點範圍；對並存指派指定的範圍照常作用，對僅由映射持有的角色指定範圍則忽略並以揭露欄告知，不拒絕

#### Scenario: 無使用者入口能力不能讀取直接指派

- **WHEN** 不具使用者入口能力的主體讀取某使用者的直接指派
- **THEN** 請求被拒，不回傳任何指派資料

### Requirement: 節點範圍指派的寫入一致性

帶節點範圍的指派寫入（使用者直接指派與使用者群組角色指派）SHALL 在同一交易內依序完成：取得對象鎖（使用者群組路徑另依識別碼升冪取得其全部成員的使用者鎖）、取得節點拓撲寫入與引用拓撲的寫入共用的序列化點（先於任何指派、節點範圍與權限列的鎖）、以取得序列化點之後重讀的現值通過共用授權關卡、驗證每個節點存在且未刪除、寫入指派與其節點、推進權限版本、服務審計、權限狀態事件，以及命中時的授權變更告警事件。取得序列化點之後，同一交易 SHALL NOT 新取得尚未持有的使用者或群組鎖；對同一交易已持有的鎖再次取得屬重入，不受此限。唯一例外是使用者群組角色指派：在預取成員鎖之後才加入該群組、且受本次寫入影響的成員，SHALL 於推進權限版本之後補取其使用者鎖並照常完成其失權處理，SHALL NOT 因此略過；補取若與另一筆交易互相等待，資料庫 SHALL 中止其中一筆並整筆回滾，SHALL NOT 留下部分寫入。判定 SHALL NOT 沿用取得序列化點之前讀到的結果；權限版本的推進 SHALL 在指派與節點列寫入之後。任一步驟失敗 SHALL 全部回滾。節點存在的驗證 SHALL 與節點刪除的被引用檢查經同一序列化點互斥：並發的「以某節點建立指派」與「刪除該節點」之中 SHALL 恰有一方成功，SHALL NOT 留下指向已刪除節點的新指派。

範圍的任何改變（新增或移除節點、在全域與節點範圍之間切換）SHALL 推進權限版本，受影響主體的下一個請求 SHALL 依新範圍裁決；送出與現值相同的範圍 SHALL NOT 推進。角色集不變、只改範圍的請求 SHALL 照常寫入範圍，SHALL NOT 因角色集相同而略過。範圍縮小時，因此在該角色上失去涵蓋的使用者 SHALL 比照移除指派，於同一交易推進憑證世代並撤銷刷新憑證；經群組路徑時只計經該群組取得、且沒有其他指派補回涵蓋的成員。純擴大 SHALL NOT 推進憑證世代。

只改範圍的寫入 SHALL 留下與角色增減可區分的服務審計，記錄變更前後的範圍種類與節點識別碼。使用者或使用者群組被刪除時，其指派的節點範圍列 SHALL 於同一交易移除，使已刪除的主體不再被計為節點的管理範圍引用。

#### Scenario: 擴大範圍推進版本但不踢人

- **WHEN** 把某使用者資產管理指派的範圍由甲節點擴為甲、乙兩個節點
- **THEN** 權限版本加一，該使用者下一個請求可管理乙節點子樹內的資產，其憑證世代不變

#### Scenario: 縮小範圍撤銷會話

- **WHEN** 把某使用者資產管理指派的範圍由甲、乙兩個節點縮為甲節點，且該使用者沒有其他指派涵蓋乙節點
- **THEN** 該使用者的憑證世代被推進、刷新憑證被撤銷，下一個請求不再能管理乙節點子樹內的資產

#### Scenario: 指派與刪除節點並發

- **WHEN** 一個請求以節點 N 建立指派，同時另一個請求刪除節點 N
- **THEN** 恰有一方成功：指派成功則節點刪除因被引用而被拒，刪除成功則指派因節點已刪除而被拒

#### Scenario: 刪除主體後不再引用節點

- **WHEN** 只有使用者 U 的一筆指派以節點 N 為範圍，U 被刪除
- **THEN** 同一交易移除該筆指派的節點範圍列，節點 N 不再計入被管理範圍引用的筆數

#### Scenario: 審計寫入失敗則範圍不變

- **WHEN** 一次範圍變更的服務審計寫入失敗
- **THEN** 指派的範圍、權限版本與受影響使用者的憑證世代皆維持交易前狀態

#### Scenario: 只改範圍留下可區分的審計

- **WHEN** 只把一筆既有指派的範圍由甲節點改為乙節點
- **THEN** 同一交易有一筆記錄變更前後範圍的服務審計，與角色新增或移除的審計列可區分

### Requirement: 指派用的節點清單

系統 SHALL 提供一個指派專用的唯讀端點，供能指派角色的操作者選擇節點範圍。端點 SHALL 回傳全部未刪除節點的識別碼、名稱、上層節點、層級與路徑，每個節點附其子樹（含子節點）內的未刪除資產台數，同一台資產在同一子樹內只計一次；並 SHALL 回傳目前能限定節點的角色識別碼，其判定 SHALL 與共用指派關卡對節點範圍的判定相同。

能限定節點的角色中，權限集合不含任何已實作範圍過濾權限點者，以及只在全系統指派時生效的內建角色（一般使用者、審核者），其節點範圍不會生效；端點 SHALL 另回傳這些角色的識別碼與各自不會生效的原因，列入與否與原因 SHALL 與指派寫入回應列出的範圍不會生效角色及其原因一致。這些角色 SHALL 仍列為能限定節點，以有效節點範圍指派時照常寫入。

台數 SHALL NOT 依呼叫者的連線授權或管理範圍收斂。端點 SHALL NOT 回傳任何資產的名稱、位址、識別碼或資產清單，也 SHALL NOT 回傳已刪除的節點。不持有指派角色權限點的主體 SHALL 被拒絕，不回傳任何節點資料。端點 SHALL 唯讀：SHALL NOT 改變指派或其他業務資料、SHALL NOT 推進權限版本，也 SHALL NOT 產生授權變更的審計標記或告警事件；系統對每個請求既有的請求紀錄照常保留；路徑與欄位 SHALL NOT 使用既有的範圍字樣。既有節點樹端點的回應與收斂規則 SHALL 不因此端點而改變。

#### Scenario: 只能指派角色者可讀全部節點與台數

- **WHEN** 只持指派角色權限點、本身沒有任何資產權限也沒有連線授權的身分管理員呼叫此端點
- **THEN** 回應含全部未刪除節點的名稱、上層節點、層級、路徑與子樹資產台數，台數與超級管理者呼叫時相同

#### Scenario: 不回資產清單

- **WHEN** 能指派角色的操作者呼叫此端點
- **THEN** 回應不含任何資產的名稱、位址或識別碼

#### Scenario: 不能指派角色者被拒

- **WHEN** 具使用者入口與資產檢視能力但不持指派角色權限點的主體呼叫此端點
- **THEN** 請求被拒，不回傳任何節點資料

#### Scenario: 已刪除的節點不列出

- **WHEN** 某節點已被刪除，而仍有指派以它為範圍
- **THEN** 此端點不列出該節點，讀取該指派時仍可見其節點識別碼

#### Scenario: 能限定節點的角色與關卡一致

- **WHEN** 對每個角色比對此端點是否列為能限定節點，與以節點範圍指派該角色時共用指派關卡的結果
- **THEN** 列為能限定節點的角色，以有效節點範圍指派時不因角色不能限定節點而被拒；未列者以節點範圍指派時被拒

#### Scenario: 範圍不會生效的角色仍列為能限定節點

- **WHEN** 能指派角色的操作者呼叫此端點，其中有一個權限集合為空的自訂角色，之後以有效節點範圍指派該角色
- **THEN** 此端點把該角色同時列為能限定節點與範圍不會生效，原因為權限不受節點限制；指派照常寫入，寫入回應列出該角色為範圍不會生效，原因相同

#### Scenario: 內建一般使用者列為範圍不會生效並附原因

- **WHEN** 能指派角色的操作者呼叫此端點，之後以有效節點範圍把內建一般使用者角色指派給一位使用者
- **THEN** 此端點把該角色同時列為能限定節點與範圍不會生效，原因為內建角色只在全系統指派時生效；指派照常寫入，寫入回應列出該角色與相同原因

#### Scenario: 既有節點樹不變

- **WHEN** 同一主體在此端點上線前後呼叫既有節點樹端點
- **THEN** 兩次回應相同

### Requirement: 角色異動審計的請求脈絡

經管理介面的請求異動帳號直接指派（指派、移除、只改範圍、釘住）或使用者群組的角色指派（指派、移除、只改範圍）時，系統為該次寫入留下的服務審計列，以及同一交易內的授權分級審計列，SHALL 記錄該次請求的操作者識別與帳號名、來源位址、請求方法、請求路徑與請求識別；同一請求的稽核中介層請求列 SHALL 與這些列使用同一請求識別，操作者與來源位址 SHALL 一致。沒有管理介面請求的寫入路徑（外部身分首次登入、目錄帳號建立、外部群組映射重算）SHALL 維持記為系統操作者，請求欄位留空，由指派來源欄說明來路。

上述審計列的 details SHALL 與本要求之前相同，SHALL NOT 因本要求加入帳號名、角色名或節點名；帳號與群組的角色指派、移除、只改範圍列的 details 只含識別碼，依審計重放的對帳結果 SHALL 不變。

操作日誌列表 SHALL 接受以請求識別精確篩選，回傳同一請求識別的全部列；篩選值為空時 SHALL 視同未篩選。

#### Scenario: 同一請求的紀錄互相找得到
- **WHEN** 身分管理員經管理介面把限一個節點的資產管理員角色指派給另一位帳號
- **THEN** 中介層請求列、角色指派列與授權分級列的請求識別相同且非空，三者的操作者都是該身分管理員、來源位址相同、角色指派列與授權分級列的請求路徑都是該次請求路徑；以該請求識別篩選操作日誌，回傳的恰為這三列

#### Scenario: 群組角色指派帶請求脈絡
- **WHEN** 身分管理員經管理介面替一個使用者群組新增一個角色
- **THEN** 群組角色指派列帶該身分管理員為操作者，請求識別與同一請求的中介層請求列相同

#### Scenario: 沒有管理請求的路徑仍記為系統
- **WHEN** 一位帳號以外部身分首次登入，系統依設定為其配角色
- **THEN** 該角色指派列的操作者為系統、請求欄位為空、指派來源標示該登入途徑

#### Scenario: 原文不含名稱
- **WHEN** 讀取帳號或群組的角色指派、移除、只改範圍列的 details 原文
- **THEN** 原文只含帳號、角色、群組與節點的識別碼，不含操作者帳號名、受領人帳號名、角色名或節點名，形狀與變更前相同

### Requirement: 角色異動審計的可讀呈現

操作日誌列表、單筆與每日簽核清單 SHALL 為帳號角色指派、帳號角色移除、使用者群組角色指派、使用者群組角色移除各提供可翻譯的原因；帳號角色指派 SHALL 依範圍區分全系統與限定節點兩種原因，範圍記為全系統的指派 SHALL NOT 被說成限定節點。只改範圍的列（帳號與群組相同）SHALL 呈現對象、角色與變更前後的範圍；範圍 SHALL 以全系統或節點清單加總數表示，節點清單因上限被截斷時總數 SHALL 仍為實際數量。授權分級列的原因 SHALL 列出命中的分類標記，且只陳述已建立系統告警，SHALL NOT 聲稱已通知或已送達任何人；是否送達由告警的投遞紀錄表達。

回應原因參數中的角色、對象帳號或群組與節點 SHALL 在讀取時換成名稱：角色事後刪除時 SHALL 顯示刪除前的名稱；帳號或群組查無紀錄、節點已刪除時 SHALL 退回識別碼。換名 SHALL 只改原因參數，SHALL NOT 改寫或補寫 details 原文，也 SHALL NOT 讓任何人讀到原本不能讀的列；這些回應的讀者 SHALL 維持與本要求之前相同。稽核中介層請求列 SHALL 沿用既有的原因呈現（沒有原因時顯示請求路徑），SHALL NOT 為了每列都有原因而另造原因。

操作日誌列表 SHALL 在帶自我授權或管理類發放標記的列旁標示該標記，並 SHALL 讓讀者從單筆詳情一步查看同一請求的全部紀錄。

#### Scenario: 指派列讀得出誰把什麼角色給了誰
- **WHEN** 稽核員讀取一筆限定兩個節點的資產管理員指派列
- **THEN** 原因寫出角色名稱、受領帳號名稱與兩個節點的路徑，並寫出這是管理介面操作；同一列的 details 原文仍只有識別碼

#### Scenario: 全系統指派不說成限定節點
- **WHEN** 稽核員讀取一筆以全系統範圍新建的指派列
- **THEN** 原因為全系統指派的句子，不出現限定節點的字樣

#### Scenario: 只改範圍讀得出前後範圍
- **WHEN** 身分管理員把另一位帳號的資產管理員指派由甲節點改為乙節點，角色不增不減，之後稽核員讀取操作日誌與每日簽核
- **THEN** 該列原因寫出受領帳號名稱、角色名稱、變更前為甲節點路徑、變更後為乙節點路徑；改為全系統時寫出全系統；同一列的 details 原文仍只有識別碼

#### Scenario: 刪除後的回退
- **WHEN** 指派列所指的角色事後被刪除，另一筆指派列所指的節點事後被刪除
- **THEN** 前者的原因顯示角色刪除前的名稱，後者的原因以識別碼顯示該節點

#### Scenario: 分級列不聲稱已送達
- **WHEN** 系統未設定任何通知通道時，身分管理員對他人發放管理類角色
- **THEN** 授權分級列的原因寫出已建立系統告警與管理類發放標記，不出現已通知或已送達的說法

#### Scenario: 請求列沿用既有呈現
- **WHEN** 稽核員讀取同一請求的中介層請求列
- **THEN** 該列沒有原因碼，畫面照既有規則顯示請求路徑

### Requirement: 使用者群組與帳號的角色與管理範圍呈現

節點範圍指派開放後，使用者群組列表、使用者群組的角色與範圍分頁，以及使用者詳情的角色與範圍分頁 SHALL 依下列規則呈現角色與其管理範圍。本條只規定呈現：角色能否限定節點、範圍是否會生效與其原因 SHALL 取自伺服器（角色列表或指派選項的回應），SHALL NOT 由畫面依角色名稱或權限推算；本條 SHALL NOT 改變上述分頁既有的選擇、送出、預覽、確認與伺服器裁決規則，也 SHALL NOT 新增讀取端點或回應欄位。

- 兩個角色與範圍分頁的分配角色選單 SHALL 在頁面層完整展開，SHALL NOT 被分頁或卡片的內容區截斷；選單 SHALL 可依角色名稱篩選，並把角色分為內建角色與自訂角色兩組。可限定節點且範圍會生效的角色 SHALL 在選項旁標示可限管理範圍，其他角色 SHALL NOT 有此標示。既有的停用與原因說明照舊。
- 群組的角色與範圍分頁 SHALL 不需先選取角色即呈現每個角色的管理範圍：可限定節點且範圍會生效者寫出全系統（說明涵蓋所有節點與日後新增的節點）或所選節點的路徑，並提供「設定範圍」就地展開既有的節點選擇；不能限定節點者寫出全系統並說明不需要選範圍。
- 兩個角色與範圍分頁中，內建角色因只在全系統指派時生效而範圍不會生效者（例如一般使用者），以全系統持有時管理範圍 SHALL 寫不適用，並說明這個角色以全系統指派、沒有可限定節點的管理能力；權限不受節點限制而範圍不會生效的角色以全系統持有時 SHALL 寫出全系統並說明範圍不會生效。這兩類角色仍要限定節點的操作 SHALL 放在次要位置，展開前先依伺服器給的原因說明限定節點後不會產生權限或範圍不會生效；選擇之後的節點選擇、送出與提示照既有規則，SHALL NOT 停用。以節點範圍持有者 SHALL 照既有規則寫出其範圍節點與不會生效的提示。
- 兩個角色與範圍分頁 SHALL 固定說明這裡設定的是管理範圍：角色的管理範圍決定成員能在哪些節點上做管理工作；一般管理能力不會自動帶來連線權，能連線到哪些主機由資產授權決定，超級管理者另依既有的保留身分。操作者能進入資產授權頁時 SHALL 附前往資產授權的連結，群組分頁的「儲存後的變化」在可連線主機的說明旁 SHALL 附同一連結。
- 自使用者群組畫面（群組的角色與範圍分頁、外部群組映射頁選定目標後的說明）前往資產授權時，SHALL 開啟批次授權並預先選定該使用者群組為授權主體；該群組不在操作者可選的授權主體內時 SHALL NOT 預選，並說明原因。預選只是起點，授權 SHALL 仍經批次授權既有的步驟與伺服器守衛裁決。
- 使用者群組列表 SHALL 有角色與管理範圍欄：列出群組的角色；可限定節點且範圍會生效的角色寫出管理範圍（全系統或節點路徑），節點路徑的多節點收尾、失效節點標示、只對能指派角色者呈現路徑、節點清單取不到時退回節點數，與外部群組映射頁的目標欄相同；其他角色以全系統持有時只列名稱；沒有角色者標示沒有角色並提供前往設定的連結。群組名稱 SHALL 直達該群組的角色與範圍分頁。

#### Scenario: 空群組的角色選單完整可選

- **WHEN** 能指派角色的操作者在沒有任何角色的群組開啟分配角色選單，並輸入「資產」
- **THEN** 選單完整呈現、不被分頁內容區截斷，篩出資產管理員且標示可限管理範圍；未篩選時內建角色與自訂角色分兩組

#### Scenario: 一般使用者的管理範圍寫不適用

- **WHEN** 能指派角色的操作者開啟一個以全系統持有一般使用者角色的群組的角色與範圍分頁
- **THEN** 一般使用者的管理範圍寫不適用並說明以全系統指派、沒有可限定節點的管理能力，沒有可限管理範圍的標示；仍要限定節點的操作在次要位置，展開前說明限定節點後不會產生權限

#### Scenario: 仍要限定節點照常送出

- **WHEN** 操作者在上述次要位置為一般使用者角色選擇一個節點並儲存
- **THEN** 送出的群組角色指派請求為該角色帶該節點，畫面提示內建角色只在指派到全系統時生效，儲存不被停用

#### Scenario: 群組角色的管理範圍直接可見

- **WHEN** 能指派角色的操作者開啟一個以兩個節點持有授權管理角色的群組的角色與範圍分頁
- **THEN** 未選取任何角色即看到兩個節點的路徑與「設定範圍」，按下後就地展開節點選擇

#### Scenario: 管理範圍說明與資產授權帶入群組

- **WHEN** 能進入資產授權頁的操作者在群組的角色與範圍分頁按前往資產授權
- **THEN** 分頁先說明管理範圍與連線分屬兩處；開啟的批次授權以使用者群組為主體並已選定該群組

#### Scenario: 帶入的群組不可選時不預選

- **WHEN** 操作者自群組畫面前往資產授權，而該群組不在操作者可選的授權主體內
- **THEN** 批次授權不預選該群組並說明原因，其餘步驟照常

#### Scenario: 群組列表寫出角色與管理範圍

- **WHEN** 操作者開啟使用者群組列表，一個群組以全系統持有資產管理角色，另一個群組沒有角色
- **THEN** 前者寫出資產管理角色與全系統，後者標示沒有角色並提供前往設定的連結；按群組名稱開到該群組的角色與範圍分頁

#### Scenario: 帳號的角色與範圍分頁同樣呈現

- **WHEN** 能指派角色的操作者在一位以全系統持有一般使用者角色的帳號的角色與範圍分頁開啟分配角色選單
- **THEN** 選單完整呈現、可篩選並分內建與自訂兩組；一般使用者的管理範圍寫不適用，分頁說明這裡設定的是管理範圍並附前往資產授權的連結

### Requirement: 映射頁就地建立群組並設定角色與管理範圍

外部群組映射頁 SHALL 提供「建立群組並設定角色與範圍」的流程，讓操作者在映射頁依序完成三件既有動作：建立一個使用者群組、為該群組指派角色與管理範圍、新增一條把外部群組對應到該使用者群組的映射規則。流程 SHALL 只依序呼叫這三個既有寫入，SHALL NOT 呼叫其他寫入（包括更新外部群組共用顯示名稱的寫入），SHALL NOT 新增寫入路徑、權限點或回應欄位，也 SHALL NOT 改變任一寫入的授權判定、守衛、預覽、確認、通知與留痕；為核對結果而讀取既有的使用者群組清單、群組角色指派與映射規則清單不算寫入。映射規則本身 SHALL NOT 帶範圍：流程中選的管理範圍寫入的是群組的角色指派，送出的映射規則 SHALL NOT 含任何範圍或節點欄位。角色規則可直接映射的角色清單 SHALL 不因此流程改變。

流程的入口 SHALL 只在操作者同時具備使用者群組管理、角色指派與身分來源管理三項能力時呈現，判定取自目前使用者的權限點，SHALL NOT 依角色名稱判斷；缺任一能力時所有入口 SHALL NOT 出現。入口 SHALL 位於角色規則分頁的說明、角色規則對話框目標選單的底部，以及使用者群組規則對話框目標選單的第一項。映射頁既有的步驟說明、前往使用者群組的連結與目標選單末尾前往使用者群組新增群組的連結 SHALL 保留原有的位置、功能與可見性條件：前往使用者群組的兩個連結仍只在操作者能進入使用者群組頁時呈現，步驟說明與切換到使用者群組規則分頁的操作照常呈現；入口 SHALL NOT 取代或移除它們，也 SHALL NOT 改變它們的呈現條件。從規則對話框進入時，已填的外部群組與顯示名稱 SHALL 帶入流程。從角色規則分頁的兩個入口（說明、角色規則對話框目標選單的底部）進入時，第二步 SHALL 預先選定內建的資產管理員角色，判定 SHALL 依內建識別，SHALL NOT 依角色顯示名稱，操作者 SHALL 可取消此選擇；該角色在操作者的角色選單中為停用時 SHALL NOT 預選。從使用者群組規則對話框的目標選單進入時 SHALL NOT 預選任何角色。

流程 SHALL 分三步：群組（名稱必填、描述選填）；角色與管理範圍（與使用者群組的角色與範圍分頁相同的角色選擇、停用規則與範圍設定，至少一個角色）；外部群組與確認（外部群組必填、顯示名稱選填）。第三步 SHALL 在送出前列出將依序完成的三件事，說明規則本身不帶範圍、成員取得的範圍來自群組的角色，並說明一般管理能力不會自動帶來連線權、能連線的主機由資產授權決定、超級管理者另依既有的保留身分；所選角色含管理類時 SHALL 提示儲存後會通知安全人員；所選角色含管理類或受保護角色時 SHALL 說明該外部群組的成員由外部目錄的管理者決定。外部群組已在該身分來源的外部群組清單中時，第三步的顯示名稱 SHALL 唯讀呈現清單中的既有值，並說明這個顯示名稱由使用該外部群組的規則共用、要在映射頁原處修改；外部群組不在清單中時，顯示名稱才隨建立映射規則的請求一併寫入。步驟編號 SHALL 以一般數字編號呈現，SHALL NOT 使用圓圈數字或圓框數字。

送出後 SHALL 依序寫入，前一個寫入完成才進行下一個。群組角色指派與映射規則在各自寫入前 SHALL 照既有規則取伺服器預覽，需要確認時 SHALL 開與使用者群組頁、映射頁相同的確認；操作者在確認時返回，該步及其後的寫入 SHALL NOT 送出。映射規則寫入要求來源設定確認或用途確認時，SHALL 照映射頁既有的確認方式處理。

每個寫入的結果 SHALL 分為三種：成功；確定被拒絕；結果未確認。確定被拒絕 SHALL 只限逐一列舉的封閉清單：伺服器在寫入提交前就回絕、且依該寫入現行的處理可證明沒有留下寫入的錯誤；SHALL NOT 依回應的狀態類別概括判定。封閉清單為：建立群組的權限不足、請求內容驗證失敗與群組名稱已存在；群組角色指派的權限不足、請求內容驗證失敗、群組不存在、角色不存在或不能經使用者群組取得，以及指派規則的拒絕（受保護角色、不支援範圍、不能限定節點、節點範圍為空或含不存在的節點）；建立映射規則的權限不足、請求內容或比對值驗證失敗、規則帶範圍或節點欄位、身分來源不存在、目標群組不存在、指派規則的拒絕與顯示名稱過長。清單以外的任何失敗，包括回應映射規則不存在、清單以外的其他用戶端錯誤、伺服器內部錯誤、逾時與沒有收到回應，SHALL 一律視為結果未確認（寫入可能已經生效）。映射規則寫入要求來源設定確認或用途確認的回應不是失敗，照前段的確認方式處理。結果未確認時，流程 SHALL 先以既有讀取核對實際狀態再決定下一步：讀回顯示已存在者 SHALL 視為完成，SHALL NOT 重送該寫入（建立群組另依下述同名群組的規則）；讀回顯示不存在者才判為沒有寫入、可重試；讀回本身失敗者 SHALL 維持結果未確認；讀回的群組角色指派與本次送出的不同時，SHALL 呈現讀回的指派，重試時的角色草稿 SHALL 以讀回的角色與範圍為基底。建立群組的結果未確認時，只有使用者群組清單中查無該名稱才可認定沒有建立；清單中已有同名群組時 SHALL NOT 認定那是本流程建立的群組，也 SHALL NOT 以它繼續後續步驟；在前一次結果未確認、讀回查無而重試建立群組時，重試回應群組名稱已存在 SHALL 同樣依清單中已有同名群組處理，SHALL NOT 說沒有建立任何東西。無法核對（讀取失敗）時，流程 SHALL 顯示結果未確認並提供查看實際狀態的途徑，SHALL NOT 宣稱寫入沒有生效或沒有影響，也 SHALL NOT 自動重送。

任一寫入被拒絕、結果未確認或操作者在確認時返回時，流程 SHALL 逐項呈現每一步的結果（已完成、被拒絕及原因、結果未確認、未執行），SHALL NOT 自動刪除或撤回已完成的寫入，並 SHALL 讓操作者只重試未完成的步驟；重試 SHALL 沿用已建立的群組，SHALL NOT 再建立一個群組。首次送出的建立群組被拒絕（例如名稱已存在）時 SHALL 回到第一步並就地說明原因，此時沒有任何東西被建立。

全部完成後，流程 SHALL 列出三件事的結果、提供開啟該群組角色與範圍分頁的連結，並說明一般管理能力不會自動帶來連線權；操作者能進入資產授權頁時 SHALL 提供前往資產授權並預先帶入這個群組的連結，不能進入時 SHALL NOT 呈現該連結。流程關閉後映射頁 SHALL 重新讀取規則與群組。

三個寫入各自的操作紀錄、服務留痕與管理類通知 SHALL 與分別在使用者群組頁、映射頁執行時相同；流程 SHALL NOT 另寫留痕，也 SHALL NOT 合併或抑制各寫入產生的通知。上述呈現只供操作，伺服器 SHALL 仍以各寫入既有的守衛裁決。

#### Scenario: 一次完成三件事

- **WHEN** 同時具備三項能力的操作者從使用者群組規則對話框選「建立新群組並設定角色與範圍」，建立一個群組、給資產管理員角色並維持全系統，填入外部群組後按「建立並儲存」，並在確認時繼續
- **THEN** 系統依序建立群組、寫入該群組的角色指派、建立一條指向該群組的映射規則，完成畫面列出三件事皆已完成，映射頁重新讀取後顯示這條規則

#### Scenario: 指定節點的範圍寫在群組的角色指派

- **WHEN** 操作者在流程第二步為資產管理員選一個節點，完成送出
- **THEN** 群組角色指派的請求為該角色帶該節點，映射規則的請求不含任何範圍或節點欄位

#### Scenario: 缺能力時看不到入口

- **WHEN** 具備身分來源管理能力、但沒有角色指派能力的操作者開啟外部群組映射頁的兩個分頁與兩種規則對話框
- **THEN** 三個入口都不出現，角色規則分頁照常呈現既有的步驟說明

#### Scenario: 入口與既有的前往連結並存

- **WHEN** 同時具備三項能力的操作者開啟角色規則分頁，並展開兩種規則對話框的目標選單
- **THEN** 三個入口都出現，角色規則分頁的步驟說明與前往使用者群組的連結、角色規則選單底部的說明，以及使用者群組規則選單末尾前往使用者群組新增群組的連結照常存在

#### Scenario: 缺使用者群組管理能力時入口與前往連結都不出現

- **WHEN** 具備角色指派與身分來源管理能力、但沒有使用者群組管理能力的操作者開啟角色規則分頁，並展開兩種規則對話框的目標選單
- **THEN** 三個入口與前往使用者群組的連結都不出現；角色規則分頁的步驟說明、角色規則選單底部的說明與切換到使用者群組規則分頁的操作照常存在

#### Scenario: 從規則對話框進入時帶入外部群組

- **WHEN** 操作者在角色規則對話框填好一個尚未在外部群組清單中的外部群組與顯示名稱後，按目標選單底部的「建立群組並設定角色與範圍」
- **THEN** 規則對話框關閉，流程開啟，第一步顯示帶入的外部群組，第三步的外部群組與顯示名稱已填入相同的值

#### Scenario: 從角色規則分頁進入時預選資產管理員

- **WHEN** 操作者從角色規則分頁說明的入口進入流程並走到第二步
- **THEN** 內建的資產管理員角色已被選定，操作者可以取消它改選其他角色

#### Scenario: 從使用者群組選單進入時不預選

- **WHEN** 操作者從使用者群組規則對話框的目標選單進入流程並走到第二步
- **THEN** 沒有任何角色被預先選定

#### Scenario: 已在清單中的外部群組顯示名稱唯讀

- **WHEN** 帶入流程的外部群組已在該身分來源的外部群組清單中，操作者走到第三步
- **THEN** 顯示名稱唯讀呈現清單中的既有值並說明要在映射頁原處修改；送出後只有建立群組、群組角色指派與建立映射規則三個寫入

#### Scenario: 名稱已存在時沒有建立任何東西

- **WHEN** 操作者在第一步填入一個已存在的群組名稱，走到第三步按「建立並儲存」
- **THEN** 建立群組被拒絕，流程回到第一步並說明名稱已存在，沒有送出角色指派與映射規則的寫入

#### Scenario: 規則建立被拒絕時保留已完成的步驟

- **WHEN** 群組與角色指派都已寫入，建立映射規則的請求被伺服器以確定被拒絕清單中的錯誤回應（例如操作者已失去權限）
- **THEN** 流程逐項顯示前兩步已完成、第三步被拒絕及原因，說明已完成的步驟不會撤回；按「重試新增規則」只送出映射規則的寫入，指向同一個群組，不再建立群組

#### Scenario: 角色指派已寫入但回應失敗時不重送

- **WHEN** 寫入群組角色指派的請求回應內部錯誤，而讀回該群組的角色指派與本次送出的相同
- **THEN** 流程把第二步顯示為已完成，不再送出角色指派的寫入，並照常進行映射規則的預覽與確認

#### Scenario: 規則已寫入但回應失敗時不重送

- **WHEN** 建立映射規則的請求沒有收到成功回應，而讀取該來源的使用者群組規則清單時已有同一外部群組指向該群組的規則
- **THEN** 流程把第三步顯示為已完成，不再送出建立映射規則的請求

#### Scenario: 規則已提交但回應規則不存在時不重送

- **WHEN** 建立映射規則的請求回應映射規則不存在，而讀取該來源的使用者群組規則清單時已有同一外部群組指向該群組的規則
- **THEN** 流程不把第三步顯示為被拒絕，而是在核對後顯示為已完成，不再送出建立映射規則的請求

#### Scenario: 無法核對時顯示結果未確認

- **WHEN** 建立映射規則的請求逾時，而讀取該來源的使用者群組規則清單也失敗
- **THEN** 流程把第三步顯示為結果未確認並提供查看映射規則的途徑，不說規則沒有建立，也不自動重送

#### Scenario: 確認時返回停在該步

- **WHEN** 群組已建立，操作者在群組角色指派的確認中按返回
- **THEN** 角色指派與映射規則都沒有送出，流程顯示群組已建立、其餘兩步未執行，並可從角色指派重試

#### Scenario: 管理類角色照常確認與通知

- **WHEN** 操作者經流程把資產管理員給一個新群組並建立規則
- **THEN** 第三步在送出前提示儲存後會通知安全人員；送出後群組角色指派與映射規則各自照既有規則開確認，且系統照常各自產生管理類通知，與分別在群組頁與映射頁操作時相同

#### Scenario: 不能進資產授權者沒有前往連結

- **WHEN** 沒有資產授權管理能力的操作者完成流程
- **THEN** 完成畫面說明一般管理能力不會自動帶來連線權，但不呈現前往資產授權的連結；能進入資產授權頁的操作者則看到該連結，開啟後批次授權的主體已帶入這個群組

#### Scenario: 角色規則選單仍只列可直接映射的角色

- **WHEN** 操作者在角色規則對話框開啟目標選單
- **THEN** 選單仍只列可直接映射的角色，可限定管理範圍的角色不在選項中；選單底部在既有說明之外提供進入流程的按鈕
