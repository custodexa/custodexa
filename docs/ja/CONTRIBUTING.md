# コントリビューションガイド

<p><a href="../../CONTRIBUTING.md">English</a> | <a href="../zh-TW/CONTRIBUTING.md">繁體中文</a> | <b>日本語</b> | <a href="../README.md">他の言語 →</a></p>

Custodexa へのコントリビューションをありがとうございます。この文書は、変更を取り込んで
もらうまでの流れを説明します。環境の構築については [`QUICKSTART.md`](QUICKSTART.md) を
参照してください。

## やりたいこと別の入口

- **バグの報告やアイデアの提案**: 再現手順、または提案の動機を添えて GitHub の issue を
  立ててください。
- **ドキュメントや誤字の修正、明らかな小さなバグの修正**: 事前の相談は不要です。そのまま
  PR を送ってください。コミットには `-s` を付けるのを忘れずに（後述の DCO を参照）。
- **振る舞いの変更や機能の追加**: まず issue を立てて動機と方針を相談し、合意ができてから
  振る舞い変更のワークフローに沿って進めてください。作ったあとで方向が合わないと分かる
  事態を避けるためです。

## 開発環境とテスト

```bash
bash scripts/quickstart.sh --up                # スタック全体を起動
docker compose exec backend go test ./...      # バックエンドのテスト
docker compose exec frontend npm run test      # フロントエンドのテスト
```

検証はすべて docker compose の中で行います。その他のコマンド、環境まわりの落とし穴、
ガードテストの規律は [`docs/dev/testing.md`](../dev/testing.md) にあります。

## DCO の署名（必須）

本プロジェクトのライセンスは **AGPL-3.0** で、コントリビューションは **DCO** のもとで
受け入れます。署名する契約書はなく、コミットごとに 1 行を付けるだけです。

```bash
git commit -s -m "fix: describe your change"
```

この 1 行は、あなたがそのコードを書いたこと、またはプロジェクトのライセンスのもとで
提出する権利を持っていることを表明するものです。**著作権が移転することはありません**
（全文は [`DCO.md`](../../DCO.md)）。署名は git の設定（`user.name` / `user.email`）から
取られ、公開履歴に永久に残ります。公開して差し支えない情報をお使いください。

- 署名を忘れた場合: 直前のコミットなら `git commit --amend -s`、複数なら
  `git rebase --signoff <base>` を実行し、force-push してください。
- 署名のない PR はマージされませんが、レビューは通常どおり進み、メンテナが直し方を
  お知らせします。
- CLA を使わない理由: CLA は、コントリビューションを AGPL 以外の条件で再ライセンスする
  ために存在します。本プロジェクトはそれを行わないため、必要ありません。

## PR チェックリスト

- すべてのコミットに `Signed-off-by` が付いている。
- コミットメッセージが Conventional Commits に従っている
  （`feat:` / `fix:` / `refactor:` / `docs:` / `test:` / `chore:`）。
- テストが緑である。振る舞いの変更にはテストが伴っている。
- 振る舞いの変更とリファクタリングが別のコミットに分かれており、それぞれ単独で
  revert できる。
- 利用者に見える文言が i18n を経由している（機械可読なコードと 3 言語。単一言語の
  ハードコード文字列はガードテストで落ちます。
  [`docs/dev/conventions.md`](../dev/conventions.md) を参照）。
- ハードコードされたシークレットがない。外部入力は検証されている。
- コミットメッセージとドキュメントは英語でも繁體中文でもかまいません。技術用語は
  原語のまま残します。

## 振る舞い変更のワークフロー（OpenSpec）

[`openspec/specs/`](../../openspec/specs/) はシステムが**現在**何をするのかを記述したもので、
権威ある拠りどころです。振る舞いの変更はすべて同じ道筋をたどります。

```
証拠 → 提案（openspec/changes/<id>/）→ 実装 → アーカイブ（specs/ へ統合）
```

`openspec/changes/` 配下の change フォルダは、その変更が進行中のあいだだけ存在します。
アーカイブの際に spec の差分が `openspec/specs/` へ統合され、フォルダは畳まれます。

要点は次のとおりです。

1. **設計には証拠が必要です。** file:line 付きのコード棚卸し、実際の実行時の挙動、または
   スクリーンショットに基づいてください。記憶に頼ってはいけません。他のオープンソースの
   踏み台プロジェクトを調査してもかまいませんが、コードの複製は決して行わないでください。
   多くは GPL 系のライセンスであり、複製したコードは本プロジェクトを汚染します。
2. **ガードで保護された機械生成物**（ルートの golden、API エンドポイント索引）は
   [`docs/dev/testing.md`](../dev/testing.md) の手順で再生成します。手で編集しては
   いけません。
3. **ルートを触った場合**は [`docs/API_SPEC.md`](../API_SPEC.md) の散文部分を更新して
   ください。**モデルやマイグレーションを触った場合**は
   [`docs/DB_SCHEMA.md`](../DB_SCHEMA.md) を更新してください。
4. **アーカイブされた spec に書いてよいのは、システムが実際に行うことだけです。**
   未完了の部分は PR で説明してください。メンテナが issue で追跡します。spec には
   書かないでください。
5. **振る舞いの権威ある記述は `openspec/specs/` にあります。** コード中のコメントは、
   その箇所で行った取捨選択を説明するものです。コメントと spec が食い違う場合は spec が
   優先されます。理由が読み取れない場合は issue で質問してください。メンテナが
   ドキュメントへ追記します。

## 設計原則（機能を提案する前にお読みください）

- **ロールごとに専用の機能ページを持たせます。** 既存のページに別のロール向けのセクションを
  継ぎ足さないでください。設計の前に、その機能がどのロールのナビゲーションに属するのかを
  決めてください。
- **行き詰まった利用者には、製品として抜け出す道が必要です**（UI の操作と API エンドポイント）。
  答えが「管理者にデータベースを直してもらう」であれば、機能が足りていません。
- **見た目に関する唯一の拠りどころは
  [`docs/DESIGN_SPEC.md`](../DESIGN_SPEC.md) です。** ブランドトークンの変更にはメンテナの
  承認が必要で、監査に関わる技術的な識別子を見た目の都合で変更することはありません。

## セキュリティのレッドライン（交渉の余地はありません）

いずれかに抵触する PR はマージされません。

1. **接続の集約**: フロントエンドは平文の資格情報に決して触れません。資格情報は
   バックエンドにのみ存在し、フロントエンドが受け取るのはワンタイムの接続トークンです。
2. **操作の全面的な監査**: すべての接続と管理操作が記録を残します。監査の記録が
   書けないときは、閉じる方向で失敗します。
3. **入力の検証**: 外部からの入力はすべて、使用前に検証します。

具体的なアーキテクチャ上の不変条件は
[`docs/dev/conventions.md`](../dev/conventions.md) にあります。
