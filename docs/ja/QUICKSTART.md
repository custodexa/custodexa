- Docker 20.10+

- Git

インストールの確認：


## 起動手順

自分の環境で運用する場合も、開発に参加する場合も**同じ手順**です。既定の `docker-compose.yml`
がそのまま本番スタックで、nginx がビルド済みのフロントエンドを配信し、backend はスリムなバイナリ、
テストターゲットは含まれません。開発に参加する方は 1 ステップだけ追加で、`.env` の
`COMPOSE_FILE=docker-compose.dev.yml` のコメントを外します。以降すべての `docker compose` コマンドが
開発スタック（フロントエンドは Vite HMR、バックエンドは Air のホットリロード、各プロトコルのテストターゲット付き）を対象とし、毎回 `-f` を付ける必要はありません。

### 1. ソースコードの取得

```bash
git clone https://github.com/custodexa/custodexa.git
cd custodexa
```

### 2. 環境変数の設定（必須）

> **手早く済ませる方法**：`bash scripts/quickstart.sh` が本節の作業を自動で行います。`.env` を確認し
> （無ければテンプレートから作成）、未設定のシークレットを CSPRNG で生成します。記入済みの値は
> 一切変更しないため、再実行しても安全です。`--up` を付けると起動まで一括で行い、進捗を段階的に
> 報告し、バックエンドの healthy を待って、最後に接続 URL と admin のログイン情報を出力します
> （出力は英語です）。Windows では WSL 内で実行してください。
> 各値の意味を理解したい場合や手動で設定したい場合は、このまま読み進めてください。

まずテンプレートをコピーし、環境に合わせて編集します。

```bash
cp .env.example .env
# 新規（空の DB）へのすべての配備：ADMIN_INITIAL_PASSWORD（初期 admin パスワード、公開の既定値は廃止）を必ず設定
# 本番配備：JWT_SECRET（release では未変更なら起動を拒否）と DB_PASSWORD を必ず変更し、必要に応じて DB_SSLMODE / LDAP / DATA_PATH を設定
#   （ENCRYPTION_KEY が必要なのは KEK_PROVIDER=env のときだけ。出荷時の既定は ui＝鍵をディスクに置かない。テンプレートの KEK 節を参照）
# 開発に参加する場合：COMPOSE_FILE=docker-compose.dev.yml のコメントを外し、KEK_PROVIDER=env と
#   ENCRYPTION_KEY の設定を推奨——ホットリロードは再ビルドのたびにプロセスを再起動するため、ui のままでは毎回アンシールを求められます
```

> **初期管理者パスワード（`ADMIN_INITIAL_PASSWORD`）**：出荷時の既定パスワードはありません。新規（空の DB）への配備では
> 必ず適格な値を自分で設定します。12 文字以上、前後に空白を含まない、テンプレートのプレースホルダーそのままではないこと。
> 満たさない場合、サービスは起動を拒否し、その理由をログに出力します。
> `openssl rand -base64 24` での生成を推奨します（末尾の改行は除いてください）。
> この値が使われるのは一度きりで、初回ログイン時にパスワード変更が強制されます。その後は `.env` から削除するかローテーションしてください。
> 既存のデータベース（空でない DB）ではこの値は不要です。

> **オフサイト保管（`OFFSITE_*`）は初期設定です**：このグループのキーは**初回起動時**にデータベースへ書き込まれ、
> 以降は管理画面の「システム設定 → オフサイト保管」ページで管理します。`.env` を変更しても反映されません
> （ディレクトリ連携の `LDAP_*` も同じ形態です）。自動化された配備が不利になることはありません。`.env` に記入しておけば初回起動時に反映されます。
> 既定は空＝無効で、システムの挙動は一切変わりません。

`.env.example` は**唯一の環境変数テンプレート**です（開発用・本番用いずれの compose も `env_file` でこれを読み込みます）。
バックエンドが消費する変数の網羅性は `backend/config/env_drift_test.go` がガードします。コードが実際に消費している変数を走査し、
本テンプレートと compose が提供するトポロジー変数と突き合わせ、ドリフトがあればテストが失敗します。
トポロジーやモードの定数（`DB_HOST=postgres`、`GUACD_HOST=guacd`、`GIN_MODE` など）は compose ファイルが提供し、テンプレートには含まれません。

> **注意**：`env_file` は「値が空の行」に付いたインラインコメントを取り除きません（`KEY=  # 説明` の値は `# 説明` になります）。
> テンプレートの設定項目は既定で空値のものが多いため、`.env`（およびテンプレート）の説明は必ず独立した行に書き、値の行にはインラインコメントを付けません。
> 付けると値にコメントが混入し、サービスの起動に失敗します。

**データの配置先（`DATA_PATH`）**：アプリケーションの主要データ（監査 / 録画 / データベース）は単一のフォルダルート配下に置かれ、
その位置は `DATA_PATH` が決めます。既定はプロジェクト内の `./data`（開発ではそのまま中身を確認できます）。本番配備では指定のフォルダやディスクへ上書きできます：

```bash
# 本番：データを指定のパスへ集約する
DATA_PATH=/opt/custodexa/data
```

> **データの永続化とリセット**：データは bind mount で `${DATA_PATH}` ディレクトリに置かれ、`docker compose down -v`
> では**消去されません**（`-v` が消すのは named volume だけです）。データを完全にリセットするには、サービスを停止してから
> `DATA_PATH` が指すディレクトリの中身を削除します（既定は `./data`、独自に設定した場合はそのパス。`.env` の
> `DATA_PATH` は手動の shell コマンドには引き継がれません）：
> `rm -rf ./data/*`。`./data/` は `.gitignore` に登録済みで、誤ってバージョン管理に入ることはありません。

### 3. サービスの起動

```bash
# バックグラウンドで実行（既存イメージが無い場合はまずビルドされます——本番スタックではビルドが配備手順の第一歩です）
docker compose up -d

# フォアグラウンドで実行（ログを確認できます）
docker compose up
```

初回起動はイメージのビルドと依存関係のダウンロードが必要で、5〜10 分ほどかかります。

### 4. サービスの確認

**コンテナの状態を確認**：
```bash
docker compose ps
# 本番スタック（既定）：backend, frontend, postgres, guacd, tls-proxy
#   （tls-init は証明書を準備したら終了するため、状態が exited(0) になるのは正常です）
# 開発スタック（COMPOSE_FILE を有効化した場合）には、さらにテストターゲットがあります：
#   ssh-test, ssh-multi-test, mssql-test, mysql-test, rdp-test, vnc-test, k3s-test
#   （加えて ldap-test / dex / localstack の 3 サービスが LDAP、OIDC、S3 関連機能のために用意されています）
```

**アクセス先（スタックごとに異なります）**：

| | 本番スタック（既定） | 開発スタック |
|---|---|---|
| フロントエンド | https://localhost （TLS プロキシ。http://localhost は 301 でこちらへ転送） | http://localhost:3000 （Vite 開発サーバー） |
| バックエンド | 外部にポートを公開しません（プロキシと nginx が `/api` を転送） | http://localhost:8080 |

本番スタックが外部に開くのは TLS プロキシの 2 ポートだけで、`443`（https）と `80`（http、転送のみ）です。
ブラウザが前提とするポートなので、利用者が入力するアドレスにポート番号は付きません。
そのポートを別のサービスがすでに使っているホストでは、別の組を指定します——`.env` で `TLS_HTTPS_PORT=8443` と
`TLS_HTTP_PORT=8088` を設定します——この場合、アドレスは `https://localhost:8443` のようにポートを伴います。
以下の記述はすべて既定のポートを前提にしています。
証明書の出どころは既定では製品自身が生成するローカル CA（`TLS_MODE=selfsigned`）のため、CA を利用者側へ
配布するまではブラウザに警告が表示されます。自前の証明書を使う方法と CA の配布方法は「外部通信の暗号化（TLS）」を参照してください。

**バックエンド API のテスト**：
```bash
# 本番スタック：backend は外部にポートを公開せず、/health は nginx のプロキシ経路にも含まれないため、コンテナ内から実行します
docker compose exec backend wget -qO- http://localhost:8080/health
# 開発スタック：直接アクセス
curl http://localhost:8080/health
# {"status":"ok","service":"custodexa-backend"}
```

**封印状態（出荷時の既定は `KEK_PROVIDER=ui`）**：新規インストールの起動直後、システムは**封印されたまま初期化待ち**の状態です。
`/health` は正常に応答しますが業務エンドポイントはまだ公開されず、初めてフロントエンドを開くと初期化アンシール画面に入ります。状態の確認：

```bash
curl -k https://localhost/api/v1/seal/status
```

- 初期アカウント: `admin`。初期パスワードは `.env` で設定した `ADMIN_INITIAL_PASSWORD` です

> **初回ログイン時のパスワード変更は必須です**：初期 admin は初回ログイン後にパスワード変更画面へ遷移し、新しいパスワードを設定すると
> （画面に表示されるポリシーに従います：長さ、英字＋数字、直近数件の再利用不可）そのままシステムに入ります。ログインし直す必要はありません。
> 変更後 `ADMIN_INITIAL_PASSWORD` は役目を終えるので、`.env` から削除するかローテーションしてください。

ログイン後に最初の資産を作成し、最初の接続を開始する手順は、下の「初回利用」の節をご覧ください。
本番環境で必ず設定すべき項目は「本番配備の補足」にまとめてあります。外部 TLS、時刻同期、監査の完全性の境界、
ログの保持といった配備者の責任と挙動の説明は「本番環境における配備者の責任と挙動の境界」を、admin のパスワード紛失、
脆弱な認証情報のスキャンによる起動拒否、管理者が送信元制限で締め出された場合のオフラインでのリセットは「トラブルシューティング」をご覧ください。

### 5. ログの確認

```bash
# すべてのサービス
docker compose logs -f

# 特定のサービス
docker compose logs -f backend
docker compose logs -f frontend
```

## 初回利用：ログインから最初の接続まで

以下の流れは本番スタックでも開発スタックでも共通です。開発スタックでは内蔵のテストターゲットを接続先にできます（「接続機能のテスト」を参照）。
本番スタックでは、実際に管理したいホストに置き換えてください。

### 1. 初期化アンシール、ログイン、パスワード変更

`https://localhost/`（開発スタックでは `http://localhost:3000`）を開きます。

**出荷時の既定（`KEK_PROVIDER=ui`）では、最初に初期化アンシール画面に入ります**。マスター鍵はお使いの
ブラウザで**ローカルに生成され、サーバー側ではメモリ上にのみ存在します**。画面では鍵を確実に保管したことの確認を求められます
（以降もプロセスを再起動するたびに封印状態で止まり、この鍵でアンシールする必要があります）。初期化の認可には
`admin` と `ADMIN_INITIAL_PASSWORD` を使います。
（env／kms モードにこの手順はなく、そのままログイン画面へ進みます。）

続いてログインします。アカウントは `admin`、パスワードは `.env` の `ADMIN_INITIAL_PASSWORD` です。初回ログインでは
まずパスワード変更画面に入り、新しいパスワードを設定するとそのままダッシュボードへ進みます。

### 2. 最初の資産を作成する

「資産管理」→「資産を追加」。各項目の説明：

| 項目 | 説明 |
|---|---|
| 名前、プロトコル、ホスト、ポート | 必須です。ホストには IP かホスト名を入力します（コンテナ配備でホストマシン上のサービスに接続する場合は `host.docker.internal` が使えます） |
| ユーザー名、パスワード、SSH 秘密鍵 | 接続に使う認証情報で、保存時は空でも構いません。実際の接続では**秘密鍵が優先、次にパスワード**を使います。両方とも空の資産も保存はできますが、接続を開始すると失敗します（「資産に利用可能な認証情報が設定されていません」） |
| ノードに配置 | 資産ツリー上での所属ノードで、複数選択できます（1 つの資産を複数のノードに同時に配置できます）。空のままなら「未分類」に並びます |
| 接続ポリシー | 資産ごとの接続の管理です。既定は「グローバル設定に従う」で現在のグローバル値を表示します。この資産だけ緩めたい／厳しくしたいときに変更します |
| 説明 | 任意です。一覧での識別に使います |

資産一覧の「ステータス」列は疎通確認の結果です（作成直後で未確認の資産は「-」と表示されます）。
疎通確認が今のところ検証するのはパスワード認証だけのため、秘密鍵のみを設定した資産では失敗しますが、実際に接続できないという意味ではありません。
接続できるかどうかは、次の手順の「接続」で判断してください。

### 3. 接続を開始する

資産一覧から該当の資産を探し、その行の「**接続**」を押すとワークスペースのタブが開きます。
Web ターミナルにリモートホストのプロンプトが表示されれば接続成功です。いくつかコマンド（`whoami`、`ls`）を試し、
`exit` を入力するかタブを閉じるとセッションが終了します。

### 4. 監査を確認する

セッション終了後、「接続管理」にこのセッションの履歴が表示されます。詳細を開くと**録画の再生**
（シークと再生速度の変更ができます）と、そのセッションの**コマンド記録**があります。セッションをまたいでコマンドを検索するには「コマンド監査」ページを使います。
この「操作は必ず記録に残る」という一連の流れが本製品の中核です。初回配備時には、実際に一度たどって録画を再生できることを確認しておくことをおすすめします。

## 本番配備の補足

本番スタックは既定の compose そのものです（上の起動手順を参照）。本節では release 特有の必須設定項目と配備の検証を補足します。
本番スタックの特徴：DB／guacd のポートを外部に公開しない、`restart: always`、バックエンドはビルド済みバイナリで動作
（ソースコードのマウントなし、`GIN_MODE=release`）、外部に開くのは TLS プロキシの `443`（https）と `80`（http、転送）だけ。

### 1. `.env` の release 必須項目

release モードはこれらの値に対して **fail-close** です（適格でなければ警告ではなく起動を拒否します）：

| 変数 | 要件 |
|---|---|
| `JWT_SECRET` | 出荷時の既定値から必ず変更すること（PCI 2.2.2） |
| `ENCRYPTION_KEY` | 必要なのは `KEK_PROVIDER=env` のときだけ。出荷時の既定 `ui`（鍵をディスクに置かない）ではコメントアウトのまま維持すること。値があると設定の矛盾として起動を拒否します |
| `DB_PASSWORD` | 必須——本番 compose には既定値がありません |
| `ADMIN_INITIAL_PASSWORD` | 新規の空 DB では必須（12 バイト以上、プレースホルダーでない、前後に空白／改行がない）。既存 DB では不要 |
| `CORS_ALLOWED_ORIGINS` | クロスオリジンの配備では必須。未設定の場合は同一オリジンのみ許可します |
| `DATA_PATH` | 専用のフォルダかディスクを指すことを推奨（既定は `./data`） |
| `TLS_DOMAIN` | 外部向けホスト名で、証明書に書き込まれます。空の場合は `localhost` と同じ扱いです |
| `PUBLIC_BASE_URL` | 外部向けの https アドレス（OIDC の `redirect_uri` はこの値を使います）。`TLS_DOMAIN` と同じドメインにします |

### 2. 起動

```bash
# 既存イメージが無い場合、up はまず本番イメージをビルドします（ビルドが配備手順の第一歩です）。
docker compose up -d
```

> 本番と開発のイメージは名前が分かれています（`custodexa/*:latest` と `custodexa/*:dev`）。
> 同じマシンに両方を保持でき、どちらをビルドしてももう一方を上書きしません。

### 3. 配備の検証（本番配備のたびに実施してください）

```bash
# (1) すべてのサービスが起動し、postgres が healthy であること
docker compose ps

# (2) バックエンドのヘルスチェック——backend は外部にポートを公開せず、/health は nginx のプロキシ経路にも含まれないため、コンテナ内から実行します
docker compose exec backend wget -qO- http://localhost:8080/health

# (3) フロントエンドに到達でき、http が https へ転送されること（自己署名証明書の場合は curl に -k を付けます）
curl -skI https://localhost/
curl -sI http://localhost/ | head -1     # 301

# (4) ログインの経路が通ること（アカウントは admin、パスワードは .env の ADMIN_INITIAL_PASSWORD）
curl -sk -X POST https://localhost/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<ADMIN_INITIAL_PASSWORD>"}'

# (5) 起動ログに fatal が無いこと（release の fail-close はすべてここに出ます）
docker compose logs backend | tail -30
```

> 開発マシンで本番スタックを検証するときは、上のコマンドすべてに明示的な `-f docker-compose.yml` を付けます（`.env` の `COMPOSE_FILE` を上書きします）。

出荷時の既定である `ui` モードでは、(4) は**初期化アンシールが完了する前**は封印ゲートに阻まれます。先にブラウザで
初期化を済ませるか（「初回利用」を参照）、`curl -k https://localhost/api/v1/seal/status` で状態を確認してください。

(4) が**新規配備**で返すのは、通常のトークンではなく `{"change_token": "...", "password_change_required": true, "policy_hint": {...}}` です。
これは初回ログイン時のパスワード変更強制（PCI 8.3.5）であり、これが返れば認証の経路は正常です。正式なセッションはパスワード変更後に発行されます。

いずれかの手順が失敗したときは、まず (5) のログを見てください。release の起動拒否には必ず明確なメッセージ（どの変数が、なぜ適格でないか）があります。

> **外部からの接続は既定で TLS です**：本番スタックはリバースプロキシを内蔵し、`443` が https、`80` は必ずそこへ転送します。
> 証明書は既定では製品自身が署名します（ローカル CA）。CA を利用者側へ配布すればブラウザは信頼済みと表示します。
> 自組織の証明書がある場合や自前の ingress がある場合は別の 2 つの道があり、3 つとも下の「外部通信の暗号化（TLS）」に記載しています。

### 4. OIDC／SSO 配備の注意

provider 自体の設定（issuer／client_id／secret／受け入れ条件）は管理画面からデータベースへ保存します。
配備層が決めるのは次の 3 つの環境変数と、**SSO を有効化する前に必ず確認すべき運用上の前提**が 1 つです。

| 変数 | 説明 |
|---|---|
| `PUBLIC_BASE_URL` | 外部向けの基準 URL で、IdP に渡す `redirect_uri`（`${PUBLIC_BASE_URL}/api/v1/auth/oidc/callback`）と callback の戻り先を組み立てるのに使います。**リクエストの Host からは推定しません**。リバースプロキシが多段の転送を行う構成では推定が必ず外れ、その値は `redirect_uri` に書き込まれるため、誤ると利用者が間違ったホストへ誘導されます。未設定の場合、有効化済みの provider は「設定が未完了」と印を付けられ、ログイン画面から隠されます（fail-close）。本番環境では https にしてください。 |
| `OIDC_DEDICATED_ISSUERS` | 専用 issuer の宣言（カンマ区切り）。システムは「未知の issuer」を一律 fail-close で**共有 ID ドメイン**とみなし、その受け入れ条件に組織の所属条件（テナント識別子か hosted domain）を含めることを要求します。しかし Okta や自前構築の IdP などはそうした claim を**発行しません**。この宣言が無いと、それらの自動プロビジョニングは設定できません。宣言の意味は「この issuer は自組織だけに提供されている」であり、その判断ができるのは配備者だけなので、管理画面の API ではなく配備層に置いています（admin アカウント自身がセキュリティ規則を緩めることは認めません）。内蔵の共有リスト（Google、Microsoft のマルチテナントエンドポイントなど）が優先され、この宣言で覆すことはできません。**変更後はすべてのレプリカをローリング再起動して初めて反映されます**（宣言は起動時に読み込まれます。1 つのレプリカだけ再起動すると各レプリカの判定が食い違い、管理画面の provider 詳細に表示されるのは「そのレプリカ」の判定根拠です）。 |
| `OIDC_ALLOWED_INTERNAL_HOSTS` | アウトバウンドを許可する内部ホスト名（カンマ区切り）。IdP へのアウトバウンドは既定で loopback／link-local（クラウドのメタデータアドレスを含む）／プライベートネットワークへの解決を拒否するため、**社内 IdP はここで明示的に許可する必要があります**。「アドレス検査を無効にする」ブール値のスイッチは用意していません。release モード以外では、ここに列挙したホスト名は http も許可されます（開発用 IdP ターゲット向け）。社内 IdP が自己署名証明書を使う場合は、その CA をコンテナのトラストストアに追加してください。**TLS 検証をスキップするスイッチは提供していません。** |

**ローカルの admin アカウントを最低 1 つ残す必要があります**（SSO を有効化する前に確認してください）：

- システムは「ローカル admin の数を 1 以上からゼロへ減らすことはできない」という不変条件を保ちます。最後のローカル admin を外部ログイン専用に変更する、
  無効化する、admin ロールを外す、削除する——いずれも拒否されます。
- 理由は「IdP が停止したら入れなくなる」ことだけではありません。**封印のアンシール（`KEK_PROVIDER=ui`）と初期管理者の検証はローカルの認証情報しか受け付けません**。
  この経路はシステムがまだ完全には起動していない段階で行われるため、外部 IdP 経由で完了させることは原理的に不可能です。admin 全員を外部化すると、
  ひとたび封印状態に入ったとき誰もアンシールできなくなります。
- そのローカル admin には強固なパスワードを設定して MFA を有効にし、ブレークグラス用のアカウントとして扱ってください。

**IdP 側での停止は、進行中のプロトコル接続を自動では切断しません**：

- 利用者が IdP 側で停止／削除されても、本システムはそれを**即時には知りません**（OIDC に逆方向の通知はなく、
  back-channel logout を別途つなぐ場合を除きます。本バージョンでは未実装です）。既存の SSH／RDP／VNC などのプロトコル接続は確立後に認証情報を使わないため、
  **そのまま生き続け**、アイドルタイムアウト（`SSH_IDLE_TIMEOUT_MINUTES`）と最大接続時間によって制御されます。
  発行済みのアクセストークンも有効期限まで生き続けます（固定 15 分）。IdP 側での停止の実際の効果は「次回のログインが拒否される」ことです。

**マルチレプリカ配備における既知の境界**（単一インスタンス配備は影響を受けません）：

- 本バージョンから、同じデータベースに対して起動された 2 つ目のアプリケーションインスタンスはガードが**検知して確認を求めます**。ガードが防ぐのは気づかないままの
  並存であって、並存そのものではありません——確認したうえでの実行は監査証跡に残り、そのデータ上の結果は確認した人が負います
  （[配備形態の制限](ops/deployment-topology-limits.md)を参照）。
- 録画再生用のアクセストークン（recording token）の認可は **per-process** です。トークンを発行したバックエンドのレプリカだけが、それを引き換え、失効させられます。
  マルチレプリカ構成でアカウント／provider を無効化するリクエストが別のレプリカに届いた場合、発行側レプリカにある既存のトークンは TTL 満了まで生き続けます。
  残る窓は **120 秒以下、能力は読み取り専用**です（すでに録画された内容を取得できるだけで、新しい接続は作れません）。この境界はマルチレプリカ配備における前提上の欠落であり
  （[配備形態の制限](ops/deployment-topology-limits.md)を参照）、HA に進む前にレプリカ間の通知機構とあわせて解決する必要があります。
- **即時に遮断したい場合は、本システムの管理画面で操作してください**：当該利用者のアカウントを無効化する（利用者の認証情報の世代を進めます）か、
  provider 全体を無効化します（provider の世代を進めます）。いずれもリフレッシュを失効させ、発行済みのアクセストークンを拒否し、
  その範囲のプロトコル接続を切断し、監視／共有の購読も終了させます。
- **オフサイト保管のアップロード worker にはレプリカ間の排他がありません**：マルチレプリカ構成では同じ録画や証拠パッケージが重複して取得され、
  **同じキーへ再送**されます。内容は同一なので上書きは無害で、記帳の結果も一致します。したがって正確性の問題ではありません。
  代償は無駄になった帯域と競合による再送です。単一インスタンス配備では発生しません。
- provider の **secret のローテーションと削除は無効化と同じ**完全な失効フローを通ります。`auth_epoch` は増えるだけで減らないため、
  「無効化して短時間で再度有効化する」ことによって攻撃者の手元にある発行済みの認証情報が復活することはありません。副作用として、その provider の利用者全員が
  再ログインを強制されます。これは意図的な選択です（ローテーションの動機は多くの場合、古い secret が漏れた可能性があることだからです）。

**信頼するプロキシの設定が重要です**：SSO の callback と exchange のエンドポイントは公開エンドポイントで、IP 単位のレート制限が掛かっています。
`TRUSTED_PROXIES` が未設定の場合、レート制限のキーは必ずソケットのピア IP を採用し、転送ヘッダーは無視します
（信頼できるプロキシ連鎖の取り決めが無ければヘッダーは自由に偽装できるため、可用性を損なってでも迂回可能な見せかけの防御は提供しません）。
リバースプロキシの背後に配備する場合は `TRUSTED_PROXIES` を必ず正しく設定してください。さもないと、すべてのリクエストがプロキシという同一の IP から来たものとして扱われます。

### 5. LDAP ディレクトリ設定

LDAP のディレクトリ設定（アドレス／bind の資格情報／検索パラメーター／属性マッピング）は管理画面からデータベースへ保存し、
「ID と権限 → ディレクトリ設定（LDAP）」ページで保守します。**データベースが唯一の正**であり、
`.env` の `LDAP_*` 9 個のキーは**初回起動時の seed 元にすぎません**。

| 状況 | 挙動 |
|---|---|
| 初回起動時に `.env` で `LDAP_ENABLED=true` を設定済み | アンシール後に env の値を一度だけデータベースへ書き込み、以降は常にデータベースを正とします |
| 初回起動時に有効化されていない（テンプレートの既定は `LDAP_ENABLED=false`） | seed せず、テーブルは空のままです。管理画面の UI で設定を作成してください |
| seed 完了後に `.env` の `LDAP_*` を変更した | **反映されません**——設定の変更は UI から行ってください |
| UI で設定を削除してから再起動した | env から再投入されることはありません（システムは「評価済み」の印を記録しており、データ行が消えても再実行しません） |

アウトバウンドの制限：ディレクトリへの接続は loopback／link-local（クラウドのメタデータアドレスを含む）／未指定アドレス／
マルチキャストへの解決を一律拒否します。**プライベートネットワークは既定で許可します**（ディレクトリサービスの通常の設置場所は社内網であり、この点は公開網の IdP を前提とする OIDC とは逆です）。
loopback アドレスで接続する必要がある特殊な場面では、`LDAP_ALLOWED_LOOPBACK_ENDPOINTS` に `host:port` の形で
正確に列挙して許可します。ワイルドカードには対応せず、検査を無効にするスイッチも提供しません。

**`.env` へ書き戻されることはありません**：seed 後に管理画面で行った変更は `.env` には一切反映されません。
製品が配備者の管理するファイルを書き換えることはないためです。したがって `.env` の `LDAP_*` の値は初回起動時点のスナップショットにすぎず、
現行設定の参照元にはできません。現在の値を見るには管理画面のページを開いてください。

### 6. キャパシティとストレージの計画

キャパシティ計画の主軸は**録画ストレージの増加**です。バックエンドのプロセス自体が先に飽和する資源になることはありません（本節の末尾を参照）。
以下の数値は開発環境での参考値であり、約束された値ではなく、お使いのハードウェアに対する予測力もありません。環境をまたいで持ち運べるのは**換算方法**です。

#### 録画ストレージの増加率（テキストとグラフィックは分けて扱います。約 2 桁違うため平均してはいけません）

| プロトコル | 観測値 | 性質 |
|---|---|---|
| テキストターミナル SSH（`.cast`） | アイドル時およそ 30 B/s ≈ 105 KB/セッション時間。フル稼働時の増加係数はおよそ 1.32 倍 | テキスト |
| グラフィック RDP／VNC（`.guac`） | 静止したデスクトップでおよそ 10.4 MB/セッション時間から | グラフィック |

> どちらも**アイドル時の下限**です（入力の無いターミナル、画面が変化しない静止デスクトップで計測）。実際の操作（出力のスクロール、
> ウィンドウのドラッグ、画面の切り替え）では数倍から 1 桁大きくなります。下限が確認できるのは「最低でもこれだけは必要」ということだけで、計画値には使えません。

**換算方法（ハードウェアをまたいで持ち運べる部分）**

- **テキスト**：録画のディスク使用量 ≈ ターミナル出力のバイト数 × 1.32（asciicast の JSON フレームとタイムスタンプのオーバーヘッド）。
  自分の環境の「1 人 1 日あたりのターミナル出力量」を代入してください。
- **グラフィック**：10.4 MB/セッション時間**から**始め、実際の操作の強度に応じて掛け上げます。ディスク要件 ≈
  同時グラフィックセッション数 × 平均セッション時間 × 増加率 × 保持日数、これに余裕を加えます。
- 保持期間はセキュリティポリシーのページで管理します（下の「本番環境における配備者の責任と挙動の境界 → ログと録画の保持」を参照）。
  ディスク要件 ≈ 1 日あたりの増加量 × 保持日数。

#### 同時実行のキャパシティ

**Custodexa は同時セッション数の上限を設けず、セッション数を理由に接続を拒否することもありません。** 実際に先に飽和する資源を、確認すべき順に挙げます：

1. **guacd コンテナ（グラフィックプロトコル）**：RDP/VNC のセッション 1 本ごとに guacd の接続が 1 本対応し、CPU もメモリもそれが負担します。
   グラフィックの場面における真の上限であり、自分の環境のグラフィックセッション比率に応じて個別に負荷試験を行う必要があります。
2. **録画ディスクの書き込み帯域と容量**：上表のグラフィック増加率 × 同時グラフィックセッション数で見積もります。
3. **データベース接続プールの上限**。
4. **接続先ホスト自身の制限**：たとえば sshd の `MaxSessions`／`MaxStartups` です。本システムとは無関係ですが、先にこちらで止められます。

バックエンドの Go プロセス自体はボトルネックになりません。1 セッションあたりおよそ +16 goroutine、メモリの増分は計測ノイズを下回るほど小さく
（上限でおよそ 148 KB/セッション）、1 GB の空きメモリで数千本のテキストセッションに相当します。
**テキストセッションのキャパシティはほぼディスクだけに、グラフィックセッションのキャパシティは guacd に決まります。**

#### ストレージの監視

- 録画の使用容量は製品内で確認できます（監査の閲覧権限を持つ人のダッシュボードの「録画の使用容量」カード）。収集側は
  `custodexa_recording_storage_bytes` を読めます（`/metrics`、30 秒ごとに更新。値は最大で 1 更新周期ぶん遅れます）。
- **システムはストレージの上限を設けません**：監査システムの可用性がストレージ量に人質に取られるべきではなく、かといって「接続は通常どおり作るが録画はしない」のでは
  録画の無い特権セッションが生まれてしまい、どちらも受け入れられないためです。したがってディスク全体の容量と枯渇のリスクは、お使いのインフラ監視が担います。
  `custodexa_recording_storage_bytes` に増加率か容量のしきい値でアラートを設定してください。
- 使用量を減らす必要があるときは**保持期間**（システム設定 → セキュリティポリシー）で行い、期限切れの録画を時間に基づいて削除します。

## 本番環境における配備者の責任と挙動の境界

外部に向けてサービスを提供する前に、次の事項は**配備者の責任**です。本製品は意図的に肩代わりせず、やっているふりもしません。
あわせて 2 つの挙動の説明もここにまとめてあります。本番稼働の前に一項ずつ確認してください。

### 外部通信の暗号化（TLS）

本番スタックの外部向け接続は、内蔵のリバースプロキシが TLS を終端します。`443` が https を提供し、`80` は必ず 301 でそこへ転送します。
frontend も backend もホストのポートを公開しません。プロキシは TLS 1.2+、HSTS、**WebSocket upgrade の転送（wss）**を提供し、
設定ファイルを手で書き換える必要はありません——ドメインは `.env` の `TLS_DOMAIN` から取り、起動時に設定へ展開されます。
あわせて `bash scripts/quickstart.sh` は、このスタックが動作する Docker サブネットを `TRUSTED_PROXIES` に記入します。
これにより、バックエンドはすべての要求をプロキシ自身のアドレスとして扱うのではなく、プロキシが転送してくる
クライアントのアドレスを読み取ります。

証明書の出どころは `.env` の `TLS_MODE` が決め、2 つの値が下の最初の 2 つの小節に対応します。`selfsigned`（既定、
製品が自己署名するローカル CA）と `provided`（自分の証明書）です。すでに自前の ingress がある配備は 3 つ目の道を通り、
overlay で内蔵プロキシを止めます。

どの道を通っても、次の 2 点は変わりません。外部のエッジは TLS 1.2+、HTTP→HTTPS の転送、HSTS、WebSocket upgrade の転送を提供すること。
エッジから本ホストまでの hop が信頼できないネットワークをまたぐ場合、その hop も暗号化すること（re-encrypt）。
アプリケーション自体は TLS-ready です。フロントエンドはページのプロトコルに応じて `ws`↔`wss` を自動で切り替え、アクセストークンは Authorization ヘッダーで送ります。
そろえる必要があるのは `PUBLIC_BASE_URL` だけです（「セッション更新 cookie の Secure フラグ」を参照）。

**セッション更新 cookie の Secure フラグ**：Web セッションの更新用の認証情報は `HttpOnly` cookie
（`custodexa_refresh`）で発行され、その `Secure` フラグはセキュリティポリシーの
**「ログイン状態を https 接続でのみ保持する」**が決めます（システム設定 → セキュリティポリシー →「接続とアカウント」）。
このページで値を変更して保存すると、次に発行される cookie から新しい値になります。再起動は不要です。

初回起動時、このポリシーの初期値は `.env` から取られます：

| 初回起動時の設定 | seed される初期値 |
|---|---|
| `AUTH_REFRESH_COOKIE_SECURE=true` または `false` | その値をそのまま採用（最優先） |
| 未設定で、`PUBLIC_BASE_URL` が `https://…` | 有効 |
| 未設定で、`PUBLIC_BASE_URL` が `http://…` | 無効 |
| 未設定で、`PUBLIC_BASE_URL` も空 | 有効（出荷時の既定） |

この 2 つの環境変数が働くのは、ポリシーにまだ値が無いときだけです。ポリシーに値が入ったら（初回起動で seed された、あるいは誰かが
セキュリティポリシーのページで保存した）、その後 `.env` を変更しても何の効果もありません。調整するにはそのページに戻ってください。

**HTTPS で外部公開する配備では `PUBLIC_BASE_URL` を https のアドレスにしてください**（OIDC を使わない場合でも同様です）。
TLS がさらに手前の層で終端され `PUBLIC_BASE_URL` が外部向けのアドレスを反映できないときは、
`AUTH_REFRESH_COOKIE_SECURE=true` で seed します。

**平文の HTTP で外部公開する配備**では、初回起動の前に `AUTH_REFRESH_COOKIE_SECURE` を `false` にするか、
起動後にセキュリティポリシーのページでこの項目を無効にしてください。有効のままでもシステムは使えますが、代償としてブラウザはこの
cookie を保存せず、全員がおよそ 15 分（アクセストークンの寿命）ごとにログインし直すことになります。これは利用者からも見えます。
ログアウトされたときログイン画面が現状を説明して管理者に連絡するよう促し、管理者が同じ http のアドレスでログインすると、セキュリティポリシーのページの
上部にも対応する案内と 2 つの対処の道筋が表示されます。**システムがこの設定を自ら変更することはありません。**

ローカル開発の `http://localhost` は影響を受けません。Chromium 145 と Firefox 146 では実測でこのアドレスからの
Secure cookie を受け入れました。Safari 系の WebKit は破棄するため、Safari で開発するときはこのポリシーを無効にしてください。

起動ログには常に現在の有効値とその出どころ（セキュリティポリシーのページの設定／env による seed／出荷時の既定）が出力されます。
**本番稼働を始めたら、まず一度確認してください**：

```bash
docker compose logs backend | grep "refresh cookie"
```

値が無効のとき、ログは「refresh の認証情報が平文の HTTP で送信されます」と注意します——実際には https で運用しているのなら、
それは設定を厳しくすべきということなので、セキュリティポリシーのページで有効にしてください。

#### 既定：製品が自己署名するローカル CA（`TLS_MODE=selfsigned`）

組織の PKI が無くても、コマンド 1 つで https を得られます。初回起動時、システムは `tls/` にローカル CA と
サーバー証明書を一組生成し（証明書 825 日、CA 10 年）、以降の起動ではそれを使い続けます。通信は全区間で暗号化され、信頼の鎖は CA を
利用者側へ配布することで成立します。

1. `.env` に外部向けホスト名と基準 URL を設定します（`bash scripts/quickstart.sh` はローカルのホスト名と IP から自動で記入します）：

   ```bash
   TLS_DOMAIN=jumper.example.internal
   TLS_IP_SAN=10.0.0.5            # IP でも接続できるようにする場合に記入、カンマ区切り。不要なら空のまま
   PUBLIC_BASE_URL=https://jumper.example.internal
   ```

2. `docker compose up -d`。証明書は初回起動時に生成されます。

3. CA 証明書をダウンロードし、接続してくるマシンへ配布します：

   ```bash
   curl -sk https://jumper.example.internal/custodexa-ca.crt -o custodexa-ca.crt
   ```

   Windows ドメイン環境ではグループポリシー（コンピューターの構成 → Windows の設定 → セキュリティの設定 → 公開キーのポリシー →
   信頼されたルート証明機関）で配布し、macOS／モバイル端末では MDM の構成プロファイルを使い、単体のマシンなら
   システムの信頼されたルート証明書ストアへ手動でインポートします。配布が完了すれば、ブラウザは信頼された接続として表示します。
   CA 証明書は公開してよいデータです。CA の秘密鍵はホストの `tls/ca-private/` 配下に残り、プロキシのコンテナには入りません。

4. あとから組織の CA や公的 CA が発行した証明書に切り替えたい場合は、`tls/` 内のファイルを削除し、`TLS_MODE=provided` に変更して
   新しい証明書を置き（次の節を参照）、再起動すれば完了です。

CA を配布するまでは、ブラウザに証明書の警告が表示され、OIDC を使う外部の ID プロバイダーもコールバックを拒否します——
この段階の自己署名リーフ証明書は、テスト用途にしか適しません。

#### 社内ドメインと組織の CA

`TLS_DOMAIN` はこのシステムの外部向けホスト名にすぎず、社内 DNS か利用者側の hosts で解決できれば十分で、
公的に登録されたドメインである必要はありません（たとえば `jumper.bnc.prod`）。`PUBLIC_BASE_URL` は同じホスト名の
https アドレスにすれば構いません。

組織が自前の CA を持っている場合は、ローカルで秘密鍵と証明書署名要求を作り（SAN にそのホスト名を含めます）、発行を依頼します：

```bash
openssl req -newkey rsa:2048 -nodes -keyout tls/privkey.pem \
  -out custodexa.csr -subj "/CN=jumper.bnc.prod" \
  -addext "subjectAltName=DNS:jumper.bnc.prod"
```

発行された証明書が戻ったら、サーバー証明書と中間証明書をこの順に連結して `tls/fullchain.pem` にし（リーフ証明書が先頭）、
秘密鍵は `tls/privkey.pem` に置いて、`TLS_MODE` を `provided` にしてから再起動します。利用者側にその CA を信頼させる作業は、
通常 AD のグループポリシーか MDM で配布します。SSO に使う ID プロバイダーも社内網にあり、https で同じ CA を使っている場合は、
CA 証明書をバックエンドのコンテナのトラストストアに追加してください（「OIDC／SSO 配備の注意」の
`OIDC_ALLOWED_INTERNAL_HOSTS` の項を参照）。

#### 自分の証明書を使う（`TLS_MODE=provided`）

公的 CA または組織の CA が発行した証明書をすでに持っている場合：

1. 証明書チェーンと秘密鍵を `tls/fullchain.pem` と `tls/privkey.pem` に置きます。
2. `.env` に `TLS_MODE=provided`、`TLS_DOMAIN`（証明書のホスト名と一致させます）、
   `PUBLIC_BASE_URL=https://<ホスト名>` を設定します。
3. `docker compose up -d`。

どちらかのファイルが欠けていると、起動は証明書の準備手順で停止し、どちらが欠けているかを名指しします。プロキシが中途半端な設定のまま起動することはありません：

```bash
docker compose logs tls-init
```

#### 自前の ingress に任せる（external ingress overlay）

前段にすでにクラウドの LB や既存の nginx／Traefik のような ingress がある場合は、overlay で内蔵プロキシを止め、
フロントエンド自身が HTTP ポートを公開して、そこへ ingress から接続させます：

```bash
docker compose -f docker-compose.yml -f docker-compose.external-ingress.yml up -d
```

`.env` の `COMPOSE_FILE=docker-compose.yml:docker-compose.external-ingress.yml`
のコメントを外しておけば、日常の `docker compose up -d`／`ps`／`down` に毎回 `-f` を付ける必要はありません。
この形態ではフロントエンドが `80` を公開し（`.env` の `HTTP_PORT` で変更できます）、外部向けの TLS はお使いの ingress が担います。
その契約は本節の冒頭に挙げたとおりです。`PUBLIC_BASE_URL` には利用者が実際に目にする https のアドレスを記入してください。

次の 2 つの設定は、このスタックではなくお使いの ingress 側の担当です。**Host ヘッダーは、利用者が実際に接続する
ポートを含めて転送してください**——ポートが `443` でないときは必ず付けます。バックエンドは同一オリジンの要求かどうかを
`Origin` と `Host` の比較で判定するため、ポートの落ちた `Host` では認証済みの要求がクロスオリジンに見え、
本文が空の 403 で応答されます（最初に現れるのはログインと解封です）。nginx では HTTP/1.1 の場合
`proxy_set_header Host $http_host;`、Host ヘッダーを持たない HTTP/2 で待ち受ける場合は `$host` と外部向けポートを
組み立てた値を指定します。あわせて **`.env` の `TRUSTED_PROXIES` にお使いの ingress のアドレスかそのサブネットを
設定してください**。これはすべての要求をどのアドレスに帰属させるかを決め、監査ログが記録する値と
ログインのレート制限が数える対象がこれで決まります。

#### リバースプロキシ設定のカスタマイズ

内蔵のテンプレートは一般的な要件を満たします。変更する場合は 1 部コピーし、そちらを指すようにして、元のファイルは触りません：

```bash
cp docker/reverse-proxy/nginx-tls.conf.template tls/custodexa.conf.template
# .env
TLS_NGINX_TEMPLATE=./tls/custodexa.conf.template
```

そのファイルで変更できる箇所：`server_name`（既定では `TLS_DOMAIN` が入ります）、証明書のパス、追加のヘッダー
（HSTS の `max-age`、`includeSubDomains`／`preload` はお使いのドメイン戦略に合わせます）、そして upstream
（同じ docker ネットワークではサービス名 `frontend:80`）。変更後は `docker compose up -d tls-proxy` で適用します。

#### ホストに導入した nginx を使う場合

プロキシのコンテナを動かさず、ホスト上の既存の nginx を使いたい場合：external ingress overlay でフロントエンドに HTTP ポートを公開させ
（loopback へのバインドを推奨します。overlay 内のマッピングを `127.0.0.1:8088:80` に変更してください）、設定は同じテンプレートを流用し、
upstream を `127.0.0.1:8088` に向け、`server_name` と証明書のパスを自分のものに置き換えます。
nginx 1.25.1 未満は `http2 on;` ディレクティブに対応していないため、`listen 443 ssl http2;` と書き換えれば動きます。
その他のリバースプロキシ（Caddy、Traefik、クラウドの LB）も、本節の冒頭に挙げた契約を満たせば構いません。
`docker/reverse-proxy/Caddyfile.example` が等価な Caddy 版です。

#### TLS が有効になったことの確認

```bash
docker compose ps                                  # tls-proxy が Up（tls-init は exited(0)）
curl -sI http://localhost/ | head -1          # 301、https へ転送
curl -skI https://localhost/ | head -1        # 200
curl --cacert tls/ca-public/custodexa-ca.crt -sI https://<TLS_DOMAIN>/ | head -1   # 自己署名モード：200
```

さらにログインして SSH 接続を 1 本開き、ブラウザの DevTools の Network に `wss://` のストリームが見えることを確認します——
ページは正常なのにターミナルが開かないときは、WebSocket upgrade の転送が効いていない場合がほとんどです。

### 時刻同期（PCI 10.6）

コンテナの時計はホストを継承し、本製品は NTP クライアントを内蔵しません。本番のホストでは時刻同期を必ず有効にし
（chrony / systemd-timesyncd / クラウドプラットフォームの既定 NTP）、時刻源は UTC を採用して業界で広く認められた時刻サーバーを指すようにします（10.6.2）。
ホストのシステム時刻の変更に対するアクセス制御と監査は OS 層の責任です（10.6.3）。
監査ログのタイムスタンプの比較可能性は、ホストの時計が正しいことに全面的に依存します。

### 監査の完全性の能力の境界（PCI 10.3.4）

audit_logs の行単位 HMAC、エクスポート manifest の Ed25519 署名、syslog によるリアルタイムの外部転送の 3 つが合わさって補償的コントロールを構成し、
「既存の行が変更された」ことと「基準時刻より後に改ざんされ HMAC が空にされた」ことを検知できます（初回起動時に有効化の基準を記録し、
それ以降すべての**保存**経路が `BeforeCreate` で刻印します。基準より後で HMAC が空のままなら不一致と判定します。ファイルへのフォールバックや
キュー満杯による破棄のイベントは保存されず刻印も経ないため、「書き込み経路」ではなく「保存経路」と表現しています）。
「行を HMAC ごとまるごと削除する」ことは**チェックポイントチェーンが検知します**（区間の集約、連鎖、Ed25519 署名により、
正当な削除は署名付きの tombstone で窃取と区別します）。その証明力の境界 R0-R6 は検証ページと
`openspec/specs/audit-checkpoint-chain/spec.md` を参照してください。
完全性の刻印鍵はシステムが生成するバージョン付きの鍵で（KEK でラップして保存、v1 以降）、`JWT_SECRET` とは導出関係になく、環境変数の設定も一切不要です。

### ログイン前の告知

ログイン画面では、利用者がアカウントとパスワードを入力する前に、アクセスに関する声明を表示できます（システム設定 → セキュリティポリシー → ログイン告知）。
**出荷時は空で、空なら表示しません**——声明の文言は配備者の法務の範疇であり、製品は内容を一切あらかじめ定めません。
新規に導入して引き渡すときは、[配備とアップグレードの SOP §1.7](ops/upgrade-sop.md#17-ログイン告知の設定) に従って設定してください。その節に手順と、設定しない場合の帰結が書かれています。

### ログと録画の保持

保持日数はセキュリティポリシーのページで管理し、`0 = 無期限保持`です。`RECORDING_RETENTION_DAYS` が seed されるのは**初回起動時**
（ポリシーのテーブルにその行が無いとき）だけで、以降は env を変えて再起動しても反映されず、常にポリシーのページが正となります。
期限切れの削除は毎日 02:00 の完全削除で、復元できません。保持期間を短縮するときは UI が先に確認します。
1 回の実行あたりの削除上限は既定で 10 万件／テーブルです。流量の多い配備では `RETENTION_MAX_PER_RUN` を大きくして、日々の期限到来量に追いつかなくなるのを防げます。

### admin のパスワード紛失、脆弱な認証情報のスキャンによる起動拒否、管理者が送信元制限で締め出された場合（オフラインでのリセット）

この 3 つはいずれも同じオフラインのリセット手順をたどります。共通するのは、人がすでにシステムへ入れず、データベースから変更するしかない状況だという点です：

- **唯一の admin がまだ初回ログインをしておらず、初期パスワードを紛失した**（システムに入れません）。
- **脆弱な認証情報のスキャンによる起動拒否**：release の起動時に admin ロールを持つすべてのアカウントをスキャンし、いずれかが
  公知の脆弱な認証情報（たとえば `admin123`）を使っている場合、サービスは**起動を拒否**し、先にリセットするよう求めます。
- **管理者が自分を許可送信元 CIDR の外に締め出した**：アカウントに許可送信元 CIDR（`users.allowed_cidrs`）を設定すると、
  リストの外のアドレスからのログイン、更新、接続の作成はすべて拒否されます。**他に管理者がいる場合はこの手順を取らないでください**——その人に
  画面上でリストを戻してもらえば済みますし、その経路はフィールド単位の監査差分を残します。他に管理者がいないときにだけ、
  下のオフラインでの消去を使います。

パスワード紛失と脆弱な認証情報のスキャンの 2 つでは、入れ替えるのはパスワードです。手順は、DB へ直接接続して**単一のトランザクション**内で
パスワードハッシュ、`must_change_password=true`、`password_histories` への書き込みを同時に行うことです
（3 つを同じトランザクションにするのは、不整合な状態を残さないためです）。
例（PostgreSQL、`$1`＝新しい bcrypt ハッシュ、`$2`＝admin のユーザー id）。
**`$1`／`$2` はプレースホルダーです。そのまま `psql` に貼ると `ERROR: there is no parameter $1` が返ります——実際の値へ手作業で置き換えてください**：

```sql
BEGIN;
UPDATE users SET password = $1, must_change_password = true, password_changed_at = now() WHERE id = $2;
INSERT INTO password_histories (user_id, password_hash, created_at) VALUES ($2, $1, now());
COMMIT;
```

bcrypt ハッシュは**外部のツール**で生成する必要があります。例：

```bash
htpasswd -bnBC 10 "" '新しいパスワード' | tr -d ':\n'
```

あるいは任意の言語の bcrypt ライブラリを使います（cost は 10。製品の既定と同じです）。

**本番イメージにはハッシュを生成するツールも Go ツールチェーンも入っていません。** ご自身のマシンで生成してから SQL に貼り付けてください。
（`backend/scripts/generate_hash.go` には `//go:build ignore` が付いており、どのバイナリにも組み込まれません。
Go 環境のある開発マシンで `go run` として実行するしかありません。）

**3 つ目の状況（送信元制限で締め出された場合）ではパスワードに触れないでください**：パスワード自体には問題がなく、入れ替えても
パスワード変更の強制をもう一度たどるだけです。`password_histories` への書き込みも不要です。そのアカウントの許可送信元 CIDR を空文字列に消すだけで済みます——空文字列は
送信元を制限しないという意味です。例（PostgreSQL）：

```sql
-- どの行を消すか先に確認します（allowed_cidrs が空文字列なら送信元制限なしです）
SELECT id, username, allowed_cidrs FROM users WHERE username = 'admin';
-- そのアカウントの許可送信元 CIDR を消去します（$1＝前の行で確認した id）
UPDATE users SET allowed_cidrs = '' WHERE id = $1;
```

消去後にサービスを再起動する必要はありません。ログイン、更新、接続の作成はいずれも毎回この列を読み直すため、次回のログインから送信元制限は掛かりません。
ログインしたら直ちに画面でリストを必要な範囲に設定し直してください。空のまま放置するのは、このアカウントがどのアドレスからでも入れる状態にしておくのと同じです。

本製品はオンラインの救済 API を**提供しません**（DB への書き込み権限を持つ人はもともと直接リセットできるため、リモートの権限面を別途開くことはしません）。

上記 3 つのオフラインでのリセットは、いずれも**製品の監査を経ません**。この経路はアプリケーションを迂回するため、`audit_logs` に対応する行は残りません。
その変更の記録は、配備者自身の変更管理で残してください（誰が、いつ、なぜデータベースへ接続したか）。製品側からあとで見えるのは、
復旧後のログインの監査行（送信元アドレスを含みます）と、画面に戻ってリストを設定し直したときのフィールド単位の差分です。

### 消去してやり直す
```bash
docker compose down -v
rm -rf ./data/*          # bind mount のデータは down -v では消えないため手動で削除します（既定は ./data。DATA_PATH を独自設定している場合はそのパス）
docker image prune -a
docker compose up --build
```

### macOS：フロントエンドを変更しても画面が更新されない（HMR が発火しない）
macOS の Docker volume は fsnotify が不安定で、Vite がファイルの変更を検知しないことがあります。
`docker compose restart frontend` は使わないでください（bind-mount の競合で ENOENT のクラッシュを起こします）。代わりに：
```bash
docker compose up -d --force-recreate frontend
```

### バックエンドの変更が反映されていないように見える（Air のホットリロードが古いバイナリで動作）
複数ファイルを行き来して編集している途中の壊れた状態では、Air のビルドが失敗し、古いバイナリで動作し続けます。変更後は：
```bash
docker compose restart backend
```

### SSO（OIDC）ログインのテスト——dex ターゲット（開発スタックのみ）

開発スタックには IdP のテストターゲットとして dex（CNCF の軽量 OIDC provider）が同梱されています。構成は `docker/dex/config.yaml` にあります。

**ターゲットの情報**：
- issuer: `http://dex.localhost:5556/dex`（**バックエンドのコンテナ内とブラウザで同じ文字列を共有します**。下の説明を参照）
- client_id / client_secret: `custodexa-dev` / `custodexa-dev-secret`
- redirect URI: `http://localhost:3000/api/v1/auth/oidc/callback`
- テストアカウント：`oidcuser@dex.localhost` / `oidcpass123`（一般利用者）、
  `conflict@dex.localhost` / `conflictpass123`（`preferred_username` を意図的に `admin` にしてあり、同名衝突の拒否を確認できます）

**設定手順**：
1. `.env` に `PUBLIC_BASE_URL=http://localhost:3000`、
   `OIDC_ALLOWED_INTERNAL_HOSTS=dex.localhost` を設定し（release モード以外では、ここに列挙したホスト名は http も許可されます）、
   必要に応じて `http://dex.localhost:5556/dex` を `OIDC_DEDICATED_ISSUERS` に追加します（追加しない場合は共有 ID ドメインとみなされ、
   受け入れ条件に組織の所属条件を含める必要があります）。変更後は `docker compose up -d --force-recreate backend` を実行します。
2. admin でログイン → OIDC プロバイダーの管理ページで provider を作成します（issuer / client_id / secret は上記のとおり）。
3. ログアウトすると、ログイン画面にその provider の SSO ボタンが表示されるはずです。

**discovery の確認（provider を設定する前に行うと、誤った判断を大幅に減らせます）**：
```bash
# バックエンドのコンテナ内（go-oidc が実際にたどる経路）——応答の issuer は設定値と一字一句同じでなければなりません
docker compose exec backend wget -qO- http://dex.localhost:5556/dex/.well-known/openid-configuration
# ブラウザ側（host 側）
curl -s http://dex.localhost:5556/dex/.well-known/openid-configuration
```

> **なぜホスト名が `dex.localhost` でなければならないのか**：go-oidc は discovery 応答の issuer を**文字列全体で比較**するため、
> バックエンド（コンテナ内で解決）とブラウザ（host 側で解決）が同じ文字列を使う必要があります。IP リテラルは使えません。backend コンテナ内の
> `127.0.0.1` は backend 自身を指し、`extra_hosts` はホスト名の解決を変えられるだけで、IP リテラルの loopback という意味は変えられないからです。
> `dex.localhost` なら両側から到達できます。compose の network alias によりコンテナ内の DNS は dex コンテナへ解決し、
> ブラウザ側は RFC 6761 に従って loopback へ解決し、`127.0.0.1:5556` のポートマッピングを経て同じ dex に届きます。
> alias、ポート、`docker/dex/config.yaml` の issuer——この 3 つは必ず同期させてください。

> dex は `docker-compose.dev.yml` にしか存在せず、本番スタックにこのサービスは含まれません。ポートは `127.0.0.1` にバインドされ、LAN には公開されません。

## API ドキュメント

API ドキュメントの唯一の正は [API_SPEC.md](../API_SPEC.md) です。本プロジェクトはコメントから生成する 2 つ目の
API 成果物を維持しません。

その中の**エンドポイント索引**は、実際に登録されたルートからテストが生成し、`TestAPIIndex` が双方向の一致をガードします。
索引にルートが欠けていても、実在しない項目が含まれていてもテストは red になります。ルートを変更したら再生成してください（**開発スタック**で実行します。
`.env` で `COMPOSE_FILE=docker-compose.dev.yml` を有効化していれば `-f` は不要です）：

```bash
docker compose run --rm --no-deps -v ./docs:/app/cmd/server/testdata/docs-rw backend \
  go test ./cmd/server -run '^TestAPIIndex$' -update
```

普段テストを実行するコンテナは `docs/` を読み取り専用でマウントしているため（ガードが検証対象を書き換えてはいけません）、再生成には
上のように書き込み可能なマウントを追加した使い捨てのコンテナが必要です。索引以外の文章の節は引き続き人手で保守します。

ルート自体には golden baseline による保護もあります（`cmd/server/testdata/route-golden`）。意図的にルートを変更したときは
同じく再生成が必要で、**その diff は commit の中で一項ずつ目視で確認してください**：

```bash
docker compose exec backend go test ./cmd/server -run '^TestRoutesMatchGolden$' -update
```
