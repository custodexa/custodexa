# セキュリティ問題の報告

## 公開 issue は立てないでください

セキュリティ上の問題を見つけた場合は、GitHub の**非公開脆弱性報告**をご利用ください。

**[非公開で報告する](https://github.com/custodexa/custodexa/security/advisories/new)**
（リポジトリの Security タブ → Report a vulnerability）

この窓口から送られた報告はメンテナだけが閲覧でき、アドバイザリが公開されるまで何も
公になりません。本プロジェクトは特権アクセス管理の製品であり、公開 issue は、稼働中の
あらゆるデプロイに対する攻撃手法を攻撃者へそのまま手渡すことになります。

## 書けるなら書いてほしいこと

以下はいずれも**あると助かる**もので、**必須ではありません**。項目が欠けていることを理由に
報告が却下されることはありません。

1. 影響を受けるバージョンまたはコミット
2. 関係するコンポーネントとプロトコル（SSH／RDP／VNC／データベース CLI／K8s exec／
   Web 管理画面／API）
3. 再現手順。できれば最小構成の環境で
4. 影響。攻撃者が何を得るのか、そのために事前にどの権限が必要なのか
5. クレジットの希望（匿名を希望する場合はその旨）

**実在の資格情報、個人データ、顧客データは決して含めないでください。**
再現に特定のデータが必要な場合は、その形式を説明してください。データそのものは貼らないでください。

## テストの前提ルール

- テストの対象は、**ご自身が所有しているデプロイ、または書面で許可を得たデプロイ**に
  限ります。公開のテスト用インスタンスはなく、本プロジェクトが他者のデプロイに対する
  テストを許可することもできません。
- データの破壊、テスト用でないデータへのアクセス、サービス妨害を目的とした負荷試験は
  行わないでください。

## 報告後に期待できること

**本プロジェクトは応答時間（SLA）を約束しません。** これは意図的なものです。個人が
維持しているプロジェクトであり、「24 時間以内に応答」「7 日以内に修正」といった数字は
それを保証する主体を欠くため、書き記しても守れない一文になるだけだからです。

代わりに明示するのは、**対応の優先順位**です。

| 深刻度 | 対応 |
|---|---|
| **Critical** | 進行中のすべての作業を中断します。いかなる機能開発よりも優先します |
| **High** | 次の作業のまとまりより前に組み込みます。機能項目と優先順位を争うことはありません |
| **Medium / Low** | バックログへ入り、他のセキュリティ項目とあわせて計画します |

すでに実環境で悪用されているもの、または PoC が公開されているものは、1 段階引き上げます。

### 深刻度の決め方

判断基準に CVSS スコアは用いません。本製品は接続を集約するシステムであり、同じ技術的欠陥でも
実際の影響は「攻撃者はすでに管理面の内側にいるのか」「認証を経ない入口から到達できるのか」に
大きく左右されます。これはまさに CVSS の基本値がもっとも捉えにくい部分です。CVSS ベクタを
提供いただければ記録しますが、深刻度は次の 3 つの軸で決めます。

- **到達性**: 未認証で発火するのか。一般利用者としてか。管理者としてか。ホスト上からのみか。
- **前提条件**: 特定の設定やデプロイ構成を要するのか。既定の設定で踏むのか。
- **結果**: 資格情報の露出／接続集約の回避／監査または録画の回避／権限昇格／サービス妨害／
  情報漏えい

**修正が難しいことを理由に深刻度を下げることはありません。** 修正が難しい場合の対応は、
評価を調整することではなく、緩和策を公開することです。

### 「修正しない」も正当な結論です

修正しないという判断は妥当な結論のひとつですが、必ず理由を添えます。正当な理由の典型は、
前提が成り立たない場合（挙動の読み違いに基づく報告である）、脅威モデルの外にある場合
（たとえば「署名鍵を持つ管理者は署名し直せる」といった、仕様書ですでに述べている境界）、
あるいは同等の代替統制が存在し運用文書に記載されている場合です。

## 公表について

**修正がリリースされるまでは詳細を伏せてください。**

報告から **90 日**が経っても修正がリリースされない場合は、追加の許可なくご自身で公表して
かまいません。これは**あなたの権利であり、本プロジェクトからの期限の約束ではありません**。
90 日以内に修正が存在する保証はありませんが、まだ直っていないという理由だけで、既知の問題が
無期限にあなたの手を縛ることもありません。

修正がリリースされる際は **GitHub Security Advisory** として公表し、影響、影響を受ける
バージョン、緩和策、そして報告者へのクレジット（匿名を希望される場合を除く）を記載します。
CVE ID は必要に応じて GitHub 経由で申請します。

## 本プロジェクトにないもの

時間を無駄にしないよう、ここに挙げておきます。

- **バグバウンティ**: ありません。予定もありません。
- **法的なセーフハーバー**: ありません。本プロジェクトは個人が維持しており、法的拘束力の
  ある保証を提供できません。上記のルールに従った善意の報告者に対してメンテナが法的措置を
  取ることはありませんが、それは意思の表明であって、法的な約束ではありません。
- **公開のテスト用インスタンス**: ありません。ご自身のデプロイでテストしてください。

## 依存関係の既知の状況

**MSSQL 接続に用いる `sqlcmd` バイナリは、古いライブラリのバージョンを内包しています。**
本プロジェクトはこのバイナリを上流（Microsoft go-sqlcmd）の**ソース**からビルドしており
（`docker/backend/Dockerfile` の `sqlcmd-builder` ステージ、`v1.10.0` に固定）、v1.10.0 は
その最新リリースです。**その依存関係ツリーは上流の `go.mod` が決めるものであり、本プロジェクトは
それを上書きしません。** 独断でバージョンを上げることは、上流が検証した組み合わせから外れる
ことであり、フォークを維持するのと変わりません。したがって方針は「上流のリリースに追随する」
であり、上流の更新を待っています。

**判断できること**: ほとんどのアドバイザリは、本プロジェクトが使用していない機能経路
（SSH 接続、コンテナ管理のサブコマンド）に該当します。

**判断できないこと**: このバイナリに対して到達性の分析を確実に行う手段はありません。
スキャナは実際の呼び出し経路ではなくパッケージのバージョンを比較し、ビルドは `-w -s` で
シンボルテーブルを取り除いています。
**そのため本プロジェクトは、これらのアドバイザリが無害であるとは主張しません。**

**実際に存在する構造上の制約**（約束ではなく、ビルドのたびに機械的に検証されます）:
このバイナリは非特権ユーザーとして動作し、書き込み可能なパスを持たず、setuid もなく、
本番イメージにシェルは含まれません。

MSSQL 接続機能を使用しないデプロイは影響を受けません。

RDP/VNC で使用する guacd は、そのベースシステムがセキュリティ更新を受けなくなっています。
状況とデプロイ上の含意は
[デプロイ構成の制約](ops/deployment-topology-limits.md)を参照してください。

## サポート対象のバージョン

1.0 以降、セキュリティ修正は**最新のマイナーバージョン**にのみ提供されます。過去のマイナー
バージョンへのバックポートはありません。本プロジェクトに複数のブランチを維持する余力はなく、
そうでないと約束しても現実には持ちこたえられないからです。
