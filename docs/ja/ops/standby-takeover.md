# アプリケーションホストのスタンバイ切り替え

[English](../../ops/standby-takeover.md) | [繁體中文](../../zh-TW/ops/standby-takeover.md) | **日本語** | [他の言語 →](../../README.md)

> 対象バージョン：Custodexa 1.12.2。
>
> **この手順の検証状況**：プロジェクトは 1 台のマシン上で 1 回演習しました。2 つの compose プロジェクトを 2 台のアプリケーションホストに、3 つめをデータベースに見立て、ガードの挙動、確認コードの経路、スタンバイでのログインをその演習で通しています。物理的な 2 台のホスト間では演習していません。頼りにする前に、お使いの環境で 1 回演習し、記録を残してください。
>
> 関連文書：[デプロイ形態の制限](./deployment-topology-limits.md)、[バックアップとリストア](./backup-and-restore.md)、
> [デプロイとアップグレードの SOP](./upgrade-sop.md)（§2.6b はガードのメッセージ、§3.4 は実行中のロック状態）。
>
> 本書のすべての `docker compose` コマンドは external database 形態のアプリケーションホスト上で実行するため、2 つのファイル（`-f docker-compose.yml -f docker-compose.external-database.yml`）を指定するか、`.env` の `COMPOSE_FILE` にそれらを並べておく必要があります。前段に自前の ingress がある場合、その並びは 3 ファイルになります。以下では簡潔にするため `docker compose` とだけ書きます。

---

## 1. この手順が扱う範囲

**形態**：PostgreSQL はアプリケーションホストの外で動きます。アプリケーションホストは**プライマリ**と**スタンバイ**の 2 台で、同じファイルから用意し、どちらもそのデータベースへ向けます。動いているのはプライマリだけです。プライマリが止まったとき、計画したものでも障害でも、同じデータベースへ向けてスタンバイを起動し、引き継ぎます。

**これは何であり、何でないか**：

| これである | これではない |
|---|---|
| コールドスタンバイ。スタンバイはプライマリが停止したあとにだけ起動する | 2 つめの稼働中インスタンス。1 つのデータベースに 2 つのインスタンスというのは[デプロイ形態の制限](./deployment-topology-limits.md)が除外する形態です。ここでも単一インスタンスガードは起動時に 2 つめを止めて確認を求めるだけで、誰かが確認したあとに 2 つが動くことを防ぎはしません |
| 人かスクリプトが開始する手順 | 自動フェイルオーバー。製品の中にプライマリを監視するものも、スタンバイを起動するものもない |
| アプリケーションホストの喪失からの復旧 | データベースの喪失からの復旧。この形態ではデータベースがデータの唯一の複製であり、失われたときの戻り道は、どのホストで行うにせよ[バックアップとリストア](./backup-and-restore.md) |
| ホスト障害のあとサービスが戻るまでの時間を短くする方法 | 故障したホストだけが持っていたものの喪失を防ぐ方法（§7） |

2 台のホストが共有するものはすべてデータベースにあります。各ホストが自分だけで持つもの、まず録画は、§2.3 に挙げ、§7 でもう一度挙げます。この手順がお使いの復旧目標を満たすかを判断する前に、両方を読んでください。

## 2. 必要になる前にスタンバイを用意する

### 2.1 データベースをアプリケーションホストの外に置く

スタック同梱の postgres はアプリケーションホスト上にあるため、既定の形態ではホストとデータが一緒に落ちます。external database overlay は同梱の postgres を外し、バックエンドを指定したサーバーへ向けます：

```env
# すべてのアプリケーションホストの .env（プライマリとスタンバイで同じ値）
COMPOSE_FILE=docker-compose.yml:docker-compose.external-database.yml
EXTERNAL_DB_HOST=db.example.internal
EXTERNAL_DB_PORT=5432
DB_NAME=custodexa
DB_USER=custodexa
DB_PASSWORD=<そのサーバー上のアカウントのパスワード>
DB_SSLMODE=verify-full
```

そのサーバーをどこで動かすかは自由です。組織が既に運用している PostgreSQL サーバー、マネージドサービス、自前の 2 台目のマシンのいずれでも、切り替えの手順は同じです。サーバーに求められるもの：

- **PostgreSQL 16**。データベースとアカウントは初回起動の前に作成しておきます（空のデータベースに対する初回起動でバックエンドがスキーマを作成します）。
- **両方のアプリケーションホストからのアクセス。** サーバー側でクライアントのアドレスを制限しているもの（`pg_hba.conf`、ファイアウォール、セキュリティグループ）は、必要になる日より前に、プライマリだけでなくスタンバイのアドレスも許可しておきます。データベースに届かないスタンバイは、最悪の瞬間に見つかります。
- **接続の TLS。** データベースはネットワーク越しになりました。`DB_SSLMODE=require` が下限で、サーバー証明書を検証できるなら `verify-full` にします（PCI DSS 要件 4）。同梱の形態で `disable` なのは、その接続がホストの外に出ないからです。その値をこの形態に持ち込まないでください。
- **直接接続、またはセッションモードのプール。** 単一インスタンスガードはセッション単位のロックを保持します。トランザクションモードのプールはそれを壊します（[デプロイ形態の制限](./deployment-topology-limits.md)を参照）。
- **バックアップの対象はこのサーバーになります。** バックアップ手順の表にあるデータベースの行は、もうアプリケーションホストの `DATA_PATH` の下にありません。`pg_dump` はこのサーバーに対して、その運用者が実行し、録画と監査のディレクトリはこれまでどおりアプリケーションホストからバックアップします（§8）。
- **TCP keepalive。** アプリケーションホストがクラッシュすると、そのデータベースセッションはサーバー側の TCP keepalive が見切りをつけるまでサーバー上で開いたままです。残っているあいだは単一インスタンスロックを保持し続けるため、スタンバイは §4.3 の確認手順を通ることになります。PostgreSQL は `tcp_keepalives_idle`、`tcp_keepalives_interval`、`tcp_keepalives_count` でこれを決め、出荷時の既定ではオペレーティングシステムに従います（Linux ではおよそ 2 時間）。`tcp_keepalives_idle=300`、`tcp_keepalives_interval=10`、`tcp_keepalives_count=3` を設定したサーバーは、クライアントの最後のパケットからおよそ 5 分半で見切りをつけます。プロジェクトの演習ではこの値で、確認コードつきで起動したスタンバイがクラッシュの 5 分 46 秒後に自力でロックを取得しました（サーバーの 5 分半に、スタンバイの 15 秒の再試行間隔の一部が加わった時間です）。確認手順はどちらでも同じで、この設定が縮めるのは、そのあとスタンバイがバナーを表示し続ける時間だけです。

データベースを別のマシンで自分で動かすなら、出荷されているイメージで足ります。データベース専用ホストの最小の compose ファイル（keepalive の設定と TLS を含む）：

```yaml
# データベースホスト上の docker-compose.yml
services:
  postgres:
    image: postgres:16.15-alpine3.24
    command:
      - postgres
      - -c
      - ssl=on
      - -c
      - ssl_cert_file=/certs/server.crt
      - -c
      - ssl_key_file=/certs/server.key
      - -c
      - tcp_keepalives_idle=300
      - -c
      - tcp_keepalives_interval=10
      - -c
      - tcp_keepalives_count=3
    environment:
      POSTGRES_DB: custodexa
      POSTGRES_USER: custodexa
      POSTGRES_PASSWORD: <アプリケーションホストの DB_PASSWORD と同じ値>
    ports:
      - "5432:5432"
    volumes:
      - /opt/custodexa-db/postgres:/var/lib/postgresql/data
      # このホスト名で発行した server.crt と server.key。鍵ファイルは 0600 で、コンテナ内の postgres ユーザー（出荷イメージでは uid 70）が所有していること。そうでなければサーバーは読み込みを拒否する
      - /opt/custodexa-db/certs:/certs:ro
    restart: always
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U custodexa"]
      interval: 10s
      timeout: 5s
      retries: 5
```

`verify-full` を通すには証明書の名前が `EXTERNAL_DB_HOST` と一致し、アプリケーションホストが発行元の CA を信頼している必要があります（`DB_SSLMODE=require` は名前と信頼の検査を省き、暗号化だけ行います）。待ち受けアドレスとクライアントアドレスの制限は、ほかのデータベースサーバーと同じく、ホストのファイアウォールか `pg_hba.conf` で行います。

### 2.2 スタンバイホストを用意する

スタンバイは同じファイルから用意した 2 台目のアプリケーションホストで、必要になるまで**停止**したままにします。プライマリと同時に用意し、プライマリに変更を加えるたびに用意をやり直します。遅れたスタンバイは、誤ったバージョンや誤った設定で引き継いでしまうからです。

1. **同じイメージ、同じバージョン。** スタンバイ上で本番イメージをプライマリとまったく同じようにビルドまたはロードします（デプロイとアップグレードの SOP §2.2）。プライマリのアップグレードはそのままスタンバイのアップグレードでもあります（§8）。前のバージョンのままのスタンバイは新しいスキーマに対して起動を拒み（SOP §2.6）、新しいバージョンのスタンバイはプライマリの足元でスキーマを移行してしまいます。
2. **同じ compose ファイルと同じ `.env`。** プライマリから `docker-compose.yml`、`docker-compose.external-database.yml`（ingress overlay を使うならそれも）、`docker/`、`.env` をコピーします。2 台のあいだで異なる値は下表の少数だけで、シークレットを含めそれ以外はすべて同一でなければ、スタンバイはプライマリが書いたものを読めません。

   | キー | スタンバイでは |
   |---|---|
   | `DATA_PATH` | このホスト自身のデータルート。`${DATA_PATH}/recordings` と `${DATA_PATH}/audit` を SOP §1.3 の権限で作成する |
   | `TLS_DOMAIN`、`TLS_IP_SAN`、`PUBLIC_BASE_URL` | 利用者が名前か仮想アドレス経由で接続し、切り替え時にそれをスタンバイへ向け直すなら変更なし（本書が前提とする構成）。利用者が別のアドレスでこのホストに来るなら、このホスト自身の値 |
   | `TRUSTED_PROXIES` | 内蔵プロキシのサブネットは両ホストで同じ。自前の ingress なら、このホストから見たそのアドレス |
   | `INSTANCE_GUARD_ACK` | 存在しない。障害後の切り替えは停止ページで確認します（§4.3）。この変数はスクリプト向けの代替経路で、その切り替えのときだけ設定し、あとで削除する |

   ```bash
   # プライマリ上で：スタンバイに必要なデプロイ用ファイル。.env と tls/ を含む
   rsync -a --relative \
     docker-compose.yml docker-compose.external-database.yml docker/ .env tls/ \
     standby:/opt/custodexa/
   ```

   `.env` にはデータベースのパスワードが、`KEK_PROVIDER=env` モードでは KEK の材料も入っています。`tls/ca-private/` にはローカル CA の秘密鍵があります。シークレットを運ぶのと同じやり方で運び、スタンバイでも `0600` の権限を保ってください。
3. **同じ TLS 材料。** `TLS_MODE=selfsigned` では `tls/` をコピーし、スタンバイが同じ CA と証明書を提供するようにします。初回起動で自分の CA を生成したスタンバイは、すべてのブラウザとすべての SSO コールバックにとって、新しい信頼されていないサイトです。`TLS_MODE=provided` では同じ証明書ファイルを置きます。
4. **KEK の材料がスタンバイで使えること。** そうでなければスタンバイは起動してもシール状態のままで、何も読めません：

   | `KEK_PROVIDER` | スタンバイに必要なもの |
   |---|---|
   | `env` | `.env` 内の同じ `ENCRYPTION_KEY`（上のコピーで一緒に届く） |
   | `ui` | ディスク上には何も不要。**スタンバイの起動後、誰かがスタンバイのアンシール画面でアンシールの材料を入力する必要がある。** 切り替え時間にはその人が含まれる |
   | `kms` | 保管先へこのホストから到達できること、そして**スタンバイの起動後にアンシールする人がいること**。その人はスタンバイのアンシール画面でローカルの管理者のユーザー名とパスワードを入力し、そこに表示された保管先を照合したうえで、その事業者の資格情報を改めて入力します。切り替え時間にはその人が含まれます。保管先の設定は共有のデータベースから来るため、このホストでの事前の準備は不要です。資格情報はメモリにのみ保持し、`.env` とともに複製されることはないため、切り替える人がその時点で入手できる必要があります |

   **委任型のスタンバイは、起動しても提供できる状態にはなりません。** `kms` モードの資格情報は、プライマリで動いていたアンシール世代のメモリにしか存在せず、スタンバイが自力で入手する手段はありません。したがってシール済みの状態で立ち上がり、待機します。その資格情報を持つ人と、時間外にどう連絡するかを、`ui` モードの担当者とあわせて切り替えの計画に書き入れてください。シール済みのあいだ、スタンバイはヘルスチェックとシール関連のエンドポイントしか提供しないため、§5 の最初の 3 項目より後の確認は、アンシールが終わるまで実施できません。
5. **オフサイト証拠保管をプライマリで有効化し、検証しておく**（システム設定 → オフサイト保管）。プライマリが作った録画をスタンバイが再生できる唯一の手段です。これがなければ、スタンバイにはそれらが 1 つもありません（§2.3）。設定はデータベースにあるため、スタンバイは起動した時点で使えます。スタンバイ自身のホストがストレージのエンドポイントに到達できることは別途必要です。
6. **利用者が接続するアドレス。** 切り替え後に利用者がどうスタンバイへ届くかを今決めます。DNS 名か仮想アドレスをスタンバイへ向け直せば、`PUBLIC_BASE_URL`、証明書、すべての SSO リダイレクト URI が変わらずに済みます。本書はこの構成を前提にしています。それ以外の構成では、スタンバイ上のそれらの値と、IdP 側のリダイレクト URI が変わります。
7. **1 回起動し、それから落とす。** プライマリを**停止**した状態でスタンバイを起動し（計画切り替え、§3）、検証し（§5）、元に戻し、スタンバイを停止したままにします。離れる前に確かめることが 2 つあります。スタンバイの `docker compose ps` に何も表示されないこと、そしてそのホスト上で起動時にスタックを立ち上げるものが何もないことです（`restart: always` は存在するコンテナにしか作用せず、`down` はコンテナを削除します）。

### 2.3 スタンバイが持っていないもの

データベースは共有ですが、ホストのファイルシステムは共有ではありません。切り替えのあと、プライマリが自分のディスクに置いていたものはスタンバイにはありません：

| プライマリのホストにしかないもの | スタンバイでの帰結 | 軽減するもの |
|---|---|---|
| `${DATA_PATH}/recordings` 下の録画ファイル | セッションの記録はデータベースにあるが、再生にはファイルが要る。スタンバイがファイルを持たない録画は、複製がオフサイト保管に上げられていた場合にだけ再生できる（初回再生時に取得する） | オフサイト証拠保管。プライマリのディスクが回収できるときはディレクトリのコピー（§4.4） |
| `${DATA_PATH}/audit` 下の監査フォールバックファイルとシール期間のジャーナル | 当時データベースに届かなかった監査行はこれらのファイルに残る。`KEK_PROVIDER=ui` モードのシールジャーナルも同様 | ディスクが回収できるときのディレクトリのコピー。行はまずデータベースへ行くため、通常時の量は少ない |
| コンテナ内 `/var/lib/custodexa/exports` のエクスポート成果物（証拠パッケージ、ローテーション証跡レポート） | それらのダウンロードは無効になる。ジョブの行はデータベースにあるので、スタンバイでエクスポートし直す | オフサイト保管は完了した成果物の複製を保持期間内は保持する。それ以外はなし。このディレクトリはどのホストでもコンテナローカル |
| オフサイト取得キャッシュ（`OFFSITE_SPOOL_PATH`） | 録画は初回再生時に取得し直す | 不要。キャッシュである |
| 進行中のセッションと、その録画の書かれていない末尾 | ホストの障害でプロトコルセッションはすべて終わり、そのように終わったセッションの録画はアップロードされない（オフサイト保管は正常に終了した録画だけをアップロードする）。スタンバイの初回起動時に、それらのセッションは `end_reason=backend_restart` で閉じられる | なし。§7 を参照 |

## 3. 計画切り替え（プライマリが健全なとき）

プライマリホストのメンテナンス、§2.2 手順 7 の演習、そのあとプライマリへ戻すとき（§6）に使います。確認コードは関わりません。正常に停止したプライマリは単一インスタンスロックを解放し、スタンバイはすぐにそれを取得します。

1. **停止を告知する。** プライマリが止まると、進行中のプロトコルセッションはすべて終わり、利用者にはターミナルが閉じたように見えます。時刻はアップグレードと同じ基準で選びます。
2. **プライマリのキューを空にする。** アップグレードで停止する前と同じ確認です。監査キューが空であること（SOP §2.4）、オフサイト保管が有効ならアップロードキューも空であること（SOP §3.2b）。プライマリ停止時にまだアップロードキューにある録画は、プライマリが戻るまでプライマリのディスクに留まります。
3. **プライマリを停止する。**

   ```bash
   # プライマリ上で
   docker compose down
   docker compose ps          # 何も表示されないこと
   ```

   `down` はコンテナを削除するので、次の再起動でスタックが勝手に戻ることはありません。`stop` はコンテナを残し、`restart: always` がそれらを戻してしまいます。ロックは backend コンテナが停止した時点で解放されます。
4. **スタンバイを起動する。**

   ```bash
   # スタンバイ上で
   docker compose up -d
   docker compose logs backend | grep -E 'InstanceGuard|資料庫連線成功|Listening|監聽'
   ```

   ログにはデータベース接続、続いて `[InstanceGuard]` の警告を含まない通常の起動が出ます。ロックは空いていたということです。`KEK_PROVIDER=ui` と `kms` では、バックエンドはここでアンシールを待ち、それ以外もすべて待ちます。
5. 利用者が接続する**アドレス（DNS または仮想アドレス）をスタンバイへ向け直し**、検証します（§5）。

戻すときはホストを入れ替えて同じ手順です。

## 4. プライマリが故障したあとの切り替え

### 4.1 判断し、プライマリが戻ってこないようにする

スタンバイを起動する前に、次の 2 つを確定し、どう確かめたかを記録します：

- **プライマリはサービスしていない。** 利用者向けのネットワークを失っただけでデータベースには届いているホストは、まだ稼働中のインスタンスです。その隣でスタンバイを起動するのは除外された形態であり、ガードの確認手順（§4.3）はまさにそれについてあなたに責任を求める場所です。ネットワーク側から見て曖昧なら、ホスト自体で障害を確かめます（コンソール、電源状態、ハイパーバイザ）。
- **スタンバイが引き継いでいるあいだ、プライマリが勝手に戻ってこない。** プライマリのコンテナには `restart: always` が付いています。クラッシュ後に再起動したホストはスタックも一緒に戻します。スタンバイを起動する前に、次のいずれかでそれを不可能にします。ホストの電源を落としたままにする。データベースサーバーで、どちらを残すか決めるまでプライマリのアドレスを拒否する（`pg_hba.conf` かファイアウォール）。ホストに届くなら、そこで `docker compose down` する。なぜこれが重要かは §4.4 にあります。

### 4.2 スタンバイを起動し、ガードの答えを読む

```bash
# スタンバイ上で
docker compose up -d
docker compose logs -f backend
```

結果は 2 通りです：

- **バックエンドが通常どおり起動する。** データベース接続の行があり、`[InstanceGuard]` の警告がない。プライマリのデータベースセッションはすでに消えていた（ホストが正常に停止していたか、データベースの keepalive がすでに回収していた）ということです。§5 へ進みます。
- **バックエンドがロックは別のデータベースセッションに保持されていると報告し、サービスを開かない。** プロセスは終了せず、ガードの停止モードにとどまります。15 秒ごとにロックを取り直しながら、対処のためのページを 1 つ開きます。その一節は次のようなものです（`pid`、時刻、`code` は毎回異なります）：

  ```
  CRITICAL：單實例鎖由另一個資料庫工作階段持有。本版不支援多實例部署，本實例未啟動服務。
    持鎖者：application_name=custodexa-instance-guard pid=268 backend_start=2026-09-05T13:50:58.116184Z code=2936aed7c309
    風險：兩個實例同時執行會造成金鑰快取、匯出工作、錄影落地與封存期留痕的資料問題（見 docs/ops/deployment-topology-limits.md）。
    處置 (a)：若確認另一實例仍在執行：先停止它，再重啟本實例（無需任何設定）。
    處置 (b)：若確認無其他實例在執行（例如持鎖者是主機當機後殘留的工作階段）：開啟本實例的守衛攔下頁 /instance-guard，以管理員帳密重打確認碼 2936aed7c309 後確認，不需重啟；腳本化替代路徑為設定環境變數 INSTANCE_GUARD_ACK=2936aed7c309 後重啟。兩者都會寫入稽核事件並在管理介面顯示橫幅，直到鎖由本實例取得。
    澄清：這不是資料庫損毀；本次啟動未由本實例執行 migration 或任何資料寫入；INSTANCE_GUARD_ACK 綁定上列指紋，持鎖者變更後失效；確認後兩實例並存造成的資料問題由確認者承擔，守衛只保證此事被記錄。
  ```

  続いて、停止モードがバックエンドのポートで開いたこと、提供されるのはヘルスチェックとシールの状態と停止確認だけであること、マイグレーションは実行せずデータベースへの書き込みも行っていないことを伝える行が出ます。

  **停止ページを開きます**：スタンバイの `https://<アドレス>/instance-guard`。`<アドレス>` はスタンバイ自身のアドレスです（利用者が接続するアドレスはまだプライマリを指しているかもしれません）。ログインは不要で、到達条件はアンシールのページと同じ、つまり `SEAL_UNSEAL_ALLOWED_CIDRS` に設定した送信元ネットワーク範囲です（未設定なら制限しません）。停止中、それ以外のパスはすべて 503 を返します。

  ページが示す事実はログと同じです。保持者の `application_name`、`pid`、`backend_start`、この衝突の確認コード、2 つのインスタンスが同時に動くとデータが壊れること、そしてこのインスタンスはまだ何も書いていないのでデータベースの破損ではないこと。再取得の間隔ごとにガードの状態を読み直すので、再読み込みしなくても状況に追随します。

  保持者は故障したプライマリのデータベースセッションで、TCP keepalive が見切りをつけるまでサーバー上で開いたままです（§2.1）。スタンバイはマイグレーションを実行しておらず、何も書いていません。開いている待ち受けは、そのページを提供する 1 つだけです。`backend_start` はそのセッションが作られた時刻、つまりプライマリが最後に起動した時刻のあたりです。その値がプライマリの最後の起動と一致し、プライマリの停止が確認できているなら、それが残留セッションの姿です。各項目の読み方と、`pg_locks` を `pg_stat_activity` に結合する任意の診断クエリは SOP §2.6b にあります。データベースサーバーでそのセッションを終了させないでください。ガードの復旧にそれは要らず、下の手順こそ本書が演習したものです。

  **もう一方のインスタンスが実際に動いていた場合**は、それを停止するだけで足ります。スタンバイは次の再試行でロックを取得して自力で起動し、確認も再起動も要らず、ページは「起動しました」に変わります。

### 4.3 確認コードで確認し、スタンバイに引き継がせる

§4.1 が確定してからです。停止ページで：

1. **引き受けにチェックを入れる**：もう一方のインスタンスが動いておらず、勝手に再起動しないことを、ホスト自体で確かめたこと。
2. **確認コードを打ち直す**：保持者のフィンガープリントの横に表示されているものです。
3. **管理者のアカウントとパスワードを入力**し、送信します。

3 つとも必要で、どれか欠けた送信は拒否されます。確認コードは、ページが先ほど表示したものではなく、**送信した時点の**保持者と照合されます。入力中に保持者が変わっていれば送信は拒否され、ページは新しいフィンガープリントと新しいコードを示して打ち直しを求めます。管理者の資格情報が正しくない場合も拒否され、確認は受け付けられません。資格情報の失敗が 5 回続くと、ページは 5 分間、送信を受け付けなくなります。この待ち時間は停止中のプロセスの中だけにあり、プロセスが終われば消え、その一部たりともデータベースには書かれません。停止中のインスタンスはデータベースに書き込まないからです。これが止めるのは自動化された推測であって、ホストにアクセスできる人ではありません。ページがここでは管理者の資格情報を検証できないと答えたら、そのインスタンスはユーザーテーブルを読めていません（別バージョンのスキーマか、データベースの問題）。本節末尾のスクリプト向けの経路を使ってください。

送信が受け付けられると、ページは**起動中**を表示します。インスタンスは停止ページの待ち受けを閉じ、マイグレーションと残りの起動処理を実行し、サービスのポートを開き直します。**そのあいだポートは応答しませんが、それが正常です。** ページは応答するまで問い続け、応答したら「起動しました」に変わり、ログインへの導線を示します。再起動は不要で、`.env` を編集する必要もありません。

ここからスタンバイは完全にサービスします。ログイン、接続、監査、スケジュールのすべてです。残留セッションが消えるまでに見えるもの：

- ログインしたすべての利用者に常設バナー「このインスタンスは確認コードで起動しました。単一インスタンスロックは別のデータベースセッションが保持しています」が出ます。管理者にはさらに確認した人のアカウント、保持者のフィンガープリントとコードが表示されます。
- `GET /api/v1/seal/status` は `instance_guard.state = overridden`、`reason = ack_page` を返し、メトリクス `custodexa_instance_guard_overridden` は 1 です。
- `audit_logs` の行が 1 つ。`resource=instance_guard`、`event=overridden`、`actor` は確認した管理者アカウント、その出所はページとして記録され、送信が通るまでの資格情報の失敗回数も入ります。製品が記録するのはアカウントです。**なぜ**その確認をしたのかは製品の中にないので、§4.1 の証拠はインシデントチケットに記録してください。

データベースが残留セッションを回収すると、スタンバイは次の再試行（15 秒ごと）で自力でロックを取得します。ログに `[InstanceGuard] 已重新取得單實例鎖（自 overridden 起未持鎖 … ms，reason=…）；告知解除` が出て、バナーは画面の次のポーリングで消え、`state` は `held` になり、`audit_logs` に `event=regained` の行が増えます。**再起動は不要です。** かかる時間はデータベースサーバーの keepalive 設定で決まり（§2.1）、オペレーティングシステムの既定ではおよそ 2 時間です。

確認することの意味の全体は SOP §2.6b にあります。ここで大事なのは一文だけです。**プライマリが実は生きていたなら、いま 2 つのインスタンスが同じデータベースに書いており、それが招くデータの問題をガードは防ぎません。それは確認した人のものです。** あなたとそれのあいだに立つのが §4.1 です。

**スクリプト向けの代替経路：`INSTANCE_GUARD_ACK`。** 同じ確認は、スクリプトで進める切り替えや、ページに到達できないホストでは、ページを経ずに与えることもできます。最新のメッセージの code をスタンバイの `.env` に入れ、バックエンドを起動し直します：

```bash
# スタンバイ上で：値は最新メッセージの code= で、この衝突にだけ有効
printf 'INSTANCE_GUARD_ACK=%s\n' 2936aed7c309 >> .env
docker compose up -d backend
docker compose logs backend | grep InstanceGuard
```

ログには `CRITICAL：以 INSTANCE_GUARD_ACK 啟動：單實例鎖仍由 … 持有；本實例將照常執行 migration 與服務；此確認已記錄（actor=operator via env）` が出て、通常の起動が続き、`reason` は `ack_page` ではなく `ack_startup` になります。**この経路は誰が確認したかを記録できません**：監査行の `actor` は `operator via env` で、環境変数は自然人を識別できないため、その人はチケットに属します。そのあと `.env` から `INSTANCE_GUARD_ACK` の行を削除します。何も再起動する必要はありません。この値はあの残留セッション 1 つに束縛され、保持者が変わった時点で無効ですが、`.env` に残った古い行は次の担当者に再利用を誘います。

### 4.4 故障したホストが戻ってきたとき

プライマリのホストは、修理や再起動であとから戻ってくるかもしれません。そのスタックはまだ `.env` にあり、あなたが落としていない限り、コンテナ一覧に `restart: always` 付きで残っています。3 つの状況があります：

- **スタンバイがロックを保持している（`state = held`）**：プライマリのバックエンドは起動時にガードに止められ、§4.2 と同じ一節を、保持者をスタンバイとして出力し、同じ停止ページを提供します。これはガードが設計どおりに働いている姿で、§4.1 がガードに頼らない理由でもあります。ガードが効くのは、スタンバイが実際にロックを持ってからです。スタンバイがサービスしているあいだにプライマリの停止ページで確認するのは、除外された形態です。停止させたままにするか、落としてください。
- **スタンバイがまだ `overridden`**（残留セッションがまだ回収されていない）：プライマリの新しいバックエンドも残留セッションによって停止モードに留め置かれます。残留セッションが回収されたとき、**両方が再試行しており、先に着いたほうがロックを取ります**。それがプライマリなら、プライマリはログに `[InstanceGuard]` の警告を出さずに通常どおり起動し、両方がサービスします。スタンバイは `overridden` のままで、`reason` も当初の確認の出所のままなので、状態だけを見ても何が起きたかは分かりません。分かるのは保持者です。`GET /api/v1/instance-guard` と、詳細を再読み込みしたあとの管理者向けバナーでは、保持者の `backend_start` が故障したプライマリの最後の起動時刻ではなく、その新しいバックエンドが立ち上がった時刻になっています（スタンバイのログにも新しい保持者が、多くても 10 分に 1 回出力されます）。これが §4.1 が閉じる窓であり、スタンバイが `held` を報告するまでプライマリを起動させないのはそのためです。
- **プライマリのディスクが回収できる**：それが持つ録画と監査のファイル（§2.3）はスタンバイへ移せます。データベースは録画をコンテナ内のパスで参照し、それは両ホストで同じなので、同じ相対配置でスタンバイの `${DATA_PATH}` 下にコピーしたファイルは再生時に見つかります。

  ```bash
  # 回収したプライマリのディスクからスタンバイのデータルートへ。相対配置と所有者を保つ
  rsync -a /mnt/primary-disk/custodexa/data/recordings/ standby:${DATA_PATH}/recordings/
  rsync -a /mnt/primary-disk/custodexa/data/audit/      standby:${DATA_PATH}/audit/
  ```

  クラッシュ時に進行中だったセッションの録画はファイルとしては渡りますが、書き込み完了の確認は取れていません。再生できるかは、ファイルがどこまで書かれていたかによります。監査フォールバックファイルは既存の手順で再投入します（[バックアップとリストア §7.3](./backup-and-restore.md#73-リストア後の監査の退避ファイルの回収)）。

スタンバイが `held` になり、プライマリをサービスに戻すと決めたら、戻すのは計画切り替えです（§6）。プライマリの `.env` には以前の切り替えの `INSTANCE_GUARD_ACK` 行が残っているかもしれません。無効ですが（保持者が変わっているため）、いずれにせよ削除してください。

## 5. 切り替えの検証

§3 または §4 のあと、スタンバイ上で実行します。切り替え完了と宣言する前に、すべての行が成立している必要があります。

| # | 確認 | 方法 | 期待される結果 |
|---|---|---|---|
| 1 | サービスが起動している | `docker compose ps` | backend、frontend、guacd、tls-proxy が稼働。postgres はない（この形態には含まれない） |
| 2 | バックエンドが健全 | `docker compose exec backend wget -qO- http://localhost:8080/health` | 正常な応答 |
| 3 | ロックの状態 | `curl -sk https://<アドレス>/api/v1/seal/status`。`overridden` のあいだは、管理者として `GET /api/v1/instance-guard` も確認するか、バナーの保持者を見る | §3 のあとは `instance_guard.state` が `held`。§4.3 のあとは `held` か、`overridden` で保持者の `backend_start` が §4.2 のメッセージと同じ。`reason` は停止ページで確認したときは `ack_page`、`INSTANCE_GUARD_ACK` で確認したときは `ack_startup` です。`overridden` の監査行は、前者では確認したアカウント、後者では `operator via env` を記録します。保持者の `backend_start` が新しくなっていれば、別のバックエンドがロックを取ったということです（§4.4） |
| 4 | ログインできる | パスワードを知っているアカウントでログイン | ログイン成功。利用者のアカウント、ロール、資産はすべてある（データベースにあるため） |
| 5 | データはプライマリのもの | 資産一覧と監査ページを開く | プライマリで作成した資産が並ぶ。プライマリが最後に書いた監査行があり、その後にいまスタンバイで行ったログインが続く |
| 6 | アンシール済み | `KEK_PROVIDER=ui` か `kms` ならアンシール画面 | 完了している。`kms` モードでは、画面はまずローカルの管理者のユーザー名とパスワードを求め、次に保管先を表示するので導入記録と照合し、そのうえでその事業者の資格情報を受け取る。完了後は `seal/status` がアンシール済みを報告する。`env` なら、バックエンドのログにシール関連の拒否がない |
| 7 | 録画 | プライマリで作られ、オフサイトへ上げられた録画を再生 | 取得の待ち時間ののち再生される（オフサイト録画の初回再生はダウンロードを伴う） |
| 8 | アドレス | 利用者が使うアドレスでサービスを開く | スタンバイに着く（`docker compose ps` のコンテナ名を証明書と応答に照らす） |
| 9 | 送信元の帰属 | いま行ったログインの監査行 | プロキシではなく自分のクライアントアドレスが記録されている。そうでなければこのホストの `TRUSTED_PROXIES` が誤っている |

```bash
# スタンバイ上で、確認 1 から 3
docker compose ps
docker compose exec backend wget -qO- http://localhost:8080/health
curl -sk https://<アドレス>/api/v1/seal/status
```

障害後の切り替えは、インシデントチケットに §4.1 の証拠、使った確認コード（あれば）、スタンバイが `held` を報告した時刻が記録されて完了です。

## 6. プライマリへ戻す

修理したプライマリは逆向きの計画切り替えで戻します（§3）。告知し、スタンバイのキューを空にし、スタンバイで `docker compose down`、プライマリで `docker compose up -d`、アドレスを向け直し、検証します。プライマリを起動する前に、そのあいだにスタンバイが変えたものをすべてプライマリが持っていることを確かめます。同じバージョン、`.env` の変更、そしてプライマリでも再生したいならスタンバイが作った録画です（§4.4 を逆向きに行うか、オフサイト保管に任せます）。

## 7. 計画外の切り替えで保たれないもの

これはこの手順の境界であり、そのまま復旧計画に入れられる形で述べます。ホスト障害のあとの切り替えでは：

- **進行中のセッションはすべて終わり**、どのプロトコルでも利用者は接続し直します。セッションの移行はありません。
- **それらのセッションの録画は障害の時点で切れます。** クラッシュの瞬間までのファイルは故障したホストのディスクにあり、オフサイト保管には上げられず（アップロードは正常に終了した録画が対象）、スタンバイにもありません。スタンバイでは、それらのセッション記録は `end_reason=backend_restart` を示し、再生できる録画はありません。ディスクが回収できればファイルをコピーでき（§4.4）、書かれていたところまで再生されます。
- **正常に終了したがアップロードが終わっていなかった録画**は、故障したホストのディスクが回収されるまでそこにしかありません。さらされる窓は障害時点のアップロードキューです（テキストの録画はセッション終了から数秒でキューに入り、グラフィカルの録画は最短でも 1 分後。到達できないストレージのエンドポイントを待っているものはさらに長く待ちます）。
- **オフサイト保管が無効なら、プライマリで作られた録画はスタンバイでは 1 つも再生できません。** プライマリのディスクが回収されコピーされるまでです。
- **故障したホストでファイルにフォールバックしていた監査行**（データベースに届かなかったあいだに書かれたもの）は、ファイルが回収され再投入されるまで、データベースにもスタンバイにもありません。
- **エクスポート成果物**のうち作成中またはまだダウンロードされていなかったものは、そのダウンロードリンクが無効になります。スタンバイでエクスポートし直せ、完了していたものは保持期間内ならオフサイト保管から取得できる場合があります。
- **ブラウザのログインは失われず、保たれます**：2 台のホストは `JWT_SECRET` を共有しており、プロジェクトの演習ではプライマリが発行したアクセストークンをスタンバイがそのまま受け付けました。利用者が失うのはプロトコルセッションであって、ログインではありません。
- **停止ページで確認した場合、その確認は確認した管理者アカウントに帰属します。`INSTANCE_GUARD_ACK` で確認した場合は、人ではなく `operator via env` に帰属します。** いずれにせよ、その判断の根拠はチケットにあって、製品の中にはありません。

上の一覧のうち、製品が自力で回復するものは 1 つもありません。データベースが持つもの、つまりアカウント、資産、資格情報、ポリシー、監査行、セッション記録、スケジュール、オフサイトの保管台帳は無傷です。ホスト上には最初からなかったからです。

## 8. バックアップ、アップグレード、デプロイ形態の制限への影響

- **バックアップ**（[バックアップとリストア](./backup-and-restore.md)）：データベースはデータベースサーバー上で、`docker compose exec postgres` の代わりにそのサーバーに対する `pg_dump` でバックアップします。録画と監査のディレクトリは**ファイルを持つすべてのアプリケーションホスト**からバックアップし、切り替えのあとはそれが 2 台になります。`.env` と `tls/` は両ホストから取ります。リストア手順のうち postgres を起動してダンプを読み込む段階はデータベースサーバー上で行います。整合性の要件（データベースとファイルの保存先が同じ時点であること）は変わらず、マシンをまたぐぶん満たしにくくなります。バックアップの窓のあいだは稼働中のアプリケーションホストを停止してください。
- **アップグレード**（[デプロイとアップグレードの SOP](./upgrade-sop.md)）：アップグレードはこれまでどおり稼働中のホストを停止して行い、そのあと**両方**のホストに新しいイメージとファイルを入れ、1 台だけを起動します。足並みをそろえてアップグレードされていないスタンバイは、引き継げないスタンバイです（§2.2 手順 1）。SOP が除外するローリングアップデートはここでも除外です。プライマリのアップグレードを「カバー」するためにスタンバイを起動することは決してしないでください。
- **デプロイ形態**（[デプロイ形態の制限](./deployment-topology-limits.md)）：この手順はいかなる形態も追加しません。どの時点でもデータベースに対して動くアプリケーションインスタンスはちょうど 1 つで、それが単一インスタンスガードの要求するものであり、そうでなくなったときに知らせるのがガードです。

## 出力の機密情報検出：対象範囲と運用上の判定

検出は SSH、K8s、データベースコンソールの解析済みテキスト出力のみを走査します。RDP/VNC の画面、暗号化・圧縮・符号化された内容（Base64 を含む）は対象外です。端末の制御シーケンスは描画も除去もしません。符号化により照合を回避でき、一致は機密情報を**含む可能性**を示します。未検出は不存在を意味しません。この機構は警告のみで、配信済みのバイトを遮断・変更しません。

出力ルールの追加、無効化、変更は**新しいセッション**から適用されます。進行中のセッションは開始時のルール集合を維持します。アップグレード、リストア、切り替え後は方向、有効状態、プロトコルを確認し、新しいテキストセッションで適用ルールを確認してください。インストール後の初期ルールは計16件で、元の入力12件、agent 向けの入力阻止2件、カード番号・秘密鍵ヘッダーの出力2件です。組み込みカードパターンが元のままであれば Luhn 検証も行います。編集後は通常の正規表現となり、カード番号の検証は行いません。

同じルールとセッションの一致は5秒の窓で集約し、セッション終了時に残りを確定します。アラートと転送には識別子、ルール、回数、時刻を残し、command は空で、一致した原文やバイト位置は保存しません。reason_code の `o1:<base36 count>` が回数を表し、webhook には `possible_sensitive_output.count` もあります。これは含む可能性の兆候であり、全出力を走査した証明ではありません。

容量制限のあるキューがあふれると、そのセッションの走査を無効化し、出力は継続します。既存の監査検索で action=`output_scan_disabled`、resource=`session`、当該セッションの resource_id を確認します。details は session_id と reason=`queue_overflow` のみで、出力原文を含みません。サーバーログだけでは監査記録の代わりになりません。それ以降の出力は未走査として扱い、既存の権限で証拠を確認し、負荷を確認してから新しいセッションを開始します。スキャナーの失敗もサーバーログに残りますが、アラートがないことは走査成功の保証ではありません。

共通のマスキングプリミティブは完全置換したテキストと置換回数を返しますが、**本バージョンの製品応答経路には接続されていません**。録画、コマンド記録、その他の証拠には適用しません。原文には既存の保存期間、アクセス制御、バックアップ／リストア手順が引き続き適用されます。


### 主体と資格情報の完全性の対象範囲

検証画面はロール割り当て、主体の種別／所有者、資格情報の状態を個別に表示します。アップグレード後、新しいスナップショットを含む最初のチェックポイントまで、新しい二行は「対象外」です。検出は即時ではなく、検証、チェックポイント作成、トークン発行前に照合します。不一致は項目ごとに `principal_state_integrity`／`principal_state_mismatch` イベントと通知を生成し、差分には識別値だけを含めます。不一致や照合エラーでも発行を続行します。エラーは不明としてログに記録し、業務データを変更しません。サービス層の状態投影行の actor は `system` とし、操作者は既存の HTTP 監査行で記録します。

互換性は一方向です。新版は旧チェックポイントを検証できますが、旧版は新しいスナップショットキーを完全には検証できません。キーの削除、再署名、旧来の単一機構の失敗イベント一意インデックスへ戻すことは禁止です。ロールバックにはアップグレード前の整合したバックアップとリストア手順が必要です。ペイロードは現行の最新バージョン（現在 v3）を維持します。

## Agent MCP の運用

有効な人間の owner を指定して agent 主体を作成します。owner または管理者が名前と有効期限付きの agent token を発行し、一度だけ表示される平文を実行者のシークレット保管先に保存します。agent は user ロールのみを持ち、資産とアカウントの許可範囲を明示します。agent を動かすマシンに stdio クライアント `custodexa-mcp` を https://github.com/custodexa/custodexa-mcp からインストールします。`go install github.com/custodexa/custodexa-mcp@latest` を使うか、リリースのバイナリを取得します。リリースのバイナリは、同じリリースで公開された `checksums.txt` で検証します。環境変数 `CUSTODEXA_AGENT_TOKEN` を `custodexa-mcp` に渡し、`CUSTODEXA_MCP_URL` を HTTPS の `/api/v1/mcp` に設定します。人間の JWT と cookie はこのエンドポイントでは使用できません。stdio クライアントは転送のみを行い、判定と証跡保存はサービス側で行います。token をコマンド引数や報告書に記載しないでください。

agent が申請したタスクが人の承認を待つかどうかは、申請対象ごとの資産のアクセスポリシー区分で決まります。資産自身に `access_policy` が設定されていればそれを、なければ全体の `access_policy_default` を使います。`approval` 区分の項目は、その資産を範囲に含む承認者が判断するまで保留されます。`open` と `reason` 区分の項目は申請時に承認され、`auto_approved: true` とポリシースナップショットとして記録され、承認票は付きません。出荷時の既定では多くの資産が `approval` 以外に入るため、設定を変更しない環境では agent のタスクがすべて自動承認されます。人の判断を必須にするには、対象資産の `access_policy` を `approval` に設定するか、全体の `access_policy_default` を `approval` にします。必要な承認票数は `access_request_min_approvals` で決まります。この選択は agent に最初の資産許可を与える前に決め、運用手順書に明記してください。自動承認も記録は完全に残りますが、人による統制ではありません。

ローテーションでは新しい名前付き token を発行し、実行者のシークレットを更新し、新しい MCP 接続で資産の可視性を確認してから旧 token を失効させます。既存 token の秘密を直接交換する機能や、バックアップから平文を自動復元する機能はありません。失効は旧 token のセッションを閉じます。ハンドルを別の token や MCP 接続に引き継ぐことはできません。リストアやスタンバイへの切り替えの後は MCP 接続を新規作成し、必要に応じてタスクを申請します。メモリー上のハンドルと 60 秒間の冪等キャッシュは再起動を越えて保持されません。再開前に token とタスクの保存状態を確認します。

インシデント時は該当 token を失効または停止し、必要なら agent を無効化して、タスク、ツール台帳、HTTP リクエストの監査記録を確認します。探索ブレーカーは token を停止してイベントを記録します。owner または管理者が理由を付けて解除しますが、停止済み token は再有効化されないため、新たに発行してください。この計数が対象とする参照は一種類だけです。すなわち、実在し、かつその agent に一度も開示されたことのない資産への参照です。存在しない、または削除済みの資産 id への参照は retired、過去に開示された資産への参照は revoked に分類され、いずれもイベントとしては記録されますが、作動しきい値には計上されません。識別子を手当たり次第に列挙しても計上されないイベントが並ぶだけであり、これを一般的なスキャン検知として説明しないでください。これは範囲外の実在資産へ繰り返し手を伸ばす行為に対する統制です。より広い列挙は、アラートルールと申請レート方針で扱ってください。拒否された参照の意味を判断する前に、ブレーカーイベント一覧の `class` 欄を確認します。通知は既存の webhook／Slack に `owner_id` 付きで送られます。個人受信箱ではなく、本人への到達を証明しません。可視 exposure は migration 後から記録され、以前の可視履歴は復元しません。拒否された参照を不正と判断する前にこの境界を確認します。

Token の期限切れ、紐付いたタスク項目の期限切れ、タスク終了は、既存セッションと実行中のツールを終了し、現在のコマンド完了を待ちません。期限の現状確認は 250ms ごとですが、この間隔は完了 SLA ではありません。失効は既存の終了経路を使います（目標は 3 秒以内、遅延時は証跡を記録）。対象は本システムが作成したセッションだけで、遠隔のバックグラウンド処理の停止や実行済み変更の取消しは保証しません。実行中リクエストの取消しはそのセッションを閉じます。POST 間のクライアント離脱は即座には検出できず、5 分間の idle lease 満了でハンドルを終了します。即時切断検出とは記載しないでください。

`completed` はプロンプトを再観測したことだけを示し、コマンドの終了も成功も保証しません。プロンプトは偽装でき、バックグラウンドの出力が混在することもあります。`timed_out` は結果不明です。再送前に後続出力を確認してください。同じハンドルの冪等キーは 60 秒間の重複書込みを抑止しますが、キーなしでは再実行され得ます。`needs_input` では実行者が `send_keys` で復帰を要求し、システムは自動で割込みを送りません。`read_screen` は行バッファーであり仮想画面ではありません。agent に返す文字列はマスクされますが、録画とコマンド記録は原文を保持します。マスクはルール駆動で、対象を個別に列挙する方式です。汎用の機微データ保護ではありません。適用されるのは、有効で `direction=output` かつ主体種別が agent を含み、プロトコルが一致するアラートルールで、一致した範囲をプレースホルダーに置き換えます。有効なルールに一致しない内容はそのまま agent に返り、出荷時のルールはカード番号パターンと秘密鍵ヘッダーパターンの二種類のみです。このルール一覧を「この環境が agent チャネルで何を機微と定めるか」の定義として扱い、許可した資産で実際に取得できるデータと突き合わせ、不足する種類はルールを追加してください。マスクは人間の端末、録画、コマンド記録には適用されません。

データベース、録画、チェックポイント、対応するバージョンの完全性鍵を保全します。pending 行が示すのは記録済みの意図であり、送達や完了ではありません。タスク／ハンドルに帰属できない呼出しはツール台帳の前で拒否し、当該 MCP HTTP 監査行に主体、ツール、理由コード、時刻を保存します。コマンド完全性の coverage 軸は監査調査ビューと一括エクスポートのみで提供します。単一 session 指定のエクスポートには coverage がありません。degraded 行がゼロでもコマンド欠落がなかった証明にはなりません。報告書の各版とタスク終了時刻を保持し、pending の結果を捏造しないでください。

切り替えは既存の MCP セッションを移行しません。再実行前に不明な結果を確認します。
