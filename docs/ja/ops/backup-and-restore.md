## 1. バックアップはデプロイ側が標準のツールで実行します

バックアップとリストアは `pg_dump`、`pg_restore`、`tar` を用います。本書は完全な手順を示します。インストールパッケージでデプロイした場合は、管理スクリプト `custodexa.sh` が §3.2 の停止してのバックアップを代わりに実行します（§3.8）。リストアは常に第 5 節に沿って手作業で行います。バックアップの保存場所、保持期間、暗号化、遠隔地への複製は、デプロイ側のデータガバナンスの範囲です。

---

## 2. 永続データの保存先

`docker compose` でデプロイする場合、永続データはすべて**単一のデータルート** `DATA_PATH`（`.env` で設定、既定は `./data`）の下に置かれ、bind mount でコンテナにマウントされます。

| 保存先 | コンテナ内のパス | 内容 | マウントする側 |
|---|---|---|---|
| `${DATA_PATH}/postgres` | `/var/lib/postgresql/data` | PostgreSQL のデータディレクトリ（すべての業務データ、監査記録、暗号化済みの資格情報と鍵のラップ） | postgres |
| `${DATA_PATH}/recordings` | `/var/lib/custodexa/recordings` | セッションの録画ファイル | backend、guacd（共有マウント） |
| `${DATA_PATH}/audit` | `/var/log/custodexa/audit` | 監査の退避ファイル、シール期間の記録 journal | backend |
| `${DATA_PATH}/exports` | `/var/lib/custodexa/exports` | 非同期のエクスポートの成果物（証拠パッケージ、ローテーション証跡レポート、コンプライアンスレポート）。**コンテナを作り直しても残りますが、バックアップのコマンドの対象ではありません**（下記参照） | backend |
| **オブジェクトストレージ**（任意） | コンテナのファイルシステム内にはありません | **オフサイトの証拠の複製**：録画と証拠パッケージのアップロードされた複製 | オフサイト保管の機能がアップロードします。**データルートの外にあります** |

> **最後の行はデータルートの一部ではなく、バックアップの手順も対象としません。** オフサイト保管の機能を有効にすると、録画と証拠パッケージの複製がデプロイ側自身のオブジェクトストレージのバケットへアップロードされます。その複製のバックアップ、保持、復旧は**すべてデプロイ側のストレージガバナンス**に属し、`tar` も `pg_dump` もそこには届きません。逆も忘れないでください。**オフサイトにあることはバックアップ済みであることを意味しません。** それはさらされる窓を短くする 2 つめの複製であって、バックアップの手順の代わりではありません（§3.3 参照）。データベース内の保管台帳（どの録画の複製がどのバケットのどの key にあり、アップロード時点のハッシュは何か）は**データベースのバックアップとともに移動します**。したがって台帳と遠隔のオブジェクトの対応は、両者の時点が揃っているかどうかに依存します（§3.1 参照）。

**上表の最初の 4 行はすべて bind mount であり、named volume はありません。** 直接の帰結が 2 つあります。

- `docker compose down -v` はデータを消去**しません**（`-v` が消すのは named volume だけです）。
- 逆に言えば、`DATA_PATH` ディレクトリそのものを削除または上書きすることは、すべてのデータを削除することであり、2 つめの複製はありません。

資産のパスワード変更の経路の設定（WinRM の経路でアップロードした CA 証明書を含みます）はデータベースの資産テーブルにあり、上表の 1 行目とともにバックアップされます。別の保存先はありません。

**残るがバックアップの対象ではないディレクトリ**：非同期のエクスポートの成果物は `/var/lib/custodexa/exports`（`EXPORT_ARTIFACT_PATH`、コンテナ内のパス）に置かれ、証拠パッケージ、ローテーション証跡レポート、コンプライアンスレポートがこの 1 つのディレクトリを共用します。本番の compose はこれを `${DATA_PATH}/exports` にマウントします。**これはバックアップの対象ではありません**。また成果物の種類によって保持期間と取得の方法が異なります。

- **証拠パッケージ**：成果物は保持期間（24 時間）の経過後にシステムが自動で消去し、期限が切れればダウンロードもできなくなります。これをバックアップする意味はありません。内容は申請者が改めてエクスポートを実行すれば取得できます。
- **ローテーション証跡レポート**：成果物の保持期間はスケジュールの設定によります（1 日から 3650 日）。期限が来れば同じく消去され、ダウンロードもできなくなります。スケジュールが生成したレポートには自然人の申請者がおらず、「申請者が再実行する」という経路はありません。監査の閲覧権限を持つ人がもう 1 件生成することはできますが、生成されるのは新しい生成時刻と新しい署名を持つ新しいレポートであり、すでに引き渡された同じ文書ではありません。レポートが述べる事実はデータベース（アカウント、パスワード変更の記録、ポリシーの設定）に由来し、バックアップにはそれらの事実が含まれます。
- **コンプライアンスレポート**：コンプライアンス対照ページから手動で生成します。保持期間は申請者が設定し（1 日から 3650 日、既定は 90 日）、期限が来れば同じく消去され、ダウンロードもできなくなります。レポートが述べるのはパッケージ化の時点の設定であり、改めて生成すると新しいデータ時点を持つ新しいレポートになり、同じ文書ではありません。レポートの根拠となる設定、条文、確認記録はデータベースにあり、バックアップに含まれます。

このディレクトリは bind mount なので、成果物はコンテナの再作成（バージョンのアップグレードを含みます）の後も残り、保持期間が終わるまでダウンロードできます。**§3 のバックアップのコマンドは意図的にこれを含めていません。** そこでの `tar` は `recordings` と `audit` だけを指定しており、理由は下記の機微性です。`DATA_PATH` 全体を複製するバックアップ（ファイルシステムのスナップショットなど）はこのディレクトリも取り込むため、`exports` を除外してください。リストアの後の結果は次のとおりです。ジョブの行はデータベースとともに戻りますが、成果物は戻りません。そのようなジョブのダウンロードは 410（`RULE_EXPORT_ARTIFACT_UNAVAILABLE`）を返し、一覧では完了のまま表示されます。**この点はレポートについて特に重要です。** レポートの保持期間は数年に及ぶことがあり、ホストの喪失を越えて残したい場合は、オフサイト保管を有効にするか、保持期間のうちに自分でダウンロードして持ち出してください。同梱の compose ではなく独自の compose ファイルで運用するデプロイは、このパスを自分でマウントする必要があります。マウントがなければ、このディレクトリはコンテナが存続するあいだしか存在せず、コンテナを作り直すたびに空になります。**その機微性に注意してください。** 証拠パッケージの成果物には**復号されたクリップボードの平文**と録画の本体が含まれます（§4 とエクスポートの説明を参照）。そのためこのディレクトリのファイル権限は `0700`／`0600` であり、一般のバックアップの流れに取り込んで平文の複製を広げるべきではありません。

オフサイト保管を有効にすると、この段落に経路が 1 つ加わります。**成果物の複製もアップロードされます**（証拠パッケージもレポートも同様です）。ローカルに成果物がない場合（消去された、あるいはコンテナの再作成で消えた場合）でも、その成果物が完了した時点で複製がアップロードされていれば、**成果物の保持期間のうちは**オブジェクトストレージから取得できます（取得時にハッシュを検証してから引き渡します）。期限を過ぎた場合は、遠隔の複製が残っていても一律にダウンロードを拒否します。**製品が遠隔のものを代わりに削除することはありません。** ローカルの成果物の消去も ジョブの行の整理も、オブジェクトストレージへ削除を発行しません。その複製がいつ消えるかは、デプロイ側がバケットに設定したライフサイクルのルール次第です。これは同時に、**平文の証拠パッケージの複製があなたのオブジェクトストレージに残る**ことも意味します。そのアクセス制御と暗号化は、本番のデータベースと同じ水準で扱う必要があります。

**オフサイトの取得用の一時領域**（`OFFSITE_SPOOL_PATH`、コンテナ内のパス）は、取得時に一度書き出して検証するための**コンテナローカルのキャッシュ**です。こちらも既定では bind mount されず、バックアップの対象ではありません。存続期間と総量の上限があり、内容は**平文**で、意味づけは複製ではなくキャッシュです。

### 2.1 データルートの外にある保存先（バックアップで最も漏れやすい箇所）

監査の退避ファイルとシール期間の journal の実際の保存先は、環境変数 `AUDIT_LOG_PATH` が決めます。**未設定の場合は相対パス `logs/audit_fallback` に戻ります。** このパスはプロセスの作業ディレクトリからの相対であり、`DATA_PATH` の下にはありません。

- **compose でのデプロイ**：どちらの compose ファイルも `environment:` で `AUDIT_LOG_PATH=/var/log/custodexa/audit` を明示しており、このパスは `${DATA_PATH}/audit` にマウントされています。したがってデータルートの中にあり、`DATA_PATH` をバックアップすれば含まれます。
- **単体バイナリでのデプロイ（compose を経由しない場合）**：`AUDIT_LOG_PATH` を自分で設定していないと、この 2 種類のファイルは**プロセスを起動したときの作業ディレクトリ**の下の `logs/audit_fallback/` に置かれます。`DATA_PATH` をバックアップしてもこれは含まれません。

> **デプロイの前に必ず行うこと**：compose 以外のデプロイでは必ず `AUDIT_LOG_PATH` を明示的に設定し、そのパスがバックアップの範囲に入っていることを確認してください。

この 2 種類のファイルは重要度が同じではないため、分けて理解する必要があります。

- **監査の退避ファイル**：データベースへの書き込みに失敗した場合、または監査のキューが満杯になった場合に、監査の記録がここへ書き込まれます（**ファイルへの退避のスイッチが有効な場合に限ります**。無効な場合、その一群の記録はそのまま破棄され、永久に失われます）。ここが担うのは「データベースが当時書き込めなかった一群の監査記録」であり、まさに事故の最中に最も必要となる記録です。**これらのファイル自体には完全性の保護が一切ありません。** 痕跡を残さずに変更も削除もできます。これらは機能低下の期間の手がかりであり、証拠として扱うことはできません。バックアップする目的は事後にデータを回収することであって、証明を得ることではありません。
- **シール期間の記録 journal**（次節を参照）。

**データルートの外にある 2 つめの箇所：オブジェクトストレージ。** オフサイト保管を有効にすると、録画と証拠パッケージの複製がデプロイ側自身のオブジェクトストレージのバケットに置かれます。これも同じくデータルートの外にあり、しかも**どの compose のマウントにも含まれません**。`tar -C "$DATA_PATH"` では取得できません。責任の所在をここで一度はっきりさせます。

- **製品が担うこと**：アップロード、データベースの保管台帳へのバケット、key、アップロード時点の SHA-256 の記録、取得時の検証。
- **デプロイ側が担うこと**：バケット自体のバックアップまたはリージョンをまたぐ複製、バージョニング、保持期間と期限到来時の整理、アクセス制御、保存時の暗号化。製品は遠隔のオブジェクトを削除しませんし、遠隔の複製が何らかの保護を受けているとも主張しません。それらの保護はすべてバケット側の設定から来ます（推奨のパラメーターは §3.7 参照）。

バックアップの範囲を計画するときは、これを**独立した 1 つのデータの保存先**として扱ってください。バックアップするかどうか、どこへ取るか、どれだけ保持するかは、いずれもストレージガバナンスの判断です。

**データルートの外にある 3 つめの箇所：`tls/`。** 内蔵 TLS プロキシの証明書はプロジェクトディレクトリ配下の `tls/` に置かれ、`DATA_PATH` の下にはありません。`fullchain.pem` と `privkey.pem` が外部向けの証明書で、自己署名モード（`TLS_MODE=selfsigned`）ではそれらを発行したローカル CA（`ca-private/custodexa-ca.key` と `ca-public/custodexa-ca.crt`）も併せて置かれます。**この CA 秘密鍵を失うと元の CA は使い続けられません**。新しい CA で発行し直すほかなく、CA を変えることは新しい CA 証明書をすべての利用者端末へ配り直すことを意味します。したがって `tls/` はバックアップの範囲に含め、`.env` と同じく暗号化して保管してください（同様に秘密鍵を含みます）。

### 2.2 シール期間の記録 journal

ファイル名は `seal_journal.bin` で固定され、`AUDIT_LOG_PATH` が指すディレクトリに置かれます。**専用の環境変数のキーはありません。** 内容はシール期間（KEK の画面入力モードでまだアンシールされていないあいだ）のアンシールの試行の記録で、固定長のリングバッファーであり、増え続けることはありません。

**これはバックアップに安全に含められますし、バックアップとともに安全にリストアできます。** アンシールの後、journal は自動的に監査へ書き戻されます。各イベントの冪等キー `IdempotencyUUID` は、journal の UUID、連番、イベントの種類、スロットから決定的に導出される値であり、`audit_logs` に一意索引があります。**同じ journal を何度再生しても、重複した監査の行は生成されません。**

### 2.3 本書の shell コマンドがデプロイの変数をどう取得するか（作業の前に読んでください）

第 3 節と第 5 節のコマンドは、デプロイ層の変数を 3 つ使います。`DATA_PATH`、`DB_USER`、`DB_NAME` です。**これらはあなたの shell に自動的には現れません。** `docker compose` が `.env` を読むのは、自分自身の `${...}` の置換のためであり、**呼び出し側の shell へ値をエクスポートすることはありません**。

そのため、コマンドに `"${DATA_PATH:-./data}"` のような既定値つきの形を書くのは危険です。`DATA_PATH` はあなたの shell ではほぼ確実に未設定であり、そのため常に `./data` にフォールバックします。**最悪のフォールバックはリストアで起きます。** `tar -xzf ... -C "${DATA_PATH:-./data}"` はバックアップを `./data` へ展開しますが、そのディレクトリはたいてい存在するため、**tar は成功し、エラーメッセージも一切出ません。** その後サービスが起動し、マウントされるのは空の本当のデータルートです。録画も監査もそうして消え、しかもそれが災害復旧のただ中で起きます。

そこで本書の手順は 2 つの規則に従って書かれています。

1. **`.env` から明示的に、しかも書かれたとおりに読みます。`source .env` は使いません。** `.env` は `docker compose` の env_file 形式であって、shell スクリプトではありません。本製品の `.env` のテンプレートには `LDAP_USER_FILTER=(uid=%s)` が含まれます。これを POSIX sh（Debian／Ubuntu の `/bin/sh` すなわち dash）に渡すと `Syntax error: "(" unexpected` となって全体が中断し、bash に渡すと配列の代入として扱われます。下の `env_get` は記述された値をそのまま取得し、`.env` に対して shell の評価を一切行いません。引用符、空白、`#`、括弧はそのまま取得されます。
2. **取得できなければ大きな声で失敗させます。** コマンドでは常に `"${VAR:-既定値}"` ではなく `"${VAR:?説明}"` を使います。バックアップとリストアは、圧力のもとで書かれたとおりに写す手順です。「先に何かをしておくのを忘れないこと」という前提は必ず飛ばされます。ですから値の取得の手順を飛ばしてしまっても、コマンド自体は中断して理由を出力するだけで、既定値で物事を「成功」させてしまうことはありません。**災害復旧の場面では、誤ったディレクトリを使いながら成功を報告するコマンドは、そのまま中断するコマンドよりはるかに悪いのです。**

次の断片は §3.2 と第 5 節の最初の手順であり、両方にそれぞれ再掲されています。**ここへ戻って読み直す必要はありません。**

```bash
# ---- このデプロイの変数の値を取得します ----
# ENV_FILE は、このデプロイの docker compose プロジェクトのディレクトリにある .env を指します。
# 作業する場所がそのディレクトリでない場合は、絶対パスに変えてください。例：ENV_FILE=/opt/custodexa/.env
ENV_FILE="${ENV_FILE:-./.env}"

# .env から 1 つのキーの値を書かれたとおりに取ります。同じキーが重複する場合は最後の 1 件を取ります（後勝ちという compose の挙動に合わせています）
env_get() { sed -n "s/^[[:space:]]*$1=//p" "$ENV_FILE" | tail -n 1; }

# shell の環境ですでに設定されているものを優先します。これは docker compose の優先順位（環境変数 > .env）と同じです
DATA_PATH="${DATA_PATH:-$(env_get DATA_PATH)}"
DB_USER="${DB_USER:-$(env_get DB_USER)}"
DB_NAME="${DB_NAME:-$(env_get DB_NAME)}"

# 目で一度確認します。この 3 つの値は、このデプロイが実際に使っている値でなければなりません
printf 'ENV_FILE=%s\nDATA_PATH=%s\nDB_USER=%s\nDB_NAME=%s\n' \
  "$ENV_FILE" "$DATA_PATH" "$DB_USER" "$DB_NAME"
```

> - `DATA_PATH` が相対パス（例：`./data`）として出力された場合、**以降のすべてのコマンドを同じ作業ディレクトリで実行しなければならない**ことを意味します。より確実にするには、その場で絶対パスに変えてください：`DATA_PATH="$(cd "${DATA_PATH:?}" && pwd)"`。ディレクトリが存在しない場合、`cd` がエラーを出力して `DATA_PATH` は空文字列になります。これは静かに通り抜けることはありません。以降のコマンドの `${DATA_PATH:?...}` は空の値に対しても同じく中断するためです（実測：`tar` は実行されません）。
> - 3 つの値のいずれかが空で出力された場合、`ENV_FILE` が誤ったファイルを指しています。**先へ進まないでください。**
> - 本書の `docker compose` コマンドは、デプロイのプロジェクトのディレクトリで実行することを前提としています（本番のデプロイであれば `docker-compose.yml` です）。開発版の compose も置かれている機械で検証する場合は、必ず明示的に `-f docker-compose.yml` を付けてください。
> - TLS を自社の ingress に担わせるデプロイ（`docker-compose.external-ingress.yml`）では、本書のすべての `docker compose` コマンドに `-f` を 2 つ付ける（`-f docker-compose.yml -f docker-compose.external-ingress.yml`）か、`.env` に `COMPOSE_FILE` を設定して既定にしてください。1 つだけ付けた場合は、内蔵 TLS プロキシの形態で起動します。
> - パッケージのデプロイ（§3.8）では、デプロイフォルダーで実行してください。そこの `.env` の `COMPOSE_FILE` が `current/` の下の compose ファイルを指しているので `-f` は不要ですが、`up` と `down` には `--project-directory .` が必要です（第 5 節のコマンドには付けてあります）。先に設定しておくことは §5.1 を参照してください。

## 3. バックアップの手順

### 3.1 一貫性の要件（3 つの保存先は同じ時点から取る必要があります）

3 つの保存先は互いに参照関係を持ちます。最も重要なのは、`sessions` テーブルの `recording_path` 列が録画ディレクトリ内のファイルを指している点です。

- **データベースが新しく、録画ディレクトリが古い場合** → データベース内の新しいセッションの記録が存在しない録画ファイルを指し、そのセッションは再生時にファイルを取得できません。
- **録画ディレクトリが新しく、データベースが古い場合** → 持ち主のいない録画ファイルが生じます。サービスの動作には影響しませんが、これらのファイルはどの一覧にも現れず、保持ポリシーによって消去されることもありません。

したがって**録画ディレクトリのほうがデータベースより新しいほうがよく、その逆は避けます**。以下の手順の順序はこれに従って組まれています。

**オフサイト保管を有効にすると参照の連なりが 1 本増えます。** セッションは指標を通じてデータベース内の保管台帳に対応し、台帳の行がさらにオブジェクトストレージのあるバケットと key を指します。**台帳はデータベースのバックアップとともに移動します。** そこで次のことが言えます。

- **台帳の作成より前のバックアップへリストアすると**、その後にアップロードされた遠隔のオブジェクトは**孤児**になります。遠隔にはまだ存在しますが（製品は削除しません）、データベースにそれを指す行が 1 つもありません。突き合わせるときは、監査の中の保管の連なりのイベント（アップロード、完全性の判定、ローカルの期限到来）とバケット内のオブジェクトの一覧を比較します。
- **ローカルのキャッシュが消去された後、`recording_path` は残っているがファイルはない、という状態は正常です。** バックアップが何かを取り漏らしたわけではありません。その録画のローカルの複製は保持の設定に従って消去されており、再生時には自動的にオブジェクトストレージから取得されます。これを「録画が失われた」と誤って判断すると、不要なリストアの操作につながります。

### 3.2 推奨の手順（サービスを停止する方法。一貫性が最もよい）

停止してのバックアップは、3 つの保存先を厳密に同じ時点で取得できる唯一の方法です。停止の時間はデータ量によります。

```bash
# 0. このデプロイの変数の値を取得します（原理は §2.3 参照）。この手順を飛ばすと、以降のコマンドは既定値を使うのではなく中断します。
ENV_FILE="${ENV_FILE:-./.env}"
env_get() { sed -n "s/^[[:space:]]*$1=//p" "$ENV_FILE" | tail -n 1; }
DATA_PATH="${DATA_PATH:-$(env_get DATA_PATH)}"
DB_USER="${DB_USER:-$(env_get DB_USER)}"
DB_NAME="${DB_NAME:-$(env_get DB_NAME)}"
printf 'ENV_FILE=%s\nDATA_PATH=%s\nDB_USER=%s\nDB_NAME=%s\n' \
  "$ENV_FILE" "$DATA_PATH" "$DB_USER" "$DB_NAME"

# このバックアップで共用するタイムスタンプ（以降の各手順がこれを参照します。手順ごとに時刻を取って食い違うことを避けるためです）
STAMP="$(date +%Y%m%d-%H%M)"

# 1. 新しいデータを生み出すサービスを停止します（論理バックアップのため postgres は残します）
docker compose stop backend guacd frontend

# 2. データベースの論理バックアップ（カスタム形式。選択的なリストアがしやすくなります）
docker compose exec -T postgres \
  pg_dump -U "${DB_USER:?DB_USER を取得できていません。先に手順 0 を実行してください}" \
          -d "${DB_NAME:?DB_NAME を取得できていません。先に手順 0 を実行してください}" -Fc \
  > "custodexa-db-${STAMP}.dump"

# 3. ファイルの保存先の複製（録画と監査）
#    **ローカルの複製のみが対象です**。オフサイト保管が有効な場合、オブジェクトストレージのバケット内の
#    複製はここに含まれず、そのバックアップはデプロイ側のストレージガバナンスに属します（§2.1 参照）。
#    キャッシュから消去済みの録画は、ローカルに固めるファイルがありません。
tar -czf "custodexa-files-${STAMP}.tar.gz" \
  -C "${DATA_PATH:?DATA_PATH を取得できていません。先に手順 0 を実行してください。既定値のまま続けないでください}" recordings audit

# 4. デプロイ層の設定ファイル（KEK の材料を含みます。第 4 節参照。必ず暗号化して保管してください）と TLS 証明書のディレクトリ
cp "$ENV_FILE" "custodexa-env-${STAMP}.bak"
#    tls/ には外部向け証明書の秘密鍵と、自己署名モードではローカル CA の秘密鍵が含まれます（§2.1 参照）。.env と同じく暗号化して保管してください
tar -czf "custodexa-tls-${STAMP}.tar.gz" tls

# 5. サービスを再開します
#    KEK モード B（KEK_PROVIDER=ui）：backend は再起動すると**シール済み**に戻り、
#    業務のルートは一律 503 を返します。誰かが画面でアンシールの材料を入力し直すまでそのままです。
#    この手順はコンテナを起こすだけであって、サービスの回復と同じではありません。
#    スケジュールされたバックアップでは「誰がアンシールするか」も一緒に組み込んでください（本節末を参照）。
docker compose start backend guacd frontend

# 6. その場で 2 つのバックアップが読めることを確認します（これをしないことは、自分が何をバックアップしたか分からないのと同じです）
#    コンテナ内の pg_restore を使うので、操作する機械に PostgreSQL のクライアントを入れる必要はありません
docker compose exec -T postgres pg_restore --list < "custodexa-db-${STAMP}.dump" | head
tar -tzf "custodexa-files-${STAMP}.tar.gz" | head
```

> **モード B（`KEK_PROVIDER=ui`）：このバックアップの一巡は、システムをシール済みへ戻します。**
> 手順 1 で backend を止め、手順 5 で起きてくるのは**シール済み**のインスタンスです。KEK の材料はディスクに残らないため、起動のたびに誰かがアンシールし直す必要があります。バックアップ自体は影響を受けません（`pg_dump` は postgres を使い、シールとは無関係です）。影響を受けるのはバックアップの**後**です。誰かがアンシールするまで、ログインも接続も一律 503 になります。
>
> それに伴う帰結が 2 つあり、定期バックアップを組むときに一緒に考える必要があります。
>
> - **バックアップをスケジュールすることは、サービスの中断をスケジュールすることと同じです。** 長さは「手順 5 から誰かがアンシールしに行くまで」です。深夜に走るバックアップには、たいてい見ている人がいません。バックアップを人のいる時間帯に組むか、この中断を受け入れたうえで、シール済みのときに監視がアラートを出すようにしてください。
> - シール期間の `/metrics` には `custodexa_audit_queue_depth` が**ありません**（非同期の監査はアンシールの後に組み立てられる段 2 に属します）。[アップグレード SOP §2.4](./upgrade-sop.md#24-停止の前に監査キューが空になったことを確認する)の「値が 0 になってから停止する」は、この状態では値を取得できません。それはメトリクスの故障ではありません。先にアンシールし、それからその確認を行ってください。
>
> モード A（`KEK_PROVIDER=env`）は影響を受けません。材料はデプロイ層から供給され、再起動すれば自ら取得するため、サービスは手順 5 とともに回復します。モード C（`KEK_PROVIDER=kms`）はモード B と同じくシール済みに戻ります。保管先の資格情報はメモリーにしかなく、アンシールのページで入力し直すためです（§4.3）。上の 2 つの帰結はモード C にも当てはまります。このデプロイがどれに当たるかの判別は第 4 節を参照してください。

### 3.3 停止しないバックアップ（有界の不一致を受け入れられる場合）

上記の手順 0（値の取得。これも省略できません）と手順 2 から 4 を実行し、1 と 5 を飛ばします（サービスを止めません）。手順 6 のバックアップが読めることの確認は同じく行ってください。`pg_dump` が取るのは開始した時点の一貫したスナップショットであり、データベース自体に問題はありません。不一致が生じるのは「データベースのスナップショットの時点」と「ファイルを複製する時点」のあいだに新しく生まれたセッションだけです。不一致の方向を安全な側（録画のほうが新しい）に抑えるため、**先にデータベースをバックアップし、その後に録画ディレクトリを複製してください**。

**オフサイト保管はこの順序を変えず、バックアップの範囲を狭めもしません。** アップロードは**事後の非同期**です。セッションの終了から複製が置かれるまでには窓があり（テキストの録画は秒単位、グラフィカルの録画は最低 1 分、エンドポイントに到達できない場合は回復するまで）、そのあいだローカルが唯一の複製です。停止しないバックアップが取る時点では、まだ**オフサイトへ渡っていない**録画が一群あるかもしれません。

### 3.4 してはならないこと

- **サービスの実行中に、ファイル層で `${DATA_PATH}/postgres` ディレクトリを複製しないでください。** 実行中の PostgreSQL のデータディレクトリは安全に複製できるファイルの集合ではなく、複製したものは起動できないことがあります。ファイル層のバックアップを取るなら、先に postgres のコンテナを停止する必要があります。
- **データベースだけをバックアップしないでください。** KEK の材料（第 4 節）、録画ファイル、監査の退避ファイルは、いずれもデータベースの中にはありません。
- **「オフサイトにある」を「バックアップ済み」と扱わないでください。** 2 つは別々に成立し、それぞれに穴があります。
  - **さらされる窓**：オフサイトへのアップロードはセッションの終了の後に初めて行われ、そのあいだローカルが唯一の複製です。窓のうちに機械が壊れれば、その録画に 2 つめの複製はありません。オフサイトはこの窓を**短くする**ものであって、なくすものではありません。
  - **孤児のオブジェクト**：より古いデータベースの時点へリストアすると、その後にアップロードされた遠隔のオブジェクトは台帳との対応を失います（§3.1 参照）。遠隔には残っていても、システムがそれを認識できません。
  - 逆方向の穴もあります。アップロードに一度も成功していない（再試行を使い切った）録画はローカルに 1 件しかなく、管理画面のオフサイト保管のページと失敗一覧は、まさにそれを見えるようにするためにあります。

### 3.5 バックアップファイル自体の保護

バックアップの内容には、暗号化された資産の資格情報、暗号化された鍵のラップ、そしてすべての監査記録が含まれ、その機微性は本番のシステムに劣りません。`.env` のバックアップにはさらに、KEK の材料と `JWT_SECRET` の平文が直接含まれます。バックアップのファイルは必ず暗号化して保管し、**KEK の材料と同じ場所に置いてはなりません**。両者を同じ場所に置くことは、エンベロープ暗号化を暗号化のない状態へ格下げすることと同じです。

管理スクリプトが作るバックアップファイル（§3.8）は、これらを 1 つのファイルにまとめます。`.env` は `env.bak` という名前で中に入ります。

- **モード A（`KEK_PROVIDER=env`、§4.1）：バックアップファイルにマスターキーが含まれます。** `env.bak` には `ENCRYPTION_KEY` が入っているため、KEK の材料とそれが保護するデータが一緒に運ばれ、暗号化されていない複製を手にした人は、暗号化して保存されたすべての資格情報を復号できます。完了画面は `.env` にマスターキーが含まれることを明示します。バックアップの際にパスフレーズでの暗号化を選ぶ（§3.8）か、ファイルがホストを離れる前に別の方法で暗号化し、パスフレーズや鍵はファイルと分けて保管してください。
- **モード B と C（§4.2、§4.3）：外部の材料はファイルに含まれません。** モード B のアンシールの材料とモード C の保管先の資格情報は、どのファイルにもどのテーブルにもなく、スクリプトもそれらを集めません。ファイルに記録されるのは、リストア後の照合に使うマスターキーのフィンガープリントまたはキー ID だけです。これらのモードでは `ENCRYPTION_KEY` は空でなければならず、値があるとバックアップは開始を拒否します。
- **`.env` はバイト単位でそのまま複製されるため、そこに書かれたほかのものもバックアップに入ります。** クラウドの資格情報を `.env` に書かないでください。たとえばモード C の保管先のアクセスキー、サービスアカウントのキーファイル、Vault のシークレットです。値としてもコメントとしても同じです。製品は保管先の資格情報を `.env` から読むことはなく（§4.3）、スクリプトもそれらをほかの文字列と区別できません。

### 3.6 `DATA_PATH` のファイル権限（デプロイ側の責任）

**bind mount の状況では、イメージ内で設定したディレクトリの権限は効きません。** 実際の権限はホスト側のディレクトリが決めます。デプロイ側は、`DATA_PATH` とその下の 4 つのサブディレクトリが**誰でも読める状態ではない**ことを自ら確保する必要があります。

録画ファイルには、利用者が対象ホスト上で入力した内容の全体が含まれます（対象側で入力したパスワードを含みます）。テキスト（SSH）の録画は root が所有する `0600` のファイルで、バックエンドが作成して `0700` に保つ日付ディレクトリの中に置かれます。グラフィカル（RDP と VNC）の録画は所有者が `1000:0` の `0640` のファイルで、録画ディレクトリの最上位に置かれ、uid 1000 で動く guacd が書き込みます。録画ディレクトリ自体は `1000:0`、モード `2770` です（[デプロイとアップグレードの SOP §1.3](./upgrade-sop.md#13-data_path-のファイル権限を確認します)）。guacd は所有者としてここに書き込み、バックエンドは root で動きますがファイルの権限を迂回する capability を持たないため、グループ 0 を通じてグラフィカルな録画を読み取り、名前を変更し、保持期間に従って削除します。この所有者、グループ、モードは変更しないでください。したがって、ホスト上の uid 1000 のアカウントは、製品を経由せずにグラフィカルな録画を読み取り、録画ディレクトリの最上位にあるどの項目も名前を変更したり移動したりできます。この uid は本システムを管理する人だけに割り当ててください。ファイルの権限は層の 1 つにすぎず、ディレクトリの権限が必要な 2 つめの層です。

エクスポートのディレクトリは事前の準備が不要です。バックエンドは起動のたびに `${DATA_PATH}/exports` を `0700` に設定し、各成果物を `0600` のファイルとして書き込みます。コンテナ内から見ると、どちらも root の所有です。その中の証拠パッケージの成果物には復号された平文が含まれます（§4）。

推奨：`DATA_PATH` のディレクトリ自体は root の所有とし、権限を `0750` かそれより厳しくします。各コンテナはその下のサブディレクトリだけをマウントするため、データのルートが root の所有でもコンテナの動作の妨げにはなりません。

**リストアの後は録画ディレクトリを設定し直します。** 展開で所有者とモードが保たれるのは root として実行した場合だけです。また 1.12.2 以前でデプロイしたホストで取得したバックアップは、Docker が当初与えた `root:root 0755` のままのことがあり、この権限では RDP と VNC のセッションは録画されません。そのためリストア手順（§5）の手順 4 は、データを展開した直後に SOP §1.3 の準備コマンドを実行します。パッケージのデプロイでは本手順の準備ステップを使います。`scripts/quickstart.sh` はソースツリーの評価用であり、パッケージのデプロイには使いません。

**オブジェクトストレージ側の同等の保護はデプロイ側が担います。** バケットへアップロードされた録画と証拠パッケージは、その内容の機微性が `DATA_PATH` の下の原本と同じですが、そこでの権限のモデルは製品の手にありません。バケットのアクセス制御（誰が一覧でき、誰が読め、誰が削除できるか）と保存時の暗号化は、デプロイ側がバケット側で設定する必要があります。**製品はオブジェクトの内容を暗号化しません。** バケット自身が保存時の暗号化を行っていない限り、オブジェクトはストレージ側では平文です。少なくとも次までは行うことを推奨します。専用の最小権限の識別情報（書き込みと読み取りができ、**削除の権限は不要です**。製品は使いません）、公開アクセスの遮断、保存時の暗号化の有効化、そして保持の要件に応じたバージョニングと保持のルールの設定です。

**オフサイトの取得用の一時ディレクトリは、コンテナローカルの平文のキャッシュです**（`OFFSITE_SPOOL_PATH`）。取得したバイト列はまずそこへ置いて検証し、検証を通ってから引き渡します。存続期間と総量の上限があり、コンテナのライフサイクルとともに存在し、バックアップの対象ではありません。ただし存在しているあいだ、内容は平文の録画または証拠パッケージです。したがってこのパスを共有の場所や、誰でも読める場所にマウントしないでください。

### 3.7 オブジェクトストレージのバケットの推奨設定（デプロイ側の責任）

> **本節はすべて推奨値であり、製品の能力ではありません。** 製品が遠隔のオブジェクトに対して行うのは 3 つだけです。アップロード、台帳への記録（バケット、key、アップロード時点の SHA-256 とサイズ）、取得時の検証です。**保持のフィールドは一切設定せず、バージョンの履歴も追跡せず、遠隔のオブジェクトを削除しません。** したがって「遠隔の複製が上書きされたり誤って削除されたりしない」ことと「遠隔の複製が期限に達したら整理される」ことは、**バケット側の設定によってのみ提供されます**。製品は接続テストとオフサイト保管のページで、あなたが何を設定したかを**探査してありのままに表示します**が、現況を報告するだけで良し悪しを判断せず、代わりに修復もしません。

保持の要件に応じて、有効にするかどうか、どれだけの期間にするかを決めてください。これらの数値はあなたの証拠の保持ポリシーの一部であり、製品が代わりに決めることはありません。

#### S3／MinIO

- **バージョニング**：有効にすることを推奨します。これは「同じ key の古い内容が残っている」ための前提であり、証拠が上書きされた後に取り戻せる唯一の道でもあります。有効でない場合、上書きされた内容はそれで失われます。製品にできるのは、取得時にハッシュが合わないために引き渡しを拒否することだけで、原本を取り戻すことはできません。
- **オブジェクトロック（Object Lock）**：削除に対する保護が必要な場合、**バケットの作成時に**有効にする必要があります（AWS では作成時にチェックし、MinIO では `mc mb --with-lock` です）。**既存のバケットに後から有効にすることはできません。** 有効にしたうえで default retention rule を 1 つ設定し、モード（governance／compliance）と日数を保持の要件に応じて決めてください。**製品は保持のヘッダーを一切送りません。** 保護はこのルールから来ます。
- **ライフサイクルのルール**：遠隔のオブジェクトの期限到来時の整理はこれに依ります。推奨は 2 つです。
  - **期限の日数を録画の保持ポリシーに揃えてください。** 製品の保持ポリシーとこのルールは**それぞれ別に動く 2 つの期限**です。ルールを設定しなければ遠隔には永遠に残ります。保持ポリシーより短く設定すれば遠隔が先に消え、ローカルの複製もキャッシュから消去されていれば再生できなくなります。製品はこの 2 つの期限を検知も同期もしません。
  - **`NoncurrentVersionExpiration` を 1 つ追加**して、再送で積み上がる過去のバージョンを整理してください（再試行は同じ key への再送であり、バージョニングを有効にしていれば古いバージョンが積み上がります）。
  - 必ず生じる例外を 2 つ先に知っておいてください。**オブジェクトロックの期間内のオブジェクトは消せません**（ライフサイクルのルールはそれらを読み飛ばします。これは想定どおりの挙動であってルールの失効ではありません）。**接続テストが残した探査用のオブジェクト**も、保持のルールの対象範囲に入っている場合は削除できません。製品はそれを警告として記録し、以後は追跡せず、ライフサイクルのルールまたは人手による整理に委ねます。
- **最小権限**：製品には専用の識別情報を与え、権限は「あなたが指定した接頭辞の下にオブジェクトを書き込む」ことと「オブジェクトとその metadata を読み取る」こと、加えて「バケットの構成を読み取る」こと（接続テストがバージョニングと保持の現況を明らかにするために使います。読み取れない場合は警告として表示されるだけで、アップロードには影響しません）で足ります。**保持のフィールドへの書き込みの権限も、削除の権限も必要ありません。** 製品の正規の経路は遠隔に対して削除を行いません。削除を使う唯一の場面は、接続テストが自ら残した探査用のオブジェクトを消すときで、その手順が失敗しても警告にとどまります。

#### Google Cloud Storage

- **基準となる推奨はバケットの保持ポリシー（bucket retention policy。ロックを追加することもできます）です。** バケット内の**すべての**オブジェクトに自動的に作用し、個々のオブジェクトに対して何かをする必要がありません。本製品のように「アップロードするだけで保持を設定しない」書き込み側に最も適した形態です。
- **オブジェクト単位の保持（`--enable-object-retention`）はよく確認してから進んでください。** `gcloud storage buckets create --enable-object-retention` は**その能力を有効にする**だけです（既存のバケットはコンソールからしか有効にできません）。**本製品はどのオブジェクトにも保持期間を設定しません**ので、これを有効にしただけでは**本製品がアップロードしたどのオブジェクトも保護されません**。この道を選ぶなら、外部の自動化で個々のオブジェクトに保持期間を設定する必要があります。そうしなければ「保護を有効にしたつもりで、実際にはされていない」デプロイになります。
- **両者が併存する場合は、期限の遅いほうが採られます。** また event-based hold と保持の設定は排他です。**製品はこの併存の衝突を扱いません。** どちらを使うかはバケット側であなたが決めてください。
- **バージョニング（object versioning）**：有効にすることを推奨します。理由は S3 の項と同じです。
- **ライフサイクルのルール**：S3 の項の 2 つに対応します（期限の日数を保持ポリシーに揃える、現行でないバージョンを整理する）。保持ポリシーのあるバケットでは、ロックの期間内のオブジェクトは同じく消せません。
- **サービスアカウントの最小のロール**：オブジェクトの作成と読み取りができれば十分です（`objectCreator` ＋ `objectViewer` の水準）。加えて、状況を明らかにするためにバケットの構成を読み取る権限が必要です。**削除の権限は不要です。**
- **HMAC key は不要です。** 本製品は GCS のネイティブ API を使い、サービスアカウントの JSON またはアプリケーションのデフォルト認証情報で接続します。組織のポリシーで HMAC が制限されている環境でも影響を受けません。

### 3.8 管理スクリプトによるバックアップ（パッケージのデプロイ）

インストールパッケージでデプロイした場合、`custodexa.sh` が §3.2 の停止してのバックアップを実行します。実行されるのは、求めたとき（メニューの「**1 つのファイルにバックアップ**」、またはデプロイフォルダーで `sudo ./custodexa.sh backup`）と、毎回のアップグレードの手順 7（[アップグレード SOP](./upgrade-sop.md#管理スクリプトによるアップグレード)）です。どちらも同じ形式の 1 つのバックアップファイルを書き出し、別のホストへ複製できます。アップグレードが取るバックアップは、含まれる内容だけが異なります（本節の末尾）。外部データベースを使うデプロイも同じ方法でバックアップしますが、組み込みのデータベースの代わりにリリースの PostgreSQL クライアントを使います（後述）。

#### `backup` が書き出すバックアップファイル

- **行うこと**：画面と同じ番号の 7 つの手順です。(1) backend、guacd、frontend を止めます。データベースは動かしたままです。(2) `pg_dump -Fc` でデータベースを書き出し、`snapshot.txt` を取ります。(3) `audit` をまとめ、録画を入れることを選んだ場合は `recordings` もまとめます。(4) `.env` を複製し、デプロイに `tls/` があればまとめ、`TLS_NGINX_TEMPLATE` が設定されていればそれが指すプロキシテンプレートを複製し、2 つのリリースマニフェストを複製します。(5) サービスを起動し、backend の準備ができるまで最大 180 秒待ちます。(6) 書き出したデータベースが `pg_restore --list` で、各アーカイブが `tar -tzf` で一覧できることを確認します。(7) 1 つのファイルに組み立て（暗号化を選んだ場合は同時に暗号化し）、読み戻して照合します。サービスが止まるのは手順 1 から 5 だけで、プレビューは 2 つの所要時間を分けて示します。
- **何かを止める前に確認すること**：空き容量（ファイルの大きさ、組み立て中に最も大きい部分を置く余地、さらに 1 GB の余裕）。マスターキーの設定（§4。モード A では `ENCRYPTION_KEY` に値があり、モード B と C では空で、`KEK_PROVIDER` が backend の受け付ける値であること。拒否するときはキー名だけを示し、値は表示しません）。`state.json` に記録されたバージョンが `current/MANIFEST.json` と同じであること。`.env` に `TLS_NGINX_TEMPLATE` が設定されている場合は、それが指すものが読み取れる通常のファイルであること、そしてそのパスにマニフェストが記録できない文字（二重引用符、バックスラッシュ、タブなどの制御文字、日本語などの ASCII 以外の文字）が含まれないこと（リストアのときはこのパスへテンプレートを戻します）。暗号化する場合はパスフレーズファイルと openssl のイメージ。拒否された場合、何も止まりません。
- **手順 5 の後**：モード A では完了画面がサービスの回復を示します。モード B と C では再起動の後にシール済みへ戻ります（§3.2 のモード B の説明と §4.3）。プレビューで先に警告し、完了画面はアンシールのページを示します。backend が 180 秒以内に準備できなかった場合、手順 5 は WARN となり、バックアップは最後まで進み、完了画面に `status` と `start` のコマンドが表示されます。
- **質問とフラグ**：端末で `--yes` を付けずに実行すると、スクリプトは 2 つ質問します。どちらも既定は「いいえ」です。録画をファイルに入れるかどうかと、パスフレーズでファイルを暗号化するかどうかです。`--with-recordings` を付けると質問せずに録画を入れ、`--passphrase-file <ファイル>` を付けると質問せずに暗号化します（後述）。`--yes` だけでどちらのフラグもない場合、録画は入らず暗号化もされず、プレビューがそれぞれのフラグを示します。端末がない場合は `--yes` が必要です。この 2 つのフラグを受け付けるのは `backup` だけです。
- **場所**：デプロイフォルダーの `backups/custodexa-backup-<バージョン>-<STAMP>.tar`（暗号化した場合は `.tar.enc`）で、その隣に同じ名前に `.sha256` を付けたチェックサムファイルがあります。`<バージョン>` はインストール済みのバージョン、`<STAMP>` は `YYYYMMDD-HHMMSS`（§3.2 と違い秒を含みます）です。`backups/` の権限は `0700`、バックアップファイルとチェックサムファイルは `0600` です。スクリプトはバックアップを上書きしません。名前がすでに使われていれば次の秒に移り、これを最大 2 回繰り返します。3 つの名前がすべて使われていれば、何かを止める前に拒否します。最新のバックアップは大きさとともに `status` に表示され、暗号化されていればそのことも示されます。

チェックサムファイルは `sha256sum` の形式で、パスを含まないファイル名だけを記録します。2 つのファイルを別のフォルダーやホストへ一緒に複製した後、そのフォルダーで `sha256sum -c <名前>.sha256` を実行すれば複製を照合できます。

バックアップファイルは圧縮していない tar です。メンバーはすべて最上位にある通常のファイルで、それぞれ多くとも 1 回しか現れません。

| メンバー | 内容 |
|---|---|
| `backup-manifest.json` | このバックアップの説明（後述）。シークレットの値は含みません |
| `release-MANIFEST.json` | インストール済みのバージョンのリリースマニフェスト（`current/MANIFEST.json`）そのもの |
| `tool-MANIFEST.json` | このファイルを書き出したスクリプトが属するリリースのマニフェスト |
| `snapshot.txt` | サービスが止まった時点のデータベースの状態（後述） |
| `db.dump` | データベース。`pg_dump -Fc`（§3.2 の手順 2） |
| `audit.tar.gz` | `DATA_PATH` の下の `audit` |
| `recordings.tar.gz` | `DATA_PATH` の下の `recordings`。入れることを選んだ場合だけ |
| `env.bak` | `.env` そのもの。シークレットを含み、モード A ではマスターキーも含みます（§3.5） |
| `tls.tar.gz` | `tls/`。デプロイにこのディレクトリがある場合だけ（自前の入口で TLS を終端する形態にはありません） |
| `nginx-tls.conf.template` | `.env` の `TLS_NGINX_TEMPLATE` が指すプロキシテンプレートそのもの。設定されている場合だけ |
| `db-ca.pem` | 外部データベースの場合：`.env` の `PGSSLROOTCERT` が指す CA ファイルそのもの。それがファイルを指している場合だけ |
| `state.json` | アップグレードが取るバックアップにだけあります。そのアップグレードが始まった時点のスクリプトの記録です（§5.1） |
| `SHA256SUMS` | ほかのすべてのメンバーのチェックサム |

`exports` は決して含まれません（§2）。録画は通常、容量の大半を占めるため、選ばない限り入りません。その場合、完了画面が録画のフォルダーを示します。録画を別の方法で保存するなら、バックアップが終わってから複製し、録画の側が新しくなるようにしてください（§3.1）。

**`backup-manifest.json`** は 1 行に 1 つの `"キー": "値"` です。手作業でリストアするときに読むキーは次のとおりです。`product.version`（データが属するバージョン。リストア先はこのバージョンを動かします。§5 の手順 0）、`created_at`（サービスが止まった時刻）、`kek.provider`（backend が実際に使うマスターキーの方式。モード A は `env`、B は `ui`、C は `kms`）、`kek.material_included`（モード A だけ `true`）、`kek.fingerprint`（マスターキーのフィンガープリントまたはキー ID。`snapshot.txt` の `fp.kek` と同じ値）、`encryption.enabled` と `encryption.scheme`、`contents.recordings`、`contents.tls`（デプロイに `tls/` がなかった場合は `false`。ファイルに `tls.tar.gz` がないのは欠落ではありません）、`contents.nginx_template` と `source.tls_nginx_template`（プロキシテンプレートがファイルに入っているかどうかと、`.env` に書かれていたパス）、`trigger`（`backup` では `manual`、アップグレードが取るバックアップでは `upgrade`。後者だけ `contents.state` が `true`）、そして `db.location`（`bundled`、または `external` で、そのキーは後述の「外部データベースのデプロイ」にあります）です。このほか、PostgreSQL のサーバーと `pg_dump` のバージョン、データベースのエンコーディング、使用中の overlay、元のホストの名前、デプロイフォルダー、`DATA_PATH`、`TLS_DOMAIN`、`TLS_IP_SAN`、`PUBLIC_BASE_URL` も記録されます。

**バックアップファイルが完成したと言えるとき**：スクリプトは `backups/.partial-<STAMP>/`（権限 `0700`）でファイルを組み立て、全体を読み戻して各メンバーを `SHA256SUMS` と照合し、チェックサムファイルを `backups/` に置いてから、最後にバックアップファイルへ正式な名前を付けます。したがって、正式な名前で存在するバックアップファイルは、一度すべて読み戻して照合されています。その後、スクリプトはそれを `state.json` に記録し、`.partial-<STAMP>/` を削除します。失敗や中断（Ctrl-C、端末を閉じた、TERM シグナル）で何が残るかは、バックアップがどこまで進んだかで決まります。

- **`.partial-<STAMP>/` ができる前**（確認の途中で、まだ何も止めていない段階）：バックアップは取り消されます。何も止めず何も書いていないため、削除するものはなく、後のコマンドにも影響しません。
- **`.partial-<STAMP>/` ができた後、バックアップファイルに正式な名前が付く前**：バックアップファイルはなく、`state.json` は前のバックアップを指したままです。`.partial-<STAMP>/` が残ります。これはリストアに使えず、機微な平文を含むため、原因を確かめたら削除してください。対応するバックアップファイルのない `.sha256` もこの状況から生じたもので、削除して構いません。サービスが止まったままの可能性があるときは、画面にサービスを起動するコマンドが表示されます。
- **バックアップファイルに正式な名前が付いた後、`state.json` に記録される前**：画面はファイルが有効であることと、`state.json` が更新されていないことを示します。そのため `status` は前のバックアップを表示します。`.partial-<STAMP>/` は手作業で削除してください。
- **`state.json` に記録された後**：残っているのは `.partial-<STAMP>/` の削除だけです。画面はファイルが有効であることを示すので、フォルダーを手作業で削除してください。このバックアップは完了したものとして扱われます。

2 つ目または 3 つ目の状況で中断された場合、`state.json` はそのバックアップを未完了として保持します。`start`、`stop`、`backup` は通常どおり動き、最初に警告を表示します。`upgrade` は、バックアップが一度完了するまで拒否し、`start` だけではこれは解除されません。停電やプロセスの強制終了はスクリプトが捕捉できませんが、扱いは同じです。その場合 `.partial-<STAMP>/` がないこともあり、警告は前回のバックアップが完了しなかったことだけを示します。

#### 外部データベースのデプロイ

外部データベースの形態（`compose.external-database.yml`）では、`backup` とアップグレードの手順 7 のバックアップは、`.env` が指すサーバー（`EXTERNAL_DB_HOST`、`EXTERNAL_DB_PORT`、`DB_NAME`、`DB_USER`、`DB_SSLMODE`）からデータベースを書き出します。手順、ファイル、メンバー、質問は上記のとおりです。手順 1 は backend、guacd、frontend を止め、データベースには触れません。

- **書き出しのツール。** リリースには PostgreSQL 16、17、18 のクライアントが、マニフェストで固定されたイメージとして同梱されています。この形態では `install`、`upgrade`、`load` がそれらを取得してマニフェストと照合します。これらはスクリプトが実行するツールでありサービスではないため、`status` はコンテナーとして一覧しません。何かを止める前に、スクリプトはサーバーにバージョンを尋ね、サーバーと同じメジャーバージョンのクライアントだけを、書き出しと `snapshot.txt` の両方に使います。15 や 19 など、ほかのメジャーバージョンのサーバーは、別のクライアントで読める場合でも拒否されます。マニフェストは使ったクライアントを `tool.dump_image`（`pgclient16`、`pgclient17`、`pgclient18`）に記録し、そのダイジェストは `tool-MANIFEST.json` にあります。
- **何かを止める前に確認すること**。上記の確認に加えて、それぞれ専用のメッセージがあります。クライアントのイメージがこのホストにあること（なければ `load` でリリースのオフラインイメージバンドルを読み込みます）、サーバーに到達でき、ログインが受け付けられること（失敗の理由はログファイルにあります）、リリースにサーバーのメジャーバージョンのクライアントがあること、そして以下の各項目が述べる設定です。拒否された場合、何も止まりません。
- **書き出しに含まれないもの。** `pg_dump` はロールもテーブルスペースも書きません。そのため、新しいサーバーでそれらが必要になるデータベースは、見つかった内容を示して拒否されます。独自のテーブルスペース、`DB_USER` 以外のロールが所有するオブジェクト、`plpgsql` 以外の拡張です。PostgreSQL が作成するとおり、組み込みロール `pg_database_owner` が所有する `public` スキーマは別の所有者とは数えませんが、その中のオブジェクトは `DB_USER` が所有している必要があります。
- **ほかのロールへ付与された権限**は拒否されません。オブジェクトが `DB_USER`、`PUBLIC`、組み込みの `pg_` ロール以外のロール（たとえば監視用のアカウント）へ権限を付与している場合、バックアップは完了し、最後の画面がそれらのロールを挙げて警告し、マニフェストは `db.extra_grant_roles_hex` に一覧します。各名前を UTF-8 のバイト列の小文字の 16 進数にし、空白で区切ります（§5.3 は名前として表示します）。新しいデータベースサーバーには、リストアの前にそれらのロールが必要です。ないと、リストア後の権限が異なります。
- **TLS。** クライアントは、同じ `.env` でのバックエンドと同じ厳しさでサーバーを検査します。それより緩くも厳しくもなりません。プレビューには方式とサーバーの検査の仕方が示されます。`DB_SSLMODE` が未設定または空なら、バックエンドと同じく `disable` です。

  | `DB_SSLMODE` | `PGSSLROOTCERT` | サーバーの検査（バックエンドもバックアップも同じ） |
  |---|---|---|
  | `disable`、`allow`、`prefer`、`require` | 未設定 | 検査しない |
  | `verify-ca` | 未設定 | システムが信頼する認証局で検査し、ホスト名は検査しない。バックアップ側ではクライアントイメージの CA ファイルが使われ、なければバックアップは拒否される |
  | `verify-full` | 未設定 | システムが信頼する認証局で検査する |
  | 任意 | `system` | システムが信頼する認証局で検査する。`verify-full` と同じ |
  | `disable`、`allow`、`prefer` | ファイル | 検査しない。CA ファイルはそれでもバックアップに入る |
  | `require`、`verify-ca` | ファイル | CA ファイルで検査し、ホスト名は検査しない |
  | `verify-full` | ファイル | CA ファイルで検査する |

  バックエンドとクライアントイメージには、それぞれ別の信頼する認証局の一覧があります。サーバーの証明書に署名した認証局がクライアントの一覧にない場合、接続は何かを止める前に失敗します。バックアップがより緩い検査に切り替わることはありません。
- **TLS のファイル。** `PGSSLROOTCERT`、`PGSSLCERT`、`PGSSLKEY` には、backend コンテナー内のパスを書きます。スクリプトはこれらのファイルを backend のマウントを通じてホスト上で読むため、`/var/log/custodexa/audit`、`/var/lib/custodexa/recordings`、`/var/lib/custodexa/exports`（`DATA_PATH` の下の `audit`、`recordings`、`exports`）のいずれかの下にある必要があります。それ以外の場所のファイルは拒否されます。公開情報である CA ファイルは `db-ca.pem` としてバックアップに入ります（`contents.db_ca`）。クライアント証明書は接続に使われ、`db.tls_client_cert` が `true` と記録されますが、**その秘密鍵はバックアップファイルに入りません**。リストアで再び必要になるため、デプロイのほかのシークレットと一緒に保管してください。バックアップがまとめる audit や recordings のフォルダーの中にある秘密鍵は、拒否されます。
- **データベースのパスワード**は、`backups/` の下の非公開フォルダー（権限 `0700`）にある権限 `0600` のファイルでクライアントへ渡されます。バックアップの各手順の実行中は `backups/.partial-<STAMP>/`、それ以外のデータベースの確認（何かを止める前、およびアップグレードの手順 6 と 12）では `backups/.db-client-<PID>/` です。このファイルは呼び出しのたびと中断時に削除され、`.db-client-<PID>/` も一緒に削除されます。どのコマンドラインにも環境変数にも現れません。
- **バックアップ中はほかの書き込み側を置かないこと。** このホストのサービスを止めても、別のホストが同じデータベースへ書き込むのは止まりません。バックアップの実行中にスタンバイのホストへデータベースを引き継がせないでください（[アプリケーションホストのスタンバイ引き継ぎ](./standby-takeover.md)）。引き継ぐと、データベースとファイルの保存先が別々の時点のものになります（§3.1）。プレビューもそのことを示します。

#### パスフレーズによるバックアップファイルの暗号化

質問で選ぶか、`--passphrase-file <ファイル>` を付けます。パスフレーズは 12 文字から 256 文字で、使えるのは半角の英字、数字、空白、記号（印字可能な ASCII）です。空白もパスフレーズの一部として数えます。質問では 2 回入力し、画面には表示されません。`--passphrase-file` の場合はファイルの 1 行目がパスフレーズです。そのファイルは通常のファイル（シンボリックリンクではない）で、所有者があなたか root であり、グループとその他に読み書きの権限がなく、拡張 ACL もない必要があります。そうでなければ、バックアップは何かを止める前に拒否し、直すための `chown`、`chmod`、`setfacl` のコマンドを表示します。パスフレーズをシェルの履歴に残さずにこのファイルを作るには、次のようにします。

```bash
sudo install -m 600 -o root /dev/null /root/cx-pass
sudo bash -c 'IFS= read -r -s p && printf "%s\n" "$p" > /root/cx-pass'
```

暗号化は、リリースマニフェストが固定しそれと照合した openssl のイメージの中で行い、ホストのツールは使いません。スクリプトはどのデプロイ形態でもインストールとアップグレードのときにこのイメージを取得します。欠けている場合、バックアップは何かを止める前に拒否し、そのリリースのオフラインイメージバンドルを読み込むよう案内します。パスフレーズは標準入力で openssl に渡されます。コマンドラインにも、環境変数にも、ログにも現れず、`state.json` にも書かれません。スクリプトはパスフレーズを含むファイルを作りません。暗号化されていない tar 全体はディスクに書かれず、そのまま openssl へ流れます。`backups/.partial-<STAMP>/` の各部分は、ファイルが完成して削除されるまで平文です。

暗号化の方式は `cx-enc-1`（マニフェストの `encryption.scheme`）という名前で、パラメーターは固定です。

| 項目 | 値 |
|---|---|
| 暗号 | AES-256-CBC、PKCS#7 パディング |
| 鍵と IV | PBKDF2-HMAC-SHA256、600,000 回。32 バイトの鍵と 16 バイトの IV を導出 |
| ソルト | ランダムな 8 バイト |
| ファイルの形式 | ASCII の `Salted__`（8 バイト）、続いてソルト（8 バイト）と暗号文。`openssl enc` の形式 |
| パスフレーズ | 入力したとおりのバイト列、またはファイルの 1 行目のバイト列。行末の改行は含みません |

暗号化したバックアップファイルの名前は `.tar.enc` で終わり、先頭は `Salted__` です。開くのに必要なのは OpenSSL 1.1.1 以降と tar だけで、コマンドは後に示します。

> **パスフレーズを失うと、暗号化したバックアップはリストアできません。** ファイルにはパスフレーズから導いた値が一切なく、スクリプトはパスフレーズを保存せず、スクリプトにも開発者にも取り戻す手段はありません。パスフレーズはファイルと分けて保管し、あなた以外にも取り出せる人がいることを確かめてください。

暗号化は、ファイルを手にした人から内容を守ります。しかし、誰がファイルを作ったかは証明しません。AES-256-CBC には認証タグがなく、チェックサムが検出するのは損傷であって、内容を変えたうえでチェックサムも計算し直した変更ではありません。バックアップファイルは、システムを管理する人だけが書き込める場所に置いてください。

**ファイルとパスフレーズの確認。** 復旧のときが初めてパスフレーズを使う場面にならないよう、バックアップの後なるべく早く一度行ってください。まずパスフレーズを画面に表示せずに読み込みます。以降、パスフレーズは標準入力で openssl に渡り、コマンドラインには現れません。

```bash
FILE=backups/custodexa-backup-1.16.0-YYYYMMDD-HHMMSS.tar.enc   # 実際のファイル名に変えてください
IFS= read -r -s -p 'Passphrase: ' CX_PASS; echo
```

続いて、手元の openssl に合う 1 つのコマンドを実行します。どれもメンバーを一覧します。`enc` に `-saltlen` が加わったのは OpenSSL 3.2 からで、1.1.1、3.0、3.1 にはありません。バージョン番号ではなく、`openssl enc -help` に実際に表示されるかどうかで判断してください。`openssl enc -help` に `-saltlen` がある OpenSSL（3.2 以降）の場合：

```bash
printf '%s\n' "$CX_PASS" | openssl enc -d -aes-256-cbc -saltlen 8 -pbkdf2 -md sha256 -iter 600000 -pass stdin -in "${FILE:?}" | tar -tvf -
```

OpenSSL 1.1.1、3.0、3.1、または `openssl enc -help` に `-saltlen` がないバージョンの場合（これらのバージョンではソルトは常に 8 バイトです）：

```bash
printf '%s\n' "$CX_PASS" | openssl enc -d -aes-256-cbc -pbkdf2 -md sha256 -iter 600000 -pass stdin -in "${FILE:?}" | tar -tvf -
```

ホストの openssl の代わりにリリースの openssl のイメージを使う場合は、デプロイフォルダーで次を実行します。

```bash
printf '%s\n' "$CX_PASS" | docker run --rm -i --network none \
  --mount "type=bind,src=$(realpath "${FILE:?}"),dst=/backup.tar.enc,readonly" \
  "${CUSTODEXA_IMAGE_OPENSSL:-alpine/openssl:3.5.4}" \
  enc -d -aes-256-cbc -saltlen 8 -pbkdf2 -md sha256 -iter 600000 -pass stdin -in /backup.tar.enc | tar -tvf -
```

終わったら `unset CX_PASS` を実行します。パスフレーズが誤っていると、openssl が `bad decrypt` を報告するか、tar が入力は tar アーカイブに見えないと報告します。ほかのパラメーターで試し直さないでください。この方式のパラメーターは上のものだけです。

#### アップグレードが取るバックアップ

アップグレードの手順 7 では、スクリプトが `backup` が書くものと同じ形のバックアップファイルを書きます。`backups/custodexa-backup-<バージョン>-<STAMP>.tar` とその `.sha256` で、`<バージョン>` はアップグレード前のバージョンです。サービスはすでに止まっており、次の手順でバージョンを切り替えるため再起動しません。そのため、上の 7 つの手順のうち実行するのは 2、3、4、6、7 です。何も質問せず、含まれる内容は固定です。

- 録画は常に含まれます。
- 暗号化されません（`encryption.enabled` は `false`）。ホストの外へ出す前に、これか、そのコピーを暗号化してください（§3.5）。
- アップグレードが始まった時点の `state.json` を含みます（`trigger` は `upgrade`、`contents.state` は `true`）。§5.1 はこの記録を戻します。
- どのバックアップファイルとも同じく、`.env`、デプロイに `tls/` があればそれ、`TLS_NGINX_TEMPLATE` が指すプロキシテンプレートを含みます。そのテンプレートが読み取れない場合や、パスにマニフェストが記録できない文字がある場合、アップグレードは何かを止める前に拒否します。アップグレードが自前のバックアップしか取れない場合（`--backup-ref` が指定された、または今回は外部データベースをスクリプトがバックアップできない）、この確認は行いません。
- 外部データベースの場合は、上で述べたとおりリリースのクライアントで作ります。今回それができない場合、アップグレードは自前のバックアップだけを提示します（[アップグレード SOP](./upgrade-sop.md#管理スクリプトによるアップグレード)）。

`snapshot.txt` が最初に取られます。ファイルの中のメンバーに加えて、スクリプトはアップグレードのログの隣にコピー `logs/upgrade-<STAMP>.before.txt` を残し、手順 12 の確認はこのコピーと比較します。ファイルが作られると、それが `status` に表示される最新のバックアップになり、アップグレードの記録もそれを指します。アップグレードの画面はその完全なパスを表示します。バックアップが失敗した場合、バックアップファイルは残らず、上で述べた `backups/.partial-<STAMP>/` だけが残り、画面は古いバージョンを再び起動するコマンドを表示します。このファイルに必要な空き容量（録画を含む）は手順 1 で確認し、プレビューの停止時間の見積もりにも、ファイルの組み立てと読み戻しが含まれます。

1.16.0 より前のリリースへのアップグレードでは、このバックアップはフォルダーでした。`backups/<STAMP>/`（権限 `0700`）で、`<STAMP>` は中の各ファイルの接尾辞でもあります。§5.1 は今もそのようなフォルダーからリストアします。

| ファイル | 内容 |
|---|---|
| `custodexa-db-<STAMP>.dump` | データベース（§3.2 の手順 2） |
| `custodexa-files-<STAMP>.tar.gz` | `DATA_PATH` の下の `recordings` と `audit`（手順 3）。`exports` は含みません（§2） |
| `custodexa-env-<STAMP>.bak` | `.env`。シークレットを含みます（手順 4） |
| `custodexa-tls-<STAMP>.tar.gz` | `tls/`（手順 4）。デプロイに `tls/` がない場合（自前の入口で TLS を終端する形態）はこのファイルはありません |
| `snapshot.txt` | サービスが止まった時点のデータベースの状態（後述） |
| `state.json` | そのアップグレードが始まった時点のスクリプトの記録です（§5.1 F） |
| `SHA256SUMS` | 上の各ファイルのチェックサム。そのフォルダーで `sha256sum -c SHA256SUMS` を実行します |
| `INCOMPLETE` | バックアップが失敗したときにだけ存在します。このファイルがあるフォルダーは、リストアに使えるバックアップではありません |

このようなフォルダーには `TLS_NGINX_TEMPLATE` が指すプロキシテンプレートは入りません。§5.1 で戻すときも、そのファイルはそのままの場所に残ります。

手順 7 で自前のバックアップを選んだ場合も、スクリプトはそれを `backups/<STAMP>/` というフォルダーに記録します。そのフォルダーにあるのは、アップグレードが始まった時点の `state.json` と、スクリプトが取れた場合の `snapshot.txt` だけで、データはありません。

**`snapshot.txt`** は 1 行に 1 つの `key=value` です。`users`、`sessions`、`audit_logs` の 3 つのテーブルの件数、`schema_migrations` の適用済みの行ごとに 1 行の `migration=`、§6 の項目 6 の 4 つのフィンガープリント（`fp.jwt`、`fp.kek`、`fp.export_signing`、`fp.checkpoint_signing`。鍵管理ページと同じ算法で計算）、そして `usable=true` または `usable=false` です。いずれかのフィンガープリントを計算できない場合や、その元が一意でない場合は `false` になり、理由が `unusable=` の行に書かれます。このときアップグレード後の照合では、鍵は鍵管理ページでの手作業の比較に回ります。作成にはシール解除もログインも要りません。バックアップと一緒に保管してください。§6 が比較する「バックアップの前に記録した値」はこれです。

**保管**：バックアップファイルやフォルダーには §3.5 が述べるすべてが入っており、ファイルを暗号化していなければ平文の `.env` も含みます。しかも稼働中の `.env` と同じホストにあります。暗号化して別の場所へ保存してください。モード B と C では KEK の材料と分けて保管します。モード A では KEK の材料がその中にあるため、それを暗号化したパスフレーズや鍵と分けて保管します。スクリプトはバックアップを削除しません。不要になったものは自分で削除し、`backups/` をディスクの計画に入れてください。

**スクリプトが扱わないもの**：§3.3 の停止しないバックアップ。

## 4. 暗号鍵に関する災害復旧の前提（デプロイの前に必ず読んでください）

システムはエンベロープ暗号化により、資産の資格情報、ディレクトリ統合の bind パスワード、通知チャネルの URL と秘密鍵、署名用の秘密鍵、**クリップボードの監査の内容**、**オブジェクトストレージの資格情報**などの列を保護します。**データベースのバックアップをリストアした後にそれらを復号できるかどうかは、KEK（鍵暗号化鍵）を取り戻せるかどうかで完全に決まります。** **KEK の紛失は、上に挙げた列がすべて復号できなくなることを意味します。** オブジェクトストレージの資格情報もその中に含まれます。過去のどの保管世代の資格情報もこの一群の一員であり、復号できなければその世代のオフサイトの複製を取り戻せません。これはオフサイトの機能がもたらした新しいリスクではなく、クリップボードの内容やディレクトリ統合のパスワードと同じ運命にあるということです。

> **クリップボードの監査の内容も KEK に依存します。** クリップボードの内容はエンベロープ暗号化されてデータベースに保存されます（`clipboard_events.content_enc`）。**鍵を失えばクリップボードの監査の内容は読めません。** 資産の資格情報などほかのエンベロープ暗号化された列と同じ前提であり、「監査データだから」という例外はありません。クリップボードのイベントの**事実の側面**（時刻、方向、内容の長さ、状態）は暗号化されておらず、リストアの後も読めます。しかし**内容の全文**は KEK がなければ復号できません。災害復旧の計画では、クリップボードの内容を「KEK に依存する」側に入れる必要があり、鍵を欠いた状態でも閲覧できると仮定してはなりません。
>
> **証拠パッケージの成果物には平文が含まれます。** 証拠パッケージのエクスポートは、クリップボードの内容を**復号**し、録画の本体とあわせて ZIP にまとめ、エクスポートのディレクトリ（コンテナ内の `/var/lib/custodexa/exports`、ホスト上の `${DATA_PATH}/exports`。バックアップの対象ではありません。§2 参照）に置きます。これはシステムの中で平文の秘密が存在する数少ない保存先の 1 つであり、そのデータ漏えいのリスクは本番のデータベースと同じ水準で扱う必要があります。ディレクトリの権限は `0700`／`0600`、ダウンロードは申請者本人に紐づき、成果物は 24 時間後に自動で消去されます。このディレクトリを一般のバックアップに含めたり、鍵の保管場所以外の場所へ複製したりすることは**絶対に避けてください**。それは平文の秘密を、同等の保護を受けていない場所へばらまくことと同じです。

KEK には保管のモードが 3 つあり、環境変数 `KEK_PROVIDER` で宣言します。**3 つのモードは災害復旧の前提がまったく異なるため、デプロイの前に選定し、理解しておく必要があります。**

### 4.1 モード A：`KEK_PROVIDER=env`（ローカルの環境変数）

- **材料の位置**：`.env` の `ENCRYPTION_KEY`。これは **32 バイト**の鍵で、書き方は 3 通りのいずれでも構いません。32 文字（A-Z a-z 0-9）、64 文字の十六進、またはデコードするとちょうど 32 バイトになる base64 です。**3 つの書き方は同じ 1 つの鍵です。** バックアップした材料を別の書き方で入れ直しても同じデータを復号できるため、復旧の際に当初どの書き方を使ったかを覚えている必要はありません。
- **復旧の前提**：`.env` そのものをオフサイトにバックアップしておく必要があります。**データベースだけをリストアして `ENCRYPTION_KEY` がなければ、エンベロープ暗号化されたすべての列が復号できず**、サービスも起動を拒否します。
- **保管の責任**：デプロイ側。
- **注意**：本モードの KEK の材料のキーは `ENCRYPTION_KEY` の 1 つだけで、システムはほかのどのキー名も読みません。
- **`KEK_PROVIDER` が未設定または空の場合**：`ENCRYPTION_KEY` に値があれば backend は本モードで動き、本節がすべて当てはまります。
- **`backup` が書き出すバックアップファイル（§3.8）**：`env.bak` は `ENCRYPTION_KEY` を含む `.env` そのもので、マニフェストには `kek.material_included=true` が記録されます。そのため、暗号化していないファイル、または暗号化したファイルをパスフレーズで復号した内容があれば、リストアで鍵が戻ります。暗号化していない複製が漏れれば、それだけで保存されたすべての資格情報を復号できます。パスフレーズかほかの方法で暗号化してください（§3.5）。`.tar.enc` ファイルには元のパスフレーズが引き続き必要です。

### 4.2 モード B：`KEK_PROVIDER=ui`（画面から鍵を入力し、ディスクに残さない）

- **材料の位置**：**メモリの中だけにあり、ディスクへ書き込まれることはありません。** システムは起動後にシール済みの状態にあり、ヘルスチェックとシールのエンドポイントを除くすべてのルートが 503 を返します。人が `/unseal` のページで材料を入力して初めてアンシールされます。
- **起動の前提条件**：`ui` モードを宣言する場合、`ENCRYPTION_KEY` に値があってはなりません。材料をディスクに残さないと宣言しながら環境に材料を残すことは構成の矛盾であり、システムは起動を拒否します。
- **保管の責任：お客様自身。**

> ### デプロイの前に必ず知っておくべき事実
>
> **このモードでは、アンシールの材料をいったん失うと、暗号化されたすべてのデータが永久に復号できなくなります。製品は救出の手段を一切提供しません。予備の鍵も、預託された複製も、ベンダーの裏口もなく、技術サポートも取り戻すことはできません。**
>
> このモードを選ぶことは、材料の保管を貴組織が単独で負うことを選ぶことです。初期化を送信する前に、材料をオフラインの安全な場所（パスワードの保管庫や物理的な保管など）へ保存し、少なくとも 1 名以上が取り出せることを確認してください。

- **初期化の落とし穴（きわめて重要）**：初期化の途中でタイムアウトした場合、画面は**最初に入力した鍵で再試行し、新しい鍵に替えないよう**求めます。**必ずそのとおりにしてください。** タイムアウトは初期化の失敗を意味しません。内部では**すでに完了している可能性があり**、最初の鍵がこのデプロイのマスター鍵として確定しています。この時点で新しい鍵に替えると**永久に失敗し**、取り返しがつきません。
- **通常のアンシール**（初期化ではなく、既存のデプロイの場合）：ページはまずローカルの管理者のユーザー名とパスワードを確認し、そのうえで材料を受け取ります。**シール済みのあいだワンタイムコードは確認しません。** その種はデータ鍵で保護されているためで、したがってこの手順は多要素認証ではなく、記録にもそう書いてはいけません。材料自体の形式の検証も行いません（既存のデプロイの KEK は現行の形式の規則より前のものである可能性があるためです）。連続して失敗すると指数的なバックオフが働き、しきい値に達すると期限つきのクールダウンに入ります。**クールダウンは期間が満ちれば自動で解除され、どの場合でもプロセスの再起動は必要ありません。** クールダウン中の試行はそのまま拒否され、クールダウンを延長することもありません。
- **有効にすることを推奨する絞り込み**：`SEAL_UNSEAL_BIND_ADDR` を設定すると、アンシールのエンドポイントはそのアドレスの独立した待ち受けが提供するようになり、その待ち受けはシールに関わるエンドポイントだけを公開します（アンシールした後に完全な業務の画面に変わることはありません）。主となる待ち受けはアンシールのリクエストを固く拒否し、管理用のポートを使うよう案内します。**バインドに失敗すれば起動を拒否し**、「隔離したつもりで実際はしていない」状態へ黙って移行することはありません。信頼するプロキシ（`TRUSTED_PROXIES`）が未設定の場合、送信元の判定はトランスポート層の相手側アドレスのみを信頼し、IP ごとのバックオフは保守的に全体のバックオフへ格下げされます。

### 4.3 モード C：`KEK_PROVIDER=kms`（鍵の保管先への委任）

```
KEK_PROVIDER=kms
KEK_KMS_PROVIDER=aws
```

**キーはこの 2 つだけです。** `KEK_KMS_REGION`、`KEK_KMS_KEY_ID`、`KEK_VAULT_ADDR`、`KEK_VAULT_ROLE_ID`、`KEK_VAULT_SECRET_ID` はもう効きません。かつてそこに入れていたものは、いま 2 つの別々の場所にあります。

- **秘密ではないトポロジー**（サービスのリージョン、保管先のアドレス、Transit の鍵の名前、ロール識別子）は鍵管理ページで設定し、データベースの `kek_topologies` テーブルに保存します。**データベースのバックアップとともに移る**ため、これのために別途保管するものはありません。鍵の識別情報自体はそのテーブルにはなく、鍵の行の `kek_id` に従います。その行もデータベースの中にあります。
- **資格情報**（AWS のアクセスキーの組、GCP のサービスアカウント鍵ファイルの内容、Vault のロールの秘密または直接渡すトークン）は、アンシールのたびにアンシールのページで入力し、そのアンシール世代のメモリにのみ保持し、シールの時点で消去します。**どのバックアップにも含まれません。** ファイルにもテーブルにも存在しないためです。その保管の責任は導入側にあり、モード B の材料と同じ位置づけです。

**これが復旧に与える影響。** リストアの後、システムは自分の保管先がどこにあるかを知っています（それはデータベースとともに戻ってきました）。どうやってそこへ接続するかは知りません（そちらは戻ってきません）。**したがってリストア後の初回の起動は、シール済みの状態で人を待ちます。** 担当者はアンシールのページでローカルの管理者のユーザー名とパスワードを入力し、そこに表示された保管先を導入記録と照合したうえで、その事業者の資格情報を入力します。待っているあいだ、プロセスは終了しません。この担当者とその資格情報の両方を復旧の計画に入れてください。「コンテナが起動した」で終わるリストアの演習は、このモードを演習したことになりません。

- **復旧の前提**：鍵が保管先に存続していて利用可能であること、それを保持するアカウントまたはプロジェクトが閉じていないこと、そして利用権限のある資格情報をなお入手できること。鍵が削除の予定に入る、アカウントが閉鎖される、資格情報を二度と入手できない、のいずれも材料の紛失と同じです。資格情報の失効は鍵の削除とは異なり、発行者が別の組を発行できます。
- **AWS の経路に必要な権限**：`kms:Encrypt`、`kms:Decrypt`、`kms:DescribeKey`。ネイティブの再暗号化を使う場合は、`kms:ReEncryptFrom` と `kms:ReEncryptTo` の 2 つの action も必要です。構築時には `DescribeKey` のほかに使い捨ての暗号化と復号の往復を 1 回行うため、権限の不足は最初の利用時ではなくアンシールの時点で表に出ます。
- **資格情報は明示的に注入され、環境から自動的に発見されることはありません。** AWS SDK の既定のチェーン（IRSA／instance profile／`AWS_*`／SSO）と GCP の Application Default Credentials はもう使わず、資格情報が渡されない場合は構築を拒否します。インスタンスのロールに依存しているリストア先の環境は自力では立ち上がりません。アンシールのページで資格情報を入力してください。
- **Vault は AppRole のログインの代わりにトークンを直接渡せます。** ライフサイクルは同じで、シールの時点で消去し、期限切れでは fail-close します。長命のトークンは推奨される運用ではありません。露出の窓がその寿命と等しく、本製品はそれをローテーションできないためです。
- **信頼の境界**：鍵の行の `kek_id` は同時に、信頼するアカウントの範囲の唯一の出所でもあります。委任先へ再ラップする際の対象の鍵は、それと同じ AWS のアカウントおよび partition に属している必要があり、そうでなければ拒否されます。
- **トポロジーの変更はセキュリティ上の変更です。** アドレスは、ラップされたデータ鍵をどこへ送って解くか、そして再ラップのときに平文の鍵の材料がどこへ行くかを決めます。これを変更できるのは認証を経た鍵管理ページだけで、変更は成功も拒否も変更前後の値とともに監査に書き込まれ、成功したものは設定済みの通知チャネルを通じてセキュリティのアラートを送出します（チャネルが未設定なら、記録は監査の行だけです）。**これらはデータベースへ直接書き込める人を止めるものではありません。** また、アンシールのページでの照合は人が行う手順であって、システムが課す保証ではありません。その経路の防御は、データベースのアクセス制御と、別マシンに置いた監査ログの複製です。
- **マルチリージョンの鍵（MRK）**：データベースに保存される識別情報にはリージョンが含まれます。**replica への切り替えは鍵の交換と同じであり、先に再ラップする必要があります。** 災害復旧の計画がリージョンをまたぐ切り替えを含む場合、この再ラップを手順に組み込んでください。そのまま切り替えても既存のデータは復号できません。
- **エンドポイントの上書きは一律拒否します。** `AWS_ENDPOINT_URL_KMS` または `AWS_ENDPOINT_URL` に値があることを検知した時点で起動を拒否します。この変数は SDK が直接解釈し、平文のデータ鍵を含む `kms:Encrypt` のリクエストをそのアドレス（HTTP の平文でもありえます）へ向けてしまうためです。

### 4.4 オブジェクトストレージの資格情報に関する災害復旧の前提

オフサイト保管の接続のパラメーターも**資格情報**もデータベースの中にあり、資格情報はエンベロープ暗号化されて保存されます（保管の世代ごとにそれぞれ 1 件）。したがって災害復旧の前提はとても単純です。**データベースをリストアし、同じ KEK を用意すれば、取得の能力は回復します。** オブジェクトストレージの鍵を別途保管する必要も、`.env` に残しておく必要もありません。

> **この項に関する `.env` の平文の負担はこれでなくなります。** オブジェクトストレージの資格情報は `.env` を通らなくなったため、これのために設定ファイルを機密として保管する必要はありません。**ほかのキーは依然として機密です。** `.env` には引き続き `DB_PASSWORD` と `JWT_SECRET` があり、モード A ではさらに `ENCRYPTION_KEY` があります。§3.5 の `.env` のバックアップを暗号化して保管する要求は変わりません。

- **KEK を失った場合の帰結**：すべての世代のオブジェクトストレージの資格情報が復号できなくなり、それらの世代のオフサイトの複製は取り戻せなくなります（オブジェクトはバケットに残っていますが、システムがそれを読むための資格情報を得られません）。これはクリップボードの内容やディレクトリ統合のパスワードと同じく、第 4 節の冒頭で述べた一群に属するものであり、追加のリスクではありません。**迂回路**は 1 つだけです。デプロイ側がストレージ側で直接それらのオブジェクトを取り扱うことで、それはストレージガバナンスの事柄であって製品の経路ではありません。
- **保管の設定の世代の変更**：provider、エンドポイント、バケットのいずれの変更も管理画面で確認したうえで反映され、古い世代は**過去の世代へ移ります**。その資格情報は、過去のオブジェクトを引き続き取得できるよう**世代とともに保持されます**。ある過去の世代がもう不要になった場合は、その世代に対して**個別に資格情報を失効させられます**。失効の後はその世代のオブジェクトを取得できず、メッセージがどの世代に何が欠けているかを明示します。**クラウドの既定の資格情報チェーンへ戻ることはありません。**
- **オフサイトの停止も管理画面で行います。** 停止の後は新しいアップロードが行われなくなりますが、**過去のオブジェクトの取得は影響を受けません。** 資格情報は停止に伴って失効せず、失効させるには世代ごとに明示する必要があります。
- **初回設定の実行の印はデータベースのバックアップとともにリストアされます。** `.env` のオフサイトのキーは初回の起動時に一度だけ読まれてデータベースへ書き込まれ、同時に実行の印が記録されます。印はデータベースの中にあるため、リストアの結果、次の 2 種類のずれのどちらかが生じることがあります。

  | リストア後の状態 | 結果 | 対応 |
  |---|---|---|
  | **印はあり、設定テーブルは 0 行** | システムは「評価済み」とみなし、`.env` は**再投入されず**、そのデプロイは「未設定」となります | **管理画面から設定し直すしかありません。** データベースを変更したり、印を消そうとしたりしないでください。`.env` を変更して再起動しても何の効果もありません |
  | **設定テーブルは空でなく、印がない** | 次回の起動で印を書き足すだけで、データベース内の設定を**上書きしません** | 対応は不要です。実行時はデータベース内の設定をそのまま使います |
  | 完全な時点でのリストア | 両者が一致し、挙動はリストア前と同じです | 資格情報を復号できるかどうかは同じ 1 つの KEK に依存します（上記参照） |

## 5. リストアの手順

1.16.0 から、パッケージのデプロイは単一のバックアップファイル（§3.8）を管理スクリプトでリストアします。デプロイのフォルダーで `sudo ./custodexa.sh restore <バックアップファイル>` を実行するか、メニューで「バックアップファイルから復元」を選びます（未インストールのホストでは「バックアップファイルからこの新しいホストへ復元」）。スクリプトはファイルを確認し、必要ならバックアップ時のバージョンをインストールし、置き換えるデータを保持します。データ、バージョン、マスターキーをすべて確認するまで、リストアは完了とみなしません。下の「`restore` でリストアする」で、内蔵データベースのデプロイでのやり方を説明し、その後の「外部データベースのデプロイをリストアする」で、データベースがデプロイの外のサーバーにある場合の違いを説明します。

スクリプトが拒否する場合は、下の「手作業でリストアする」に従います。いずれもサービスを止める前、何かをダウンロードする前に拒否し、どの場合かを画面に示します。

- **単一のバックアップファイルではないバックアップ**：§3.2 の一組のファイル、または 1.16.0 より前のリリースへのアップグレードで残った `backups/<STAMP>/` フォルダー（§3.8）。このようなバックアップには `backup-manifest.json` がありません。作成元のホストで手作業でリストアするか、作成元を 1.16.0 以降にアップグレードしてからバックアップを作成し直してください。
- **データが 1.16.0 より前のバージョンに属するバックアップファイル**（`product.version`）：1.13 から 1.15 のデプロイに対してアップグレード時に作成したバックアップです。これらのバージョンはアンシール後にマスターキーの ID を返さないため、スクリプトはリストア後のマスターキーを確認できません。§5.2 で各ファイルを取り出し、このホストでそのバージョンに戻す場合は続けて §5.1 に、別のホストにリストアする場合は続けて下の手順に従います。
- **マスターキーのフィンガープリントがないバックアップファイル**（`kek.fingerprint_status` が `ok` ではない。作成時に一意の値を読めなかったもの）。手作業でリストアし、§6 の項目 6 に従って鍵の台帳を照合してください。
- **マスターキーの方式が `hsm` のバックアップファイル**：このリリースには動作する HSM の実装がありません。
- **`DB_USER`、`PUBLIC`、組み込みの `pg_` ロール以外のロールへ権限を付与している内蔵データベース**：新しいデータベースには `DB_USER` しかありません。拒否のメッセージがそのロールを示します。

リリースのパッケージからインストールしていないデプロイには管理スクリプトがなく、同じく手作業でリストアします。

#### `restore` でリストアする

**どちらのリストアになるか**は、ファイルではなくホストで決まります。

| ホスト | `restore` がすること |
|---|---|
| インストール済み（`status` がバージョンを表示する） | このホストのデータを置き換えます。上書きの前に現在のデータをバックアップします（安全バックアップ、下記）。別のホストで作成したバックアップも同じやり方でリストアし、プレビューは別のホストのバックアップであることを警告します |
| 未インストール | バックアップ時のバージョンをインストールしてから、そこへリストアします。ホストは空でなければなりません。選んだ `DATA_PATH` の下に `postgres` と `audit` がないか、空のフォルダーであること。`recordings` にすでにあるファイルは妨げにならず、そのまま残ります |

端末がない場合は、ホストの状態に合わせて `--same-host`（インストール済み）または `--new-host`（未インストール）と `--yes` を指定します。インストール済みのホストでは `--confirm-data-loss` も必要です。1.16.0 より前のデプロイには `restore` がありません。先に 1.16.0 以降へアップグレードしてください。

**新しいホストでは**、先に `get-custodexa.sh` でリリースのパッケージを置きます。バージョンはバックアップ時のもの、またはそれより新しいものです。そのとき置かれた `custodexa.sh` で `restore` を実行します。スクリプトはバックアップのバージョンより古くてはなりません。スクリプトのほうが新しい場合、スクリプトはバックアップのバージョンを `releases/<バージョン>/` に置き、リストア後のデプロイはそのバージョンで動きます。オフラインの場合は、バックアップのバージョンのパッケージとその `SHA256SUMS`（`--package`）、そのバージョンのオフラインのイメージバンドル（`--images`）も持ち込みます。暗号化されたバックアップファイルでは、復号をスクリプト自身のリリースの openssl イメージで行うため、そのリリースのオフラインのイメージバンドルも必要です。2 つのバージョンが同じなら、パッケージとイメージバンドルは 1 つずつで足ります。プレビューが不足しているものを示します。

**何かを止める前に確認すること。** この段階での拒否は何も変更しません。

- コピーが完全であること：隣にある `.sha256` が OK を返す必要があります。このファイルがない場合、スクリプトは端末で確認を求めるか、`--no-checksum-file` を必要とします。ファイル内のチェックサムはどちらの場合も確認します。
- 暗号化されたファイル（`.tar.enc`）：パスフレーズは 1 度尋ね、合わせて 3 回まで試せます。または `--passphrase-file` から読みます。このファイルの条件は `backup` と同じです（§3.8）。
- メンバー、チェックサム、マニフェスト。§3.8 の説明のとおりです。
- データのバージョンとマスターキー。上の一覧のとおりです。モード A では、バックアップ内の `.env` のマスターキーのフィンガープリントが `kek.fingerprint` と一致する必要があります。`snapshot.txt` に `fp.jwt` がある場合、バックアップ内の `.env` のログイン署名鍵 `JWT_SECRET` がそれと一致する必要があります。バックアップ内の `.env` には `JWT_SECRET` と `DB_PASSWORD`、モード A では `ENCRYPTION_KEY` の実際の値が必要です。スクリプトは新しい値を補いません。
- データに、バックアップのバージョンが知らないデータ構造の変更がないこと。知らない変更があるのは、より新しいバージョンがデータを変えたことを意味します。スクリプトはより新しいデータをより古いバージョンに入れません。
- バックアップのバージョン：すでにこのホストにある場合、そのリリースのマニフェストがバックアップ内の `release-MANIFEST.json` と完全に一致する必要があります。ない場合、パッケージは `--package`（同じフォルダーに `SHA256SUMS` が必要）から取るか、ダウンロードします。チェックサムは一致する必要があり、発行者の署名はアップグレードと同じく確認します。`cosign` がない、署名がない、署名が一致しない、のいずれも警告にとどまります。リリースのファイルがないバージョンは拒否し、別のバージョンを代わりにインストールすることはしません。
- そのバージョンのイメージ（このホスト、`--images`、またはレジストリから）と、作業フォルダー、安全バックアップ、リストアするデータに必要な空き容量。

続いてプレビューが、リストアするもの、置き換えるものと保持するもの、停止時間と容量、マスターキーに必要なものを示します。インストール済みのホストではリストア後のバージョン番号を入力して確定し、新しいホストでは `y` と答えます。

**ホストの値。** `DATA_PATH`、`TLS_DOMAIN`、`TLS_IP_SAN`、`PUBLIC_BASE_URL` はホストを表す値です。`.env` のそれ以外の値は、秘密情報も含めてすべてバックアップから取ります。

- インストール済みのホストでは、この 4 つはこのホストの現在の値を保ち、プレビューはバックアップと異なるものを示します。
- 新しいホストでは 1 つずつ尋ね、バックアップの値とこのホスト向けの値を示します。Enter でこのホスト向けの値、`-` でバックアップの値を使います。端末がない場合は `--data-path`、`--tls-domain`、`--tls-ip-san`、`--public-base-url` で指定し、指定しなかったものはこのホスト向けの値になります。自前の入口で TLS を終端するデプロイ（バックアップに `tls/` がない）では、`TLS_DOMAIN` と `TLS_IP_SAN` は尋ねません。
- 自己署名の証明書で名前またはアドレスが変わる場合、リストアした認証局をそのまま使い、起動時に新しい値のサーバー証明書を発行します。それまでのサーバー証明書は `tls/` の中の別の場所へ移して残します。その認証局を信頼しているクライアントは引き続き信頼します。自分で用意した証明書は変更しません。新しい名前またはアドレスを含まない場合は、プレビューと完了の画面が警告します。
- `PUBLIC_BASE_URL` が変わると、完了の画面は外部ログイン（OIDC）の ID プロバイダーでコールバックのアドレスを更新するよう促します。
- `TLS_NGINX_TEMPLATE` が指すプロキシのテンプレート（バックアップにある場合）は元のパスへ戻します。新しいホストで元のパスが使えない場合（親フォルダーがない、シンボリックリンクである、`releases/` または `current/` の下にある）、スクリプトは別の絶対パスを尋ねるか `--nginx-template <パス>` を受け取り、`.env` をそこへ向けます。置き先に内容の異なるファイルがすでにある場合は、`<名前>.before-restore-<STAMP>` に名前を変えて保持します。

**安全バックアップ**（インストール済みのホスト）。上書きの前に、スクリプトは現在のデータを `backups/custodexa-backup-<バージョン>-<STAMP>.tar` にバックアップします。データベース、監査ファイル、設定、証明書で、録画は含めず、暗号化もしません。そのためにサービスを止め、再び起動することはせず、データベースは動かしたままにします。続いてこのファイルを読み戻し、リストアの入力として通しで確認し、合格した場合にだけ先へ進みます。リストア前の `state.json` と `.env` も作業フォルダーにコピーします。

代わりに、サービスを止めた後に自分で取ったバックアップ（ストレージのスナップショットなど）を使うこともできます。質問で選ぶか、`--backup-ref`、`--backup-time`、`--backup-restore` を指定します（アップグレードと同じ。[アップグレード SOP](./upgrade-sop.md#管理スクリプトによるアップグレード)）。`--backup-time` はサービスを止めた時刻より前にできません。スクリプトが作る安全バックアップを後で `restore --revert` でリストアできない場合は、自分のバックアップだけを提示し、理由を画面に示します。たとえば現在のデータベースから一意のマスターキー ID を読めない場合や、現在のバージョンのイメージがもうこのホストにない場合です。

**置き換えるものと保持するもの。**

- `DATA_PATH` の下の現在の `postgres` と `audit`、デプロイのフォルダーの `tls/` は、`*.before-restore-<STAMP>` に名前を変えて保持し、削除しません。第 6 節の確認が済んだら自分で削除してください。
- 録画：バックアップに録画がない場合、`recordings` フォルダーには触れません。インストール済みのホストでは、そのため録画がバックアップの時点と一致しないことがあります。バックアップ後に録った録画はディスクに残りますがシステムには表示されなくなり、バックアップ後に消去された録画は戻りません。新しいホストでは、リストアしたデータベースが記録している録画のうちファイルがこのホストにないものの数を完了の画面が示し、一覧は作業フォルダーの `missing-recordings.txt` にあります。作成元のホストの `DATA_PATH` の下の `recordings` からコピーしてください。オフサイト保管へアップロード済みの録画は、再生のときにそこから取得されます。バックアップに録画がある場合は戻し、同じ名前のファイルがすでにあればそれを保持して上書きしません。
- バージョンはデータとともに戻ります。インストール済みのホストでは、ホストがより新しいバージョンを動かしていても、リストア後のバージョンはバックアップのバージョンです。

**手順。** インストール済みのホストでは 10 段階です。バックアップのバージョンとイメージを置く。サービスを止める（データベースは動かしたまま）。安全バックアップ。それがリストアできることの確認。データベースを止め、現在のデータの名前を変えて保持する。データベースの取り込み。データベースの確認。監査ファイル、証明書、設定を戻す。サービスを起動し準備完了を待つ。マスターキーの確認。新しいホストでは 8 段階で、安全バックアップがなく、バックアップから設定ファイルを書く段階があります。データベースの確認では、取り込んだ migration、`users`、`sessions`、`audit_logs` の行数、マスターキー ID を、バックアップが記録したものと比べます。起動後は、実行中のイメージが記録したものであること、backend がバックアップのバージョンを返すことを確認します。backend の準備完了は最大 180 秒待ちます。

**マスターキーと、リストアが完了とみなされるとき。**

- **モード A**：backend は `.env` の鍵で自らアンシールします。スクリプトは backend がアンシール後に返すマスターキー ID を読み、`kek.fingerprint` と比べます。一致すればリストアは完了です。
- **モード B と C**：スクリプトはサービスを起動し、終了コード 4 で終わります。データは取り込み済みで、システムはアンシールを待っています。誰かがバックアップ内の管理者アカウントでアンシールのページにログインし、マスターキーを入力します（モード B）。またはデータベースとともに戻った保管先を画面で照合し、保管先の資格情報を改めて入力します（モード C。このホストのアドレスが保管先の許可する送信元に含まれている必要があります）。その後 `restore --resume` を実行すると、マスターキー ID を読んで完了します。まだシール済みの場合はそのことを示し、何も変更せず、再び終了コード 4 で終わります。
- マスターキーを確認するまでリストアは完了しておらず、`upgrade` と `backup` は実行を拒否します。
- **ID が一致しない場合**、スクリプトはサービスを止め、リストアは完了しません。§6 の項目 6 に従って鍵の台帳を確認してから、続行するか（モード A では先に `.env` の鍵を確認し直し、一致しないままならサービスを起動しません。モード B と C ではサービスを再び起動し、正しいマスターキーでアンシールされた後にもう一度確認します）、下の説明に従って元に戻すか中止します。

**完了したとき**、完了の画面は、リストア元のバックアップ、保持したフォルダーと安全バックアップ、アドレス、マスターキーの確認結果、録画、各警告を示し、まだ残っている第 6 節（下記）を案内します。デプロイのフォルダーの `restore/` の下の作業フォルダー（権限 `0700`）からは、データベース、`.env`、各アーカイブの平文のコピーを削除します。欠けている録画の一覧と、リストア前の `state.json` と `.env` のコピー（`state-before.json`、`env-before-restore`。権限 `0600`、秘密情報を含む）は残します。端末がある場合、スクリプトは続けてメニューと同じ方法で最新のバージョンを調べ、アップグレードするかを尋ねます（既定は「いいえ」）。端末がない場合はコマンドを示すだけです。バックアップがアップグレードの取ったもの（`trigger` が `upgrade`）の場合は、調べることも尋ねることもしません。アップグレード前のバージョンに戻ったことを示し、アップグレードのコマンドを示します。

#### `restore` が途中で止まった場合

失敗または中断（Ctrl-C、端末を閉じる、TERM シグナル）のとき、リストアはその場で止まり、自動では何も元に戻しません。サービスは止まったまま、名前を変えたデータは保持したまま、作業フォルダーとこのリストアの記録も残ります。画面は 2 つのコマンドを示し、そのパスはこのリストアを始めたスクリプトの完全なパスです。新しいホストでスクリプトがバックアップのバージョンより新しい場合は `releases/<スクリプトのバージョン>/custodexa.sh` なので、画面に示されたパスで実行してください。

- `restore --resume` は終わらなかった段階から続行します。
- インストール済みのホストでは、`restore --revert` で元に戻します。まだ何も上書きしていない場合は、このリストアの記録を消して元のサービスを起動し、準備が整った時点で完了とします。上書きを始めた後は、同じ手順で安全バックアップをリストアし、安全バックアップを改めて作ることはしません。このリストアが置いたデータは `*.partial-restore-<STAMP>` に名前を変えて保持します。安全バックアップの代わりに自分のバックアップを使った場合は、登録したリストアの手順を示します。
- 新しいホストでは、`restore --abandon` でこのリストアを中止します。このリストアが起動したサービスを止め、置いたもの（`postgres`、`audit`、`tls/`、`.env`）を `*.abandoned-<STAMP>` に名前を変え、`current` をスクリプトのバージョンへ戻して `releases/<バージョン>/` は残し、作業フォルダーの平文を削除します。自分で先にコピーしたファイルが入っている可能性があるため、`recordings` フォルダーには触れません。その後ホストは未インストールに戻ります。

安全バックアップが終わらなかった場合は、まだ何も上書きしていません。続行して安全バックアップを取り直すか、自分のバックアップで続行するか（端末で選ぶか、`restore --resume` に `--backup-ref`、`--backup-time`、`--backup-restore` を加えます。時刻はこのリストアがサービスを止めた時刻より前にできません）、元に戻します。元に戻す処理や中止そのものが中断された場合は、同じコマンドをもう一度実行すれば続きから終えられます。

`--revert` が扱うのは完了していないリストアだけです。完了したリストアの前のデータを取り戻すには、その安全バックアップのファイルを `restore` でリストアします。これは新しいリストアであり、先に現在のデータの安全バックアップを作ります。

デプロイに対する自身の変更（フォルダーの名前の変更、ファイルの配置）が済んだかどうかをスクリプトが判断できない場合、その変更と関係するパスを示し、何も変更せずに止まります。何かを変える前にそれらのパスを確認してください。`*.before-restore-<STAMP>` として保持したデータと安全バックアップは影響を受けません。どれがどれか見分けられない場合は、下の「手作業でリストアする」に従ってバックアップファイルからリストアします。上書きを始めた後に作業フォルダーが失われた場合、`restore --resume` は拒否し、`restore --revert` または `restore --abandon` が残ります。

リストアが完了していないあいだ、`status` はそれを「復元」の段に続行のコマンドとともに表示し、メニューは続行、元に戻すまたは中止、状態の表示、サービスの起動と停止、ヘルプだけを示します。`status`、`load`、`stop` は通常どおり動きます。`start` は、リストア自身がサービスを起動した後（アンシール待ち、または時間内に準備が整わなかった場合）にだけ動きます。`backup`、`upgrade`、`install`、別の `restore` は拒否し、続行、元に戻す、中止のコマンドを示します。

#### 外部データベースのデプロイをリストアする

バックアップのマニフェストの `db.location` が `external`（§3.8）の場合、`restore` はそのサーバー上のデータベースを空にしてからバックアップをインポートします。手順は上と同じで、違いは次のとおりです。

**始める前に。**

- 新しいホストへのリストアでは、先に作成元のホストのサービスを止め、スタンバイのホストがデータベースを引き継いでいないことを確認します（[アプリケーションホストのスタンバイ引き継ぎ](./standby-takeover.md)）。リストアが完了するまでこの状態を保ってください。スクリプトは下に示す時点でほかの接続を確認しますが、そのあいだに作成元のホストやスタンバイのホストを誰かが起動してはいけません。
- データベースサーバーには、データベースの約 2 倍の空きが必要です。インポートがコミットされるまで、新旧のデータが両方サーバー上にあるためです。プレビューはこの数値を警告として示します。スクリプトはサーバーのディスクを確認できないため、先に確認してください。
- インポートのあいだ、作業フォルダーにはインポート用の SQL テキストも置かれ、その大きさは圧縮していないデータベースとほぼ同じです。新しいホストでデータベースにすでにデータがある場合は、事前のエクスポート（下記）も作業フォルダーに置かれます。デプロイのフォルダーの空きは両方を見込んでください。
- 接続はバックアップのものです。`EXTERNAL_DB_HOST`、`EXTERNAL_DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`DB_SSLMODE`、および `PGSSLROOTCERT`、`PGSSLCERT`、`PGSSLKEY` のパスは、どちらの種類のホストでもバックアップの `.env` の値を使います。新しいホストで尋ねるのは 4 つのホストの値だけです。別のデータベースサーバーや別のデータベースへ移すには §5.3 に従って手作業でリストアし、そこで `.env` の接続を新しいサーバーに合わせて設定します。

**サービスを止める前の確認**は、バックアップの接続と、このリリースに含まれるサーバーと同じメジャーバージョンの PostgreSQL クライアントで行います。拒否するときは見つかった理由をすべて示し、終了コード 3 で終わり、何も変更しません。

- サーバーが PostgreSQL 16、17、18 のいずれか（このリリースがクライアントを持つメジャーバージョン）で、そのバージョンのクライアントのイメージがこのホストにあること（ない場合は、このリリースのオフラインのイメージバンドルを `load` で読み込みます）。サーバーのメジャーバージョンがバックアップ作成元のサーバーより低くなく、クライアントのメジャーバージョンがダンプを作ったツールより低くないこと。
- クライアントが接続して認証を通り、サーバー証明書をバックアップ時とまったく同じ厳しさで検査すること（§3.8 の TLS の表）。それより緩くはなりません。
- `DB_USER` がデータベース `DB_NAME` を所有し（`public` スキーマの作り直しにはデータベースの所有者が必要です）、そのシステム以外のスキーマにあるすべてのオブジェクトも所有していること。`public` スキーマ自体は PostgreSQL が与える所有者 `pg_database_owner` のままでかまいません。拒否のメッセージはオブジェクトとその所有者を示します。
- データベースに `plpgsql` 以外の拡張機能がないこと。
- エンコーディング、照合順序、文字種別がバックアップと同じであること（`db.encoding`、`db.collate`、`db.ctype`）。異なる場合は画面がその設定を示し、データベース管理者がその設定でデータベースを作成します。スクリプトはデータベースもロールも作成しません。
- ほかの接続がそのデータベースを使っていないこと。新しいホストではこれを厳密に確認し、拒否のメッセージは送信元のアドレス、アプリケーション名、接続数を示します。インストール済みのホストでは、この時点では自身の backend がまだ接続しているため、プレビューは接続を示すだけです。厳密な確認はサービスを止めた後に行います（下記）。
- バックアップが権限を付与しているロールがサーバーにあること（下記）。
- データベースが空かどうか：システム以外のスキーマにオブジェクトが 1 つもないこと。

**サーバーにないロール。** 対象のロールは `db.extra_grant_roles_hex` とダンプ内の権限付与から取り、`DB_USER`、`PUBLIC`、組み込みの `pg_` ロールを除きます。端末がある場合、スクリプトは足りないロールを示し、2 つの選択肢を出します。`[1]` 先にこれらのロールを作成する（既定。リストアを終了し、何も変更しません）、または `[2]` これらのロールへの権限付与を省いて続ける（省くのはそのロールへの権限付与だけで、ほかはすべてリストアします）。端末がない場合、`--accept-grant-loss` がなければ拒否します。省くには、どの権限付与の文も「足りないロールだけに関わる」か「まったく関わらない」かのどちらかでなければなりません。そう区別できない文があるときは、先にロールを作成するよう求め、何も変更しません。プレビューは省く権限付与を示し、完了の画面は省いた数と一覧のファイル（作業フォルダーの `skipped-grants.txt`）を示します。

**CA ファイルとクライアント証明書。** バックアップの CA ファイル（`db-ca.pem`）は、`PGSSLROOTCERT` が指すパス（`DATA_PATH` の下、§3.8 の TLS のファイル）に置きます。そこに内容の異なるファイルがすでにある場合は拒否します。バックアップ時の接続がクライアント証明書を使っていた場合（`db.tls_client_cert` が `true`）、証明書と秘密鍵を `--db-client-cert` と `--db-client-key` で指定するか、端末で尋ねられたときに 2 つのパスを入力します。このホストで `PGSSLCERT` と `PGSSLKEY` が指すパスにファイルがすでにあればそれをそのまま使い、内容の異なるファイルがあれば拒否します。秘密鍵はバックアップファイルに入っていないため（§3.8）、デプロイのほかの秘密情報と一緒に保管してください。確認の後、これらのファイルを権限 `0600` で上記のパスへコピーします。秘密鍵はそこへ直接置き、作業フォルダーを経由せず、ログにも書きません。

**空にする範囲。** `DB_NAME` のうち、システムのスキーマ（`pg_catalog`、`information_schema`、PostgreSQL の toast と一時スキーマ）以外にあるすべてのオブジェクトです。`public` スキーマは削除した後、PostgreSQL 15 以降の既定どおりに作り直します。所有者は `pg_database_owner` で、`PUBLIC` に `USAGE` があります。ほかのデータベース、ロール、テーブルスペースには触れません。プレビューは、サーバー、データベースとその PostgreSQL のバージョン、使うクライアント、サーバーの検査方法、空にするスキーマごとのオブジェクト数を示します。データベースが空なら消去は不要で、プレビューもそう示します。

**1 つのトランザクション。** スクリプトはまずインポート用の SQL を作業フォルダーのファイルに書き出し、それぞれが完全であることを確認します。その後で初めて、消去とインポートを 1 つのトランザクションとしてサーバーへ送ります。トランザクションが失敗した場合はすべて取り消され、データベースは元のままです。

**確認。** データベースが空でない場合、確認はデータベース名の入力になり、インストール済みのホストでのバージョンの入力、新しいホストでの `y` に代わります。端末がない場合は、どちらの種類のホストでも `--yes` と `--confirm-data-loss` を指定します。

**インストール済みのホスト**では、安全バックアップに外部データベースも含まれます。スクリプトはサーバーと同じメジャーバージョンのクライアントでデータベースをエクスポートし、同じバックアップファイルに入れます。名前を変える `postgres` フォルダーはありません。データベースはその場で空にしてインポートし、元の内容は安全バックアップにあります。ほかの接続は 3 つの時点で厳密に確認します。サービスを止めた後（段階 2「サービスを停止（外部データベースには影響しません）」）、このホストの何かの名前を変える前（段階 5「他の接続がないことを確認」）、トランザクションを送る直前（段階 6「データベースを空にしてインポート（1 つのトランザクション）」）です。ほかの接続が見つかると、その段階は送信元とアプリケーション名を示して失敗し、サービスは止まったまま、外部データベースは変更されていません。その接続を見つけて終わらせ（スタンバイのホストが引き継いだものでないことを確認し）、`restore --resume` を実行するか、`restore --revert` で元に戻します。上書きを始めた後の `restore --revert` は、上の説明どおり安全バックアップをリストアし、そのデータベースも 1 つのトランザクションで戻します。

**新しいホスト**の安全バックアップはデータベースによって決まります。

- **空の場合**：プレビューは安全バックアップが不要であることを示し、作成もしません。上と同じ 8 段階です。
- **空でない場合**：その内容はそのデータの唯一のコピーです。設定ファイルを書いた後、段階 3 でもう一度ほかの接続がないことを確認し、サーバーと同じメジャーバージョンのクライアントでデータベースを作業フォルダーの `safety-db.dump` にエクスポートします（事前のエクスポート）。エクスポートは全体を読み戻し、データベースはエクスポートの前後で 1 回ずつ測ります。2 回の結果が異なる場合はエクスポート中に書き込みがあったことを意味し、そのエクスポートは使いません。完全で、そのあいだに変化のなかったエクスポートがある場合にだけ、リストアは先へ進みます。9 段階になります。

**インポートが途中で止まった場合。** サーバーがエラーを返した場合、トランザクションは取り消され、外部データベースは元のままです。結果が確認できない場合（インポートが強制終了された、または接続が切れた）、`restore --resume` はまずデータベースを測ります。インポート前と同じならコミットされておらず、インポートをやり直します。データベースの確認の段階の項目がすべて合えばコミット済みで、先へ進みます。どちらでもない場合、スクリプトは止まって 2 つの測定結果を示し、インポートはやり直しません。その後は画面のコマンドに従い、安全バックアップまたは事前のエクスポートで元に戻すか、データベースがもともと空だった新しいホストではデータベース管理者にデータベースを確認してもらいます。

**新しいホストで元に戻す、または中止する。**

- **データベースがもともと空でなかった場合**：`restore --revert` は確認を求め（または `--yes` を受け取り）、サービスを止め、事前のエクスポートを 1 つのトランザクションで外部データベースへ戻し、データベースがエクスポート時と同じと測れたときにだけ完了とします。その後このホストは `--abandon` と同じように未インストールに戻ります。戻すのに失敗した場合は `safety-db.dump` を保持し、同じコマンドをもう一度実行できます。消去とインポートをサーバーへ送った後は、`restore --abandon` は終了コード 3 で拒否し、`restore --revert` を示します。それより前なら外部データベースには触れておらず、中止できます。`safety-db.dump` は保持し、画面にそのパスを示すので、不要と確認できたら自分で削除してください。
- **データベースがもともと空だった場合**：`restore --abandon` はデータベースを空にしません。今回インポートしたデータはデータベースに残り、画面もそのことを示します。必要ならデータベース管理者が消去してください。次にリストアするときは、そのデータベースを空でない対象として扱い、先にエクスポートします。

スクリプトが `safety-db.dump` を削除するのは、`restore --revert` が完了したときだけです。それ以外の場合は、リストアが完了した後も含めて作業フォルダーに残ります。データベースの平文なので、第 6 節の確認が済んだら自分で削除してください。

#### 手作業でリストアする

**管理スクリプトでアップグレードした後に元へ戻す場合**（スクリプトの画面はここを案内します）：先に §5.1 を読んでください。以下の手順の前後に行うことと、`backups/` の下のフォルダーを使った値の埋め方を説明しています。

**単一のバックアップファイルからリストアする場合**（`backup` またはアップグレードが書き出す `custodexa-backup-<バージョン>-<STAMP>.tar` または `.tar.enc`、§3.8）：先に §5.2 で中のファイルを取り出してください。§5.2 が以下の手順のために `STAMP` と `BACKUP_DIR` を設定します。そのデータベースが外部だった場合（`db.location` が `external`）は、手順 5 の代わりに §5.3 を使います。

**§3.2 と順序が異なる点が 1 つあります。** `.env` を先にリストアし、変数の取得はその後です。理由は手順 2 の説明にあります。

以下では `STAMP` に、リストアする一組のバックアップファイルのタイムスタンプ（すなわち §3.2 が生成したファイル名の接尾辞）を受け取ります。**実行の前に実際の値へ設定してください。**

```bash
# 0. 対象の環境にはあらかじめ次を用意します。バックアップと同じバージョンのコード／イメージ、および対応する KEK（第 4 節参照）
#    バージョンが一致しない場合は、先にアップグレード SOP の互換性の線引きを確認してください
#
#    リストアする一組のバックアップファイルのタイムスタンプです。**次の行の値は実際のファイル名の接尾辞に変えてください**。
#    変え忘れた場合、以降の 3 つのコマンドはファイルが存在しないために失敗します（誤ったものへリストアされることはありません）
#    管理スクリプトのバックアップフォルダーは YYYYMMDD-HHMMSS で、backups/ の下のフォルダー名です（§3.8）
#    単一のバックアップファイルでは §5.2 が STAMP と BACKUP_DIR を設定済みです。下の 2 行の代入は飛ばしてください
STAMP=YYYYMMDD-HHMM
#    バックアップファイルのあるフォルダー：ファイルがこのディレクトリにあれば .、スクリプトのバックアップフォルダーなら backups/<STAMP>
BACKUP_DIR=.

# 1. すべてのサービスを止めます。対象の環境の ${DATA_PATH}/postgres は空のディレクトリでなければなりません
#    （postgres のコンテナは、データディレクトリが空のときにだけきれいなデータベースを初期化します）。
#    空にしないと、postgres は今あるデータベースをそのまま使い、初期化しません。別のホストでは、そのデータベースのパスワード（とユーザー）は
#    そのホストのインストール時のもので、リストアした .env と一致しないため、backend がデータベースに接続できません。
#    同じホストでは、バックアップにないテーブルなどのオブジェクトがデータベースに残ります。
#    この機械がリストア用の環境であることを確認してください。下の行は今のデータベースを削除せずに脇へ移します。
#    第 6 節がすべて通ったら postgres.before-restore-<STAMP> を削除してください。
docker compose --project-directory . down
DATA_NOW="$(sed -n 's/^[[:space:]]*DATA_PATH=//p' "${ENV_FILE:-./.env}" | tail -n 1)"
( cd "${DATA_NOW:?.env に DATA_PATH がありません。先へ進まないでください}" && pwd )
[ ! -d "${DATA_NOW:?}/postgres" ] || mv "${DATA_NOW:?}/postgres" "${DATA_NOW:?}/postgres.before-restore-${STAMP:?}"
mkdir -m 700 "${DATA_NOW:?}/postgres"

# 2. 先にデプロイ層の設定をリストアします（KEK モード A では必須。モード B には材料が含まれず、モード C には KMS の資格情報が含まれません）。
#    この手順を値の取得より前に置くのは、これが .env を丸ごと上書きするためです。先に値を取ってから上書きすると、
#    手元の DATA_PATH／DB_USER／DB_NAME は上書き前の古い値となり、サービスが実際に使う値と食い違います。
ENV_FILE="${ENV_FILE:-./.env}"
cp "${BACKUP_DIR:?}/custodexa-env-${STAMP}.bak" "$ENV_FILE"
#    注意：リストアされたのは「元の機械」の .env です。この機械のデータルートが元の機械と異なる場合は、
#    ここで .env の DATA_PATH をこの機械の実際のパスに変えてから先へ進んでください。

# 3. このデプロイの変数の値を取得します（原理は §2.3 参照）。**これが本手順で最も重要な一歩です。**
#    DATA_PATH を取得できずに既定値へフォールバックすると、次の手順はバックアップを誤ったディレクトリへ展開し、しかもエラーになりません。
env_get() { sed -n "s/^[[:space:]]*$1=//p" "$ENV_FILE" | tail -n 1; }
DATA_PATH="${DATA_PATH:-$(env_get DATA_PATH)}"
DB_USER="${DB_USER:-$(env_get DB_USER)}"
DB_NAME="${DB_NAME:-$(env_get DB_NAME)}"
printf 'ENV_FILE=%s\nDATA_PATH=%s\nDB_USER=%s\nDB_NAME=%s\n' \
  "$ENV_FILE" "$DATA_PATH" "$DB_USER" "$DB_NAME"

# 4. ファイルの保存先をリストアします。展開の前に、展開先の絶対パスを一度出力して確認します
#    （ディレクトリが存在しない場合や DATA_PATH を取得できていない場合、この行で失敗し、tar までは進みません）
( cd "${DATA_PATH:?DATA_PATH を取得できていません。先に手順 3 を実行してください。既定値のまま続けないでください}" && pwd )
#    root（sudo）で展開します。ほかのアカウントで展開すると、録画の日付ディレクトリ、テキストの録画、監査ファイルが
#    そのアカウントの所有になり、下の準備コマンドでは元に戻りません。
#    バックアップフォルダーでは録画と監査が 1 つのアーカイブに入っています。単一のバックアップファイル（§5.2）には audit.tar.gz があり、
#    録画を入れた場合にだけ recordings.tar.gz もあります。
if [ -e "${BACKUP_DIR:?}/custodexa-files-${STAMP}.tar.gz" ]; then
  tar -xzf "${BACKUP_DIR:?}/custodexa-files-${STAMP}.tar.gz" \
    -C "${DATA_PATH:?DATA_PATH を取得できていません。先に手順 3 を実行してください。既定値のまま続けないでください}"
else
  tar -xzf "${BACKUP_DIR:?}/audit.tar.gz" \
    -C "${DATA_PATH:?DATA_PATH を取得できていません。先に手順 3 を実行してください。既定値のまま続けないでください}"
  if [ -e "${BACKUP_DIR:?}/recordings.tar.gz" ]; then
    tar -xzf "${BACKUP_DIR:?}/recordings.tar.gz" -C "${DATA_PATH:?}"
  fi
fi
#    録画ディレクトリを 1000:0 2770 に戻します（§3.6）。展開で権限が保たれている場合に実行しても問題ありません
docker run --rm --network none -v "$(cd "${DATA_PATH:?}" && pwd)/recordings:/r" --entrypoint /bin/sh "${CUSTODEXA_IMAGE_OPENSSL:-alpine/openssl:3.5.4}" -c \
  'chown 1000:0 /r && chmod 2770 /r && find /r -mindepth 1 -maxdepth 1 -type f -group 1000 -exec chgrp 0 {} +'
#    TLS 証明書のディレクトリをプロジェクトディレクトリ配下へリストアします（これを戻さないと、
#    自己署名モードは起動時に新しい CA と証明書を生成し、すべての利用者端末へ CA を配り直すことになります）。
#    自前の入口で TLS を終端するデプロイのバックアップには tls のアーカイブがなく（マニフェストの contents.tls が false）、戻すものはありません。
if [ -e "${BACKUP_DIR:?}/custodexa-tls-${STAMP}.tar.gz" ]; then
  tar -xzf "${BACKUP_DIR:?}/custodexa-tls-${STAMP}.tar.gz"
fi
#    .env の TLS_NGINX_TEMPLATE が指すプロキシテンプレート：バックアップファイルにある場合（§3.8）、そのパスへ戻します
if [ -e "${BACKUP_DIR:?}/nginx-tls.conf.template" ]; then
  CX_TPL="$(env_get TLS_NGINX_TEMPLATE)"
  install -D -m 644 "${BACKUP_DIR:?}/nginx-tls.conf.template" "${CX_TPL:?.env に TLS_NGINX_TEMPLATE が設定されていません}"
fi

# 5. postgres だけを起こし、**本当に接続を受け付けられるようになってから**論理バックアップを流し込みます。
#    `up -d` はコンテナが起きたことを保証するだけで、postgres の準備ができたことは保証しません。しかも初回の起動（データディレクトリが空）では、
#    postgres のイメージはまず「unix socket だけを待ち受ける」一時的なサーバーを走らせて初期化を行います。
#    このあいだ `pg_isready` は socket 経由では準備完了と報告しますが、対象のデータベースは**まだ存在しません**。
#    この時点でバックアップを流し込むと `database "..." does not exist` となり、リストア全体が空振りに終わります。
#    そのためここでは、**TCP**（`-h 127.0.0.1`。初期化中は待ち受けません）と**対象のデータベースへ実際に接続できること**の 2 条件が同時に成立することを基準にします。
docker compose --project-directory . up -d postgres
for _ in $(seq 1 60); do
  docker compose exec -T postgres \
    pg_isready -h 127.0.0.1 -U "${DB_USER:?DB_USER を取得できていません。先に手順 3 を実行してください}" >/dev/null 2>&1 \
  && docker compose exec -T postgres \
    psql -U "${DB_USER:?}" -d "${DB_NAME:?DB_NAME を取得できていません。先に手順 3 を実行してください}" -c 'select 1' >/dev/null 2>&1 \
  && break
  sleep 2
done
# 最後にもう一度はっきり確認します。この行が 0 以外なら先へ進まないでください（準備半ばのサーバーへ流し込んでも、欠けたデータベースが得られるだけです）
docker compose exec -T postgres psql -U "${DB_USER:?}" -d "${DB_NAME:?}" -c 'select 1'

docker compose exec -T postgres \
  pg_restore -U "${DB_USER:?DB_USER を取得できていません。先に手順 3 を実行してください}" \
             -d "${DB_NAME:?DB_NAME を取得できていません。先に手順 3 を実行してください}" --clean --if-exists \
  < "${BACKUP_DIR:?}/custodexa-db-${STAMP}.dump"

# 6. 残りのサービスを起こします
docker compose --project-directory . up -d
```

KEK モード B のデプロイは、手順 6 の後もなおシール済みの状態にあり、`/unseal` で材料を入力して初めてサービスを開始します。**モード C のデプロイも手順 6 の後はシール済みです。** 保管先の設定はデータベースとともに戻ってきましたが、資格情報はどのバックアップにもないため、誰かが `/unseal` で画面上の保管先を照合し、資格情報を改めて入力する必要があります（§4.3）。それまで業務のルートは一律 503 を返しますが、これは想定どおりの挙動であり、リストアの失敗ではありません。

### 5.1 管理スクリプトでアップグレードした後、アップグレード前のバージョンに戻す

1.16.0 からは、まず `rollback` コマンドを使います。`rollback` はサービスを止める前に、アップグレード前のバージョンへ直接戻せるかどうかを判断します。戻せる場合はバージョンだけを戻し、データはそのまま保ちます。戻せない場合は何も変更せず、次の手順を表示します。バックアップを自分でリストアすることはありません。

バージョンを切り替える前の失敗では、前のバージョンに戻す必要はありません。手順 1 から 7 の画面は古いバージョンを再起動するコマンドを示します。手順 8 は番号だけを残し、変換しません。この状態で `rollback` を実行すると、アップグレードが切り替えの前で止まったことを示し、同じコマンドを表示します。

#### `rollback` で直接戻せる条件

次の 4 つがすべて成り立つ必要があります。

- このパッケージのデプロイで最後に行われたバージョンの変更が、スクリプトによるアップグレードで、新しいバージョンへの切り替え（手順 9 以降）まで進んでいること。アップグレードは完了していても、その後で失敗または中断していてもかまいません。
- アップグレード前のバージョンが 1.16.0 以降であること。
- 新しいバージョンがデータベースを変更していないこと。次の 3 つの根拠のどれか 1 つで足ります。新しいバージョンが一度も起動していない。データベースの migration がアップグレード前の記録と同じである。新しいリリースのマニフェストが、前のバージョンへ直接戻せると明記している。データベースを読めない場合は、変更されたものとして扱います。
- 前のバージョンのすべてのイメージがこのホストにあり、image ID がアップグレード前の記録と一致すること。スクリプトはこのホストだけを確認します。足りないイメージの読み込み方は下の表にあります。

最初の 2 つが成り立つとき、アップグレードの画面にこのコマンドが表示されます（例：`1.16.1 に戻す   sudo /opt/custodexa/custodexa.sh rollback`）。残りの 2 つは `rollback` 自身が判断します。

#### `rollback` で戻す

```bash
sudo /opt/custodexa/custodexa.sh rollback
```

最初に確認の画面を表示します。インストール済みのバージョン、戻す先のバージョン、データベースが変更されていないとみなす根拠、見つかった古いイメージです。この時点では何も変更しておらず、「開始しますか？[y/N]」と尋ねます。自動化では `--yes` を付けて確認を省きます。その後、4 つの手順を実行します。

1. **サービスを停止します。** `stop` と同じく、まず監査記録がすべてデータベースに書き込まれるのを待ち、内蔵データベース以外のサービスを止めます。それを確認できない場合はどのサービスも止めません。新しい実行は何も変更せずに終わり、再開中の実行は未完了のまま残ります。
2. **データベースを再確認して戻します。** アプリケーションのサービスが止まった状態で、新しいバージョンがデータベースを変更したかどうかをもう一度判断します。確認の画面で待っている間にも、新しいバージョンが変更する可能性があるためです。変更がなければデータベースを止め、`current` を `releases/<前のバージョン>` に向け、2 つのバージョンについてのスクリプトの記録を入れ替えます。
3. **サービスを起動します。** 使うのは前のバージョンのイメージです。
4. **確認します。** バックエンドが前のバージョンを返し、実行中のイメージがアップグレード前に記録したものであることを確かめます。

データ、`.env`、証明書には触れず、バックアップもリストアしないため、アップグレード後に作成された記録はすべて保持されます。デプロイがシール済みの状態で起動する場合（KEK モード B または C、§4.2 と §4.3）は、最後の行に `/unseal` のアドレスが表示されます。以降、デプロイフォルダーの `custodexa.sh` は前のバージョンのスクリプトになり、`status` は前回のアップグレードが元に戻されたことを表示します。実行ごとに記録ファイル `logs/rollback-<時刻>.log` が残ります。

#### `rollback` が途中で止まった場合

いずれかの手順が失敗した場合や実行が中断された場合、その戻し作業は未完了のまま残ります。画面は現在の状態を示し、バックエンドのログを見るコマンドに続けて、再開のためのコマンドを表示します。

```bash
sudo /opt/custodexa/custodexa.sh rollback --resume   # 原因を解消したら、前のバージョンに戻す処理を再開する
sudo /opt/custodexa/custodexa.sh rollback --revert   # または、アップグレード後のバージョンに戻す
```

- `--resume` は止まった手順から続けます。結果がすでに揃っている手順は飛ばします。
- `--revert` は戻し作業を取り消し、同じ 4 つの手順でアップグレード後のバージョンに戻します。データベースの再確認は行いません。手順 1 で止まった場合はまだ切り替えていないため、画面には `--resume` だけが表示されます。
- `--revert` を始めた後は、未完了なのはアップグレード後のバージョンへ戻す作業です。その後の画面には `rollback --resume` だけが表示され、これでその取り消しを完了します。完了後にもう一度前のバージョンへ戻すには、`rollback` を改めて実行します。
- 戻し作業が未完了の間、`upgrade`、`backup`、`restore` は実行を拒否し、同じコマンドを表示します。`start`、`stop`、`status` は通常どおり使えます。

#### 戻せるのは 1 つ前のバージョンだけ

`rollback` で戻せるのは 1 つ前のバージョンだけです。戻し終えた後にもう一度 `rollback` を実行すると、「戻せる前のバージョンがありません」として拒否され、何も変更されません。アップグレード後のバージョンに戻すには、通常どおりもう一度アップグレードします（[アップグレード SOP](./upgrade-sop.md#管理スクリプトによるアップグレード)）。

#### `rollback` で直接戻せない場合

条件のどれかが成り立たないとき、`rollback` はサービスを止める前に終了コード 3 で終わり、何も変更しません。例外は手順 2 の再確認だけです。確認の画面で待っている間に新しいバージョンがデータベースを変更した場合は、バージョンを切り替えず、アプリケーションのサービスは止まったまま、内蔵データベースは動いたままで、終了コードは 1 です。この画面には、新しいバージョンでサービスを続けるための `sudo /opt/custodexa/custodexa.sh start` も表示されます。ただし、アップグレード自体が未完了の場合は表示されません。

次の手順は画面の内容に従います。

| 画面の内容 | 次の手順 |
|---|---|
| 新しいバージョンがデータベースを変更した、またはデータベースを読めなかったとして、`restore` コマンドを表示する | 表示されたとおりに実行します。コマンドはアップグレードが取ったバックアップファイルを指します（例：`sudo /opt/custodexa/custodexa.sh restore /opt/custodexa/backups/custodexa-backup-1.16.1-<STAMP>.tar`）。そのバックアップより後に記録されたものはすべて置き換わります。リストアが完了すると、失敗したアップグレードは `upgrade` の妨げにならず、通常どおり再びアップグレードできます。リストアの説明は第 5 節にあります。 |
| スクリプトで戻せるのは 1.16.0 以降のバージョンである、または第 5 節の手動のリストアを案内する | 下の「手作業で戻す」に従います。画面にバックアップの場所が表示されます。アップグレード前のバージョンが 1.16.0 より前の場合や、手順 7 で自前のバックアップを選んだ場合がこれに当たります。 |
| 前のバージョンのイメージがこのホストにない、または記録と異なる | 画面の `load` コマンドで前のバージョンのオフラインイメージバンドルを読み込み、もう一度 `rollback` を実行します。 |
| 戻せる前のバージョンがない | 戻す対象の変更がありません。このデプロイがスクリプトでアップグレードされていない、前回のバージョン変更がすでに前のバージョンへの戻しだった、アップグレード後にバージョンの記録が変わった、または実行中のバージョンが記録と一致しない、のいずれかです。`status` で状態を確認してください。 |

#### 手作業で戻す

この手順は、アップグレードが手順 7 で取ったバックアップをリストアします。アップグレードの画面がそれを示します。スクリプトが取った場合はバックアップファイル `backups/custodexa-backup-<バージョン>-<STAMP>.tar`、1.16.0 より前のリリースへのアップグレードの場合はフォルダー `backups/<STAMP>/` です（§3.8）。**そのバックアップより後に記録されたものはすべて失われます。** バックアップをサービスの停止中に取るのはそのためです。

手順 7 で自前のバックアップを選んだ場合は、そのために記録した手順でリストアします。下の A と E の代わりに使い、B、D、F は引き続き当てはまります。`BACKUP_DIR` はスクリプトがそのために記録したフォルダーです。

root としてデプロイフォルダーで作業し、画面の値を入れてください。

```bash
sudo -s
cd /opt/custodexa                      # デプロイフォルダー
OLD=1.13.0                             # アップグレード前のバージョン
STAMP=YYYYMMDD-HHMMSS                  # バックアップファイルまたはフォルダーの名前にあるタイムスタンプ
BACKUP_DIR="backups/${STAMP}"          # バックアップフォルダー。バックアップファイルでは E で §5.2 が設定します

# A. バックアップフォルダーが完全であること：INCOMPLETE ファイルがなく、すべてのチェックサムが OK。
#    バックアップファイルは E で §5.2 が確認します。その場合はこの行を飛ばしてください
test ! -e "${BACKUP_DIR}/INCOMPLETE" && ( cd "${BACKUP_DIR}" && sha256sum -c SHA256SUMS )

# B. 新しいバージョンのコンテナーを止めて削除します（DATA_PATH のデータには触れません）
docker compose --project-directory . down

# C. 新しいバージョンが使ったデータベースを、空にせず残します（第 5 節の手順 1）。
#    外部データベースには postgres フォルダーがありません。下の 4 行は飛ばし、
#    新しいバージョンのデータベースは §5.3 のとおりサーバーに残します
DATA_NOW="$(sed -n 's/^[[:space:]]*DATA_PATH=//p' .env | tail -n 1)"
( cd "${DATA_NOW:?}" && pwd )           # 確認：このデプロイのデータルート
mv "${DATA_NOW:?}/postgres" "${DATA_NOW:?}/postgres.before-restore-${STAMP}"
mkdir -m 700 "${DATA_NOW:?}/postgres"
```

**D. 前のバージョンのファイルを元の位置に戻します。** コマンドはアップグレード前のデプロイの形で異なります。

アップグレード前からパッケージのデプロイだった場合は、`current` を前のリリースに戻し、そのリリースのイメージの参照をこの shell に読み込みます（スクリプトは compose を呼ぶたびに読み込みます。第 5 節のコマンドにも必要です）。

```bash
ln -sfn "releases/${OLD}" current.new && mv -Tf current.new current
set -a; . ./current/images.env; set +a
```

**E. バックアップファイルの場合は、この shell で §5.2 に従って中のファイルを取り出します**（その `sudo -s` は実行しません）。その手順 G が、`current` が今指すリリースがバックアップのバージョンであることを確認し、`STAMP` と `BACKUP_DIR` を設定します。**そのうえで、どちらの種類でも、この shell で第 5 節の手順 2 から 6 を実行します。** `STAMP` と `BACKUP_DIR` は設定した値のままです。手順 1 からではありません。B と C がその作業を済ませているためです。外部データベースの場合は、手順 5 の代わりに §5.3 を使います。`docker compose` は `current` を通じて前のパッケージのリリースを起動します。続いて第 6 節を順に確認します。項目 6 のフィンガープリントと、`users`、`sessions` の件数は、`${BACKUP_DIR}/snapshot.txt` と比較してください。

**F. その後。** 第 6 節がすべて通り、新しいバージョンのデータが不要だと確かめてから、`postgres.before-restore-${STAMP}`（外部データベースの場合は、サーバーに取り分けておいたデータベース）を削除します。前のバージョンのイメージはホストに残っている必要があります。スクリプトはイメージを削除せず、欠けている場合はアップグレードのプレビューで警告しています。

パッケージのデプロイでは、スクリプト自身の記録 `state.json` がまだ新しいバージョンとそのアップグレードを示しています。`status` は新しいバージョンを表示し、`upgrade` は実行を拒否して同じ案内をもう一度表示します。そのアップグレードのバックアップ（§5.2 が取り出した `state.json` のメンバー、またはバックアップフォルダーのファイル）から、アップグレード前の記録を戻してください：`cp -p "${BACKUP_DIR}/state.json" state.json`。本バージョンにはこの記録をほかの方法で直すコマンドがありません。その後、§5.2 の説明のとおり、§5.2 が作ったフォルダーを削除してください。平文のデータベース、`.env`、秘密鍵が入っています。

### 5.2 単一のバックアップファイルから各ファイルを取り出す

1.16.0 から、`restore` は各ファイルを自ら取り出します（§5）。以下の手順は、§5 に挙げた場合に手作業でリストアするためのものです。

`backup` またはアップグレードが書き出すバックアップファイル（§3.8）は、第 5 節の前にフォルダーへ展開します。以下の手順はファイルを確認し、メンバーを取り出し、第 5 節が使う名前に変え、インストール済みのリリースのイメージの参照を読み込み、第 5 節のために `STAMP` と `BACKUP_DIR` を設定します。その後、同じ shell で第 5 節の手順 1 から続けてください。手順 0 は、2 行の代入を除いてそのまま当てはまります。

| メンバー | 使う場所 |
|---|---|
| `backup-manifest.json` | 下の手順 E：§5 の手順 0 に必要なバージョンと、マスターキーの方式（第 4 節） |
| `env.bak` | §5 の手順 2。手順 F で `custodexa-env-<STAMP>.bak` に改名 |
| `audit.tar.gz`、`recordings.tar.gz` | §5 の手順 4。`custodexa-files-<STAMP>.tar.gz` がない場合は両方を展開します |
| `tls.tar.gz` | §5 の手順 4。手順 F で `custodexa-tls-<STAMP>.tar.gz` に改名。デプロイに `tls/` がなかった場合はファイルに入っていません（`contents.tls` が `false`） |
| `nginx-tls.conf.template` | §5 の手順 4。`.env` の `TLS_NGINX_TEMPLATE` が指すパスへ戻します。当時設定されていた場合だけ（`contents.nginx_template`） |
| `db.dump` | §5 の手順 5。手順 F で `custodexa-db-<STAMP>.dump` に改名 |
| `db-ca.pem` | §5.3。外部データベースの場合：`PGSSLROOTCERT` が指す CA ファイル（`contents.db_ca`） |
| `state.json` | §5.1 F。アップグレードが取るバックアップにあります（`contents.state`） |
| `snapshot.txt` | 第 6 節：項目 6 のフィンガープリントと、`users`、`sessions` の件数 |
| `release-MANIFEST.json`、`tool-MANIFEST.json`、`SHA256SUMS` | 照合だけに使います |

リストア先は、`product.version` のバージョンのパッケージのデプロイです。別のホストでは、先にそこへこのバージョンをインストールします。root として**リストア先のデプロイフォルダーで**作業してください。第 5 節はそこで `docker compose` を実行し、`.env` を書き、`tls/` を展開するためです。バックアップファイルとその `.sha256` はどこにあっても構いません。`FILE` は絶対パスで指定してください。

以下の各ブロックは、前のブロックが成功したときだけ実行され、最後にどこまで進んだかを表示します。**最後のブロックが `5.2: ready` を表示したときだけ、第 5 節へ進んでください。** それ以外の表示は、照合、復号、改名のいずれかが失敗したことを示します。そこで止まり、その行の上にあるエラーを読み、`BACKUP_DIR` を削除して（`rm -rf "${BACKUP_DIR:?}"`）最初のブロックからやり直してください。

```bash
sudo -s
cd /opt/custodexa                                     # リストア先のデプロイフォルダー
FILE=/path/to/custodexa-backup-1.16.0-YYYYMMDD-HHMMSS.tar   # 絶対パス。暗号化したものは .tar.enc で終わります
STAMP=YYYYMMDD-HHMMSS                                 # その名前の中のタイムスタンプ
BACKUP_DIR="$(pwd)/backups/restore-${STAMP}"          # メンバーを置く新しいフォルダー（絶対パス）
CX_52=start

# A. 複製が完全であること：隣のチェックサムファイルが OK を報告すること
# B. root だけが開ける新しいフォルダー（すでにあれば mkdir は失敗します）
( cd "$(dirname "${FILE:?}")" && sha256sum -c "$(basename "${FILE:?}").sha256" ) \
  && { [ -d backups ] || mkdir -m 700 backups; } \
  && mkdir -m 700 "${BACKUP_DIR:?}" \
  && CX_52=B
echo "5.2: ${CX_52}"
```

C. メンバーを取り出します。暗号化していないファイル（`.tar`）の場合：

```bash
[ "${CX_52}" = B ] && tar -xf "${FILE:?}" -C "${BACKUP_DIR:?}" && CX_52=C
echo "5.2: ${CX_52}"
```

暗号化したファイル（`.tar.enc`）の場合は、§3.8 の「ファイルとパスフレーズの確認」から手元の openssl に合うコマンドを選び、`tar -tvf -` を `tar -xf - -C "${BACKUP_DIR:?}"` に置き換えます。パイプライン全体の終了コードはパスフレーズを消す前に保存し、3 つとも 0 の場合だけ成功とします。`openssl enc -help` に `-saltlen` がある OpenSSL（3.2 以降）の場合：

```bash
if [ "${CX_52}" = B ]; then
  IFS= read -r -s -p 'Passphrase: ' CX_PASS; echo
  printf '%s\n' "$CX_PASS" | openssl enc -d -aes-256-cbc -saltlen 8 -pbkdf2 -md sha256 -iter 600000 -pass stdin -in "${FILE:?}" | tar -xf - -C "${BACKUP_DIR:?}"
  CX_RC="${PIPESTATUS[*]}"
  unset CX_PASS
  echo "exit codes (printf openssl tar): ${CX_RC}"
  [ "${CX_RC}" = "0 0 0" ] && CX_52=C
fi
echo "5.2: ${CX_52}"
```

続いて、どちらの場合も：

```bash
# D. すべてのメンバーが、ファイルを作ったときに書いたチェックサムと一致すること
# E. このバックアップが何か：リストア先のバージョン、マスターキーの方式とフィンガープリント、録画、tls/、プロキシテンプレートを含むかどうか、データベースがどこにあったか
# F. 第 5 節が使う名前
# G. インストール済みのリリースがバックアップのバージョンであること。docker compose のためにそのイメージの参照を読み込みます
[ "${CX_52}" = C ] \
  && ( cd "${BACKUP_DIR:?}" && sha256sum -c SHA256SUMS ) \
  && grep -E '"(product\.version|created_at|kek\.provider|kek\.material_included|kek\.fingerprint|contents\.recordings|contents\.tls|contents\.nginx_template|source\.tls_nginx_template|db\.location)"' \
       "${BACKUP_DIR:?}/backup-manifest.json" \
  && ( cd "${BACKUP_DIR:?}" && mv db.dump "custodexa-db-${STAMP}.dump" \
       && mv env.bak "custodexa-env-${STAMP}.bak" \
       && { [ ! -e tls.tar.gz ] || mv tls.tar.gz "custodexa-tls-${STAMP}.tar.gz"; } ) \
  && CX_VER="$(sed -n 's/^ *"product\.version": "\([^"]*\)".*/\1/p' "${BACKUP_DIR:?}/backup-manifest.json")" \
  && echo "backup ${CX_VER}, installed $(tr -d '[:space:]' < current/VERSION)" \
  && [ "$(tr -d '[:space:]' < current/VERSION)" = "${CX_VER:?}" ] \
  && set -a && . ./current/images.env && set +a \
  && CX_52=ready
echo "5.2: ${CX_52}"
```

手順 G は、インストール済みのリリースがインストール時に記録したイメージの参照 `current/images.env` をこの shell に読み込みます。スクリプトが `docker compose` を呼ぶたびに行うことと同じです。第 5 節は `docker compose` を自分で実行するため、これがないとホストにあるイメージを見つけられないことがあります。表示された 2 つのバージョンが異なる場合は、先にバックアップのバージョンをインストールしてください。

第 5 節へ進む前に：

- **マスターキー**：`kek.provider` が `env` なら、鍵は §5 の手順 2 で `.env` とともに戻ります。`ui` または `kms` なら、バックアップファイルには含まれていないため、アンシールの材料または保管先の資格情報を用意してください。どちらの場合も、第 6 節の項目 6 でリストア後のマスターキーを `kek.fingerprint` と比較します。これは `snapshot.txt` の `fp.kek` と同じ値です。
- **別のホスト**：バックアップの `.env` は、それを作ったホストのものです。§5 の手順 2 の直後、先へ進む前に、ホストを表す 4 つの値をこのホストのものにしてください。`DATA_PATH`（手順 2 の注意）、`TLS_DOMAIN`、`TLS_IP_SAN`、`PUBLIC_BASE_URL` です。マニフェストの `source.data_path`、`source.tls_domain`、`source.tls_ip_san`、`source.public_base_url` に元のホストの値があり、比較に使えます。バックアップにプロキシテンプレートがある場合、§5 の手順 4 は `TLS_NGINX_TEMPLATE` が指す場所へそれを置きます。そのパスがこのホストに合わなければ、これも変えてください（`source.tls_nginx_template` が元のホストの値です）。
- **新しい名前やアドレスの証明書**：これらの値を変えても、§5 の手順 4 でリストアした証明書は変わりません。組み込みの TLS プロキシは、`tls/fullchain.pem` と `tls/privkey.pem` の両方がある限りそれを使い続けます。名前やアドレスが異なる場合は、手順 4 の後、手順 6 の前に一致する証明書を用意してください。`TLS_MODE=selfsigned` では、この 2 つのファイルを削除し、`tls/ca-private/` と `tls/ca-public/` は残します。手順 6 で、リストアした CA から `.env` の現在の値に合わせた新しいサーバー証明書が発行され、その CA をすでに信頼している利用者端末はそのまま信頼を続けます。`TLS_MODE=provided` では、新しい名前とアドレスに一致する証明書チェーンと秘密鍵をこの 2 つのファイルに置きます。自前の入口で TLS を終端している場合、証明書はその入口が管理します。
- **外部データベース**：手順 E が `"db.location": "external"` を表示した場合、第 5 節の手順 5 は当てはまりません。代わりに §5.3 がデータベースを読み込みます。
- **その後**：`BACKUP_DIR` には平文のデータベース、`.env`、秘密鍵が入っています。第 6 節がすべて通ったら削除してください。

### 5.3 外部データベースのデプロイのデータベースを読み込む

1.16.0 から、`restore` はこのようなデータベースを自ら読み込みます（第 5 節の「外部データベースのデプロイをリストアする」）。以下の読み込みは、手作業でリストアする場合（第 5 節に示した場合）と、別のデータベースサーバーや別のデータベースへ移す場合のためのものです。

マニフェストの `db.location` が `external` のバックアップファイルには、デプロイの外にあるサーバー上のデータベースのダンプが入っています（§3.8）。その場合、バンドルされたデータベースを起動して読み込む第 5 節の手順 5 は、以下の読み込みに置き換わります。その後、手順 6 へ進んでください。この形態では手順 1 はサービスを止めるだけで、それが用意する `postgres` フォルダーは使いません。

読み込みの前に、データベースサーバーを運用する人が次を用意します。

- **バージョン**：`db.server_major` のメジャーバージョンの PostgreSQL。ダンプは同じメジャーバージョンの `pg_restore` で読み込みます。リリースのそのバージョンのクライアントイメージにあります（下の 2 つ目のブロックが使います）。
- **データベース**：`DB_NAME` という名前の空のデータベース。所有者は `DB_USER` で、パスワードは `.env` のものです。エンコーディング、照合順序、文字種は `db.encoding`、`db.collate`、`db.ctype` のとおりに作成します。置き換えられるデータベース（アップグレード後に戻す場合は新しいバージョンのもの）を残したいときは、削除せず名前を変え、第 6 節が通ってから削除してください。
- **ロール**：下の 1 つ目のブロックが `db.extra_grant_roles_hex` から一覧するロールを、読み込みの前に作成します。ないと、`pg_restore` はそれらの権限付与についてエラーを報告し、終了コード 1 で終わり、それらの権限は戻りません。backend 自身は `DB_USER` だけで接続します。ダンプにはほかのロール、テーブルスペース、拡張は不要です。バックアップが実行前にそれらを拒否しています（§3.8）。

デプロイ側では、第 5 節の手順 4 の後に次を行います。

- **別のサーバー**：バックアップの `.env` は元のサーバーを指しています。データベースを別のサーバーへ移す場合は、第 5 節の手順 2 の直後に、`.env` の `EXTERNAL_DB_HOST`、`EXTERNAL_DB_PORT`、`DB_SSLMODE`、`PGSSLROOTCERT` をそのサーバーに合わせて設定します。マニフェストの `db.external_host`、`db.external_port`、`db.sslmode` に元の値があります。
- **CA ファイル**：`.env` の `PGSSLROOTCERT` がファイルを指している場合、backend はそのパスで読みます。`/var/log/custodexa/audit` または `/var/lib/custodexa/recordings` の下のパスは、それらがバックアップに入っていれば第 5 節の手順 4 で戻っています。`/var/lib/custodexa/exports` の下のパスは戻りません。どのバックアップにも `exports` は入らないためです（§2）。ファイルがなければ、`BACKUP_DIR` の `db-ca.pem` をそこ（`DATA_PATH` の下）に置いてください。
- **クライアント証明書**（`db.tls_client_cert` が `true`）：その秘密鍵はバックアップファイルに入っていません。証明書と鍵を `PGSSLCERT` と `PGSSLKEY` が指す場所へ戻してください。それらを使って読み込むには、両方を下のコンテナーにマウントし、`CX_CONN` に `sslcert=` と `sslkey=` を加えます。

まず、バックアップのデータベースに必要なものです。

```bash
# このバックアップのデータベースに必要なもの（BACKUP_DIR は §5.2 が設定した値）
grep -E '"(db\.location|db\.server_version|db\.server_major|db\.name|db\.user|db\.encoding|db\.collate|db\.ctype|db\.external_host|db\.external_port|db\.sslmode|db\.tls_trust|db\.tls_verify|db\.tls_client_cert|contents\.db_ca|tool\.dump_image)"' \
  "${BACKUP_DIR:?}/backup-manifest.json"
# 権限を持つほかのロール。1 行に 1 つの名前（ない場合は何も表示されません）
for h in $(sed -n 's/^ *"db\.extra_grant_roles_hex": "\([0-9a-f ]*\)".*/\1/p' "${BACKUP_DIR:?}/backup-manifest.json"); do
  printf '%b\n' "$(printf '%s' "$h" | sed 's/../\\x&/g')"
done
```

次に読み込みです。デプロイフォルダーで、第 5 節の shell の中で行います（`env_get`、`DB_USER`、`DB_NAME`、`STAMP`、`BACKUP_DIR` はそこで設定した値）。サーバーのメジャーバージョンのリリースのクライアント（この形態のインストールが取得したもの）を実行し、バックアップのときと同じ方法で `.env` から接続します。つまり §3.8 の表のとおりで、CA ファイルにはバックアップの `db-ca.pem` を使います。終了コード 0 だけが成功です。それ以外はデータベースが不完全という意味なので、手順 6 へ進まないでください。

```bash
# サーバーのメジャーバージョンのリリースのクライアント。インストールまたはアップグレードで記録したイメージ ID による
CX_MAJOR="$(sed -n 's/^ *"db\.server_major": "\([0-9]*\)".*/\1/p' "${BACKUP_DIR:?}/backup-manifest.json")"
CX_PGIMG="$(sed -n 's/^ *"current\.tool_image_ids": "\([^"]*\)".*/\1/p' state.json | tr ' ' '\n' | sed -n "s/^pgclient${CX_MAJOR:?}=//p")"
echo "PostgreSQL ${CX_MAJOR} client: ${CX_PGIMG:?state.json にそのクライアントの記録がありません}"

# .env からの接続。バックエンドと同じ方法でサーバーを検査します（§3.8 の表）
CX_PORT="$(env_get EXTERNAL_DB_PORT)"
CX_MODE="$(env_get DB_SSLMODE)"; CX_MODE="${CX_MODE:-disable}"
CX_ROOT="$(env_get PGSSLROOTCERT)"
CX_TLS=""
case "${CX_ROOT}" in
  "")
    case "${CX_MODE}" in
      verify-full) CX_TLS="sslrootcert=system" ;;
      verify-ca) CX_TLS="sslrootcert=/etc/ssl/certs/ca-certificates.crt" ;;
    esac ;;
  system) CX_MODE=verify-full CX_TLS="sslrootcert=system" ;;
  *)
    case "${CX_MODE}" in
      require | verify-ca | verify-full) CX_TLS="sslrootcert=/backup/db-ca.pem" ;;
    esac ;;
esac
CX_CONN="host=$(env_get EXTERNAL_DB_HOST) port=${CX_PORT:-5432} dbname=${DB_NAME:?} user=${DB_USER:?} sslmode=${CX_MODE} ${CX_TLS}"
echo "${CX_CONN}"

# ダンプを読み込みます。pg_restore は DB_USER のパスワードを尋ねます
docker run --rm -it --network host \
  --mount "type=bind,src=$(cd "${BACKUP_DIR:?}" && pwd),dst=/backup,readonly" \
  "${CX_PGIMG:?}" pg_restore --dbname="${CX_CONN}" "/backup/custodexa-db-${STAMP:?}.dump"
echo "pg_restore exit code: $?"
```

## 6. リストア後の検証チェックリスト

**1 項目ずつ確認し、いずれか 1 つでも失敗したらシステムを本番の利用へ戻さないでください。**

**`restore` でリストアした後**（§5）は、この一覧の一部をスクリプトがすでに確認しています。すべてのサービスが記録したイメージで動いていること（項目 1）、backend が準備完了でバックアップのバージョンを返すこと（項目 2）です。項目 6 のうち、マスターキー ID と `kek.fingerprint`、および `JWT_SECRET` のフィンガープリントと `snapshot.txt` の `fp.jwt`（記録がある場合）を比べています。取り込んだデータベースもバックアップと比べています。migration、`users`、`sessions`、`audit_logs` の行数、マスターキー ID です。手作業で残るのは、項目 3 から 5、項目 6 のうちエクスポート署名鍵とチェックポイント署名鍵、項目 7 から 10 です。

| # | 確認 | やり方 | 合格の判定 |
|---|---|---|---|
| 1 | すべてのサービスが起動している | `docker compose ps` | 各サービスが実行中で、postgres が healthy（外部データベースの場合、postgres のサービスはありません） |
| 2 | バックエンドのヘルスチェック | `docker compose exec backend wget -qO- http://localhost:8080/health` | 応答が正常（backend は外部にポートを開かないため、コンテナ内から呼ぶ必要があります） |
| 3 | 起動ログに fatal がない | `docker compose logs backend \| tail -50` | 起動を拒否するメッセージがないこと。**KEK が一致しない場合はここではっきり示されます** |
| 4 | フロントエンドに到達できる | 組み込みの TLS プロキシ：`curl -skI https://localhost/`。自前の入口で TLS を終端する場合：このホストで `curl -I http://localhost:${HTTP_PORT:-80}/` を実行し、続けて入口のアドレスでも開く | 200 が返ること。組み込みのプロキシでは `http://` が 301 を返して HTTPS へ転送しますが、これは正常です |
| 5 | ログインの経路が通る | 既存の管理者アカウントでログイン | トークンを取得でき、コンソールに入れること |
| 6 | **鍵の台帳のフィンガープリントの照合** | 管理側の「鍵管理」ページ | env 側の 4 項目（`ENCRYPTION_KEY (KEK)`、`JWT_SECRET`、`エクスポート署名鍵 (Ed25519)`、`チェックポイント署名鍵 (Ed25519)`）のフィンガープリントが、**バックアップ前に記録した値と同じ**であること |
| 7 | 暗号化された列を復号できる | 資格情報を持つ資産を 1 つ開く、または LDAP のログインを 1 回起こす | 復号の失敗が出ないこと |
| 8 | 録画を再生できる | バックアップ前から存在するセッションの録画を 1 件開く | 再生できること。**ローカル由来でもオフサイト由来でも合格とします。** ローカルのファイルがキャッシュから消去済みのものはオブジェクトストレージから取得されます（初回の再生にはダウンロードの待ち時間があります）。その経路でも同じくハッシュを検証してから引き渡されます |
| 9 | 監査チェーンの検証 | 監査側の完全性の検証ページ | 検証の結果がバックアップ前と一致すること |
| 10 | **台帳とバケット内のオブジェクトが対応している**（オフサイト保管を有効にしている場合のみ） | 管理側の「オフサイト保管」ページ：設定の要約と世代の状態が想定どおりであること、失敗一覧に異常な滞留がないことを確認し、オフサイトへ渡った録画を 1 件抜き取りで再生します | 台帳の状態と遠隔の実際が一致していること。**対応しない場合、2 つの方向を分けて読み取ります。** 台帳に行があってバケットにない＝より新しいデータベースの時点へリストアした（または遠隔がライフサイクルのルールで整理された）。バケットにあって台帳にない＝孤児のオブジェクトで、多くはより古い時点へリストアした場合です（§3.1 参照）。監査の中の保管の連なりのイベントで突き合わせてください |

> 6 番目が最も価値のある項目です。**フィンガープリントは一方向の要約であり、照合して同じであれば、リストア後に使っているのが同じ鍵であることを確認できます。** 鍵の材料に触れる必要はありません。バックアップのたびにこの**4 つ**のフィンガープリントもあわせて記録し、バックアップとともに保管してください。バックアップ時に 3 つしか記録しないと、リストア後に照合できない項目が 1 つ残ります。抜けるのはチェックポイント署名鍵です。
>
> 鍵管理のページは**アンシールの後でなければ**入れません（モード B とモード C）。そのためこの項目は、サービスが回復した後に行います。
>
> **モード C では、同じページにいるあいだに保管先の設定もあわせて照合してください。** アドレス、リージョン、Transit の鍵の名前、ロール識別子はバックアップから戻ってきたものであり、バックアップの時点の姿です。その時点より後にトポロジーが変更されていた場合、いま見えているのは古い宛先であり、このページで設定し直す必要があります。その変更のアラートと監査の行は、バックアップされた側のシステムにあり、こちらにはありません。
>
> リストア後、チェックポイント検証ページの役割の割り当ての照合は、バックアップに含まれるチェックポイントのうち、保全の時点の照合が一致していた最新のものを基準として行われます（不一致が残ったまま保全されたチェックポイントは起点になりません）。リストア後、照合が一致した最初の保全が新しい起点になります。

## 7. 例外的な状況での手作業による対応

### 7.1 シール期間の journal の 2 つの header がどちらも無効な場合

**現象**：サービスは待ち受けの開始を拒否し、**その journal ファイルを書き換えません**。

システムはこのファイルを自動で再構築しないよう意図的に作られています。アンシールの試行の回数を記載したファイルを自動で「修復」することは、履歴をゼロに戻す正当な経路を提供することと同じだからです。

**対応（4 段階。順を追って実行してください）**：

1. そのファイル（`seal_journal.bin`）をオフラインで複製して保存します。**その場で変更しないでください。**
2. 外部のツールで読み取れるかどうかを確認し、記憶媒体の破損なのか人の手による変更なのかを判断します。
3. 新しいファイルで数え直すかどうかを人が判断し、**その判断を記録します**。誰が決めたのか、いつ、なぜか。この記録は、後日「この記録がなぜゼロから始まっているのか」を説明する唯一の根拠になります。
4. 壊れたファイルを取り除いてからサービスを再起動します。

### 7.2 退役済みだが材料が未消去の KEK で起動した場合

**現象**：サービスは fail-close で起動を拒否し、エラーメッセージがそれが退役済みの KEK であることを直接示し、退役の理由に応じて異なる案内を出します。

- **理由が「切り替え済み」の場合**：「この KEK へどうしても戻す必要があるなら、runbook に従ってその退役の行を手作業で復元してから再起動してください。誤設定であれば `ENCRYPTION_KEY` を現行の KEK へ戻してください」と案内します。
- **理由が「破棄済み」の場合**（その KEK が現役になったことがない）：現行の KEK へ戻すか、現行の KEK で起動したうえで再ラップをやり直すよう案内します。

システムは**退役を自動で反転しません**。切り替えが完了した後に古い KEK を設定するのは、ほぼ確実に操作の誤りであり、自動で反転すれば、意図して行った鍵の儀式を静かに取り消すことになります。

**「退役の行を手作業で復元する」ことの可否**：KEK の退役はソフトな退役であり、状態の列を変更するだけで、**ラップ材料は明示的に消去するまで保持されます**。したがって「退役データをクリーンアップ」を実行するまでは、データ層で古い KEK へ戻すことが常に可能です。いったん明示的な消去を実行すると、その材料は消されて復元できず、その時点で古い KEK で起動しても一般的な不一致のエラーが出るだけになります。詳しくは[プラットフォーム自身の特権資格情報のローテーション](./privileged-credential-rotation.md)の KEK の項を参照してください。

### 7.3 リストア後の監査の退避ファイルの回収

リストアされた `${DATA_PATH}/audit` の下に退避ファイルがある場合、バックアップの時点より前に監査の書き込みの失敗があったことを意味します。これらの記録はリストアによって自動的にデータベースへ取り込まれることは**ありません**。対応は、事後の追跡の根拠としてファイルを保存しておくことです。

## 出力の機密情報検出：対象範囲と運用上の判定

検出は SSH、K8s、データベースコンソールの解析済みテキスト出力のみを走査します。RDP/VNC の画面、暗号化・圧縮・符号化された内容（Base64 を含む）は対象外です。端末の制御シーケンスは描画も除去もしません。符号化により照合を回避でき、一致は機密情報を**含む可能性**を示します。未検出は不存在を意味しません。この機構は警告のみで、配信済みのバイトを遮断・変更しません。

出力ルールの追加、無効化、変更は**新しいセッション**から適用されます。進行中のセッションは開始時のルール集合を維持します。アップグレード、リストア、切り替え後は方向、有効状態、プロトコルを確認し、新しいテキストセッションで適用ルールを確認してください。インストール後の初期ルールは計16件で、元の入力12件、agent 向けの入力阻止2件、カード番号・秘密鍵ヘッダーの出力2件です。組み込みカードパターンが元のままであれば Luhn 検証も行います。編集後は通常の正規表現となり、カード番号の検証は行いません。

同じルールとセッションの一致は5秒の窓で集約し、セッション終了時に残りを確定します。アラートと転送には識別子、ルール、回数、時刻を残し、command は空で、一致した原文やバイト位置は保存しません。reason_code の `o1:<base36 count>` が回数を表し、webhook には `possible_sensitive_output.count` もあります。これは含む可能性の兆候であり、全出力を走査した証明ではありません。

容量制限のあるキューがあふれると、そのセッションの走査を無効化し、出力は継続します。既存の監査検索で action=`output_scan_disabled`、resource=`session`、当該セッションの resource_id を確認します。details は session_id と reason=`queue_overflow` のみで、出力原文を含みません。サーバーログだけでは監査記録の代わりになりません。それ以降の出力は未走査として扱い、既存の権限で証拠を確認し、負荷を確認してから新しいセッションを開始します。スキャナーの失敗もサーバーログに残りますが、アラートがないことは走査成功の保証ではありません。

共通のマスキングプリミティブは完全置換したテキストと置換回数を返しますが、**本バージョンの製品応答経路には接続されていません**。録画、コマンド記録、その他の証拠には適用しません。原文には既存の保存期間、アクセス制御、バックアップ／リストア手順が引き続き適用されます。


### 主体と資格情報の完全性の対象範囲

検証画面はロール割り当て、主体の種別／所有者、資格情報の状態を個別に表示します。アップグレード後、新しいスナップショットを含む最初のチェックポイントまで、新しい二行は「対象外」です。検出は即時ではなく、検証、チェックポイント作成、トークン発行前に照合します。不一致は項目ごとに `principal_state_integrity`／`principal_state_mismatch` イベントと通知を生成し、差分には識別値だけを含めます。不一致や照合エラーでも発行を続行します。エラーは不明としてログに記録し、業務データを変更しません。サービス層の状態投影行の actor は `system` とし、操作者は既存の HTTP 監査行で記録します。

互換性は一方向です。新版は旧チェックポイントを検証できますが、旧版は新しいスナップショットキーを完全には検証できません。キーの削除、再署名、旧来の単一機構の失敗イベント一意インデックスへ戻すことは禁止です。ロールバックにはアップグレード前の整合したバックアップとリストア手順が必要です。ペイロードは現行の最新バージョン（現在 v3）を維持します。

## Agent MCP の運用

有効な人間の owner を指定して agent 主体を作成します。owner または管理者が名前と有効期限付きの agent token を発行し、一度だけ表示される平文を実行者のシークレット保管先に保存します。agent は user ロールのみを持ち、資産とアカウントの許可範囲を明示します。agent を動かすマシンに stdio クライアント `custodexa-mcp` を https://github.com/custodexa/custodexa-mcp からインストールします。`go install github.com/custodexa/custodexa-mcp@latest` を使うか、リリースのバイナリを取得します。リリースのバイナリは、同じリリースで公開された `checksums.txt` で検証します。環境変数 `CUSTODEXA_AGENT_TOKEN` を `custodexa-mcp` に渡し、`CUSTODEXA_MCP_URL` を HTTPS の `/api/v1/mcp` に設定します。人間の JWT と cookie はこのエンドポイントでは使用できません。stdio クライアントは転送のみを行い、判定と証跡保存はサービス側で行います。token をコマンド引数や報告書に記載しないでください。

agent が申請したタスクが人の承認を待つかどうかは、申請対象ごとの資産のアクセスポリシー区分で決まります。資産自身に `access_policy` が設定されていればそれを、なければ全体の `access_policy_default` を使います。`approval` 区分の項目は、その資産を範囲に含む承認者が判断するまで保留されます。`open` と `reason` 区分の項目は申請時に承認され、`auto_approved: true` とポリシースナップショットとして記録され、承認票は付きません。出荷時の既定では多くの資産が `approval` 以外に入るため、設定を変更しない環境では agent のタスクがすべて自動承認されます。人の判断を必須にするには、対象資産の `access_policy` を `approval` に設定するか、全体の `access_policy_default` を `approval` にします。必要な承認票数は `access_request_min_approvals` で決まります。この選択は agent に最初の資産許可を与える前に決め、運用手順書に明記してください。自動承認も記録は完全に残りますが、人による統制ではありません。

ローテーションでは新しい名前付き token を発行し、実行者のシークレットを更新し、新しい MCP 接続で資産の可視性を確認してから旧 token を失効させます。既存 token の秘密を直接交換する機能や、バックアップから平文を自動復元する機能はありません。失効は旧 token のセッションを閉じます。ハンドルを別の token や MCP 接続に引き継ぐことはできません。リストアやスタンバイへの切り替えの後は MCP 接続を新規作成し、必要に応じてタスクを申請します。メモリー上のハンドルと 60 秒間の冪等キャッシュは再起動を越えて保持されません。再開前に token とタスクの保存状態を確認します。

インシデント時は該当 token を失効または停止し、必要なら agent を無効化して、タスク、ツール台帳、HTTP リクエストの監査記録を確認します。探索ブレーカーは token を停止してイベントを記録します。owner または管理者が理由を付けて解除しますが、停止済み token は再有効化されないため、新たに発行してください。この計数が対象とする参照は一種類だけです。すなわち、実在し、かつその agent に一度も開示されたことのない資産への参照です。存在しない、または削除済みの資産 id への参照は retired、過去に開示された資産への参照は revoked に分類され、いずれもイベントとしては記録されますが、作動しきい値には計上されません。識別子を手当たり次第に列挙しても計上されないイベントが並ぶだけであり、これを一般的なスキャン検知として説明しないでください。これは範囲外の実在資産へ繰り返し手を伸ばす行為に対する統制です。より広い列挙は、アラートルールと申請レート方針で扱ってください。拒否された参照の意味を判断する前に、ブレーカーイベント一覧の `class` 欄を確認します。通知は既存の webhook／Slack に `owner_id` 付きで送られます。個人受信箱ではなく、本人への到達を証明しません。可視 exposure は migration 後から記録され、以前の可視履歴は復元しません。拒否された参照を不正と判断する前にこの境界を確認します。

Token の期限切れ、紐付いたタスク項目の期限切れ、タスク終了は、既存セッションと実行中のツールを終了し、現在のコマンド完了を待ちません。期限の現状確認は 250ms ごとですが、この間隔は完了 SLA ではありません。失効は既存の終了経路を使います（目標は 3 秒以内、遅延時は証跡を記録）。対象は本システムが作成したセッションだけで、遠隔のバックグラウンド処理の停止や実行済み変更の取消しは保証しません。実行中リクエストの取消しはそのセッションを閉じます。POST 間のクライアント離脱は即座には検出できず、5 分間の idle lease 満了でハンドルを終了します。即時切断検出とは記載しないでください。

`completed` はプロンプトを再観測したことだけを示し、コマンドの終了も成功も保証しません。プロンプトは偽装でき、バックグラウンドの出力が混在することもあります。`timed_out` は結果不明です。再送前に後続出力を確認してください。同じハンドルの冪等キーは 60 秒間の重複書込みを抑止しますが、キーなしでは再実行され得ます。`needs_input` では実行者が `send_keys` で復帰を要求し、システムは自動で割込みを送りません。`read_screen` は行バッファーであり仮想画面ではありません。agent に返す文字列はマスクされますが、録画とコマンド記録は原文を保持します。マスクはルール駆動で、対象を個別に列挙する方式です。汎用の機微データ保護ではありません。適用されるのは、有効で `direction=output` かつ主体種別が agent を含み、プロトコルが一致するアラートルールで、一致した範囲をプレースホルダーに置き換えます。有効なルールに一致しない内容はそのまま agent に返り、出荷時のルールはカード番号パターンと秘密鍵ヘッダーパターンの二種類のみです。このルール一覧を「この環境が agent チャネルで何を機微と定めるか」の定義として扱い、許可した資産で実際に取得できるデータと突き合わせ、不足する種類はルールを追加してください。マスクは人間の端末、録画、コマンド記録には適用されません。

データベース、録画、チェックポイント、対応するバージョンの完全性鍵を保全します。pending 行が示すのは記録済みの意図であり、送達や完了ではありません。タスク／ハンドルに帰属できない呼出しはツール台帳の前で拒否し、当該 MCP HTTP 監査行に主体、ツール、理由コード、時刻を保存します。コマンド完全性の coverage 軸は監査調査ビューと一括エクスポートのみで提供します。単一 session 指定のエクスポートには coverage がありません。degraded 行がゼロでもコマンド欠落がなかった証明にはなりません。報告書の各版とタスク終了時刻を保持し、pending の結果を捏造しないでください。

リストア後は証跡を照合してから agent 作業を再開します。
