# デプロイ形態の制限

[English](../../ops/deployment-topology-limits.md) | [繁體中文](../../zh-TW/ops/deployment-topology-limits.md) | **日本語** | [他の言語 →](../../README.md)

> 対象バージョン：Custodexa 1.0。パッケージのデプロイの節は 1.13.0 から適用されます。

## 本バージョンがサポートするデプロイ形態

**本バージョンは単一インスタンスでのデプロイです。システム全体で、アプリケーションのインスタンスは 1 つしか実行できません。**

2 つ以上のアプリケーションインスタンスを同時に実行するとデータの問題が発生します。この形態は設計も検証もされておらず、本番環境で使用してはなりません。

**本バージョンから、同じデータベースに対して 2 つめのアプリケーションインスタンスを起動しようとすると、確認を求めて停止します。** いかなる書き込みよりも前に停止し、ロック保持者のフィンガープリントと 2 つの進み方を出力します。確認が行われるまで、サービスのパスを開くことも、マイグレーションの実行も、データベースへの書き込みも行いません。**確認は、そのインスタンス自身が提供する停止ページで行い**、管理者がロック保持者の確認コードに署名します。そのコードを `INSTANCE_GUARD_ACK` に設定するのは、スクリプト向けの同等の手段です。いずれにせよ、確認を経た起動は毎回、`audit_logs` のイベント、メトリクス、管理画面の常設バナーとして残ります。**確認したうえでの実行には監査証跡が残ります。**

**ガードが防ぐのは「知らないまま起きること」であり、「起きること」そのものではありません。** 確認後に 2 つのインスタンスが並存して生じるデータの問題は、ガードが防ぐものではなく、確認した人が負うものです。ガードが保証するのは、停止させること、知らせること、そして事後に「どのインスタンスが、いつ、どのロック保持者に対して、（停止ページを使った場合は）どの管理者アカウントで確認したか」を `audit_logs` から証明できることです。メッセージの読み方と復旧手順は[デプロイとアップグレードの SOP §2.6b](./upgrade-sop.md#26b-単一インスタンスロックが別のデータベースセッションに保持されていてバックエンドが停止した場合)を参照してください。

具体的には、次の 3 つのアーキテクチャを除外します。

- ロードバランサーの背後に 2 つ以上のアプリケーションインスタンスを配置する構成。
- 2 つ以上のインスタンスが同時に動く多重化デプロイ：高可用性（HA）クラスタ、active-active、あるいは稼働中のインスタンスの隣で既に動いているホットスタンバイ。
  **コールドスタンバイは別のものであり、手順としてサポートされます**：データベースをアプリケーションホストの外に置く（external database overlay）とき、2 台目のホストは 1 台目が停止したあとにだけ起動し、同じデータベースへ向けて引き継ぎます。どの時点でも稼働するインスタンスは 1 つだけです。手順、スタンバイホストに事前に必要なもの、切り替えで保たれないものは[アプリケーションホストのスタンバイ切り替え](./standby-takeover.md)を参照してください。この形態でもガードはまったく同じで、1 台目が実はまだ動いていたときにスタンバイを止めるのがガードです。
- ローリングアップデートによるアップグレード。切り替えの過程で、新旧 2 つのインスタンスが必ず並存します。
  **ガードを備えたバージョン同士のローリングアップデートは、新しいインスタンス側で停止します**（新しいインスタンスがロックを取ろうとした時点で旧インスタンスの保持を検知し、確認の関門で止まります）。ガードのない旧バージョンから本バージョンへ上げる、その 1 回だけは停止しません（旧バージョンはロックを保持しないため）。この回はアップグレード SOP のチェックに頼る必要があります。

> この制限が対象とするのは**アプリケーションインスタンス**です。データベース、guacd、フロントエンドの nginx がそれぞれ独立したコンテナとして動作することは正常なデプロイ形態であり、この制限の対象外です。

> **ガードはガードを備えたバージョンしか認識しません。** ガードを含まない旧バージョンはロックを保持しません。ガードのないバージョンから本バージョンへ初めて上げるとき、および本バージョンからガードのないバージョンへ戻すときは、新旧インスタンスが並存しても停止しません。この 2 つの窓は、アップグレード SOP の「旧インスタンスが停止していることを先に確認する」チェックが担います。

> **コネクションプールのモード。** アプリケーションは postgres に直接接続するか、セッションプーリングモードのコネクションプールを経由する必要があります。トランザクションプーリングではロックがセッション間を移動してしまい、ガードがロックの喪失と再取得を繰り返し報告します。この構成はサポートされません。

## インストールパッケージによるデプロイと管理スクリプト

インストールパッケージでインストールしたデプロイは、その管理スクリプト `custodexa.sh` で運用します。本バージョンのスクリプトの対応範囲は次のとおりです。

- **Linux 専用**（x86_64 または aarch64）。それ以外のオペレーティングシステムでは何もする前に停止し、評価用にソースからの実行を案内します。
- **1 台のホストに 1 つのデプロイ。** コンテナー名が固定されている（`custodexa-backend` など）ため、同じホストに 2 つ目のデプロイは共存できません。`install` は既存のデプロイを見つけると実行を拒否します。対象は、フォルダー内の状態ファイル、別のフォルダーに属する `custodexa-backend` コンテナー、ソースの git 作業ツリーです。
- **デプロイフォルダーのパス**に使えるのは英字、数字、`. _ / -` だけです。このパスはエスケープせずに `.env` と状態ファイルに書き込まれます。`install` は何かを書き込む前にこれを確認します。
- **コマンドは一度に 1 つ。** デプロイを変更するコマンドはフォルダーのロックを取得し、その間に起動された 2 つ目は終了コード 3 で停止します。`status` はロックを取得せず、何も変更しません。
- **Compose は常に同じプロジェクトで呼び出します。** スクリプトはプロジェクト名 `custodexa`、プロジェクトディレクトリとしてのデプロイフォルダー、現在のリリースの compose ファイルを明示します。`install` は `COMPOSE_FILE` と `COMPOSE_PROJECT_NAME` も `.env` に書き込むため、デプロイフォルダーで手入力した `docker compose ps` や `logs` も同じサービスを対象にします。`up` と `config` を手入力するときは `--project-directory .` も付けてください。付けないと `.env` を誤った場所で探して停止し、コンテナーには何も変更を加えません。
- **アップグレードとバックアップもスクリプトで行います。** `upgrade` はサービスを止め、バックアップを取り、新しいリリースへ切り替えます。`backup` は同じ停止してのバックアップを単独で行います。どちらもローリングアップデートではありません。`rollback` は、新バージョンがデータベースを変更していなければデプロイを直前のリリースへ戻し、変更していた場合、またはデータベースを読めない場合（外部データベースでは、このホストでデータベースクライアントを選べない場合）は何も変更せず、代わりに使う `restore` コマンドまたは手動の手順を表示します。リストアは、そのバックアップより後に記録されたものをすべて置き換えます（[バックアップとリストア §5.1](./backup-and-restore.md#51-管理スクリプトでアップグレードした後アップグレード前のバージョンに戻す) を参照）。[アップグレード SOP](./upgrade-sop.md#管理スクリプトによるアップグレード) と[バックアップとリストア §3.8](./backup-and-restore.md#38-管理スクリプトによるバックアップパッケージのデプロイ) を参照してください。古い git clone デプロイは、ファイルやサービスを変更する前にすべての `custodexa.sh` 入口で拒否されます。[手動移行](./upgrade-sop.md#古いソースデプロイの手動移行)を計画するか、別の空のディレクトリにインストールして手動でリストアしてください。スクリプトは古いツリーを変換しません。`--images-from source` はソースのチェックサムを確認してからパッケージ自身のイメージだけをローカルでビルドします。上流イメージとビルド依存関係は別途取得するため、完全なオフライン手段ではありません。

### フォルダー構成

パッケージを展開すると `custodexa/` ができ、これがデプロイフォルダーです。`install` の後（`DATA_PATH` が既定値の場合）は次のとおりです。

```
custodexa/
  custodexa.sh -> current/custodexa.sh   管理スクリプト
  current -> releases/<バージョン>       実行中のリリース
  releases/<バージョン>/                 出荷時のままのリリース：スクリプト、compose ファイル、
                                         MANIFEST.json、VERSION、.env.example、reverse-proxy/、
                                         source/。install が images.env と image-ids.env を追加
  .env                                   設定とシークレット（権限 600）
  state.json                             何がインストールされているか。スクリプトだけが書き込む
  logs/                                  デプロイを変更したコマンドごとに 1 つのログ（権限 700）。
                                         .env のシークレットの値は書き込まれない
  backups/custodexa-backup-<バージョン>-<タイムスタンプ>.tar
                                         `backup` で取ったバックアップ：1 つのファイル（暗号化
                                         した場合は .tar.enc）とその .sha256。権限 600、
                                         シークレットを含む。組み立て中は各部分が
                                         backups/.partial-<タイムスタンプ>/（権限 700）にある
  backups/<タイムスタンプ>/              アップグレードが取るバックアップ：フォルダー
                                         （権限 700、シークレットを含む）
  tls/                                   組み込み TLS プロキシの証明書
  restore/<タイムスタンプ>-<接尾辞>/     `restore` を 1 回実行するごとの作業フォルダー（権限 700）
  data/postgres/                         データベース（同梱のデータベースの場合のみ）
  data/recordings/                       セッションの録画（所有者 1000、グループ 0、権限 2770）
  data/audit/                            監査ログファイル
  data/exports/                          非同期のエクスポートの成果物
```

デプロイがバージョンをまたいで保持するものはすべてフォルダーの最上位にあります（`.env`、`state.json`、`tls/`、`data/`、`backups/`）。`releases/` の下のリリースには、出荷時の内容と、`install` がそのリリース用に記録したイメージの参照だけが入ります。

`data/exports/` はコンテナーを作り直しても残りますが、**バックアップの対象ではありません**。その中の証拠パッケージの成果物には復号された平文が含まれます。`DATA_PATH` 全体を複製するバックアップからは除外してください。[バックアップとリストア §2](./backup-and-restore.md#2-永続データの保存先) を参照してください。

`restore` は 2 種類のフォルダーも残します。リストアがいったん始まると、スクリプトはどちらも自動では削除しません。1 つ目は、実行ごとに `restore/` の下に作られる作業フォルダー（権限 700）です。実行中は、作業フォルダーにデータベース、`.env`、各アーカイブの平文のコピーが入り、デプロイフォルダーのあるファイルシステムにバックアップファイルの約 1.1 倍の空き容量が必要です。リストアが完了すると、これらのコピーは削除され、残るのは小さなものだけです。データベースが把握しているのにこのホストにない録画の一覧と、リストア前の `state.json` と `.env` のコピー（秘密情報を含む、権限 600）です。途中で止まったリストアは、`restore --resume`、`--revert`、`--abandon` がここから読むため、フォルダー全体を残します。リストアが完了するか断念するまでは残してください。その後は削除できます。サービスを停止する前に拒否された実行は、自分が作った作業フォルダーを削除し、何も残しません。外部データベースのデプロイでは、インポートのあいだ作業フォルダーにインポート用の SQL テキストも入り、その大きさは圧縮していないデータベースとほぼ同じです。権限付与を省いた場合は、省いた権限付与の一覧（`skipped-grants.txt`）を残します。新しいホストで外部データベースにすでにデータがあった場合は、事前のエクスポート `safety-db.dump`（そのデータベースの平文のコピー）を、リストアが完了した後も残します。削除するのは完了した `restore --revert` だけなので、不要になったら自分で削除してください。

2 つ目は、リストアが置き換えたデータです。`DATA_PATH` の下の現在のデータベースと監査ファイル、および `tls/` は、`postgres.before-restore-<タイムスタンプ>`、`audit.before-restore-<タイムスタンプ>`、`tls.before-restore-<タイムスタンプ>` に名前を変えてその場に保持され、削除するまで、それぞれ元のデータと同じ容量を使います。元に戻したリストアは、置いたデータを `*.partial-restore-<タイムスタンプ>` として残し、新しいホストで断念したリストアは `*.abandoned-<タイムスタンプ>` を残します（容量の見積もりは同じです）。以前の内容がすべて入っており、シークレットや記録された証拠も含むため、稼働中のデータと同じアクセス制御で扱ってください。[バックアップとリストア §6](./backup-and-restore.md#6-リストア後の検証チェックリスト)の確認が済み、元に戻す必要がなくなってから、自分で削除してください。`backups/` の下の安全バックアップは別のファイルで、独自の保存期間を持ちます。外部データベースのデプロイには名前を変える `postgres` フォルダーがありません。データベースはそのサーバー上でその場で空にしてインポートし、元の内容は安全バックアップに、新しいホストでは事前のエクスポートにあります。手順は[バックアップとリストア §5](./backup-and-restore.md#5-リストアの手順)にあります。

`state.json` は 1 行ずつ決まった形式と照合して読み込まれます。壊れている場合、これを読むコマンド（`status` を含む）は終了コード 5 で停止し、何行目かを示して、隣に保存されている前のコピー `state.json.prev` を案内します。

## 製品のロールが届かないところ：ホスト

製品のロールと権限が管理するのは、人がインターフェースと API を通じて行うことです。製品が動くホストには届きません。ホストで root として操作できる人、そこで Docker を使える人、`.env` を読み書きできる人、データベースの認証情報でデータベースに接続できる人は、製品でどのロールを持っていても、このモデルの外にいます。

- **管理スクリプト**はホスト上で root 権限で動き（各手順とも `sudo` で実行します）、製品へのサインインを求めません。バックアップ、リストア、アップグレード、戻し、その他のコマンドは、実行できる人なら誰でも使えます。製品のロールはホスト上の権利を何も与えません。一部のノードだけを管理する管理者ロールを持っていても、スクリプトを実行する権利は得られず、スクリプト自体も製品のロールを確認しません。ホストの root または Docker へのアクセスも与えられた人は、製品でどのロールを持っていても、デプロイ全体に対してスクリプトのすべてのコマンドを実行できます。ホストへのアクセスは、システム全体を預かるべき人にだけ与えてください。
- **`.env`** には秘密と、サービスの起動時の設定があり、これを編集できる人はサービスの動き方を変えられます。監査の総スイッチ `FEATURE_AUDIT_LOG_ENABLED` は、release モード（同梱の compose ファイルが設定するモード）ではオンに保たれ、`false` が上書きされたときは起動ログがその名前を示します。モードと compose ファイルもホスト上にあるため、これはホストを動かす人に対する制御ではありません。
- **データベースで直接行った**ロール割り当て、グループのメンバー、外部グループのマッピングの変更は止められません。後から検出されます。権限状態は、チェックポイントの検証時、チェックポイントを封じるとき、トークンの発行前に、アプリケーションが記録した変更と比べられます。記録された変更にはそれぞれ、監査ログと同じ完全性キーで計算した完全性コードが付きます。有効なコードのない記録は、記録のない変更として扱われます。確認の記録も同じです。差異があると、項目 `permission_state` の `principal_state_integrity` 障害イベントが開き、異なる識別子と通知が出ます。このイベントは、状態が再び一致するか、スーパー管理者が監査ログのページの「障害イベント」タブで理由を入力して確認するまで開いたままです。確認は監査ログに記録され、権限を何も変えず、どの操作も止めません。比較は権限の付証が有効になってから働きます。付証を持つ最初のチェックポイント、通常は 1.18.0 へのアップグレード後の最初の封印から始まり、それより前の変更は報告されません。有効になった後、比較を完了できない場合（たとえば変更記録が欠けている、または検証に通らない場合）は、同じ項目の障害イベントが開き、チェックポイントの検証ページに表示されます。その間は、その後の直接変更を検出できません。封印を続けても、保存期間による切り詰めが行われても、この状態は終わりません。チェックポイントが信頼できる起点かどうかはそのチェックポイント自身の署名の中に記録されており、比較を完了できない間に封じたチェックポイントが起点になることはありません。切り詰めてもこれは変わりません。署名付きの切り詰め記録が、切り詰めたチェックポイントに付証があったか、検証に通らない点があったかを引き継ぐためです。スーパー管理者はこのイベントを確認して、比較の基準を現在の状態にリセットできます。理由と、比較できなかった理由の概要、そして信頼できる参照点がある場合はそれと現在の状態との差異（件数と最大 20 個の識別子）が監査ログに記録され、破損した記録はそのまま残ります。リセットは現在の状態全体を受け入れるもので、それ以前の検証に通らない記録の出所を証明するものではありません。権限の付証は各チェックポイントの署名内容の一部です。どのチェックポイント（最新のものを含む）でも付証が消去または改変されると、そのチェックポイントは検証に失敗し、チェーン構造の警告が出ます。この項目の障害イベントがデータベースで直接削除されたり終了時刻を入れられたりした場合、次の比較で再び開かれ、通知もあらためて送られます。それまでは障害イベントのタブに表示されません。次の制限が残ります。データベースへのアクセス権と、完全性キーまたはチェックポイントの署名キーの両方を持つ人は、検証に通る記録を書けます。最後の封印より後に書かれた変更記録を、それが記録する変更とともに取り除いた場合、比較はそれを報告しません。付証が有効になって以降ホスト上に残る証拠をすべて削除した場合（その後に封じたすべてのチェックポイント、その間の切り詰め記録、すべての変更記録）、次の封印はその時点の状態を新しい起点とし、比較は一致と報告します。権限関連のテーブル、チェックポイント、切り詰め記録、変更記録をまとめて以前の整合したコピーに戻した場合（データベースの残りはそのままでも）も同じです。どちらもホストの外に置いたコピーでしか見分けられません（次の段落）。最新のチェックポイントに保存された内容が一部消去されると、封印が止まり障害イベントは開いたままになります。スーパー管理者のリセットでは修復できず、復旧には信頼できるバックアップの復元が必要です。
- **管理対象ホストのシークレットを設定できる人は、その人だけが知る値を選べます。** 新しいシークレットの宣言と、カスタムのシークレットでの切り離しは、監査記録に残りアラートが出ますが、これを止める仕組みはありません。その人は以後、このプラットフォームを経由せずにホストへ直接接続できます。これらの権限は、担当範囲のホストへのアクセスを本来持ってよい人にだけ与えてください（[プラットフォーム自身の特権認証情報のローテーション §13.7](./privileged-credential-rotation.md#137-誰が行えるか権限を失うとどうなるか)）。
- **バックアップのリストア**はホストの操作です。バックアップ時点の権限を戻し、その後に取り消した割り当ても戻ります。新しい復元世代はリストア前に発行されたサインインとトークンを終わらせますが、バックアップの後に変わったことを再構成はしません（[バックアップとリストア §5](./backup-and-restore.md#restore-でリストアする)）。

ホストを制御する人は、プログラム、秘密、データベース全体を、より古いコピーも含めて置き換えられます。製品にはそれを防ぐ仕組みがありません。ホストのアクセス制御と、ホストの外に置く証拠のコピー（監査記録の syslog 転送とオフサイト保管）で備えてください。

## ロールと各ロールの管理範囲

コンソールで何ができるかは、割り当てられたロールで決まります。ロールは、どのページが見えるか、そのページで何を変更できるかを決めます。**管理権限は、プラットフォーム内の接続権限を自動的には付与しません**。資産管理者・認可管理者などの管理権限では、ホストに接続できるかどうかは接続の認可で決まり、管理ロールとは関係ありません。例外は組み込みのスーパー管理者で、接続の免除を持ち、別途の接続認可を必要としません。

| 組み込みロール | 管理するもの | ノードで限定できるか |
|---|---|---|
| 管理者（スーパー管理者） | ロール定義を含むすべて。カスタムロールの作成・変更・複製・削除ができるのはスーパー管理者だけです。 | いいえ |
| 資産管理者 | 資産、ノード（資産グループ）の管理、資産のテスト、資格情報ライブラリとその資格情報の変更（秘密の設定、ローテーション、範囲の変換、切り離し、紐付け）、パスワード変更の計画。認可ルール、資産ごとのアクセスポリシー、承認範囲は含みません。 | はい |
| 認可管理者 | 認可ルール、承認範囲、資産ごとのアクセスポリシー。資産の閲覧、ユーザー管理、ユーザーグループ管理は含みません。 | はい |
| ID 管理者 | ユーザー、ユーザーグループ、ロールの割り当て。割り当てられないロールは次の節を参照してください。 | いいえ |
| システムセキュリティ管理者 | セキュリティ設定、アラート、通知チャネル。 | いいえ |
| 監査担当者 | 読み取り専用の監査業務、日次レビューの承認、アクセスレビューの閲覧。アクセスレビューの承認には別途 `accessreview:manage` が必要で、このロールには含まれません。 | いいえ |
| 承認者 | 割り当てられた承認範囲内の接続申請の承認。 | システム全体の割り当てでのみ有効（下記） |
| 一般ユーザー | ワークスペースと、自分の接続および申請。 | システム全体の割り当てでのみ有効（下記） |

組み込みロールは変更できません。資産管理者と認可管理者はロックされたテンプレートで、アップグレード後は誰かが割り当てるまで誰も持っていません。

**組み込みの一般ユーザーと承認者は、システム全体に割り当てた場合のみ有効です。ノードに限定すると権限は付与されず、システムは割り当てを送信された内容のまま保存して通知を表示します。**

### ロールをノードで限定する

- ロールは、ユーザーまたはユーザーグループに**割り当てるとき**にノードで限定します。ロール自体にはノードの設定はありません。同じロールを、ある人にはシステム全体で、別の人にはノード限定で割り当てられます。範囲を限定された保持者が何をでき、何をできないかは、後続の各節（ノード、資産、認可ルール、共有認証情報、個別資産の接続ポリシーの管理）に書かれています。製品が記録するだけで防がないこと（資産やノードの移動、範囲外でも使われる共有認証情報の変更、個別ポリシーの引き下げ、既知のパスワードの設定、資産のアドレス変更による誘導、二人の共謀）は、それらの節、前述のホストの節、ID 管理者ロールの節、SSH ホスト鍵の節で説明しています。
- 外部ディレクトリのグループを、資産管理者または認可管理者に直接マッピングすることはできません。外部グループをユーザーグループにマッピングし、そのユーザーグループにノード限定でロールを割り当ててください。
- ノードで限定した割り当てがシステム全体に広がることはありません。割り当てが指定するノードがひとつも存在しない場合、その割り当ては権限を与えません。割り当てが指定しているノードは、その割り当てがある間は削除できません（「限定された範囲でのノード管理」を参照）。
- カスタムロールは、含まれる機能がすべてノード限定に対応している場合にだけノードで限定できます。システム全体にしか適用できない機能を含む場合は、システム全体にしか割り当てられません。
- 権限セットが空のカスタムロールはノード限定で割り当てられますが、ノードは効力を持ちません。レスポンスの `node_range_no_effect` に表示され、管理画面にも通知が表示されます。システム全体でのみ有効な権限、またはノード限定が未実装の権限を一つでも含むカスタムロールは、ノード限定での割り当てが拒否されます。
- ID 管理者は、スーパー管理者ロール、システムセキュリティ管理者ロール、高リスクの権限を含むカスタムロール以外のすべてのロールを割り当てられます（この 3 種を割り当てられるのはスーパー管理者だけです）。次の節を参照してください。

## ID 管理者ロールを誰に渡すか：何に届き、製品は何を報告するだけか

**ID 管理者とシステムセキュリティ管理者は、ロックされた 2 つのロールテンプレートです。権限の内容は変更できず、ほかのロールと同じ方法で割り当てます。** アップグレード後は、誰かが割り当てるまで誰も保持していません。アカウントへの直接の割り当て（アカウントの「ロールと範囲」タブ）、ユーザーグループ、外部グループのマッピングのいずれでも割り当てられます（[デプロイとアップグレードの SOP](./upgrade-sop.md#1180-へ上げる場合権限モデルの移行)）。アカウントを作成するフォームはアップグレード前にあったロールだけを示すため、テンプレートはアカウントを作成した後に割り当ててください。ロール管理ページには 2 つのテンプレートが組み込み・変更不可として一覧表示されます。以下に挙げる制限（スーパー管理者のアカウントに対する制限と、スーパー管理者ロールおよびシステムセキュリティ管理者ロールの割り当ての制限）は、これらのどの経路にも適用されます。

ID 管理者は、アカウントとロールの割り当てを担当する IT または SRE の担当者向けのロールで、権限が限定されたロールではありません。保持者は、下に挙げる保護されたロール以外のロールを、誰にでも（自分自身を含む）付与でき、接続の許可を持つグループにメンバーを加えることもできます。そのため実際には、保護されたロールの権限以外のほぼすべての権限に届きます。スーパー管理者に近い水準で信頼できる人にだけ渡してください。

- **このロール単独ではできないこと。** アカウントまたはユーザーグループに対するスーパー管理者ロールまたはシステムセキュリティ管理者ロールの割り当てと取り外し、そのどちらかを持つグループのメンバー変更、およびそうしたグループの削除は、スーパー管理者に限られます。高リスクの権限を 1 つでも含むカスタムロールも、同じく保護されたロールです。高リスクの権限とは、証拠の削除、アラートの停止や送信先の変更、セキュリティ制御の緩和、鍵の管理ができる権限で、録画の削除（`recording:delete`）、システムアラート・アラートルール・通知チャネル・syslog 転送の管理（`systemalert:manage`、`alertrule:manage`、`notification_channel:manage`、`syslog:manage`）、セキュリティポリシーとポリシーグループの管理（`securitypolicy:manage`、`policygroup:manage`）、鍵とオフサイトストレージの管理（`key:manage`、`offsite:manage`）です。こうしたロールの割り当てと取り外し、それを持つグループのメンバー変更、およびそうしたグループの削除は、スーパー管理者に限られます。スーパー管理者のアカウントに対するパスワードの設定、多要素認証の無効化、外部 ID の紐づけ、直接のロールの書き込みも、スーパー管理者に限られます。この 2 つのロールのどちらかを（どの経路で得たものでも）持つアカウントの無効化、削除、有効化、および外部 ID の紐づけ解除とあわせたアカウントの無効化も、スーパー管理者に限られます。拒否された要求は、その理由とともに監査ログに記録されます。こうしたアカウントに対するその他の操作（外部 ID の紐づけ解除だけを行う場合、基本情報の編集、ログインロックの解除など）は通常のルールに従います。
- **システムセキュリティ管理者のアカウントには、ID 管理者から守られていない操作があります。** そのアカウントの無効化、削除、有効化は前の項目のとおり拒否されますが、ID 管理者は、そのパスワードの設定、多要素認証の無効化、外部 ID の紐づけと解除ができ、製品はそれを止めません。この種の操作はそのたびに同じトランザクションで監査ログに書かれ、セキュリティ担当者向けのシステムアラートが発生します。これは事後の検知です。したがって 2 つのロールの職務分離は、ID 管理者が同じ水準で信頼できる場合にのみ成り立ちます。システムセキュリティ管理者ロールを誰が持つかはデプロイ時に決めてください。同じ人が両方のロールを持つことを製品は止めません。ロール割り当てのプレビュー要求（`POST /api/v1/role-assignment-previews`）はこの組み合わせを報告しますが、割り当て自体はプレビューを必要とせず、止められることもありません。
- **付与は報告されますが、ブロックされません。** ロールの割り当てやグループの変更を保存する前に、影響を受ける人の権限を合わせるとリスクの高い組み合わせになる場合、事前にプレビューのリクエストで確認できます。プレビューの結果はヒントであり、変更を止めません。変更後、自分自身の権限の変更ではシステムアラートが発生し、他の人に管理系のロールを付与した場合も同様です。他の人に一般のロールを渡す場合や、接続の許可だけを持つグループにメンバーを加える場合はアラートが発生せず、通常の監査ログにのみ残ります。複数人が共謀する場合は、上記のいずれでも対象になりません。

## 限定された範囲でのノード管理：移動で何が変わり得るか、スーパー管理者だけができる操作

ノード管理を含むロールは、一部のノードに限って割り当てられます。保持者は、そのノードとそのサブツリーの内側でのみ、ノードの作成、名前変更、説明の変更、移動、削除を行えます。以下は、製品が実際に止めることと、記録するだけのことです。

- **ノードや資産の移動は、誰が対象に含まれるかを変え得ますが、製品は止めません。** 管理範囲と接続権限は別です。ツリーの同じ部分で両方を持つ人は、ノードやその配下の資産を、自分がすでに接続権限を持つノードへ移し、自分の接続範囲を広げられます。また、移動によって、他の人の接続権限や承認範囲が一部の資産に及ばなくなることもあります。どちらの場合も製品は止めません。ノードの移動ごとの監査記録には、対象に加わった資産と外れた資産、影響を受けた接続権限、承認範囲、管理範囲が識別子のみで並び、一覧ごとに最大 100 件と総数が付きます。同じノードに対して両方の権限を持つ人がいる場合は、この記録を確認してください。
- **管理範囲から参照されているノードは、誰も削除できません。** アカウントまたはユーザーグループのロール割り当てのいずれかがそのノードを範囲ノードとして使っていると、削除は `RULE_NODE_SCOPE_REFERENCED` で拒否されます。スーパー管理者も同じです。スーパー管理者には、参照している割り当ての一覧（誰か、どのロールか、グループなら所属人数）と、各アカウントまたはグループのページへのリンクが返ります。それ以外の保持者には割り当ての件数だけが返り、誰が持っているかは分かりません。判定は割り当ての記録そのものを数えるため、無効化されたアカウントが持つ割り当ても削除を止めます。
- **一部のノード操作はスーパー管理者に限られます。** 保持者自身の範囲のルートであるノードの名前変更、説明の変更、削除は 403 で拒否されます。最上位でのノード作成、ノードの最上位への移動も同じです。移動は保持者の範囲ルートより厳密に下にあるノードだけが対象で、いずれかの割り当てが範囲ノードとして使っているノードを含むサブツリーの移動は、スーパー管理者に限られます。範囲の制限がないノード管理の保持者（全ノードが対象）は、この最後の規則と構造上の検査（深さ、同名、ループ）にだけ従います。
- **範囲外のノードは操作できません。** 範囲が限られた保持者が、範囲外または削除済みのノードを操作する要求を送った場合、応答は存在したことのないノードと同じ 404 です。ツリーと一覧には、保持者の管理範囲内のノードと、保持者が接続権限を持つ資産のあるノードが含まれます。それらの上位のパスは位置を示すためだけに含まれます。範囲外のパス上のノードにはパスにすぎない印が付き、操作できません。
- **ノードの範囲としての利用を外すのは別の手順です。** 割り当てが使っているノードの削除は拒否されるため、先にアカウントまたはグループのページで割り当てを変更します。製品は、ノードの削除に伴って割り当てを外すことはしません。
- **共有認証情報の所属ノードは範囲に従います。** 一部のノードにだけ割り当てられた人が共有認証情報を作成するとき、認証情報を共有に変換するとき、または所属を変更するときは、自分の範囲内のノードしか選べません。下の共有認証情報のセクションを参照してください。このセクションはノード管理のみを対象とします。資産の作成と編集を一部のノードに限定した場合の動作は、次のセクションで説明します。

## 限定された範囲での資産管理：何を与えないか、製品が記録するだけのこと

資産管理を含むロールは、一部のノードに限って割り当てることができます。保持者はその範囲内で、ノードに属する資産の閲覧、編集、テスト、無効化、削除と、そのアカウントの管理を行えます。以下の制限は、製品が強制する内容と、記録するだけの内容を示します。

- **資産を管理できることは、プラットフォームからその資産へ接続する権限を意味しません。** 管理範囲と接続許可は別です。資産を編集または削除できる人が接続を開始できるのは、接続許可もその人に及ぶ場合だけです。資産一覧では、管理範囲だけで見える資産は接続が許可されていない状態として表示され、接続の入口もありません。管理範囲はホスト自体にも及びません。前述の「製品のロールが届かないところ：ホスト」を参照してください。
- **資産の作成や所属ノードの変更は、誰が対象に含まれるかを変え得ますが、製品は記録するだけです。** 木の同じ部分について管理範囲と接続許可の両方を持つ人は、すでに接続許可を持つノードに資産を所属させ、自分の接続範囲を広げることができます。所属により、資産が他の人の接続許可やレビュー範囲に入ることもあります。製品はこれらを阻止しません。資産の初回の所属と、ノード変更のたびに書かれる監査エントリには、追加・削除されたノードと、それにより対象に加わった、または外れた人と管理範囲が、識別子のみ、リストごとに最大 100 件と総数で記録されます。これはすべての操作者に当てはまります。一括インポートで作成された資産の初回の所属には、操作者が資産作成の権限を一部のノードを対象とする割り当てだけで持つ場合にのみ、この記録が付きます。同じノードについて両方の権限を持つ人がいる場合は、この記録を確認してください。
- **資産のアドレスを変えると、預かっているログイン認証情報が別の場所へ送られることがあり、製品は報告するだけです。** 資産を編集できる人は、そのホストやポートを別のマシン、自分が管理するマシンにも向けられます。以後の接続試行は新しいアドレスを使います。適用されるチェックが認証への続行を許可した場合、プラットフォームは資産が預かるログイン認証情報を使って、そのアドレスのサーバーに認証します。接続テストには資産テスト権限 `asset:test` が必要で、接続許可は不要です。認証を行うかどうかは、以下のとおりプロトコルによって異なります。データベースの接続テストは TCP 接続を開くだけで、認証情報を送りません。ホスト、ポート、プロトコルを変更すると、誰が変更しても同じトランザクションで `asset_address_changed` のシステムアラートが生成されます。RDP の証明書検証をオフにする、データベースの TLS モードを下げる、Kubernetes を検証の省略に設定すると、`transport_verification_relaxed` が生成されます。どちらもセキュリティ担当者が事後に知るためのもので、変更も認証情報の送信も止めません。同じ資産について管理範囲と接続許可の両方を持つ人は、この一連の操作を一人で完了できます。資産の編集権限は、範囲内の資産が預かっている認証情報と同じ慎重さで付与してください。新しいアドレスの相手をプラットフォームがどこまで確認するかは、プロトコルと資産の設定によります。
  - **SSH。** 提示されたホスト鍵を、アドレスに関係なくその資産の記録と照合します。資産にホスト鍵の記録があり、リセット後の再記録待ちでない場合、提示されたフィンガープリントが記録と異なると不一致と判定します。チェックと不一致の記録が成功すると、ユーザーのターミナル、ファイル転送、接続テストは認証に進み、パスワード変更と認証情報のローテーションは停止します（「SSH のホスト鍵が記録と一致しないとき」を参照）。別のマシンが同じホスト鍵を使う場合、この照合では不一致になりません。資産にまだ記録がない場合は、別の資産が新しいアドレスについて持つ記録と照合し、そのアドレスにも記録がなければ、初回の接続で提示された鍵を記録して警告なしに接続を続けます。その後パスワード認証を使えば、パスワードはそのマシンに渡ります。公開鍵認証では秘密鍵は送られません。
  - **RDP。** 資産で証明書の検証（`rdp_verify_cert`、既定はオフ）をオンにしない限り、サーバー証明書を検証しません。RDP 資産の接続テストは、この設定がオンでも検証しません。
  - **VNC。** サーバーの身元を確認しません。
  - **データベース。** サーバー証明書を確認するのは、資産の TLS モードが `verify-ca` または `verify-full` のときだけです。モードが未設定、または `disable`、`require` のときは、新しいアドレスで応答する相手を確認しません。
  - **Kubernetes。** 資産で検証の省略（`k8s_insecure_skip_tls`）を設定しない限り、資産に設定した CA またはシステムが信頼する認証局で API サーバーの証明書を検証します。
- **保持者の範囲外にも所属している資産は、その保持者は削除も無効化もできません。** リクエストは `RULE_ASSET_HAS_OUT_OF_SCOPE_NODES`（409）で拒否され、応答には範囲外のノード数だけが含まれます。保持者は自分の範囲内のノードから資産を外すことができ、外した後その資産は範囲外になります。この権限をグローバルな割り当てで持つ人には、この規則は適用されません。
- **未分類の資産。** どのノードにも所属していない資産については、削除または無効化の権限をグローバルな割り当てで持つ人が、従来どおり削除または無効化でき、監査も従来どおり残ります。その権限を一部のノードへの割り当てでしか持たない人には、存在しない資産と同じ 404 が返ります。
- **管理範囲を通じて見える資産では、範囲外のノードは表示されません。** 範囲が限定された保持者には、その範囲を通じて見える資産の一覧と詳細に、範囲内のノードと範囲外の所属数だけが表示されます。接続許可だけで見える資産では、従来どおりノードが表示されます。資産の作成と編集の応答も同じ規則に従います。グローバルな割り当てで作成または編集できても、範囲からも接続許可からも見えない資産については、応答には範囲外の所属数だけが含まれます。資産を保存しても、保持者に見えない所属は維持されます。
- **資産の一括操作に件数の上限はありません。** バックエンドは、一括移動、タグ追加、削除の 1 回のリクエストに含められる資産の数を制限しません。ただしリクエスト本文は、内蔵のフロントエンドプロキシの本文サイズ上限（既定 1 MiB、資産 ID でおよそ十万件規模）を受けます。これを超えるリクエストはバックエンドに届く前に 413 で拒否されます。バッチ全体は単一のトランザクションで実行されるため、所要時間は資産の数に応じて長くなり、実行中は同時に行われる他のトポロジー関連の書き込みが遅くなります。製品は件数で大きなバッチを阻止せず、所要時間の数値も示しません。影響がある環境では、非常に大きなバッチを自分で分割してください。
- **組み込みロール。** 組み込みの一般ユーザーと承認者は、システム全体に割り当てた場合のみ有効です。ノードに限定すると、他の割り当てチェックを通過するユーザーへの直接割り当てであれば、製品は送信された内容のまま保存しますが、権限は付与されず、レスポンスの `node_range_no_effect` に表示され、管理画面でもそのロールに通知が表示されます。承認者はユーザーグループには割り当てられません。スーパー管理者と監査員は、システム全体にしか適用できない権限を含むため、ノードに限定できず、リクエストは拒否されます。資産管理者と認可管理者のテンプレートは、一部のノードへの割り当て向けに設計されています（「ロールと各ロールの管理範囲」を参照）。

## 限定された範囲での認可ルール管理：範囲が及ぶ内容と、自己付与チェックの限界

認可ルール管理権限（`authorization:manage`）の割り当てが一部のノードに限定されている場合、保持者は範囲内の資産とノードに対してのみ、認可ルールを作成、調整、削除できます。以下の制限は、製品が強制する内容と、対象外の内容を示します。

- **範囲が制限するのはルールの対象（オブジェクト）であり、主体ではありません。** ユーザー、ユーザーグループ、エージェントはノードに属さないため、範囲が限定された保持者も、既存の任意のアカウントまたはグループを、範囲内の資産やノードに対するルールの主体にできます。認可画面が使うセレクタは固定のフィールドだけを返します（アカウント：ID、サインイン名、表示名、種別、状態、ロール名。グループ：名前、説明、メンバー数）。メールアドレス、サインイン履歴、その他のアカウント詳細は含まず、アカウント画面を開く権限や、アカウントへの書き込み権限を与えるものではありません。返される識別子は、ルールがそのアカウントやグループを指すときに使う値です。
- **範囲外へのリクエストには、存在しないものと同じ応答が返ります。** 範囲外の資産やノード、または対象が範囲外にあるルールを指定したリクエストには、存在しない資産、ノード、ルールと同じ応答が返ります（書き込みと単一の参照は 404、一覧とセレクタの絞り込みは空の結果）。範囲が限定された保持者のバッチリクエストは、含まれるオブジェクトのいずれかが範囲外または存在しない場合、全体が拒否され、何も書き込まれません。応答には使用できなかったオブジェクトの数だけが含まれます。範囲の制限がない保持者には、従来の応答が返ります。
- **ルール一覧は、範囲内の資産に届くすべてのルールを示すわけではありません。** 範囲が限定された保持者には、一覧にオブジェクトが範囲内にあるルールだけが含まれます。範囲より上のノードに付いていて、範囲内の資産も対象にするルールは一覧に出ず、その保持者は変更できません。2 つの有効アクセスのビューは、このようなルール経由を含め、範囲内の資産に到達できる全員を引き続き一覧します。これらのビューでは、ルールが保持者の一覧にない場合、ルール識別子は常に含まれません。範囲より上の祖先ノードは、位置を示すためだけに名前とパスが表示されます。それ以外の範囲外のノードを通る経路については、応答にノード名とパスを含めず、範囲外の所属数だけを含めます。そのため保持者は、範囲内の資産に誰かがアクセスできることは分かっても、それを与えているルールを見ることも削除することもできません。
- **ルールのアカウント範囲の変更に、スーパー管理者は不要になりました。** この権限の保持者は、範囲内のルールのアカウント範囲を狭めることができます。広げられるのは、ルールの作成者とスーパー管理者に限られます。主体が保持者本人、保持者が属するグループ、または保持者が所有するエージェントであるルールは、その保持者は調整できません。一時的な許可のアカウント範囲は変更できず、申請に紐づく一時的な許可は直接削除できません。
- **自己付与チェックは、ルールの作成または調整の時点だけで判定されます。** このチェックは、主体が操作者本人、操作者が属するグループ、または操作者が所有するエージェントであるルールを拒否します。スーパー管理者は対象外です。その後に再判定はしません。グループに対して作成されたルールは、後からそのグループにメンバーが加わっても再検討されません。2 人の間の関係も見ません。2 人の保持者がそれぞれ相手に対するルールを作成した場合、製品は両方を受け付けます。これらをチェック自体の限界として扱い、それに応じて、誰がこの権限を持つかと監査ログを確認してください。
- **影響を受けるすべての資産が範囲内にある保持者は、一時的な許可を取り消せます。** スーパー管理者、元の承認者、範囲が一致するレビュー担当者に加えて、この権限の保持者は、取り消しで状態が変わるすべての資産が自分の範囲内にある場合に、一時的な接続許可を取り消せます。範囲の制限がない割り当ての保持者は全資産が範囲内となるため、このリリースでは、この権限を全体に対して持つスーパー管理者以外のユーザー（カスタムロールなど）は、あらゆる一時的な許可を取り消せます。申請全体を取り消す場合、これらの資産には、取り消しによって一緒に終了する保留中の項目の資産も含まれます。そのいずれかが範囲外にあると、この経路は適用されず、既存の規則で判定されます。エージェントアカウントは、この権限ではこの能力を得られません。これらのいずれの経路にも該当しない保持者は、403 で拒否されます。
- **取り消しのたびに、取り消し自体の監査エントリが 2 件書かれます。** 取り消しとその監査エントリは 1 つのトランザクションで保存され、エントリを書けなければ取り消しは保存されません。トランザクションのコミットとセッションの切断の後、同じアクションの 2 件目のエントリに、終了したセッションが記録されます。2 件目を書けない場合はログ行が 1 行残るだけで、取り消しは有効のままです。これはスーパー管理者の取り消しを含む、すべての取り消しに当てはまります。認証済みのすべての API リクエストが残すリクエストログは別に記録されるため、API 経由の取り消し 1 回で、同じアクションのエントリが 3 件残ります。
- **一部のノードに限って割り当てる方法。** この権限（`authorization:manage`）を一部のノードに限って割り当てるには、ロール割り当ての 2 つの一括置換エンドポイント、`PUT /users/:id/roles` と `PUT /user-groups/:id/role-bindings` に `role_nodes` フィールドを付けて書き込みます（API 仕様を参照）。管理画面では、ユーザーまたはユーザーグループの「ロールと範囲」タブで、ロールを特定のノードに設定してノードを選びます。タブには、資産一覧の管理範囲について試算した台数が表示されます。これは、そのロールのすべての操作が作用できる資産数ではありません。組み込みの認可管理者ロールはこの権限を含み、一部のノードに割り当てられます。一部のノードに限定すると、権限が適用される範囲が絞られますが、そのノード配下の資産への接続権限は付与されません。この節は、一部のノードに限った割り当てを製品がどう扱うかを説明しています。

## 限定された範囲での共有認証情報：影響の確認が止めるもの、止めないもの

共有認証情報の所属は、グローバルか 1 つのノードです。一部のノードにだけ割り当てられた資産管理者は、自分の範囲内に所属する共有認証情報を管理します。共有認証情報は、所属先の範囲外にある資産にも紐付けられるため、変更すると、その管理者が管理していないホストにまで影響が及ぶことがあります。

- **共有認証情報の登録値の訂正も、パスワード変更も、紐付けられたすべてのホストに適用されます。その人の範囲外のホストも含みます。** 訂正はすべての紐付けを一度に更新します。パスワード変更は、リモート接続で紐付けられたホストごとにパスワードを変更します。自分の範囲内のホストだけを変更したい場合は、先にそれらを 1 台ずつ共有認証情報から離脱させてください。離脱するとそのホストのパスワードが変更され、そのホスト専用の認証情報を持つ状態になります。
- **確認が証明するのは、その人が知らされたことであり、変更を止めるものではありません。** どちらの操作も、送信の前に、紐付けられたホストのうち範囲内が何台、範囲外が何台かが表示され（件数のみで、範囲外のホストは名指しされません）、承知した旨のチェックが必要です。チェックを入れた人は、範囲外のホストの認証情報も一緒に変更できます。製品はこれを、範囲を越えようとする人への防御としては示しません。変更を送信する前に、範囲外の台数がその人に返されていることを確かめるだけです。共有認証情報の訂正やパスワード変更の権限は、その認証情報が紐付けられたすべてのホストに対する権限と同じ重さで扱ってください。
- **サーバーが実際に確認すること。** 確認は、その時点の範囲外のホストの集合とともにサーバーに保存されます。有効なのはそのユーザー、その認証情報、その操作に限られ、1 回だけ使えます。変更を送信する時点で、範囲外の集合に確認時には含まれていなかったホストがあれば、台数が同じでも、リクエストは `RULE_CREDENTIAL_IMPACT_CONFIRMATION_REQUIRED`（409）で拒否され、何も変更されません。集合のどのホストも確認時の集合に含まれていれば、そのまま変更されます。確認に有効期限はありません。
- **記録されるもの。** その変更の監査記録に、範囲外のホストの台数と確認の識別子が残ります。
- **どう対処するか。** `credential:set-secret` と `credential:rotate` は、その認証情報が紐付けられたすべてのホストにログインできる権限と同じ慎重さで付与してください。他の管理者のホストを特定の認証情報経由で触れさせたくない場合は、その認証情報の紐付けを所属ノードの範囲内に収めてください。

## 個別資産の接続ポリシー：誰が変更できるか、製品が報告するだけのこと

資産ごとに独自の接続ポリシー（`open`、`reason`、`approval`）を持たせ、デプロイ全体の既定値より優先させることができます。この上書きの設定と解除は独立した権限で、認可ルールグループのアクセスポリシー権限（`access_policy:manage`）です。資産の編集には含まれません。資産を編集できてもこの権限を持たないロールは、このフィールドを送れません。`access_policy` を含むリクエストは（上書きの解除に使う空文字列も含めて）全体が拒否されます。空でない値を付けた資産の作成や、いずれかの行に値があるバッチインポートも同じで、リクエストまたはバッチ全体が拒否され、何も書き込まれません。保持者は、資産の編集権限なしでこのフィールドだけを変更できます。他のフィールドを加えたリクエストには、資産の編集権限も必要です。この権限が全ノードを対象とするか一部のノードに限られるかにかかわらず、保持してもデプロイ全体の既定値は変更できません。既定値を変更できるのは、セキュリティポリシーの管理権限（`securitypolicy:manage`）を持つ人だけです。組み込みの認可管理者ロールはアクセスポリシー権限を含み、ノードで限定できます。組み込みのシステムセキュリティ管理者ロールはセキュリティポリシーの管理権限を含みます。スーパー管理者は予約された身分として両方を持ちます。それ以外の組み込みロールにはどちらも含まれません。

- **引き下げは報告されるだけで、止められません。** 上書きを下げる場合も、上書きを解除してより低い既定値に戻る場合も、資産の有効な段階を下げる変更は、操作者が誰であっても同じトランザクションで操作ログに書かれ、`access_policy_relaxed` システムアラートが発生します。段階を保つ、または上げる変更と、新規作成の資産ではアラートは発生しません。アラートには資産、操作した人、変更前後の段階が記されます。どちらかの記録が書き込めない場合、その変更は保存されません。割り当てが一部のノードに限られた保持者による範囲内の資産の変更も、同じように扱われます。
- **制約。** この権限の保持者は上書きを下げることができ、別の人がその資産への常設の接続許可を誰かに与えていれば、その人はその後レビューなしで接続できます。製品は操作ログとシステムアラート（製品に削除の手段はなく、アラートの保存期間の設定でのみ消えます）を残しますが、引き下げも、その後の接続も止めません。この権限を誰が持つかは、この点を踏まえて決めてください。
- **一部のノードに限った割り当ては、範囲内の資産だけを対象とします。** この権限の割り当てが一部のノードに限られている場合、保持者が上書きを設定または解除できるのは、範囲内のノードに少なくとも一つ所属している資産だけです。範囲外の資産へのリクエストには、存在しない資産と同じ応答が返り、何も変更されません。空でない上書きを付けた資産の作成や、いずれかの行に上書きがあるバッチインポートでは、その資産のノードの少なくとも一つが範囲内にある必要があります。そうでなければ、この権限を持たない人と同じように、リクエストまたはバッチ全体が拒否されます。上書きのある資産の一覧には、こうした保持者には範囲内の資産だけが表示され、範囲外のノードにも所属する資産については、所属の一覧には範囲内のノードだけが載ります。載ったノードの完全なパスには、位置を示すための祖先の名前が、祖先が範囲外であっても含まれます。範囲外のそのほかの所属は、数だけが示されます。範囲はこの権限自身の割り当てだけで決まります。他のノードについて資産の閲覧、資産の編集、接続許可を持っていても、範囲は広がりません。
- **この権限だけを持つ人には、設定を完了できる Web の操作手順がありません。** ロールでこの権限と資産の閲覧だけを与えられ、ほかの権限を持たない人には、現在、上書きの設定を完了できる Web 上の操作手順がありません。API を使用してください。
- **一部のノードに限って割り当てる方法。** この権限（`access_policy:manage`）を一部のノードに限って割り当てるには、ロール割り当ての 2 つの一括置換エンドポイント、`PUT /users/:id/roles` と `PUT /user-groups/:id/role-bindings` に `role_nodes` フィールドを付けて書き込みます（API 仕様を参照）。管理画面では、ユーザーまたはユーザーグループの「ロールと範囲」タブで、ロールを特定のノードに設定してノードを選びます。タブには、資産一覧の管理範囲について試算した台数が表示されます。これは、そのロールのすべての操作が作用できる資産数ではありません。組み込みの認可管理者ロールはこの権限を含み、一部のノードに割り当てられます。一部のノードに限定すると、権限が適用される範囲が絞られますが、そのノード配下の資産への接続権限は付与されません。この節は、一部のノードに限った割り当てを製品がどう扱うかを説明しています。

## 外部への提供が平文 HTTP の場合のログイン状態の保持

**外部への提供が http のままのデプロイでは、セキュリティポリシーの「ログイン状態を https 接続でのみ保持」を無効にする必要があります。** ログイン状態は 1 つの HttpOnly cookie で保持されます。このポリシーキーが既定値（有効）のとき、ブラウザーはその cookie を https 接続でしか保存・送出しません。平文 http のもとでは、そもそも保存されません。利用者はログインできますが、ページの再読み込み、新しいタブを開く、タブを閉じてから戻る、のいずれでもログイン画面に戻ります。ログイン状態を復元できるものがブラウザー側に何も残っていないためです（アクセストークンはページの実行中のメモリにのみ存在し、ブラウザーのストレージには保存されません）。

判別方法は次のとおりです。ログイン後に再読み込みすると再ログインを求められ、ログイン画面自体がその原因を説明します。対処は 2 つあり、正しい解決は外部の入口に https を構成することです。それまでの間は、セキュリティポリシーで当該キーを無効にすればログイン状態の保持は正常に戻ります。その代償として、ログイン状態の認証情報が暗号化されていない接続の上を流れます。それはデプロイ全体が http であることと同じ水準のリスクであり、新たに追加されるリスクではありませんが、長期的な状態としてよいものでもありません。

## 外部の身元情報のソースから与えられるロール：そちら側の変更がいつ効くか

外部のディレクトリや ID プロバイダーに由来するロールとユーザーグループのメンバーシップは、**ログインの時点で、そのログインが運んできたグループの情報にもとづいて再計算されます**。セキュリティポリシー「グループマッピング再検証の時限」（`mapping_revalidation_hours`：整数の時間、既定は 12、0 または 1〜168、0 は制限なし）が制限するのは、マッピング由来の権限を持つアカウントのウェブセッションの長さと、ログイン時にグループを読み取れない場合に、最後にそのアカウントのグループを読み取ったのがどれだけ前までなら権限を保つかの 2 つです。セッションはそれを開いたログインから数えられ、最後に読み取った時刻はログインの時点でだけ比べられるため、この時限そのものはソース側での取り上げが効くまでの期限ではありません。ログインのたびに再計算されるのは、そのログインで使ったソースのマッピングだけです。同じアカウントが別の紐付け済みソースからログインできる場合、元のソースから得た権限には、ここで説明する上限が適用されないことがあります。以下の目安は、その後も同じマッピング元を使い、時限が正の値で、途中でポリシーを緩めない場合に限ります。これらの前提での上限は、最悪の場合も含めて次の各点のとおりです。外部のソース側で権限を取り上げることに依存するデプロイでは、次の各点が必ず関わってきます。

- **時限を設定している（0 でない）場合、ウェブセッションはそれを開いたログインから数えて最長で時限までです。** マッピング由来の権限（どのソースから得たものでも、ロールまたはユーザーグループのメンバーシップ）を 1 つでも持つアカウントのウェブセッションは、この時限を超えません。セキュリティポリシー「Web セッションの最大時間」のほうが短ければそちらに従い（以下ではこれをセッションの長さと呼びます）、セッションを開いたログインから数えられ、更新しても延びません。そのセッションが終わると、本人はもう一度ログインする必要があり、そのログインが運んできたグループから、そのログインで使ったソースの権限が再計算されます。それまでのあいだ、すでに開いているセッションは保持していたロールを持ち続けます。したがって上記の前提のもとで、毎回のグループ情報がソース側の取り消しを反映していれば、利用できる期間は取り上げから最長でおよそセッション 1 回分です。その時点で開いているセッションが終わり、次にそのソースからログインしたときに権限が再計算されるか、ソースがそのログインを拒否します。マッピング由来の権限を持たないアカウントは「Web セッションの最大時間」だけに従います。
- **ログイン時にグループを読み取れない場合、最後に読み取ったのが時限の範囲内であればマッピング由来の権限は保たれ、そのログインで開いたセッションは長さいっぱいまで続きます。** 対象は、そのログインでアカウントのグループを読み取れなかった場合（読み取りの失敗、値の型の不一致、またはグループの一覧が長すぎて含まれていないことをトークンが示している場合）と、有効なルールがあるのにソースにグループの属性名またはクレーム名が設定されていない場合です。そのチャネルが最後にこのアカウントのグループを読み取ったのが時限の範囲内であれば、マッピング由来の権限は保たれ、再計算を見送ったことが監査ログに記録されます。最後に読み取ってから時限を過ぎている場合、または一度も読み取っていない場合は、そのチャネルのマッピングが付与したロールとユーザーグループのメンバーシップがそのログインで取り消され、監査ログに `membership_revalidation_expired` がチャネル、時限、最後に読み取った時刻とともに記録されます。これによって実際に権限が取り消された場合、そのアカウントの他のログインは終了します。後のログインでグループを読み取れた場合、そのグループと現在のルールにもとづいて再計算します。一致するルールによって認められる権限だけが付与されます。管理者が割り当てたロールとメンバーシップ、および別のソースから得た権限は影響を受けません。最後に読み取った時刻が比べられるのはログインの時点だけです。権限を保ったログインで開いたセッションは、最後に読み取った時点ではなくそのログインから数えられ、更新のときに読み取りの時刻を改めて確認することはありません。グループを読み取れないログインは、読み取りとして数えられません。最悪の場合は、最後に読み取った直後にソース側で権限を取り上げたものの、ソースが本人のログインを引き続き許し、グループだけを渡さない場合です。最後にグループを正常に読み取ってから再検証の時限に達する直前にログインすると、そのログインでは既存のマッピング由来の権限が保持され、活動を続けるセッションはセッションの長さいっぱいまで使えます。そのため上記の前提のもとで、そのソースのマッピング由来の権限は、そのソースから最後に読み取った時点から最長でおよそ時限とセッションの長さ 1 つ分を足した時間まで使えることがあり、これは最大で時限の 2 倍です。時限が既定の 12 時間で、「Web セッションの最大時間」が 0 または 12 時間以上であれば、およそ 24 時間です。これより早く、または確実にアカウントのウェブアクセスを止めるには、本システムでそのアカウントを無効化してください。そのアカウントのウェブセッションとトークンの更新はその時点で終わります（下の「ソース側でアカウントを無効化または削除しても」の項を参照）。0 ではない時限を短くすると、読み取り結果を保持できる期間は短くなります。セッションの長さは引き続き、この時限と「Web セッションの最大時間」の短いほうです。「Web セッションの最大時間」のほうが短いままなら、セッションの長さは変わりません。既存のセッションには、更新時に短縮後の上限が適用されます。
- **1.18.0 へのアップグレード前からマッピング由来の権限を持っていたアカウントは、アップグレード後の最初のログインでそれを失うことがあります。** アップグレードは、そうしたアカウントについてアップグレードの時点を最後に読み取った時刻として記録するため、時限はアップグレードから数えられ、アップグレード自体は何も取り消しません（[デプロイとアップグレードの SOP](./upgrade-sop.md#1180-へ上げる場合権限モデルの移行)）。アップグレードから時限を過ぎてから初めてログインし、そのログインでグループを読み取れないアカウントは、そのログインでマッピング由来の権限を失います。該当するのは、ソースがグループを渡さないアカウントです。典型的には、所属グループが多すぎて ID プロバイダーがトークンに入れられないアカウントや、ルールがあるのにグループの属性名またはクレーム名が設定されていないソースです。見分け方：監査ログにそのアカウントの `membership_revalidation_expired` があり、マッピング由来のロールがなくなっています。対処：ソースがグループを渡すようにする（グループの属性名またはクレーム名を設定する、またはトークンに載せるグループを減らす）、ロールを直接割り当てる、または時限を 0 にして、マッピング由来の権限に上限がなくなることを受け入れます。
- **時限を 0 にすると、マッピング由来の権限に上限はなくなります。** ソース側での取り上げは、本人の次回のログインか、ウェブセッションが「Web セッションの最大時間」に従って終わる時点の早いほうで効くようになり、ログイン時にグループを読み取れない場合は、最後に読み取ったのがどれだけ前でも権限が保たれます。「Web セッションの最大時間」も 0 の場合、活動が続いているセッションが自らログイン画面へ戻ることはなく、ソース側の変更は無期限に待つことになります。ソース側で外された人のマッピング由来の権限は、その人の次回のログインまでここに残ります。ソース側での権限の取り上げに依存するデプロイでは、時限を 0 にしないでください。時限を長くするか 0 にすると、前後の値を含む `mapping_revalidation_relaxed` のシステムアラートが発生します。短くする場合と、0 から数値に変える場合は、監査ログに記録されるだけです。
- **時限が届かないところ。** 時限が終わらせるのはウェブセッションと、それに伴う新しい接続を開く能力です。セッションが時限に達した時点ですでに確立しているプロトコルの接続は、これによって切断されません。あるログインでの再計算によって実際にロールが取り上げられた場合、そのアカウントの開いている他のセッションはその時点で終了します。本システムの中で直接ロールを取り下げるのは別の話で、同じようにその時点でそれらのセッションが終了します。
- **高い権限のロールにマッピングされた外部グループのメンバーは、ソース側で決まります。** スーパー管理者ロールまたはシステムセキュリティ管理者ロールへのマッピング（直接、またはそのどちらかを持つユーザーグループを経由するもの）は、誰がそのロールを持つかの判断を、ディレクトリや ID プロバイダーでそのグループを管理する人に委ねることになります。そちらでグループに加えられた人は、次回のログインでそのロールを得ます。本システムの中でスーパー管理者が関与することはありません。そのログインは変わったロールとともに監査ログに記録され、システムアラートは発生しません。本システムの中でこうしたマッピングを作成、変更、有効化、無効化、削除すること、およびこうしたロールを固定することは、スーパー管理者に限られます。
- **ソース側でアカウントを無効化または削除しても、本システムへは同期されません。** そのアカウントはこちらの利用者一覧に残り、ロールは最後に再計算された結果のままです。そのソースを通じた新たなログインは失敗し、ローカルのパスワードによるログインも拒否されて監査ログに記録されます。既存のブラウザーセッションでは、セッションが期限を迎える（マッピング由来の権限を持つアカウントでは、時限が 0 でない限り、セッション開始から最長で時限まで）か、本システムでアカウントを無効化または更新トークンを失効させるまで、そのロールを使用してアクセストークンを更新できます。
- **入れ子のグループが展開されるかどうかは、ソース次第です。** 本システムはログインの時点で得たグループの情報を用い、グループの連なりを上へたどるための問い合わせをソースへ改めて発することはありません。ディレクトリのグループ所属の属性は、通常そのアカウントが直接所属しているグループだけを返すため、上位のグループを通じて得ている所属は見えません。一方、ID プロバイダーのグループのクレームは、入れ子をすでに展開したものである場合があります。ルールは、ソースが実際に返す内容に合わせて記述してください。
- **ノードに限定され、外部グループからも付与されているロール。** ノードに限定したロールを、管理者による割り当てと外部グループのマッピングの両方でアカウントが持っている場合、「ロールと範囲」タブの「管理者が割り当てたロール」で削除すると、「マッピング由来のロール」にあるそのロールの行に、外部グループからも付与されていること、ここで削除するとシステム全体に適用されるロールに変わることが表示されます。この通知は確認を求めず、保存も止めません。保存すると、管理者による割り当てとそのノードの限定はなくなり、マッピングが引き続き付与するロールがシステム全体に適用されます。

## スーパー管理者にはローカルアカウントを使います

**スーパー管理者ロールはローカルアカウントに直接割り当て、ディレクトリや ID プロバイダーを通じてログインするアカウントには渡さないでください。** ID ソースを管理できる人は、ソースの設定を変えて、変更後に向けた先のディレクトリや ID プロバイダーが、そのソースを通じてログインする誰であっても通すようにできます。スーパー管理者も例外ではありません。製品はこの変更を止めません。ソースの設定の作成、変更（有効化、無効化、シークレットの差し替えを含む）、削除は、そのたびに同じトランザクションで監査ログに記録され、`identity_source_changed` のシステムアラートが発生します。アラートには変更された項目と、現在そのソースを通じてログインできるスーパー管理者の人数（ユーザーグループ経由でロールを持つ人を含む）が載ります。bind パスワードと client secret は「変更あり」とだけ示され、値は載りません。これは事後の検知です。

ソースが乗っ取られても、ローカルのスーパー管理者はログインでき、ソースの設定を元に戻せます。ソースの乗っ取りでシステムが締め出されないのは、このためです。製品は、最後のローカルのスーパー管理者（有効で、ローカルのパスワードでログインし、外部のソースに管理されておらず、スーパー管理者ロールが直接割り当てられているアカウント。ユーザーグループやグループマッピングを通じてだけロールを持つアカウントは数えません）を、無効化、削除、ロールの削除、外部ログインのみへの切り替えのいずれによっても失わせません。ただし、1 人もいないデプロイのために作ることはしません。少なくとも 1 人いることを確認し、その認証情報を、必要になる人が手の届くところに保管してください。

## システムセキュリティアラートと通知チャネル

製品は、自身のセキュリティに関わる変更について、変更と同じトランザクションでシステムセキュリティアラートを発生させます。たとえば、ID ソースの変更、自分自身の権限の変更と他の人への管理系のロールの付与、システムセキュリティ管理者のアカウントに対する操作、資産のアドレスの変更や通信の検証の緩和、手で設定したシークレット、グループマッピング再検証の時限の延長、通知チャネルの変更です。これらはアラートの画面に独自のソース種別で表示され、それぞれに宛先ごとの配信状態が付き、対応する操作ログが記録されている場合はそれも付きます。

- **削除も無効化もできません。** アラートの記録が消えるのは、アラートの保存期間に従う場合だけです。アラートの画面のアラート種別の一覧には、すべての種別が既定と現在の重要度とともに表示されます。種別について変えられるのは重要度だけで、システムアラートの重要度の権限（`systemalert:manage`）を持つ人が変更でき、変更はそのたびに同じトランザクションで監査ログに記録されます。画面にも API にも、種別を削除または無効化する方法はありません。
- **重要度が決めるのは順序と表示であり、発生するかどうか、送られるかどうかではありません。** システムセキュリティアラートは発生した時点で、有効なすべての通知チャネルについて 1 件ずつ配信の列に入ります。チャネルのプッシュのしきい値は関係しません。しきい値が絞り込むのは他のアラートだけです。低に下げた種別も発生し、送られます。ただし対応は後回しになるかもしれません。有効なチャネルが 1 つもない場合は配信の列に入らず、後から送られることもありません。syslog の転送を設定していれば、転送は通常どおり行われます。
- **配信は少なくとも 1 回、最長 72 時間です。** 配信の列はデータベースに保存されるため、再起動で失われません。失敗した配信は、1 秒から最長 10 分まで間隔を広げながら再試行されます。列に入ってから 72 時間たっても成功しない場合は放棄として記録されます。アラートの詳細にそれが表示され、サーバーのログにも記録されますが、手動で再送する方法はありません。受信側は同じアラートを複数回受け取ることがあるため、`delivery_id` で重複を除いてください。これはアラートが列に入る時点で配信ごとに割り当てられるランダムな識別子で、再試行でも変わらず、リストア後に再び発行されることもないため、受信側の既読の識別子の記録はリストア後もそのまま使えます。有効なチャネルの保存済みのアドレスや secret が復号できなくなっていても、アラートを生成した操作は止まりません。アラートは記録され、他のチャネルには送られ、そのチャネルへの配信はアラートの詳細とサーバーのログで試行回数 0 のまま直ちに放棄として記録されます。各配信には、アラートが列に入った時点のチャネルのアドレスと secret が使われます。その後にチャネルを変更または削除しても、すでに列に入ったアラートの送り先は変わりません。
- **通知チャネルには専用の権限があり、変更はすべて新旧両方の宛先に届きます。** チャネルの管理（テスト送信を含む）には、通知チャネルの権限（`notification_channel:manage`）が必要です。システムセキュリティ管理者のロールテンプレートにはこの権限が含まれ、ID 管理者のテンプレートには含まれません。チャネルの追加、変更、無効化、有効化、削除は、そのたびに同じトランザクションで監査ログに記録され、`notification_channel_changed` のアラートが発生します。このアラートは他の有効なチャネルに加えて、そのチャネル自身の変更前と変更後の宛先にも送られます。別のアドレスに変えたチャネル、無効化したチャネル、削除したチャネルからも、元の宛先へ 1 件の通知が送られます。チャネルは同じトランザクションで削除され、通知はその後に配信の列から送られます。
- **制限：チャネルを管理する人自身の操作に関するアラートは、その人が変えられる宛先へ送られます。** 通知チャネルの権限を持つ人は、アラートの配信先を変えてから、アラートが発生する操作を行うことができます。製品はこれを止めません。製品が提供するのは、チャネルの変更のたびに新旧両方の宛先へ届く通知と、チャネルの変更とその操作自体の監査記録です。この権限を誰に持たせるかは、この点を踏まえて決めてください。

## 証跡の保持、録画の削除、およびそれらを守る設定

この節では、証跡の保持と、それを消したり隠したりしうる操作について、製品が何を行うかを述べます。

- **4 つのデータ保持日数には下限があります。** 操作ログ、コマンドストリーム、アラート記録、録画の保持日数は、0（永久に保持）または 7〜3650 の数値だけを受け付けます。1〜6 を保存しようとすると拒否され、同じバッチの他の項目も反映されません。チェックポイントの保持日数には独自の下限はなく、「それが証明するデータより短くしてはならない」という規則に従います。初回起動時に環境変数 `RECORDING_RETENTION_DAYS` に 1〜6 を入れても無視され、出荷時の 90 日が使われます。データベースへ直接書き込まれた 1〜6 は、最後の有効値として読み戻され、有効値がなければ出荷時の既定値が使われます。
- **保持日数を短くすることは、通知の対象であって、阻止はされません。** 4 つのデータ保持日数のいずれかを短くすると（0 の永久保持から数値への変更を含む）、変更と同じトランザクションで監査ログに書き込まれ、`retention_shortened` システムアラートが発生します。長くする場合や 0 にする場合は監査のみです。チェックポイントの保持日数の変更は監査のみで、アラートは発生しません。
- **録画の失敗時のブロックは無効にできます。** ポリシー `recording_failclose_enabled` が有効なあいだ、録画ディレクトリに書き込めない状態では、スーパー管理者以外には接続が発行されません。既定は無効です。有効から無効へ変えると監査に書き込まれ、`recording_failclose_disabled` システムアラートが発生します。無効から有効への変更は監査のみです。無効にしている場合、録画ディレクトリに書き込めなくても接続は成立しますが、失敗は引き続き検知・報告されます。事前チェックとそのアラートはこの設定に左右されず、録画に失敗したセッションは録画失敗として印が付けられ、監査に記録されます。
- **全体の既定のアクセス段階を下げる**と、同じトランザクションで監査に書き込まれ、`access_policy_relaxed` システムアラートが発生します。アラートには、既定に従っていて実効段階が下がる資産の数が示されます。上げる場合や変更しない場合はアラートが発生しません。
- **syslog 転送の停止、オフサイト保管の停止、およびそれらやキートポロジーの向け先の変更**は、同じトランザクションで監査に書き込まれ、システムアラート（`offsite_or_syslog_changed` または `key_topology_changed`）が発生します。syslog では、停止、または保存済みの値と異なるホスト・ポート・プロトコルで有効として保存すること（別の宛先で無効から有効に変える場合を含む）を指します。オフサイト保管では、停止、または別の保存先への切り替え（確認の手順を経る場合も、現在の保存先へまだ何もアップロードしていないときに直接切り替える場合も含みます）を指します。キートポロジーでは、前後の値が異なる保存を指します。syslog の TLS CA だけの変更や、同じオフサイト保存先の更新は監査のみです。トポロジーのアラートにはアドレスやその他の値は含まれません。変更前後の値は、同じトランザクションで書かれた監査エントリで確認してください。両者には同じ相関識別子が付いています。監査エントリまたはアラートを書き込めないときは変更が反映されず、転送機能の再読み込みもコミット後に行われます。例外が 1 つあり、[特権認証情報のローテーション](./privileged-credential-rotation.md)の鍵の再ラップの項に記載しています。
- **録画の削除は API だけで、製品の画面には操作がありません。** `DELETE /api/v1/sessions/:id/recording` には録画削除の権限（`recording:delete`）が必要です。これは設定グループのグローバルな権限で、スーパー管理者ロールが持ち、カスタムロールにも含めることができます。製品は 1 つのトランザクションで監査エントリを書き込み、`recording_deleted` システムアラートを発生させ、セッションの録画を消去します。ローカルファイルの削除はコミット後に行います。監査エントリまたはアラートを書き込めない場合は、何も削除されません。この監査エントリを止められるポリシー設定やロールは製品内にありません。ホスト側については述べていません（「製品のロールが届かないところ：ホスト」を参照）。エントリとアラートは保持設定によってのみ消えます。そのセッションに発行済みの録画再生トークンはただちに無効になります。
  - **コミット後にローカルファイルの削除に失敗した場合**、セッションはすでにそのファイルを指しておらず、失敗の記録が監査ログに別途書き込まれ、ファイルはディスク上に孤児として残ります。録画の保持による消去が、こうしたファイルを削除するとは限りません。録画の保持日数が正の数のあいだ、消去処理はファイルの更新日時にもとづいて削除を試みます。削除に失敗した原因が残っていれば、消去処理も同じように失敗し、その回の消去処理はそのファイルで中断します。0（永久に保持）のときは自動で消えるものがありません。原因を取り除くか、手作業でファイルを削除してください。
  - **オフサイト保管へアップロード済みの複製は、この操作では削除されません。**
- **アラートが保証するのは作成と記録であって、誰かが受け取ることではありません。** アラートは変更と同じトランザクションで書き込まれます。届くかどうかは通知チャネルに左右され、規則は前の節のとおりです。有効なチャネルがなければキューに入らず、失敗し続ける配信は 72 時間後に打ち切られます。これらのアラートを、誰かに伝わった証拠として扱わないでください。
- **制限：システムセキュリティ管理者ロール、およびこれらの権限を持つ人は、製品自体では制限されません。** これらの権限は、キートポロジー、オフサイト保管と syslog 転送の停止、録画の削除、録画失敗時のブロックの無効化、通知チャネルの管理に及びます。製品が追加で提供するのは、保持の下限、録画削除の前に書く監査エントリ、そしてアラートです。適任でない保持者や、資産・認可・ID の管理を兼ねている人（製品はこの組み合わせを警告しますが、阻止はしません）は止められません。そうした人は先に操作を行い、保持の下限が守らない範囲の痕跡を消せます。これらの権限はセキュリティまたは監査の担当者に付与し、保持者と兼務の組み合わせを確認してください。
- **制限：保持者自身の操作で発生するアラートは、その保持者が変更できるチャネルに送られます。** 通知チャネルを管理するのも同じ人たちなので、チャネルを変えてから操作できます。製品が提供するのは、チャネルの変更ごとに旧・新の宛先へ通知すること、およびチャネル変更と操作の監査エントリです。この順序自体は阻止しません。

## パスワード変更の経路に必要な外向き接続

パスワード変更は、バックエンドのコンテナが対象ホストへ自ら接続して行います。フロントエンドの nginx も、利用者のブラウザーも経由しません。Linux ホストへは対象の SSH ポートを使います。Windows ホストへは資産に設定されたパスワード変更の経路に従い、対象の WinRM ポート（http 5985 または https 5986、変更可）か SSH ポート（既定 22、変更可）を使います。WinRM のトランスポート層は **proxy 系の環境変数を読まず、HTTP のリダイレクトにも従わず**、HTTP/1.1 のみを使用します。バックエンドと対象のあいだにプロキシやリダイレクトが必須である場合、そのホストの WinRM によるパスワード変更は接続できません。https の証明書検証モードで `system` を選んだ場合、信頼の起点はバックエンドコンテナのオペレーティングシステムの証明書ストアです。内部 CA が発行したリスナー証明書には `ca` モードを使い、その CA を資産にアップロードしてください。対象ホスト側の前提条件は[デプロイとアップグレードの SOP](./upgrade-sop.md) §2.5 の Windows ローカルアカウントのパスワード変更の項を参照してください。

## コンポーネントの基盤システムの状態（脆弱性管理の計画に影響します）

**RDP／VNC に用いる guacd コンテナは、その基盤システムのセキュリティ更新が終了しています。**

guacd サービスは Apache Guacamole の公式イメージ `guacamole/guacd:1.6.0` を手を加えずにそのまま使っており（compose ファイルがバージョンと digest で固定しています）、その基盤は Alpine 3.18 で、公式のサポート期間を過ぎています。**これは本プロジェクトが選んだ結果ではありません。** 公式の `latest` と `1.6.0` は同一の `alpine-minirootfs-3.18.12` であり、上流はまだこれより新しい基盤を提供していません。

デプロイの計画に対して、実質的な影響が 2 点あります。

- **このコンテナのオペレーティングシステム層には、上流が基盤を更新するまでセキュリティ修正が届きません。**
- **このイメージに対する脆弱性スキャンの結果は、セキュリティ上の根拠として使えません。** スキャンすると「検出ゼロ」という結果が得られますが、正しい読み方は「データがない」です。サポート期間を過ぎたシステムには脆弱性データベースの更新がもう来ませんし、guacd 本体はコンパイル済みのバイナリでパッケージ一覧に載らないため、スキャナーからは見えません。

既存の構造的な緩和策は次のとおりです（既定のデプロイでそのまま有効であり、別途設定する必要はありません）。

- guacd は**どのポートも外部に公開しません**。compose の内部ネットワークにのみ存在し、そこへ接続できるのは本システムのバックエンドサービスだけです。
- 録画ディレクトリが、唯一の共有マウントポイントです。**オフサイト保管を有効にしてもこの点は変わりません。** guacd は引き続きローカルの録画ディレクトリへ直接書き込み、アップロードは**セッション終了後に**バックエンドが別途行います。guacd はオブジェクトストレージに触れず、ストレージの認証情報も一切持ちません。そのため、**異常終了の経路で残った録画ファイルはオフサイトへ行きません。** セッションが異常終了して保存の確認が完了しなかったファイルについては、システムはアップロードの追跡を作成せず、既存のローカル整理の仕組みが処理します。オフサイト保管の対象範囲は「正常に終了し、保存が確認された」録画です。取得時に展開される一時領域は**バックエンドコンテナのローカルキャッシュ**（存続期間と総量の上限があります）であり、こちらも guacd とは共有しません。
- このコンテナは**最小権限で動作します**。これらは配布される compose 定義が課すものであり、イメージの性質ではありません。Linux のケーパビリティはすべて破棄し、setuid ファイルによる権限昇格は拒否し、ルートファイルシステムは読み取り専用です。読み取り専用のもとで残す書き込み可能な領域はメモリ上の 2 か所だけで、いずれもこのワークロードに実際に必要だと確認できたものです。RDP のドライブリダイレクトが接続ごとに使う一時ディレクトリと、RDP ライブラリが起動時に書き込みを要求するホームディレクトリです。一時ディレクトリにはその時点で利用者が転送中のファイルが置かれるため、出荷時には容量の上限を設けていません。上限が必要な場合は、配布される `docker-compose.yml` の当該 tmpfs の行を直接編集してください（例：`/tmp:size=512m`）。compose のオーバーライドファイルでは指定できません。compose は tmpfs の記述を置き換えではなく追記として扱うため、同じマウントポイントを二重に宣言すると拒否されます。RDP ライブラリが既知のホストを記録する信頼ストアはこのメモリ領域の一方に置かれるため、コンテナを再起動するたびに空になります。対象ホストの証明書をどう扱うかは資産ごとの証明書検証の設定で決まり、この信頼ストアが再起動をまたいで残ることには依存していません。読み取り専用のルートと、noexec でマウントされた 2 か所のメモリ領域により、プロトコル経由で侵入されても、コンテナの設定を書き換えることも、一時領域から何かを実行することもできません。共有している録画ディレクトリは書き込みも実行も可能なままであり、それは録画を書き出すために必要なものです。
- **このイメージは、ご自身でビルドまたは選択したものに差し替えられます。** compose ファイルの guacd の `image:` 行を変更してください。本システムがこのコンテナに求めるのは 3 点だけです。4822 番ポートで guacd プロトコルを提供すること、compose 定義がマウントする録画ディレクトリへ書き込めること、そして compose 定義が課すヘルスチェックが実行する `sh` と `nc` をイメージ内に備えていることです。上に挙げた設定はコンテナの実行時の属性であってイメージの性質ではないため、どのイメージに差し替えても最小権限の設定はそのまま有効です。

**緩和はリスクがないことを意味しません。** バックエンドが侵害された場合、あるいは管理下のリモートデスクトップホストがプロトコルを通じて逆に攻撃してきた場合、この経路は依然として存在します。**すべてのコンポーネントの基盤システムがサポート期間内であることを脆弱性管理ポリシーが要求する場合は、デプロイの前にこのイメージを例外評価の対象に入れてください。**

**バックエンドは引き続き root で実行されます。** 配布されるデプロイ設定と起動コードは、次の設定を適用します。

- `cap_drop: [ALL]` ですべての capability を削除した後、`cap_add: [SETUID, SETGID, CHOWN, KILL, IPC_LOCK]` で五つだけを付与します。`SETUID` と `SETGID` は DB CLI 子プロセスを専用ユーザーとグループに切り替え、`CHOWN` は一時 CA ファイルの所有権をそのユーザーに移します。`KILL` はコンテナの PID namespace 内で異なる UID のプロセス（DB CLI 子プロセスを含む）へのシグナル送信を許可し、`IPC_LOCK` はロック対象メモリのリソース上限を超えるメモリロックを許可します。
- `security_opt: [no-new-privileges:true]` は、setuid ファイルやファイル capability を通じた実行時の権限追加を禁止します。
- `ulimits.core` は `soft: 0`、`hard: 0` ともにゼロです。バックエンド自身も `RLIMIT_CORE` をゼロに設定します。
- `PR_SET_DUMPABLE=0` はバックエンドプロセスをダンプ不可にします。`SYS_PTRACE` が付与されていないことと合わせて、コンテナ内の他のプロセスは、その `/proc/<pid>/environ` と `/proc/<pid>/mem` を読み取れません。この capability 制限下の root プロセスも対象です。
- `ulimits.memlock: -1` と `mlockall(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)` は、常駐ページをロックし、他のマッピング済みページも常駐時にロックすることで、それらのページのスワップアウトを防ぎます。

2026-09-12（Asia/Taipei）の測定では、バックエンドに上記のメモリ保護設定を適用し、15 の開発サービス（Air を含む backend、dex、fake-gcs、frontend、guacd、k3s-test、ldap-test、localstack、mssql-test、mysql-test、postgres、rdp-test、ssh-multi-test、ssh-test、vnc-test）、測定用クライアントおよびサービスのバックグラウンド処理が同時に動作し、他の Go テストやエンドツーエンドの smoke テストは実行していない状態で、アクティブな SSH セッションが 0 本のときはバックエンドの VmRSS 68616 kB／VmLck 1369796 kB、ssh-test への同時 SSH セッション 20 本を 120×30 の端末で echo 実行後に 45 秒間開いたままにしたときは VmRSS 76952 kB／VmLck 1370060 kB であり、これらの単一サンプルは参考測定値であってメモリ上限の保証ではありません。

**鍵素材は引き続きバックエンドプロセスのメモリに存在します。** これらの設定が制限するのは、それを読み取れる他のプロセスです。鍵素材を除去するものではなく、バックエンド自身のアクセスも妨げません。ホストを管理する権限やデプロイの権限設定を変更する権限を持つ管理者から鍵素材を保護するものではありません。

**独自の編成でも、これらの設定が必要です。** すべての capability を削除してから `SETUID`、`SETGID`、`CHOWN`、`KILL`、`IPC_LOCK` だけを付与し、上記の権限およびリソース制限も適用してください。Compose でメモリロックに必要な設定は、`IPC_LOCK` を含む `cap_add` と `ulimits.memlock: -1` です。他の編成ツールでも同等の capability とリソース制限が必要です。起動時の制御を適用できない場合、バックエンドは終了します。メモリロックの失敗時には `mlockall failed (check cap_add IPC_LOCK and ulimits.memlock)` と表示されます。このエラーを調べる際は、これらの設定名を確認してください。

capability を変更した後は backend コンテナを再作成してください。再起動だけでは新しい capability 集合は適用されません。`custodexa.sh upgrade` は新しいリリースを起動する際にコンテナを再作成します。パッケージのデプロイフォルダーで手動で再作成する場合は `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend` を、その他の Compose デプロイでは `docker compose up -d --force-recreate backend` を実行します。`KILL` がない場合、backend は DB CLI 子プロセスを終了できないことがあります。ローカル端末の切断処理は子プロセスの回収を最大 1 秒待ち、終了・待機の失敗やタイムアウトをログに記録して、接続の後処理を続行します。単一のバックグラウンド待機が、後から終了する子プロセスを回収します。capability がない場合、子プロセスが動作し続ける可能性は残ります。

## 許可送信元範囲がデプロイに与える影響

**許可送信元範囲（`allowed_cidrs`）は、あるアカウントがどの送信元アドレスからシステムを利用できるかを制限します。** 一覧が空であれば送信元を制限せず、それが既定値です。制限するのは**利用できる送信元**であって、パスワードポリシー、アカウントロック、多要素認証の代わりになるものではありません。

### まず「送信元アドレス」の判定方法を決めます

本システムには「リクエストがどこから来たか」の取り方が 1 つしかなく、すべての経路がそれを共有します。

- **`TRUSTED_PROXIES` が未設定のときは、socket peer のみを信頼します。** すなわち TCP 接続の相手側アドレスです。`X-Forwarded-For`、`X-Real-IP`、`Forwarded` などの転送ヘッダーは**一切信頼しません**。
- `TRUSTED_PROXIES` を設定して初めて、宣言された信頼プロキシの連鎖に従って転送ヘッダーが解釈されます。**設定値が不正な場合、バックエンドは起動を拒否します。** 既定値に戻って動き続けることはありません。

既定でヘッダーを信頼しないのは意図的なものです。それらのヘッダーは呼び出し側が制御します。これを信頼すると、リクエストを送れる者は誰でも自分の監査記録に任意のアドレスを指定でき、毎回ヘッダーを変えることでアドレスを鍵とする制限を回避することもできます。

**アプリケーションをリバースプロキシ、ロードバランサー、CDN の背後に置きながら `TRUSTED_PROXIES` を設定していない場合、システムから見える送信元はすべてそのプロキシのアドレスになります。** 結果は 3 つあります。

- 許可送信元範囲はプロキシのアドレスを判定します。利用者の範囲を書けば**全員**が拒否され、プロキシのアドレスを書けば、そのプロキシを経由するすべての人を許可することと同じになります。
- 監査調査ビューの送信元アドレスの軸、監査記録と接続記録の送信元アドレス列は、すべてプロキシのアドレスとして記録されます。
- 新しい送信元アドレスのアラートは、プロキシのアドレスが変わったときにしか鳴りません。

**既定のデプロイではスタックが自前のプロキシを持ちます。ソースツリーの `bash scripts/quickstart.sh` とパッケージの `custodexa.sh install` は、そのプロキシの Docker サブネットを `TRUSTED_PROXIES` に記入します。** 自前の ingress を運用する場合、この一覧はご自身で書くものになります。その ingress のアドレス、または接続元となる範囲をここに設定してください。

**実際の送信元で判定し、それを記録として残すには、まず `TRUSTED_PROXIES` でプロキシの連鎖を明示的に列挙する必要があります。** この判断は、送信元の限定を有効にする**前に**行ってください。一覧を先に設定してからプロキシの設定を変えると、すでに効いている一覧が一夜にして別のアドレス群を指すことになります。

### どの入口が拒否され、拒否はどう見えるか

一覧が空でなく、送信元がそこに含まれない場合、次の操作はすべて拒否されます。

- ログイン（多要素認証の完了、OIDC の交換を含む）と、強制登録／強制パスワード変更のための限定チケットの発行および使用。
- ウェブセッションの更新（refresh）。
- 接続の発行、およびテキスト端末とグラフィカルの 2 つの引き換え入口。**引き換えの時点でそれぞれが一覧を読み直して改めて判定します**。発行時の結論をそのまま使うことはありません。
- 3 つの管理者向けエンドポイント（**他人のパスワードのリセット**、**他人のアカウントロックの解除**、**他人の多要素認証の解除**）は、**操作者本人**の一覧で判定します。

拒否の応答は**「この送信元は許可されていません」としか述べず、アドレスを表示せず、一覧も示しません。** アドレスと、判定に用いた一覧のスナップショットは監査にのみ書き込まれます。接続系の拒否には機械可読フィールド `reason=source_not_allowed` が付き、画面はこれに基づいて「現在の送信元は許可範囲にありません」と表示し、申請ダイアログは開きません。

**一覧を読み取れない場合や内容が壊れている場合は、常に拒否します**（空の一覧として通すことはしません）。外部への応答は「送信元が合わない」場合と完全に同じです。ここで応答を分けることは、呼び出し側に「このアカウントのポリシーは壊れている」と教えることになるためです。この状況では管理画面の操作ログページにある「障害イベント」タブに `source_policy` イベントが 1 件開き、原因は「読み取れない」と「文字列が壊れている」の 2 種類に分かれます。データが修復されれば、システムが自動で終結させます。

### 一覧を絞り込む前に：拒否されることになる人へ先に知らせます

**一覧の絞り込みは、すでに接続中の人を切断しません。** 具体的には次のとおりです。

- 発行済みのウェブアクセストークンは、その寿命のあいだ引き続き使えます。**残る窓の上限は 15 分です。** その後の `refresh` による更新はすべて拒否され、利用者はログイン画面へ戻され、再度ログインする時点で送信元の判定に阻まれます。
- **すでに確立されたプロトコル接続は、一覧の絞り込みによって能動的に切断されることはありません。** 通常どおり、それ自体が終わるまで続きます。阻まれるのは次回の接続からです。
- 「正式なセッションまたは限定チケットを発行する」「認証状態を書き込む」といった操作は、いずれも動作が有効になる前に判定します。したがって絞り込みの後に、一覧の外のアドレスから新しいセッションが生まれることはありません。

そのため、一覧を絞り込む正しいやり方は**先に知らせること**です。影響を受ける人に、新しく利用できる送信元、適用の時点、そして拒否されたときの連絡先を伝えてください。知らせずに絞り込むと、症状は「更新に失敗してログイン画面に戻される」という形で現れ、利用者にはそれが制限によるものか障害なのか区別できません。

### 管理者が自分を締め出してしまったときの復旧

**システムはこの保存を阻止しません。** 管理者が、まだ切り替えていない範囲を意図的に設定することもあるためです。画面は保存の前にその場で警告を表示するだけで、送信は止めません。

実際に締め出された場合は、次の順に対応します。

1. **他の管理者がいる場合**：その人に管理画面で一覧を戻してもらいます。この経路はフィールド単位の監査差分（一覧の変更前と変更後）を残すため、第一の選択肢です。
2. **利用できる他の管理者がいない場合**：既存のオフラインリセットの経路を使い、データベースへ直接接続して当該アカウントの一覧を空文字列にします。逐語的な手順と SQL は[クイックスタート — admin のパスワード紛失、脆弱な認証情報のスキャンによる起動拒否、管理者が送信元制限で締め出された場合（オフラインでのリセット）](../QUICKSTART.md#admin-のパスワード紛失脆弱な認証情報のスキャンによる起動拒否管理者が送信元制限で締め出された場合オフラインでのリセット)を参照してください。この対応は**一覧を空にするだけでよく、パスワードに触れる必要はありません**。

オフラインリセットは**製品の監査を通りません**。アプリケーションを迂回してデータベースへ直接書き込むため、`audit_logs` に対応する記録は残りません。**その操作の記録は、デプロイ側自身の変更管理が担います**（誰が、いつ、どの承認に基づいてデータベースを操作したか）。製品側から事後に見えるのは、復旧後のログインの監査記録（送信元アドレスを含みます）と、画面に戻って一覧を設定し直したときに残るフィールド単位の差分です。空にした後にサービスを再起動する必要はありません。**ただし空のままで止めないでください。** それはどのアドレスからでも入れることを意味します。

### 新しい送信元アドレスのアラートが運用上もつ意味

あるアカウントが、ある送信元アドレスから**初めて**プロトコル接続を確立したとき、システムは `new_source_ip` のアラートを 1 件生成し、既存の通知チャネルに沿って送出します。同じ（アカウント、アドレス）の組み合わせでは 1 回しか鳴りません。

読み取る際は次の 3 点に注意してください。

- **これは「以前ここから接続したことがない」という意味であり、「今回拒否された」という意味ではありません。** 許可するかどうかは許可送信元範囲が決めるもので、両者は互いに影響しません。一覧が空であれば新しいアドレスはすべて鳴りますし、一覧に阻まれた接続はそもそも接続の確立まで到達しません。
- **ログインしただけで接続しなければ鳴りません。** そのアドレスは基準に取り込まれるだけです。先にログインしてから接続する典型的な流れでは、接続の時点で 1 回鳴ります。
- **アップグレードの時点ですでに見えているアドレスは鳴りません。** アップグレード時に、システムは既存の接続の全履歴とログイン成功の記録から基準を 1 件分埋め戻します。新規インストールには埋め戻す履歴がないため、最初の接続はそれぞれ 1 回ずつ鳴ります。これは想定どおりの挙動です。

利用者のアドレスが変動する場合（家庭用ブロードバンド、モバイル回線、VPN の出口の切り替わりなど）、この種のアラートはかなり頻繁になります。「一度見ておく価値がある」という信号として扱うのが適切で、遮断の条件には向きません。遮断には許可送信元範囲を使ってください。

### バックアップとリストアへの影響

新しい保存先はありません。許可送信元範囲も送信元アドレスの基準も PostgreSQL の中にあり、データベースとともにバックアップされます。既存の[バックアップとリストア](./backup-and-restore.md)の手順は変わらず、追加の手順も必要ありません。

## SSH のホスト鍵が記録と一致しないとき

プラットフォームが初めて SSH で資産に接続するとき、接続先が提示したホスト鍵を記録します。1.18.0 以降、その後の接続で異なる鍵が提示された場合の扱いは、立ち会う人がいるかどうかで変わります。ユーザーが開くターミナル、ファイル転送、接続テストでは、ホスト鍵の確認が SSH 認証への続行を許可し、認証とチャネルの確立が成功すればユーザーにはターミナルまたはファイルマネージャーで警告が表示されます。パスワード変更と認証情報のローテーションは誰も立ち会わないため停止し、ログイン認証情報も新しい秘密も送らず、ジョブは「ホスト鍵の不一致」で終了します。自動化エージェントが開くターミナルも同様に拒否され、ログイン認証情報は送られません。どちらの場合も、認証を始める前に、記録されているフィンガープリント、今回提示されたフィンガープリント、資産、ユーザー、接続、確認の判定（続行を許可、または拒否）を含む監査記録を書き込みます。あるフィンガープリントが初めて現れたときには、システムセキュリティアラート「ホスト鍵が記録と一致しません」も作成します。誰かに届くかどうかは、通知チャネルの設定とアラートに表示される配信結果によります。実際に認証を試みた後は、同じ関連識別子でもう 1 件の監査記録を追加し、ログイン認証情報を送信したことと認証の成否を記録します。

記録はスーパー管理者が対応するまで元のフィンガープリントのままです。資産のホスト鍵欄には、未確認のフィンガープリントを最終出現時刻の新しい順に最大 5 件表示します。不一致の全履歴ではなく、全履歴は監査ログにあります。スーパー管理者はそのうちの 1 つを新しい記録として採用できます。リセットも引き続き使えますが、リセット後の最初の接続ではそのとき接続先が提示した鍵が新しい記録になるため、確認済みのフィンガープリントを採用すればその空白期間は生じません。フィンガープリントの採用とリセットはそれぞれ記録され、中レベルのシステムセキュリティアラートを作成するため、記録が変更された時点そのものも記録に残ります。

### 既知の制限：未確認のホストに対して認証を続行する

続行の許可は接続の成功を意味しません。プラットフォームが、身元を確認できないホストに対して保管中の認証情報で認証を進めるということです。何が露出するかは認証方式によります。なりすまし先にパスワード認証を試みると、相手にパスワードが渡る可能性があります。公開鍵認証では公開鍵と SSH セッションに結び付いた署名を送信し、秘密鍵自体は送信しません。接続を続けると、セッションとその後に送信するデータは未確認のホストに渡ります。監査記録とアラートで事後に把握し調査することはできますが、認証の実行を止めることはできず、この場合についてプラットフォームは保護を提供しません。

これはユーザーが開くターミナル、ファイル転送、接続テストに当てはまります。パスワード変更と認証情報のローテーション（SSH 経由の Windows アカウントのローテーションを含む）、および自動化エージェントが開くターミナルは不一致のときに停止し、認証情報を接続先に送りません。これは上記の接続を保護するものではありません。

アラートを読むときの注意点：

- **新しいフィンガープリントごとに 1 回。**ある資産で、未確認のフィンガープリントが初めて現れたときにアラートを作成します。同じフィンガープリントでのその後の接続は毎回監査され、資産のホスト鍵欄で回数が加算されますが、アラートは再作成されません。そのフィンガープリントがそれまで拒否された接続（停止したパスワード変更またはローテーション、または自動化エージェントが開いたターミナル）でしか現れていなかった場合は、その後に初めて続行を許可されたユーザーのターミナル、ファイル転送、接続テストでもう 1 件作成します。それが相手に初めて認証を試みる時点だからです。別のフィンガープリントが現れると、新しいアラートを作成します。
- **アラートには確認の判定が記載されます。**「許可」はこのホストへの認証続行を許可したこと、「拒否」は認証の前に接続が止められ、認証情報が送られなかったことを示します。パスワード変更またはローテーションが停止した場合と、自動化エージェントが開いたターミナルが拒否された場合があります。
- **監査記録を書き込めないとき**（データベースが使えない場合など）は、認証の前に接続が中止され、ユーザーには「ホスト鍵の確認に失敗しました」と表示されます。
- **エージェントのセッションはバックグラウンド作業です。**自動化エージェントがエージェントチャネル経由で開くターミナルには立ち会う人がいないため、不一致時はパスワード変更と同様に拒否されます。分類はサーバー側が接続チケットから判定し、クライアントの申告は見ません。
- **VNC 接続のファイル転送**はデスクトップゲートウェイのコンポーネントが自ら接続を開きます。そのアドレスにホスト鍵の記録がある場合、プラットフォームは記録をコンポーネントに渡し、不一致時はコンポーネントがファイル転送チャネルを拒否します。この拒否はコンポーネント自身のログにしか現れず、プラットフォームのアラートや監査記録にはなりません。記録がない場合、コンポーネントは従来どおりホストを検証せずに接続します。このチャネルは初回信頼を行わず、資産の確認待ち一覧にフィンガープリントを追加することもありません。データベース、Kubernetes、RDP の接続は SSH のホスト鍵を使いません。

### アラートが出たとき

1. ホストの管理者に、再インストールやホスト鍵の再生成があったかを確認し、資産のホスト鍵欄に表示されたフィンガープリントとホスト上の実際のフィンガープリントを照合します。
2. 一致した場合は、スーパー管理者に資産のホスト鍵欄でそのフィンガープリントを採用してもらいます。警告は表示されなくなり、パスワード変更、ローテーション、自動化エージェントが開くターミナルも再び接続できます。事前にフィンガープリントを確認できない場合に限り、リセットを使ってください。
3. 一致しない場合、または誰も確認できない場合は、最初のアラート以降にその資産で使われたパスワードをすべて漏えいしたものとして扱い、本物のホストで変更してください。公開鍵認証では秘密鍵は送信されませんが、未確認のホストとやり取りしたセッション内容は相手に見られたものとして扱ってください。誰がいつ接続したかは監査記録で確認できます。

### アップグレード時

ホスト鍵の不一致で拒否されていた資産は、アップグレード後にユーザーが開くターミナル、ファイル転送、接続テストで認証への続行が許可されるようになり、それぞれ最初の接続時にアラートを 1 件作成します。これらの資産のパスワード変更、ローテーション、自動化エージェントが開くターミナルは、スーパー管理者がフィンガープリントを採用するかリセットするまで拒否されたままです。アップグレード前に、現在この理由で接続できない資産を確認し、確認またはリセットを済ませてください。

## アップグレードへの影響

アップグレードは停止して行う必要があり、ローリングアップデートは行えません。手順は[デプロイとアップグレードの SOP](./upgrade-sop.md) を参照してください。パッケージのデプロイでは管理スクリプトがアップグレードを実行し、同じく停止してからバックアップを取る順序です。

本バージョンから、**新しいインスタンスが起動しない原因が 1 つ増えます。旧インスタンスがまだ実行中である、またはそのデータベースセッションが残留している場合です。** 残留が起きるのは、ロックを保持するホストがダウンした場合や、ネットワーク分断による TCP のハーフオープンの場合だけです。postgres はオペレーティングシステムの TCP keepalive に従ってそのセッションを回収します（postgres コンテナでは別途設定していないため、Linux の既定でおよそ 2 時間です）。起動ログにはロック保持者のフィンガープリントと確認コードが出力されます。復旧手順は[デプロイとアップグレードの SOP §2.6b](./upgrade-sop.md#26b-単一インスタンスロックが別のデータベースセッションに保持されていてバックエンドが停止した場合)を参照してください。**復旧にデータベースへの操作は一切必要ありません。**

排他の保証は、ガードを備えたバージョン同士でのみ成立します。ガードのないバージョンから初めて上げるとき、新しいバージョンがロックを取得できたことは、旧バージョンが停止していることを**意味しません**。アップグレード SOP §2.3 の初回アップグレードのチェックが、唯一の証拠となります。

アップグレードの前に、旧バージョンのインスタンスをすべて停止してください。待機系も含みます。旧バージョンと新バージョンが同じデータベースに対して同時に動いている間は、旧バージョンで採用またはリセットされたホスト鍵が新バージョンからは見えないため、進行中の認証情報変更の作業は、そのホストへの信頼が変わったことに気付かない場合があります。これは許容されるリスクであり、システムはこれを防ぎません。鍵が別のものに変わった場合は、フィンガープリントの照合で引き続き検出されます。露出するのは、鍵が変わってから記録済みの鍵に戻るケースです。システムの対応は、新バージョンの起動時に発行されるシステムアラート `concurrent_instance_detected` だけです。検知できるのは単一インスタンスのガードを備えたインスタンスだけで、書き込みが失敗した場合、またはクエリが失敗し、かつ起動が単一インスタンスのガードを確認して通過したものでない場合は、バックエンドのログに 1 行残るだけです。アラートが出ていないことを、ほかのインスタンスが動いていない証拠と読まないでください。手順は[デプロイとアップグレードの SOP](./upgrade-sop.md)を参照してください。

実行中にロックを失った場合（postgres の再起動、セッションの終了、ネットワークの事象）、このインスタンスは**サービスを継続し**、周期ごとに再取得を試みます。そのあいだ管理画面には常設バナーが表示され、メトリクス `custodexa_instance_guard_held` は 0 となり、`audit_logs` には `instance_guard` イベントが残ります。読み方は[デプロイとアップグレードの SOP §3.4](./upgrade-sop.md#34-実行中に単一インスタンスロックを失った場合ログバナー監査イベントの読み方)を参照してください。

## 可用性の計画への影響

単一インスタンスの形態には自動フェイルオーバーがありません。可用性の計画で力を入れるべき点は、復旧までの時間を短くすることです。バックアップと KEK の材料をいつでも使える状態にし、リストアの手順をあらかじめ演習しておいてください。[バックアップとリストア](./backup-and-restore.md)を参照してください。委任型の鍵モードでは、「いつでも使える状態」には次の 2 つも含まれます。当番の担当者が保管先の認証情報を入手できること、そして再起動のたびに人が立ち会えることです。その代償は次節に記します。

さらに短くできるのは、データベースではなく**アプリケーションホスト**を失ったあとにサービスが戻るまでの時間です。データベースを別のサーバーに置き、スタンバイホストを用意しておけば、同じデータベースへ向けてスタンバイを起動することでサービスは戻ります。これは人かスクリプトが実行する手順であり、製品が自分で行うものではありません。その手順に事前に必要なものと、保たれないもの（故障したホストだけが持っていた録画などのファイル）は[アプリケーションホストのスタンバイ切り替え](./standby-takeover.md)を参照してください。データベース自体を失った場合は、これまでどおりバックアップからのリストアで対処します。

**オフサイトの証拠保管が変えるのは「証拠が失われるかどうか」であって、「サービスがどれだけ早く戻るか」ではありません。** 計画にあたっては、次の 2 つを分けて考えてください。

- **これは証拠がさらされる窓を短くするものであり、なくすものではありません。** アップロードはセッションの終了後に初めて行われます。テキストの録画は秒単位で処理待ちに入り、グラフィカルの録画は最低 1 分待ちます（ファイルが変化しなくなるのを待つためです）。ストレージ側に到達できない場合は、回復するまで待ち続けます。**その窓のあいだ、ローカルが唯一の複製です。** この時点で機械が壊れれば、その録画に 2 つめの複製はありません。
- **これは復旧時間の目標を変えません。** 遠隔の複製により、すでにオフサイトへ渡った証拠は機械が壊れた後でも取り戻せますが、システムが再びサービスを提供するには、やはりリストアの手順（データベース、KEK、デプロイ層の設定）を踏む必要があります。**オフサイト保管はバックアップの代わりではありません。** 両方をあわせて計画してください。
- **オフサイトの録画の初回再生には、ダウンロードの待ち時間があります。** ローカルの複製がすでに削除されている録画は、再生時にまずオブジェクトストレージから取得し、展開してハッシュを検証したうえで送出が始まります。待ち時間はファイルの大きさと帯域によって変わります。これは想定できる挙動であり、障害ではありません。発生するのはその録画の初回再生のときだけです（一時キャッシュは存続期間のあいだ再利用できます）。監査の作業に応答時間の要件がある場合は、この待ち時間を計算に入れてください。

## 委任型の鍵モード：このデプロイは無人運転ではありません

**`KEK_PROVIDER=kms`（AWS KMS、GCP Cloud KMS、HashiCorp Vault）では、本バージョンの再起動には必ず人が必要です。** 保管先へ接続するための認証情報は、そのときのアンシール世代のメモリにだけ保持し、シールの時点で消去します。プロセスが終われば、どこからも読み戻せません。したがって**コールドスタートのたびにシール済みの状態で立ち上がり**、管理者がアンシールするまではヘルスチェックとシール関連のエンドポイントしか提供しません。ホストの再起動、コンテナの再作成、スケーリング、夜間のメンテナンス枠、そしてリストア後の初回の起動が、すべてこれに当たります。**プロセスは終了しません。** 認証情報を待っている状態は設計どおりの通常の状態であり、設定の誤りではありません。監視プロセスがコンテナを再起動しても解消しません。

計画上の帰結は 3 つです。

- **再起動のたびに連絡の取れる人が必要です。** 計画外のものも含みます。このモードを選ぶ前に、誰が担当し、時間外はどう呼び出すかを決めてください。`ui` モードはもともとこの性質を持っており、`kms` は本バージョンから同じになります。無人で再起動できるのは `env` だけで、その代償としてマスター鍵がホスト上に平文で置かれます。
- **自動スケーリングと無人の再起動ポリシーは、このモードに合いません。** サービスを提供できないプロセスを起こし直すだけです。
- **監視はシール済みの状態でアラートを出す必要があります。** そうでなければ、午前 3 時の再起動に午前 9 時まで気づきません。シール中でも状態は読めます。`GET /api/v1/seal/status` と `/metrics` のシールの組です。`/metrics` への到達方法と収集の方法は[運用メトリクスの取得](#運用メトリクスの取得metrics)にあります。

**アンシールのページが求めるものと、その確認の境界。** 管理者はアンシールのページでユーザー名とパスワードを入力し、画面に表示された保管先を導入記録と照合したうえで、その事業者の認証情報を改めて入力します。セキュリティの評価には、次の 2 つの境界を入れてください。

- **シール済みのあいだはユーザー名とパスワードだけを確認し、ワンタイムコードは確認しません。** その種はデータ鍵で保護されており、シール中は解けません。これを要求すると「アンシールしないと確認できず、確認しないとアンシールできない」という循環になります。**したがってこの手順は多要素認証ではなく、そのように書いてはいけません。** これを支えているのは、アンシールのエンドポイント自身の送信元ごとのバックオフと時間制限つきのクールダウン、`SEAL_UNSEAL_ALLOWED_CIDRS` に設定した送信元ネットワーク範囲、パスワードの誤りとアカウントの不存在を区別しない応答、試行のたびにバックエンドのログへ残る 1 行、そして有効期間 10 分で、使うたびにそのアカウントが有効な管理者であることを確認し直す認可のコンテキストです。**すでにロックされているアカウントはここでも拒否されます。** 一方、この手順が行わないのは、失敗回数の加算とアカウントのロックです。アカウントロックのポリシーは、アンシールの後にしか存在しない段に属するためです。
- **アカウントはローカルの管理者である必要があります。** ディレクトリや ID プロバイダーから作られたアカウントは、シール中は認証できません。外部認証の経路はアンシールの後に組み立てられるためです。管理者がすべて外部のソース由来であるデプロイは、自分をアンシールできません。受け渡しのチェックリストがすでに求めているとおり、ローカルの管理者アカウントを少なくとも 1 つ残してください。

**保管先の設定がどこにあるか。** アドレス、リージョン、Transit の鍵の名前、ロール識別子はデータベースの行であり、鍵管理ページで設定します。変更のたびに変更前後の値が監査に記録され、設定済みの通知チャネルを通じてセキュリティのアラートが送出されます。チャネルが未設定の場合、記録は監査の行だけです。認証情報はデータベースにも `.env` にもありません。バックアップと切り替えへの帰結はこうなります。設定はデータベースのバックアップとともに移りますが、認証情報は移りません。[バックアップとリストア §4.3](./backup-and-restore.md#43-モード-ckek_providerkms鍵の保管先への委任)と[アプリケーションホストのスタンバイ切り替え §2.2](./standby-takeover.md)を参照してください。

## データ鍵のメモリ保持時間：この設定が可用性と引き換えにするもの

資産アカウントのパスワード、記録したクリップボードの内容、ディレクトリのバインド認証情報といった保存された機密は、データ鍵で暗号化してから保管され、そのデータ鍵は使う前にマスター鍵で解く必要があります。セキュリティポリシーの**データ鍵のメモリ保持時間**（鍵管理ページ）は、解いたあとのデータ鍵をどれだけ置いておくかを決めます。

**空欄は出荷時の既定であり、デプロイの挙動は現状のままです。** データ鍵は一度解いたあと、システムをシールするかプロセスが再起動するまで保持され、委任型の鍵の保管先は日常の動作経路に入りません。

**0 または秒数を設定すると、保管先が実行時の経路に入ります。** 保管先に到達できない間は、鍵を解き直す必要のある操作がすべて失敗します。接続を確立するときの資産アカウントのパスワード取得や、実行中のセッションで書き込む記録内容もそこに含まれます。これはこの設定が提供するトレードオフそのもの（メモリに置く時間の短縮を可用性で支払う）であり、その場で回避できる劣化ではありません。

有効にする前に、次の 2 点を決めてください。

- **保管先に到達できない間、新しい接続が失敗することを受け入れられるか、どれだけの時間なら受け入れられるか。** 値を選ぶ前に答えるべきことであり、最初の障害のあとではありません。失敗しても以前の鍵素材に戻ることはありません。解けなければ、解けないままです。
- **自分の保管先との往復にかかる時間。** 解き直しのたびに 1 回の呼び出しが発生し、遅延はリージョン、ネットワーク経路、保管先そのものによって変わります。**自分の環境で計測してください。** どの文書の数値も転記せず、計測した結果から値を選びます。

ローカル鍵モード（マスター鍵を環境変数で渡す、または起動時に管理者が入力する）でも、この設定は使え、データ鍵を置いておく時間を同じように短くします。変わらないのはマスター鍵そのもので、これらのモードではマスター鍵は終始プロセスのメモリにあります。

監査記録はこの設定の対象外です。記録に押印する鍵は保持期間の影響を受けないため、保管先に到達できない間も記録は書き込めます。この設定が短くするのはデータ鍵がメモリに存在する時間であり、操作の実行中はメモリに鍵とデータの元の内容が存在します。

## 運用メトリクスの取得（`/metrics`）

backend は自身の HTTP ポート（コンテナ内の 8080）の `/metrics` で Prometheus のメトリクスを提供します。**既定のデプロイでは、`https://<お使いのドメイン>/metrics` を開くと返ってくるのは Web の画面であり、メトリクスではありません。** backend のポートはホストに公開されておらず、前段のプロキシが転送するのは `/api` と `/ws` だけだからです。これは意図した既定の構成です。このエンドポイントに到達できるのはデプロイの docker ネットワークの内側だけであり、ほかのホストから取得できるようにするのは別の判断で、token の設定と一体です（後述の方式 B）。

- **認証**：`.env` の `METRICS_TOKEN` が空（既定）の場合は認証なしで応答します。値を設定すると、どこから来た要求でも `Authorization: Bearer <token>` が必要になります。token がない場合も誤っている場合も 401 を返し、応答本文にメトリクスは含みません。
- **システムがシール済みの間**、`/metrics` にあるのはシールの状態、単一インスタンスのガードの系列、Go runtime と process のメトリクスだけです。それ以外（監査キューも含みます）はアンシールの後に現れます（[アップグレード SOP §2.4](./upgrade-sop.md#24-停止の前に監査キューが空になったことを確認する)）。

### その場で値を見る

ホスト上で、要求を backend コンテナの中で実行します。本番のイメージにはシェルがありませんが、busybox の `wget` は残っています。

```bash
# METRICS_TOKEN が空（既定）の場合
docker exec custodexa-backend wget -qO- http://127.0.0.1:8080/metrics

# METRICS_TOKEN を設定している場合：token はコンテナ自身の環境変数から読むため、
# ホストのコマンドラインには現れません
docker exec custodexa-backend /bin/busybox sh -c \
  'wget -qO- --header="Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:8080/metrics'
```

末尾に `| grep '^custodexa_'` を付けると、製品自身の系列だけが残ります。

### ブラウザーで見る（SSH トンネル経由）

backend コンテナは docker ネットワーク上に、ホストから到達できるアドレスを持っています。ホスト上でそのアドレスを読み、作業端末からローカルのポートをそこへ転送します。

```bash
# ホスト上で
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' custodexa-backend

# 作業端末で。上で表示されたアドレスを入れます
ssh -N -L 9180:<backend のアドレス>:8080 <ユーザー>@<ホスト>
```

続けて `http://localhost:9180/metrics` を開きます。このアドレスはコンテナの作成時に割り当てられるため、backend を再作成した後（アップグレード、リストア、設定の変更）は読み直してください。ブラウザーは `Authorization` ヘッダーを送りません。`METRICS_TOKEN` を設定している場合は、同じトンネル越しに `curl -H "Authorization: Bearer <token>" http://localhost:9180/metrics` を使います。

### 継続的な収集、方式 A：同じホストで Prometheus を動かす

Prometheus をコンテナとしてデプロイの docker ネットワークにつなぎ、backend をコンテナ名で収集します。ホストの外へ何も開かず、プロキシも変更しません。

ネットワーク名は `<compose プロジェクト名>_custodexa-network` です。パッケージのデプロイではプロジェクト名が常に `custodexa` なので（[インストールパッケージによるデプロイと管理スクリプト](#インストールパッケージによるデプロイと管理スクリプト)）、`custodexa_custodexa-network` になります。ソースからのデプロイでは、`COMPOSE_PROJECT_NAME` を設定していない限り、プロジェクト名はそのディレクトリー名です。ホスト上で確認します。

```bash
docker inspect -f '{{range $name, $net := .NetworkSettings.Networks}}{{println $name}}{{end}}' custodexa-backend
```

最小の `prometheus.yml`：

```yaml
scrape_configs:
  - job_name: custodexa
    static_configs:
      - targets: ["custodexa-backend:8080"]
    # METRICS_TOKEN を設定している場合のみ。ファイルには token の値だけを入れます
    # authorization:
    #   type: Bearer
    #   credentials_file: /etc/prometheus/custodexa-metrics-token
```

Prometheus 用の compose ファイル（専用のフォルダーに置きます）：

```yaml
services:
  prometheus:
    image: prom/prometheus:<バージョン>
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:9090:9090"
    networks:
      - custodexa
networks:
  custodexa:
    external: true
    name: custodexa_custodexa-network   # 上のコマンドで表示された名前
```

このネットワークは Prometheus の起動より前に存在している必要があるため、先に Custodexa を起動します。Prometheus がつながっている間はネットワークを削除できません。Custodexa のプロジェクトで `docker compose down` を実行する前に Prometheus を止め、その後で起動し直してください。

### 継続的な収集、方式 B：別のホストから収集する

別のホストから収集するには、https の入口に `/metrics` への経路を開く必要があります。そして**`METRICS_TOKEN` を設定せずにこの経路を開いてはいけません。** token がなければ、そのアドレスに到達できる人は誰でも、エンドポイントの一覧、機能ごとの利用量、エラー率を読めてしまいます。

**手順 1：token を設定します。** 値を生成します。

```bash
openssl rand -hex 32
```

デプロイフォルダーの `.env` に `METRICS_TOKEN=<値>` として書き込みます。backend は `.env` の設定をコンテナの作成時に読むため、コンテナを再作成してください。再起動だけでは反映されません。パッケージのデプロイフォルダーでは `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend` を、その他の Compose デプロイでは `docker compose up -d --force-recreate backend` を実行します。`KEK_PROVIDER=ui` または `kms` の場合、再作成された backend はシール済みで起動し、アンシールが必要です（[委任型の鍵モード](#委任型の鍵モードこのデプロイは無人運転ではありません)）。その後は、「その場で値を見る」の token なしの形は 401 を返し、token ありの形はメトリクスを返します。

token を設定しても、アップグレード前に監査キューが空になるのを待つ管理スクリプトの確認はそのまま動きます。この確認は backend コンテナの中で実行され、コンテナがすでに持っている token を使うためです。

**手順 2：経路を開きます。** できることは、デプロイの前段に何があるかで決まります。

- **内蔵のプロキシ（既定）。** テンプレートをコピーし、`.env` の `TLS_NGINX_TEMPLATE` でそのコピーを指します。やり方は[クイックスタート：リバースプロキシ設定のカスタマイズ](../QUICKSTART.md#リバースプロキシ設定のカスタマイズ)のとおりです。パッケージのデプロイでコピー元にするテンプレートは `current/reverse-proxy/nginx-tls.conf.template` で、コピーは `releases/` と `current/` の外、たとえば `tls/custodexa.conf.template` に置きます。コピーの `listen 443` の server ブロックの中、`location /` の前に次を加えます。

  ```nginx
      location = /metrics {
          set $backend_upstream http://backend:8080;
          proxy_pass $backend_upstream;
          proxy_http_version 1.1;
          proxy_set_header Host $public_host;
      }
  ```

  内蔵のプロキシはデプロイの docker ネットワーク上にあるため、サービス名で backend に到達できます。名前はテンプレートにもともとある `resolver` の行によって要求のたびに解決されます。適用は、パッケージのデプロイフォルダーでは `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate tls-proxy`、それ以外では `docker compose up -d --force-recreate tls-proxy` です。コピーは利用者のものです。管理スクリプトのバックアップには含まれますが（[バックアップとリストア §3.8](./backup-and-restore.md#38-管理スクリプトによるバックアップパッケージのデプロイ)）、アップグレードでは変更されません。アップグレードのたびに、同梱のテンプレートと比べてください。
- **自前の ingress（external ingress overlay）。** 同梱の compose ファイルは backend のポートを一切公開しません。お使いの ingress が `/metrics` を転送できるのは、コンテナとしてデプロイの docker ネットワークにつながっている場合だけです。同梱の例がフロントエンドを `frontend:80` で指せるのも同じ前提によります。その場合は、パス `/metrics` に完全一致する要求を `backend:8080` へ送ります。ホストに導入した ingress や別のマシンで動く ingress が到達できるのはフロントエンドが公開するポートだけで、フロントエンドが転送するのは `/api` と `/ws` だけです。そのため同梱のデプロイ形態では `/metrics` に届きません。この場合は方式 A を使うか、デプロイの docker ネットワーク上にプロキシのコンテナを置いてください。

**手順 3：Prometheus を入口に向けます。**

```yaml
scrape_configs:
  - job_name: custodexa
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/custodexa-metrics-token
    static_configs:
      - targets: ["bastion.example.com"]   # TLS_HTTPS_PORT が 443 でなければ :<ポート> を付けます
    # 自己署名モード（TLS_MODE=selfsigned）：デプロイのローカル CA を信頼します。
    # CA は入口の /custodexa-ca.crt から取得できます
    # tls_config:
    #   ca_file: /etc/prometheus/custodexa-ca.crt
```

token のファイルには token の値だけを入れ、`.env` と同じアクセス規則で扱います。

### 見ておくべきメトリクス

全体の一覧、ラベル、各メトリクスの意味は [API 仕様（繁体字中国語）](../../API_SPEC.md#營運指標端點prometheus)にあります。出発点として 5 つのアラートを Prometheus のルールで示します。継続時間としきい値は、自組織の約束に合わせて調整してください。

```yaml
groups:
  - name: custodexa
    rules:
      # サービスを提供していない：シール済み、アンシール中、または障害の後のシール。
      # KEK モード ui と kms では、再起動のたびに誰かがアンシールするまでここに留まります。
      - alert: CustodexaNotUnsealed
        expr: custodexa_seal_state{state="unsealed"} != 1
        for: 5m
      # データベースに届かなかった監査の行。reason="fallback_file"：退避ファイルに書かれ、
      # 後から回収できます。reason="discarded"：失われました。
      - alert: CustodexaAuditRowsDropped
        expr: increase(custodexa_audit_dropped_total[15m]) > 0
      # 非同期の監査キューの容量は 1000 行です。満杯になると、新しい行は上の経路をたどります。
      - alert: CustodexaAuditQueueBacklog
        expr: custodexa_audit_queue_depth > 500
        for: 5m
      # まだ誰も確認していないコマンドのアラート。重大度ごと。
      - alert: CustodexaCommandAlertsUnreviewed
        expr: sum by (severity) (custodexa_command_alerts_pending) > 0
        for: 24h
      # このインスタンスが単一インスタンスのロックを持っていない。
      - alert: CustodexaInstanceLockNotHeld
        expr: custodexa_instance_guard_held == 0
        for: 5m
```

収集そのものが失敗する場合に備えて、一般的な `up{job="custodexa"} == 0` も加えてください。シール済みの間、監査の系列は 0 ではなく存在しないため、それらのルールは鳴りません。その状態は最初のルールが受け持ちます。各信号の読み方は、監査の行と退避ファイルが[アップグレード SOP §3.1](./upgrade-sop.md#31-終了時にキューは空にされますが時間の上限があります)、単一インスタンスのロックが[アップグレード SOP §3.4](./upgrade-sop.md#34-実行中に単一インスタンスロックを失った場合ログバナー監査イベントの読み方)、システムが上限を設けない録画のストレージ量が[クイックスタート：ストレージの監視](../QUICKSTART.md#ストレージの監視)にあります。

## 出力の機密情報検出：対象範囲と運用上の判定

検出は SSH、K8s、データベースコンソールの解析済みテキスト出力のみを走査します。RDP/VNC の画面、暗号化・圧縮・符号化された内容（Base64 を含む）は対象外です。端末の制御シーケンスは描画も除去もしません。符号化により照合を回避でき、一致は機密情報を**含む可能性**を示します。未検出は不存在を意味しません。この機構は警告のみで、配信済みのバイトを遮断・変更しません。

出力ルールの追加、無効化、変更は**新しいセッション**から適用されます。進行中のセッションは開始時のルール集合を維持します。アップグレード、リストア、切り替え後は方向、有効状態、プロトコルを確認し、新しいテキストセッションで適用ルールを確認してください。インストール後の初期ルールは計16件で、元の入力12件、agent 向けの入力阻止2件、カード番号・秘密鍵ヘッダーの出力2件です。組み込みカードパターンが元のままであれば Luhn 検証も行います。編集後は通常の正規表現となり、カード番号の検証は行いません。

同じルールとセッションの一致は5秒の窓で集約し、セッション終了時に残りを確定します。アラートと転送には識別子、ルール、回数、時刻を残し、command は空で、一致した原文やバイト位置は保存しません。reason_code の `o1:<base36 count>` が回数を表し、webhook には `possible_sensitive_output.count` もあります。これは含む可能性の兆候であり、全出力を走査した証明ではありません。

容量制限のあるキューがあふれると、そのセッションの走査を無効化し、出力は継続します。既存の監査検索で action=`output_scan_disabled`、resource=`session`、当該セッションの resource_id を確認します。details は session_id と reason=`queue_overflow` のみで、出力原文を含みません。サーバーログだけでは監査記録の代わりになりません。それ以降の出力は未走査として扱い、既存の権限で証拠を確認し、負荷を確認してから新しいセッションを開始します。スキャナーの失敗もサーバーログに残りますが、アラートがないことは走査成功の保証ではありません。

共通のマスキングプリミティブは完全置換したテキストと置換回数を返しますが、**本バージョンの製品応答経路には接続されていません**。録画、コマンド記録、その他の証拠には適用しません。原文には既存の保存期間、アクセス制御、バックアップ／リストア手順が引き続き適用されます。


### 主体と認証情報の完全性の対象範囲

検証画面はロール割り当て、主体の種別／所有者、資格情報の状態を個別に表示します。アップグレード後、新しいスナップショットを含む最初のチェックポイントまで、新しい二行は「対象外」です。検出は即時ではなく、検証、チェックポイント作成、トークン発行前に照合します。不一致は項目ごとに `principal_state_integrity`／`principal_state_mismatch` イベントと通知を生成し、差分には識別値だけを含めます。不一致や照合エラーでも発行を続行します。エラーは不明としてログに記録し、業務データを変更しません。サービス層の状態投影行の actor は `system` とし、操作者は既存の HTTP 監査行で記録します。

互換性は一方向です。新版は旧チェックポイントを検証できますが、旧版は新しいスナップショットキーを完全には検証できません。キーの削除、再署名、旧来の単一機構の失敗イベント一意インデックスへ戻すことは禁止です。ロールバックにはアップグレード前の整合したバックアップとリストア手順が必要です。ペイロードは現行の最新バージョン（現在 v3）を維持します。

## Agent MCP の運用

有効な人間の owner を指定して agent 主体を作成します。owner または管理者が名前と有効期限付きの agent token を発行し、一度だけ表示される平文を実行者のシークレット保管先に保存します。agent は user ロールのみを持ち、資産とアカウントの許可範囲を明示します。agent を動かすマシンに stdio クライアント `custodexa-mcp` を https://github.com/custodexa/custodexa-mcp からインストールします。`go install github.com/custodexa/custodexa-mcp@latest` を使うか、リリースのバイナリを取得します。リリースのバイナリは、同じリリースで公開された `checksums.txt` で検証します。環境変数 `CUSTODEXA_AGENT_TOKEN` を `custodexa-mcp` に渡し、`CUSTODEXA_MCP_URL` を HTTPS の `/api/v1/mcp` に設定します。人間の JWT と cookie はこのエンドポイントでは使用できません。stdio クライアントは転送のみを行い、判定と証跡保存はサービス側で行います。token をコマンド引数や報告書に記載しないでください。

agent が申請したタスクが人の承認を待つかどうかは、申請対象ごとの資産のアクセスポリシー区分で決まります。資産自身に `access_policy` が設定されていればそれを、なければ全体の `access_policy_default` を使います。`approval` 区分の項目は、その資産を範囲に含む承認者が判断するまで保留されます。`open` と `reason` 区分の項目は申請時に承認され、`auto_approved: true` とポリシースナップショットとして記録され、承認票は付きません。出荷時の既定では多くの資産が `approval` 以外に入るため、設定を変更しない環境では agent のタスクがすべて自動承認されます。人の判断を必須にするには、対象資産の `access_policy` を `approval` に設定するか、全体の `access_policy_default` を `approval` にします。必要な承認票数は `access_request_min_approvals` で決まります。この選択は agent に最初の資産許可を与える前に決め、運用手順書に明記してください。自動承認も記録は完全に残りますが、人による統制ではありません。

ローテーションでは新しい名前付き token を発行し、実行者のシークレットを更新し、新しい MCP 接続で資産の可視性を確認してから旧 token を失効させます。既存 token の秘密を直接交換する機能や、バックアップから平文を自動復元する機能はありません。失効は旧 token のセッションを閉じます。ハンドルを別の token や MCP 接続に引き継ぐことはできません。リストアやスタンバイへの切り替えの後は MCP 接続を新規作成し、必要に応じてタスクを申請します。メモリー上のハンドルと 60 秒間の冪等キャッシュは再起動を越えて保持されません。再開前に token とタスクの保存状態を確認します。

インシデント時は該当 token を失効または停止し、必要なら agent を無効化して、タスク、ツール台帳、HTTP リクエストの監査記録を確認します。探索ブレーカーは token を停止してイベントを記録します。owner または管理者が理由を付けて解除しますが、停止済み token は再有効化されないため、新たに発行してください。この計数が対象とする参照は一種類だけです。すなわち、実在し、かつその agent に一度も開示されたことのない資産への参照です。存在しない、または削除済みの資産 id への参照は retired、過去に開示された資産への参照は revoked に分類され、いずれもイベントとしては記録されますが、作動しきい値には計上されません。識別子を手当たり次第に列挙しても計上されないイベントが並ぶだけであり、これを一般的なスキャン検知として説明しないでください。これは範囲外の実在資産へ繰り返し手を伸ばす行為に対する統制です。より広い列挙は、アラートルールと申請レート方針で扱ってください。拒否された参照の意味を判断する前に、ブレーカーイベント一覧の `class` 欄を確認します。通知は既存の webhook／Slack に `owner_id` 付きで送られます。個人受信箱ではなく、本人への到達を証明しません。可視 exposure は migration 後から記録され、以前の可視履歴は復元しません。拒否された参照を不正と判断する前にこの境界を確認します。

Token の期限切れ、紐付いたタスク項目の期限切れ、タスク終了は、既存セッションと実行中のツールを終了し、現在のコマンド完了を待ちません。期限の現状確認は 250ms ごとですが、この間隔は完了 SLA ではありません。失効は既存の終了経路を使います（目標は 3 秒以内、遅延時は証跡を記録）。対象は本システムが作成したセッションだけで、遠隔のバックグラウンド処理の停止や実行済み変更の取消しは保証しません。実行中リクエストの取消しはそのセッションを閉じます。POST 間のクライアント離脱は即座には検出できず、5 分間の idle lease 満了でハンドルを終了します。即時切断検出とは記載しないでください。

`completed` はプロンプトを再観測したことだけを示し、コマンドの終了も成功も保証しません。プロンプトは偽装でき、バックグラウンドの出力が混在することもあります。`timed_out` は結果不明です。再送前に後続出力を確認してください。同じハンドルの冪等キーは 60 秒間の重複書込みを抑止しますが、キーなしでは再実行され得ます。`needs_input` では実行者が `send_keys` で復帰を要求し、システムは自動で割込みを送りません。`read_screen` は行バッファーであり仮想画面ではありません。agent に返す文字列はマスクされますが、録画とコマンド記録は原文を保持します。マスクはルール駆動で、対象を個別に列挙する方式です。汎用の機微データ保護ではありません。適用されるのは、有効で `direction=output` かつ主体種別が agent を含み、プロトコルが一致するアラートルールで、一致した範囲をプレースホルダーに置き換えます。有効なルールに一致しない内容はそのまま agent に返り、出荷時のルールはカード番号パターンと秘密鍵ヘッダーパターンの二種類のみです。このルール一覧を「この環境が agent チャネルで何を機微と定めるか」の定義として扱い、許可した資産で実際に取得できるデータと突き合わせ、不足する種類はルールを追加してください。マスクは人間の端末、録画、コマンド記録には適用されません。

データベース、録画、チェックポイント、対応するバージョンの完全性鍵を保全します。pending 行が示すのは記録済みの意図であり、送達や完了ではありません。タスク／ハンドルに帰属できない呼出しはツール台帳の前で拒否し、当該 MCP HTTP 監査行に主体、ツール、理由コード、時刻を保存します。コマンド完全性の coverage 軸は監査調査ビューと一括エクスポートのみで提供します。単一 session 指定のエクスポートには coverage がありません。degraded 行がゼロでもコマンド欠落がなかった証明にはなりません。報告書の各版とタスク終了時刻を保持し、pending の結果を捏造しないでください。

MCP ハンドルはプロセス内にあり、複数レプリカは共有セッションストアではありません。
