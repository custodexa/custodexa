# プラットフォーム自身の特権資格情報のローテーション

[English](../../ops/privileged-credential-rotation.md) | [繁體中文](../../zh-TW/ops/privileged-credential-rotation.md) | **日本語** | [他の言語 →](../../README.md)

> 対象バージョン：Custodexa 1.0。
>
> **本ページの範囲は「システム自身が保持する資格情報」です。** プラットフォームが動作するために保持しなければならないサービスアカウントのパスワード、暗号鍵、署名鍵を指します。管理下の資産上のアカウント資格情報のローテーション（パスワード変更）は製品の機能であって運用手順ではないため、その日常の操作は本ページの対象外です。**そのうち運用手順にあたる部分が一つあり、§13 に記載しています。** 一組のログイン資格情報を複数のホストで共有していて、その入れ替えがすべてのホストで完了しなかった場合の対処です。Windows の対象ホストの前提条件は[デプロイとアップグレードの SOP](./upgrade-sop.md) §2.5 の Windows ローカルアカウントのパスワード変更の項を参照してください。
>
> 関連文書：[バックアップとリストア](./backup-and-restore.md)、[デプロイとアップグレードの SOP](./upgrade-sop.md)。

## 1. 一覧表

| 資格情報 | 保存先 | ローテーションの入口 | 反映のタイミング | 既存の接続／ログインを切断するか | 外部での対応の要否 |
|---|---|---|---|---|---|
| LDAP bind パスワード | データベース（エンベロープ暗号化） | ID 管理 → LDAP ディレクトリ（UI） | 即時 | いいえ | ディレクトリサーバー側で先に変更が必要 |
| 通知チャネルの secret | データベース（エンベロープ暗号化） | 通知チャネル（UI） | 即時（同一プロセス） | 該当なし | 受信側の同期更新が必要 |
| 通知チャネルの URL | データベース（エンベロープ暗号化） | 通知チャネル（UI） | 即時（同一プロセス） | 該当なし | — |

| DEK（データ鍵） | データベース（KEK でラップ） | 鍵管理（`POST /keys/rotate`） | 即時 | いいえ | — |
| 監査スタンプ鍵 | データベース（KEK でラップ） | 鍵管理（`POST /keys/rotate`） | 即時 | いいえ | — |
| `ENCRYPTION_KEY`（KEK 材料、モード A） | `.env` | env を直接変更するのではなく KEK 再ラップウィザードを使用 | 再ラップ＋再起動の後 | はい（再起動） | — |
| KEK 材料（モード B、`KEK_PROVIDER=ui`） | メモリのみ（アンシール時に入力） | KEK 再ラップウィザードを使用 | 再ラップ＋再起動＋アンシールの後 | はい（再起動。かつ誰かがアンシールしなければサービスは戻りません） | — |
| `JWT_SECRET` | `.env` | env を変更してから再起動 | 再起動の後 | **はい。全員がログアウトされます** | — |
| Ed25519 エクスポート署名鍵 | データベース（秘密鍵はエンベロープ暗号化） | システム管理。必要な場合はデータ層で対応（§8 参照） | — | — | **はい。公開鍵の再配布が必要** |
| Ed25519 チェックポイント署名鍵 | データベース（秘密鍵はエンベロープ暗号化） | システム管理。関連エンドポイントは読み取り専用（§9 参照） | — | — | **はい。公開鍵の再配布が必要** |
| `METRICS_TOKEN` | `.env` | env を変更してから再起動 | 再起動の後 | いいえ（収集側の同期変更が必要） | 収集側の同期更新が必要 |

## 2. LDAP bind パスワード

**保存先**：データベース `ldap_directories` テーブルの `bind_password_enc` 列（エンベロープ暗号化）。このテーブルは単一行の設定テーブルで、1 つのデプロイに LDAP ディレクトリの設定は 1 件だけです。この列は write-only です。どの API 応答もこれを返さず、編集フォームにも再表示されません。

**ローテーションの手順**：

1. まずディレクトリサーバー（AD／LDAP）側で、当該サービスアカウントのパスワードを変更します。
2. 管理側 → ID 管理 → LDAP ディレクトリ → 新しいパスワードを入力します。
3. 「接続テスト」を押して bind の成功を確認します。**このテストは現在のフォームの値（未保存の変更を含みます）で実行されます**。そのため保存の前に新しいパスワードが正しいことを検証できます。最長でおよそ 15 秒です。
4. 保存します。

**反映のタイミング：即時。** bind パスワードは**キャッシュされません**。LDAP ログインが発生するたびに設定を 1 回読み、1 回復号します。平文はそのログインの呼び出しスタックの中にしか存在しません。したがって、

- **サービスの再起動は不要です。**
- **既存のログインは切断されません。** ログイン済みの利用者が持っているのは本システムが発行したトークンであり、LDAP の bind とは無関係です。
- 手順 1 と 2 のあいだの空白時間には、**新しい LDAP ログインが失敗します**（ローカルアカウントのログインは影響を受けません）。空白は短いほどよく、あるいは利用の少ない時間帯を選んでください。

**失敗時の挙動**：bind パスワードの復号に失敗した場合、システムは fail-close で動作します。外部への応答は資格情報の誤りに収束し、**「LDAP が有効化されていない」ように見せかけて通すことはありません**。内部のログには、それが鍵の事故であってアカウントやパスワードの誤りではないことが明示されます。

**`.env` の `LDAP_*` 変数**：**初回起動時にのみ**、設定をデータベースへ投入するために使われます。投入が済んだ後にこれらの変数を変更しても**反映されません**。ローテーションは必ず UI から行ってください。

## 3. 通知チャネルの secret と URL

**保存先**：`notification_channels` テーブルの `secret` 列と `url` 列（いずれもエンベロープ暗号化）。

**secret の用途**：webhook へ配信するリクエストの本文に対して HMAC 署名を計算し、`X-OT-Signature` ヘッダーに載せて受信側が送信元を検証できるようにします。**secret が空であれば署名しません。**

- **Slack 種別のチャネルには常に secret がありません。** Slack は独自ヘッダーを検証しないため、付けても誤解を招くだけです。webhook から slack 種別へ変更した場合、残っていた secret は消去されます。
- **webhook 種別**：編集時に空欄のままにすると既存の値を引き継ぐ意味になります（secret は返却されないため、編集操作が静かに値を消してしまうことを避けます）。明示的に「消去」を選んだときだけ空になります。

**ローテーションの手順**：

1. 通知チャネルの UI → 当該チャネルを編集 → 新しい secret を入力 → 保存します。
2. **受信側の検証鍵も同時に更新します。**
3. 「テスト送信」で、受信側が受け取り、署名の検証に成功することを確認します。

**反映のタイミング：即時**（同一プロセスでチャネルのキャッシュを直接更新するため、再起動は不要です）。

> ### 知っておく必要のある、静かな機能低下の経路
>
> チャネルのキャッシュを更新する際に、URL と secret を配信用の平文に復号します。**どちらか一方でも復号に失敗すると、そのチャネルはそのまま読み飛ばされて配信されず、ログが 1 行残るだけです。アラートは生成されず、UI 上ではそのチャネルは正常に見えます。**
>
> これは意図的な取捨選択ですが（暗号文を URL として送出するくらいなら送らない）、その代償として、**「画面が正常に見えること」は「配信されていること」を意味しません。**
>
> どういう場合に踏むか：KEK や暗号化の設定を変更した後、古い暗号化列が復号できなくなった場合です。
>
> **確認の方法**：暗号化に関わる設定を変更した後は、有効なチャネルそれぞれに対して「テスト送信」を 1 回押し、受信側が**実際に受け取ったこと**を確認してください。UI 上でチャネルが有効な状態かどうかだけを見ないでください。
>
> 関連するもう 1 つの経路：キャッシュの更新自体に失敗した場合は、古いキャッシュをそのまま使い、ログを記録するだけで、次回の更新で補われます。設定を変更したのに期待どおりの挙動が見えないときは、ログが唯一の手がかりです。

## 3b. オブジェクトストレージの資格情報（オフサイト証拠保管）

**保存先**：データベースのオフサイト保管の設定テーブル。エンベロープ暗号化されており、**設定世代ごとにそれぞれ 1 件を保持します**（保管先を変更したことのあるデプロイには複数件があり、それぞれが当時アップロードされた一群のオブジェクトに対応します）。この列は write-only です。どの API 応答にも、管理画面にも、監査記録にも返却されず、**マスクした値さえ現れません**。編集フォームにも再表示されないため、変更するときは入力し直しになります。

**ローテーションの手順**：

1. まずストレージ側（S3／MinIO／GCS）で新しい資格情報を作成します。
2. 管理側 → システム設定 → オフサイト保管 → 新しい資格情報を入力します。
3. 「接続テスト」を押します。**このテストは現在のフォームの値（未保存の変更を含みます）で実行されます**ので、保存の前に新しい資格情報が正しいことを確認できます。
4. 保存します。
5. ストレージ側に戻り、古い資格情報を失効させます。

**反映のタイミング：保存の成功と同時。サービスの再起動も、`.env` の変更も不要です。**

- **世代の切り替えを起こさず、設定のフィンガープリントも変えません。** 資格情報は接続先の一部ではありません。資格情報だけを変更する場合は、現行の世代をその場で更新することになり、過去のオブジェクトの帰属も取得経路も影響を受けません。
- **逆に、保管先を変更した場合は資格情報を入力し直す必要があります。** provider、エンドポイント、バケットのいずれかが変わると、システムは既存の資格情報の流用を拒否します（資格情報が設定に追随して別の場所へ送られることはありません）。この経路は同時に世代の切り替えでもあり、管理画面で確認を求められます。

**失敗時の挙動：静かではありません。** 新しい資格情報がストレージ側で無効な場合、アップロードは失敗の状態になり、管理画面のオフサイト保管のページと失敗一覧から確認でき、メトリクスにも反映されます。**資格情報の復号の失敗（鍵の事故）は独立した状態であり**、「機能が未設定」と扱われて静かに止まることはありません。

**過去の世代の資格情報の失効**：保管先を変更した後、古い世代の資格情報は**その世代とともに保持されます**。過去のオブジェクトの取得に必要だからです。ある過去の世代についてもう取得の必要がないと判断した場合は、その世代に対して個別に資格情報を失効させられます。失効させると、その世代のオブジェクトは取得できなくなり、画面と API のいずれもどの世代に何が欠けているかを明示します。**そしてクラウドの既定の資格情報チェーンへ戻ることはありません。** 「失効させたのに接続できてしまう」ことは起こりません。失効は不可逆です。現行の世代は設定ページで資格情報を入力し直せば復旧できますが、**過去（退役済み）の世代は失効させた後に復旧する手段がありません**。設定ページは現行の世代にしか資格情報を書き込めず、その世代の遠隔のオブジェクトは以後システムから取得できなくなります。過去の世代を失効させる前に、そのオブジェクトに取得の必要がないことを確認してください。

**オフサイトを停止しても資格情報は失効しません。** 管理画面での「オフサイトの停止」は新しいアップロードを行わなくなるだけで、過去のオブジェクトの取得は通常どおり行え、資格情報も残ります。失効させるには世代ごとに明示する必要があります。

**`.env` の `OFFSITE_*` 変数**：**初回起動時にのみ**、設定をデータベースへ投入するために使われます。投入が済んだ後にこれらの変数を変更しても**反映されません**ので、ローテーションは必ず UI から行ってください。したがって資格情報をデプロイ層の設定ファイルに残しておく必要はなく、その災害復旧の前提は「データベースをリストアし、同じ KEK を用意すること」になります。[バックアップとリストア §4.4](./backup-and-restore.md#44-オブジェクトストレージの資格情報に関する災害復旧の前提)を参照してください。

## 4. KEK（鍵暗号化鍵）

GCP は先に [§13b](#gcp-kms) を参照してください。本番接続と完全な移行／復旧の受入確認は未完了で、一般の KEK 手順は GCP のデプロイ準備完了を示しません。

Vault については先に [§14](#vault-transit) を参照してください。現在の証拠は隔離したフルサービスのテスト組立を対象とし、環境固有の TLS やストレージ復旧は対象外です。以下の一般的な KEK 手順は Vault 対応の証拠ではありません。

KEK はエンベロープ暗号化の体系全体の根です。本製品ではその「ローテーション」を**再ラップ（rewrap）**と呼びます。新しい KEK で既存のデータ鍵をラップし直すもので、データそのものを暗号化し直すわけではありません。

**入口**：鍵管理ページ → KEK 再ラップウィザード（admin 限定）。関連する API はいずれも admin 限定です。

| エンドポイント | 用途 |
|---|---|
| `POST /api/v1/keys/rewrap` | 再ラップを実行します |
| `DELETE /api/v1/keys/rewrap` | まだ切り替わっていない再ラップを破棄します |
| `DELETE /api/v1/keys/retired-material` | 退役した KEK の材料を消去します。**材料を破棄する唯一の地点です** |

**重要な性質：退役の後も、明示的に消去するまで材料は保持されます。** KEK の退役はソフトな退役で、状態の列を変更するだけであり、ラップ材料は消去されません。したがって**「退役データの消去」を実行するまでは、データ層で古い KEK へ戻すことが常に可能です**（最後の手段であり、§10.4 に従って手作業で行う必要があります）。消去を実行すると材料は消され、復元できません。退役の軌跡（元、先、タイムスタンプ）とフィンガープリントは恒久的に残ります。

**再ラップの破棄**：破棄した対象は削除ではなく、退役として記録されます（理由は「破棄済み」として記録されます）。その後に改めて再ラップを行うとき、システムは過去に現れたことのある鍵参照（退役済みの記録を含みます）の再利用を拒否します。新しい鍵を使う必要があります。

**切り替えを完了させる手順は KEK のモードによって異なります。** 再ラップそのものと切り替えの仕組みはどのモードでも同じで、切り替えは常に**起動処理**が完了させます（システムが新しい KEK ですべての鍵をアンラップできることを検証したうえで、古いラップの行を退役として記録します）。異なるのは「新しい KEK がどこからプロセスに入るか」と、その起動処理が**いつ実行できるようになるか**です。モード A／C では再起動した時点で、モード B では起動後にシール状態で止まるため、誰かがアンシールページで材料を提出した後に実行されます。そのため、モード B の切り替えはアンシールの時点で完了します。

| モード | 再ラップの完了後に行うこと |
|---|---|
| `env`（モード A） | 新しい KEK を `.env` の `ENCRYPTION_KEY`（または compose ファイル）に書き込む → バックエンドのサービスを再起動する → 起動時に切り替えが完了します |
| `ui`（モード B） | バックエンドのサービスを再起動する（再起動後はシール状態に戻ります）→ **アンシールページで新しい KEK を入力する** → アンシールの時点で切り替えが完了します。**新しい KEK を `.env` やいかなる環境変数にも書き込まないでください。** モード B の材料はメモリにのみ存在し、ディスクに書くことは本モード唯一の保護を放棄することと同じです |
| `kms`（モード C） | 下の「モードをまたぐ移行」を参照してください。切り替えには `KEK_PROVIDER` の宣言と対応する構成を変更してからの再起動が必要で、デプロイ層の変更にあたります |

モード B の全体の流れは、再ラップ → 再起動 → アンシールページで新しい世代の KEK を入力 → アンシールに成功し正常にログインできること、です。

鍵管理ページと鍵交換ウィザードの画面の案内は、**実行時の provider** に応じた版を表示します。provider を読み取れない場合は各モードのやり方を並べて表示し、操作者自身に判別を求めます。**既定で `env` 版を表示することはありません。**

**モードをまたぐ移行（ローカル → クラウド KMS）**：

1. まず KMS の構成キー（`KEK_KMS_PROVIDER`／`KEK_KMS_REGION`／`KEK_KMS_KEY_ID`）を揃えて再起動します（この時点ではまだローカルの KEK で動作しています）。
2. 鍵管理ページ → KEK 再ラップウィザード → 委譲先を選択 → 対象の鍵の ARN を入力します。事前チェックが実際に KMS を呼び出し、疎通、鍵の利用可否、権限を検証します。
3. 再ラップの完了後、`KEK_PROVIDER` を `kms` に変更し、ローカルの `ENCRYPTION_KEY` を削除して再起動します。
4. 鍵の台帳に `provider=kms` と、正規の ARN の `key_ref` が表示されることを確認します。

**逆方向の移行（クラウド → ローカル）**も同じく再ラップウィザードを通し、ローカルの対象を選ぶだけです。

### 稼働中の seal とアンシール

検証範囲（2026-09-13）：開発版の env、ui、委託モードに対する HTTP 操作。委託には提供済みの AWS driver と隔離ターゲットを使用しました。三モードすべての画面操作と release 全体のメモリダンプの結論は、未検証の制限です。

1. シール前にサービス中断を計画し、現在の鍵ソースと既存の管理者セッションを保持します。seal は新たな材料利用を止め、作業と接続を含むサービスグラフを解放します。セッションの無中断やすべての外部作業の完了は約束しません。
2. 管理者は既存の Bearer token で `POST /api/v1/seal/seal` を要求します。`GET /api/v1/seal/status` を読み、`state=sealed` かつ `cleanup_pending=false` を待ちます。sealed の表示だけではクリーンアップ成功の証明になりません。状態照会はサービスをアンシールしません。
3. `POST /api/v1/seal/unseal` でアンシールします。`ui` では同じ有効な KEK を明示的に再入力します。通常のアンシールにログインは不要です。`env` では既存の管理者 token と空オブジェクトを送り、バックエンドが `ENCRYPTION_KEY` を再読込します。配置ファイルの編集は稼働中プロセスの環境を変更しません。委託モードでは同じ認可済み要求が配置資格情報で再アンシールし、ローカル KEK は入力しません。`KEK_KMS_PROVIDER`、`KEK_KMS_REGION`、`KEK_KMS_KEY_ID` と設定した鍵サービスへのアクセスを保持します。
4. `unsealing` の終了と `unsealed` を確認し、元の暗号文データにアクセスできることを確認します。材料の誤りや委託ソースの利用不能を成功と扱いません。クリーンアップ中や並行アンシールの `409` は、再試行前に状態を確認する意味です。並行して再送しないでください。seal とアンシールは鍵ローテーションではありません。
5. env または委託モードで管理者 token が期限切れ、失効、その他の理由で無効なら、設定したソースでバックエンドを再起動します。別の救援ログインや新規の救援 token はありません。`sealed-faulted` または継続する `cleanup_pending` では結果を保存し、報告された原因を解消して旧プロセスを停止してから再起動します。journal を削除せず、再起動を以前のクリーンアップ成功の証明と扱わないでください。
6. アカウントの平文は SSH ハンドシェイク後まで保持されません。DEK と署名鍵はプロセス保護設定が適用されたプロセスメモリに常駐し、seal 操作で消去できます。メモリスナップショットには鍵や平文が含まれる可能性があります。 env モードの鍵はプロセス環境、設定 string、配置ファイルに残り得ます。unsealed 中は DEK をキャッシュします。プロトコル string、ライブラリのコピー、セッション通信は全メモリ消去の約束に含まれません。所有 buffer がゼロでも、あらゆる平文の不在は証明しません。ソースの資格情報は後のアンシールを許可し得ます。seal はそれらを失効させません。

## 5. DEK と監査スタンプ鍵

**入口**：鍵管理ページ、または `POST /api/v1/keys/rotate`（admin 限定）。`purpose` でローテーションの対象を指定します。

- データ鍵（資産の資格情報などの暗号化列を保護します）。
- 監査完全性のスタンプ鍵。

**反映のタイミング：即時。再起動は不要で、既存の接続も切断しません。** 新しいバージョンが有効になると、新しい書き込みは新しいバージョンを使います。既存の暗号文は引き続きそれぞれ対応するバージョンで復号され、バージョンの連なりは保持されます。

**起こりうる拒否の応答**（いずれも正常な関門であり、エラーではありません）：

- 鍵の操作が進行中（他の鍵の操作がロックを保持している）→ 409。
- まだ切り替わっていない再ラップが進行中 → 409。先にその再ラップを完了させるか破棄してください。
- プロセス内の鍵キャッシュが期限切れ → 409。

**ローテーションの頻度**：鍵管理ページは `key_cryptoperiod_reminder_days` のポリシーキーを担います。0 より大きい値を設定すると、鍵が年数を超えた際に台帳へリマインダーが表示されます。リマインダーは台帳に現れるだけで、実際のローテーションは人が実行する必要があります。

## 6. `ENCRYPTION_KEY`（KEK モード A の材料）

**「`.env` の値を直接書き換えて再起動する」という方法でこの鍵をローテーションしないでください。** それはローテーションではなく、システムを起動しなくする操作です。起動時に KEK とデータベース内のラップが一致しなければ、fail-close で起動を拒否します。

正しいやり方は §4 の**再ラップウィザード**を使うことです。新しい材料で再ラップし、システムが切り替えを完了させてから `.env` を更新します。

鍵の台帳には、この鍵の**フィンガープリント**（材料の SHA-256 の先頭 8 バイト）が表示されます。環境変数はローテーションの記録を持たないため、台帳にはフィンガープリントだけがあり、経過年数も前回のローテーション日時もありません。ローテーションの日時の記録が必要な場合は、運用の文書側で管理してください。

退役済みの KEK を誤って設定した場合のエラーの案内は、[バックアップとリストア §7.2](./backup-and-restore.md#72-退役済みだが材料が未消去の-kek-で起動した場合)を参照してください。

**モード B（`KEK_PROVIDER=ui`）にはこの env のキーがありません。** 材料はアンシールの時点で入力されるだけで、ディスクには残りません。このモードでの再ラップの切り替え手順は §4 のモード対照表を参照してください。再起動の後にアンシールページで新しい KEK を入力し、`.env` には**書き込まないでください**。

## 7. `JWT_SECRET`

**保存先**：`.env`。これはログイントークンの HS256 署名の信頼の根であり、長さは最低 32 バイト必要です。

**ローテーションの手順**：`.env` の値を変更する → サービスを再起動します。

**反映のタイミング：再起動の後。**

> **すべての利用者が切断されます。既存のトークンはすべて直ちに無効となり、全員が再ログインする必要があります。**
> 古いトークンは古い鍵で署名されており、鍵を替えれば検証を通りません。署名鍵のローテーションでは必ずこうなります。
> メンテナンスの時間帯を設け、利用者に事前に周知してください。

システムは release モードで `JWT_SECRET` が出荷時のプレースホルダーのままかどうかを検知し、変更されていなければ起動を拒否します。

## 8. Ed25519 エクスポート署名鍵（監査証拠のエクスポート）

**用途**：監査証拠のエクスポートの manifest に署名します。検証する側（外部の監査担当者、QSA など）は組織の外にいて、**公開鍵によりオフラインで検証します**。HMAC ではなく Ed25519 を選んだ理由がここにあります。共有秘密は組織の外の検証者には使えません。

**保存先**：`export_signing_keys` テーブルの**単一行**（秘密鍵はエンベロープ暗号化、公開鍵はダウンロード用に平文で保存）。初回起動時に自動生成されます。**このテーブルにはバージョン列がありません。**

**公開鍵の取得**：`GET /api/v1/audit-export/public-key`（`audit:view` 権限が必要）、または鍵管理ページの公開鍵のコピー／ダウンロードです（台帳に表示されるのは**公開鍵のフィンガープリント**であり、材料のフィンガープリントではありません）。この鍵は台帳で「システム管理」と表示され、**ローテーションのボタンはありません**。

### どうしても交換する必要がある場合：データ層の手順

この鍵の交換はデータ層の操作です。`export_signing_keys` の当該行を削除してから再起動すると、サービスが次回の起動時に新しい鍵を生成します。この経路は**製品として検証されていません**。実行の前に必ずバックアップを取り、次の帰結を理解してください。

> ### 鍵を交換した後は公開鍵を再配布しなければ、外部での検証が静かに失敗します
>
> - **外部の検証者が持つ古い公開鍵はすべて直ちに無効になります。** 古い公開鍵で新しくエクスポートした証拠を検証すると「署名の検証に失敗」という結果になり、その結果は「証拠が改ざんされた」場合と**見た目がまったく同じ**です。
> - **すでに引き渡し済みの既存のエクスポート証拠は、新しい公開鍵では検証できません。** 古い署名は古い秘密鍵に対応しており、その秘密鍵はもう存在しないため、それらの証拠は以後検証できなくなります。
>
> **したがって鍵を交換する前に確認してください。** 引き渡し済みのすべての証拠について、検証の期間はすでに終了していますか。
> 交換の後は、新しい公開鍵を外部の検証者一人ひとりに能動的に再配布し、交換の時点を書面で伝えて、どの証拠をどの公開鍵で検証するのかが分かるようにする必要があります。
>
> これを代わりに行う仕組みはなく、行い忘れたことを知らせるエラーメッセージもありません。

## 9. Ed25519 チェックポイント署名鍵（監査チェックポイントチェーン）

**用途**：監査チェックポイントチェーンのチェックポイントに署名し、オフラインでの再検証に供します。エクスポート署名鍵とは**意図的に分けており**、同じ鍵を共用しません。初回起動時に自動生成され、テーブル（`checkpoint_signing_keys`）は当初からバージョン列を持ちます。

**公開鍵の取得**：`GET /api/v1/audit-checkpoints/public-key`（公開鍵、バージョン、フィンガープリントを返します）。

### この鍵のライフサイクル

この鍵は生成された後、同じものを使い続けます。`/api/v1/audit-checkpoints` 配下の 3 つのエンドポイント（一覧、公開鍵、検証）はすべて読み取り専用です。テーブルがバージョン列を持ち、検証のロジックもバージョンを指定した署名検証を受け付けるのは、複数バージョンの併存に備えた余地です。

将来ローテーションを開放する場合、§8 の外部での対応の要件が同じく成立します。**新しい公開鍵をオフラインで再検証する人へ再配布する必要があり**、古いバージョンのチェックポイントは引き続き古い公開鍵で検証する必要があります。

## 10. KEK に関わる例外の対応

以下の 4 項目は「誤るとデータが復号できなくなる」操作です。順を追って実行し、手順を飛ばさないでください。

### 10.1 `kek_id` が正規の形式でない場合の行ごとの対応

**現象**：起動時に、委譲モード（`wk:2:kms:`）の行のうち `kek_id` が KMS の key ARN の構文に合致しないものを検知し、システムが fail-close で起動を拒否します。

> **対応は必ず行ごとに行ってください。テーブル全体を一度に `UPDATE` することは厳禁です。**

1. 当該行の `purpose`／`version`／`kek_id`／`wrapped_key` をエクスポートします。
2. **各行について**、明示的な KeyId と正しい AAD でアンラップを試み、材料が確かにその鍵に属することを確認します。
3. **アンラップに成功した行だけ**を、正規の ARN へ書き換えてよいものとします。
4. アンラップに失敗した行は**書き換えてはなりません**。アンラップの失敗は、ラベルと材料の対応関係そのものに問題があることを示します。素の `UPDATE` は「診断できるエラー」を「不可逆なラベルの汚染」へ変えるだけです。

### 10.2 AAD の再計算（クラウド KMS の監査照合に使用）

委譲モードでは、KMS へ送る `EncryptionContext` は単一キーの不透明なマッピング `{"aad": base64(aadBytes)}` です。

**これにより CloudTrail の監査能力は「直接読める」から「照合できる」へ変わります。** CloudTrail の記録に現れる base64 の値はそのままでは読み取れず、ローカルで再計算してから照合する必要があります。

再計算の方法は次のとおりです。データ鍵の層の AAD は、その鍵の `purpose` と `version` を長さ前置の canonical 形式で符号化したうえで base64 を取ったものです。再計算の結果が CloudTrail の記録と一致すれば、その KMS 操作がどの鍵の用途とバージョンに対応するかを確認できます。

### 10.3 バージョンを戻す順序

逆方向の再ラップ（委譲 → ローカル）そのものは再ラップウィザードで実行します。§4 を参照してください。

> **バージョンを戻す操作は、逆方向の再ラップの 1 ステップだけです。** ラップの接頭辞の正当な値は常に単一の形式で、戻る分岐はありません。再ラップが完了すれば終わりであり、2 つめの手順はありません。

### 10.4 退役した KEK の行を手作業で復元する（最後の手段）

Vault には [§14.7](#vault-recovery) を適用してください。本節の手動で行を復活させる手順を Vault に適用せず、整合したバックアップ全体から復旧してください。

「どうしても退役済みのある KEK へ戻す必要がある」場合にのみ使います。また、**その KEK の材料がまだ明示的に消去されていない場合にのみ可能です**（§4 を参照）。

前提と注意：

- これはデータ層の操作であり、製品は UI も API も入口を提供しません。
- 実行の前にデータベースを完全にバックアップしてください。
- システムは**退役を自動で反転しません**。切り替えが完了した後に古い KEK を設定するのは、ほぼ確実に操作の誤りであり、自動で反転すれば、意図して行った鍵の儀式を静かに取り消すことになります。
- 退役の理由が「破棄済み」（その KEK が現役になったことがない）の場合、それを復元することは、意図して行った破棄の判断を静かに取り消すことと同じです。この場合の正しいやり方は、**現行の KEK で起動したうえで再ラップをやり直すこと**であり、退役した行を復元することではありません。

退役済みの KEK を誤って設定して起動した場合、システムは退役の理由に応じた案内を出します。[バックアップとリストア §7.2](./backup-and-restore.md#72-退役済みだが材料が未消去の-kek-で起動した場合)を参照してください。

## 11. メール（SMTP）の資格情報

監査や調達の評価では「メールサービスのアカウントは誰がローテーションするのか」がよく問われます。**本製品はメール送信のコンポーネントを含みません。** SMTP クライアントも、送信元アカウントも、メールサーバーの設定もないため、ローテーションすべき SMTP の資格情報も存在しません。

アラートの外部への送出経路は webhook と Slack です（§3 を参照）。いずれも HTTP POST であり、資格情報の形はチャネルの URL と HMAC の secret です。ローテーションの手順は §3 のとおりです。

電子メールでアラートを受け取る必要がある場合は、webhook の受信側で転送するかたちになります。その部分のメールの資格情報は貴組織が管理するものであり、本製品の範囲には含まれません。

## 12. ローテーションの後に共通して確認する項目

どの項目をローテーションした場合でも、完了後に次を確認してください。

1. **鍵の台帳のフィンガープリントが想定どおりに変化していること**（変わるべきものが変わり、変わるべきでないものが変わっていないこと）。あわせて、バックアップとともに保管しているフィンガープリントの記録を更新します。
2. **有効なすべての通知チャネルに対して「テスト送信」を 1 回ずつ押し**、受信側が実際に受け取ったこと（§3 の静かな機能低下の経路）。
3. **監査記録に今回のローテーションの記録があること。** 鍵の操作はいずれも admin 限定で監査に入ります。材料の消去では、消去した行数と各鍵のバージョンのフィンガープリントも記録されます。
4. env 側の鍵に触れた場合は、サービスの再起動の後、起動ログに fail-close のメッセージがないこと。

## 13. 管理下の資産における共有資格情報

**対象**：一組のログイン資格情報を複数の管理対象ホストが共同で使用している状態。資格情報ライブラリでは、名前の付いた 1 件の資格情報と複数のバインドとして表され、バインドの一覧が「この秘密をどのホストが使っているか」の答えになります。本節は、その秘密の入れ替えがすべてのホストで終わらなかった場合の対処手順です。

### 13.1 グループ全体を入れ替える

開始するとすぐに応答が返り、ホストはバックグラウンドで 1 台ずつ処理されます。**あるホストが新しい秘密に切り替わるのは、システムがその新しい秘密でログインに成功した後です。** それまでそのホストは元のバージョンを使い続けます。

**したがって「途中まで入れ替わった」状態は正常であり、障害ではありません。** 各バインドが実際に使用しているバージョンを保持しており、接続はそのバージョンで行われます。検証を通過したホストは新しい秘密を、まだのホストは元の秘密を使います。どちらの側にも「使える秘密がないホスト」は生じません。

資格情報の状態は次の 5 値のいずれかで、画面に表示されます。

| 状態 | 意味 |
|---|---|
| `idle` | 進行中の入れ替えがなく、適用待ちのバージョンもない |
| `queued` | 開始済みで、すべてのホストがまだ順番待ち |
| `changing` | ホストを順に処理している |
| `partial` | 新しい秘密に切り替わったホストと、まだのホストが混在している |
| `out_of_sync` | 今回の回は終了したが、切り替わっていないホストが残っている |

`partial` は意図的に `changing` より優先して表示されます。「一部は完了、一部は未完了」が成立した時点で、それが最初に見えるべき事実だからです。

**自動で進むものと、進まないもの。** 進行中の回の中では、再試行可能な失敗になったホストと、リモートの結果がまだ判明していないホストは、再試行スケジュールが再び拾い上げます（バックオフの間隔はパスワード変更の候補の再試行と同じです）。**最終的な失敗で終わったホスト、その回とともに打ち切られたホスト、そして放棄した回のすべてのホストは、自動では進みません。** これらは 1 台ずつ手動で再実行する必要があります。確実に変更できないホストを無期限に試行し続けるべきではないからです。

**1 台ずつの再実行**はそのホストだけに作用し、同期的に応答します。実際に接続を確立してログインを検証するため、数十秒かかることがあります。

### 13.2 回を放棄する

放棄は**自動処理を止めるだけで、何も巻き戻しません**。すでに新しい秘密に切り替わったホストが元に戻ることはなく、すでにホストへ送った保留中の秘密も削除されず、どのホストにもそれ以上の指示は送られません。巻き戻すにはそれらのホストに再びログインする必要があり、「放棄」とはまさにこれ以上手を出さないという判断だからです。

結果は 2 通りです。

- **どのホストにも触れていなかった場合**（すべてが順番待ちまたは再試行待ちで、秘密が一つも送出されていない）：その回は破棄され、資格情報は `idle` に戻ります。
- **それ以外**：資格情報は `out_of_sync` に入り、そこにとどまります。**出口は 1 台ずつ再実行して全ホストを同じバージョンに揃えることだけです。** `out_of_sync` の間、システムはその資格情報に対する新しい回の開始を拒否します。新しい回を始めてしまうと、「どのホストが実際にどの秘密を使っているか」に二度と答えられなくなるためです。

**状態を整えるために保留中の秘密を消さないでください。** その記録は、あるホストですでに有効になっている秘密の唯一の複製である可能性があり、消した後の手段はそのホスト自身のコンソールだけになります。

### 13.3 ホストごとに別々の秘密にする

もう一つのモードは、各ホストに互いに異なる新しい秘密を割り当て、共有関係を解消します。検証を通過したホストから順に、そのホスト専用の資格情報へ付け替えられます。元の資格情報はバインドが 1 件だけ残るとそのホスト専用になり、1 件も残らず保留中の秘密もない場合は削除されます。

**元に戻す操作はありません。** 「同じ一組に戻す」動作をシステムは提供していません。秘密は各ホストで実際に別々のものになっているからです。再び共有するには、新しい共有資格情報を作成し、ホストをバインドしたうえで、その資格情報に対して一括の変更をもう一度開始します。バインドそのものはどのホストの秘密も変えません。各ホストに同じ新しい秘密を設定するのは、その一括の変更です。

### 13.4 1 台だけ共有から外す

1 台を共有から外す操作は、そのホストが現在使用している秘密でログインし、新しい秘密を適用し、もう一度その新しい秘密でログインして検証します。**その検証を通過した場合にのみ**、そのホストは専用の資格情報へ移ります。検証に失敗した場合、またはリモートの結果を判定できない場合、そのホストは共有資格情報にとどまり、応答はそのどちらであったかを示します。この違いは重要です。単純な失敗はそのまま再試行できますが、結果不明の場合はそのホストが現在どの秘密を受け付けるのかをまず確認する必要があります。

**共有から外すことと、バインドを解除することは別の操作です。** バインドの解除はそのホストを資格情報から外すだけで、**ホスト上のパスワードには触れません**。共有から外す操作はホスト上のパスワードを変更します。画面では操作の場所でこの違いを説明しています。

### 13.5 スケジュール実行の計画が共有ホストを含む場合

アカウントを対象とするパスワード変更計画は、**選択範囲に共有資格情報を使うホストが含まれていると保存できません**。実行時にそのようなホストに到達した場合、そのホストはスキップとして記録されます。代替案はどちらも受け入れられません。1 台だけを変更すると同じ組の他のホストが使える秘密を失い、残りのホストへ黙って範囲を広げると操作者が選択していないホストを変更することになるからです。

進め方は 2 通りで、いずれもシステムが対応しています。

- **計画の対象をアカウントから資格情報に変更する。** 計画はその資格情報をグループとして入れ替えるようになり、スケジュールとパスワードの生成方針は同じ設定をそのまま使います。
- **先にそのホストを共有から外す**（§13.4）。その後は、アカウントを対象とする計画が他のホストと同様にそのホストを対象にできます。

### 13.6 完了後に確認する項目

1. **資格情報の状態が `idle` であり**、すべてのバインドが同じバージョンを示していること。`partial` または `out_of_sync` のまま残っている資格情報は、入れ替えが完了していないことを意味します。
2. **監査記録に今回の変更の記録があること。** 資格情報ライブラリの操作はいずれも admin 限定で監査に入ります。バインドとバインド解除は影響を受けたホストも記録するため、資格情報の側からだけでなくホストの側からもこの変更を追跡できます。
3. **ローテーション証跡レポートの表示が想定どおりであること。** 共有から外したホストは共有として表示されなくなります。レポートは資格情報のスコープを読みます。

<a id="gcp-kms"></a>
## 13b. GCP Cloud KMS の KEK 操作

<a id="gcp-availability"></a>
### 13b.1 提供範囲とリリースの前提条件

GCP Cloud KMS は選択できます。契約テスト一式とプロセス内の fake に対する実行は済んでいますが、実際の GCP プロジェクトでの実行は本プロジェクトではまだ行っていません。現在のビルドには GCP driver、五つの provider の共通契約テスト、fake client を使うサービスオブジェクトのテスト、そして本番起動と client ownership の接続が含まれます。完全な移行ウィザードは未提供です。実際のプロジェクトでの ADC／IAM、PostgreSQL のトランザクションロールバック、プロセス再起動、既存セッション、監査の送信、完全なバックアップ復旧は未検証です。稼働中のデプロイの保管先を GCP にする前に、この点を判断に含めてください。

以下の手順は、必要な本番接続を備え、隔離したフルサービス環境で受入確認を終えたリリースにのみ適用します。前提が欠ける場合は停止し、手作業のデータベース編集や独自に組み立てたリクエストで代用しないでください。GCP では §4 と §10 の一般手順にもこの条件を適用します。現行データベースの復旧のためにローカルの退役判定を迂回してはいけません。

<a id="gcp-configuration"></a>
### 13b.2 リソース識別、設定と TLS

完全な CryptoKey リソース名 `projects/<p>/locations/<l>/keyRings/<r>/cryptoKeys/<k>` を `kek_id` として使います。鍵名だけ、URL、cryptoKeyVersions 子リソースは使いません。デプロイの参照が信頼する project を定め、ウィザードの対象はその project 内の鍵参照だけを指定します。新しい project の信頼設定や資格情報は渡しません。driver は project ID と project number の同一性を推測しません。完全な参照は保存上限の 255 bytes 以内に収めます。[Cloud KMS リソースリファレンス](https://cloud.google.com/kms/docs/reference/rest)を参照してください。

以下は対象設定の例であり、未接続のリリースを有効にする指示ではありません。

```dotenv
KEK_PROVIDER=kms
KEK_KMS_PROVIDER=gcp
KEK_KMS_KEY_ID=projects/example-project/locations/global/keyRings/platform/cryptoKeys/platform-kek
KEK_KMS_REGION=
ENCRYPTION_KEY=
```

GCP は `KEK_KMS_REGION` を必要としません。未設定または空のままにします。残した値は無視され SDK に渡されず、location はリソース名から取得します。委託モードは空でない `ENCRYPTION_KEY` を拒否します。切替前は、§13b.5 で対象設定の適用を明示するまで現行のローカルモードと復旧材料を維持してください。

KMS のデータ transport は https://cloudkms.googleapis.com のみを使用し、証明書を検証する TLS 1.2 以降で通信します。redirect を追跡せず、環境 proxy も使いません。独自 endpoint、HTTP、TLS 検証の無効化、既定外の SDK universe／mTLS 設定は拒否します。資格情報の token／metadata 通信は独立した公式 ADC の経路を使い、その正当な宛先を KMS ホストだけには制限しません。製品独自の endpoint や GCP 資格情報の設定キーは追加しません。

<a id="gcp-authentication"></a>
### 13b.3 ADC、権限と資格情報の交換

認証は公式 SDK の Application Default Credentials（ADC）を使い、token の更新はそのライブラリが担当します。承認された workload identity またはサービスアカウント資格情報の取得元をデプロイから提供します。`GOOGLE_APPLICATION_CREDENTIALS` は標準 SDK の入力であり、製品の秘密情報ストアではありません。匿名や静的テスト資格情報へのフォールバック、稼働中に資格情報を交換する製品 API はありません。資格情報ファイルを変更すれば構築済み client も更新されるとは考えないでください。

実行時の身分には、選択した CryptoKey の metadata 読み取りと encrypt/decrypt に必要な権限だけを付与します。バージョン作成、primary の変更、バージョンの無効化・破棄、アクセス方針の変更には別の管理者身分を使います。metadata の権限だけでは不十分で、事前検証は encrypt と decrypt も完了する必要があります。実プロジェクトの IAM と資格情報更新は、隔離した実プロジェクトでの受入確認が必要です。

1. 承認された身分、秘密でないリソース参照、資格情報の保管、保守時間帯、復旧用アクセスを記録します。秘密鍵や bearer token は記録しません。
2. デプロイの秘密情報管理機構で代替アクセスを用意します。採用を確認するまで承認済みの復旧用アクセスを維持し、資格情報の内容を shell 引数、チケット、バージョン管理対象ファイルに置かないでください。
3. §13b.1 を満たした後、そのリリースが対応するデプロイ／再起動手順で client を再構築します。本番アクセスの切替前に、実プロジェクトで metadata、encrypt/decrypt、資格情報更新の確認成功を要求します。
4. 採用成功後に旧アクセスを失効させます。失敗した場合は停止し、デプロイ手順で承認済みアクセスを復旧します。漏えいが疑われる場合は対象アクセスを速やかに失効させ、KMS が必要な操作が利用不能になる可能性を受け入れてください。資格情報だけでは失われた KEK バージョンを代替できません。

<a id="gcp-actions"></a>
### 13b.4 API 操作、AAD と異なるローテーション

以下のパスの `<cryptoKey>` は §13b.2 の完全なリソース名です。

| 操作 | リクエスト | 効果と境界 |
| --- | --- | --- |
| DEK のラップ | `POST /v1/<cryptoKey>:encrypt` | CryptoKey の primary を使用します。平文と元の AAD を送り、暗号文、実際のバージョン名、整合性フィールドを受け取ります。 |
| DEK のアンラップ | `POST /v1/<cryptoKey>:decrypt` | 暗号文と元の AAD を送り、DEK をバックエンドへ返します。サービスが暗号文のバージョンを選択します。 |
| リモートバージョンの作成 | `POST /v1/<cryptoKey>/cryptoKeyVersions` | 管理者操作です。create 応答だけでは primary やデータベースのラップが変更された証拠になりません。 |
| primary の選択 | `POST /v1/<cryptoKey>:updatePrimaryVersion` | 管理者が `cryptoKeyVersionId` を指定し、応答／再取得した CryptoKey の primary が一致することを要求します。CryptoKey 参照は変わらず、既存のデータベースのラップも書き換えません。 |
| 製品 KEK 参照の交換 | 元の decrypt、次に対象の encrypt | ネイティブ ReEncrypt エンドポイントは使いません。GCP 関連のサービス再ラップでは、両操作と clone 行の書き込みが既存のロック付き DB トランザクション内で行われます。操作またはコミットの失敗は成功を返さず、メモリの pending 状態を公開しません。リモートリクエスト自体は DB からロールバックできません。 |

公式 schema：[encrypt](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/encrypt)、[decrypt](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/decrypt)、[バージョン作成](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions/create)、[primary 更新](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/updatePrimaryVersion)。

driver は既存の用途／バージョンの正規 DEKAAD bytes をそのまま `additionalAuthenticatedData` に渡し、REST JSON が base64 を一度適用します。論理 AAD を事前にエンコードしたり、操作間で変更したりしないでください。driver はリクエスト CRC32C を付け、応答の整合性を確認します。encrypt のバージョン parent は期待する CryptoKey と完全一致する必要があり、空や不正な結果は拒否します。これらは IAM の代わりではありません。保存形式は `wk:2:gcp:<base64(raw-ciphertext)>` です。

バージョン作成、primary 選択、データベースのラップ交換は別の事象です。リモート管理だけで DB のバージョン更新が済んだと報告してはいけません。同じ KeyRef を拒否するため、ウィザードをその場のバージョン更新ツールには使えず、その製品エンドポイントもありません。製品の DEK ローテーションも別の操作です。現行行や保持中のバックアップが必要とするリモートバージョンを無効化・破棄しないでください。KMS がまだ暗号文を復号できても、本システムはローカルで退役した KEK 行を拒否します。

<a id="gcp-migration"></a>
### 13b.5 local→gcp の操作手順

以下は必要な統合を備えたリリースの受入手順であり、現在のビルドで本番移行を完了した証拠ではありません。

1. §13b.1 を満たし、他の鍵操作を止め、DB・関連ファイル・設定の整合したバックアップを取得します。復旧時点、アプリケーションイメージの digest／バージョン、schema バージョン、ローカル KEK の復旧方法、対象 CryptoKey を記録します。[バックアップとリストア](./backup-and-restore.md)に従い、§13b.7 の追加の鍵要件も適用します。
2. 現行のローカルモードと材料を維持します。GCP の対象設定と ADC 取得元を用意し、隔離した実プロジェクトで対象 metadata と encrypt/decrypt の権限を実証します。この段階ではローカル復旧材料を除去しません。
3. そのリリースが対応する admin ウィザードで GCP を選び、完全な対象参照だけを送ります。scope 検証と canary 事前検証の成功を要求します。選択肢や本番 client ownership の接続がなければ、KEK を切り替えず停止してください。
4. トランザクション成功後、すべての pending 対象ラップと元のラップが併存することを要求します。元の KEK で既存データを読め、失敗操作で pending 行が追加されないことを確認します。デプロイで依存する前に PostgreSQL のロールバック受入確認を完了する必要があります。
5. §13b.2 の対象設定を適用し、使用中のローカル `ENCRYPTION_KEY` を除去して、リリースが対応する手順で再起動します。現行の全行のアンラップ、暗号文が変わらない旧データの読み取り、正しい台帳モード／参照、元のラップのソフト退役を要求します。鍵名の一致だけでは不十分です。
6. 観測した起動と監査の結果を記録し、継続性に依存する前に §§13b.6–13b.7 の障害・復旧受入確認を完了します。必要な鍵バージョンと復旧材料は、承認されたバックアップ保持期間の終了まで維持してください。

<a id="gcp-continuity"></a>
### 13b.6 可用性の証拠と障害時の受入確認

サービスオブジェクトの fake テストでは、fake KMS が到達不能でもキャッシュしたデータの暗号化・復号と監査鍵へのアクセスが続き、KMS を必要とする操作と新しいサービスオブジェクトの読み込みは失敗します。これは既存セッション、監査の送信、実プロセスの再起動が同じ動作をする証拠ではありません。この結果から無停止サービスを約束しないでください。

リリースの条件を満たした後、隔離したフルサービス環境で KMS 到達不能と ADC 拒否を演習します。デプロイを受け入れる前に、既存データの読み取り、新規接続、監査の送信、リモート操作の拒否、コールドスタートの拒否を実際に観測することを要求します。観測した障害に応じて停止または復旧し、endpoint 変更、整合性検査の迂回、暗号文の代わりにキャッシュ平文を使う方法で成功を強制しないでください。これらのフルサービス演習は未完了です。

<a id="gcp-recovery"></a>
### 13b.7 放棄とバックアップからの復旧

**切替前：**現行のローカル KEK と設定を保持します。未切替の pending 対象に対して、そのリリースが対応する admin 放棄操作（`DELETE /api/v1/keys/rewrap`）を使い、pending 状態、対象の退役、現行データの読み取り、監査結果を確認します。pending を放棄するためだけに古い DB へ戻さないでください。ローカルの pending／放棄にはサービスオブジェクトの fake の証拠がありますが、完全な handler／ウィザードの手順は未検証です。再試行はそのリリースの対象参照ガードを満たす必要があり、退役行を手作業で復活させてはいけません。

**切替後：**バイナリだけを旧版へ戻す、退役フラグを戻す、現行 DB を退役済みの元の KEK に向ける、といった操作をしないでください。承認された復旧環境で書き込みを止め、現状の証拠を保全します。[バックアップとリストア](./backup-and-restore.md)に従い、互換性のあるアプリケーションイメージ、schema、関連ファイル、デプロイ設定で整合したバックアップ一式を復元します。切替前のバックアップには元の復旧可能なローカル KEK 材料が必要です。GCP のバックアップには同じ完全な CryptoKey、そのラップ行が必要とする全リモートバージョン、有効で承認済みの ADC アクセスが必要です。DB バックアップに KMS KEK は含まれず、必要な鍵材料を失えば資格情報だけではデータを復旧できません。

書き込み再開前に、復旧した行の実際のアンラップ、旧データの読み戻し、台帳と監査の整合性を要求します。選んだ復旧時点、バイナリ／イメージと schema の互換性、鍵バージョンへの依存、観測結果を記録します。バックアップ時点より後の書き込みは失われる可能性があり、ファイルや外部ストレージも同じ時点に照合します。一致したリソース名や新しいバイナリは、互換性も復号可能性も証明しません。これはバックアップ全体の復旧であり、現行 DB の退役行の復活ではありません。GCP の完全な復元手順は未検証です。

<a id="gcp-protection"></a>
### 13b.8 保護に関する主張と操作記録

driver の境界では、**KEK はバックエンドプロセスに入りませんが、DEK と認証資格情報はバックエンドに残ります**。パスワード平文とセッションの通信内容もメモリに存在し得ます。バックエンドに秘密情報や平文がない、すべてのメモリコピーが消去される、製品が HSM 等級の保護を提供する、といった主張をしてはいけません。デプロイで Cloud KMS の HSM protection level を選んでも、そのような製品全体の主張は成立しません。

記録は時刻、秘密でない参照、バージョン識別子、ステータスコード、読み戻し結果に限定します。秘密鍵、bearer token、DEK、平文、秘密を含むリクエスト／応答本文は収集しません。fake の証拠と実プロジェクトの証拠を分け、実プロジェクトの結果は資格情報と受入確認待ちのままとします。契約テストが成功しただけで完了とはしません。

## 14. Vault Transit の KEK 操作

<a id="vault-availability"></a>
### 14.1 提供範囲と前提条件

正式な起動経路と委譲ウィザードの factory には、Vault client owner の接続が実装されています。隔離したフルサービスのテスト組立は、正式な handler とデータベースを経由し、実際の dev Vault AppRole／Transit を使います。HTTP client だけをテスト専用コードから注入し、local→vault の移行とサービス世代の再起動を検証します。正式な transport は引き続き証明書検証付き HTTPS を要求し、この演習は本番 TLS の検証ではありません。

稼働中の環境で §14.4、§14.6、§14.7 を適用する前に、その環境の互換イメージ／schema、永続的な Vault 鍵バージョン、ストレージ、TLS で演習してください。前提条件がなければ停止します。§4 と §10 の一般手順は Vault の利用可能性を示しません。復旧を含む Vault 操作には本節の適用範囲が優先します。

<a id="vault-configuration"></a>
### 14.2 TLS とデプロイ設定

固定の `transit` マウントに対称 derived key を作成し、AppRole を `auth/approle` にマウントします。専用の鍵を使用し、エクスポートと平文バックアップを無効にします。この adapter はカスタムマウントや namespace に対応しません。以下は切替先の設定例であり、デプロイ環境での演習の代わりにはなりません。資格情報の値はデプロイ側の秘密情報注入機構から渡してください。

```dotenv
KEK_PROVIDER=kms
KEK_KMS_PROVIDER=vault
KEK_KMS_KEY_ID=custodexa-kek
KEK_VAULT_ADDR=https://vault.example.com
KEK_VAULT_ROLE_ID=
KEK_VAULT_SECRET_ID=
KEK_KMS_REGION=
ENCRYPTION_KEY=
```

デプロイ時に空でない role_id と secret_id を注入します。Vault は `KEK_KMS_REGION` を必須としないため、未設定または空のままにします。AWS の分岐では引き続き region が必須です。委譲モードでは空でない `ENCRYPTION_KEY` を拒否します。local→vault の切替前は、手順で変更を指定するまで既存の `KEK_PROVIDER` とローカル材料を保持してください。

`KEK_KMS_KEY_ID` は鍵名、または正規参照 `vault:<base64url-without-padding(HTTPS-origin)>:transit:<key-name>` を受け付けます。鍵名に使えるのは ASCII 英字、数字、`_`、`-` のみで、参照全体は最大 255 bytes です。origin は正規の HTTPS scheme/host/port で、パス、query、資格情報、fragment を含みません。参照に鍵のバージョンや資格情報は入りません。対象参照はデプロイの origin に解決される必要があり、ウィザードのリクエストから別のアドレスや資格情報を渡すことはできません。

正式な transport は証明書検証を行う HTTPS と TLS 1.2 以上を要求し、redirect を拒否します。バックエンドの実行環境がシステムの信頼ストアを通じてサーバー証明書を信頼するようにしてください。`VAULT_ADDR`、`VAULT_TOKEN`、`VAULT_CACERT`、`VAULT_SKIP_VERIFY` などの Vault SDK 環境変数による上書きは使わないでください。adapter が拒否し、カスタム CA ファイルやクライアント証明書の設定もありません。この transport は環境変数の proxy 設定を使用しません。loopback HTTP の dev 検証環境を使えるのは非公開のテスト注入経路だけです。dev mode は本番用の TLS や永続化の仕組みではありません。

<a id="vault-authentication"></a>
### 14.3 AppRole の権限と token の更新

製品の実行主体には、指定した鍵の metadata 読み取り、encrypt/decrypt/rewrap、および token 自身の更新だけを許可します。鍵名が `custodexa-kek` の場合、policy の形は次のとおりです。

```hcl
path "transit/keys/custodexa-kek" { capabilities = ["read"] }
path "transit/encrypt/custodexa-kek" { capabilities = ["update"] }
path "transit/decrypt/custodexa-kek" { capabilities = ["update"] }
path "transit/rewrap/custodexa-kek" { capabilities = ["update"] }
path "auth/token/renew-self" { capabilities = ["update"] }
```

鍵名はすべて同じ値に置き換えてください。任意の鍵へのアクセス、rotate、export、全体管理を許す別の policy は付与しません。マウント、鍵、policy、AppRole は管理者の主体で別途作成します。製品は認証の代替として root token を受け付けません。[AppRole API](https://developer.hashicorp.com/vault/api-docs/auth/approle) と [token API](https://developer.hashicorp.com/vault/api-docs/auth/token) を参照してください。

client は auth token と正のリース期間を検証し、返された期間の半分で更新し、新しい期間で再スケジュールします。更新不可の token を無理に更新しません。再試行可能な更新障害の再試行は最大 2 回です。期限切れまたは拒否を検出した時点で、設定された SecretID がまだ有効なら、単一のログイン処理で再利用できます。ログインが失敗するとその client は終了し、provider を切り替えません。失効した token を検出できるのは、Vault が操作や更新を拒否したとき、またはローカルのリースが終了したときです。token の更新は KEK や DEK のローテーションではありません。

<a id="vault-secretid"></a>
### 14.4 SecretID の交換

このデプロイ手順には §14.1 の条件が必要です。client は構築時に渡された資格情報を保持します。環境変数の供給元を編集しても、既存 client には再読込されません。稼働中の client に AppRole 資格情報を注入したり交換したりする製品のエンドポイントはありません。

1. 資格情報の値を含めず、role、policy、token／SecretID の TTL と使用回数制限、保守／復旧時間枠を記録します。交換用 SecretID が予定したログインと許可された復旧ログインに使えることを確認します。1 回限りの SecretID をテストログインで消費した場合、バックエンドには使えません。テスト用には別の SecretID を発行してください。
2. Vault 管理者が交換用 SecretID を発行します。承認されたデプロイの秘密情報経路で渡し、チケット、コマンドライン引数、ログ、バージョン管理対象のファイルには入れません。収集する応答本文や shell tracing に role_id と secret_id を含めないでください。
3. 隔離したフルサービス環境で、そのリリースが対応する再起動手順により client を再構築し、新しい `KEK_VAULT_SECRET_ID` を注入します。role を変えた場合は `KEK_VAULT_ROLE_ID` も更新します。本番で繰り返す前に、ログイン、指定鍵の metadata／canary、更新の成功を要求します。新しい AppRole client とサービス世代はテスト組立で実行済みですが、環境固有の SecretID 交換と更新の準備完了を示すものではありません。
4. 採用に成功した後、管理者が accessor を使って古い SecretID を無効化し、必要に応じて古い client token を別途失効させます。SecretID の破棄はそれを使う今後のログインを止めますが、すでに発行された token 自体は失効させません。資格情報の漏えいが疑われる場合は速やかに失効させ、Vault に依存する操作が利用不可になることを受け入れてください。停止回避だけを理由にアクセスを残してはいけません。
5. 採用に失敗したら切替を止め、許可されたデプロイ設定を復元するか新しい資格情報を発行します。古い SecretID に使用可能回数が残っている、または失効した token を更新できるとは考えないでください。

<a id="vault-actions"></a>
### 14.5 四つの操作と二つの異なるローテーション

| 操作 | Vault リクエスト | 効果と制約 |
| --- | --- | --- |
| DEK のラップ | `POST /v1/transit/encrypt/<key>` | base64 DEK と context を送り、`data.ciphertext` を読みます。KEK は Vault に留まります。 |
| DEK のアンラップ | `POST /v1/transit/decrypt/<key>` | 完全な暗号文と元の context を送り、`data.plaintext` をバックエンドの DEK にデコードします。 |
| リモート KEK バージョンのローテーション | `POST /v1/transit/keys/<key>/rotate` | 管理者の操作です。同名鍵の新バージョンを作成しますが、参照もデータベースのラップ行も変更しません。製品の AppRole は rotate できません。 |
| 同名鍵による古い暗号文の再ラップ | `POST /v1/transit/rewrap/<key>` | 応答に平文を含めず、新しい `data.ciphertext` を返します。provider はその値を返すだけで、データベースに保存しません。 |

[Transit API](https://developer.hashicorp.com/vault/api-docs/secret/transit) を参照してください。driver は既存の用途／バージョンの正規 AAD バイト列を、ちょうど 1 回 `context=base64(aad)` に符号化します。`context` は鍵導出の入力であり、AEAD の `associated_data` ではありません。この driver は後者を使用しません。decrypt と rewrap では元の context を保持します。完全な `vault:v<n>:` 暗号文がリモートバージョンを保持し、保存形式は `wk:2:vault:<base64(complete-transit-ciphertext)>` です。

リモートバージョンのローテーションと製品の KEK 参照交換は異なる手順です。リモート rotate だけでは、データベースのラップが新バージョンへ移ったことになりません。製品は同じ KeyRef を拒否するため、ウィザードをデータベース内のバージョン更新ツールには使えません。その更新エンドポイントは提供されていません。ラップ行を手作業で書き換えないでください。製品の DEK ローテーションはさらに別の操作で、Vault rotate の代わりにはなりません。

provider 層で別の鍵や provider から変換する場合は、元の unwrap の後に対象の encrypt を行います。ネイティブ Transit rewrap は同名鍵、同じ origin の場合だけです。サービスの再ラップ経路は既存のデータベーストランザクション内で、すでにキャッシュした DEK に対して対象の Wrap を呼びます。フルサービス handler の証拠と制限は §14.1 を参照してください。現行データや保管中のバックアップのラップが旧バージョンを必要とする間は、`min_decryption_version` を引き上げたり旧リモートバージョンを削除したりしないでください。Vault が旧バージョンを復号できても、本システムはローカルの KEK ラップ行の退役判定を適用します。

<a id="vault-migration"></a>
### 14.6 local→vault の操作手順

§14.1 を満たした後にのみ、まず隔離したフルサービス環境で実行します。以下は必要な操作と受入確認であり、本番移行を完了したという主張ではありません。

1. 他の鍵操作を止めます。整合したデータベースと必要なファイル／設定のバックアップを取得し、時点、アプリケーションイメージの digest／バージョン、schema バージョン、元の KEK の復旧方法、対象 Vault の origin／key と保持バージョンを記録します。秘密材料は別途保護します。基本の手順は[バックアップとリストア](./backup-and-restore.md)を参照し、§14.2 と §14.7 の Vault 固有条件も適用してください。
2. TLS、derived 対象鍵、権限を制限した AppRole を用意します。現行のローカルモード／材料を維持して Vault 設定を注入します。別発行のテスト用 SecretID でログイン、metadata、encrypt/decrypt、更新を確認し、デプロイ用 SecretID は利用可能な状態に保ちます。
3. そのリリースが対応する admin 再ラップウィザードで Vault を選び、正規参照だけを送信します。対象の事前検証が成功することを要求します。Vault の選択肢または client ownership の接続がなければ、現行 KEK を変えずに停止してください。
4. pending の対象ラップと元のラップが併存し、元の KEK で引き続きデータを読めることを要求します。復旧期間の判断が終わる前に、元の復旧材料を除去したり退役材料を消去したりしないでください。
5. §14.2 の対象設定へ変更し、ローカル `ENCRYPTION_KEY` を除去して、対応する手順で再起動します。現行の全代表行の実際のアンラップ、暗号文が変わらない既存データの読み取り、正しい台帳モード／参照、元のラップのソフト退役を要求します。参照の一致だけでは不十分です。
6. 観測した起動、ログイン、更新、監査の結果を記録します。サービス継続に依存する前に、隔離環境で Vault 到達不能時の動作とコールドスタートの拒否を演習してください。テスト組立では実 Vault への経路を切断しても、キャッシュ済みデータの暗号化／復号、再利用した HTTP 接続、新しい監査書き込みが継続し、Vault 必須操作とコールドアンシールが失敗しました。SSH／RDP セッションやデプロイ全体の継続性を示す結果ではありません。

<a id="vault-recovery"></a>
### 14.7 放棄とバックアップからの復旧

どちらの手順にも §14.1 のフルサービスの条件が必要です。隔離した Vault だけでは、製品のデータベース、ウィザードの放棄、リストアを演習できません。dev 検証環境を永続的な鍵バックアップとして使わないでください。

**切替前：**現行のローカル KEK と設定を維持します。未切替の pending 対象に限り、対応する admin 放棄操作（`DELETE /api/v1/keys/rewrap`）を使います。pending が収束し、現行データが引き続き読め、放棄対象が retired として記録されることを確認します。退役行を復活させてはいけません。放棄済みの委譲参照は、改めて事前検証と既存の現行参照・live 行・pending のガードを通ることを条件に、ウィザードで再送できます。放棄によってリモート鍵が永久に使用不能になるわけではありません。操作時刻と監査結果を記録します。未切替の操作を放棄するためだけに古いデータベースへ復元しないでください。実 Vault の handler 演習では、放棄 HTTP 200、pending がゼロ、ラップ材料を保持した `abandoned` 退役、ローカルの読み取り、監査記録を確認しました。業務書き込みは失われません。

**切替後：**バイナリだけを戻す、退役行のフラグを戻す、現行データベースに対して退役済みの元の KEK を再設定するといった操作をしないでください。承認された復旧環境で書き込みを止め、現在の証拠を保全してから、互換性のあるアプリケーションイメージと schema、関連ファイル、デプロイ設定で整合したバックアップ一式を復元します。[バックアップとリストア](./backup-and-restore.md)に従いますが、その AWS 資格情報の前提は Vault の AppRole 秘密情報には適用できません。バックアップが必要とする KEK を用意してください。切替前のバックアップには元のローカル材料、Vault のバックアップには同じ Vault origin／鍵名、必要な全リモートバージョン、有効な AppRole 資格情報が必要です。これはバックアップ全体の復旧であり、現行データベースの退役行を復活させる操作ではありません。書き込みを許可する前に、行のアンラップ、旧データの読み取り、台帳と監査の整合性を実際に確認してください。

選んだ復旧時点、実行ファイル／イメージと schema の互換性、設定／資格情報の保管、必要なリモート鍵バージョン、実際の読み取り結果を記録します。復元したデータベースの時点より後の書き込みはそのバックアップに含まれず、失われる可能性があります。関連ファイルと外部ストレージも同じ時点に照合します。新しいアプリケーションや一致した鍵ラベルは、互換性や復号可能性の証明になりません。必要な KEK バージョンや復旧可能なローカル材料を失った場合、認証資格情報だけではデータを復旧できません。以下の演習範囲はデプロイのバックアップ／リストアより限定的です。

**完了した隔離演習と制限：**`--case rollback --require-vault` は上記の未切替の放棄を行った後、別のフルサービス fixture を Vault に切り替え、**切替後の Vault バックアップ**を復旧時点として選びます。シールとクリーンアップの完了後、journal を閉じ、SQLite データベース全体（全テーブル）、seal journal、保護された設定を保存します。正確なテストバイナリ hash、schema hash、toolchain、時刻、正規参照、必要なリモートバージョンを記録します。サービスを再開して後続のデータを 1 行コミットし、再び書き込みを止め、現在のデータベース／journal を保全してから、新しいパスとサービス状態機械にバックアップを復元し、新しい AppRole 資格情報を発行します。アンシール前に行・監査・ファイルの一致を確認し、アンシール後に全 live 行を実際にアンラップし、旧暗号文の不変、読み取り、kms/vault 台帳を検証します。後続の 1 行は存在せず、復旧時点による損失を明示します。元の退役行は退役のままです。

同じテストバイナリと schema を使い、録画や外部ストレージは設定していません。[バックアップとリストア](./backup-and-restore.md)に記載されたデプロイの `pg_dump`／`pg_restore`／`tar` 演習**ではなく**、バージョン間の互換性、Vault ストレージの復元、切替前のローカルバックアップの復元も証明しません。これらには別のデプロイ証拠が必要で、SQLite の結果から推測してはいけません。実験が成功しても、切替前バックアップには復旧可能な元の材料を、Vault バックアップには必要なリモートバージョンを永続的に保持してください。

<a id="vault-protection"></a>
### 14.8 保護に関する主張と操作記録

driver の境界では、**KEK はバックエンドプロセスに入りませんが、DEK と認証資格情報はバックエンドに残ります**。パスワードの平文とセッションの通信内容もメモリに存在し得ます。メモリに平文がない、すべてのコピーが消去される、製品が HSM 等級の保護を提供するといった主張をしてはいけません。Vault のストレージや seal 保護のデプロイ上の選択は、そのような製品の主張を裏付けません。

操作記録は時刻、秘密でない参照、バージョン、ステータスコード、読み取り結果に限定します。token、role_id、secret_id、DEK、平文、秘密を含むリクエスト／応答本文を収集しないでください。フルサービスのテストでは実 Vault への経路切断中も、既存 HTTP 接続、新しい監査書き込み、キャッシュ済みデータ暗号処理を確認しました。SSH／RDP の継続性、本番 TLS、PostgreSQL や外部ストレージの復旧は証明していません。デプロイ側でそれらの依存関係を演習してください。
