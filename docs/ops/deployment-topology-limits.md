# Deployment Topology Limits

**English** | [繁體中文](../zh-TW/ops/deployment-topology-limits.md) | [日本語](../ja/ops/deployment-topology-limits.md) | [More languages →](../README.md)

> Applies to: Custodexa 1.0. The package deployment section applies from 1.13.0.

## Topologies supported in this release

**This release is a single-instance deployment: the whole system runs exactly one application instance.**

Running two or more application instances at the same time causes data problems. That topology is neither designed for nor verified, and must not be used in production.

**As of this release, a second application instance started against the same database is stopped and asked to confirm.** It halts before any write: it prints the lock holder's fingerprint and the two ways forward, and until it is acknowledged it opens no service path, does not run migrations, and does not write to the database. **The acknowledgement is given on the halt page that instance serves**, where an administrator signs off on the holder's confirmation code; setting `INSTANCE_GUARD_ACK` to that code is the scripted equivalent. Either way, every acknowledged start leaves an `audit_logs` event, a metric, and a persistent banner in the admin interface. **A start after acknowledgement leaves audit evidence.**

**The guard protects against acting unaware, not against the situation occurring.** Data problems caused by two instances coexisting after an acknowledgement are not prevented by the guard; they are owned by whoever acknowledged. What the guard guarantees is the halt, the notification, and the ability to prove afterwards from `audit_logs` which instance acknowledged, when, against which lock holder, and, when the halt page was used, under which administrator account. For reading the message and the recovery procedure, see [Deployment and Upgrade SOP §2.6b](./upgrade-sop.md#26b-if-the-backend-is-stopped-and-reports-that-the-single-instance-lock-is-held-by-another-database-session).

The following three architectures are specifically excluded:

- Two or more application instances behind a load balancer.
- Multi-replica deployments in which more than one instance runs at the same time: high-availability (HA) clusters, active-active, or a hot standby that is already running next to the active instance.
  **A cold standby is a different thing and is supported as a procedure**: with the database outside the application host (the external database overlay), a second host that is started only after the first one has stopped takes over against the same database, so that at any moment exactly one instance is active. The procedure, what the standby host needs in advance, and what a takeover does not preserve are in [Application Host Standby Takeover](./standby-takeover.md). The guard is the same in that shape; it is what stops the standby if the first instance turns out to be still running.
- Upgrading by rolling update; the switchover necessarily has the old and new instances coexisting.
  **A rolling update between guard-bearing releases is stopped on the new instance** (when the new instance takes the lock it sees the old instance holding it, and halts at the acknowledgement gate). The one upgrade from a release without the guard to this release is not stopped (the old release holds no lock), and depends on the checks in the upgrade SOP.

> This limit applies to the **application instance**. Running the database, guacd, and the frontend nginx as separate containers is the normal deployment shape and is not affected.

> **The guard only recognizes guard-bearing releases.** Older releases without the guard hold no lock: on the first upgrade from a release without the guard to this one, and on a rollback from this release to one without the guard, coexisting old and new instances are not stopped. Those two windows are covered by the "confirm the old instance has stopped" check in the upgrade SOP.

> **Connection pool mode.** The application must connect to postgres directly, or through a pool in session pooling mode. Transaction pooling lets the lock drift between sessions, and the guard will repeatedly report losing and retaking it. That topology is not supported.

## Package deployments and the management script

A deployment installed from the release package is operated by its management script,
`custodexa.sh`. What the script supports in this release:

- **Linux only**, on x86_64 or aarch64. On any other operating system it stops before doing
  anything and points to running from source for evaluation.
- **One deployment per host.** The containers have fixed names (`custodexa-backend` and so on),
  so a second deployment on the same host cannot coexist with the first. `install` refuses to run
  when it finds a deployment already there: a state file in the folder, a `custodexa-backend`
  container belonging to another folder, or a git working tree of the source.
- **The deployment folder path** may contain letters, digits and `. _ / -` only; it is written
  into `.env` and the state file without escaping. `install` checks this before writing anything.
- **One command at a time.** Commands that change the deployment take a lock on the folder; a
  second one started meanwhile stops with exit code 3. `status` takes no lock and changes nothing.
- **Compose is always called with the same project.** The script names the project `custodexa`,
  the deployment folder as the project directory and the compose files of the current release.
  `install` also writes `COMPOSE_FILE` and `COMPOSE_PROJECT_NAME` into `.env`, so `docker compose
  ps` or `logs` typed in the deployment folder reach the same services. `up` and `config` typed
  by hand also need `--project-directory .`; without it they look for `.env` in the wrong place and
  stop without touching any container.
- **Upgrades and backups go through the script as well.** `upgrade` stops the service, backs it up
  and switches to the new release; `backup` takes the same stopped backup on its own. Neither is a
  rolling update. `rollback` points the deployment back to the previous release when the new
  version has not changed the database; otherwise, including when it cannot read the database
  (with an external database, when no database client can be chosen on this host), it changes
  nothing and prints the `restore` command or the manual procedure to use instead; a restore replaces
  everything recorded after its backup (see
  [Backup and Restore §5.1](./backup-and-restore.md#51-going-back-to-the-previous-version-after-an-upgrade-by-the-management-script)).
  See the [upgrade SOP](./upgrade-sop.md#upgrading-with-the-management-script) and
  [Backup and Restore §3.8](./backup-and-restore.md#38-backups-taken-by-the-management-script-package-deployments).
  An older git clone deployment is refused by every `custodexa.sh` entry before files or services change. Plan a [manual migration](./upgrade-sop.md#manual-migration-of-an-older-source-deployment) or install in a separate clean directory and restore by hand; the script does not convert the old tree. `--images-from source` builds only the package's own images locally after checking their source checksum. Upstream images and build dependencies still have to be obtained, so this is not a fully offline option.

### Folder layout

The package unpacks to `custodexa/`, which is the deployment folder. After `install`, with the
default `DATA_PATH`:

```
custodexa/
  custodexa.sh -> current/custodexa.sh   the management script
  current -> releases/<version>          the running release
  releases/<version>/                    one release as shipped: the script, the compose files,
                                         MANIFEST.json, VERSION, .env.example, reverse-proxy/,
                                         source/; install adds images.env and image-ids.env
  .env                                   settings and secrets (mode 600)
  state.json                             what is installed, written only by the script
  logs/                                  one log per command that changed something (mode 700);
                                         secret values from .env are never written to it
  backups/custodexa-backup-<version>-<timestamp>.tar
                                         a backup taken with `backup`: one file (.tar.enc when
                                         encrypted) and its .sha256, mode 600; secrets included.
                                         While it is built, its parts are in
                                         backups/.partial-<timestamp>/ (mode 700)
  backups/<timestamp>/                   the backup an upgrade takes: a folder (mode 700;
                                         secrets included)
  tls/                                   certificates of the built-in TLS proxy
  restore/<timestamp>-<suffix>/          working folder of one `restore` run (mode 700)
  data/postgres/                         the database (bundled database only)
  data/recordings/                       session recordings (owner 1000, group 0, mode 2770)
  data/audit/                            audit log files
  data/exports/                          artifacts of asynchronous exports
```

Everything the deployment keeps between versions is at the top of the folder (`.env`,
`state.json`, `tls/`, `data/`, `backups/`); a release under `releases/` holds what was shipped plus the image
references `install` recorded for it.

`data/exports/` is kept across container rebuilds but is **not covered by backups**: evidence
package artifacts in it hold decrypted plaintext. Exclude it from any backup that copies the whole
of `DATA_PATH`; see [Backup and Restore §2](./backup-and-restore.md#2-where-persistent-data-lives).

`restore` also leaves two kinds of folders behind; once a restore has started, the script deletes neither. The first is the working folder under `restore/`, created for each run (mode 700). While a run is going the working folder holds plaintext copies of the database, `.env` and the archives, and needs about 1.1 times the size of the backup file on the file system of the deployment folder. When the restore finishes, those copies are removed; what stays is small: the list of recordings the database knows about but this host does not have, and the copies of `state.json` and `.env` from before the restore (secrets included, mode 600). A restore that stopped partway keeps the whole folder, because `restore --resume`, `--revert` and `--abandon` read from it: leave it until the restore is finished or given up. After that, the folder can be deleted. A run refused before any service is stopped leaves nothing behind: it removes the working folder it created. With an external database, the working folder also holds the SQL text of the import while it runs, about the size of the database uncompressed, and keeps the list of skipped grants (`skipped-grants.txt`) when grants were skipped. On a new host whose external database already held data, it keeps the safety export `safety-db.dump`, a plaintext copy of that database, even after the restore finishes; only a finished `restore --revert` deletes it, so delete it yourself once you no longer need it.

The second kind is the data a restore replaced. The current database and audit files under `DATA_PATH`, and `tls/`, are renamed `postgres.before-restore-<timestamp>`, `audit.before-restore-<timestamp>` and `tls.before-restore-<timestamp>` and kept in place, so each needs as much space as the data it was renamed from, until you remove it. A restore that goes back leaves the data it had put in place as `*.partial-restore-<timestamp>`, and one that is given up on a new host leaves `*.abandoned-<timestamp>` (plan for the same space). They hold the full previous contents, secrets and recorded evidence included, so keep them with the same access rules as the live data. Delete them yourself once the checks in [Backup and Restore §6](./backup-and-restore.md#6-post-restore-verification-checklist) have passed and you no longer need to go back; the safety backup under `backups/` is a separate file with its own retention. With an external database there is no `postgres` folder to rename: the database is emptied and imported in place on its server, and what it held before is in the safety backup, or on a new host in the safety export. The steps are in [Backup and Restore §5](./backup-and-restore.md#5-restore-procedure).

`state.json` is read line by line against one fixed format. If it is damaged, the commands that
read it, `status` included, stop with exit code 5, name the line, and point at the previous copy,
`state.json.prev`, kept next to it.

## What the product's roles do not reach: the host

Roles and permissions in the product govern what people do through its interface and its API. They do not reach the host the product runs on. Whoever can act as root on the host, use Docker there, read or edit `.env`, or connect to the database with its credentials is outside that model, whatever role the person holds in the product:

- **The management script** runs on the host with root privileges, as every procedure shows (`sudo`), and asks for no sign-in to the product. Backup, restore, upgrade, going back and the other commands are open to anyone who can run it. A role in the product gives no right on the host: an administrator role limited to some nodes does not give a person the right to run the script, and the script checks no product role. Anyone who is also given root or Docker access on the host can run every command of the script against the whole deployment, whatever role that person holds in the product. Give host access only to people who are meant to hold the whole system.
- **`.env`** holds the secrets and the settings the services start with, and whoever edits it changes how they run. The audit switch `FEATURE_AUDIT_LOG_ENABLED` is held on in release mode, the mode the shipped compose files set, and the startup log names it when a `false` is overridden. The mode and the compose files are on the host as well, so this is not a control against whoever runs the host.
- **Changes made directly in the database** to role assignments, group memberships or external group mappings are not blocked. They are detected after the fact: the permission state is compared with the changes the application recorded, during checkpoint verification, at checkpoint sealing and before token issuance. Each recorded change carries an integrity code computed with the same integrity key as the audit log; a record without a valid code counts as an unrecorded change, and so does a confirmation without one. A difference opens a `principal_state_integrity` failure event for the item `permission_state`, with the identifiers that differ and a notification. It stays open until the state matches again or a super administrator confirms it, with a reason, on the failure events tab of the audit log page. The confirmation is written to the audit log, changes no permission and blocks nothing. The comparison works only once the permission attestation is active: it starts with the first checkpoint that carries one, normally the first seal after the upgrade to 1.18.0, and a change made before that is not reported. After that, a comparison that cannot be completed (for instance because change records are missing or fail verification) opens a failure event for the same item and is shown on the checkpoint verification page; while it lasts, later direct changes cannot be detected. Neither sealing further checkpoints nor retention trimming ends that state: whether a checkpoint is a trusted starting point is recorded inside its own signature, and a checkpoint sealed while the comparison cannot be completed is never one. Trimming does not change that, because the signed trim record carries forward whether the trimmed checkpoints held an attestation or failed verification. A super administrator can confirm that event to reset the comparison to the current state: the reason, a summary of why the comparison failed and, when a trusted reference point exists, the differences between it and the current state (counts and up to 20 identifiers) are written to the audit log, and the damaged records are kept. A reset accepts the whole current state; it does not establish where earlier unverified records came from. The permission attestation is part of each checkpoint's signed content: removing or altering it on any checkpoint, the newest included, makes that checkpoint fail verification and raises the chain structure alert. If the failure event for this item is deleted or closed directly in the database, the next comparison opens it again and sends a new notification; until then it is missing from the failure events tab. The following limits remain. Someone who holds both database access and the integrity key or the checkpoint signing key can write records that pass verification. Change records written after the last checkpoint seal can be removed together with the changes they describe without the comparison reporting it. If all the evidence kept on the host since the attestation became active is deleted (every checkpoint sealed since then, the trim records in between and all change records), the next seal takes the state at that moment as a new starting point and the comparison reports a match. The same holds when the permission tables, the checkpoints, the trim records and the change records are put back to an earlier consistent copy, even if the rest of the database is left as it is. Both can only be told apart with the copies kept outside the host (next paragraph). If the stored content of the newest checkpoint is partly cleared, sealing stops and the failure stays open; a super administrator's reset does not repair it, and recovery means restoring a trusted backup.
- **A person who may set secrets on managed hosts can choose a value only they know.** Declaring a new secret and detaching a host with a custom secret are recorded in the audit log and raise an alert, and nothing blocks them. The person can then connect to the host directly, without going through this platform. Give those permissions only to people who may hold that access to the hosts in their scope ([Rotating the Platform's Own Privileged Credentials §13.7](./privileged-credential-rotation.md#137-who-may-do-this-and-what-happens-when-permission-is-lost)).
- **Restoring a backup** is a host operation. It brings back the permissions of the backup point, including assignments revoked since. The new restore generation ends the sign-ins and tokens issued before the restore, but it does not reconstruct what changed after the backup ([Backup and Restore §5](./backup-and-restore.md#restoring-with-restore)).

Someone who controls the host can replace the program, the secrets or the whole database, including with an older copy of it. Nothing in the product prevents that. Plan for it with access control on the host and with copies of the evidence outside it: syslog forwarding of the audit records and offsite storage.

## Roles and what each one manages

A person's access to the console comes from the roles assigned to them. A role decides which pages the person sees and what they can change there. **Management rights do not automatically grant connection rights within the platform**: for the Asset Admin and Authorization Admin roles and other management permissions, whether someone can connect to a host is decided by connection grants, not by the management role. The built-in Super Admin is the exception and keeps a connection exemption that needs no separate connection grant.

| Built-in role | What it manages | Can be limited to nodes |
|---|---|---|
| Administrator (super administrator) | Everything, including role definitions; only a super administrator can create, change, copy and delete custom roles. | No |
| Asset administrator | Assets, node (asset group) management, asset tests, the credential library and its credential changes (secret setting, rotation, conversion of scope, detaching, binding), and credential change plans. It does not include authorization rules, per-asset access policy or approval scopes. | Yes |
| Authorization administrator | Authorization rules, approval scopes and per-asset access policy. It does not include asset viewing, user management or user group management. | Yes |
| Identity administrator | Users, user groups and role assignment; see the next section for what it cannot assign. | No |
| System security administrator | Security settings, alerts and notification channels. | No |
| Auditor | Read-only audit duties, sign-off of daily reviews, and viewing of access reviews. Signing off an access review requires the separate permission `accessreview:manage`, which this role does not hold. | No |
| Approver | Approves connection requests within the approval scopes assigned to the person. | Only takes effect system-wide (below) |
| User | The workspace and the person's own connections and requests. | Only takes effect system-wide (below) |

Built-in roles cannot be changed. The asset administrator and authorization administrator roles are locked templates: after the upgrade nobody holds them until someone assigns them.

**The built-in user and approver roles take effect only when assigned to the whole system. If one is limited to some nodes, it gives no permission; the system saves the assignment as sent and shows a notice.**

### Limiting a role to nodes

- A role is limited to nodes when it is **assigned**, to a user or a user group; the role itself has no node setting. The same role can be assigned system-wide to one person and limited to nodes for another. Details of what a holder with a limited scope can and cannot do are in the sections on managing nodes, assets, authorization rules, shared credentials and per-asset connection policy below; the points that the product only records and does not prevent (moving assets or nodes, changing a shared credential used outside the scope, lowering a per-asset policy, setting a known password, redirecting an asset's address, two people acting together) are described in those sections, in the section on the host above, in the section on the identity administrator role and in the section on the SSH host key.
- External directory groups cannot be mapped directly to the asset administrator or authorization administrator role. Map the external group to a user group and assign the role, limited to nodes, to that user group.
- An assignment limited to nodes never widens to the whole system: when none of the nodes it names exist, it gives no permission. A node that an assignment names cannot be deleted while the assignment exists (see "Managing nodes within a limited scope").
- A custom role can be limited to nodes only when every function in it supports node limits; a custom role that also contains a function that applies only to the whole system can be assigned only to the whole system.
- A custom role with an empty permission set can still be assigned with nodes, but the nodes have no effect: the response lists it under `node_range_no_effect` and the web console shows a notice. A custom role that holds any permission that applies only system-wide, or whose node limits are not yet implemented, is rejected when assigned with nodes.
- The identity administrator can assign every role other than the super administrator role, the system security administrator role and custom roles that include a high-risk permission, which only a super administrator can assign; see the next section.

## Who to give the identity administrator role: what it can reach and what the product only reports

**The identity administrator and the system security administrator are locked role templates: their permissions cannot be changed, and they are assigned like other roles.** After the upgrade nobody holds them until someone assigns them, directly on an account (the Roles and scope tab of the account), through a user group, or through an external group mapping ([Deployment and Upgrade SOP](./upgrade-sop.md#upgrading-to-1180-the-permission-model-migration)). The form that creates an account offers only the roles that existed before the upgrade, so assign the templates after the account exists. The role management page lists both templates as built in and not changeable. The limits below, on super administrator accounts and on assigning the super administrator and system security administrator roles, apply on each of these paths.

The identity administrator is a role for IT or SRE staff who manage accounts and assign roles. It is not a limited role. A holder can give any role other than the protected roles described below to anyone, themselves included, and can add people to groups that carry connection grants, so in practice the holder can reach nearly every permission other than those of the protected roles. Give it only to people trusted at a level close to a super administrator.

- **What the role cannot do alone.** Assigning or removing the super administrator role or the system security administrator role, on an account or on a user group, changing the members of a group that carries either of them, and deleting such a group, are limited to a super administrator. A custom role that includes any high-risk permission is a protected role in the same way. The high-risk permissions are those that can delete evidence, turn off or redirect alerts, relax security controls, or manage keys: deleting recordings (`recording:delete`), managing system alerts, alert rules, notification channels and syslog forwarding (`systemalert:manage`, `alertrule:manage`, `notification_channel:manage`, `syslog:manage`), managing security policies and policy groups (`securitypolicy:manage`, `policygroup:manage`), and managing keys and offsite storage (`key:manage`, `offsite:manage`). For such a role, assigning or removing it, changing the members of a group that carries it, and deleting such a group are limited to a super administrator. Setting a password, turning off multi-factor authentication, binding an external identity or writing a direct role on a super administrator account is also limited to a super administrator. Disabling, deleting or enabling an account that holds either of those two roles, from any source, and unbinding an external identity together with disabling the account, are limited to a super administrator as well; a refused request is recorded in the audit log with its reason. Other operations on such an account, such as unbinding an external identity alone, editing its profile or clearing a sign-in lockout, follow the ordinary rules.
- **Some operations on a system security administrator's account are not blocked for an identity administrator.** Disabling, deleting or enabling that account is refused, as described above, but an identity administrator can set its password, turn off its multi-factor authentication, or bind or unbind an external identity, and the product does not stop it. Each such operation is written to the audit log in the same transaction and raises a system alert for the security staff. This is detection after the fact. Separation of duties between the two roles therefore holds only if the identity administrator is trusted to the same degree. Decide who holds the system security administrator role when you deploy. The product does not stop one person from holding both roles: the role assignment preview request (`POST /api/v1/role-assignment-previews`) reports the combination, but an assignment does not require a preview and is not blocked.
- **Granting is reported, not blocked.** Before a role assignment or a group change is saved, a preview request reports when the combined permissions of the people affected form a risky combination. The report is a hint and does not stop the change. After the change, a change to a person's own grants raises a system alert, and so does a grant of a management-level role to someone else. Handing an ordinary role to someone else, or adding someone to a group that carries only connection grants, raises no alert and appears only in the general audit log. Two people acting together are not covered by any of this.

## Managing nodes within a limited scope: what a move can change and what only a super administrator can do

A role that includes node management can be assigned for some nodes only. A holder can then create, rename, describe, move and delete nodes inside those nodes and their sub-trees, and only there. The limits below describe what the product enforces and what it only records.

- **Moving nodes or assets can change who is covered, and the product does not block it.** Management scope and connection grants are separate. A person who holds both for the same part of the tree can move a node, or the assets under it, into a node on which that person already holds a connection grant, and widen their own connection reach that way. A move can also take assets out of the reach of other people's connection grants and review scopes. The product does not block either case. The audit entry of each node move lists the assets that gained or lost coverage and the grants, review scopes and management scopes that were affected, as identifiers only, with up to 100 entries per list and a total count. Review that record when a person holds both permissions for the same nodes.
- **A node that a management scope refers to cannot be deleted, by anyone.** If any role assignment, on an account or on a user group, uses the node as a scope node, deleting it is refused with `RULE_NODE_SCOPE_REFERENCED`, super administrators included. A super administrator receives the list of referring assignments (who, which role, and for a group its member count) and a link to each account or group page to change it. Every other holder receives only the number of assignments, not who holds them. The check counts the assignment records themselves, so an assignment held by a disabled account still blocks the deletion.
- **Some node actions are limited to a super administrator.** Renaming, describing or deleting a node that is itself the root of the holder's scope is refused with a 403. So is creating a node at the top level, and moving a node to the top level. Moving a node is allowed only for a node strictly below the holder's scope root, and any move of a sub-tree that contains a node used as a scope node by any assignment is limited to a super administrator. A holder of node management without a scope limit, that is, on all nodes, is bound only by the last of these rules and by the structural checks (depth, same-name, loops).
- **Nodes outside the scope cannot be acted on.** For a holder with a limited scope, a request that acts on a node outside the scope, or on a node that was deleted, returns the same 404 response as a node that never existed. The tree and list responses carry the nodes in the holder's management scope and the nodes that hold assets the holder has a connection grant for. The path above those nodes is included only to show where they sit: path nodes outside the scope are marked as path only and cannot be acted on.
- **Removing a node's scope usage is a separate step.** Deleting a node is refused while an assignment uses it, so the assignment must be changed first, on the account or group page. The product does not remove assignments as a side effect of a node deletion.
- **The owner node of a shared credential follows the scope.** When a holder limited to some nodes creates a shared credential, converts a credential to shared, or changes its owner, only nodes within that holder's scope can be chosen; see the section on shared credentials below. This section covers node management only; limiting asset creation and editing to some nodes is described in the next section.

## Managing assets within a limited scope: what it does not grant, and what the product only records

A role that includes asset management can be assigned for some nodes only. A holder can then see, edit, test, disable and delete the assets attached to those nodes, and manage their accounts, within that scope. The limits below describe what the product enforces and what it only records.

- **Managing an asset does not grant a connection to it through the platform.** Management scope and connection grants are separate. A person who may edit or delete an asset can open a session to it only if a connection grant also covers that person. In the asset list, an asset that is visible only through management scope is shown as not authorized for connection and has no connection entry. Management scope says nothing about the host itself either; see the section on the host above.
- **Creating an asset or changing the nodes it is attached to can change who is covered, and the product only records it.** A person who holds both a management scope and a connection grant for the same part of the tree can attach an asset to a node that person already holds a connection grant on, and widen their own connection reach that way. Attaching can also bring an asset under other people's connection grants and review scopes. The product does not block these cases. The audit entry written for an asset's initial attachment and for each change of its nodes lists the nodes added and removed, and the people and the management scopes that gained or lost coverage because of it, as identifiers only, with up to 100 entries per list and a total count. This applies to every actor. Assets created through batch import carry this record on their initial attachment only when every assignment through which the person holds the asset creation permission is limited to some nodes. Review the record when a person holds both permissions for the same nodes.
- **Changing an asset's address can send its stored credential elsewhere, and the product only reports it.** A person who may edit an asset can point its host or port at another machine, including one that person controls. Subsequent connection attempts use the new address. If the applicable checks allow authentication to proceed, the platform authenticates to the server at that address using the asset's stored credential. Connection tests require the asset test permission (`asset:test`), not a connection grant; whether they authenticate depends on the protocol, as described below. A database connection test only opens a TCP connection and sends no credential. Changing the host, port or protocol raises the `asset_address_changed` system alert in the same transaction as the change, whoever makes it, and turning off RDP certificate verification, lowering a database TLS mode or setting Kubernetes to skip verification raises `transport_verification_relaxed`. Both let the security staff find out afterwards; neither stops the change or the credential from being sent. A person who holds both a management scope and a connection grant for the same asset can carry out the whole sequence alone. Grant asset editing with the same care as the stored credentials of the assets in the scope. How much the platform checks the other side at the new address depends on the protocol and the asset's settings:
  - **SSH.** The presented host key is compared with the key recorded for the asset, whatever the address. If the asset has a recorded key and is not awaiting a new key after a reset, a different fingerprint is a mismatch. After the check and mismatch records succeed, user terminal sessions, file transfer and connection tests proceed to authentication, while credential changes and rotations stop (see "When an SSH host key does not match the record"). A different machine using the same host key is not identified as a mismatch by this comparison. When the asset has no record yet, the key is compared with a record that another asset holds for the new address; when there is none either, the key is recorded on first use and the connection goes on without a warning. Password authentication then gives the password to that machine; public-key authentication does not send the private key.
  - **RDP.** The server certificate is not verified unless certificate verification is turned on for the asset (`rdp_verify_cert`, off by default). A connection test of an RDP asset does not verify it even when that setting is on.
  - **VNC.** Nothing checks the identity of the server.
  - **Databases.** The server certificate is checked only when the asset's TLS mode is `verify-ca` or `verify-full`. With the mode left unset, or set to `disable` or `require`, nothing checks who answers at the new address.
  - **Kubernetes.** The API server certificate is verified, against the CA set on the asset or the system's trusted certificate authorities, unless the asset is set to skip verification (`k8s_insecure_skip_tls`).
- **An asset that is also attached outside the holder's scope cannot be deleted or disabled by that holder.** The request is refused with `RULE_ASSET_HAS_OUT_OF_SCOPE_NODES` (409), which carries only the number of nodes outside the scope. The holder can remove the asset from the nodes in their own scope; after that it is out of their reach. A person with a global assignment of the permission is not affected by this rule.
- **Ungrouped assets.** For an asset attached to no node, a person who holds the deletion or disabling permission through a global assignment can delete or disable it as before, and the action is audited as before. A person who holds the permission only through an assignment to some nodes receives the same 404 as for an asset that does not exist.
- **For assets seen through the management scope, nodes outside the scope are not shown.** For a holder with a limited scope, the list and detail of an asset the holder sees through that scope show only the nodes within the scope and the number of attachments outside it. An asset the holder sees only through a connection grant shows its nodes as before. The response to creating or editing an asset follows the same rule. For an asset the holder can create or edit through a global assignment but sees neither through the scope nor through a connection grant, the response carries only the number of attachments outside the scope. Saving an asset keeps the attachments the holder cannot see.
- **Batch actions on assets have no item-count limit.** The backend does not cap how many assets one batch move, tag or delete request may name. The request body is still bound by the body size limit of the built-in frontend proxy (1 MiB by default, on the order of a hundred thousand asset IDs); a larger request is rejected with 413 before it reaches the backend. The whole batch runs in a single transaction, so the time it takes grows with the number of assets, and while it runs, other topology-related writes that happen at the same time are slower. The product does not block a large batch by count and does not state a duration; split a very large batch if that matters for your deployment.
- **Built-in roles.** The built-in general user and approver roles take effect only when assigned to the whole system. If one of them is limited to some nodes, in a direct assignment to a user that passes the other assignment checks the product saves it as sent, but it grants no permission, and the response lists it under `node_range_no_effect` and the web console shows a notice on that role. The approver role still cannot be assigned to a user group. The super administrator and auditor roles include permissions that can only apply to the whole system, so they cannot be limited to nodes and the request is refused. The asset administrator and authorization administrator templates are designed for assignment to some nodes (see "Roles and what each one manages").

## Managing authorization rules within a limited scope: what the scope covers, and the limits of the self-grant check

When an assignment of the authorization rule permission (`authorization:manage`) is limited to some nodes, the holder can create, adjust and delete authorization rules only for assets and nodes inside the scope. The limits below describe what the product enforces and what it does not cover.

- **The scope limits the object of a rule, not the subject.** Users, user groups and agents are not tied to nodes, so a holder with a limited scope can name any existing account or group as the subject of a rule on an asset or node inside the scope. The pickers the authorization pages use return a fixed set of fields only (for an account: ID, sign-in name, display name, kind, status and role names; for a group: name, description and member count), not an email address, sign-in history or other account detail, and they do not give the ability to open the account pages or to write to an account. The identifier they return is the value a rule uses to refer to that account or group.
- **A request outside the scope receives the same answer as one for something that does not exist.** A request that names an asset or node outside the scope, or a rule whose object is outside it, returns the same response as for an asset, node or rule that does not exist: a 404 for writes and single lookups, an empty result for list and picker filters. A batch request from a holder with a limited scope is refused as a whole, with nothing written, when any object in it is outside the scope or does not exist; the response carries only the number of objects that could not be used. A holder with no scope limit receives the existing responses.
- **The rule list does not show every rule that reaches an asset in the scope.** For a holder with a limited scope, the list carries the rules whose object is in the scope. A rule attached to a node above the scope, which also covers assets inside the scope, is not listed and cannot be changed by that holder. The two effective-access views still list everyone who can reach an asset in the scope, including through such rules. In those views the rule identifier is left out whenever the rule is not in the holder's list. A node that is an ancestor of the scope is shown with its name and path, only to locate the scope. For a path that runs through any other node outside the scope, the response leaves out the node name and path and carries only the number of attachments outside the scope. A holder can therefore see that someone has access to an asset in the scope without being able to see or remove the rule that gives it.
- **Changing the account scope of a rule no longer needs a super administrator.** A holder of the permission can narrow the account scope of a rule inside the scope. Widening it is limited to the person who created the rule and to a super administrator. A rule whose subject is the holder, a group the holder belongs to, or an agent the holder owns cannot be adjusted by that holder. The account scope of a temporary grant cannot be changed, and a temporary grant that is linked to a request cannot be deleted directly.
- **The self-grant check applies when a rule is created or adjusted, and only then.** The check refuses a rule whose subject is the operator, a group the operator belongs to, or an agent the operator owns, and a super administrator is exempt. It does not look again later: a rule that was created for a group is not reconsidered when a member joins that group afterwards. It does not look at two people either. If two holders each create a rule for the other, the product accepts both. Treat these as limits of the check and review who holds the permission and the audit log accordingly.
- **Revoking a temporary grant is open to a holder whose scope covers every asset affected.** In addition to a super administrator, the original approver and a reviewer whose scope matches, a holder of the permission can revoke a temporary connection grant when every asset the revocation changes is inside the holder's scope. A holder whose assignment has no scope limit covers every asset, so a non-super-administrator who holds the permission globally (through a custom role, for example) can revoke any temporary grant in this release. When revoking a whole request, the assets include those of pending items that the revocation closes as well. If any of them is outside the scope, this route does not apply and the existing rules decide. An agent account does not gain the ability through this permission. A holder who qualifies through none of these routes is refused with a 403.
- **Every revocation writes two audit entries of its own.** The revocation and its audit entry are saved in one transaction, and the revocation is not saved if the entry cannot be written. After the transaction commits and the sessions are closed, a second entry of the same action records which sessions were ended. If the second entry cannot be written, only a log line is made and the revocation stands. This applies to every revocation, a super administrator's included. The request log that every authenticated API call produces comes in addition, so one revocation made through the API leaves three entries with the same action.
- **How to assign it for some nodes.** An assignment of this permission (`authorization:manage`) limited to some nodes is written through the two whole-set replacement endpoints for role assignment, `PUT /users/:id/roles` and `PUT /user-groups/:id/role-bindings`, using the `role_nodes` field (see the API specification). In the web console you choose the nodes on the Roles and scope tab of a user or a user group, by setting the role to specific nodes; the tab shows an estimated count of the assets in the asset list's management scope that the selection gives; it is not the number of assets the role's every operation can act on. The built-in authorization administrator role includes this permission and can be assigned for some nodes. Limiting an assignment to some nodes limits where the permission applies; it does not grant a connection to the assets under those nodes. This section describes how the product treats an assignment that is limited to some nodes.

## Shared credentials within a limited scope: what the impact confirmation stops and what it does not

A shared credential is owned by Global or by one node, and an administrator whose role is assigned for some nodes only manages the shared credentials owned within that scope. A shared credential can still be attached to assets outside its owner's scope, so changing it can reach hosts that its administrator does not manage.

- **Correcting the registered secret of a shared credential, or rotating it, applies to every host it is attached to, including hosts outside the person's scope.** Correcting updates all attachments at once. Rotating changes the password on each attached host over a remote connection. To change only the hosts within your scope, detach each of them from the shared credential first; detaching changes that host's password and leaves it with a credential of its own.
- **The confirmation proves that the person was told; it does not stop the change.** Before either action, the person is shown how many attached hosts are within and outside their scope (counts only; the hosts outside are not named) and has to tick an acknowledgement. A person who ticks it can change the credential for the hosts outside their scope as well. The product does not present this as protection against someone who means to go beyond their scope; it only makes sure that the number of hosts outside the scope was returned to the person before the change is submitted. Treat the right to correct the secret of, or rotate, a shared credential as a right over every host it is attached to.
- **What the server does check.** The confirmation is kept on the server together with the set of hosts outside the person's scope at that moment. It is valid only for that person, that credential and that action, and it is used once. If, by the time the change is submitted, the set includes a host that was not in it when the confirmation was made, the request is refused with `RULE_CREDENTIAL_IMPACT_CONFIRMATION_REQUIRED` (409) and nothing is changed, even when the number of hosts is the same; if every host in the set was already in it, the change goes ahead. The confirmation has no expiry time.
- **What is recorded.** The audit entry of the change records the number of hosts outside the scope and the confirmation identifier.
- **What to do about it.** Grant `credential:set-secret` and `credential:rotate` with the same care as the right to log in to every host the credential is attached to, and keep a credential's attachments within the scope of the node that owns it when other administrators' hosts should not be reachable through it.

## Per-asset connection policy: who may change it, and what is only reported

An asset can carry its own connection policy (`open`, `reason` or `approval`) that overrides the deployment-wide default. Setting or clearing that override is a permission of its own, the access policy permission (`access_policy:manage`), in the authorization rules group. It is not part of asset editing: a role that can edit assets but does not hold it cannot send the field at all, and a request that includes `access_policy` (an empty string, which clears the override, included) is refused as a whole. The same holds for creating an asset with a non-empty value and for a batch import in which any row has one: the whole request or batch is refused and nothing is written. A holder can change only that field without any asset editing permission; a request that adds any other field needs asset editing as well. Holding the permission, for every node or for some, does not allow changing the deployment-wide default; only a holder of the security policy management permission (`securitypolicy:manage`) can change it. The built-in authorization administrator role includes the access policy permission and can be limited to nodes, and the built-in system security administrator role includes the security policy management permission. The super administrator holds both as part of the reserved identity; no other built-in role includes either of them.

- **Lowering the override is reported, not blocked.** When a change lowers an asset's effective level, whether by setting a lower override or by clearing an override so the asset follows a lower default, the change is written to the audit log in the same transaction and raises the `access_policy_relaxed` system alert, whoever makes it. A change that keeps or raises the level, and a newly created asset, raise no alert. The alert states the asset, the person, and the level before and after. If either record cannot be written, the change is not saved. A holder whose assignment is limited to some nodes is treated the same way for the assets in the scope.
- **Limitation.** A holder of the permission can lower an override, and if someone else has given a person a standing connection grant on that asset, that person can then connect without a review. The product keeps the audit entry and a system alert (the product has no way to delete it; it goes away only under the alert retention setting), and it blocks neither the lowering nor the connections that follow. Decide who holds this permission with that in mind.
- **An assignment limited to some nodes covers only the assets in the scope.** When an assignment of this permission is limited to some nodes, the holder can set or clear the override only on an asset attached to at least one node inside the scope. For an asset outside the scope, the request receives the same answer as for an asset that does not exist, and nothing is changed. Creating an asset with a non-empty override, or importing a batch in which a row has one, needs at least one of that asset's nodes inside the scope; otherwise the whole request or batch is refused in the same way as for a person who does not hold the permission. The list of assets with an override shows such a holder only the assets in the scope, and for an asset also attached to nodes outside the scope it lists only the nodes inside the scope. The full path of a listed node still includes the names of its ancestors for orientation, even when an ancestor is outside the scope. Other attachments outside the scope are given only as a number. The scope comes from the assignments of this permission alone: holding asset viewing, asset editing or a connection grant for other nodes does not widen it.
- **A person who holds only this permission has no complete web workflow for it.** For a person whose roles give this permission and asset viewing, and nothing more, the web console currently has no workflow that completes setting an override. Use the API.
- **How to assign it for some nodes.** An assignment of this permission (`access_policy:manage`) limited to some nodes is written through the two whole-set replacement endpoints for role assignment, `PUT /users/:id/roles` and `PUT /user-groups/:id/role-bindings`, using the `role_nodes` field (see the API specification). In the web console you choose the nodes on the Roles and scope tab of a user or a user group, by setting the role to specific nodes; the tab shows an estimated count of the assets in the asset list's management scope that the selection gives; it is not the number of assets the role's every operation can act on. The built-in authorization administrator role includes this permission and can be assigned for some nodes. Limiting an assignment to some nodes limits where the permission applies; it does not grant a connection to the assets under those nodes. This section describes how the product treats an assignment that is limited to some nodes.

## Keeping sign-in state when the service is exposed over plain HTTP

**A deployment still exposed over http must turn off the security policy "Keep sign-in only on https connections."** Sign-in state is kept in a single HttpOnly cookie, and while that policy key is at its default (on), the browser only stores and returns it over an https connection; over plain http it is never stored at all. Users can still sign in, but reloading the page, opening a new tab, or closing a tab and coming back all return to the sign-in page; nothing usable for restoring the session was left on the browser side (the access token exists only in the page's runtime memory and is never written to browser storage).

How to recognize it: pressing reload after signing in asks for sign-in again, and the sign-in page itself explains why. There are two responses. The correct one is to configure https on the public entry point; until then, turning that key off in the security policy restores normal sign-in persistence, at the cost of the credential for the sign-in state travelling over an unencrypted connection. That is the same order of risk as running the whole deployment over http, not an additional risk, but it should not become a long-term state either.

## Roles granted from an external identity source: when a change there takes effect

Roles and user group memberships that come from an external directory or identity provider are recomputed **at sign-in, from the group information that sign-in carried**. The security policy "Group mapping revalidation limit" (`mapping_revalidation_hours`: whole hours, 12 by default, 0 or 1 to 168, where 0 means no limit) bounds two things: how long a web session lasts for an account that holds a grant from a mapping, and how long ago the account's groups may last have been read for a sign-in that cannot read them to keep those grants. The session is counted from its own sign-in, and the age of the last reading is checked only at sign-in, so the limit on its own is not the time within which a removal at the source takes effect. Each sign-in recomputes mappings only for the source used for that sign-in. If the account can sign in through another bound source, grants from the original source may remain usable without the bound described here. The estimates below assume that subsequent sign-ins use the same mapping source, the limit is positive, and the policies are not relaxed. The points below give the bounds under those assumptions, including the worst case, and matter whenever the deployment relies on the external source to take an access right away.

- **With the limit set (not 0), a web session lasts at most the limit, counted from its own sign-in.** An account that holds any grant from a mapping, a role or a user group membership through any source, gets a web session no longer than the limit, or than the security policy "Web session max hours" when that is shorter (called the session length below), counted from the sign-in that opened it; renewing the session does not extend it. When that session ends, the person has to sign in again, and that sign-in recomputes the grants of the source it goes through from the groups it carries. Until then, a session that is already open keeps the roles it held. Under the assumptions above, if every group reading reflects the removal at that source, access therefore lasts at most about one session length after the removal: the session open at that moment ends, and the next sign-in through that source either recomputes the grants or is refused by the source. Accounts without a grant from a mapping follow "Web session max hours" alone.
- **A sign-in that cannot read the groups keeps the grants while the last reading is within the limit, and the session it opens runs its full length.** This covers a sign-in where the account's groups could not be read (the read failed, the value had an unexpected type, or the token said the list was too long to include), and a source that has an enabled rule but no group attribute or claim name set. If that channel last read the account's groups within the limit, the grants from its mappings are kept and the skipped recomputation is recorded in the audit log. If it last read them longer ago than the limit, or never, the roles and user group memberships given by that channel's mappings are withdrawn at that sign-in, and the audit log records `membership_revalidation_expired` with the channel, the limit and the time of the last reading. When that removes a permission, the account's other sign-ins end. When a later sign-in reads the groups, grants are recomputed from those groups and the current rules. Only grants supported by matching rules are given. Roles and memberships an administrator assigned, and grants through another source, are not affected. The age of the last reading is checked only at sign-in: a session opened by a sign-in that kept the grants is counted from that sign-in, not from the last reading, its renewals do not look at the reading again, and a sign-in that cannot read the groups does not count as a reading. The worst case is a removal made at the source just after the last reading, while the source still lets the person sign in but does not deliver the groups: if the person signs in just before the revalidation limit has elapsed since the last successful group reading, that sign-in keeps the existing mapped grants, and a session kept active then runs its full session length. Under the assumptions above, the mapped grants from that source can therefore stay usable for up to about the limit plus one session length after the last successful reading from that source, which is at most twice the limit; with the default limit of 12 hours and "Web session max hours" at 0 or at least 12, that is about 24 hours. To stop the account's web access sooner or with certainty, disable the account in this system, which ends its web sessions and token renewal at that moment (see the point below on disabling at the source). Reducing a nonzero limit shortens the observation retention window. The session length remains the shorter of that limit and "Web session max hours"; it does not change while "Web session max hours" remains shorter. Existing sessions apply the reduced cap when they renew.
- **Accounts that held grants from a mapping before the upgrade to 1.18.0 can lose them at their first sign-in after it.** The upgrade records its own moment as the last reading for those accounts, so the limit counts from the upgrade and the upgrade itself withdraws nothing ([Deployment and Upgrade SOP](./upgrade-sop.md#upgrading-to-1180-the-permission-model-migration)). An account whose first sign-in comes more than the limit after the upgrade, and whose groups that sign-in cannot read, loses its mapping grants at that sign-in. The accounts concerned are those whose source does not deliver their groups: typically an account in too many groups for the identity provider to put them in the token, or a source with rules but no group attribute or claim name. To recognize it, look for `membership_revalidation_expired` in the audit log for the account, with its roles from mappings gone. To correct it, have the source deliver the groups (set the group attribute or claim name, or reduce the groups the token has to carry), assign the roles directly, or set the limit to 0 and accept that mapping grants then have no upper bound.
- **With the limit set to 0 there is no upper bound for mapped grants.** A removal at the source then takes effect at the earlier of the person's next sign-in and the end of the web session under "Web session max hours", and a sign-in that cannot read the groups keeps the grants however old the last reading is. With "Web session max hours" also at 0, a session that stays active is never returned to sign-in on its own, and a change made at the source can wait indefinitely; a person removed at the source keeps the mapped permissions here until their next sign-in. A deployment that relies on source-side removal should not set the limit to 0. Making the limit longer, or setting it to 0, raises the `mapping_revalidation_relaxed` system alert with the old and new values; making it shorter, or changing it from 0 to a number, is only recorded in the audit log.
- **What the limit does not reach.** It ends web sessions and, with them, the opening of new connections; a protocol connection already open when the session reaches the limit is not closed by it. When a sign-in does recompute and a role is taken away, that account's other open sessions end at that moment. Withdrawing a role inside this system is a separate matter, and it ends those sessions at that moment in the same way.
- **Who is in a group mapped to a high-privilege role is decided at the source.** A mapping to the super administrator or system security administrator role, directly or through a user group that carries one of them, leaves the choice of who holds that role to whoever manages the group in the directory or identity provider. A person added to the group there gets the role at their next sign-in, without any super administrator acting in this system; that sign-in is recorded in the audit log with the roles it changed, and it raises no system alert. In this system, creating, changing, enabling, disabling or deleting such a mapping, and pinning such a role, are limited to a super administrator.
- **Disabling or deleting the account at the source is not synchronized into this system.** The account stays in the user list here, with the roles last computed for it. A new sign-in through that source fails, and an attempt to sign in with a local password is refused and recorded in the audit log. An existing browser session can still use those roles and refresh its access token until its session expires (for an account with grants from a mapping, at most the revalidation limit after it started, unless the limit is 0) or the account is disabled or its refresh tokens are revoked in this system.
- **Whether nested groups are included depends on the source.** This system uses the group information the sign-in gave it, and does not query the source again to walk the group chain upwards. A directory's group membership attribute commonly reports only the groups the account is a direct member of, so membership held through a parent group is not seen; an identity provider's group claim may instead already have nested groups expanded. Write the rules against what the source actually reports.
- **A role limited to some nodes that an external group also grants.** When a role limited to some nodes is held by an account both through an administrator's assignment and through an external group mapping, removing it under Administrator-assigned roles on the Roles and scope tab shows a notice on that role's row under Roles from mappings: an external group still grants the role, and removing it here makes it apply to the whole system. The notice asks for no confirmation and does not block saving. Once saved, the administrator's assignment and its node limit are gone, and the role that the mapping still grants applies to the whole system.

## Keep super administrators on local accounts

**Give the super administrator role to local accounts, assigned to them directly, not to accounts that sign in through a directory or an identity provider.** Whoever may manage identity sources can change a source's settings so that the directory or identity provider it then points to admits anyone who signs in through it, super administrators included. The product does not stop such a change. It records every creation, change (enabling, disabling and secret replacement included) and deletion of a source's settings in the audit log in the same transaction, and raises the `identity_source_changed` system alert, which lists the fields changed and states how many super administrators can currently sign in through that source, counting those who hold the role through a user group. The bind password and the client secret appear only as changed, never with their value. This is detection after the fact.

A local super administrator still signs in when a source has been taken over, and can set the source back; that is what keeps a takeover of a source from locking the system. The product refuses to take the last local super administrator away (an enabled account that signs in locally with a local password, is not managed by an external source, and holds the super administrator role assigned to it directly; holding the role only through a user group or a group mapping does not count), whether by disabling it, deleting it, removing the role or switching it to external sign-in. It does not create one for a deployment that has none: check that at least one exists, and keep its credentials where the people who may need them can reach them.

## System security alerts and notification channels

The product raises system security alerts about changes to its own security, in the same transaction as the change: among them changes of an identity source, changes to a person's own grants and grants of a management-level role to someone else, operations on a system security administrator's account, changes of an asset's address or a relaxation of its transport verification, secrets set by hand, a longer group mapping revalidation limit, and changes of notification channels. They are shown on the alerts page under their own source category, each with the delivery state per destination and, when one is recorded, the operation log entry it belongs to.

- **They cannot be deleted or turned off.** An alert record goes away only under the alert retention setting. The alert type catalog on the alerts page lists every type with its default and current severity. The only setting a type has is its severity, which holders of the system alert severity permission (`systemalert:manage`) can change; each change is recorded in the audit log in the same transaction. Neither the interface nor the API has a way to delete or disable a type.
- **Severity sets the order and the display, not whether an alert is raised or sent.** Every system security alert is queued at once for every enabled notification channel, whatever the channel's push threshold; the threshold filters only the other alerts. A type lowered to low is still raised and still sent, though it may then be handled later. With no enabled channel, nothing is queued and nothing is sent later; the alert is still forwarded to syslog when forwarding is configured.
- **Delivery is at least once, for up to 72 hours.** The delivery queue is kept in the database, so a restart does not lose it. A failed delivery is tried again at growing intervals, from 1 second up to 10 minutes apart. When 72 hours have passed since it was queued without success, it is marked abandoned: the alert's detail shows that and the server log records it, and there is no manual resend. A receiver can get the same alert more than once and should discard repeats by `delivery_id`, a random identifier given to each delivery when the alert is queued; it stays the same across retries and is not issued again after a restore, so the receiver's record of identifiers already seen stays valid. An enabled channel whose stored address or secret can no longer be decrypted does not stop the operation that raised the alert: the alert is still recorded and sent to the other channels, and that channel's delivery is marked abandoned at once, with zero attempts, in the alert's detail and in the server log. Each delivery uses the address and secret the channel had when the alert was queued; changing or deleting the channel afterwards does not change where an already queued alert goes.
- **Notification channels have a permission of their own, and every change of a channel reaches both its old and its new destination.** Managing channels, sending a test included, requires the notification channel permission (`notification_channel:manage`). The system security administrator role template includes it; the identity administrator template does not. Creating, changing, disabling, enabling or deleting a channel is recorded in the audit log in the same transaction and raises the `notification_channel_changed` alert, which is sent to the other enabled channels and also to the channel's own destination before and after the change: a channel moved to another address, disabled or deleted still sends one notice to where it pointed before. The channel is deleted in the same transaction, and the notice is sent from the queue afterwards.
- **Limitation: alerts about the actions of whoever manages the channels go where that person can send them.** A holder of the notification channel permission can change where alerts are delivered and then do something that raises an alert. The product does not stop this. What it provides is the notice of every channel change to the old and new destinations, and the audit records of the channel change and of the action. Decide who holds this permission with that in mind.

## Evidence retention, recording deletion and the settings that guard them

This section states what the product does about the retention of evidence, and about the actions that could remove it or hide it.

- **The four data retention settings have a floor.** The retention of the operation log, the command stream, alert records and recordings each accept 0, which keeps the data forever, or a number from 7 to 3650 days. Saving 1 to 6 is refused, and nothing in the batch it came with is applied. The checkpoint retention setting has no floor of its own; it stays bound by the rule that it may not be shorter than the data it vouches for. A value of 1 to 6 for recordings in the `RECORDING_RETENTION_DAYS` variable at a first start is ignored and the factory 90 days applies. A value of 1 to 6 written into the database directly is read back as the last valid value, or as the factory default when there is none.
- **Lowering a retention setting is reported, not blocked.** Lowering any of the four data settings, going from 0 (forever) to a number included, is written to the audit log in the same transaction as the change and raises a `retention_shortened` system alert. Raising a setting, or setting it to 0, is only audited. A change to checkpoint retention is only audited and raises no alert.
- **The block on a recording failure can be turned off.** With the policy `recording_failclose_enabled` on, anyone other than a super administrator cannot be issued a connection while the recording directory is not writable. It is off by default. Turning it from on to off is audited and raises a `recording_failclose_disabled` system alert; turning it on is only audited. With it off, connections go ahead when the recording directory is not writable, but the failure is still detected and reported: the pre-check and its alert do not depend on the setting, and a session whose recording failed is marked and audited as a recording failure.
- **Lowering the deployment-wide default access level** is audited in the same transaction and raises an `access_policy_relaxed` system alert that states how many assets follow the default and end up at a lower effective level. Raising it, or leaving it unchanged, does not raise an alert.
- **Turning off syslog forwarding, turning off offsite storage, and changing where either or the key topology points** are audited in the same transaction and raise a system alert (`offsite_or_syslog_changed`, or `key_topology_changed`). For syslog, that means disabling it, or saving it enabled with a host, port or protocol that differs from the saved one (which includes turning it on with a different destination). For offsite storage, it means disabling it or switching to a different destination, whether through the confirmation step or directly when nothing has been uploaded to the current one yet. For the key topology, it means a save whose before and after values differ. Changing only the TLS CA of syslog, or updating the same offsite destination in place, is only audited. The topology alert does not carry the address or any other value: read the before and after values from the audit entry written in the same transaction, which carries the same correlation identifier. If the audit entry or the alert cannot be written, the change is not applied, and the forwarder is reloaded only after the commit. One exception is described under the key rewrap in [Privileged Credential Rotation](./privileged-credential-rotation.md).
- **Deleting a recording is an API operation only, and the product's interface has no control for it.** `DELETE /api/v1/sessions/:id/recording` requires the recording deletion permission (`recording:delete`), a global permission in the settings group that the super administrator role holds and that a custom role can include. In one transaction the product writes the audit entry and raises the `recording_deleted` system alert, then clears the recording from the session; it removes the local file only after that commits. If the audit entry or the alert cannot be written, nothing is deleted. No policy setting or role in the product turns that audit entry off; this says nothing about the host (see "What the product's roles do not reach: the host"). The entry and the alert go away only under the retention settings. Recording playback tokens already issued for the session stop working at once.
  - **If removing the local file fails after the commit**, the session no longer points at the file, a failed entry is written to the audit log, and the file stays on the disk as an orphan. Recording retention is not guaranteed to remove such a file. While the recording retention setting is a positive number of days, the cleanup tries to remove it by its modification time; if whatever made the removal fail is still there, the cleanup fails the same way, and that cleanup run stops at the file. With 0 (keep forever) nothing removes it automatically. Fix the cause, or remove the file by hand.
  - **Copies already uploaded to offsite storage are not deleted** by this operation.
- **An alert guarantees that it is created and left on record, not that someone receives it.** The alert is written in the same transaction as the change; whether it is delivered depends on the notification channels, as described in the section above: with no enabled channel nothing is queued, and a delivery that keeps failing is abandoned after 72 hours. Do not read any of these alerts as proof that a person was told.
- **Limitation: the system security administrator role, and anyone holding these permissions, is not limited by the product itself.** The permissions cover the key topology, turning off offsite storage and syslog forwarding, deleting recordings, turning off the recording-failure block, and managing notification channels. What the product adds is the floor on retention, the audit entry written before a recording is deleted, and the alerts. It does not stop a holder who is unsuitable, or who also holds asset, authorization or identity administration (a combination the product warns about and does not block): that person can act first and then remove any trace that the retention floor does not protect. Give these permissions to security or audit staff and check who holds them and in what combination.
- **Limitation: the alerts about a holder's own actions go where that holder can send them.** The same people manage the notification channels, so they can change a channel and then act. What the product provides is the notice of every channel change to the old and the new destination, and the audit entries of the channel change and of the action; it does not stop the sequence.

## Outbound connection requirements for the credential change channel

Credential changes are initiated by the backend container towards the target host; they pass through neither the frontend nginx nor the user's browser. Linux hosts use the target's SSH port; Windows hosts use whichever change channel is configured on the asset, either the target's WinRM port (http 5985 or https 5986, configurable) or its SSH port (22 by default, configurable). The WinRM transport **does not read proxy environment variables and does not follow HTTP redirects**, and speaks only HTTP/1.1; if traffic between the backend and the target must pass through a proxy or a redirect, WinRM credential changes for that host cannot connect. When the https certificate verification mode is `system`, the trust anchor is the certificate store of the backend container's operating system; for a listener certificate issued by an internal CA, use `ca` mode instead and upload that CA on the asset. For target-side prerequisites, see the Windows local account credential change section of §2.5 in the [Deployment and Upgrade SOP](./upgrade-sop.md).

## State of the base systems of components (affects vulnerability management planning)

**The base system of the guacd container used for RDP and VNC no longer receives security updates.**

The guacd service uses the official Apache Guacamole image `guacamole/guacd:1.6.0` directly and unmodified (the compose files pin it by version and digest), and its base is Alpine 3.18, past its official support period. **This is not a choice made by this project**: the official `latest` and `1.6.0` are the same `alpine-minirootfs-3.18.12`, and upstream has not yet provided a newer base.

Two consequences matter for your deployment planning:

- **The operating system layer of that container will receive no further security patches** until upstream updates the base.
- **Vulnerability scan results for that image cannot be used as a security basis.** Scanning it yields "zero findings," which correctly reads as "no data": a system past its support period no longer receives vulnerability database updates, and guacd itself is a compiled binary that is not in the package list, so the scanner cannot see it.

Structural mitigations already in place (in effect with the default deployment, no extra configuration needed):

- guacd **exposes no port at all**; it exists only on the compose internal network, and the only thing that can reach it is this system's backend service.
- The recording directory is its only shared mount point. **Enabling offsite storage does not change this**: guacd still writes directly into the local recording directory, and the upload is performed separately by the backend **after the session ends**. guacd never touches object storage and holds no storage credentials. For the same reason, **recordings left behind on a crash path do not go offsite**: for a file whose session ended abnormally without a completed write confirmation, the system creates no upload tracking, and the existing local cleanup mechanism handles it. Offsite retention covers recordings that ended normally and were confirmed written. On retrieval, the staging area the file lands in is **a cache local to the backend container** (with a lifetime and a total size cap), which likewise is not shared with guacd.
- The container **runs with minimum privileges**, and these are set by the shipped compose definition rather than by the image: every Linux capability is dropped, privilege escalation through setuid files is refused, and the root filesystem is read-only. Two small in-memory writable areas are kept because the workload measurably needs them: the per-connection staging directory used by RDP drive redirection, and the writable home directory the RDP library requires in order to start. The staging area holds whatever a user is transferring at that moment, so no size cap is set on it; a deployment that wants one edits that tmpfs line in the shipped `docker-compose.yml` directly, for example `/tmp:size=512m` (a compose override file cannot do it: compose appends tmpfs entries rather than replacing them, and the same mount point declared twice is rejected). The RDP library's trust store for known hosts lives in one of those in-memory areas and is therefore empty again after every container restart; how this system treats a target host's certificate is decided by the asset's certificate verification setting, not by that store surviving a restart. The read-only root and the two in-memory areas, which are mounted noexec, mean that a break-in arriving through the protocol can neither alter the container's configuration nor execute anything from the staging areas; the shared recording directory remains writable and executable, which is what writing recordings requires.
- **You may replace this image with one you build or select yourself**, by changing the guacd `image:` line in the compose file. What this system requires of the container is only three things: that it speak the guacd protocol on port 4822, that it be able to write to the recording directory the compose definition mounts into it, and that it contain `sh` and `nc`, which the health check applied by the compose definition runs to decide whether the container is ready. Everything above is a runtime attribute of the container, not a property of the image, so the minimum-privilege settings continue to apply to whatever image you put there.

**Mitigation is not the absence of risk**: if the backend is compromised, or a managed remote desktop host attacks back through the protocol, that path still exists. **If your vulnerability management policy requires every component's base system to be within its support period, put this image into an exception assessment before deployment.**

**The backend still runs as root.** Its shipped deployment and startup code apply the following settings:

- `cap_drop: [ALL]` removes the capability set, then `cap_add: [SETUID, SETGID, CHOWN, KILL, IPC_LOCK]` adds back exactly five capabilities: `SETUID` and `SETGID` switch DB CLI subprocesses to their dedicated user and group; `CHOWN` transfers ownership of temporary CA files to that user; `KILL` permits signalling processes with a different UID within the container PID namespace, including DB CLI children; `IPC_LOCK` permits memory locking beyond the locked-memory limit.
- `security_opt: [no-new-privileges:true]` prevents gaining privileges through execution of setuid files or file capabilities.
- `ulimits.core` has both `soft: 0` and `hard: 0`; the backend also sets its own `RLIMIT_CORE` to zero.
- `PR_SET_DUMPABLE=0` makes the backend process non-dumpable. Together with the absence of `SYS_PTRACE`, this denies other processes in the container, including root processes under these capability limits, access to its `/proc/<pid>/environ` and `/proc/<pid>/mem`.
- `ulimits.memlock: -1` and `mlockall(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)` lock resident pages and lock other mapped pages when they become resident, preventing those pages from being swapped out.

On 2026-09-12 (Asia/Taipei), with the memory controls above and 15 development services running (backend with Air, dex, fake-gcs, frontend, guacd, k3s-test, ldap-test, localstack, mssql-test, mysql-test, postgres, rdp-test, ssh-multi-test, ssh-test, and vnc-test), alongside the measurement client and background service work but no other Go tests or end-to-end smoke tests, the backend measured VmRSS 68616 kB / VmLck 1369796 kB with 0 active SSH sessions and VmRSS 76952 kB / VmLck 1370060 kB with 20 concurrent SSH sessions to ssh-test held open for 45 seconds after an echo command in 120×30 terminals; these single samples are reference measurements, not a guaranteed memory ceiling.

**Key material remains in the backend process's memory.** These settings restrict which other processes can read it; they do not remove it or prevent the backend itself from accessing it. They do not protect it from an administrator who controls the host or can change the deployment's privileges.

**Custom orchestration must supply these settings.** Drop all capabilities and add only `SETUID`, `SETGID`, `CHOWN`, `KILL`, and `IPC_LOCK`; also apply the privilege and resource limits listed above. In Compose, the required memory-locking settings are `cap_add` containing `IPC_LOCK` and `ulimits.memlock: -1`. Other orchestrators must supply equivalent capabilities and resource limits. If a startup control cannot be applied, the backend exits; a memory-locking failure reports `mlockall failed (check cap_add IPC_LOCK and ulimits.memlock)`. Check those exact settings when diagnosing that error.

After changing capabilities, recreate the backend container; restarting it does not apply the new capability set. `custodexa.sh upgrade` recreates it when it starts the new release. When recreating by hand in a package deployment folder, run `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend`; for other Compose deployments, run `docker compose up -d --force-recreate backend`. Without `KILL`, the backend may be unable to terminate a DB CLI child. Local terminal closure waits at most one second for child reaping, logs termination or wait failures and timeouts, and then continues connection cleanup. A single background wait reaps the child if it later exits; a missing capability can still leave the child running.

## How allowed source ranges affect the deployment

**Allowed source ranges (`allowed_cidrs`) restrict which source addresses an account may use the system from.** An empty list means no source restriction, which is the default. It restricts the **usable sources**; it does not replace the password policy, account lockout, or multi-factor.

### First decide how the "source address" is determined

This system has exactly one way of determining where a request came from, shared by every path:

- **When `TRUSTED_PROXIES` is not set, only the socket peer is trusted**, meaning the far end of the TCP connection. Forwarding headers such as `X-Forwarded-For`, `X-Real-IP`, and `Forwarded` **are never trusted**.
- Once `TRUSTED_PROXIES` is set, forwarding headers are interpreted according to the trusted proxy chain you declared. **If the value is invalid the backend refuses to start**; it does not fall back to the default and keep running.

Not trusting headers by default is deliberate: those headers are controlled by the caller. Trusting them lets anyone who can send a request set an arbitrary address on their own audit row, and lets them bypass any address-keyed restriction by using a different header each time.

**When the application sits behind a reverse proxy, load balancer, or CDN and `TRUSTED_PROXIES` is not set, the source the system sees is always that proxy's address.** Three consequences:

- Allowed source ranges are evaluated against the proxy address. Entering your users' ranges blocks **everyone**; entering the proxy address permits everyone who goes through that proxy.
- The source address pivot in the Investigation Workbench, and the source address column on audit rows and session rows, all record the proxy address.
- The new source address alert only fires when the proxy address changes.

**The default deployment brings its own proxy. Source-tree `bash scripts/quickstart.sh` and package `custodexa.sh install` fill `TRUSTED_PROXIES` with the Docker subnet that proxy runs on.** Run an ingress of your own and the list is yours to write: put the ingress address, or the range it connects from, there.

**To evaluate and record the real source, you must first set `TRUSTED_PROXIES` and list the proxy chain explicitly.** Make this decision **before** enabling source restrictions: setting up the list first and then changing the proxy configuration makes an already-effective list suddenly apply to a different set of addresses.

### Which entry points are blocked, and what a block looks like

When the list is non-empty and the source does not fall within it, the following actions are all denied:

- Sign-in (including multi-factor completion and the OIDC exchange), and the issuance and consumption of the restricted tickets for forced enrollment and forced password change.
- Web session refresh.
- Connection issuance, and both redemption entry points, text terminal and graphical. **Each redemption reads the current list and evaluates again**, rather than reusing the conclusion from the moment of issuance.
- Three administrator endpoints (**resetting another user's password**, **unlocking another user's account**, and **clearing another user's multi-factor**), evaluated against **the operator's own** list.

A blocked response **says only "this source is not allowed"; it does not echo the address and does not list the ranges**. The address and a snapshot of the matched list are written only to the audit record. Connection-type denials additionally carry the machine field `reason=source_not_allowed`, from which the interface shows "your current source is outside the allowed range" instead of opening a request dialog.

**When the list cannot be read or its content is corrupt the action is always denied** (it is not treated as an empty list and permitted), and the outward response is exactly the same as for a source mismatch; diverging would tell the caller "this account's policy is broken." Such a case opens a `source_policy` event on the Failure Events tab of the Operation Logs page in the admin interface, with the cause classified as either unreadable or a corrupt string; the system closes it out by itself once the data is fixed.

### Before tightening the list: notify the people it will block

**Tightening the list does not cut off people already online.** Specifically:

- Web access tokens already issued remain usable for their lifetime, with **a residual window of at most 15 minutes**; after that every `refresh` is denied, the user is returned to the sign-in page, and the source evaluation blocks the next sign-in.
- **Protocol connections already established are not actively cut when the list is tightened**; they run to their normal end. Only the next connection is blocked.
- Actions such as issuing a full session or a restricted ticket, and writing authentication state, are all evaluated before the action takes effect, so after tightening no new session can grow from an address outside the list.

The right way to tighten the list is therefore to **notify first**: tell the affected people the new usable sources, when the change takes effect, and who to contact if they are blocked. Tightening without notification shows up as failed refreshes and being kicked back to the sign-in page, and users cannot tell that apart from a system fault.

### How to recover when an administrator locks themselves out

**The system does not block such a save**, because an administrator may deliberately configure a range they have not yet moved to. The interface only shows a warning next to the field before saving; it does not block submission.

If you really are locked out, in order:

1. **Another administrator is available**: ask them to change the list back in the admin interface. This path leaves a field-level audit diff (the list's before and after values), and is the preferred one.
2. **No other administrator is available**: use the existing offline reset path, connecting to the database directly to clear that account's list to an empty string. For the literal steps and the SQL, see [Quick Start — Lost admin password, a startup blocked by the weak-credential scan, or an administrator locked out by source restrictions (offline reset)](../QUICKSTART.md#lost-admin-password-a-startup-blocked-by-the-weak-credential-scan-or-an-administrator-locked-out-by-source-restrictions-offline-reset). This one **only needs the list cleared; the password does not have to be touched**.

An offline reset **does not go through product audit**: it bypasses the application and writes to the database directly, so `audit_logs` has no corresponding row. **The record of that operation is owned by the deployment's own change management** (who touched the database, when, under what authorization). What the product side can show afterwards is the sign-in audit rows after recovery (including the source address), and the field-level diff left when the list is configured again through the interface. No service restart is needed after clearing. **But do not stop at the cleared state**, because that means every address can get in.

### What the new source address alert means for operations

The first time an account establishes a protocol connection from a given source address, the system produces a `new_source_ip` alert and pushes it through the existing notification channels. Each (account, address) pair fires once.

Three things to keep in mind when reading it:

- **It means "this account has not connected from here before," not "this attempt was blocked."** Whether the attempt is permitted is decided by allowed source ranges, and the two do not affect each other: with an empty list every new address fires, while a connection the list blocks never reaches the point of establishing a connection at all.
- **Signing in without connecting does not fire it**; it only adds that address to the baseline. The typical flow of signing in and then connecting still fires once at connection time.
- **Addresses already visible at the time of the upgrade do not fire**: on upgrade the system backfills a baseline from the full session history and successful sign-in records. A fresh installation has no history to backfill, so the first batch of connections each fire once, which is expected.

If your users are on floating addresses (home broadband, mobile networks, rotating VPN egress), these alerts will be quite frequent. They suit being a "worth a look" signal, not a blocking condition; use allowed source ranges to block.

### Effect on backup and restore

Nothing new to store. Allowed source ranges and the source address baseline both live in PostgreSQL and are backed up along with the database; the existing [backup and restore](./backup-and-restore.md) procedure is unchanged and needs no extra steps.

## When an SSH host key does not match the record

The first time the platform connects to an asset over SSH, it records the host key the target presents. From 1.18.0, when a later connection is offered a different key, what happens depends on who is waiting for it. For terminal sessions opened by users, file transfer and connection tests the host key check allows the connection to proceed to SSH authentication, and if authentication and the channel succeed the user sees a warning in the terminal or the file manager. Credential changes and credential rotations run with nobody watching, so they stop without sending any credentials or new secrets, and the job ends with a host key mismatch result. A terminal opened by an automation agent is refused in the same way, before any credentials are sent. In both cases, before authentication starts, the platform writes an audit entry with the recorded and the presented fingerprints, the asset, the user, the connection and the check's decision (allowed to proceed, or refused). The first time a given fingerprint appears it also creates a system security alert, "Host key does not match the record"; whether anyone receives it depends on the configured notification channels and the delivery result shown on the alert. Once authentication has actually been attempted, a second audit entry with the same correlation identifier records that the sign-in credentials were sent and whether authentication succeeded.

The record keeps the original fingerprint until a super administrator changes it. The asset's host key panel shows up to five unconfirmed fingerprints, ordered by most recent observation; it is not the complete mismatch history, which is in the audit log. A super administrator can adopt one of them as the new record. Resetting is still available: the first connection after a reset records whatever key the target presents, so adopting a fingerprint you have checked leaves no such gap. Adopting a fingerprint and resetting are each recorded and create a medium-level system security alert, so the moment the record changes is itself on the record.

### Known limitation: authentication proceeds against an unverified host

Being allowed to proceed does not mean the connection succeeded; it means the platform went on to authenticate with the stored credential against a host whose identity it could not confirm. What that exposes depends on the authentication method. If password authentication is attempted against an impersonating host, that host can obtain the password. Public-key authentication sends a public key and a signature bound to the SSH session; it does not send the private key. Continuing still exposes the session and any data sent to the unverified host. The audit entries and the alert let you find out and investigate afterwards. They do not stop authentication from happening, and the platform offers no protection against this case.

This applies to terminal sessions opened by users, file transfer and connection tests. Credential changes and credential rotations, including rotation of Windows accounts over SSH, and terminals opened by automation agents stop on a mismatch, so they do not send credentials to the target; this does not protect the connections listed above.

Things to keep in mind when reading the alert:

- **One alert per new fingerprint.** An asset creates the alert the first time a given unconfirmed fingerprint appears. Later connections with the same fingerprint are audited every time and counted on the asset's host key panel, without further alerts. If the fingerprint had only been seen in connections that were refused (a credential change or rotation that stopped, or a terminal opened by an automation agent), the first user terminal session, file transfer or connection test that is allowed to proceed with it creates one more alert, because that is the first time authentication is attempted against it. A different fingerprint creates a new alert.
- **The alert states the check's decision.** "Allowed" means authentication was permitted to proceed against this host; "refused" means the connection was stopped before authentication and no credentials were sent: either a credential change or rotation stopped, or a terminal opened by an automation agent was refused.
- **If the audit entry cannot be written**, for example because the database is unavailable, the connection stops before authentication, and the user sees "host key check failed".
- **Agent sessions are background work.** A terminal opened by an automation agent through the agent channel has nobody watching it, so on a mismatch it is refused like a credential change; the classification is made on the server from the connection ticket, not from anything the client declares.
- **File transfer on VNC connections** is opened by the desktop gateway component itself. When the platform already has a recorded host key for that address, it hands the key to the component, which refuses the file transfer channel on a mismatch; that refusal is visible only in the component's own log, not as a platform alert or audit entry. When there is no record, the component connects without verifying the host, exactly as before. This channel never records a key on first use and never adds fingerprints to the asset's list. Database, Kubernetes and RDP connections do not use SSH host keys.

### What to do when the alert fires

1. Ask whoever runs the host whether it was reinstalled or its host keys regenerated, and compare the fingerprint listed on the asset's host key panel with the one on the host itself.
2. If they match, have a super administrator adopt that fingerprint on the asset's host key panel. The warnings stop, and credential changes, rotations and terminals opened by automation agents can connect again. Use reset only when you cannot check the fingerprint in advance.
3. If they do not match, or nobody can confirm, treat every password used against that asset since the first alert as exposed: change it on the real host. Private keys are not sent during public-key authentication, but any session content exchanged with the unverified host should be treated as seen by it. Use the audit entries to see who connected and when.

### On upgrade

Assets that were refused because of a host key mismatch are allowed to proceed to authentication for terminal sessions opened by users, file transfer and connection tests after the upgrade, and each creates an alert on its first connection. Their credential changes, rotations and terminals opened by automation agents keep being refused until a super administrator adopts a fingerprint or resets the record. Before upgrading, review the assets whose connections currently fail for this reason, and confirm or reset them.

## Effect on upgrades

Upgrades must be performed with downtime; rolling updates are not permitted. For the procedure, see the [Deployment and Upgrade SOP](./upgrade-sop.md). In a package deployment the management script runs the upgrade with the same stop-and-backup order.

As of this release, **there is one more reason a new instance may fail to come up: the old instance is still running, or its database session is left over**. A leftover only happens when the lock holder's host crashes or a network partition leaves the TCP connection half open; postgres reclaims that session according to the operating system's TCP keepalive (the postgres container sets nothing of its own, so the Linux default of roughly 2 hours applies). The startup log prints the lock holder's fingerprint and the confirmation code; for the recovery procedure, see [Deployment and Upgrade SOP §2.6b](./upgrade-sop.md#26b-if-the-backend-is-stopped-and-reports-that-the-single-instance-lock-is-held-by-another-database-session). **Recovery requires no operation on the database.**

The mutual exclusion guarantee only holds between guard-bearing releases. On the first upgrade from a release without the guard, the new release acquiring the lock **does not mean** the old one has stopped; the first-upgrade check in §2.3 of the upgrade SOP is the only source of evidence.

Before upgrading, stop every instance of the old version, the standby included. While an old and a new version run against the same database at the same time, a host key adopted or reset on the old version is not seen by the new one, so credential-change work under way may not notice that the trust in that host has changed. This is an accepted risk, and the system does not prevent it; a key that changes to a different one is still caught by the fingerprint comparison, and the exposed case is a key that changes and returns to the recorded one. The system's only response is a system alert, `concurrent_instance_detected`, raised when the new version starts. The detection recognises only instances that carry the single-instance guard, and when the write fails, or the query fails and the start was not confirmed past the single-instance guard, it leaves a line in the backend log and nothing else, so a missing alert is not evidence that no other instance is running. For the steps, see the [Deployment and Upgrade SOP](./upgrade-sop.md).

If the lock is lost at runtime (postgres restart, the session being terminated, a network event), this instance **keeps serving** and retakes it each cycle. During that time the admin interface shows a persistent banner, the metric `custodexa_instance_guard_held` is 0, and `audit_logs` holds an `instance_guard` event; for how to read them, see [Deployment and Upgrade SOP §3.4](./upgrade-sop.md#34-losing-the-single-instance-lock-at-runtime-reading-the-log-the-banner-and-the-audit-event).

## Effect on availability planning

The single-instance shape has no automatic failover, so availability planning works on shortening the time to restore: keep backups and KEK material ready at all times, and rehearse the restore procedure in advance. See [backup and restore](./backup-and-restore.md). With a delegated key mode, "ready at all times" also means the custodian credentials being obtainable by whoever is on call, and a person being available for every restart; the next section states what that costs.

What can be shortened further is the time to service after the loss of the **application host**, as opposed to the database: with the database on a separate server and a prepared standby host, service comes back by starting the standby against the same database, which is a procedure a person or a script runs rather than something the product does by itself. What that procedure needs in advance and what it does not preserve (the recordings and other files that only the failed host held) are in [Application Host Standby Takeover](./standby-takeover.md). The loss of the database is still handled by restoring a backup.

**Offsite evidence storage changes whether evidence can be lost, not how fast the service comes back.** Keep the two apart when planning:

- **It shortens the exposure window for evidence; it does not remove it.** The upload happens only after the session ends: text recordings are queued within seconds, graphical recordings wait at least a minute (until the file stops changing), and if the storage endpoint is unreachable they wait until it recovers. **Within that window the local copy is still the only copy.** If the machine is destroyed then, that recording has no second copy.
- **It does not change the recovery time objective.** A remote copy means evidence already offsite can still be retrieved after the machine is destroyed, but bringing the system back into service still requires the restore procedure (database, KEK, deployment-layer configuration). **Offsite storage is not a substitute for backups**; plan for both together.
- **The first playback of an offsite recording involves a download wait.** For a recording whose local copy has been cleared, playback first retrieves it from object storage, writes it locally, and verifies the hash before streaming begins; the wait depends on file size and bandwidth. This is expected behavior, not a fault, and it happens only on that recording's first playback (the staged cache is reusable within its lifetime). If your audit work has response time requirements, count this wait in.

## Delegated key mode: the deployment is not unattended

**With `KEK_PROVIDER=kms` (AWS KMS, GCP Cloud KMS or HashiCorp Vault), this release does not restart without a person.** The credentials used to reach the custodian are held only in the memory of the current unseal generation and are erased when the system is sealed, so nothing can read them back once the process has ended. Every cold start therefore comes up **sealed**, serving only the health check and the seal endpoints until an administrator unseals it: a host reboot, a container recreation, a scaling event, a nightly maintenance window, and the first start after a restore are all on that list. **The process does not exit.** Waiting for credentials is the designed normal state rather than a configuration error, and a supervisor that restarts the container does not resolve it.

Three consequences for planning:

- **Someone has to be reachable for every restart**, the unplanned ones included. Decide who, and how they are called out of hours, before choosing this mode. `ui` mode has always had this property; from this release `kms` shares it. `env` is the one mode that restarts unattended, and it pays for that with the master key sitting in cleartext on the host.
- **Automatic scaling and unattended restart policies do not fit this mode**: they bring back a process that cannot serve.
- **Monitoring has to alert on the sealed state**, or a restart at 03:00 is found at 09:00. The state is readable while sealed, from `GET /api/v1/seal/status` and from the seal group in `/metrics`. How to reach `/metrics` and collect it is in [Collecting the operational metrics](#collecting-the-operational-metrics-metrics).

**What the unseal page asks for, and the boundary of that check.** The administrator signs in on the unseal page with a username and password, checks the custodian shown there against the deployment record, and supplies that provider's credentials again. Two limits belong in a security assessment:

- **While the system is sealed only the username and password are checked; the one-time code is not.** Its seed is protected by the data key, which cannot be unwrapped while sealed, so requiring it would mean having to unseal before being able to unseal. **This step is therefore not two-factor and must not be described as one.** What stands behind it: the unseal endpoints' own per-source backoff and time-limited cooldown, the source ranges in `SEAL_UNSEAL_ALLOWED_CIDRS`, responses that do not distinguish a wrong password from an unknown account, a line in the backend log for every attempt, and an authorization context that lasts ten minutes and re-checks on each use that the account is still an active administrator. **An account already locked is refused here too**; what this step does not do is add to the failed-attempt count or lock the account itself, because the account lockout policy belongs to the stage that exists only after unseal.
- **The account has to be a local administrator.** An account provisioned from a directory or an identity provider cannot be authenticated while sealed, because the external authentication path is assembled only after unseal. A deployment whose administrators all come from an external source cannot unseal itself, so keep at least one local administrator account, as the delivery checklist already requires.

**Where the custodian settings live.** The address, region, Transit key name and role identifier are rows in the database, set on the key management page; every change is recorded in the audit log with its before and after values and raises a security alert through the configured notification channels, and with no channel configured the audit row is the only record. The credentials are in neither the database nor `.env`. What follows for backup and takeover: the settings travel with the database backup, the credentials do not. See [Backup and Restore §4.3](./backup-and-restore.md#43-mode-c-kek_providerkms-delegated-to-a-key-custodian) and [Application Host Standby Takeover §2.2](./standby-takeover.md).

## Data key retention in memory: what the setting costs in availability

Stored secrets — asset account passwords, recorded clipboard content, directory bind credentials — are encrypted with a data key, and that key is unwrapped by the master key before use. The security policy **Data key retention in memory** (key management page) decides how long the unwrapped data key is kept.

**Left empty, which is the factory default, nothing about your deployment changes.** The data key is unwrapped once and kept until the system is sealed or the process restarts, and a delegated key custodian is not on the everyday path.

**Set it to 0 or to a number of seconds and the custodian enters the runtime path.** While the custodian is unreachable, every action that needs the key unwrapped again fails: retrieving an asset account password as a connection is established, and writing recorded content during a session already in progress. That is the trade the setting exists to offer — a shorter time in memory, paid for in availability — and it is not a degradation that can be worked around at the time.

Settle two things before turning it on:

- **Whether new connections failing while the custodian is unreachable is acceptable, and for how long.** Answer that before choosing a value, not after the first outage. There is no fallback to the previous key material: an unwrap that fails, fails.
- **The round trip to your own custodian.** Each unwrap is one call to it, and the delay depends on the region, the network path and the custodian itself. **Measure it in your own environment** rather than taking a number from any document, and choose the value from what you measured.

On local key modes — the master key comes from an environment variable, or an administrator enters it at startup — the setting is still available and still shortens how long the data key is kept. What it does not change is the master key itself, which is in the process's memory throughout in those modes.

Audit records are outside this setting: the key that stamps them is not subject to the retention period, so records can still be written while the custodian is unreachable. What the setting shortens is the time the data key is present in memory; during an operation, memory still holds keys and unencrypted data.

## Collecting the operational metrics (`/metrics`)

The backend serves Prometheus metrics at `/metrics` on its own HTTP port, 8080 inside the container. **In a default deployment, `https://<your domain>/metrics` returns the web interface, not metrics**: the backend's port is not published on the host, and the proxies in front of it forward only `/api` and `/ws`. This is the intended default. The endpoint is reachable only from inside the deployment's docker network, and making it reachable from other hosts is a separate decision that comes with a token (method B below).

- **Authentication**: with `METRICS_TOKEN` in `.env` empty (the default), the endpoint answers without authentication. Once it has a value, every request needs `Authorization: Bearer <token>`, wherever it comes from; a missing or wrong token gets 401 with no metrics in the body.
- **While the system is sealed**, `/metrics` carries only the seal state, the single-instance guard series and the Go runtime and process metrics. The others, the audit queue among them, appear once the system is unsealed ([Upgrade SOP §2.4](./upgrade-sop.md#24-confirm-the-audit-queue-has-drained-before-stopping)).

### Looking at the values once

On the host, run the request inside the backend container. Its image has no shell, but it keeps the busybox `wget`:

```bash
# METRICS_TOKEN empty (the default)
docker exec custodexa-backend wget -qO- http://127.0.0.1:8080/metrics

# METRICS_TOKEN set: the token is read from the container's own environment,
# so it never appears on the host's command line
docker exec custodexa-backend /bin/busybox sh -c \
  'wget -qO- --header="Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:8080/metrics'
```

Add `| grep '^custodexa_'` to keep only the product's own series.

### Looking at them in a browser, through an SSH tunnel

The backend container has an address on the docker network that the host can reach. Read it on the host, then forward a local port to it from your workstation:

```bash
# On the host
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' custodexa-backend

# On your workstation, with the address printed above
ssh -N -L 9180:<backend address>:8080 <user>@<host>
```

Then open `http://localhost:9180/metrics`. The address is assigned when the container is created, so read it again after the backend has been recreated (an upgrade, a restore, a settings change). A browser sends no `Authorization` header: with `METRICS_TOKEN` set, use `curl -H "Authorization: Bearer <token>" http://localhost:9180/metrics` through the same tunnel instead.

### Continuous collection, method A: Prometheus on the same host

Run Prometheus as a container attached to the deployment's docker network and scrape the backend by its container name. Nothing is opened outside the host, and no proxy changes.

The network is named `<compose project>_custodexa-network`. A package deployment always uses the project `custodexa` ([Package deployments and the management script](#package-deployments-and-the-management-script)), which gives `custodexa_custodexa-network`; a source deployment's project is its directory name unless `COMPOSE_PROJECT_NAME` says otherwise. Confirm the name on the host:

```bash
docker inspect -f '{{range $name, $net := .NetworkSettings.Networks}}{{println $name}}{{end}}' custodexa-backend
```

A minimal `prometheus.yml`:

```yaml
scrape_configs:
  - job_name: custodexa
    static_configs:
      - targets: ["custodexa-backend:8080"]
    # Only when METRICS_TOKEN is set; the file holds the token value alone
    # authorization:
    #   type: Bearer
    #   credentials_file: /etc/prometheus/custodexa-metrics-token
```

A compose file for Prometheus, kept in its own folder:

```yaml
services:
  prometheus:
    image: prom/prometheus:<version>
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:9090:9090"
    networks:
      - custodexa
networks:
  custodexa:
    external: true
    name: custodexa_custodexa-network   # the name the command above printed
```

The network has to exist before Prometheus starts, so start Custodexa first. While Prometheus is attached, the network cannot be removed: stop Prometheus before a `docker compose down` of the Custodexa project, and start it again afterwards.

### Continuous collection, method B: scraping from another host

Scraping from another host needs a route to `/metrics` through the https entry point, and **that route must not be opened without `METRICS_TOKEN`**: without it, anyone who can reach the address reads the endpoint inventory, per-feature usage and error rates.

**Step 1: set the token.** Generate a value:

```bash
openssl rand -hex 32
```

Write it into `.env` in the deployment folder as `METRICS_TOKEN=<value>`. The backend takes its settings from `.env` when its container is created, so recreate it; a restart is not enough. In a package deployment folder, run `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend`; for other Compose deployments, run `docker compose up -d --force-recreate backend`. With `KEK_PROVIDER=ui` or `kms`, the recreated backend comes up sealed and needs an unseal ([Delegated key mode](#delegated-key-mode-the-deployment-is-not-unattended)). Afterwards, the plain request from "Looking at the values once" is answered with 401, and the variant with the token returns the metrics.

The management script's check before an upgrade, which waits for the audit queue to drain, keeps working with a token set: it runs inside the backend container and uses the token the container already holds.

**Step 2: open the route.** What is possible depends on what sits in front of the deployment.

- **The built-in proxy (the default).** Copy its template and point `TLS_NGINX_TEMPLATE` in `.env` at the copy, as in [Quick Start: customizing the reverse proxy configuration](../QUICKSTART.md#customizing-the-reverse-proxy-configuration). In a package deployment the template to copy is `current/reverse-proxy/nginx-tls.conf.template`, and the copy goes outside `releases/` and `current/`, for example `tls/custodexa.conf.template`. In the copy, add this inside the `listen 443` server block, before `location /`:

  ```nginx
      location = /metrics {
          set $backend_upstream http://backend:8080;
          proxy_pass $backend_upstream;
          proxy_http_version 1.1;
          proxy_set_header Host $public_host;
      }
  ```

  The built-in proxy is on the deployment's docker network, so it reaches the backend by service name, resolved at request time through the `resolver` line the template already has. Apply it with `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate tls-proxy` in a package deployment folder, or `docker compose up -d --force-recreate tls-proxy` elsewhere. The copy is yours: backups taken by the management script include it ([Backup and Restore §3.8](./backup-and-restore.md#38-backups-taken-by-the-management-script-package-deployments)), and an upgrade does not change it, so compare it with the shipped template after each upgrade.
- **Your own ingress (the external ingress overlay).** The shipped compose files publish no port for the backend. Your ingress can route `/metrics` only when it runs as a container attached to the deployment's docker network, the same condition under which the shipped examples address the frontend as `frontend:80`; it then sends the exact path `/metrics` to `backend:8080`. An ingress installed on the host or running on another machine reaches only the port the frontend publishes, and the frontend forwards only `/api` and `/ws`, so in the shipped topology it cannot reach `/metrics`. Use method A in that case, or put a proxy container on the deployment's docker network.

**Step 3: point Prometheus at the entry point.**

```yaml
scrape_configs:
  - job_name: custodexa
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/custodexa-metrics-token
    static_configs:
      - targets: ["bastion.example.com"]   # add :<port> when TLS_HTTPS_PORT is not 443
    # Self-signed mode (TLS_MODE=selfsigned): trust the deployment's local CA,
    # which the entry point serves at /custodexa-ca.crt
    # tls_config:
    #   ca_file: /etc/prometheus/custodexa-ca.crt
```

The token file holds the token value alone. Keep it under the same access rules as `.env`.

### Which metrics to watch

The full list, with labels and the meaning of each, is in the [API reference (Traditional Chinese)](../API_SPEC.md#營運指標端點prometheus). Five alerts to start from, as Prometheus rules; adjust the durations and thresholds to your own commitments:

```yaml
groups:
  - name: custodexa
    rules:
      # Not serving: sealed, unsealing, or sealed after a fault. Every restart in
      # KEK modes ui and kms lands here until someone unseals.
      - alert: CustodexaNotUnsealed
        expr: custodexa_seal_state{state="unsealed"} != 1
        for: 5m
      # Audit rows that did not reach the database. reason="fallback_file": written to
      # the fallback file and recoverable; reason="discarded": lost.
      - alert: CustodexaAuditRowsDropped
        expr: increase(custodexa_audit_dropped_total[15m]) > 0
      # The asynchronous audit queue holds 1000 rows; when it is full, new rows take the path above.
      - alert: CustodexaAuditQueueBacklog
        expr: custodexa_audit_queue_depth > 500
        for: 5m
      # Command alerts nobody has reviewed yet, by severity.
      - alert: CustodexaCommandAlertsUnreviewed
        expr: sum by (severity) (custodexa_command_alerts_pending) > 0
        for: 24h
      # This instance does not hold the single-instance lock.
      - alert: CustodexaInstanceLockNotHeld
        expr: custodexa_instance_guard_held == 0
        for: 5m
```

Add the usual `up{job="custodexa"} == 0` for a scrape that fails altogether. The audit series are absent while the system is sealed rather than 0, so their rules stay quiet then; the first rule covers that state. For reading each signal: audit rows and the fallback file in [Upgrade SOP §3.1](./upgrade-sop.md#31-the-queue-is-drained-at-shutdown-with-a-time-limit), the single-instance lock in [Upgrade SOP §3.4](./upgrade-sop.md#34-losing-the-single-instance-lock-at-runtime-reading-the-log-the-banner-and-the-audit-event), and recording storage, which has no built-in cap, in [Quick Start: storage monitoring](../QUICKSTART.md#storage-monitoring).

## Sensitive output detection: scope and operational checks

Detection scans only parsed text output from SSH, K8s and database consoles. RDP/VNC graphics, encrypted, compressed or encoded content (including Base64) are outside its coverage. Terminal control sequences are not rendered or removed. Encoding can bypass matching; a match means the output **may contain** sensitive data, and no match does not establish absence. This mechanism raises alerts and does not block or alter delivered bytes.

Output rule additions, disabling and edits take effect for **new sessions**. Sessions already in progress retain the rule set captured at startup. After an upgrade, restore or takeover, check rule direction, enabled state and protocols, then open a new text session to verify the applicable rule set. The installed seed set has 16 rules: 12 original input rules, two agent input/block rules, plus card-number and private-key-header output rules. The builtin card pattern additionally uses Luhn validation; editing that pattern makes it an ordinary regular expression without card validation.

Hits for the same rule and session are aggregated over five seconds; session close flushes the remaining window. Alert records and forwarding retain identifiers, rule, count and time, with an empty command and no matching text or byte offsets. The count is encoded as `o1:<base36 count>` in `reason_code`; webhook payloads also expose `possible_sensitive_output.count`. These are indications of possible sensitive output, not evidence that all output was scanned.

A bounded queue overflow disables scanning for that session without interrupting output. Query the existing audit records for action `output_scan_disabled`, resource `session` and the session's resource ID; `details` contains `session_id` and `reason=queue_overflow`, with no output text. A server log alone is not the audit record. Treat that session's subsequent output as unscanned; inspect the existing evidence under the usual permissions and open a new session after checking load. Scanner failures also leave server logs; absence of alerts is not a successful-scan guarantee.

The shared redaction primitive returns fully replaced text and a replacement count; it is **not connected to a product response path in this release**. Recordings, command records and other evidence are not redacted. Existing retention, access controls and backup/restore procedures continue to apply to their original contents.


### Principal and credential integrity coverage

The verification page reports role assignments, principal kind/owner, and agent credential state separately. After upgrade, the two new rows remain “Not covered” until the first checkpoint containing their snapshots. Detection is not immediate: reconciliation runs during verification, checkpoint sealing, and before token issuance. A mismatch raises one `principal_state_integrity` / `principal_state_mismatch` event per projection, with identifier-only differences and a notification. Issuance continues on mismatch or reconciliation error; errors are logged as unknown and do not change business state. Service-layer projection state rows record actor `system`; the existing HTTP audit rows identify the operator.

Compatibility is one-way: this release verifies old checkpoints, but old releases cannot fully verify the new snapshot keys. Do not remove snapshot keys, re-sign checkpoints, or restore the old single-mechanism failure index. Rollback requires a consistent pre-upgrade backup and the documented restore procedure. The payload version remains the current latest version (v3).

## Agent MCP operations

Create an agent principal with an active human owner. As that owner or an administrator, create a named, expiring agent token; save the one-time plaintext in the operator's secret store. The agent has only the user role and explicitly scoped asset/account grants. Install the `custodexa-mcp` stdio client on the agent's machine from https://github.com/custodexa/custodexa-mcp, either with `go install github.com/custodexa/custodexa-mcp@latest` or as a release binary verified against the `checksums.txt` published with that release. Supply `CUSTODEXA_AGENT_TOKEN` to `custodexa-mcp` through its environment and set `CUSTODEXA_MCP_URL` to the HTTPS `/api/v1/mcp` endpoint. Human JWTs and cookies cannot authenticate this endpoint. The stdio client forwards tool calls; all decisions and evidence writes happen in the service. Never put the token in command arguments or reports.

Whether a task the agent submits waits for a person is decided by the access policy segment of each requested asset, taken from the asset's own `access_policy` when set and otherwise from the `access_policy_default` security policy. An item in the `approval` segment stays pending until an approver whose scope covers that asset decides it. Items in the `open` and `reason` segments are approved at submission, are recorded with `auto_approved: true` and a policy snapshot, and carry no approval votes. Under the shipped defaults most assets fall outside `approval`, so a deployment that changes nothing will see agent tasks approve themselves. To require a human decision, set `access_policy` to `approval` on the assets concerned, or set `access_policy_default` to `approval` for the whole deployment; `access_request_min_approvals` then sets how many approvals such a request needs. Decide this before granting an agent its first asset, and state the choice in the runbook: automatic approval is still fully recorded, but it is not a human control.

Rotate by issuing a new named token, updating the operator's secret, starting a new MCP connection and verifying asset visibility, then revoking the old token. There is no in-place token secret rotation or automatic token recovery from backup. Revocation closes sessions created with the old token; a session handle cannot move to a new token or MCP connection. After restore or standby takeover, create new MCP connections and tasks as needed; old in-memory handles and the 60-second idempotency cache do not survive restart. Inspect retained token state and task state before resuming work.

To contain an incident, revoke or suspend the affected token, disable the agent if necessary, and inspect its task, tool-call and HTTP request records. A probe breaker suspends tokens and records an incident. An owner or administrator releases it with a reason; release does not reactivate suspended tokens, so issue a new token afterward. Its count covers one class of reference only: assets that exist and have never been exposed to that agent. A reference to an asset id that does not exist, or to a deleted one, is classified as retired, and a reference to an asset previously exposed to that agent is classified as revoked; both are recorded as events but neither counts toward the trip threshold. Enumerating identifiers at random therefore mostly produces uncounted events, and the breaker should not be presented as general scanning detection. It is a control against repeated reach for real assets outside the agent's scope; cover broader enumeration with alert rules and request rate policy, and read the `class` field on the breaker event list before judging how much a denied reference means. Existing webhook/Slack notifications include `owner_id`; they are not a private inbox or proof of delivery. Visibility exposure history begins at its migration and cannot reconstruct older visibility; verify that boundary before attributing a denied reference to abuse.

Token expiry, the bound task item's expiry and task closure terminate existing sessions and in-flight tools without waiting for the current command to finish. Expiry checks sample current state every 250 ms; that interval is not a completion SLA. Revocation uses the existing termination path (target at most three seconds, with late termination evidence). Termination controls only sessions created by this system, not detached processes or changes already made on the target. During an in-flight request, cancellation closes its session. Between POST requests, client departure cannot be detected immediately: the server closes abandoned handles when its five-minute idle lease expires. Do not describe this as immediate disconnect detection.

`completed` means a prompt was observed again; it guarantees neither command termination nor success. Prompts can be forged and background output can interleave. `timed_out` means the outcome is unknown: inspect subsequent output before retrying. Same-handle idempotency keys suppress repeat writes for 60 seconds; calls without a key can execute again. `needs_input` requires an explicit `send_keys` reset; the service never sends an interrupt automatically. `read_screen` is a line buffer, not a virtual screen. Agent-visible text is masked while recordings and command records retain the original. Masking is rule-driven and enumerated, not a general sensitive-data filter: it applies the enabled alert rules with `direction=output` whose subject kind covers agents and whose protocol list covers the session, and replaces each matched span with a placeholder. Anything no enabled rule matches reaches the agent in full, and the shipped rule set covers two categories, a card-number pattern and a private-key header pattern. Treat the rule list as the definition of what this deployment considers sensitive on the agent channel, review it against the data actually reachable on the granted assets, and add rules for the categories that matter there. Masking never applies to human terminals, recordings or command records.

For evidence, preserve the database, recordings, checkpoints and matching versioned integrity keys. A pending tool row proves recorded intent, not delivery or completion. An unattributable task/handle is rejected before the tool ledger and recorded in that MCP HTTP request's audit row with principal, tool, reason code and time. Command integrity coverage is available only through the Investigation Workbench and batch export; a single-session export has no coverage axis. Zero degraded rows does not prove that no commands were lost. Keep report versions and closed-task timestamps; do not manufacture results for pending calls.

MCP handles are process-local; do not treat multiple replicas as a shared session store.
