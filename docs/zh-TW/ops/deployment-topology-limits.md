## 本版支援的部署形態

**本版為單實例部署：整套系統只能有一個應用實例在執行。**

同時執行兩個以上的應用實例會造成資料問題。該形態未經設計、未經驗證，不得用於生產。

**本版起，對同一資料庫啟動的第二個應用實例會被攔下並要求確認。** 它在任何寫入之前停住：
印出持鎖者指紋與兩條救援路徑，未確認即不開放任何服務路徑、不執行 migration、不寫入資料庫。
**確認在該實例自己提供的攔下頁上完成**，由管理員為持鎖者的確認碼背書；以該碼設定
`INSTANCE_GUARD_ACK` 是腳本化的等價做法。無論哪一條，每一次確認啟動都留下
`audit_logs` 事件、指標與管理介面常駐橫幅——**確認後的執行有稽核證據**。

**守衛防的是不知情，不是不發生。** 確認後兩個實例並存造成的資料問題不由守衛防止，
由確認者承擔；守衛保證的是攔下、告知，以及事後可由 `audit_logs` 證明「哪個實例、何時、
對著哪個持鎖者、（經攔下頁時）以哪個管理員帳號確認」。訊息判讀與救援程序見
[部署與升級 SOP §2.6b](./upgrade-sop.md#26b-若後端被攔下並指出單實例鎖由另一個資料庫工作階段持有)。

具體排除下列三種架構：

- 負載平衡後方掛兩個以上的應用實例。
- 兩個以上的實例同時執行的多副本部署：高可用（HA）叢集、active-active，或已經在活動實例旁邊
  跑著的熱備（hot standby）。
  **冷備（cold standby）是另一回事，以程序的形式受支援**：資料庫放在應用主機之外（external
  database overlay）時，第二台主機在第一台停下之後才啟動、指向同一個資料庫接手，任一時刻只有
  一個活動實例。程序、備援主機事先要備妥的東西、接手保不住的東西，見
  [應用主機備援接手](./standby-takeover.md)。守衛在該形態下相同；第一個實例其實還在跑時，
  攔下備援主機的就是它。
- 以滾動更新（rolling update）方式升級；切換過程中必然出現新舊兩個實例並存。
  **守衛版之間的滾動更新會在新實例端被攔下**（新實例取鎖時看到舊實例持鎖，停在確認關卡）。
  自無守衛的舊版本升級到本版的那一次不會被攔（舊版不持鎖），須靠升級 SOP 的檢核。

> 此限制針對的是**應用實例**。資料庫、guacd 與前端 nginx 各自作為獨立容器執行是正常
> 部署形態，不在此限。

> **守衛只認得守衛版。** 不含守衛的舊版本不持鎖：首次自無守衛版升級到本版、或自本版回滾到
> 無守衛版時，新舊實例並存不會被攔下。這兩個窗口由升級 SOP 的「先確認舊實例已停」檢核承擔。

> **連線池模式。** 應用須直連 postgres，或經 session pooling 模式的連線池。transaction pooling
> 會讓鎖在工作階段間漂移，守衛會反覆回報失鎖再重取——該拓撲不受支援。

## 安裝包部署與管理腳本

用安裝包安裝的部署，由它的管理腳本 `custodexa.sh` 維運。本版腳本支援的範圍：

- **只支援 Linux**（x86_64 或 aarch64）。其他作業系統在做任何事之前就停下，並指向以原始碼執行的評估方式。
- **一台主機一套部署。** 容器名稱是固定的（`custodexa-backend` 等），同一台主機上無法並存第二套部署。
  `install` 發現已有部署時拒絕執行：目錄裡有狀態檔、有屬於別的目錄的 `custodexa-backend` 容器，
  或部署目錄是原始碼的 git 工作樹。
- **部署目錄的路徑**只能含英文字母、數字與 `. _ / -`；這個路徑會不經跳脫寫進 `.env` 與狀態檔。
  `install` 在寫入任何檔案前就檢查它。
- **一次只跑一個子命令。** 會改變部署的子命令先取得目錄上的鎖；期間再啟動的第二個以結束碼 3 停下。
  `status` 不取鎖，也不做任何變更。
- **呼叫 Compose 時一律用同一個專案。** 腳本明定專案名稱為 `custodexa`、以部署目錄為專案目錄、
  並指定目前版本的 compose 檔。`install` 也會把 `COMPOSE_FILE` 與 `COMPOSE_PROJECT_NAME` 寫進 `.env`，
  所以在部署目錄手動輸入的 `docker compose ps`、`logs` 指向的是同一組服務。
  手動輸入 `up`、`config` 時要另帶 `--project-directory .`；少了它會到錯的位置找 `.env`，
  指令會停下，不會動到任何容器。
- **升級與備份同樣經由腳本。** `upgrade` 停止服務、備份，再換到新版；`backup` 單獨做同樣的停機備份。
  兩者都不是滾動更新。`rollback` 在新版沒有改動過資料庫時，把部署指回上一版；改動過，或讀不到資料庫時
  （外接資料庫時，是這台主機上選不出資料庫用戶端），它不做任何變更，
  並印出要改執行的 `restore` 指令或手動程序；還原會取代該次備份之後記錄的一切（見[備份與還原 §5.1](./backup-and-restore.md#51-以管理腳本升級後回到升級前的版本)）。見
  [升級 SOP](./upgrade-sop.md#以管理腳本升級) 與
  [備份與還原 §3.8](./backup-and-restore.md#38-管理腳本做的備份安裝包部署)。
  舊 git clone 部署會在檔案或服務變動前被所有 `custodexa.sh` 入口拒絕。請規劃[人工遷移](./upgrade-sop.md#舊原始碼部署的手動遷移)，或在另一個乾淨目錄安裝後手動還原；腳本不轉換舊樹。`--images-from source` 只在核對原始碼校驗和後本機建置安裝包自家映像；上游映像與建置依賴仍須取得，不是完全離線選項。

### 目錄結構

安裝包解開後是 `custodexa/`，就是部署目錄。`install` 完成後（`DATA_PATH` 為預設值）：

```
custodexa/
  custodexa.sh -> current/custodexa.sh   管理腳本
  current -> releases/<版本>             執行中的版本
  releases/<版本>/                       出貨時的一個版本：腳本、compose 檔、MANIFEST.json、
                                         VERSION、.env.example、reverse-proxy/、source/；
                                         install 另加入 images.env 與 image-ids.env
  .env                                   設定與機密（權限 600）
  state.json                             安裝了什麼，只由腳本寫入
  logs/                                  每個改變部署的子命令一份紀錄（權限 700）；
                                         不會寫入 .env 的機密值
  backups/custodexa-backup-<版本>-<時間戳>.tar
                                         以 `backup` 做的備份：單一檔案（加密時為 .tar.enc）
                                         與其 .sha256，權限 600；含機密。組裝期間各部分放在
                                         backups/.partial-<時間戳>/（權限 700）
  backups/<時間戳>/                      升級所做的備份：一個資料夾（權限 700；含機密）
  tls/                                   內建 TLS 代理的憑證
  restore/<時間戳>-<字尾>/               一次 `restore` 執行的暫存目錄（權限 700）
  data/postgres/                         資料庫（僅限內建資料庫）
  data/recordings/                       會話錄影（擁有者 1000、群組 0、權限 2770）
  data/audit/                            稽核紀錄檔
  data/exports/                          非同步匯出的產物
```

部署跨版本保留的東西都在目錄頂層（`.env`、`state.json`、`tls/`、`data/`、`backups/`）；`releases/` 底下的版本只放出貨內容，
加上 `install` 為它記下的映像參照。

`data/exports/` 跨容器重建保留，但**不在備份範圍內**：其中的證據包產物含解密後的明文。
複製整個 `DATA_PATH` 的備份請把它排除在外，見[備份與還原 §2](./backup-and-restore.md#2-持久化資料的落點)。

`restore` 另外會留下兩類目錄，還原一旦開始，腳本都不會自動刪除。第一類是 `restore/` 底下每次執行建立的暫存目錄（權限 700）。執行期間，暫存目錄存放資料庫、`.env` 與各封存檔的明文複本，部署目錄所在的檔案系統需要約備份檔 1.1 倍的空間。還原完成時這些複本會刪除，留下的很小：資料庫記得、但本機沒有的錄影清單，以及還原前 `state.json` 與 `.env` 的複本（含密鑰，權限 600）。中途停下的還原會保留整個目錄，因為 `restore --resume`、`--revert`、`--abandon` 都從它讀取：在還原完成或放棄之前請留著。之後即可刪除。在停止任何服務之前就被拒絕的那次執行，則會自行刪除它建立的暫存目錄，不留下任何東西。外接資料庫部署時，匯入期間暫存目錄還會放匯入用的 SQL 文字，約等於資料庫未壓縮的大小；有略過授權時，會保留略過的授權清單（`skipped-grants.txt`）。新主機的外接資料庫原本已有資料時，暫存目錄會保留安全匯出 `safety-db.dump`，也就是那個資料庫的明文複本，還原完成之後也一樣；只有完成的 `restore --revert` 會刪除它，不再需要時請自行刪除。

第二類是還原所取代的資料。`DATA_PATH` 下目前的資料庫與稽核檔，以及 `tls/`，會改名為 `postgres.before-restore-<時間戳>`、`audit.before-restore-<時間戳>`、`tls.before-restore-<時間戳>` 原地保留，在你刪除之前，各佔與原資料相同的空間。回退的還原會把它已放上去的資料留成 `*.partial-restore-<時間戳>`，在新主機上放棄的還原則留下 `*.abandoned-<時間戳>`（空間規劃相同）。它們完整保有先前的內容，包含密鑰與錄製的證據，請沿用與現行資料相同的存取控管。等[備份與還原 §6](./backup-and-restore.md#6-還原後的驗證清單)的核對通過、且不再需要回退，再自行刪除；`backups/` 底下的安全備份是另一個檔案，有它自己的保存期限。外接資料庫部署沒有 `postgres` 目錄可以改名：資料庫在它的伺服器上原地清空並匯入，原本的內容在安全備份裡，新主機上則在安全匯出裡。操作步驟見[備份與還原 §5](./backup-and-restore.md#5-還原程序)。

`state.json` 逐行以固定格式讀取。檔案損壞時，會讀取它的子命令（包括 `status`）都以結束碼 5 停下，指出第幾行，
並指向放在旁邊的前一份副本 `state.json.prev`。

## 產品角色管不到的地方：主機

產品裡的角色與權限，管的是人透過介面與 API 做的事，管不到產品所在的主機。能在主機上以 root 身分操作、能使用那裡的 Docker、能讀寫 `.env`，或能以資料庫憑證連上資料庫的人，都在這個模型之外，不論他在產品裡是什麼角色：

- **管理腳本**在主機上以 root 權限執行（各程序都以 `sudo` 執行），不要求登入產品。備份、還原、升級、回退與其他指令，凡是能執行它的人都能用。產品裡的角色在主機上不帶任何權利：只管部分節點的管理者角色，不會讓人因此取得執行腳本的權利，而且腳本本身不檢查任何產品角色。另外被授予主機上 root 或 Docker 存取權的人，能對整個部署執行腳本的每一個指令，不論他在產品裡持有什麼角色。主機存取權只給本來就該掌握整個系統的人。
- **`.env`** 存放秘密與服務啟動時的設定，能改它的人就能改變服務的執行方式。稽核總開關 `FEATURE_AUDIT_LOG_ENABLED` 在 release 模式（隨附的 compose 檔所設定的模式）下維持開啟，被設為 `false` 而遭覆寫時，啟動日誌會點名。模式與 compose 檔同樣在主機上，所以這不是針對主機管理者的控制。
- **直接在資料庫上改**角色指派、群組成員或外部群組映射，不會被擋下，而是事後被偵測到：權限狀態會在驗證檢查點、封出檢查點與核發憑證之前，與應用程式記錄下來的變更比對。每一筆變更紀錄都帶有一個完整性驗證碼，用的是與稽核日誌相同的完整性密鑰；驗證碼無效的紀錄視同沒有紀錄的變更，確認紀錄也一樣。有差異時開一筆 `principal_state_integrity` 失效事件，項目為 `permission_state`，附上不同之處的識別值並發出通知。這筆事件會一直開著，直到狀態再度相符，或由超級管理員在稽核日誌頁的「失效事件」分頁填寫原因確認。確認會寫進稽核日誌，不改任何權限，也不阻擋任何操作。比對要在權限附證啟用之後才有效：它從第一個帶有權限附證的檢查點開始，通常是升級到 1.18.0 之後的第一次封章，在那之前做的變更不會被回報。啟用之後，比對無法完成時（例如變更紀錄缺漏或驗證不過），會為同一個項目開一筆失效事件，並顯示在檢查點驗證頁；在這段期間，之後的直接修改無法被偵測。繼續封章或保存期限修剪都不會結束這個狀態：一個檢查點是不是可信的起點，記在它自己的簽章裡，比對無法完成時封出的檢查點永遠不是；修剪也改變不了這一點，因為帶簽章的修剪記錄會把被剪掉的檢查點是否帶過附證、是否有驗證不過的點一路帶下去。超級管理員可以確認這筆事件，以目前的狀態重設比對基準：原因、比對無法完成的原因摘要，以及（有可信參考點時）參考點與目前狀態的差異（筆數與最多 20 個識別值）會寫進稽核日誌，被破壞的紀錄原樣保留。重設接受的是整份目前狀態，並不能證明先前那些驗證不過的紀錄從何而來。權限附證是每個檢查點簽章內容的一部分：任何一個檢查點（包括最新的那一個）的附證被清除或改動，該檢查點都會驗證失敗並觸發鏈結構告警。這個項目的失效事件若直接在資料庫裡被刪除或填上結束時間，下一次比對會重新開立並再發一次通知；在那之前，失效事件分頁上看不到它。仍有以下限制：同時持有資料庫存取權與完整性密鑰或檢查點簽章密鑰的人，可以寫出通過驗證的紀錄；最近一次封章之後寫下的變更紀錄，若連同它所記錄的變更一起被移除，比對不會回報；附證啟用以來留在主機上的證據若全部被刪除（之後封出的每一個檢查點、其間的修剪記錄與全部變更紀錄），下一次封章會把當下的狀態當成新的起點，比對回報相符；把權限相關的表、檢查點、修剪記錄與變更紀錄一起換回較早的一份一致副本（資料庫其餘部分維持現狀也一樣）亦然。兩者都只能靠放在主機之外的副本分辨（見下一段）。最新檢查點儲存的內容若被部分清除，封章會停擺、失效事件持續開著；超級管理員的重設修復不了它，只能還原可信的備份。
- **有權設定被管理主機秘密的人，可以選一個只有自己知道的值。** 宣告新秘密、以自訂秘密脫離主機，都會寫入稽核紀錄並發出告警，但沒有任何機制阻擋。之後這個人可以不經過本平台，直接連到該主機。請只把這些權限給本來就可以持有其範圍內主機存取能力的人（[更換平台自身的特權憑證 §13.7](./privileged-credential-rotation.md#137-誰能做這些事以及權限失去時會怎樣)）。
- **還原備份**是主機層的操作。它帶回備份時點的權限，包括之後才撤銷的指派。新的還原世代會結束還原前簽出的登入與憑證，但不會重建備份之後的變更（[備份與還原 §5](./backup-and-restore.md#以-restore-還原)）。

能控制主機的人可以換掉程式、秘密或整個資料庫，包括換成較舊的一份。產品沒有任何機制能防止這件事。請以主機的存取控制，以及放在主機之外的證據副本（稽核紀錄的 syslog 轉發與離機儲存）來因應。

## 角色與各自管理的範圍

每個人在主控台能做什麼，取決於被指派的角色。角色決定看得到哪些頁面、能在頁面上修改什麼。**管理權不自動授予平台內連線權**：資產管理員、授權管理員及其他管理權限，能不能連到主機由連線授權決定，與管理角色無關。內建超級管理者是例外，保有連線豁免，不需另有連線授權。

| 內建角色 | 管理什麼 | 可否限定節點 |
|---|---|---|
| 管理員（超級管理者） | 全部，包含角色定義；只有超級管理者能新增、修改、複製與刪除自訂角色。 | 否 |
| 資產管理員 | 資產、節點（資產分組）管理、資產測試、帳號憑證庫與其憑證變更（設定秘密、輪替、轉換範圍、卸除、掛載），以及改密計畫。不含授權規則、單台存取政策與審核範圍。 | 可 |
| 授權管理員 | 授權規則、審核範圍與單台存取政策。不含資產檢視、使用者管理與使用者群組管理。 | 可 |
| 身分管理員 | 使用者、使用者群組與角色指派；不能指派哪些角色，見下一節。 | 否 |
| 系統安全管理員 | 安全設定、告警與通知通道。 | 否 |
| 稽核員 | 稽核職能唯讀、每日審閱的簽核，以及存取複審的檢視。存取複審的簽核須另具 `accessreview:manage`，此角色不含該權限。 | 否 |
| 審核人員 | 核准指派給他的審核範圍內的連線申請。 | 只在全系統指派時生效（見下） |
| 一般使用者 | 工作區，以及自己的連線與申請。 | 只在全系統指派時生效（見下） |

內建角色不能修改。資產管理員與授權管理員是鎖定的範本：升級後沒有人持有它們，直到有人指派。

**內建一般使用者與審核者只在全系統指派時生效，限定節點後不產生權限，系統照常儲存並提示。**

### 把角色限定在節點

- 角色是在**指派**給使用者或使用者群組時限定節點；角色本身沒有節點設定。同一個角色可以對一個人指派為全系統，對另一個人限定節點。限定範圍的持有者能做與不能做什麼，見下面各節（管理節點、資產、授權規則、共用憑證與單台連線政策）；產品只記錄、不防止的情形（搬移資產或節點、修改範圍外也在用的共用憑證、降低單台政策、設定已知密碼、改資產位址導流、兩人合作）分別在那些節、前文的主機一節、身分管理員角色一節與 SSH 主機金鑰一節說明。
- 外部目錄的群組不能直接映射到資產管理員或授權管理員。請把外部群組映射到使用者群組，再把限定節點的角色指派給該使用者群組。
- 限定節點的指派不會變成全系統：指派所列的節點都不存在時，這筆指派不提供任何權限。指派所列的節點在指派存在期間不能被刪除（見「在限定範圍內管理節點」）。
- 自訂角色只有在所有功能都支援節點限定時，才能限定節點；另含只能套用到全系統的功能時，只能指派為全系統。
- 權限集合為空的自訂角色仍可以限定節點指派，但節點不會生效：回應的 `node_range_no_effect` 會列出它，管理介面也會顯示提示。含任一只能全系統生效或尚未實作節點限定的權限點的自訂角色，以節點指派時會被拒絕。
- 身分管理員可以指派超級管理者角色、系統安全管理員角色與含高風險權限點的自訂角色以外的所有角色（那三類只有超級管理者能指派），見下一節。

## 把身分管理員角色交給誰：它碰得到什麼，產品只負責回報什麼

**身分管理員與系統安全管理員是兩個鎖定角色範本：權限內容不能修改，指派方式與其他角色相同。** 升級後沒有人持有它們，要等有人指派：可以直接指派給帳號（帳號的「角色與範圍」分頁）、經使用者群組，或經外部群組映射（[部署與升級 SOP](./upgrade-sop.md#升到-1180權限模型遷移)）。建立帳號的表單只提供升級前就有的角色，範本請在帳號建立後再指派。角色管理頁面會列出這兩個範本，標示為內建、不能修改。下面列出的限制，包括對超級管理者帳號的限制，以及超級管理者、系統安全管理員兩種角色的指派限制，在上述每一條途徑上都適用。

身分管理員是給負責帳號與角色指派的 IT 或 SRE 人員的角色，不是受限角色。持有者可以把下面所列受保護角色以外的任何角色，發給任何人，包括自己，也可以把人加進帶連線授權的群組，所以實際上除了受保護角色的權限，幾乎所有權限他都碰得到。只交給可信度接近超級管理者的人。

- **這個角色自己做不到的事。** 對帳號或使用者群組指派或移除超級管理者、系統安全管理員角色，異動帶這兩種角色的群組的成員，以及刪除這種群組，限超級管理者。自訂角色只要含任何一項高風險權限，也同樣是受保護角色。高風險權限是能刪除證據、關閉或改道告警、放寬安全控制或管理金鑰的權限：刪除錄影（`recording:delete`），管理系統告警、告警規則、通知通道與 syslog 轉發（`systemalert:manage`、`alertrule:manage`、`notification_channel:manage`、`syslog:manage`），管理安全政策與政策群組（`securitypolicy:manage`、`policygroup:manage`），以及管理金鑰與離機儲存（`key:manage`、`offsite:manage`）。指派或移除這種角色、異動帶這種角色的群組的成員，以及刪除這種群組，限超級管理者。對超級管理者帳號設定密碼、停用多因素驗證、綁定外部身分或寫入直接角色，也限超級管理者。停用、刪除或啟用持有這兩種角色（不論來源）的帳號，以及解除外部身分綁定並停用帳號，同樣限超級管理者，被拒絕的請求會連同原因記入稽核。對這類帳號的其他操作，例如單純解除外部身分綁定、編輯基本資料、解除登入鎖定，照一般規則。
- **系統安全管理員的帳號，有幾項操作擋不住身分管理員。** 停用、刪除或啟用這個帳號會被拒絕（見上一項），但身分管理員可以替它設定密碼、停用它的多因素驗證，或綁定、解除外部身分，產品不會阻止。每次這類操作都在同一個交易內寫入稽核，並觸發給資安人員的系統告警。這是事後偵測。兩個角色之間的職責分離，因此只在身分管理員同樣可信時成立。部署時就決定誰持有系統安全管理員角色。產品不阻止同一人兼任兩個角色：角色指派的預覽請求（`POST /api/v1/role-assignment-previews`）會回報這個組合，但指派本身不必先預覽，也不會被擋下。
- **發放只回報，不阻擋。** 儲存角色指派或群組異動之前，可以先用預覽請求查看受影響的人合起來的權限是否形成高風險組合。預覽結果只是提示，不會阻止變更。變更之後，改動自己的授權會觸發系統告警，把管理類角色發給他人也會；把一般角色發給他人，或把人加進只帶連線授權的群組，不觸發告警，只留在一般稽核。兩個人串通的情形不在上述任何一項的涵蓋範圍內。

## 在限定範圍內管理節點：搬移能改變什麼，哪些動作只有超級管理者能做

含節點管理的角色可以只指派在部分節點上。持有者只能在這些節點及其子樹內建立、改名、改描述、搬移與刪除節點。下面寫的是產品實際攔住的，以及只留紀錄的。

- **搬移節點或資產可能改變誰被涵蓋，產品不阻擋。** 管理範圍與連線授權是分開的。同一段樹上兩者都持有的人，可以把節點或其下的資產搬進自己已有連線授權的節點，替自己擴大連線範圍；搬移也可能讓他人的連線授權與審核範圍不再涵蓋某些資產。這兩種情形產品都不阻擋。每次節點搬移的稽核紀錄會列出因此新增或失去涵蓋的資產，以及受影響的授權、審核範圍與管理範圍，只含識別碼，每份清單最多列 100 筆並附總數。有人在同一批節點上同時持有這兩種權限時，請檢視這些紀錄。
- **被管理範圍引用的節點，任何人都不能刪除。** 只要有任何角色指派（在帳號或使用者群組上）把該節點當成範圍節點，刪除就會被拒絕並回 `RULE_NODE_SCOPE_REFERENCED`，超級管理者也一樣。超級管理者會收到引用此節點的指派清單（誰、哪個角色，群組另附成員數），並可從連結前往各帳號或群組頁修改；其他持有者只收到指派的筆數，看不到是誰。檢查以指派紀錄本身為準，因此被停用帳號持有的指派同樣會擋住刪除。
- **部分節點動作只有超級管理者能做。** 對持有者自己範圍的根節點改名、改描述或刪除，會被拒絕並回 403；在最上層建立節點、把節點搬到最上層也一樣。搬移只允許嚴格位於持有者範圍根之下的節點，而含有任何指派用作範圍節點的子樹，其搬移一律限超級管理者。節點管理不限範圍的持有者（即涵蓋全部節點）只受最後這一條與結構檢查（深度、同名、環路）約束。
- **範圍外的節點不能操作。** 對範圍受限的持有者，對範圍外或已刪除節點進行操作的請求，回應與從未存在的節點相同，皆為 404。節點樹與列表含持有者管理範圍內的節點，以及持有者有連線授權的資產所在的節點。這些節點的上層路徑一併列出，只用來定位：範圍外的路徑節點會標示為只是路徑，不可操作。
- **解除節點的範圍用途是另一個步驟。** 節點被指派用作範圍時刪除會被拒絕，必須先到帳號或群組頁修改該指派；產品不會在刪除節點時順帶移除指派。
- **共用憑證的歸屬節點依範圍限定。** 只被指派到部分節點的人建立共用憑證、把憑證轉為共用，或變更它的歸屬時，只能選擇自己範圍內的節點；見下方共用憑證那一節。本節只涵蓋節點管理；把資產建立與編輯限定在部分節點時的行為，見下一節。

## 在限定範圍內管理資產：它不授予什麼，產品只負責記錄什麼

包含資產管理的角色可以只指派給部分節點。持有者可在該範圍內檢視、編輯、測試、停用與刪除掛在這些節點上的資產，並管理其帳號。下列限制說明產品強制執行什麼、只記錄什麼。

- **管理一台資產，不等於取得從平台連線到它的權限。** 管理範圍與連線授權是分開的。能編輯或刪除某台資產的人，只有在另有連線授權涵蓋他時才能對它開啟連線。資產列表中只因管理範圍而看得到的資產，會顯示為未授權連線，也沒有連線入口。管理範圍同樣不涉及主機本身，見前文「產品角色管不到的地方：主機」。
- **建立資產或變更資產所掛的節點，可能改變誰被涵蓋，產品只記錄。** 對樹的同一部分同時持有管理範圍與連線授權的人，可以把資產掛到自己已有連線授權的節點上，藉此擴大自己的連線範圍。掛載也可能讓資產落入其他人的連線授權與審核範圍。產品不阻擋這些情形。資產初始掛載與每次節點變更所寫的稽核列，會列出加入與移出的節點，以及因此新增或失去涵蓋的人員與管理範圍，只有識別碼，每個清單最多 100 項並附總數。這適用於所有操作者。經批次匯入建立的資產，只有在操作者的資產建立權限只經部分節點的指派持有時，其初始掛載才附這項記錄。當某人對同一批節點同時持有兩種權限時，請檢視這項記錄。
- **改資產位址可能把託管的登入憑證送到別處，產品只回報。** 能編輯資產的人可以把它的主機或連接埠指向另一台機器，包括自己控制的機器。後續連線嘗試會改用新位址。適用的檢查允許進入認證時，平台才會以資產託管的登入憑證向該位址的伺服器認證。連線測試需要資產測試權限 `asset:test`，不需要連線授權；是否進行認證則依協定而定，見下文。資料庫的連線測試只建立 TCP 連線，不送出任何憑證。變更主機、連接埠或協定時，不論由誰變更，都會在同一交易中產生 `asset_address_changed` 系統告警；關閉 RDP 憑證驗證、調降資料庫 TLS 模式或把 Kubernetes 設為略過驗證，則產生 `transport_verification_relaxed`。兩者都讓安全人員事後得知，既不阻止變更，也不阻止憑證送出。對同一台資產同時持有管理範圍與連線授權的人，可以獨自完成整個過程。授予資產編輯權限時，請比照範圍內資產託管憑證的審慎程度。平台對新位址上的對方檢查到什麼程度，取決於協定與資產設定：
  - **SSH。** 出示的主機金鑰與這台資產的記錄比對，與位址無關。資產已有金鑰記錄，且不是重置後等待重新記錄時，出示的指紋與記錄不同才判為不符。查核及不符留痕成功後，使用者終端、檔案傳輸與連線測試繼續進入認證，改密與憑證輪替則停止（見「SSH 主機金鑰與記錄不符時」）。另一台機器若沿用相同主機金鑰，這項比對不會判為不符。資產還沒有記錄時，改與其他資產對新位址留下的記錄比對；該位址也沒有記錄時，首次連線即記錄對方出示的金鑰並繼續連線，不會警示。之後若用密碼認證，密碼就交給了那台機器；公鑰認證不會送出私鑰。
  - **RDP。** 除非資產開啟憑證驗證（`rdp_verify_cert`，預設關閉），否則不驗證伺服器憑證。RDP 資產的連線測試即使開啟了這項設定也不驗證。
  - **VNC。** 不檢查伺服器的身分。
  - **資料庫。** 只有資產的 TLS 模式為 `verify-ca` 或 `verify-full` 時才檢查伺服器憑證。模式未設定、或設為 `disable`、`require` 時，不檢查新位址上回應的是誰。
  - **Kubernetes。** 除非資產設為略過驗證（`k8s_insecure_skip_tls`），否則以資產設定的 CA 或系統信任的憑證機構驗證 API 伺服器憑證。
- **掛在持有者範圍之外仍有節點的資產，該持有者不能刪除或停用。** 請求會以 `RULE_ASSET_HAS_OUT_OF_SCOPE_NODES`（409）拒絕，回應只帶範圍外的節點數。持有者可以把資產從自己範圍內的節點移出，移出後該資產就不在他的範圍內。以全域指派持有該權限點的人不受這項規則影響。
- **未分組資產。** 對沒有掛在任何節點的資產，以全域指派持有刪除或停用權限點的人，可照常刪除或停用，並照常留下稽核。只以部分節點的指派持有該權限點的人，得到與資產不存在相同的 404。
- **經管理範圍看到的資產，範圍外的節點不顯示。** 對範圍受限的持有者，經其範圍看到的資產，列表與詳情只顯示範圍內的節點，以及範圍外歸屬的數量。只經連線授權看到的資產，照現行顯示其節點。建立與編輯資產的回應依同一規則。持有者以全域指派可以建立或編輯、但從範圍與連線授權都看不到的資產，回應只帶範圍外歸屬的數量。儲存資產時，持有者看不到的歸屬會被保留。
- **資產的批次操作沒有筆數上限。** 後端不限制一次批次搬移、加標籤或刪除請求所列的資產數量。請求本文仍受內建前端代理的本文大小上限約束（預設 1 MiB，約十萬筆識別碼的量級），超過時在送達後端之前即回 413。整批在單一交易內執行，耗時隨資產數量增加；執行期間，同時進行的其他拓撲相關寫入會變慢。產品不以筆數阻擋大批量，也不給出耗時數字；若這對你的部署有影響，請自行把很大的批次拆小。
- **內建角色。** 內建的一般使用者與審核者只在指派給全系統時生效。限定節點後，若是能通過其他指派關卡的使用者直接指派，系統照常儲存，但這個指派不產生任何權限，回應的 `node_range_no_effect` 會列出它，管理介面也會在該角色上顯示提示。審核者仍不能指派給使用者群組。超級管理者與稽核員含只能套用到全系統的權限，不能限定節點，請求會被拒絕。資產管理員與授權管理員範本就是為指派給部分節點設計的（見「角色與各自管理的範圍」）。

## 在限定範圍內管理授權規則：範圍涵蓋什麼，防自我授權檢查的限度

當授權規則管理權限（`authorization:manage`）的指派限定在部分節點時，持有者只能對範圍內的資產與節點建立、調整與刪除授權規則。下列限制說明產品強制執行什麼、不涵蓋什麼。

- **範圍限制的是規則的客體，不是主體。** 使用者、使用者群組與 agent 不屬於任何節點，所以範圍受限的持有者可以把任何現有的帳號或群組，當成範圍內資產或節點上規則的主體。授權畫面用的選擇器只回固定欄位（帳號：ID、登入名稱、顯示名稱、種類、狀態與角色名稱；群組：名稱、說明與成員數），不含電子郵件、登入紀錄或其他帳號細節，也不會授予開啟帳號頁或寫入帳號的能力。選擇器回傳的識別碼，是規則用來指向該帳號或群組的值。
- **範圍外的請求，得到與不存在相同的回應。** 請求指名範圍外的資產或節點，或指名客體在範圍外的規則，得到與不存在的資產、節點或規則相同的回應：寫入與單筆查詢為 404，列表與選擇器的篩選為空結果。範圍受限的持有者送出的批次請求，只要其中任一客體在範圍外或不存在，整批拒絕、不寫入任何資料；回應只帶無法使用的客體數。沒有範圍限制的持有者，收到的是原有的回應。
- **規則列表不會列出所有觸及範圍內資產的規則。** 對範圍受限的持有者，列表只含客體在範圍內的規則。掛在範圍之上的節點、同時涵蓋範圍內資產的規則不會列出，該持有者也無法變更它。兩個有效權限視角仍會列出所有能連到範圍內資產的人，包括經由這類規則的人。在這些視角中，規則不在持有者的列表內時，回應一律不含規則識別碼。範圍之上的祖先節點會顯示名稱與路徑，只作定位用。路徑若經過其他範圍外的節點，回應不含節點名稱與路徑，只帶範圍外歸屬的數量。持有者因此能看到某人對範圍內的資產有存取權，卻看不到也無法移除給予該存取權的規則。
- **調整規則的帳號範圍，不再需要超級管理者。** 持有這項權限的人可以縮小範圍內規則的帳號範圍。擴大則限規則的建立者與超級管理者。主體是持有者本人、持有者所屬群組或持有者所擁有 agent 的規則，該持有者不能調整。臨時授權的帳號範圍不可變更，有關聯申請單的臨時授權不可直接刪除。
- **防自我授權檢查只在建立或調整規則的當下判定。** 檢查會拒絕主體是操作者本人、操作者所屬群組或操作者所擁有 agent 的規則，超級管理者不受此限。之後不會再判一次：為某群組建立的規則，不會因為事後有人加入該群組而被重新考慮。檢查也不看兩個人之間的關係。兩位持有者各自對對方建立規則，產品兩筆都接受。請把這些當作檢查本身的限度，並據此檢視誰持有這項權限與稽核紀錄。
- **範圍涵蓋所有受影響資產的持有者，可以撤銷臨時授權。** 除了超級管理者、原核准人與範圍命中的審核者，持有這項權限的人在撤銷所變更的每一台資產都在自己範圍內時，也可以撤銷臨時連線授權。指派沒有範圍限制的持有者，範圍涵蓋全部資產；因此本版中，全域持有這項權限的非超級管理者（例如透過自訂角色），可以撤銷任何臨時授權。整單撤銷時，這些資產也包含撤銷一併結束的待審項所涉的資產。其中任何一台在範圍外，這條途徑就不適用，改由既有規則裁決。agent 帳號不會因這項權限而取得此能力。以上途徑都不符的持有者，會被以 403 拒絕。
- **每次撤銷本身寫兩筆稽核紀錄。** 撤銷與它的稽核紀錄在同一個交易內儲存，稽核紀錄寫不進去，撤銷就不會儲存。交易提交並收線會話之後，同一動作的第二筆紀錄會記下哪些會話被結束。第二筆寫不進去時，只留下一行 log，撤銷依然成立。這適用於每一次撤銷，超級管理者的也一樣。每個已認證的 API 請求都會產生的請求紀錄另計，因此經 API 做的一次撤銷，共留下三筆同一動作的紀錄。
- **只指派給部分節點的做法。** 這項權限（`authorization:manage`）只指派給部分節點時，經角色指派的兩個整組替換入口寫入：`PUT /users/:id/roles` 與 `PUT /user-groups/:id/role-bindings`，使用 `role_nodes` 欄位（見 API 規格）。在管理介面，可在使用者或使用者群組的「角色與範圍」分頁把該角色設為指定節點來選擇節點，分頁會顯示資產列表管理範圍的試算台數，這不是角色所有操作可作用的資產數。內建的授權管理員角色含這項權限，可以指派給部分節點。只指派給部分節點，限制的是權限適用的範圍，不會因此授予連線到這些節點下資產的權限。本節描述的是產品對只指派給部分節點的指派所採的處理。

## 限定範圍內的共用憑證：影響確認擋得住什麼，擋不住什麼

共用憑證的歸屬是全域或某一個節點；只被指派到部分節點的資產管理員，管理的是歸屬在自己範圍內的共用憑證。共用憑證仍然可以掛在歸屬者範圍之外的資產上，所以修改它，可能影響到它的管理者並不管理的主機。

- **更正共用憑證的登記值，或對它改密，都會套用到它掛載的每一台主機，包括這個人範圍之外的主機。** 更正一次更新全部掛載；改密則透過遠端連線，逐台更換每台掛載主機上的密碼。只想改自己範圍內的主機時，先把那幾台逐台從這筆共用憑證脫離；脫離會更換該台的密碼，並讓它擁有自己的憑證。
- **確認只證明這個人被告知過，無法阻止這項修改。** 兩個動作送出之前，畫面會顯示掛載的主機中有多少台在這個人的範圍內、多少台在範圍外（只有台數，範圍外的主機不列名），並要求勾選知情。勾選之後，這個人也能一併修改範圍外主機所用的憑證。產品不把這當成對「有意越過範圍者」的防護，它只確保修改送出之前，伺服器已經向這個人回報過範圍外的台數。請把「更正或改密共用憑證」的權限，視同對它掛載的每一台主機的權限。
- **伺服器實際檢查什麼。** 確認連同當時範圍外主機的集合，保存在伺服器上。它只對該使用者、該憑證、該動作有效，且只能使用一次。送出修改時，範圍外集合只要含有確認時不在其中的主機，即使台數相同，請求也會被 `RULE_CREDENTIAL_IMPACT_CONFIRMATION_REQUIRED`（409）拒絕，不改動任何東西；集合裡的每一台都已在確認時的集合中，修改就照常進行。確認沒有到期時間。
- **記錄什麼。** 該次修改的稽核紀錄會記下範圍外主機的台數與確認識別。
- **怎麼處理。** 授予 `credential:set-secret` 與 `credential:rotate` 時，請比照「可以登入該憑證掛載的每一台主機」的標準審慎；若不希望其他管理者的主機能經由某筆憑證被觸及，就把該憑證的掛載限制在歸屬節點的範圍內。

## 單台資產的連線政策：誰能改，產品只負責回報什麼

每台資產可以有自己的連線政策（`open`、`reason` 或 `approval`），蓋過全系統預設。設定或清除這個覆寫是獨立的權限，即授權規則群組的存取政策權限（`access_policy:manage`），不屬於資產編輯：只能編輯資產、沒有這項權限的角色無法送出此欄位，請求只要帶 `access_policy`（包括用來清除覆寫的空字串）就整筆拒絕。建立資產帶非空值、批次匯入任一列帶非空值也一樣：整個請求或整批拒絕，不寫入任何資料。持有者不需要資產編輯權限就能只改這一個欄位；請求若另外帶了其他欄位，就同時需要資產編輯權限。不論這項權限涵蓋全部節點或只涵蓋部分節點，持有它都不能改全系統預設；全系統預設只能由持有安全政策管理權限（`securitypolicy:manage`）的人修改。內建的授權管理員角色含存取政策權限，且可限定節點；內建的系統安全管理員角色含安全政策管理權限。超級管理者以保留身分兩項都具備；其他內建角色都不含這兩項權限。

- **降級只回報，不阻止。** 變更使資產的有效段位下降時，不論是把覆寫調低，或清除覆寫而回落到較低的預設，不論操作者是誰，都會在同一交易內寫入操作日誌，並產生 `access_policy_relaxed` 系統告警。維持或調高段位的變更，以及新建的資產，不產生告警。告警載明資產、操作者與調整前後的段位。兩筆紀錄任一寫不進去，這次變更就不會儲存。指派只限部分節點的持有者，對範圍內資產的變更也照這個方式處理。
- **限制。** 持有這項權限的人可以把覆寫調低；若另有他人給了某人這台資產的常設連線授權，那個人之後就能免審連線。產品留下操作日誌與系統告警（產品沒有刪除的途徑，只會依告警保留期限清除），不阻止調低，也不阻止之後的連線。決定誰持有這項權限時請把這點算進去。
- **只限部分節點的指派，只涵蓋範圍內的資產。** 這項權限的指派限定在部分節點時，持有者只能對至少掛在一個範圍內節點上的資產設定或清除覆寫。對範圍外的資產，請求得到與資產不存在相同的回應，不做任何變更。建立帶非空覆寫的資產，或批次匯入時有任一列帶覆寫，該資產的節點至少要有一個在範圍內；否則整個請求或整批被拒，方式與不持這項權限的人相同。已覆寫資產的清單對這類持有者只列範圍內的資產；資產另外掛在範圍外節點時，歸屬清單只列範圍內的節點。所列節點的完整路徑仍含定位用的祖先名稱，即使祖先在範圍外；其他範圍外的歸屬只告知個數。範圍只看這項權限本身的指派：對其他節點持有資產檢視、資產編輯或連線授權，都不會擴大它。
- **只持這項權限的人沒有可完成設定的網頁流程。** 角色只給了這項權限與資產檢視、此外沒有其他權限的人，目前沒有可完成覆寫設定的網頁操作流程，請使用 API。
- **只指派給部分節點的做法。** 這項權限（`access_policy:manage`）只指派給部分節點時，經角色指派的兩個整組替換入口寫入：`PUT /users/:id/roles` 與 `PUT /user-groups/:id/role-bindings`，使用 `role_nodes` 欄位（見 API 規格）。在管理介面，可在使用者或使用者群組的「角色與範圍」分頁把該角色設為指定節點來選擇節點，分頁會顯示資產列表管理範圍的試算台數，這不是角色所有操作可作用的資產數。內建的授權管理員角色含這項權限，可以指派給部分節點。只指派給部分節點，限制的是權限適用的範圍，不會因此授予連線到這些節點下資產的權限。本節描述的是產品對只指派給部分節點的指派所採的處理。

## 對外走純 HTTP 時的登入狀態保存

**對外仍為 http 的部署，須把安全政策的「登入狀態僅在 https 連線保存」關閉。**
登入狀態由一枚 HttpOnly cookie 保存，該政策鍵為預設值（開啟）時瀏覽器只在 https 連線下
保存與回送它；純 http 之下它根本不會被保存。使用者仍可登入，但重新載入頁面、開新分頁
或關掉分頁再回來都會回到登入頁——瀏覽器端沒有留下任何可用來恢復登入的東西
（access token 只存在頁面執行期記憶體，不落瀏覽器儲存）。

判讀方式：登入後按重新整理即被要求重新登入，而登入頁本身會說明成因。
處置有兩條，正解是為對外入口配置 https；在此之前於安全政策關閉該鍵即可恢復正常的
登入保存，代價是登入狀態的憑證會在未加密的連線上傳輸——那與整個部署走 http 的
風險同級，不是額外新增的風險，但也不該當成長期狀態。

## 外部身分來源賦予的角色：那一端的變更何時生效

來自外部目錄或身分提供者的角色與使用者群組成員資格，是**在登入時、依該次登入帶進來的群組資料重算**的。
安全政策「外部群組映射重新驗證時限」（`mapping_revalidation_hours`：整數小時，預設 12，可設 0 或
1–168，0 表示不設限）限制兩件事：持有映射權限的帳號，網頁工作階段最長多久；登入時讀不到群組時，
上一次讀到該帳號的群組最久可以在多久以前，仍保留這些權限。工作階段從它自己的那次登入起算，上一次讀到的
時間只在登入時比對，所以這個時限本身並不是來源端收權的生效期限。每次登入只重算該次來源的映射。若
同一帳號可經另一個已綁定來源登入，原來源的映射可能持續保留，以下時限不是該帳號全部映射權限的撤權保證。
以下估算限於後續登入都經過同一映射來源、時限為正數且期間不放寬政策的情況。這些前提下的上界
（含最壞情形）見以下各點；凡部署方倚賴外部來源收回權限，以下幾點都會遇到。

- **時限有設（不是 0）時，網頁工作階段最長一個時限，從它自己的那次登入起算。** 持有任何映射權限的帳號
  （任一來源經映射取得的角色或使用者群組成員資格），網頁工作階段最長不超過這個時限；安全政策「Web 工作階段
  最長時數」較短時以它為準（下文稱為工作階段長度），從開啟它的那次登入起算，續期也不會延長。工作階段
  結束後，當事人必須再登入，該次登入依帶進來的群組重算它所經來源的權限。在此之前，已經開著的工作階段
  仍持有原本的角色。因此在上述前提下，若每次讀到的群組都已反映來源端撤權，收權後最長約為
  一個工作階段長度：當時開著的工作階段到期，下一次經該來源登入時依群組重算權限，或被來源拒絕。
  沒有映射權限的帳號只依「Web 工作階段最長時數」。
- **登入時讀不到群組，只要上一次讀到仍在時限內就保留映射權限，而這次登入開啟的工作階段可用滿整個長度。** 這包括該次登入讀不到帳號的群組（讀取失敗、值的型別
  不符，或權杖註明群組清單太長而未附上），以及來源有啟用中的規則卻沒設群組屬性名或宣告名。若該通道
  上一次讀到這個帳號的群組是在時限內，經映射取得的權限照舊保留，跳過重算一事記入稽核紀錄。若上一次讀到
  已超過時限、或從未讀到，該通道經映射取得的角色與使用者群組成員資格在這次登入收回，稽核紀錄記下
  `membership_revalidation_expired`，含通道、時限與上一次讀到的時間；因此確有權限被收回時，該帳號其他的
  登入隨之結束。之後某次登入讀到群組時，依該次群組與現行規則重新計算；只有仍符合規則的權限會被授予。
  管理者指派的角色與成員資格、經其他來源取得的權限，都不受影響。上一次讀到的時間只在登入時比對：
  因保留權限而開啟的工作階段從那次登入起算，不是從上一次讀到起算，續期時也不再比對讀到的時間；讀不到群組的登入也不算一次讀到。最壞的情形是來源端
  在上一次讀到之後隨即收權，卻仍讓當事人登入、只是不提供群組：若當事人在距離上一次成功讀到群組即將
  滿一個時限前登入，該次登入會保留既有映射權限，工作階段保持活動就能用滿整個工作階段長度。因此在上述
  前提下，該來源的映射權限在最後一次成功讀到該來源群組之後，最長約可再用一個時限加一個工作階段長度，至多是
  時限的兩倍；時限為預設的 12 小時、「Web 工作階段最長時數」為 0 或不短於 12 小時時，約為 24 小時。
  需要更快或確定停止該帳號的網頁存取時，請在本系統停用帳號，它的網頁工作階段與權杖續期即在當下結束
  （見下方「在來源端停用或刪除帳號」一點）。調短非 0 的時限會縮短觀測保留窗口。工作階段長度仍取此時限
  與「Web 工作階段最長時數」的較短者；若「Web 工作階段最長時數」一直較短，工作階段長度不變。
  既有工作階段會在續期時重新套用縮短後的上限。
- **升級到 1.18.0 之前就持有映射權限的帳號，可能在升級後第一次登入時失去這些權限。** 升級會把升級當下
  記為這些帳號上一次讀到群組的時間，所以時限從升級起算，升級本身不收回任何權限
  （[部署與升級 SOP](./upgrade-sop.md#升到-1180權限模型遷移)）。若帳號在升級後超過時限才第一次登入，
  而那次登入讀不到它的群組，映射權限就在那次登入收回。會遇到的是來源不提供群組資料的帳號：典型的是
  所屬群組太多、身分提供者無法放進權杖的帳號，或是有規則卻沒設群組屬性名或宣告名的來源。辨認方式：
  稽核紀錄裡該帳號有 `membership_revalidation_expired`，經映射取得的角色已不在。處理方式：讓來源提供
  群組資料（設好群組屬性名或宣告名，或減少權杖要帶的群組），改用直接指派角色，或把時限設為 0、
  接受映射權限從此沒有上界。
- **時限設為 0 時，映射權限沒有上界。** 來源端的收權改為在以下兩者較早者生效：當事人的下次登入，或網頁
  工作階段依「Web 工作階段最長時數」到期；登入時讀不到群組，不論上一次讀到是多久以前都保留權限。
  「Web 工作階段最長時數」也設為 0 時，持續活動的工作階段不會自行回到登入頁，來源端的變更可能無限期
  等下去；在來源端被移除的人，在這裡的映射權限保留到他下次登入。倚賴來源端收權的部署不宜把時限設為 0。
  把時限調長或設為 0，會產生 `mapping_revalidation_relaxed` 系統告警，帶前後時數；調短、或由 0 改為
  數值，只記入稽核紀錄。
- **時限管不到的地方。** 它結束的是網頁工作階段，以及隨之而來開新連線的能力；工作階段到期時已經建立的
  協議連線，不會因此中斷。若某次登入重算後確有角色被收回，該帳號其他開著的工作階段即在當下結束；
  在本系統內直接撤下角色是另一回事，同樣會在當下結束那些工作階段。
- **映射到高權角色的外部群組，成員由來源決定。** 映射到超級管理者或系統安全管理員角色的規則（直接映射，
  或經帶有這兩種角色的使用者群組），等於把「誰持有這個角色」交給在目錄或身分提供者管理該群組的人。
  在那一端被加進群組的人，下次登入即取得該角色，本系統內沒有任何超級管理者經手；那次登入會連同變動的
  角色記入稽核紀錄，不產生系統告警。在本系統內，建立、修改、啟用、停用、刪除這類規則，以及釘住這類
  角色，限超級管理者。
- **在來源端停用或刪除帳號不會同步到本系統。** 該帳號仍留在這裡的使用者列表上，角色維持
  最後一次重算的結果。透過該來源重新登入會失敗；改以本地密碼嘗試登入也會被拒絕並記入
  稽核紀錄。既有瀏覽器工作階段仍可使用原有角色並續期存取權杖，直到工作階段到期（持有映射權限的帳號，
  除非時限為 0，最長為工作階段開始後一個時限），或在本系統停用帳號、撤銷續期權杖為止。
- **巢狀群組展不展開，取決於來源。** 本系統採用登入時取得的群組資料，不再向來源另發查詢
  往上追群組鏈。目錄的群組成員屬性通常只報帳號直接所屬的群組，透過上層群組取得的成員資格
  看不到；身分提供者的群組宣告則可能已把巢狀展開。規則請照來源實際回報的內容填寫。
- **限定節點、又由外部群組給予的角色。** 一個限定節點的角色，若帳號同時透過管理者指派與外部群組映射持有，在「角色與範圍」分頁的「管理者指派的角色」移除它時，「來自映射的角色」中該角色那一列會顯示提示：此角色仍由外部群組給予，在這裡移除後改為全系統生效。提示不要求確認，也不阻擋儲存。儲存後，管理者的指派與它的節點限制消失，映射仍給予的角色改為全系統生效。

## 超級管理者請用本地帳號

**超級管理者角色請直接指派給本地帳號，不要交給經目錄或身分提供者登入的帳號。** 能管理身分來源的人，
可以改動來源設定，讓它改指向的目錄或身分提供者替經此來源登入的任何人放行，超級管理者也包括在內。
產品不阻止這類變更。來源設定的每一次建立、修改（含啟停與密鑰更換）與刪除，都在同一交易內記入
稽核紀錄，並產生 `identity_source_changed` 系統告警，列出變更的欄位，並寫明此來源目前有幾位超級管理者
可經它登入（經使用者群組取得該角色的也算在內）。bind 密碼與 client secret 只標示「已變更」，不帶值。
這是事後偵測。

來源遭接管時，本地超級管理者仍能登入並把來源設定改回；系統不會因來源被接管而鎖死，靠的就是這一點。
產品拒絕拿掉最後一位本地超級管理者（啟用中、以本地密碼登入、不由外部來源託管，且超級管理者角色
是直接指派給它的帳號；只經使用者群組或群組映射持有該角色的不算），不論是停用、刪除、移除角色還是
改為僅外部登入。對已經一位都沒有的部署，產品不會自行建立：請確認至少
有一位，並把它的登入資料放在需要時找得到的人手上。

## 系統安全告警與通知通道

產品對自身安全相關的變更，在變更的同一交易內產生系統安全告警，例如：身分來源的變更、對自己的授權變更
與對他人發放管理類角色、對系統安全管理員帳號的身分操作、資產位址的變更或傳輸驗證的放寬、自行設定的
秘密、外部群組映射重新驗證時限被調長，以及通知通道的變更。這些告警在告警頁以獨立的來源類別呈現，每筆
附各目的地的投遞狀態；有對應的操作日誌時，一併附上。

- **不能刪除，也不能停用。** 告警記錄只隨告警保留期限清除。告警頁的告警類型目錄列出每一種類型的預設與目前分級。類型唯一能調的是分級，
  由持有系統告警分級權限（`systemalert:manage`）者調整，每次調整都在同一交易內記入稽核紀錄。介面與 API
  都沒有刪除或停用類型的方式。
- **分級決定順序與標示，不決定是否產生或送出。** 每筆系統安全告警在產生當下，就為每一個啟用中的通知通道
  各排一筆投遞，不看該通道的推送門檻；門檻只篩選其他告警。調為低分級的類型照樣產生、照樣送出，只是可能
  較晚被處理。沒有任何啟用中的通道時，不排投遞，事後也不補送；有設定 syslog 轉發時照常轉發。
- **投遞至少一次，最長 72 小時。** 投遞佇列存在資料庫，重啟不會遺失。投遞失敗會以漸長的間隔重試，從 1 秒
  起、最長間隔 10 分鐘。自排入起滿 72 小時仍未送達即標為放棄：告警明細會顯示，伺服器日誌也有紀錄，
  沒有人工重送。接收端可能收到同一筆告警不只一次，請以 `delivery_id` 去重；它是告警排入時給每筆投遞的隨機識別，
  重試時不變，還原備份後也不會再次發出，接收端已見識別的紀錄在還原後仍然有效。啟用中的通道若儲存的網址或 secret
  已解不開，不會擋下產生告警的那個操作：告警照樣記錄並送到其他通道，該通道的投遞在告警明細與伺服器日誌中立即標為放棄、嘗試次數為 0。每筆投遞使用告警排入當下通道的網址與 secret；之後修改或刪除通道，不影響已排入的告警送往何處。
- **通知通道有自己的權限，任何變更都會送到新舊兩個目的地。** 管理通道（含測試發送）需要通知通道權限
  （`notification_channel:manage`）。系統安全管理員角色範本含此權限，身分管理員範本不含。新增、修改、
  停用、啟用或刪除通道，都在同一交易內記入稽核紀錄並產生 `notification_channel_changed` 告警，送到其他
  啟用中的通道，也送到這個通道變更前與變更後的目的地：改到別的網址、停用或刪除的通道，仍會送一則通知到
  它原本指向的地方。通道在同一交易內刪除，通知在提交後由佇列送出。
- **限制：管理通道的人，其本人動作的告警送往他改得動的地方。** 持有通知通道權限的人，可以先改告警的
  投遞去向，再去做會產生告警的事。產品不阻止。產品提供的是：每次通道變更都通知新舊兩個目的地，以及通道
  變更與該動作本身的稽核紀錄。決定誰持有這個權限時，請把這一點算進去。

## 證據保留、錄影刪除與守住它們的設定

本節說明產品對證據保留、以及可能移除或遮蔽證據的操作做了什麼。

- **四項資料保留天數設有下限。** 操作日誌、指令流、告警記錄與錄影的保留天數，都只接受 0（永久保留）或 7 到 3650 之間的數字。儲存 1 到 6 會被拒絕，同一批的其他項目也一併不生效。檢查點保留天數沒有自己的下限，仍受「不得短於它所證明的資料」這條規則約束。首次啟動時，環境變數 `RECORDING_RETENTION_DAYS` 若填 1 到 6 會被忽略，沿用出廠的 90 天。直接寫進資料庫的 1 到 6 會被讀回為最後一個合法值，沒有合法值時讀回出廠預設。
- **下調保留天數是通報，不是阻擋。** 下調四項資料保留天數中的任何一項（含由 0 永久改為某個數字），會在變更的同一交易內寫入稽核日誌，並產生一筆 `retention_shortened` 系統告警。調長、或改為 0，只寫稽核。調整檢查點保留天數只寫稽核，不產生告警。
- **錄影故障時的阻擋可以關閉。** 政策 `recording_failclose_enabled` 開啟時，錄影目錄不可寫入期間，超級管理者以外的人無法取得連線簽發；預設為關閉。把它由開改關會寫稽核並產生 `recording_failclose_disabled` 系統告警，由關改開只寫稽核。關閉時，錄影目錄不可寫入的情況下連線仍會建立，但故障仍會被偵測與上報：前置檢查及其告警不受這項設定影響，錄影失敗的會話會被標記並以錄影失敗寫入稽核。
- **下調全系統預設的存取段位**會在同一交易內寫入稽核，並產生 `access_policy_relaxed` 系統告警，內容載明有多少資產跟隨預設、且有效段位因此下降。調高或不變不產生告警。
- **停用 syslog 轉發、停用離機儲存，以及更改兩者或金鑰拓撲的指向**，都會在同一交易內寫入稽核並產生系統告警（`offsite_or_syslog_changed` 或 `key_topology_changed`）。syslog 指的是停用，或以和已儲存值不同的主機、埠或協定儲存為啟用狀態（含以不同目的地由停用改為啟用）；離機儲存指的是停用，或切換到不同的目的地（不論經確認步驟，或在目前目的地尚未上傳任何物件時直接切換）；金鑰拓撲指的是前後值不同的儲存。只改 syslog 的 TLS CA、或就地更新同一個離機目的地，只寫稽核。拓撲告警不帶位址或其他數值：前後值請到同一交易寫入的稽核列查看，兩者帶相同的關聯識別。稽核列或告警寫不進去時，變更不生效，轉發器也要等到提交之後才重新載入。有一個例外，見[特權憑證輪替](./privileged-credential-rotation.md)中金鑰重包的說明。
- **刪除錄影只有 API，產品介面沒有任何入口。** `DELETE /api/v1/sessions/:id/recording` 需要錄影刪除權限點（`recording:delete`）；這是設定組的全域權限點，超級管理者角色持有，自訂角色可以勾選納入。產品在同一交易內寫入稽核並產生 `recording_deleted` 系統告警，接著清除會話上的錄影欄位，提交之後才移除本機檔案。稽核列或告警寫不進去時，什麼都不會被刪。產品內沒有任何政策設定或角色能關掉這筆稽核；這句話不涵蓋主機層（見「產品角色管不到的地方：主機」）。這筆稽核與告警只會隨保留設定而消失。該會話已簽發的錄影播放票證會立即失效。
  - **提交後移除本機檔案失敗時**，會話已不再指向該檔，稽核日誌會另寫一筆失敗紀錄，檔案留在磁碟上成為孤兒檔。錄影保留清理不保證能移除這類檔案。錄影保留天數為正數時，清理會依檔案修改時間嘗試移除；造成移除失敗的原因若仍在，清理會以同樣方式失敗，且該輪清理在這個檔案處中止。設為 0（永久保留）時沒有任何機制自動移除。請先排除原因，或手動移除該檔。
  - **已上傳到離機儲存的副本不會因這項操作而被刪除。**
- **告警保證的是建立並留痕，不是有人收到。** 告警與變更寫在同一交易內；是否送達取決於通知通道，規則見上一節：沒有啟用的通道就不會排入佇列，持續失敗的投遞在 72 小時後放棄。不要把這些告警當作已有人被告知的證明。
- **限制：系統安全管理員角色，以及持有這些權限點的人，產品本身不加以限制。** 這些權限涵蓋金鑰拓撲、停用離機儲存與 syslog 轉發、刪除錄影、關閉錄影故障阻擋，以及管理通知通道。產品另外提供的是保留下限、刪錄影前先寫的稽核列，以及告警。它擋不住不適任的持有者，也擋不住同時兼任資產、授權或身分管理的人（產品對這種組合只警告、不阻擋）：這樣的人可以先動手，再抹除保留下限保護範圍之外的痕跡。請把這些權限交給資安或稽核人員，並檢查持有者與兼任的組合。
- **限制：持有者自己動作所觸發的告警，去向是他改得動的通道。** 管理通知通道的是同一批人，所以他們可以先改通道、再動手。產品提供的是每次通道變更都通知舊的與新的目的地，以及通道變更與該動作的稽核列；它不阻止這個先後順序。

## 改密通道的出站連線需求

改密由後端容器主動連向目標主機，不經前端 nginx、也不經使用者的瀏覽器。Linux 主機走目標的 SSH 埠；
Windows 主機依資產上設定的改密通道，走目標的 WinRM 埠（http 5985 或 https 5986，可另設）或 SSH 埠（預設 22，可另設）。
WinRM 的傳輸層**不讀取 proxy 環境變數、不跟隨 HTTP 轉址**，只走 HTTP/1.1；後端與目標之間若必須經代理或轉址，
該主機的 WinRM 改密連不上。https 的憑證驗證模式選 `system` 時，信任錨是後端容器作業系統的憑證庫，
內部 CA 簽發的監聽器憑證請改用 `ca` 模式在資產上傳該 CA。目標機前置條件見
[部署與升級 SOP](./upgrade-sop.md) §2.5 的 Windows 本機帳號改密段。

## 元件基礎系統的狀態（影響漏洞管理規劃）

**RDP／VNC 用的 guacd 容器，其基礎系統已停止安全更新。**

guacd 服務直接使用 Apache Guacamole 官方映像 `guacamole/guacd:1.6.0`、不做任何修改
（編排檔以版本加 digest 釘定），其基底為 Alpine 3.18，已過官方支援期。**這不是本專案的選擇**：官方的 `latest` 與 `1.6.0`
是同一顆 `alpine-minirootfs-3.18.12`，上游尚未提供較新的基底。

對你的部署規劃有兩點實質影響：

- **該容器的作業系統層不會再收到安全修補**，直到上游更新基底為止。
- **漏洞掃描對該映像的結果不可作為安全依據。** 掃描它會得到「零發現」，
  正確的判讀是「沒有資料」：已過支援期的系統不再有漏洞資料庫更新，
  且 guacd 本體是編譯後的二進位、不在套件清單內，掃描器看不到它。

現有的結構性緩解（隨預設部署即生效，非需另行設定）：

- guacd **不對外暴露任何連接埠**，僅存在於 compose 的內部網路；
  唯一能連上它的是本系統的後端服務。
- 錄影目錄是它唯一的共享掛載點。**啟用離機儲存不改變這一點**：guacd 仍然直接寫入本機錄影目錄，
  上傳是**會話結束之後**由後端另行進行的，guacd 不接觸物件儲存、也不持有任何儲存憑證。
  也因此，**崩潰路徑遺留的錄影檔不進離機**：會話異常中斷而未完成落地確認的檔案，系統不會為它建立上傳追蹤，
  由既有的本機清理機制處置——離機保存的涵蓋範圍是「正常結束並確認落地」的錄影。
  取回時落地的暫存區是**後端容器本地的快取**（有存活期與總量上限），同樣不與 guacd 共享。
- 這顆容器**以最小權限執行**，而且這幾項是由交付的編排定義施加、不是映像的性質：丟棄全部 Linux capability、
  拒絕經 setuid 檔案提權、根檔案系統唯讀。唯讀之下只留兩塊記憶體上的可寫區，兩塊都是實測需要才給的：
  RDP 磁碟重導的每連線暫存目錄，以及 RDP 函式庫啟動時要求可寫的家目錄。
  暫存目錄放的是使用者當下正在傳的檔案，所以出廠不設容量上限；要設的部署方直接修改交付的
  `docker-compose.yml` 中該 tmpfs 那一行，例如 `/tmp:size=512m`（compose 覆寫檔做不到：
  compose 對 tmpfs 條目是串接而非取代，同一個掛載點宣告兩次會被拒絕）。
  RDP 函式庫的已知主機信任庫落在其中一塊記憶體區，隨容器重啟歸零；本產品對目標主機憑證的處置
  由資產的憑證驗證設定決定，不依賴該信任庫的跨重啟持續性。
  唯讀根與兩塊掛載為 noexec 的記憶體區，使循協議進來的入侵無法改寫容器設定、也無法自暫存區執行；
  共享的錄影目錄仍是可寫且可執行的，那是錄影落地所需。
- **你可以把這顆映像換成自建或自選的**，改編排檔中 guacd 的 `image:` 行即可。本系統對這顆容器的要求只有三件：在 4822 埠提供 guacd 協議、
  能寫入編排定義掛給它的錄影目錄、映像內含 `sh` 與 `nc` 供編排施加的健康檢查判定是否就緒。
  上面那些都是容器的執行期屬性、不是映像的性質，所以換成任何映像之後，最小權限設定仍然生效。

**緩解不等於沒有風險**：若後端遭攻破，或被納管的遠端桌面主機透過協議回攻，
該路徑仍然存在。**漏洞管理政策若要求所有元件的基礎系統都在支援期內，
請在部署前就把這顆映像列入例外評估。**

**backend 仍以 root 執行。** 交付的部署設定與啟動程式逐項施加以下設定：

- `cap_drop: [ALL]` 丟棄能力集合，再以 `cap_add: [SETUID, SETGID, CHOWN, KILL, IPC_LOCK]` 僅加回五項能力：`SETUID` 與 `SETGID` 將 DB CLI 子行程切換至專用使用者與群組；`CHOWN` 將 CA 暫存檔的擁有權交給該使用者；`KILL` 允許對容器 PID namespace 內不同 UID 的行程發送訊號，包括 DB CLI 子行程；`IPC_LOCK` 允許鎖頁超過鎖定記憶體的資源上限。
- `security_opt: [no-new-privileges:true]` 禁止透過執行 setuid 檔案或檔案能力取得額外權限。
- `ulimits.core` 的 `soft: 0` 與 `hard: 0` 均為零；backend 也將自身的 `RLIMIT_CORE` 設為零。
- `PR_SET_DUMPABLE=0` 將 backend 行程設為不可傾印。配合未授予 `SYS_PTRACE`，容器內其他行程（包括受這組能力限制的 root 行程）無法讀取其 `/proc/<pid>/environ` 與 `/proc/<pid>/mem`。
- `ulimits.memlock: -1` 與 `mlockall(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)` 鎖住已駐留的記憶體頁，其他映射頁則在駐留時鎖住，防止這些頁被換出至 swap。

2026-09-12（Asia/Taipei）量測時，backend 使用上述記憶體控制，同時執行 15 個開發服務（backend 含 Air、dex、fake-gcs、frontend、guacd、k3s-test、ldap-test、localstack、mssql-test、mysql-test、postgres、rdp-test、ssh-multi-test、ssh-test、vnc-test）、量測用 client 與服務背景工作，沒有其他 Go 測試或端對端 smoke 測試，backend 在 0 條 active SSH 會話時為 VmRSS 68616 kB／VmLck 1369796 kB，在對 ssh-test 的 20 條並發 SSH 會話以 120×30 終端執行 echo 後保持開啟 45 秒時為 VmRSS 76952 kB／VmLck 1370060 kB；這兩次單點樣本是參考量測，不是保證的記憶體上限。

**金鑰材料仍在 backend 行程記憶體中。** 這些設定限制的是哪些其他行程讀得到它，並未移除金鑰材料，也不妨礙 backend 自身存取。它們無法防止控制主機或能變更部署權限的管理者讀取金鑰材料。

**自訂編排必須提供這些設定。** 丟棄全部能力後僅加回 `SETUID`、`SETGID`、`CHOWN`、`KILL`、`IPC_LOCK`，並施加上述權限與資源限制。在 Compose 中，鎖頁所需設定為 `cap_add` 包含 `IPC_LOCK`，以及 `ulimits.memlock: -1`；其他編排工具須提供對應的能力與資源限制。任何啟動控制無法施加時，backend 都會退出；鎖頁失敗會回報 `mlockall failed (check cap_add IPC_LOCK and ulimits.memlock)`。排查此錯誤時，請核對這些同名設定。

變更 capability 後必須重建 backend 容器，僅重新啟動不會套用新能力集合。`custodexa.sh upgrade` 啟動新版本時會重建它。在安裝包的部署資料夾手動重建時執行 `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend`；其他 Compose 部署執行 `docker compose up -d --force-recreate backend`。缺少 `KILL` 時，backend 可能無法終止 DB CLI 子行程。本地終端收線等待子行程回收最多一秒；終止或等待失敗、等待逾時會記錄日誌，接著繼續連線清理。單一背景等待會在子行程最終退出時回收它；缺少能力仍可能留下持續運行的子行程。

## 允許來源網段對部署的影響

**允許來源網段（`allowed_cidrs`）限制某個帳號可以從哪些來源位址使用系統。**
清單為空＝不限來源，那是預設值。它限制的是**可用來源**，不取代密碼政策、帳號鎖定或多因素。

### 先決定「來源位址」怎麼認定

本系統對「請求從哪裡來」只有一種取法，全部路徑共用：

- **未設定 `TRUSTED_PROXIES` 時，只採信 socket peer**——也就是 TCP 連線的對端位址。
  `X-Forwarded-For`、`X-Real-IP`、`Forwarded` 等轉送標頭**一律不採信**。
- 設定 `TRUSTED_PROXIES` 之後，轉送標頭才依你宣告的可信代理鏈解讀。
  **設定值非法時後端拒絕啟動**，不會退回預設值繼續跑。

預設不採信標頭是刻意的：那些標頭由呼叫端控制。採信它們，任何能發出請求的人都能為自己
那筆稽核列指定任意位址，也能靠每次換一個標頭繞開以位址為鍵的限制。

**把應用放在反向代理、負載平衡器或 CDN 後方而沒有設 `TRUSTED_PROXIES` 時，
系統看到的來源一律是那台代理的位址。** 三個後果：

- 允許來源網段判的是代理位址。填使用者的網段會把**所有人**擋掉；填代理位址則等於
  對所有經過該代理的人放行。
- 調查工作台的來源位址樞紐、稽核列與會話列的來源位址欄，全部記成代理位址。
- 新來源位址告警只在代理位址改變時才會響。

**預設部署自帶代理；原始碼樹的 `bash scripts/quickstart.sh` 與安裝包的 `custodexa.sh install` 會把 `TRUSTED_PROXIES` 填成該代理所在的 Docker 子網。** 自己跑 ingress 時這份清單由你來寫：填該 ingress 的位址，或它連進來的網段。

**要按真實來源判定與留痕，就得先設 `TRUSTED_PROXIES` 把代理鏈顯式列出來。**
這個決定要在啟用來源限定**之前**做：先設好清單再去改代理設定，會讓已經生效的清單
一夕之間對到另一組位址。

### 哪些入口會被擋，擋下來長什麼樣

清單非空而來源不落在其中時，下列動作一律被拒：

- 登入（含多因素完成、OIDC 交換）與強制註冊／強制改密的受限票證發放與消費。
- 網頁會話續期（refresh）。
- 連線簽發，以及文字終端與圖形兩條兌換入口——**兌換時各自現讀清單再判一次**，
  不沿用簽發當下的結論。
- 三個管理者端點——**替他人重設密碼**、**解鎖他人帳號**、**解除他人的多因素**
  ——依**操作者本人**的清單判定。

擋下來的回應**只說「此來源不允許」，不回顯位址，也不列出清單**。位址與命中的清單快照
只寫進稽核。連線類的拒絕另帶機器欄 `reason=source_not_allowed`，介面據此顯示
「目前來源不在允許範圍」而不彈出申請框。

**清單讀不到或內容損壞時一律拒絕**（不當成空清單放行），對外回應與「來源不對」
完全相同——分岔等於告訴呼叫端「這個帳號的政策壞了」。這種情況會在管理介面「操作日誌」頁的
「失效事件」分頁開一個 `source_policy` 事件，成因分「讀不到」與「字串損壞」兩類；
資料修好之後由系統自行結案。

### 收緊清單之前：先通知會被擋到的人

**收緊清單不會切斷已經在線上的人。** 具體是：

- 已發出的網頁存取權杖在其壽命內仍然可用，**殘窗上限是 15 分鐘**；之後的每一次
  `refresh` 續期都會被拒，使用者被導回登入頁，再次登入時就擋在來源判定。
- **已經建立的協議連線不會因為清單收緊而被主動切斷**，它會照常走到自己結束為止。
  下一次建線才會被擋。
- 「發出正式會話或受限票證」「寫入認證狀態」這一類動作，判定都在動作生效之前，
  所以收緊之後不會再有新的會話從清單外的位址長出來。

因此收緊清單的正確作法是**先通知**：告知受影響的人新的可用來源、生效時點，
以及被擋時該找誰。沒有通知就收緊，症狀會以「續期失敗、被踢回登入頁」的形式出現，
使用者無從分辨那是被限制還是系統故障。

### 管理者把自己鎖在外面時怎麼救

**系統不阻擋這種儲存**——管理者可能刻意設定一個尚未切換過去的網段。
介面只在儲存前就近顯示警告，不擋送出。

真的鎖住時，依序：

1. **還有其他管理者**：請對方在管理介面把清單改回來。這條路徑會留下欄位級的稽核差異
   （清單的前值與後值），是首選。
2. **沒有其他管理者可用**：走既有的離線重設路徑，以資料庫直連把該帳號的清單清成空字串。
   逐字步驟與 SQL 見
   [快速開始 — admin 密碼遺失、啟動被弱憑證掃描擋下，或管理者被來源限定鎖在外（離線重設）](../QUICKSTART.md#admin-密碼遺失啟動被弱憑證掃描擋下或管理者被來源限定鎖在外離線重設)。
   這一條**只需清清單，不必動密碼**。

離線重設**不經產品稽核**：它繞過應用程式直接寫資料庫，`audit_logs` 不會有對應的列。
**該次操作的留痕由部署方自己的變更管理承擔**（誰在什麼時候、依什麼授權動了資料庫）。
產品側事後看得到的，是復原之後的登入稽核列（含來源位址），以及回到介面重新設定清單時
留下的欄位級差異。清完之後不必重啟服務；**但也別停在清空狀態**——那等於任何位址都進得來。

### 新來源位址告警對營運的意義

某個帳號**首次**自某個來源位址建立協議連線時，系統產生一筆
`new_source_ip` 告警，並照既有的通知通道推送。同一組（帳號、位址）只響一次。

判讀時請注意三件事：

- **它是「以前沒從這裡連過」，不是「這次被擋下來」。** 是否放行由允許來源網段決定，
  兩者互不影響：清單為空時每一個新位址都會響，而清單擋掉的連線根本走不到建線那一步。
- **只登入不建線不會響**，只會把該位址納入基準；先登入再建線的典型流程仍會在建線時響一次。
- **升級當下已經看得到的位址不會響**：升級時系統自既有的會話全史與登入成功紀錄
  回填一份基準。全新安裝沒有歷史可回填，因此第一批連線都會各響一次，這是預期行為。

若你的使用者是浮動位址（家用寬頻、行動網路、VPN 出口輪替），這類告警會相當頻繁。
它適合當作「值得看一眼」的訊號，不適合當作阻斷條件——阻斷請用允許來源網段。

### 對備份與還原的影響

沒有新的落點。允許來源網段與來源位址基準都存在 PostgreSQL 裡，隨資料庫一起備份，
既有的[備份與還原](./backup-and-restore.md)程序不變、不需要額外步驟。

## SSH 主機金鑰與記錄不符時

平台第一次以 SSH 連到某台資產時，會記錄目標出示的主機金鑰。自 1.18.0 起，之後的連線若出示不同的金鑰，處理方式看有沒有人在場：使用者開的終端、檔案傳輸與連線測試由主機金鑰檢查允許繼續進入 SSH 認證，認證與通道都成功時使用者在終端或檔案管理會看到警示；改密與憑證輪替沒有人在場，會停止，不送出任何登入憑證或新秘密，作業以「主機金鑰不符」結束。自動化代理開的終端也同樣拒絕，不送出任何登入憑證。兩種情形都會在認證開始之前先寫一筆稽核（記錄中的指紋、這次出示的指紋、資產、使用者、連線，以及檢查的決定：允許繼續或已拒絕）。某個指紋第一次出現時另建立一則系統安全告警「主機金鑰與記錄不符」；有沒有人收到，取決於通知通道的設定與告警上顯示的投遞結果。實際嘗試認證之後，再以同一關聯識別補一筆稽核，記下登入憑證已送出與認證是否成功。

記錄維持原指紋，直到超級管理者處理。資產的主機金鑰區塊按最近出現時間列出最多 5 個待確認指紋，不是完整的不符事件歷史，完整歷史在操作日誌。超級管理者可以直接採用其中一個作為新記錄。重置仍然可用：重置後的第一次連線會把目標當時出示的金鑰記為新記錄，因此採用一個已核對的指紋沒有這段空窗。採用指紋與重置各會記錄並建立一則中級系統安全告警，記錄被改動的時點本身也有紀錄可查。

### 已知限制：向未確認的主機繼續認證

允許繼續不等於連線成功，而是平台接著以託管的憑證，向一台身分無法確認的主機進行認證。曝露什麼取決於認證方式：若向冒充主機進行密碼認證，對方可能取得密碼；公鑰認證只傳送公鑰與綁定本次 SSH 連線的簽章，不傳送私鑰。繼續連線仍會把工作階段及之後傳送的資料交給尚未確認的主機。稽核與告警讓你事後得知並追查，無法阻止認證發生；這種情形平台不提供防護。

這適用於使用者開的終端、檔案傳輸與連線測試。改密與憑證輪替（含經 SSH 輪替 Windows 帳號）以及自動化代理開的終端遇到不符會停止，不會把憑證送給目標；這不保護上述幾種連線。

閱讀這則告警時要留意：

- **每個新指紋告警一次。**同一台資產，某個尚未確認的指紋第一次出現時建立告警；之後以同一指紋連線，每次都寫稽核並在資產的主機金鑰區塊累計次數，不再建立告警。若這個指紋先前只出現在被拒絕的連線中（停止的改密或輪替，或自動化代理開的終端），之後第一次被允許繼續的使用者終端、檔案傳輸或連線測試會再建立一則，因為那是第一次向它嘗試認證。出現另一個不同的指紋會再建立告警。
- **告警寫的是檢查的決定。**「允許」表示已允許向這台主機繼續認證；「已拒絕」表示連線在認證之前就停止，沒有送出憑證：可能是改密或輪替已停止，也可能是自動化代理開的終端被拒絕。
- **稽核寫不進去時**（例如資料庫無法使用），連線會在認證之前中止，使用者看到「主機金鑰查核失敗」。
- **代理會話屬背景作業。**自動化代理經代理通道開的終端沒有人在場，遇不符時和改密一樣拒絕；分類由伺服端依連線票判定，不看客戶端自報的任何內容。
- **VNC 連線的檔案傳輸**由桌面閘道元件自行建立連線。平台對該位址已有主機金鑰記錄時，會把記錄交給該元件，元件在不符時拒絕檔案傳輸通道；這個拒絕只出現在元件自己的日誌，不會變成平台的告警或稽核。沒有記錄時元件照舊不驗主機身分就連線。這條通道不做首次信任，也不會把指紋加進資產的待確認清單。資料庫、Kubernetes 與 RDP 連線不使用 SSH 主機金鑰。

### 收到告警時

1. 向主機的負責人確認是否重灌或重新產生過主機金鑰，並把資產主機金鑰區塊列出的指紋與主機上的實際指紋比對。
2. 相符時，請超級管理者在資產的主機金鑰區塊採用這個指紋；警示隨之消失，改密、輪替與自動化代理開的終端也能恢復連線。無法事先核對指紋時才使用重置。
3. 不相符或無人能確認時，把第一則告警以來對這台資產用過的密碼都視為已外洩，在真主機上更換。公鑰認證不會送出私鑰，但與未確認主機交換過的工作階段內容都應視為已被對方看到。以稽核查出哪些人在何時連過。

### 升級時

原本因主機金鑰不符而被拒絕的資產，升級後使用者開的終端、檔案傳輸與連線測試會被允許繼續認證，每台在第一次連線時建立一則告警；這些資產的改密、輪替與自動化代理開的終端仍會被拒絕，直到超級管理者採用指紋或重置。升級前請先檢視目前因此連不上的資產，確認或重置。

## 對升級的影響

升級必須停機進行，不得滾動更新。程序見[部署與升級 SOP](./upgrade-sop.md)。安裝包部署由管理腳本執行升級，同樣是先停機、再備份的順序。

本版起，**新實例起不來的原因多一項：舊實例仍在執行，或它的資料庫工作階段殘留**。
殘留只發生在持鎖主機當機或網路分割造成的 TCP 半開；postgres 依作業系統的 TCP keepalive
回收該工作階段（postgres 容器未另行設定，走 Linux 預設約 2 小時）。啟動日誌會印出持鎖者
指紋與確認碼，救援程序見
[部署與升級 SOP §2.6b](./upgrade-sop.md#26b-若後端被攔下並指出單實例鎖由另一個資料庫工作階段持有)。
**救援不需要對資料庫做任何操作。**

互斥保證只在守衛版之間成立。首次自無守衛版升級時，新版取得鎖**不代表**舊版已停；
升級 SOP §2.3 的首次升級檢核是唯一的證據來源。

升級前請停止舊版的每一個實例，備機也包括在內。舊版與新版同時對同一資料庫運行時，在舊版上採用或重置的主機金鑰不會被新版看見，進行中的改密工作可能因此沒有察覺該主機的信任已經改變。這是接受的風險，系統不會阻止；金鑰改成另一把不同的，仍會被指紋比對攔住，暴露的情形是金鑰改了又改回記錄中的那把。系統唯一的回應是新版啟動時發出的系統告警 `concurrent_instance_detected`。偵測只認得帶單實例守衛的實例，寫入失敗，或查詢失敗而啟動並未被確認放行時，只在後端日誌留一行、別無其他，所以沒看到告警，不能當成沒有其他實例在運行的證據。步驟見[部署與升級 SOP](./upgrade-sop.md)。

執行期若失去鎖（postgres 重啟、工作階段被終止、網路事件），本實例**繼續服務**並每個週期重取。
期間管理介面顯示常駐橫幅、指標 `custodexa_instance_guard_held` 為 0、`audit_logs` 留有
`instance_guard` 事件；判讀見
[部署與升級 SOP §3.4](./upgrade-sop.md#34-執行期失去單實例鎖日誌橫幅與稽核事件的判讀)。

## 對可用性規劃的影響

單實例形態沒有自動故障接管，可用性規劃的著力點是縮短還原時間：讓備份與 KEK 材料
隨時就緒，回存程序事先演練過。見[備份與還原](./backup-and-restore.md)。
委託模式下，「隨時就緒」還包含兩件事：值班的人取得到保管處的憑證，以及每一次重啟都有人到場；
其代價見下一節。

還能再縮短的是**應用主機**（而非資料庫）故障後恢復服務的時間：資料庫放在另一台伺服器、
備援主機事先準備好，服務就靠「對同一個資料庫啟動備援主機」回來。那是由人或腳本執行的程序，
不是產品自己做的事。該程序事先需要什麼、保不住什麼（只有故障主機持有的錄影與其他檔案），
見[應用主機備援接手](./standby-takeover.md)。資料庫本身的損毀仍走備份還原。

**離機證據儲存改變的是「證據會不會丟」，不是「服務多快回來」。** 規劃時請把兩件事分開：

- **它縮短證據的暴露窗口，不消除。** 上傳是會話結束之後才發生的：文字錄影在秒級內排入，
  圖形錄影至少要等一分鐘（等檔案不再變動）；儲存端不可達時則一路等到恢復。
  **在那段窗口內，本機仍是唯一副本**——機器在此時毀損，該筆錄影就沒有第二份。
- **它不改變還原時間目標。** 遠端副本讓已離機的證據在機器毀損後仍取得回，但要讓系統重新
  提供服務，還是得走還原程序（資料庫、KEK、部署層設定）。**離機儲存不是備份的替代品**，
  兩者要一起規劃。
- **首次播放離機錄影有下載等待。** 本機副本已被清除的錄影，播放時要先由物件儲存取回、
  落地驗證雜湊之後才開始送出，等待時間隨檔案大小與頻寬而定。這是可預期的行為，不是故障；
  只在該錄影的第一次播放發生（暫存快取在存活期內可重用）。稽核作業若對回應時間有要求，
  請把這段等待算進去。

## 委託金鑰模式：這個部署不是無人值守

**採 `KEK_PROVIDER=kms`（AWS KMS、GCP Cloud KMS 或 HashiCorp Vault）時，本版的重啟一定要有人。**
連到保管處所用的憑證只保存在當次解封世代的記憶體，封存時即抹除，行程一旦結束就沒有任何地方讀得回來。
於是**每一次冷啟動都回到已封存**，在管理者解封之前只提供健康檢查與封存相關端點：
主機重開、容器重建、擴縮事件、夜間維護窗，以及還原後的第一次啟動都在此列。
**行程不會退出**——等待憑證是設計上的正常狀態，不是組態錯誤，靠監管程序重啟容器也解決不了它。

規劃上有三個後果：

- **每一次重啟都要有人聯絡得到**，包含計畫外的那些。選這個模式之前先定下由誰負責、非上班時間怎麼找人。
  `ui` 模式一向如此，`kms` 自本版起相同。`env` 是唯一能無人值守重啟的模式，代價是主金鑰以明文留在主機上。
- **自動擴縮與無人值守的重啟策略不適用本模式**：它們把一個無法提供服務的行程叫回來。
- **監控要對已封存狀態告警**，否則凌晨三點的重啟到早上九點才被發現。
  封存期間狀態仍讀得到：`GET /api/v1/seal/status` 與 `/metrics` 的封存那一組。
  `/metrics` 的取用與採集方式見[取用營運指標](#取用營運指標metrics)。

**解封頁要求什麼，以及這道驗證的邊界。** 管理者在解封頁輸入帳號與密碼，
拿畫面上顯示的保管處與部署紀錄核對，再重新提供該服務商的憑證。安全評估要納入兩條界線：

- **已封存狀態下只核對帳號與密碼，不核對動態驗證碼。** 動態驗證碼的種子受資料金鑰保護，
  封存時解不開，要求它會構成「先解封才能驗證、先驗證才能解封」的循環。
  **因此這一步不是雙因子，任何文字都不得這樣描述它。** 站在它背後的是：
  封存端點自身的來源退避與有時限的冷卻、`SEAL_UNSEAL_ALLOWED_CIDRS` 設定的來源網段、
  密碼錯與帳號不存在無法區分的回應、每一次嘗試在後端日誌留下的一行，
  以及效期十分鐘、每次使用都重新確認該帳號仍是啟用中管理者的授權脈絡。
  **已在鎖定期的帳號在這裡同樣被拒**；這一步不做的事是累加失敗計數或把帳號鎖起來——
  帳號鎖定政策屬於解封之後才存在的那一段。
- **帳號必須是本地管理者。** 由目錄服務或身分提供者建立的帳號在封存期間無法驗證，
  因為外部認證的路徑要解封之後才組裝。管理者全部來自外部來源的部署解不開自己，
  故至少保留一個本地管理者帳號——交付檢核清單本來就這樣要求。

**保管處設定放在哪裡。** 位址、服務區域、Transit 金鑰名稱與角色識別是資料庫裡的列，於金鑰管理頁設定；
每一次變更都以前後值寫入稽核，並經已設定的通知通道發出安全類告警，未設定通道時稽核列就是唯一的紀錄。
憑證既不在資料庫、也不在 `.env`。對備份與接手的影響因此是：設定隨資料庫備份一起走，憑證不會。
見[備份與還原 §4.3](./backup-and-restore.md#43-模式-ckek_providerkms金鑰保管處委託)與[應用主機備援接手 §2.2](./standby-takeover.md)。

## 資料金鑰的記憶體保留時間：這個設定用可用性換什麼

資產帳號密碼、側錄內容、目錄繫結憑證這類保存下來的機密，都是以資料金鑰加密後才存放，
而這把資料金鑰要先由主金鑰解開才能使用。安全政策的**資料金鑰的記憶體保留時間**
（金鑰管理頁）決定解開後的資料金鑰要留多久。

**留空是出廠預設，部署的行為與現況相同。** 資料金鑰解開一次後就留著，直到系統封存或行程重啟，
委託型的金鑰保管處不在日常運作路徑上。

**設為 0 或填入秒數，保管處就進入了運行路徑。** 保管處連不上的期間，凡是需要重新解開金鑰的動作
都會失敗：建立連線時取用資產帳號的密碼、連線進行中要寫入的側錄內容都在其中。這正是這個設定
提供的取捨——用可用性換取更短的記憶體停留時間——而且它不是當下能繞過的降級。

打開之前先定兩件事：

- **保管處連不上時新連線失敗可否接受、可接受多久。** 這要在選值之前回答，不是在第一次中斷之後。
  失敗時不會回退到先前的金鑰材料：解不開就是解不開。
- **自己這套保管處的一次往返要多久。** 每次重新解開就是一次呼叫，延遲隨區域、網路路徑與保管處
  本身而異。**請在自己的環境量測**，不要抄任何文件上的數字，再依量到的結果選值。

本機金鑰模式（主金鑰由環境變數提供，或由管理員在啟動時輸入）下，這個設定同樣可用，也同樣縮短
資料金鑰的存放時間。它不改變的是主金鑰本身：在這些模式下，主金鑰全程都在行程的記憶體裡。

稽核紀錄不在本設定的範圍內：為紀錄蓋章的金鑰不受保留期限影響，保管處連不上時紀錄仍寫得進去。
本設定縮短的是資料金鑰存在於記憶體的時間；操作進行中，記憶體裡仍然會有金鑰與資料原文。

## 取用營運指標（`/metrics`）

backend 在自己的 HTTP 埠（容器內 8080）的 `/metrics` 提供 Prometheus 指標。**預設部署下開 `https://<你的網域>/metrics` 拿到的是網頁介面，不是指標**：backend 的埠沒有發佈到主機，前方的代理也只轉 `/api` 與 `/ws`。這是刻意的預設。這個端點只在部署的 docker 網路內可達；要讓其他主機取得，是另一個決定，而且必須同時設定 token（見下方方式 B）。

- **認證**：`.env` 的 `METRICS_TOKEN` 為空（預設）時免認證。設了值之後，每個請求不論來自何處都要帶 `Authorization: Bearer <token>`；未帶或不符一律回 401，回應體不含任何指標。
- **系統封存期間**，`/metrics` 只有封存狀態、單實例守衛序列與 Go runtime、process 指標。其餘指標（稽核佇列也在其中）在解封後才出現（[升級 SOP §2.4](./upgrade-sop.md#24-停機前確認稽核佇列已排空)）。

### 臨時查看

在主機上，把請求放進 backend 容器內執行。正式版映像沒有 shell，但保留了 busybox 的 `wget`：

```bash
# METRICS_TOKEN 為空（預設）
docker exec custodexa-backend wget -qO- http://127.0.0.1:8080/metrics

# METRICS_TOKEN 有設值：token 取自容器自己的環境變數，
# 不會出現在主機的命令列上
docker exec custodexa-backend /bin/busybox sh -c \
  'wget -qO- --header="Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:8080/metrics'
```

結尾加上 `| grep '^custodexa_'` 可只留產品自己的序列。

### 用瀏覽器查看（經 SSH 通道）

backend 容器在 docker 網路上有一個主機連得到的位址。先在主機上讀出位址，再從自己的工作站把本機埠轉過去：

```bash
# 在主機上
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' custodexa-backend

# 在工作站上，填入上面印出的位址
ssh -N -L 9180:<backend 位址>:8080 <使用者>@<主機>
```

接著開 `http://localhost:9180/metrics`。這個位址在容器建立時配發，backend 重建後（升級、還原、改設定）要重新讀一次。瀏覽器不會送 `Authorization` 標頭：有設 `METRICS_TOKEN` 時，改在同一條通道上用 `curl -H "Authorization: Bearer <token>" http://localhost:9180/metrics`。

### 長期採集，方式 A：Prometheus 跑在同一台主機

把 Prometheus 以容器方式接進部署的 docker 網路，以容器名稱採集 backend。主機對外不必多開任何東西，代理也不用改。

網路名稱是 `<compose 專案名>_custodexa-network`。安裝包部署的專案名一律是 `custodexa`（[安裝包部署與管理腳本](#安裝包部署與管理腳本)），因此是 `custodexa_custodexa-network`；原始碼部署的專案名預設是所在目錄名，`COMPOSE_PROJECT_NAME` 有設時以它為準。在主機上確認：

```bash
docker inspect -f '{{range $name, $net := .NetworkSettings.Networks}}{{println $name}}{{end}}' custodexa-backend
```

最小的 `prometheus.yml`：

```yaml
scrape_configs:
  - job_name: custodexa
    static_configs:
      - targets: ["custodexa-backend:8080"]
    # 只在 METRICS_TOKEN 有設值時需要；檔案內只放 token 值本身
    # authorization:
    #   type: Bearer
    #   credentials_file: /etc/prometheus/custodexa-metrics-token
```

Prometheus 的 compose 檔，放在它自己的目錄：

```yaml
services:
  prometheus:
    image: prom/prometheus:<版本>
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:9090:9090"
    networks:
      - custodexa
networks:
  custodexa:
    external: true
    name: custodexa_custodexa-network   # 上面指令印出的名稱
```

這個網路要先存在 Prometheus 才起得來，所以先啟動 Custodexa。Prometheus 接在網路上時，網路無法移除：對 Custodexa 專案執行 `docker compose down` 之前先停掉 Prometheus，之後再把它啟動。

### 長期採集，方式 B：從另一台主機採集

從另一台主機採集，需要在 https 入口開一條通往 `/metrics` 的路徑，而且**沒有設 `METRICS_TOKEN` 就不得開這條路徑**：少了它，任何連得到這個位址的人都讀得到端點清單、各功能使用量與錯誤率。

**步驟 1：設定 token。** 產生一個值：

```bash
openssl rand -hex 32
```

寫進部署目錄的 `.env`，成為 `METRICS_TOKEN=<值>`。backend 在容器建立時讀取 `.env` 的設定，所以要重建容器，只重新啟動不會生效。在安裝包的部署目錄執行 `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate backend`；其他 Compose 部署執行 `docker compose up -d --force-recreate backend`。採 `KEK_PROVIDER=ui` 或 `kms` 時，重建後的 backend 會處於封存狀態，需要解封（[委託金鑰模式](#委託金鑰模式這個部署不是無人值守)）。完成後，「臨時查看」裡不帶 token 的寫法會回 401，帶 token 的寫法則回得出指標。

設了 token 之後，管理腳本升級前等待稽核佇列排空的檢查照常運作：它在 backend 容器內執行，用的是容器本來就有的 token。

**步驟 2：開路徑。** 做得到什麼，取決於部署前方是什麼。

- **內建代理（預設）。** 複製它的範本，並在 `.env` 以 `TLS_NGINX_TEMPLATE` 指向副本，做法見[快速開始：自訂反向代理設定](../QUICKSTART.md#自訂反向代理設定)。安裝包部署要複製的範本是 `current/reverse-proxy/nginx-tls.conf.template`，副本放在 `releases/` 與 `current/` 以外，例如 `tls/custodexa.conf.template`。在副本的 `listen 443` 那個 server 區塊內、`location /` 之前加上：

  ```nginx
      location = /metrics {
          set $backend_upstream http://backend:8080;
          proxy_pass $backend_upstream;
          proxy_http_version 1.1;
          proxy_set_header Host $public_host;
      }
  ```

  內建代理就在部署的 docker 網路上，所以能以服務名稱連到 backend，名稱在請求時經範本原有的 `resolver` 那行解析。套用方式：安裝包的部署目錄執行 `set -a; . ./current/images.env; set +a; docker compose --project-directory . up -d --force-recreate tls-proxy`，其他部署執行 `docker compose up -d --force-recreate tls-proxy`。副本歸你所有：管理腳本做的備份會包含它（[備份與還原 §3.8](./backup-and-restore.md#38-管理腳本做的備份安裝包部署)），升級不會改動它，所以每次升級後要與隨版本附的範本比對一次。
- **自備 ingress（external ingress overlay）。** 隨附的 compose 檔不替 backend 發佈任何埠。你的 ingress 只有在以容器方式接進部署的 docker 網路時才能轉 `/metrics`，這也是隨附範例能以 `frontend:80` 指到前端的前提；此時把精確路徑 `/metrics` 轉到 `backend:8080` 即可。裝在主機上或跑在另一台機器上的 ingress，只連得到前端發佈的埠，而前端只轉 `/api` 與 `/ws`，所以在隨附的部署形態下它碰不到 `/metrics`。這種情況請改用方式 A，或在部署的 docker 網路上放一個代理容器。

**步驟 3：讓 Prometheus 指向入口。**

```yaml
scrape_configs:
  - job_name: custodexa
    scheme: https
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/custodexa-metrics-token
    static_configs:
      - targets: ["bastion.example.com"]   # TLS_HTTPS_PORT 不是 443 時加上 :<埠>
    # 自簽模式（TLS_MODE=selfsigned）：信任部署的本地 CA，
    # 入口在 /custodexa-ca.crt 提供下載
    # tls_config:
    #   ca_file: /etc/prometheus/custodexa-ca.crt
```

token 檔只放 token 值本身，存取規則比照 `.env`。

### 該盯哪些指標

完整清單、標籤與各指標的意義見 [API 規格](../../API_SPEC.md#營運指標端點prometheus)。以下是五條起步用的告警，寫成 Prometheus 規則；持續時間與門檻請依自己的承諾調整：

```yaml
groups:
  - name: custodexa
    rules:
      # 不在服務中：已封存、解封中，或故障後封存。KEK 模式 ui 與 kms 的
      # 每一次重啟都會停在這裡，直到有人解封。
      - alert: CustodexaNotUnsealed
        expr: custodexa_seal_state{state="unsealed"} != 1
        for: 5m
      # 沒能寫進資料庫的稽核列。reason="fallback_file"：已降級寫入檔案，事後可回收；
      # reason="discarded"：已遺失。
      - alert: CustodexaAuditRowsDropped
        expr: increase(custodexa_audit_dropped_total[15m]) > 0
      # 非同步稽核佇列容量 1000 列；滿了之後，新的列走上一條的路徑。
      - alert: CustodexaAuditQueueBacklog
        expr: custodexa_audit_queue_depth > 500
        for: 5m
      # 尚未有人審閱的指令告警，依嚴重度分。
      - alert: CustodexaCommandAlertsUnreviewed
        expr: sum by (severity) (custodexa_command_alerts_pending) > 0
        for: 24h
      # 本實例沒有持有單實例鎖。
      - alert: CustodexaInstanceLockNotHeld
        expr: custodexa_instance_guard_held == 0
        for: 5m
```

另外加上常見的 `up{job="custodexa"} == 0`，涵蓋整個採集失敗的情況。系統封存期間稽核序列是缺席而不是 0，那幾條規則因此不會響；那個狀態由第一條規則涵蓋。各訊號的判讀：稽核列與降級檔案見[升級 SOP §3.1](./upgrade-sop.md#31-關機時會排空佇列但有時限)，單實例鎖見[升級 SOP §3.4](./upgrade-sop.md#34-執行期失去單實例鎖日誌橫幅與稽核事件的判讀)，系統不設上限的錄影儲存量見[快速開始：儲存監控](../QUICKSTART.md#儲存監控)。

## 輸出敏感資料偵測：射程與營運判準

偵測只掃 SSH、K8s 與資料庫主控台的解析後文字輸出；RDP/VNC 畫面、加密、壓縮或編碼內容（含 Base64）不在射程。終端控制序列不做渲染或剝除。編碼可繞過比對；命中表示輸出**可能含**敏感資料，未命中不表示不存在。本機制只告警，不阻斷或改變已送達的位元組。

輸出面規則的新增、停用與修改於**新會話**生效；進行中的會話沿用啟動時的規則集。升級、還原或接手後，核對規則方向、啟用狀態與協議，再建立新的文字會話驗證適用規則。安裝終態共有 16 條種子規則：原 12 條輸入規則、兩條 agent 輸入阻斷規則，加卡號與私鑰標頭兩條輸出規則。內建卡號 pattern 原樣時另做 Luhn 校驗；編輯 pattern 後視為一般正則，不再套用卡號校驗。

同（規則、會話）的命中於五秒窗內彙總，會話關閉時結算餘窗。告警列與轉發保留識別值、規則、次數與時間；command 為空，不存命中原文或位元組位移。reason_code 以 `o1:<base36 count>` 編碼次數；webhook 另提供 `possible_sensitive_output.count`。這些是「可能含」的訊號，不是全部輸出皆已掃描的證明。

有界佇列溢出會停用該場掃描，不中斷輸出。透過既有稽核查詢 action=`output_scan_disabled`、resource=`session` 與該會話的 resource_id；details 含 session_id 及 reason=`queue_overflow`，不含輸出原文。伺服端 log 不能代替這筆稽核列。該場後續輸出視為未掃描，依既有權限調閱證據，核對負載後建立新會話。掃描器失敗另留伺服端日誌；沒有告警不保證掃描成功。

共用遮罩原語回傳完整替換的文字與替換次數；**本版未接上任何產品回傳路徑**。遮罩不套用於錄影、指令紀錄或其他證據；原文繼續受既有留存、存取權限及備份／還原程序管理。


### 主體與憑證完整性涵蓋範圍

驗證頁分列角色指派、主體種類／擁有者與憑證狀態。升級後首次包含新項快照的封章前，新兩列為「尚未涵蓋」。偵測非即時：在驗證、封章及核發憑證前對帳；每項不符各開 `principal_state_integrity`／`principal_state_mismatch` 事件並通知，差集僅含識別值。發證不因不符或對帳錯誤中斷；錯誤記日誌並維持未知，不更動業務資料。服務層投影狀態列 actor 記 `system`，操作者由既有 HTTP 稽核列承擔。

回退為單向相容：新版可驗舊章，舊版無法完整驗證新快照鍵。不得刪鍵、重簽檢查點或還原舊的單機制失效唯一索引；回退必須使用升級前的一致備份並遵循還原程序。載荷版本沿用當時最新值（目前 v3）。

## Agent MCP 營運程序

建立 agent 主體並指定有效的人類 owner。由 owner 或管理員建立具名稱及期限的 agent token，將僅顯示一次的明文保存於執行者的秘密儲存處。agent 僅有 user 角色，資產與帳號授權須明確限縮。在 agent 所在的機器安裝 stdio 客戶端 `custodexa-mcp`，取自 https://github.com/custodexa/custodexa-mcp：執行 `go install github.com/custodexa/custodexa-mcp@latest`，或下載 release 二進位並以同一 release 發布的 `checksums.txt` 驗證。以環境變數 `CUSTODEXA_AGENT_TOKEN` 提供給 `custodexa-mcp`，`CUSTODEXA_MCP_URL` 指向 HTTPS 的 `/api/v1/mcp`；該入口不接受人類 JWT 或 cookie。stdio 客戶端只轉送，所有判定及證據寫入均在服務端；不要把 token 放入命令參數或報告。

agent 送出的任務要不要等人核准，取決於每個被申請資產的存取政策段位：資產本身設了 `access_policy` 就以它為準，否則取全域 `access_policy_default`。落在 `approval` 段的項目會維持待審，直到範圍涵蓋該資產的審核者做出決定；落在 `open` 與 `reason` 段的項目在建單當下即核准，記為 `auto_approved: true` 並保存政策快照，沒有核准票。出廠預設下多數資產不在 `approval` 段，因此未調整政策的部署會看到 agent 任務全數自動核准。要讓 agent 任務等人決定，請把相關資產的 `access_policy` 設為 `approval`，或把全域 `access_policy_default` 設為 `approval`；`access_request_min_approvals` 再決定這類申請需要幾張核准票。這個選擇請在給 agent 第一份資產授權之前定案並寫進營運手冊：自動核准仍然全程留痕，但它不是人為控制點。

輪替時先發新具名 token、更新執行者秘密、建立新的 MCP 連線並確認可視資產，再撤銷舊 token。沒有原地換 token 秘密或從備份自動找回明文的能力。撤銷會關閉由舊 token 建立的會話；句柄不能轉給新 token 或新 MCP 連線。還原或備機接管後須新建 MCP 連線，按需要重新申請任務；記憶體句柄與 60 秒冪等快取不跨重啟保存。續作前先核對保留的 token 與任務狀態。

事件處置先撤銷或停用涉事 token，必要時停用 agent，再核對任務、工具帳本與 HTTP 請求稽核。探測熔斷會停用 token 並記錄事件；owner 或管理員須附理由解除。解除不會恢復已停用 token，之後須另發新 token。它的計數只涵蓋一類引用：資產確實存在、且從未對該 agent 曝光過。引用不存在或已刪除的資產 id 歸類為 retired，引用曾經曝光過的資產歸類為 revoked，兩者都會留事件列，但都不計入跳閘門檻。隨機列舉 id 因此多半只產生不計數的事件，不可把這道熔斷說成通用的掃描偵測；它擋的是對範圍外真實資產的反覆探取，更廣的列舉行為請另以告警規則與開單速率政策涵蓋。判斷一次拒絕引用有多少意義之前，先讀熔斷事件列的 `class` 欄。通知沿既有 webhook／Slack 並帶 `owner_id`，不是私人收件匣，也不證明已送達本人。可視 exposure 自 migration 後開始，無法還原先前可視歷史；把拒絕引用認定為濫用前須核對這條邊界。

Token 到期、綁定任務項到期與任務關閉，皆終止存量會話及進行中的工具，不等待當前命令完成。期限每 250ms 現讀取樣，取樣間隔不是完成 SLA。撤銷沿既有收線路徑（目標 ≤3 秒，超時留痕）。僅控制本系統建立的會話，不保證遠端背景程序停止或撤回已做的變更。在途請求取消會關閉其會話；兩次 POST 間無法即時察覺客戶端離開，沿五分鐘 idle lease 到期收束句柄，不得稱為即時離線偵測。

`completed` 只代表再次觀察到提示符，不保證命令已結束或成功；提示符可偽造，背景輸出可交錯。`timed_out` 表示結果未知，重試前先觀察後續輸出。同句柄冪等鍵在 60 秒內避免重複寫入；不帶鍵可能再次執行。`needs_input` 須自行呼叫 `send_keys` 復位，系統不會自動送中斷鍵。`read_screen` 是行緩衝而非虛擬螢幕。agent 回傳文字經遮罩，錄影與指令紀錄保留原文。遮罩是規則驅動、逐條列舉的，不是一套通用的敏感資料防護：套用的是「已啟用、`direction=output`、主體種類涵蓋 agent、協議相符」的告警規則，命中的片段以佔位字串取代。沒有任何啟用規則命中的內容會原樣回到 agent，而出廠規則只涵蓋兩類：卡號 pattern 與私鑰標頭 pattern。請把這份規則清單當成「本部署認定 agent 通道上什麼算敏感」的定義，對照授權資產上實際取得的資料逐項檢視，缺哪一類就補哪一條規則。遮罩不作用於人類終端、錄影與指令紀錄。

保全資料庫、錄影、檢查點與相應版本的完整性鑰匙。pending 帳本列只證明意圖已記錄，不證明送達或完成。無法歸屬任務／句柄的呼叫在工具帳本前拒絕，由該次 MCP HTTP 稽核列保存主體、工具、原因碼與時間。指令完整性 coverage 軸僅在調查工作台及批次匯出入口提供；指定單一 session 匯出沒有 coverage。零 degraded 列不證明沒有遺失指令。保留報告版本及任務關閉時刻，不替 pending 補造結果。

MCP 句柄屬於單一行程，多副本不是共用會話儲存。
