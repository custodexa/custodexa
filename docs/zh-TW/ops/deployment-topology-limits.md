## 本版支援的部署形態

**本版為單實例部署：整套系統只能有一個應用實例在執行。**

同時執行兩個以上的應用實例會造成資料問題。該形態未經設計、未經驗證，不得用於生產。

**本版起，對同一資料庫啟動的第二個應用實例會被攔下並要求確認。** 它在任何寫入之前停住：
印出持鎖者指紋與兩條救援路徑，未確認即不開放任何服務路徑、不執行 migration、不寫入資料庫。
**確認在該實例自己提供的攔下頁上完成**，由管理員為持鎖者的確認碼背書；以該碼設定
`INSTANCE_GUARD_ACK` 是腳本化的等價做法。無論哪一條，每一次確認啟動都留下
`audit_logs` 事件、指標與管理介面常駐橫幅——**確認後的執行有稽核證據**。

**守衛防的是不知情，不是不發生。** 確認後兩個實例並存造成的資料問題不由守衛防止，
由確認者承擔；守衛保證的是攔下、告知，以及事後可由 `audit_logs` 證明「哪個實例、何時、
對著哪個持鎖者、（經攔下頁時）以哪個管理員帳號確認」。訊息判讀與救援程序見
[部署與升級 SOP §2.6b](./upgrade-sop.md#26b-若後端被攔下並指出單實例鎖由另一個資料庫工作階段持有)。

具體排除下列三種架構：

- 負載平衡後方掛兩個以上的應用實例。
- 兩個以上的實例同時執行的多副本部署：高可用（HA）叢集、active-active，或已經在活動實例旁邊
  跑著的熱備（hot standby）。
  **冷備（cold standby）是另一回事，以程序的形式受支援**：資料庫放在應用主機之外（external
  database overlay）時，第二台主機在第一台停下之後才啟動、指向同一個資料庫接手，任一時刻只有
  一個活動實例。程序、備援主機事先要備妥的東西、接手保不住的東西，見
  [應用主機備援接手](./standby-takeover.md)。守衛在該形態下相同；第一個實例其實還在跑時，
  攔下備援主機的就是它。
- 以滾動更新（rolling update）方式升級；切換過程中必然出現新舊兩個實例並存。
  **守衛版之間的滾動更新會在新實例端被攔下**（新實例取鎖時看到舊實例持鎖，停在確認關卡）。
  自無守衛的舊版本升級到本版的那一次不會被攔（舊版不持鎖），須靠升級 SOP 的檢核。

> 此限制針對的是**應用實例**。資料庫、guacd 與前端 nginx 各自作為獨立容器執行是正常
> 部署形態，不在此限。

> **守衛只認得守衛版。** 不含守衛的舊版本不持鎖：首次自無守衛版升級到本版、或自本版回滾到
> 無守衛版時，新舊實例並存不會被攔下。這兩個窗口由升級 SOP 的「先確認舊實例已停」檢核承擔。

> **連線池模式。** 應用須直連 postgres，或經 session pooling 模式的連線池。transaction pooling
> 會讓鎖在工作階段間漂移，守衛會反覆回報失鎖再重取——該拓撲不受支援。

## 對外走純 HTTP 時的登入狀態保存

**對外仍為 http 的部署，須把安全政策的「登入狀態僅在 https 連線保存」關閉。**
登入狀態由一枚 HttpOnly cookie 保存，該政策鍵為預設值（開啟）時瀏覽器只在 https 連線下
保存與回送它；純 http 之下它根本不會被保存。使用者仍可登入，但重新載入頁面、開新分頁
或關掉分頁再回來都會回到登入頁——瀏覽器端沒有留下任何可用來恢復登入的東西
（access token 只存在頁面執行期記憶體，不落瀏覽器儲存）。

判讀方式：登入後按重新整理即被要求重新登入，而登入頁本身會說明成因。
處置有兩條，正解是為對外入口配置 https；在此之前於安全政策關閉該鍵即可恢復正常的
登入保存，代價是登入狀態的憑證會在未加密的連線上傳輸——那與整個部署走 http 的
風險同級，不是額外新增的風險，但也不該當成長期狀態。

## 外部身分來源賦予的角色：那一端的變更何時生效

來自外部目錄或身分提供者的角色，是**在登入時、依該次登入帶進來的群組資料重算**的。
由此有三條界線，凡部署方倚賴外部來源收回權限時都會遇到。

- **在來源端收回權限的生效時點，取以下兩者較早者：當事人的下次登入，或當前網頁工作階段
  依安全政策「Web 工作階段最長時數」到期。** 在此之前，已經開著的工作階段仍持有它開始時
  持有的角色。**該政策設為 0 時沒有上界**：0 表示網頁工作階段的絕對壽命不設限，持續活動的
  工作階段不會自行回到登入頁，來源端的變更也就可能無限期等不到那兩個時點中的第一個。
  倚賴來源端收權的部署不宜把它設為 0。若某次登入重算後確有角色被收回，該帳號其他開著的
  工作階段即在當下結束；在本系統內直接撤下角色是另一回事，其即時性與此相同。
- **在來源端停用或刪除帳號不會同步到本系統。** 該帳號仍留在這裡的使用者列表上，角色維持
  最後一次重算的結果。它做不到的是登入：由外部來源供應的帳號只由該來源認證，改以本地密碼
  嘗試登入會被拒絕並記入稽核紀錄。殘留的是列表上還看得到這個人，不是權限還能用。
- **巢狀群組展不展開，取決於來源。** 本系統採用登入時取得的群組資料，不再向來源另發查詢
  往上追群組鏈。目錄的群組成員屬性通常只報帳號直接所屬的群組，透過上層群組取得的成員資格
  看不到；身分提供者的群組宣告則可能已把巢狀展開。規則請照來源實際回報的內容填寫。

## 改密通道的出站連線需求

改密由後端容器主動連向目標主機，不經前端 nginx、也不經使用者的瀏覽器。Linux 主機走目標的 SSH 埠；
Windows 主機依資產上設定的改密通道，走目標的 WinRM 埠（http 5985 或 https 5986，可另設）或 SSH 埠（預設 22，可另設）。
WinRM 的傳輸層**不讀取 proxy 環境變數、不跟隨 HTTP 轉址**，只走 HTTP/1.1；後端與目標之間若必須經代理或轉址，
該主機的 WinRM 改密連不上。https 的憑證驗證模式選 `system` 時，信任錨是後端容器作業系統的憑證庫，
內部 CA 簽發的監聽器憑證請改用 `ca` 模式在資產上傳該 CA。目標機前置條件見
[部署與升級 SOP](./upgrade-sop.md) §2.5 的 Windows 本機帳號改密段。

## 元件基礎系統的狀態（影響漏洞管理規劃）

**RDP／VNC 用的 guacd 容器，其基礎系統已停止安全更新。**

本專案的 guacd 映像以 Apache Guacamole 官方映像為基底，該基底為 Alpine 3.18，
已過官方支援期。**這不是本專案的選擇**：官方的 `latest` 與 `1.6.0`
是同一顆 `alpine-minirootfs-3.18.12`，上游尚未提供較新的基底。

對你的部署規劃有兩點實質影響：

- **該容器的作業系統層不會再收到安全修補**，直到上游更新基底為止。
- **漏洞掃描對該映像的結果不可作為安全依據。** 掃描它會得到「零發現」，
  正確的判讀是「沒有資料」：已過支援期的系統不再有漏洞資料庫更新，
  且 guacd 本體是編譯後的二進位、不在套件清單內，掃描器看不到它。

現有的結構性緩解（隨預設部署即生效，非需另行設定）：

- guacd **不對外暴露任何連接埠**，僅存在於 compose 的內部網路；
  唯一能連上它的是本系統的後端服務。
- 錄影目錄是它唯一的共享掛載點。**啟用離機儲存不改變這一點**：guacd 仍然直接寫入本機錄影目錄，
  上傳是**會話結束之後**由後端另行進行的，guacd 不接觸物件儲存、也不持有任何儲存憑證。
  也因此，**崩潰路徑遺留的錄影檔不進離機**：會話異常中斷而未完成落地確認的檔案，系統不會為它建立上傳追蹤，
  由既有的本機清理機制處置——離機保存的涵蓋範圍是「正常結束並確認落地」的錄影。
  取回時落地的暫存區是**後端容器本地的快取**（有存活期與總量上限），同樣不與 guacd 共享。
- 這顆容器**以最小權限執行**，而且這幾項是由交付的編排定義施加、不是映像的性質：丟棄全部 Linux capability、
  拒絕經 setuid 檔案提權、根檔案系統唯讀。唯讀之下只留兩塊記憶體上的可寫區，兩塊都是實測需要才給的：
  RDP 磁碟重導的每連線暫存目錄，以及 RDP 函式庫啟動時要求可寫的家目錄。
  暫存目錄放的是使用者當下正在傳的檔案，所以出廠不設容量上限；要設的部署方直接修改交付的
  `docker-compose.yml` 中該 tmpfs 那一行，例如 `/tmp:size=512m`（compose 覆寫檔做不到：
  compose 對 tmpfs 條目是串接而非取代，同一個掛載點宣告兩次會被拒絕）。
  RDP 函式庫的已知主機信任庫落在其中一塊記憶體區，隨容器重啟歸零；本產品對目標主機憑證的處置
  由資產的憑證驗證設定決定，不依賴該信任庫的跨重啟持續性。
  唯讀根與兩塊掛載為 noexec 的記憶體區，使循協議進來的入侵無法改寫容器設定、也無法自暫存區執行；
  共享的錄影目錄仍是可寫且可執行的，那是錄影落地所需。
- **你可以把這顆映像換成自建或自選的。** 本系統對這顆容器的要求只有三件：在 4822 埠提供 guacd 協議、
  能寫入編排定義掛給它的錄影目錄、映像內含 `sh` 與 `nc` 供編排施加的健康檢查判定是否就緒。
  上面那些都是容器的執行期屬性、不是映像的性質，所以換成任何映像之後，最小權限設定仍然生效。

**緩解不等於沒有風險**：若後端遭攻破，或被納管的遠端桌面主機透過協議回攻，
該路徑仍然存在。**漏洞管理政策若要求所有元件的基礎系統都在支援期內，
請在部署前就把這顆映像列入例外評估。**

**backend 仍以 root 執行。** 交付的部署設定與啟動程式逐項施加以下設定：

- `cap_drop: [ALL]` 丟棄能力集合，再以 `cap_add: [SETUID, SETGID, CHOWN, IPC_LOCK]` 僅加回四項能力：`SETUID` 與 `SETGID` 將 DB CLI 子行程切換至專用使用者與群組；`CHOWN` 將 CA 暫存檔的擁有權交給該使用者；`IPC_LOCK` 允許鎖頁超過鎖定記憶體的資源上限。
- `security_opt: [no-new-privileges:true]` 禁止透過執行 setuid 檔案或檔案能力取得額外權限。
- `ulimits.core` 的 `soft: 0` 與 `hard: 0` 均為零；backend 也將自身的 `RLIMIT_CORE` 設為零。
- `PR_SET_DUMPABLE=0` 將 backend 行程設為不可傾印。配合未授予 `SYS_PTRACE`，容器內其他行程（包括受這組能力限制的 root 行程）無法讀取其 `/proc/<pid>/environ` 與 `/proc/<pid>/mem`。
- `ulimits.memlock: -1` 與 `mlockall(MCL_CURRENT | MCL_FUTURE | MCL_ONFAULT)` 鎖住已駐留的記憶體頁，其他映射頁則在駐留時鎖住，防止這些頁被換出至 swap。

2026-09-12（Asia/Taipei）量測時，backend 使用上述設定，同時執行 15 個開發服務（backend 含 Air、dex、fake-gcs、frontend、guacd、k3s-test、ldap-test、localstack、mssql-test、mysql-test、postgres、rdp-test、ssh-multi-test、ssh-test、vnc-test）、量測用 client 與服務背景工作，沒有其他 Go 測試或端對端 smoke 測試，backend 在 0 條 active SSH 會話時為 VmRSS 68616 kB／VmLck 1369796 kB，在對 ssh-test 的 20 條並發 SSH 會話以 120×30 終端執行 echo 後保持開啟 45 秒時為 VmRSS 76952 kB／VmLck 1370060 kB；這兩次單點樣本是參考量測，不是保證的記憶體上限。

**金鑰材料仍在 backend 行程記憶體中。** 這些設定限制的是哪些其他行程讀得到它，並未移除金鑰材料，也不妨礙 backend 自身存取。它們無法防止控制主機或能變更部署權限的管理者讀取金鑰材料。

**自訂編排必須提供這些設定。** 丟棄全部能力後僅加回 `SETUID`、`SETGID`、`CHOWN`、`IPC_LOCK`，並施加上述權限與資源限制。在 Compose 中，鎖頁所需設定為 `cap_add` 包含 `IPC_LOCK`，以及 `ulimits.memlock: -1`；其他編排工具須提供對應的能力與資源限制。任何啟動控制無法施加時，backend 都會退出；鎖頁失敗會回報 `mlockall failed (check cap_add IPC_LOCK and ulimits.memlock)`。排查此錯誤時，請核對這些同名設定。

## 允許來源網段對部署的影響

**允許來源網段（`allowed_cidrs`）限制某個帳號可以從哪些來源位址使用系統。**
清單為空＝不限來源，那是預設值。它限制的是**可用來源**，不取代密碼政策、帳號鎖定或多因素。

### 先決定「來源位址」怎麼認定

本系統對「請求從哪裡來」只有一種取法，全部路徑共用：

- **未設定 `TRUSTED_PROXIES` 時，只採信 socket peer**——也就是 TCP 連線的對端位址。
  `X-Forwarded-For`、`X-Real-IP`、`Forwarded` 等轉送標頭**一律不採信**。
- 設定 `TRUSTED_PROXIES` 之後，轉送標頭才依你宣告的可信代理鏈解讀。
  **設定值非法時後端拒絕啟動**，不會退回預設值繼續跑。

預設不採信標頭是刻意的：那些標頭由呼叫端控制。採信它們，任何能發出請求的人都能為自己
那筆稽核列指定任意位址，也能靠每次換一個標頭繞開以位址為鍵的限制。

**把應用放在反向代理、負載平衡器或 CDN 後方而沒有設 `TRUSTED_PROXIES` 時，
系統看到的來源一律是那台代理的位址。** 三個後果：

- 允許來源網段判的是代理位址。填使用者的網段會把**所有人**擋掉；填代理位址則等於
  對所有經過該代理的人放行。
- 調查工作台的來源位址樞紐、稽核列與會話列的來源位址欄，全部記成代理位址。
- 新來源位址告警只在代理位址改變時才會響。

**預設部署自帶代理，`bash scripts/quickstart.sh` 會把 `TRUSTED_PROXIES` 填成該代理所在的 Docker 子網。** 自己跑 ingress 時這份清單由你來寫：填該 ingress 的位址，或它連進來的網段。

**要按真實來源判定與留痕，就得先設 `TRUSTED_PROXIES` 把代理鏈顯式列出來。**
這個決定要在啟用來源限定**之前**做：先設好清單再去改代理設定，會讓已經生效的清單
一夕之間對到另一組位址。

### 哪些入口會被擋，擋下來長什麼樣

清單非空而來源不落在其中時，下列動作一律被拒：

- 登入（含多因素完成、OIDC 交換）與強制註冊／強制改密的受限票證發放與消費。
- 網頁會話續期（refresh）。
- 連線簽發，以及文字終端與圖形兩條兌換入口——**兌換時各自現讀清單再判一次**，
  不沿用簽發當下的結論。
- 三個管理者端點——**替他人重設密碼**、**解鎖他人帳號**、**解除他人的多因素**
  ——依**操作者本人**的清單判定。

擋下來的回應**只說「此來源不允許」，不回顯位址，也不列出清單**。位址與命中的清單快照
只寫進稽核。連線類的拒絕另帶機器欄 `reason=source_not_allowed`，介面據此顯示
「目前來源不在允許範圍」而不彈出申請框。

**清單讀不到或內容損壞時一律拒絕**（不當成空清單放行），對外回應與「來源不對」
完全相同——分岔等於告訴呼叫端「這個帳號的政策壞了」。這種情況會在管理介面「操作日誌」頁的
「失效事件」分頁開一個 `source_policy` 事件，成因分「讀不到」與「字串損壞」兩類；
資料修好之後由系統自行結案。

### 收緊清單之前：先通知會被擋到的人

**收緊清單不會切斷已經在線上的人。** 具體是：

- 已發出的網頁存取權杖在其壽命內仍然可用，**殘窗上限是 15 分鐘**；之後的每一次
  `refresh` 續期都會被拒，使用者被導回登入頁，再次登入時就擋在來源判定。
- **已經建立的協議連線不會因為清單收緊而被主動切斷**，它會照常走到自己結束為止。
  下一次建線才會被擋。
- 「發出正式會話或受限票證」「寫入認證狀態」這一類動作，判定都在動作生效之前，
  所以收緊之後不會再有新的會話從清單外的位址長出來。

因此收緊清單的正確作法是**先通知**：告知受影響的人新的可用來源、生效時點，
以及被擋時該找誰。沒有通知就收緊，症狀會以「續期失敗、被踢回登入頁」的形式出現，
使用者無從分辨那是被限制還是系統故障。

### 管理者把自己鎖在外面時怎麼救

**系統不阻擋這種儲存**——管理者可能刻意設定一個尚未切換過去的網段。
介面只在儲存前就近顯示警告，不擋送出。

真的鎖住時，依序：

1. **還有其他管理者**：請對方在管理介面把清單改回來。這條路徑會留下欄位級的稽核差異
   （清單的前值與後值），是首選。
2. **沒有其他管理者可用**：走既有的離線重設路徑，以資料庫直連把該帳號的清單清成空字串。
   逐字步驟與 SQL 見
   [快速開始 — admin 密碼遺失、啟動被弱憑證掃描擋下，或管理者被來源限定鎖在外（離線重設）](../QUICKSTART.md#admin-密碼遺失啟動被弱憑證掃描擋下或管理者被來源限定鎖在外離線重設)。
   這一條**只需清清單，不必動密碼**。

離線重設**不經產品稽核**：它繞過應用程式直接寫資料庫，`audit_logs` 不會有對應的列。
**該次操作的留痕由部署方自己的變更管理承擔**（誰在什麼時候、依什麼授權動了資料庫）。
產品側事後看得到的，是復原之後的登入稽核列（含來源位址），以及回到介面重新設定清單時
留下的欄位級差異。清完之後不必重啟服務；**但也別停在清空狀態**——那等於任何位址都進得來。

### 新來源位址告警對營運的意義

某個帳號**首次**自某個來源位址建立協議連線時，系統產生一筆
`new_source_ip` 告警，並照既有的通知通道推送。同一組（帳號、位址）只響一次。

判讀時請注意三件事：

- **它是「以前沒從這裡連過」，不是「這次被擋下來」。** 是否放行由允許來源網段決定，
  兩者互不影響：清單為空時每一個新位址都會響，而清單擋掉的連線根本走不到建線那一步。
- **只登入不建線不會響**，只會把該位址納入基準；先登入再建線的典型流程仍會在建線時響一次。
- **升級當下已經看得到的位址不會響**：升級時系統自既有的會話全史與登入成功紀錄
  回填一份基準。全新安裝沒有歷史可回填，因此第一批連線都會各響一次，這是預期行為。

若你的使用者是浮動位址（家用寬頻、行動網路、VPN 出口輪替），這類告警會相當頻繁。
它適合當作「值得看一眼」的訊號，不適合當作阻斷條件——阻斷請用允許來源網段。

### 對備份與還原的影響

沒有新的落點。允許來源網段與來源位址基準都存在 PostgreSQL 裡，隨資料庫一起備份，
既有的[備份與還原](./backup-and-restore.md)程序不變、不需要額外步驟。

## 對升級的影響

升級必須停機進行，不得滾動更新。程序見[部署與升級 SOP](./upgrade-sop.md)。

本版起，**新實例起不來的原因多一項：舊實例仍在執行，或它的資料庫工作階段殘留**。
殘留只發生在持鎖主機當機或網路分割造成的 TCP 半開；postgres 依作業系統的 TCP keepalive
回收該工作階段（postgres 容器未另行設定，走 Linux 預設約 2 小時）。啟動日誌會印出持鎖者
指紋與確認碼，救援程序見
[部署與升級 SOP §2.6b](./upgrade-sop.md#26b-若後端被攔下並指出單實例鎖由另一個資料庫工作階段持有)。
**救援不需要對資料庫做任何操作。**

互斥保證只在守衛版之間成立。首次自無守衛版升級時，新版取得鎖**不代表**舊版已停；
升級 SOP §2.3 的首次升級檢核是唯一的證據來源。

執行期若失去鎖（postgres 重啟、工作階段被終止、網路事件），本實例**繼續服務**並每個週期重取。
期間管理介面顯示常駐橫幅、指標 `custodexa_instance_guard_held` 為 0、`audit_logs` 留有
`instance_guard` 事件；判讀見
[部署與升級 SOP §3.4](./upgrade-sop.md#34-執行期失去單實例鎖日誌橫幅與稽核事件的判讀)。

## 對可用性規劃的影響

單實例形態沒有自動故障接管，可用性規劃的著力點是縮短還原時間：讓備份與 KEK 材料
隨時就緒，回存程序事先演練過。見[備份與還原](./backup-and-restore.md)。
委託模式下，「隨時就緒」還包含兩件事：值班的人取得到保管處的憑證，以及每一次重啟都有人到場；
其代價見下一節。

還能再縮短的是**應用主機**（而非資料庫）故障後恢復服務的時間：資料庫放在另一台伺服器、
備援主機事先準備好，服務就靠「對同一個資料庫啟動備援主機」回來。那是由人或腳本執行的程序，
不是產品自己做的事。該程序事先需要什麼、保不住什麼（只有故障主機持有的錄影與其他檔案），
見[應用主機備援接手](./standby-takeover.md)。資料庫本身的損毀仍走備份還原。

**離機證據儲存改變的是「證據會不會丟」，不是「服務多快回來」。** 規劃時請把兩件事分開：

- **它縮短證據的暴露窗口，不消除。** 上傳是會話結束之後才發生的：文字錄影在秒級內排入，
  圖形錄影至少要等一分鐘（等檔案不再變動）；儲存端不可達時則一路等到恢復。
  **在那段窗口內，本機仍是唯一副本**——機器在此時毀損，該筆錄影就沒有第二份。
- **它不改變還原時間目標。** 遠端副本讓已離機的證據在機器毀損後仍取得回，但要讓系統重新
  提供服務，還是得走還原程序（資料庫、KEK、部署層設定）。**離機儲存不是備份的替代品**，
  兩者要一起規劃。
- **首次播放離機錄影有下載等待。** 本機副本已被清除的錄影，播放時要先由物件儲存取回、
  落地驗證雜湊之後才開始送出，等待時間隨檔案大小與頻寬而定。這是可預期的行為，不是故障；
  只在該錄影的第一次播放發生（暫存快取在存活期內可重用）。稽核作業若對回應時間有要求，
  請把這段等待算進去。

## 委託金鑰模式：這個部署不是無人值守

**採 `KEK_PROVIDER=kms`（AWS KMS、GCP Cloud KMS 或 HashiCorp Vault）時，本版的重啟一定要有人。**
連到保管處所用的憑證只保存在當次解封世代的記憶體，封存時即抹除，行程一旦結束就沒有任何地方讀得回來。
於是**每一次冷啟動都回到已封存**，在管理者解封之前只提供健康檢查與封存相關端點：
主機重開、容器重建、擴縮事件、夜間維護窗，以及還原後的第一次啟動都在此列。
**行程不會退出**——等待憑證是設計上的正常狀態，不是組態錯誤，靠監管程序重啟容器也解決不了它。

規劃上有三個後果：

- **每一次重啟都要有人聯絡得到**，包含計畫外的那些。選這個模式之前先定下由誰負責、非上班時間怎麼找人。
  `ui` 模式一向如此，`kms` 自本版起相同。`env` 是唯一能無人值守重啟的模式，代價是主金鑰以明文留在主機上。
- **自動擴縮與無人值守的重啟策略不適用本模式**：它們把一個無法提供服務的行程叫回來。
- **監控要對已封存狀態告警**，否則凌晨三點的重啟到早上九點才被發現。
  封存期間狀態仍讀得到：`GET /api/v1/seal/status` 與 `/metrics` 的封存那一組。

**解封頁要求什麼，以及這道驗證的邊界。** 管理者在解封頁輸入帳號與密碼，
拿畫面上顯示的保管處與部署紀錄核對，再重新提供該服務商的憑證。安全評估要納入兩條界線：

- **已封存狀態下只核對帳號與密碼，不核對動態驗證碼。** 動態驗證碼的種子受資料金鑰保護，
  封存時解不開，要求它會構成「先解封才能驗證、先驗證才能解封」的循環。
  **因此這一步不是雙因子，任何文字都不得這樣描述它。** 站在它背後的是：
  封存端點自身的來源退避與有時限的冷卻、`SEAL_UNSEAL_ALLOWED_CIDRS` 設定的來源網段、
  密碼錯與帳號不存在無法區分的回應、每一次嘗試在後端日誌留下的一行，
  以及效期十分鐘、每次使用都重新確認該帳號仍是啟用中管理者的授權脈絡。
  **已在鎖定期的帳號在這裡同樣被拒**；這一步不做的事是累加失敗計數或把帳號鎖起來——
  帳號鎖定政策屬於解封之後才存在的那一段。
- **帳號必須是本地管理者。** 由目錄服務或身分提供者建立的帳號在封存期間無法驗證，
  因為外部認證的路徑要解封之後才組裝。管理者全部來自外部來源的部署解不開自己，
  故至少保留一個本地管理者帳號——交付檢核清單本來就這樣要求。

**保管處設定放在哪裡。** 位址、服務區域、Transit 金鑰名稱與角色識別是資料庫裡的列，於金鑰管理頁設定；
每一次變更都以前後值寫入稽核，並經已設定的通知通道發出安全類告警，未設定通道時稽核列就是唯一的紀錄。
憑證既不在資料庫、也不在 `.env`。對備份與接手的影響因此是：設定隨資料庫備份一起走，憑證不會。
見[備份與還原 §4.3](./backup-and-restore.md#43-模式-ckek_providerkms金鑰保管處委託)與[應用主機備援接手 §2.2](./standby-takeover.md)。

## 資料金鑰的記憶體保留時間：這個設定用可用性換什麼

資產帳號密碼、側錄內容、目錄繫結憑證這類保存下來的機密，都是以資料金鑰加密後才存放，
而這把資料金鑰要先由主金鑰解開才能使用。安全政策的**資料金鑰的記憶體保留時間**
（金鑰管理頁）決定解開後的資料金鑰要留多久。

**留空是出廠預設，部署的行為與現況相同。** 資料金鑰解開一次後就留著，直到系統封存或行程重啟，
委託型的金鑰保管處不在日常運作路徑上。

**設為 0 或填入秒數，保管處就進入了運行路徑。** 保管處連不上的期間，凡是需要重新解開金鑰的動作
都會失敗：建立連線時取用資產帳號的密碼、連線進行中要寫入的側錄內容都在其中。這正是這個設定
提供的取捨——用可用性換取更短的記憶體停留時間——而且它不是當下能繞過的降級。

打開之前先定兩件事：

- **保管處連不上時新連線失敗可否接受、可接受多久。** 這要在選值之前回答，不是在第一次中斷之後。
  失敗時不會回退到先前的金鑰材料：解不開就是解不開。
- **自己這套保管處的一次往返要多久。** 每次重新解開就是一次呼叫，延遲隨區域、網路路徑與保管處
  本身而異。**請在自己的環境量測**，不要抄任何文件上的數字，再依量到的結果選值。

本機金鑰模式（主金鑰由環境變數提供，或由管理員在啟動時輸入）下，這個設定同樣可用，也同樣縮短
資料金鑰的存放時間。它不改變的是主金鑰本身：在這些模式下，主金鑰全程都在行程的記憶體裡。

稽核紀錄不在本設定的範圍內：為紀錄蓋章的金鑰不受保留期限影響，保管處連不上時紀錄仍寫得進去。
本設定縮短的是資料金鑰存在於記憶體的時間；操作進行中，記憶體裡仍然會有金鑰與資料原文。

## 輸出敏感資料偵測：射程與營運判準

偵測只掃 SSH、K8s 與資料庫主控台的解析後文字輸出；RDP/VNC 畫面、加密、壓縮或編碼內容（含 Base64）不在射程。終端控制序列不做渲染或剝除。編碼可繞過比對；命中表示輸出**可能含**敏感資料，未命中不表示不存在。本機制只告警，不阻斷或改變已送達的位元組。

輸出面規則的新增、停用與修改於**新會話**生效；進行中的會話沿用啟動時的規則集。升級、還原或接手後，核對規則方向、啟用狀態與協議，再建立新的文字會話驗證適用規則。安裝終態共有 16 條種子規則：原 12 條輸入規則、兩條 agent 輸入阻斷規則，加卡號與私鑰標頭兩條輸出規則。內建卡號 pattern 原樣時另做 Luhn 校驗；編輯 pattern 後視為一般正則，不再套用卡號校驗。

同（規則、會話）的命中於五秒窗內彙總，會話關閉時結算餘窗。告警列與轉發保留識別值、規則、次數與時間；command 為空，不存命中原文或位元組位移。reason_code 以 `o1:<base36 count>` 編碼次數；webhook 另提供 `possible_sensitive_output.count`。這些是「可能含」的訊號，不是全部輸出皆已掃描的證明。

有界佇列溢出會停用該場掃描，不中斷輸出。透過既有稽核查詢 action=`output_scan_disabled`、resource=`session` 與該會話的 resource_id；details 含 session_id 及 reason=`queue_overflow`，不含輸出原文。伺服端 log 不能代替這筆稽核列。該場後續輸出視為未掃描，依既有權限調閱證據，核對負載後建立新會話。掃描器失敗另留伺服端日誌；沒有告警不保證掃描成功。

共用遮罩原語回傳完整替換的文字與替換次數；**本版未接上任何產品回傳路徑**。遮罩不套用於錄影、指令紀錄或其他證據；原文繼續受既有留存、存取權限及備份／還原程序管理。


### 主體與憑證完整性涵蓋範圍

驗證頁分列角色指派、主體種類／擁有者與憑證狀態。升級後首次包含新項快照的封章前，新兩列為「尚未涵蓋」。偵測非即時：在驗證、封章及核發憑證前對帳；每項不符各開 `principal_state_integrity`／`principal_state_mismatch` 事件並通知，差集僅含識別值。發證不因不符或對帳錯誤中斷；錯誤記日誌並維持未知，不更動業務資料。服務層投影狀態列 actor 記 `system`，操作者由既有 HTTP 稽核列承擔。

回退為單向相容：新版可驗舊章，舊版無法完整驗證新快照鍵。不得刪鍵、重簽檢查點或還原舊的單機制失效唯一索引；回退必須使用升級前的一致備份並遵循還原程序。載荷版本沿用當時最新值（目前 v3）。

## Agent MCP 營運程序

建立 agent 主體並指定有效的人類 owner。由 owner 或管理員建立具名稱及期限的 agent token，將僅顯示一次的明文保存於執行者的秘密儲存處。agent 僅有 user 角色，資產與帳號授權須明確限縮。在 agent 所在的機器安裝 stdio 客戶端 `custodexa-mcp`，取自 https://github.com/custodexa/custodexa-mcp：執行 `go install github.com/custodexa/custodexa-mcp@latest`，或下載 release 二進位並以同一 release 發布的 `checksums.txt` 驗證。以環境變數 `CUSTODEXA_AGENT_TOKEN` 提供給 `custodexa-mcp`，`CUSTODEXA_MCP_URL` 指向 HTTPS 的 `/api/v1/mcp`；該入口不接受人類 JWT 或 cookie。stdio 客戶端只轉送，所有判定及證據寫入均在服務端；不要把 token 放入命令參數或報告。

agent 送出的任務要不要等人核准，取決於每個被申請資產的存取政策段位：資產本身設了 `access_policy` 就以它為準，否則取全域 `access_policy_default`。落在 `approval` 段的項目會維持待審，直到範圍涵蓋該資產的審核者做出決定；落在 `open` 與 `reason` 段的項目在建單當下即核准，記為 `auto_approved: true` 並保存政策快照，沒有核准票。出廠預設下多數資產不在 `approval` 段，因此未調整政策的部署會看到 agent 任務全數自動核准。要讓 agent 任務等人決定，請把相關資產的 `access_policy` 設為 `approval`，或把全域 `access_policy_default` 設為 `approval`；`access_request_min_approvals` 再決定這類申請需要幾張核准票。這個選擇請在給 agent 第一份資產授權之前定案並寫進營運手冊：自動核准仍然全程留痕，但它不是人為控制點。

輪替時先發新具名 token、更新執行者秘密、建立新的 MCP 連線並確認可視資產，再撤銷舊 token。沒有原地換 token 秘密或從備份自動找回明文的能力。撤銷會關閉由舊 token 建立的會話；句柄不能轉給新 token 或新 MCP 連線。還原或備機接管後須新建 MCP 連線，按需要重新申請任務；記憶體句柄與 60 秒冪等快取不跨重啟保存。續作前先核對保留的 token 與任務狀態。

事件處置先撤銷或停用涉事 token，必要時停用 agent，再核對任務、工具帳本與 HTTP 請求稽核。探測熔斷會停用 token 並記錄事件；owner 或管理員須附理由解除。解除不會恢復已停用 token，之後須另發新 token。它的計數只涵蓋一類引用：資產確實存在、且從未對該 agent 曝光過。引用不存在或已刪除的資產 id 歸類為 retired，引用曾經曝光過的資產歸類為 revoked，兩者都會留事件列，但都不計入跳閘門檻。隨機列舉 id 因此多半只產生不計數的事件，不可把這道熔斷說成通用的掃描偵測；它擋的是對範圍外真實資產的反覆探取，更廣的列舉行為請另以告警規則與開單速率政策涵蓋。判斷一次拒絕引用有多少意義之前，先讀熔斷事件列的 `class` 欄。通知沿既有 webhook／Slack 並帶 `owner_id`，不是私人收件匣，也不證明已送達本人。可視 exposure 自 migration 後開始，無法還原先前可視歷史；把拒絕引用認定為濫用前須核對這條邊界。

Token 到期、綁定任務項到期與任務關閉，皆終止存量會話及進行中的工具，不等待當前命令完成。期限每 250ms 現讀取樣，取樣間隔不是完成 SLA。撤銷沿既有收線路徑（目標 ≤3 秒，超時留痕）。僅控制本系統建立的會話，不保證遠端背景程序停止或撤回已做的變更。在途請求取消會關閉其會話；兩次 POST 間無法即時察覺客戶端離開，沿五分鐘 idle lease 到期收束句柄，不得稱為即時離線偵測。

`completed` 只代表再次觀察到提示符，不保證命令已結束或成功；提示符可偽造，背景輸出可交錯。`timed_out` 表示結果未知，重試前先觀察後續輸出。同句柄冪等鍵在 60 秒內避免重複寫入；不帶鍵可能再次執行。`needs_input` 須自行呼叫 `send_keys` 復位，系統不會自動送中斷鍵。`read_screen` 是行緩衝而非虛擬螢幕。agent 回傳文字經遮罩，錄影與指令紀錄保留原文。遮罩是規則驅動、逐條列舉的，不是一套通用的敏感資料防護：套用的是「已啟用、`direction=output`、主體種類涵蓋 agent、協議相符」的告警規則，命中的片段以佔位字串取代。沒有任何啟用規則命中的內容會原樣回到 agent，而出廠規則只涵蓋兩類：卡號 pattern 與私鑰標頭 pattern。請把這份規則清單當成「本部署認定 agent 通道上什麼算敏感」的定義，對照授權資產上實際取得的資料逐項檢視，缺哪一類就補哪一條規則。遮罩不作用於人類終端、錄影與指令紀錄。

保全資料庫、錄影、檢查點與相應版本的完整性鑰匙。pending 帳本列只證明意圖已記錄，不證明送達或完成。無法歸屬任務／句柄的呼叫在工具帳本前拒絕，由該次 MCP HTTP 稽核列保存主體、工具、原因碼與時間。指令完整性 coverage 軸僅在調查工作台及批次匯出入口提供；指定單一 session 匯出沒有 coverage。零 degraded 列不證明沒有遺失指令。保留報告版本及任務關閉時刻，不替 pending 補造結果。

MCP 句柄屬於單一行程，多副本不是共用會話儲存。
