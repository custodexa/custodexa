> **本程序的驗證狀態**：專案在單一機器上演練過一次，以兩個 compose 專案代表兩台應用主機、第三個代表資料庫；守衛的行為、確認碼路徑與備援主機上的登入都在那次演練中走過。尚未在兩台實體主機之間演練過。倚賴它之前，請在自己的環境演練一次並留下記錄。

>

## 1. 本程序涵蓋什麼

**形態**：PostgreSQL 跑在應用主機之外。有兩台應用主機，**主用主機**與**備援主機**，以同一套檔案準備、都指向那個資料庫。只有主用主機在跑。主用主機停下時，不論是計畫內還是故障，就對同一個資料庫啟動備援主機接手。

**它是什麼、不是什麼**：

| 是 | 不是 |
|---|---|
| 冷備：備援主機在主用主機停下之後才啟動 | 第二個執行中的實例。兩個實例對一個資料庫是[部署形態限制](./deployment-topology-limits.md)排除的形態；在這裡同樣由單實例守衛在啟動時攔下第二個並要求確認，有人確認之後，它不會阻止兩個同時執行 |
| 由人或腳本啟動的程序 | 自動故障接管。產品裡沒有任何東西在盯著主用主機或替你啟動備援主機 |
| 從應用主機的損失中恢復 | 從資料庫的損失中恢復。這個形態下資料庫是資料唯一的一份；它沒了，回來的路是[備份與還原](./backup-and-restore.md)，在哪台主機上做都一樣 |
| 縮短主機故障後恢復服務的時間 | 挽回只有故障主機持有的東西（§7） |

兩台主機共享的東西都在資料庫裡。各主機自己保有的東西，首先是錄影，列在 §2.3 並在 §7 再列一次；判定本程序是否符合你的復原目標之前，兩處都要讀。

## 2. 在需要之前先把備援主機建好

### 2.1 把資料庫放在應用主機之外

堆疊自帶的 postgres 住在應用主機上，預設形態下主機與資料一起倒。external database overlay 讓堆疊不起自帶的 postgres，改讓後端連向你指定的伺服器：

```env
# 每台應用主機的 .env（主用主機與備援主機用相同的值）
COMPOSE_FILE=docker-compose.yml:docker-compose.external-database.yml
EXTERNAL_DB_HOST=db.example.internal
EXTERNAL_DB_PORT=5432
DB_NAME=custodexa
DB_USER=custodexa
DB_PASSWORD=<該帳號在那台伺服器上的密碼>
DB_SSLMODE=verify-full
```

那台伺服器跑在哪裡由你決定：機構既有的 PostgreSQL 伺服器、代管服務，或你自己的第二台機器。接手程序在每一種情況下都相同。伺服器要提供的東西：

- **PostgreSQL 16**，資料庫與帳號在首次啟動前建好（後端首次對空資料庫啟動時建立 schema）。
- **兩台應用主機都連得到。** 伺服器上限制用戶端位址的東西（`pg_hba.conf`、防火牆、安全群組）要在需要的那天之前就放行備援主機的位址，不只主用主機的。連不到資料庫的備援主機，會在最糟的時刻被發現。
- **連線走 TLS。** 資料庫現在隔著網路：`DB_SSLMODE=require` 是下限，伺服器憑證能驗證時用 `verify-full`（PCI DSS 第 4 項要求）。自帶形態用 `disable`，是因為那條連線不離開主機；不要把那個值帶進這個形態。
- **直連，或 session 模式的連線池。** 單實例守衛持有的是工作階段層級的鎖；transaction 模式的連線池會弄壞它（見[部署形態限制](./deployment-topology-limits.md)）。
- **備份的對象變成這台伺服器。** 備份程序那張表的資料庫列，不再位於應用主機的 `DATA_PATH` 之下：`pg_dump` 對這台伺服器執行，由營運它的人執行；錄影與稽核目錄仍從應用主機備份（§8）。
- **TCP keepalive。** 應用主機當機時，它的資料庫工作階段在伺服器上維持開啟，直到伺服器的 TCP keepalive 放棄它為止；殘留期間它仍持有單實例鎖，備援主機得走 §4.3 的確認步驟。PostgreSQL 以 `tcp_keepalives_idle`、`tcp_keepalives_interval`、`tcp_keepalives_count` 決定這件事；出貨預設跟隨作業系統（Linux 約 2 小時）。設了 `tcp_keepalives_idle=300`、`tcp_keepalives_interval=10`、`tcp_keepalives_count=3` 的伺服器，在用戶端最後一個封包之後約五分半放棄它；專案以這組值演練時，帶確認碼啟動的備援主機在當機後 5 分 46 秒自行取得鎖（伺服器的五分半，加上備援主機一個 15 秒重試週期的一部分）。確認步驟兩種情況都一樣；這個設定只縮短備援主機之後顯示橫幅的時間。

若資料庫由你自己跑在另一台機器上，出貨的映像就夠用。一台只跑資料庫的主機的最小 compose 檔，含 keepalive 設定與 TLS：

```yaml
# 資料庫主機上的 docker-compose.yml
services:
  postgres:
    image: postgres:16.15-alpine3.24
    command:
      - postgres
      - -c
      - ssl=on
      - -c
      - ssl_cert_file=/certs/server.crt
      - -c
      - ssl_key_file=/certs/server.key
      - -c
      - tcp_keepalives_idle=300
      - -c
      - tcp_keepalives_interval=10
      - -c
      - tcp_keepalives_count=3
    environment:
      POSTGRES_DB: custodexa
      POSTGRES_USER: custodexa
      POSTGRES_PASSWORD: <與應用主機 DB_PASSWORD 相同的值>
    ports:
      - "5432:5432"
    volumes:
      - /opt/custodexa-db/postgres:/var/lib/postgresql/data
      # 以這台主機的名稱簽發的 server.crt 與 server.key；金鑰檔權限 0600、擁有者為容器內的 postgres 使用者（出貨映像為 uid 70），否則伺服器拒絕載入
      - /opt/custodexa-db/certs:/certs:ro
    restart: always
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U custodexa"]
      interval: 10s
      timeout: 5s
      retries: 5
```

憑證的名稱要與 `EXTERNAL_DB_HOST` 相符，`verify-full` 才會通過，且應用主機要信任簽發的 CA（`DB_SSLMODE=require` 略過名稱與信任的檢查，仍會加密）。限制監聽位址與用戶端位址，用主機的防火牆或 `pg_hba.conf`，與任何資料庫伺服器相同。

### 2.2 準備備援主機

備援主機是以同一套檔案準備的第二台應用主機，在需要之前保持**停止**。與主用主機同時準備，主用主機每一次變動之後重做一次準備，因為落後的備援主機會以錯的版本或錯的設定接手。

1. **相同的映像、相同的版本。** 在備援主機上建置或載入正式版映像，做法與主用主機相同（部署與升級 SOP §2.2）。主用主機的每一次升級也是備援主機的升級（§8）：停在前一版的備援主機對著較新的 schema 啟動會拒絕啟動（SOP §2.6），而版本較新的備援主機會在主用主機腳下遷移 schema。
2. **相同的 compose 檔與相同的 `.env`。** 從主用主機複製 `docker-compose.yml`、`docker-compose.external-database.yml`（有用 ingress overlay 就一併）、`docker/` 與 `.env`。兩台主機之間不同的值只有下表這幾個；其餘包括機密在內都要一模一樣，否則備援主機讀不了主用主機寫的東西。

   | 鍵 | 在備援主機上 |
   |---|---|
   | `DATA_PATH` | 這台主機自己的資料根；建立 `${DATA_PATH}/recordings` 與 `${DATA_PATH}/audit`，權限依 SOP §1.3 |
   | `TLS_DOMAIN`、`TLS_IP_SAN`、`PUBLIC_BASE_URL` | 使用者經由一個名稱或虛擬位址連線、接手時把它重指向備援主機的話，維持不變（本文假定的安排）；使用者將以不同位址連到這台時，改用這台自己的值 |
   | `TRUSTED_PROXIES` | 內建代理的網段在兩台主機上相同；用自家 ingress 時，填它從這台主機看到的位址 |
   | `INSTANCE_GUARD_ACK` | 不存在。故障後的接手在攔下頁確認（§4.3）；這個變數是腳本化的替代路徑，只為那一次接手設定，之後移除 |

   ```bash
   # 在主用主機上：備援主機需要的部署檔案，含 .env 與 tls/
   rsync -a --relative \
     docker-compose.yml docker-compose.external-database.yml docker/ .env tls/ \
     standby:/opt/custodexa/
   ```

   `.env` 帶著資料庫密碼，在 `KEK_PROVIDER=env` 模式下還帶著 KEK 材料；`tls/ca-private/` 帶著本地 CA 的私鑰。用搬運機密的方式搬運它們，並在備援主機上保留 `0600` 權限。
3. **相同的 TLS 材料。** `TLS_MODE=selfsigned` 時複製 `tls/`，備援主機才會提供同一個 CA 與憑證；首次啟動自己產生 CA 的備援主機，對每個瀏覽器與每個 SSO 回呼都是一個新的、不受信任的站台。`TLS_MODE=provided` 時放入相同的憑證檔。
4. **KEK 材料在備援主機上要取得到**，否則備援主機啟動後停在封印狀態，什麼都讀不出來：

   | `KEK_PROVIDER` | 備援主機需要的東西 |
   |---|---|
   | `env` | `.env` 裡相同的 `ENCRYPTION_KEY`（隨上面的複製一起帶到） |
   | `ui` | 磁碟上不需要任何東西；**備援主機啟動之後，要有人在它的解封頁輸入解封材料。** 接手時間包含這個人 |
   | `kms` | 相同的 KMS 金鑰與憑證，且從這台主機連得到 |
5. **離機證據儲存在主用主機上啟用並驗證過**（系統設定 → 離機儲存）。它是備援主機能播放主用主機所錄錄影的唯一途徑；沒有它，備援主機一份都沒有（§2.3）。設定存在資料庫裡，備援主機一啟動就用得到；備援主機自己仍要連得到儲存端點。
6. **使用者連線的位址。** 現在就決定接手後使用者怎麼連到備援主機：把 DNS 名稱或虛擬位址重指向備援主機，能讓 `PUBLIC_BASE_URL`、憑證與每一個 SSO 的 redirect URI 都不必變，這是本文假定的安排。其他任何安排都會改變備援主機上的這些值，連同 IdP 端的 redirect URI。
7. **啟動一次，然後停掉。** 在主用主機**停止**的狀態下把備援主機拉起來（計畫內切換，§3），驗證它（§5），切回去，讓備援主機保持停止。走開之前確認兩件事：備援主機上的 `docker compose ps` 什麼都沒列，而且那台主機上沒有任何東西會在開機時啟動堆疊（`restart: always` 只作用於存在的容器；`down` 會移除它們）。

### 2.3 備援主機沒有的東西

資料庫是共享的；主機的檔案系統不是。接手之後，主用主機留在自己磁碟上的東西都不在備援主機上：

| 只在主用主機的磁碟上 | 在備援主機上的後果 | 能減輕它的 |
|---|---|---|
| `${DATA_PATH}/recordings` 下的錄影檔 | 會話記錄在資料庫裡，但播放需要檔案。備援主機沒有檔案的錄影，只有在副本已上傳到離機儲存時才播得出來（首次播放時取回） | 離機證據儲存；主用主機磁碟救得回來時複製該目錄（§4.4） |
| `${DATA_PATH}/audit` 下的稽核降級檔案與封印期 journal | 當時寫不進資料庫的稽核列留在那些檔案裡；`KEK_PROVIDER=ui` 模式的封印 journal 也是 | 磁碟救得回來時複製該目錄；正常情況下量很少，因為稽核列先寫資料庫 |
| 容器內 `/var/lib/custodexa/exports` 的匯出產物（證據包、輪替證據報告） | 它們的下載失效。工作列在資料庫裡；在備援主機上重新匯出 | 離機儲存在保留期內留有已完成產物的副本；否則沒有，這個目錄在每台主機上都是容器本地的 |
| 離機取回快取（`OFFSITE_SPOOL_PATH`） | 錄影在首次播放時重新取回 | 不需要；它是快取 |
| 進行中的會話與其錄影未寫完的尾段 | 主機故障時每一條協定會話都結束，而以這種方式結束的會話其錄影不會上傳（離機儲存只上傳正常結束的錄影）。備援主機首次啟動時，這些會話以 `end_reason=backend_restart` 收斂 | 沒有；見 §7 |

## 3. 計畫內切換（主用主機健康）

主用主機維護、§2.2 第 7 步的演練、以及之後切回主用主機（§6）都用這一節。不涉及確認碼：正常停止的主用主機會釋放單實例鎖，備援主機立刻取得。

1. **公告停機。** 主用主機停止時，進行中的每一條協定會話都結束；使用者會看到終端關閉。時間點的選法與升級相同。
2. **讓主用主機把佇列清空。** 與升級前停機相同的檢查：稽核佇列已空（SOP §2.4），啟用離機儲存時上傳佇列也已空（SOP §3.2b）。主用主機停止時仍在上傳佇列裡的錄影，留在主用主機的磁碟上，直到主用主機回來。
3. **停止主用主機。**

   ```bash
   # 在主用主機上
   docker compose down
   docker compose ps          # 必須什麼都沒列
   ```

   `down` 會移除容器，堆疊在下次重開機時就不會自己回來；`stop` 會留下容器，`restart: always` 會把它們帶回來。backend 容器停止時鎖即釋放。
4. **啟動備援主機。**

   ```bash
   # 在備援主機上
   docker compose up -d
   docker compose logs backend | grep -E 'InstanceGuard|資料庫連線成功|Listening|監聽'
   ```

   日誌先顯示資料庫連線，接著是正常啟動，沒有任何 `[InstanceGuard]` 警告；鎖是空的。`KEK_PROVIDER=ui` 時，後端接著等待解封，其他一切也跟著等。
5. **把使用者連線的位址**（DNS 或虛擬位址）**重指向備援主機**，然後驗證（§5）。

切回去就是同樣的步驟，兩台主機對調。

## 4. 主用主機故障後的接手

### 4.1 先判定，再確保主用主機不會回來

啟動備援主機之前，確立兩件事，並記下你怎麼確認的：

- **主用主機沒有在服務。** 一台對使用者失去網路、但仍連得到資料庫的主機，仍是一個執行中的實例；在它旁邊啟動備援主機就是被排除的形態，守衛的確認步驟（§4.3）正是會要你為此負責的地方。網路面看不清楚時，到主機本身確認故障（主控台、電源狀態、hypervisor）。
- **備援主機接手期間，主用主機不會自己回來。** 主用主機的容器帶著 `restart: always`：當機後重開機的主機會把堆疊一起帶回來。啟動備援主機之前先讓這件事不可能發生，方法擇一：讓主機保持關機；在資料庫伺服器上拒絕主用主機的位址（`pg_hba.conf` 或防火牆），直到你決定哪台留下；或主機連得到的話，在那邊 `docker compose down`。為什麼這很重要，見 §4.4。

### 4.2 啟動備援主機，讀守衛的回答

```bash
# 在備援主機上
docker compose up -d
docker compose logs -f backend
```

兩種結果：

- **後端正常啟動**，有資料庫連線那一行、沒有 `[InstanceGuard]` 警告。主用主機的資料庫工作階段已經不在了（主機是乾淨停止的，或資料庫的 keepalive 已經回收它）。到 §5。
- **後端回報鎖由另一個資料庫工作階段持有，服務沒有開起來。** 行程不退出，停在守衛的攔下模式：每 15 秒重取一次鎖，並開一個頁面讓你處置。那一段長這樣（`pid`、時間與 `code` 每次都不同）：

  ```
  CRITICAL：單實例鎖由另一個資料庫工作階段持有。本版不支援多實例部署，本實例未啟動服務。
    持鎖者：application_name=custodexa-instance-guard pid=268 backend_start=2026-09-05T13:50:58.116184Z code=2936aed7c309
    風險：兩個實例同時執行會造成金鑰快取、匯出工作、錄影落地與封印期留痕的資料問題（見 docs/ops/deployment-topology-limits.md）。
    處置 (a)：若確認另一實例仍在執行：先停止它，再重啟本實例（無需任何設定）。
    處置 (b)：若確認無其他實例在執行（例如持鎖者是主機當機後殘留的工作階段）：開啟本實例的守衛攔下頁 /instance-guard，以管理員帳密重打確認碼 2936aed7c309 後確認，不需重啟；腳本化替代路徑為設定環境變數 INSTANCE_GUARD_ACK=2936aed7c309 後重啟。兩者都會寫入審計事件並在管理介面顯示橫幅，直到鎖由本實例取得。
    澄清：這不是資料庫損毀；本次啟動未由本實例執行 migration 或任何資料寫入；INSTANCE_GUARD_ACK 綁定上列指紋，持鎖者變更後失效；確認後兩實例並存造成的資料問題由確認者承擔，守衛只保證此事被記錄。
  ```

  接著是一行說明：攔下模式已在後端的埠上開啟，只提供健康檢查、封印狀態與攔下確認，且未執行 migration、未產生任何資料庫寫入。

  **打開攔下頁**：備援主機的 `https://<位址>/instance-guard`，`<位址>` 是備援主機自己的位址（使用者連的位址可能還指著主用主機）。它不需要登入，可達條件與解封頁相同，也就是 `SEAL_UNSEAL_ALLOWED_CIDRS` 設定的來源網段（未設即不限制）。攔下期間其他路徑一律回 503。

  頁面顯示的事實與日誌相同：持鎖者的 `application_name`、`pid` 與 `backend_start`、這次衝突的確認碼、兩個實例同時執行會損壞資料，以及本實例尚未寫入任何資料、這不是資料庫損毀。它每個重取週期重讀一次守衛狀態，不必手動重新整理就會跟著情況走。

  持鎖者是故障的主用主機的資料庫工作階段，在伺服器上維持開啟直到它的 TCP keepalive 放棄為止（§2.1）。備援主機沒有執行 migration、什麼都沒寫；它開著的唯一監聽就是提供那個頁面的那一個。`backend_start` 是那個工作階段建立的時間，也就是主用主機最後一次啟動的時間左右；這個值對得上你的主用主機最後一次啟動，而主用主機已確認停機，就是殘留工作階段的樣子。每個欄位怎麼讀，以及選配的診斷查詢（以鎖鍵連接 `pg_locks` 與 `pg_stat_activity`），見 SOP §2.6b。不要在資料庫伺服器上終止那個工作階段；守衛的救援不需要它，而下面的程序才是本文演練過的那條。

  **另一個實例其實還在執行的話**，停掉它、別的什麼都不用做：備援主機在下一次重試取得鎖並自行啟動，不需要確認、也不需要重啟，頁面轉為「已啟動」。

### 4.3 以確認碼確認，讓備援主機接手

只在 §4.1 確定之後。在攔下頁上：

1. **勾選承擔**：你已在主機本身確認另一個實例沒有在執行，且不會自行重啟。
2. **重打確認碼**：持鎖者指紋旁顯示的那一組。
3. **輸入管理員帳號與密碼**，送出。

三項缺一即被拒。確認碼是與**你送出當下**的持鎖者比對，不是與頁面先前顯示的那一組：填表期間持鎖者換了人，送出即被拒，頁面換上新的指紋與新的碼要你重打。管理員帳密不正確同樣被拒、確認不被接受；憑證失敗連續 5 次之後，頁面 5 分鐘內不再受理送出。這個等待期只存在於攔下中的行程裡，行程結束就沒了，過程中沒有任何一部分寫進資料庫——攔下中的實例不對資料庫寫入。它擋的是自動化猜測，不是有主機存取權的人。頁面若回答無法在此驗證管理員憑證，表示這個實例讀不到使用者表（schema 來自別的版本，或資料庫有問題）；改走本節末尾的腳本化路徑。

送出被接受之後，頁面顯示**啟動中**：實例關掉攔下頁的監聽、執行 migration 與其餘啟動步驟，再重新開放服務埠。**這段期間服務埠不會有回應，這是正常的**；頁面會一直問到它答得出話，然後轉為「已啟動」並給出前往登入的入口。不需要重啟，也不必改 `.env`。

從這裡起備援主機完整服務：登入、連線、稽核、排程。殘留工作階段消失之前你會看到的：

- 每個登入使用者都看到常駐橫幅「本實例以確認碼啟動；另一個資料庫工作階段仍持有單實例鎖」；管理者在橫幅裡另看到確認者的帳號、持鎖者指紋與確認碼。
- `GET /api/v1/seal/status` 回報 `instance_guard.state = overridden`、`reason = ack_page`；指標 `custodexa_instance_guard_overridden` 為 1。
- 一筆 `audit_logs` 列，`resource=instance_guard`、`event=overridden`，`actor` 是完成確認的那個管理員帳號，來源記為頁面，並帶上送出成功前的憑證失敗次數。產品記下的是帳號；**為什麼**做這個確認不在產品裡，所以把 §4.1 的證據記在你的事件單上。

資料庫回收殘留工作階段之後，備援主機在下一次重試（每 15 秒）自行取得鎖：日誌印出 `[InstanceGuard] 已重新取得單實例鎖（自 overridden 起未持鎖 … ms，reason=…）；告知解除`，橫幅在介面下一次輪詢時消失，`state` 變成 `held`，`audit_logs` 多一筆 `event=regained`。**不需要重啟。** 要等多久由資料庫伺服器的 keepalive 設定決定（§2.1），作業系統預設約 2 小時。

確認的完整意義在 SOP §2.6b；在這裡只有一句話要緊：**主用主機其實還活著的話，現在有兩個實例在寫同一個資料庫，由此造成的資料問題守衛不會防止；它們歸確認的人。** 擋在你與那件事之間的是 §4.1。

**腳本化的替代路徑：`INSTANCE_GUARD_ACK`。** 同一個確認也可以不經頁面完成，用於腳本驅動的接手、或頁面連不到的主機。把最新一則訊息裡的 code 放進備援主機的 `.env`，再啟動後端：

```bash
# 在備援主機上：值來自最新一則訊息的 code=，只對這一次衝突有效
printf 'INSTANCE_GUARD_ACK=%s\n' 2936aed7c309 >> .env
docker compose up -d backend
docker compose logs backend | grep InstanceGuard
```

日誌接著顯示 `CRITICAL：以 INSTANCE_GUARD_ACK 啟動：單實例鎖仍由 … 持有；本實例將照常執行 migration 與服務；此確認已記錄（actor=operator via env）`，然後是正常啟動，`reason` 是 `ack_startup` 而非 `ack_page`。**這條路徑記不下是誰確認的**：稽核列的 `actor` 是 `operator via env`，環境變數無法識別一個人，所以那個人屬於你的事件單。之後把 `INSTANCE_GUARD_ACK` 那行從 `.env` 移除，不需要重啟任何東西：那個值綁定那一個殘留工作階段，持鎖者變了就是惰性的，但留在 `.env` 裡的舊行會引誘下一位操作者拿來重用。

### 4.4 故障主機回來時

主用主機可能之後修好或重開機回來。它的堆疊還在 `.env` 裡，而且除非你停過它，還在容器清單裡帶著 `restart: always`。三種情況：

- **備援主機持有鎖（`state = held`）**：主用主機的後端在啟動時被守衛攔下，印出與 §4.2 相同的一段、提供同樣的攔下頁，持鎖者是備援主機。那是守衛照設計運作，也是 §4.1 不倚賴它的原因：它只在備援主機真的持有鎖之後才成立。備援主機正在服務時還去主用主機的攔下頁確認，就是被排除的形態；讓它停在攔下，或把它關掉。
- **備援主機仍在 `overridden`**（殘留工作階段還沒回收）：主用主機的新後端同樣被殘留工作階段擋在攔下模式。殘留工作階段回收時，**兩邊都在重試，先到的拿到鎖**。是主用主機的話，它正常啟動，日誌沒有 `[InstanceGuard]` 警告，兩邊都在服務；備援主機停在 `overridden`，`reason` 仍是當初的確認來源，單看狀態看不出發生了什麼。看得出來的是持鎖者：在 `GET /api/v1/instance-guard`，以及管理者橫幅重新整理明細之後，持鎖者的 `backend_start` 不再是故障的主用主機最後一次啟動的時間，而是它的新後端起來的時間（備援主機的日誌也會印出新的持鎖者，最多每 10 分鐘一次）。這就是 §4.1 要關上的窗口：在備援主機回報 `held` 之前，不讓主用主機啟動。
- **主用主機的磁碟救得回來**：它持有的錄影與稽核檔案（§2.3）可以搬到備援主機。資料庫以容器內路徑指涉錄影，兩台主機的該路徑相同，所以以相同的相對結構複製到備援主機 `${DATA_PATH}` 之下的檔案，播放時找得到。

  ```bash
  # 從救回的主用主機磁碟到備援主機的資料根；保留相對結構與擁有者
  rsync -a /mnt/primary-disk/custodexa/data/recordings/ standby:${DATA_PATH}/recordings/
  rsync -a /mnt/primary-disk/custodexa/data/audit/      standby:${DATA_PATH}/audit/
  ```

  當機時進行中會話的錄影會以檔案的形式過來，但從未確認寫完；播不播得出來取決於檔案寫到哪裡。稽核降級檔案以既有程序重放（[備份與還原 §7.3](./backup-and-restore.md#73-還原後審計降級檔案的回收)）。

備援主機到了 `held`、你也決定主用主機要回到服務之後，切回去就是一次計畫內切換（§6）。主用主機的 `.env` 可能還留著上一次接手的 `INSTANCE_GUARD_ACK` 行；它是惰性的（持鎖者已變），仍應移除。

## 5. 驗證接手

在 §3 或 §4 之後於備援主機上執行；每一列都成立，接手才算完成。

| # | 檢查 | 做法 | 預期 |
|---|---|---|---|
| 1 | 服務都起來 | `docker compose ps` | backend、frontend、guacd、tls-proxy 執行中；沒有 postgres（它不在這個形態裡） |
| 2 | 後端健康 | `docker compose exec backend wget -qO- http://localhost:8080/health` | 正常回應 |
| 3 | 鎖狀態 | `curl -sk https://<位址>/api/v1/seal/status`；在 `overridden` 期間另以管理者身分查 `GET /api/v1/instance-guard`，或看橫幅裡的持鎖者 | §3 之後 `instance_guard.state` 為 `held`；§4.3 之後為 `held`，或 `overridden` 且持鎖者的 `backend_start` 與 §4.2 訊息裡的相同。`reason` 在攔下頁確認時為 `ack_page`、以 `INSTANCE_GUARD_ACK` 確認時為 `ack_startup`；`overridden` 稽核列前者記確認的帳號、後者記 `operator via env`。持鎖者的 `backend_start` 變新，表示另一個後端拿到了鎖（§4.4） |
| 4 | 登入可用 | 以你知道密碼的帳號登入 | 登入成功；使用者帳號、角色與資產都在，因為它們在資料庫裡 |
| 5 | 資料是主用主機的 | 打開資產清單與稽核頁 | 在主用主機上建立的資產列在裡面；主用主機寫下的最後幾筆稽核列在，後面接著你剛在備援主機上的登入 |
| 6 | 已解封 | `KEK_PROVIDER=ui` 時看解封頁 | 已完成；`env` 或 `kms` 時，後端日誌沒有封印相關的拒絕 |
| 7 | 錄影 | 播放一筆主用主機所錄、已上傳離機的錄影 | 等待取回之後播放（離機錄影的首次播放要下載） |
| 8 | 位址 | 以使用者用的位址打開服務 | 落在備援主機上（拿 `docker compose ps` 的容器名對照憑證與回應） |
| 9 | 來源歸屬 | 你這次登入的稽核列 | 顯示你的用戶端位址而非代理的；否則 `TRUSTED_PROXIES` 對這台主機是錯的 |

```bash
# 在備援主機上，檢查 1 到 3
docker compose ps
docker compose exec backend wget -qO- http://localhost:8080/health
curl -sk https://<位址>/api/v1/seal/status
```

故障後的接手，要到事件單上記有 §4.1 的證據、用過的確認碼（若有）、以及備援主機回報 `held` 的時刻，才算完成。

## 6. 切回主用主機

修好的主用主機經由反向的計畫內切換回來（§3）：公告、讓備援主機把佇列清空、在備援主機上 `docker compose down`、在主用主機上 `docker compose up -d`、重指向位址、驗證。主用主機啟動之前，確認它擁有備援主機期間變動的一切：相同的版本、任何 `.env` 變動、以及備援主機所錄的錄影（若你要它們在主用主機上播得出來；§4.4 反向做，或交給離機儲存）。

## 7. 非計畫接手保不住的東西

這是本程序的邊界，寫成可以直接放進復原計畫的形式。主機故障後的接手之後：

- **進行中的每一條會話都結束**，每一種協定都是，使用者得重新連線。沒有會話遷移。
- **那些會話的錄影在故障點被截斷。** 到當機那一刻為止的檔案在故障主機的磁碟上；它不會上傳到離機儲存（上傳只涵蓋正常結束的錄影），也不在備援主機上。在備援主機上，那些會話記錄顯示 `end_reason=backend_restart`、沒有可播放的錄影。磁碟救回來的話檔案可以複製過來（§4.4），寫到哪裡就播到哪裡。
- **正常結束但尚未上傳完成的錄影**，只存在於故障主機的磁碟上，直到它被救回。暴露窗口就是故障當下的上傳佇列（文字錄影在會話結束後秒級排入，圖形錄影至少一分鐘之後；等著不可達儲存端點的東西等更久）。
- **未啟用離機儲存時，主用主機所錄的錄影沒有一筆在備援主機上播得出來**，直到主用主機磁碟救回並複製過來。
- **在故障主機上降級到檔案的稽核列**（資料庫不可達期間寫下的）不在資料庫裡、也不在備援主機上，直到檔案被救回並重放。
- **匯出產物**在產生中或尚未下載的，其下載連結失效；可以在備援主機上重新匯出，已完成的在保留期內或許還能從離機儲存取回。
- **瀏覽器的登入狀態保留、不是丟失**：兩台主機共用 `JWT_SECRET`，專案演練時主用主機發出的 access token 原樣被備援主機接受。使用者丟的是協定會話，不是登入。
- **確認在攔下頁完成時，記的是完成確認的那個管理員帳號；由 `INSTANCE_GUARD_ACK` 完成時，記為 `operator via env`**，不是某個人。無論哪一條，做這個決定的依據都在你的事件單上，不在產品裡。

上面這份清單裡沒有一項是產品自己會救回來的。資料庫持有的東西，也就是帳號、資產、憑證、政策、稽核列、會話記錄、排程與離機保管帳冊，完好無缺，因為它們從來不在主機上。

## 8. 對備份、升級與部署形態限制的影響

- **備份**（[備份與還原](./backup-and-restore.md)）：資料庫在資料庫伺服器上備份，以對它執行的 `pg_dump` 取代 `docker compose exec postgres`；錄影與稽核目錄從**每一台持有檔案的應用主機**備份，接手之後就是兩台；`.env` 與 `tls/` 兩台都備。還原程序裡啟動 postgres 並載入 dump 的那一步，在資料庫伺服器上進行。一致性要求（資料庫與檔案落點來自同一時點）不變，跨機器更難達成；備份窗口內把活動中的應用主機停下。
- **升級**（[部署與升級 SOP](./upgrade-sop.md)）：升級仍在活動主機停止的狀態下進行；接著**兩台**主機都換上新的映像與檔案，只啟動其中一台。沒有同步升級的備援主機，是接不了手的備援主機（§2.2 第 1 步）。SOP 排除的滾動更新在這裡同樣排除：絕不為了「掩護」主用主機的升級而啟動備援主機。
- **部署形態**（[部署形態限制](./deployment-topology-limits.md)）：本程序沒有新增任何形態。任一時刻只有一個應用實例對著資料庫執行，那正是單實例守衛要求的，而守衛就是在不是這樣時告訴你的東西。
