## このテンプレートについて

本テンプレートは、開発用と本番用の両方の compose ファイルで共有されます。

### セットアップ手順（運用担当者と開発者で共通）

1. `cp .env.example .env`
2. 編集します。すべてのシークレットを変更したうえで、必要に応じて `DB_SSLMODE` / LDAP / `DATA_PATH` を
   設定します。
3. `docker compose up -d`

一括で行う場合は `bash scripts/quickstart.sh --up` を実行します。このコマンドは `.env` を作成し、
テンプレート値のまま残っているシークレットを生成したうえで、スタックを起動します。すでに記入済みの値は
変更されません。

### 本番スタックと開発スタック

既定の `docker-compose.yml` は本番スタックです。nginx がビルド済みのフロントエンドを配信し、バックエンドは
スリムなバイナリで、テスト用ターゲットは含まれません。自分の環境で Custodexa を運用することが目的であれば、
ここまでで完了です。

開発者の方は、下記の `COMPOSE_FILE` のコメントを外してください。これにより、すべての `docker compose`
コマンド（`exec ... go test` を含む）が `-f` を付けずに開発スタックを対象とします。開発スタックでは
フロントエンドとバックエンドのホットリロード、Go ツールチェーン一式、6 種類のテストターゲット
（ssh、rdp、vnc、ldap、mysql、k3s）が利用できます。明示的に `-f docker-compose.yml` を指定すればこの設定を
上書きできるため、開発マシンからでも本番構成を検証できます。あわせて `KEK_PROVIDER=env` と
`ENCRYPTION_KEY` も設定してください。ホットリロードはリビルドのたびにプロセスを再起動するため、`ui` のままでは
保存のたびに解封（unseal）操作が必要になります。

### `COMPOSE_FILE`

```
# COMPOSE_FILE=docker-compose.dev.yml
```

上の行はコメントアウトされたままにしなければなりません。このテンプレートをコピーすることによって、デプロイ
担当者は本番スタックを手にします。ここに有効な値が入っていると、気づかないうちに開発スタック（Vite 開発
サーバー、公開ポートも異なります）を渡してしまうことになります。`COMPOSE_FILE` はバックエンドではなく
docker compose CLI が解釈するため、env ドリフトガードのキー集合の対象外です。

### `env_file` の読み込みに関する注意

両方の compose ファイルが `env_file` を通じて本ファイルを読み込み、compose は `${DATA_PATH}` を使って永続
データの配置先を決めます。注意点として、`env_file` は**値が空の行に付いたインラインコメントを取り除きません**。
`SOME_KEY=  # note` という行は、リテラル文字列 `# note` を値として与えます。本ファイルのノブはほとんどが既定で
空であるため、説明はすべて独立した行に置き、値の行には末尾コメントを一切付けていません。

### compose 側から与えられ、ここでは設定できない項目

トポロジとモードの定数（`DB_HOST=postgres`、`GUACD_HOST=guacd`、`DB_DRIVER`、`GIN_MODE`、コンテナ内のパス）は
compose の `environment:` ブロックから与えられます。このブロックは `env_file` より優先されるため、本ファイルで
設定しても効果はありません。`DB_DRIVER` には出荷時の既定値がなく、値がなければバックエンドは起動を拒否します。
両方の compose ファイルはこれを供給しますが、バイナリ単体または自前ビルドによるデプロイ（k8s マニフェスト、
systemd ユニットなど）では、その側で供給する必要があります。サポート対象は PostgreSQL のみです。sqlite の分岐は
単体テスト用であり、バージョン管理されたマイグレーションは PostgreSQL の SQL です。

環境変数テンプレートはこのファイルだけです。バックエンドが利用する変数が、ここに記載されておらず compose から
供給されてもいない場合、`backend/config/env_drift_test.go` がビルドを失敗させます。

### マーカーの凡例

- `[secret]` — 本番投入の前に必ず変更してください。
- `[PCI x.y]` — そのキーの背景にある PCI DSS 要件です。マーカーが「N を推奨」となっている場合、N はその要件が挙げて
  いる値で、出荷時の既定値はそれとは別の値です。必要に応じて引き上げるか引き下げてください。それ以外の `[PCI]` キーは、
  システムが自ら強制する要件です。要件が満たされないあいだ何を拒否するかは、そのキーの説明に書いてあります。
- `[seed]` — 初回起動時に一度だけ書き込まれ、その後はポリシー画面から管理します。

## データの配置

### `DATA_PATH`

```
DATA_PATH=./data
```

アプリケーションデータ（監査ログ、録画、データベース）を置くルートフォルダで、コンテナへ bind mount されます。
既定値はプロジェクト内の `./data` で、開発中に中身を確認しやすい配置です。本番環境では専用のフォルダまたは
ディスク（例: `/opt/custodexa/data`）を指定してください。

## データベース

以下は compose の postgres サービスの名前と資格情報で、開発・本番のいずれでも同じです。

### `DB_NAME` / `DB_USER`

```
DB_NAME=custodexa
DB_USER=postgres
```

### `DB_PASSWORD`

```
DB_PASSWORD=postgres
```

`[secret]` 開発用の既定値です。本番では必ず強固なパスワードに置き換えてください。

### `DB_SSLMODE`

```
DB_SSLMODE=disable
```

同梱の postgres へは、同一ホスト上の隔離されたブリッジ経由で TLS を使わずに接続するため `disable` としています。
ネットワークを越えて外部データベースへ接続する場合は `require` または `verify-full` が必要です（PCI 要件 4）。

## シークレット

### `JWT_SECRET`

```
JWT_SECRET=change-me-in-production-dev-secret
```

`[secret][PCI 2.2.2]` `JWT_SECRET` は HS256 認証の信頼の起点であり、最低 32 バイト必要です（それより短い場合は
起動を拒否します）。上の値は出荷時の既定値です。リリース（本番）ビルドは、この値が変更されないままだと起動を
拒否します（フェイルクローズ、PCI 2.2.2）。デバッグビルドはこの値を受け入れます。本番用の値は CSPRNG で生成して
ください（例: `openssl rand -base64 32`）。

### KEK — エンベロープ暗号化の鍵暗号化鍵

KEK はデータベース内の暗号化カラムすべてを保護します。資産の資格情報、SFTP パスワード、TOTP シード、通知用
シークレットが対象です。出荷時の既定値は `ui` です。鍵素材（key material）にはどのモードでも出荷時の既定値が
存在しないため、どのデプロイでも必ず 1 つの明示的な操作が必要になります。quickstart スクリプトを実行するか、
自分で素材を生成して宣言してください。各モードの運用上の代価を理解したうえで選択してください。

- **`ui`（出荷時の既定値）** — 素材はメモリ上にのみ存在します。初回起動時の初期化画面でブラウザ内にてローカルに
  生成され、以後は解封（unseal）画面で管理者が再入力します。ディスクには一切書き込まれません。**代価**:
  プロセスが再起動するたび（クラッシュ、ホストの再起動、コンテナの再作成）にシール状態で立ち上がり、人間が
  鍵を再入力するまでサービスを提供できません。無人運用のデプロイでは `env` または `kms` を使用してください。

- **`env`** — `KEK_PROVIDER=env` を設定したうえで、後述の `ENCRYPTION_KEY` のコメントを外し、生成した値を
  記入します（`env` を宣言済みであれば `bash scripts/quickstart.sh` が一度だけ生成します）。再起動に人手が
  不要になり、この性質がホットリロード開発を成立させます。**代価**: 素材がサーバーのディスク上に平文で置かれる
  ため、このファイルを読める者は誰でも — バックアップ経由、スナップショット経由、パーミッション設定の誤り経由で
  あっても — ルート鍵を握ることになります。

- **`kms`** — クラウドの鍵サービスへ委譲します。後述の設定項目を参照してください。

- **`hsm`** — ハードウェアモジュールのインターフェースは実装されていません。この値は選択しないでください。

### `KEK_PROVIDER`

```
KEK_PROVIDER=ui
```

`KEK_PROVIDER` は大文字・小文字を区別し、ホワイトリスト外の値（`ENV` のような表記も含みます）は起動を拒否します。
推測もフォールバックも行いません。**空欄は「未設定」を意味し、`ui` ではありません。** 空欄の場合、
`ENCRYPTION_KEY` があれば `env` モードにフォールバックし、なければ起動を拒否します。`ui` はこのテンプレートが
明示的に出荷している値であり、実行時の既定値ではありません。

### `ENCRYPTION_KEY`

```
# ENCRYPTION_KEY=
```

`[secret][PCI 2.2.2]` KEK の素材で、**32 バイトの鍵 1 本**です。「32 バイト」は鍵の長さであって入力する文字列の
長さではないため、次の 3 つの形式がいずれも受け入れられます。

1. ちょうど 32 文字（A-Z、a-z、0-9）
2. 16 進数 64 文字
3. base64（標準形式または URL セーフ形式、パディングの有無は問いません）で、デコード結果がちょうど 32 バイトに
   なるもの

デコード結果が 32 バイトにならないものはすべて拒否されます。短い素材が自動的にパディングされることはありません。

上記の鍵は意図的にコメントアウトしてあります。この値が必要なのは `KEK_PROVIDER=env` の場合だけです。`ui`（既定値）と
`kms` ではコメントアウトのままにしなければならず、ここに値があると矛盾した構成として起動を拒否します。
素材は文字列を自分で考えるのではなく、CSPRNG で生成してください。エントロピーの低い値は長さのチェックを通過しても
脆弱なままであり、公開ドキュメントからコピーした値を使えば、すべてのデプロイが同じ KEK を持つことになります。
次のいずれのコマンドでも生成できます。

```
openssl rand -hex 32
openssl rand -base64 32
LC_ALL=C tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 32
```

（受け入れられる形式ごとに 1 コマンドを挙げています。ガードテストがそれぞれを実行し、出力が常に検証を通過する
ことを確認しています。）KEK 素材のキーはちょうど 1 つだけで、別名も代替キーもありません。また空文字列は「無効化」を
意味しません。空は「素材がない」ということであり、`env` モードはその状態では起動を拒否します。`ui` の場合は、
上記のプレースホルダがコメントアウトされたままであることが正しい状態です。

`env` モードを使うには、上の行のコメントを外し、生成した値を貼り付けてください。

### 委譲モードの設定（`KEK_PROVIDER=kms`）

3 つの `KEK_KMS_*` キーは、起動時に過不足がないか検査され、欠けているものは個別に列挙されます。また、
ローカルの KEK 素材キーはすべて未設定でなければならず、値が残っていると矛盾した構成として起動を拒否します。

#### `KEK_KMS_PROVIDER` / `KEK_KMS_KEY_ID` / `KEK_KMS_REGION`

```
# KEK_KMS_PROVIDER=
# KEK_KMS_KEY_ID=
# KEK_KMS_REGION=
```

`KEK_KMS_PROVIDER` は現在 `aws` のみに対応しています。`KEK_KMS_KEY_ID` にはエイリアス、素の key id、完全な ARN の
いずれも指定できます。起動時に `DescribeKey` を通じて key ARN へ正規化してから保存するため、3 つの書き方は等価です。
資格情報は AWS SDK の既定のチェーン（IRSA、インスタンスプロファイル、`AWS_*` 変数、SSO）から取得します。Custodexa は
クラウドの資格情報を保持せず、エンドポイントの上書き機能も提供しません。

エンドポイントの上書きは、本番経路では明確に拒否します。`AWS_ENDPOINT_URL_KMS` と `AWS_ENDPOINT_URL` は SDK 自身が
解決するため、指定されたアドレスへ `kms:Encrypt` リクエスト — 平文の DEK を含みます — を、場合によっては平文の HTTP で
送信してしまいます。いずれか一方でも設定されていればフェイルクローズとなり、`~/.aws/config` の `endpoint_url` も
同様です。

`KEK_KMS_KEY_ID` は、このデプロイがどの KMS アカウントを信頼するかの宣言でもあります。鍵変更ウィザードに渡された
再ラップ（rewrap）先（リクエストボディの `key_ref`）は、この鍵と同じパーティション、かつ同じ AWS アカウントに属して
いなければ拒否されます。リージョンが一致するだけでは不十分です。

必要な IAM アクションは `kms:DescribeKey`、`kms:Encrypt`、`kms:Decrypt` です。ある KMS 鍵から別の鍵へ変更する場合は、
さらに `kms:ReEncryptFrom` と `kms:ReEncryptTo` が必要です（単一の `kms:ReEncrypt` ではなく、2 つのアクションです）。
起動時には `DescribeKey` のほかに、使い捨ての Encrypt/Decrypt の往復を 1 回実行します。これにより、権限の不足や
到達できない外部キーストア（XKS）は、初回利用時ではなく起動時に表面化します。

マルチリージョンキー（MRK）も KEK として利用できますが、本バージョンではプライマリとレプリカを別々の鍵として扱う
ため（保存される `kek_id` にリージョンが含まれます）、レプリカへの切り替えは鍵変更にあたり、事前にウィザードでの
再ラップが必要です。

ローカルモード（`env` または `ui`）から `kms` へ移行する手順は次のとおりです。ローカルモードで稼働させたまま上記の
3 つのキーを記入し、鍵変更ウィザードで対象の `key_ref` へ再ラップし、そのうえでローカルの KEK 素材キーを削除して
`KEK_PROVIDER=kms` を設定し、再起動します。

#### `KEK_HSM_MODULE` / `KEK_HSM_TOKEN_LABEL` / `KEK_HSM_KEY_LABEL` / `KEK_HSM_PIN` / `KEK_HSM_PIN_FILE`

```
# KEK_HSM_MODULE=
# KEK_HSM_TOKEN_LABEL=
# KEK_HSM_KEY_LABEL=
# KEK_HSM_PIN=
# KEK_HSM_PIN_FILE=
```

未使用です。網羅性のために `hsm` モードのキーとして記載しています。

### `ADMIN_INITIAL_PASSWORD`

```
ADMIN_INITIAL_PASSWORD=change-me-admin-initial-password-in-env
```

`[secret][PCI 8.3.6/2.2.2]` `ADMIN_INITIAL_PASSWORD` は、まっさらな（データベースが空の）デプロイで作成される初期
管理者アカウントのパスワードです。公開された既定値はもはや存在しないため、シードを行うデプロイは — 開発用の新規
データベースであっても — 独自の値を設定する必要があります。上のプレースホルダは拒否リストに登録されており、値が
そのプレースホルダのまま、12 文字未満、または空白文字や改行を含む場合、空のデータベースに対する起動はどのモード
でも拒否されます。

高エントロピーの値を使用してください（`openssl rand -base64 24` の出力から末尾の改行を除いたもの）。この値は初回
ログイン時の強制パスワード変更で役目を終えるため、ログインできたらここから削除するか、値をローテーションして
ください。空でないデータベースに対して起動したときに、まだ使用可能な値が残っていると警告が出ます。既存の空でない
データベースでは、この値はそもそも不要です。

## サーバー

補足: `GIN_MODE` は環境ごとに compose 側で固定されています（開発 = `debug`、本番 = `release`）。デプロイ時に調整する
ノブではないため、ここには記載していません。

### `CORS_ALLOWED_ORIGINS`

```
CORS_ALLOWED_ORIGINS=
```

`[PCI 7.3]` カンマ区切りの許可リストです。空欄の場合、`release` では同一オリジンのみが許可されます。

### `METRICS_TOKEN`

```
METRICS_TOKEN=
```

運用メトリクスのエンドポイント `/metrics` 用の Bearer トークンです。空欄は認証なしを意味し、
空欄が安全な既定値です。`/metrics` は `/api` 配下に存在せず、本番のエッジは `/api` と `/ws` しかプロキシしないため、
外部からは到達できません。**他のホストからスクレイピングする目的でリバースプロキシに `/metrics` への経路を開く場合は、
この値を必ず設定してください。**設定しなければ、エンドポイントの一覧、機能ごとの利用状況、エラー率を公開することに
なります。

## ブラウザセッション

### `AUTH_REFRESH_COOKIE_SECURE`

```
AUTH_REFRESH_COOKIE_SECURE=
```

`[seed]` ブラウザへ渡すセッション更新用の cookie に `Secure` 属性を付けるかどうかを指定します。付けた場合、
ブラウザはこの cookie を HTTPS 接続でのみ保持し、送信します。指定できる値は `true` と `false` です。
ここに書いた値は**初回起動時**に同名のセキュリティポリシーへシードされます。それ以降のスイッチは
システム設定 → セキュリティポリシー →「接続とアカウント」にある**「ログイン状態を https 接続でのみ保持」**
であり、その画面で保存すると次に発行される cookie から新しい値が適用されます。再起動は不要です。
ポリシーに値が入ったあとは、本ファイルを変更しても効果はありません。

空欄の場合は `PUBLIC_BASE_URL` のスキームからシード値を決めます。https のアドレスなら有効、http の
アドレスなら無効、どちらも未設定ならポリシーは出荷時の既定値（有効）のままです。TLS を本システムの
手前で終端していて、`PUBLIC_BASE_URL` が公開用の https アドレスを保持していない場合は `true` を、
本システムを平文の http で公開する場合は初回起動の前に `false` を設定してください。

平文の http で公開しているのにポリシーを有効のままにしても、システムは動作し続けます。ただしブラウザが
この cookie を破棄するため、すべての利用者が 15 分ごと（アクセストークンの寿命）に再ログインすることに
なります。この状況は利用者から見えます。ログイン画面が現状を説明し、セキュリティポリシー画面でも管理者に
同じ内容を案内します。その画面でポリシーを無効にすれば、すぐに解消します。

ローカル開発で `http://localhost` を使う場合、影響の有無はブラウザによります。Chromium と Firefox はこのアドレスからの
Secure cookie を受け入れます。Safari 系の WebKit は破棄するため、Safari で開発するときはポリシーを
無効にしてください。

実際に適用された値と、その由来は起動ログに出力されます。

## 機能フラグ

補足: 権限チェックにはフラグが一切ありません。どのモードでも無条件に適用されます。

リリース時の安全下限にあたるのは `FEATURE_AUDIT_LOG_ENABLED` の 1 つだけです。`GIN_MODE=release` では、これを `false`
にしても無視され、監査は強制的に有効へ戻されます。強制されたキー名は起動ログに出力されます（すべての操作を監査する
ことはレッドラインであり、デプロイ層から無効化することはできません）。残る 4 つのフラグは通常のスイッチで、`release`
モードであっても設定したとおりに動作します。

```
FEATURE_AUDIT_LOG_ENABLED=true
FEATURE_ASYNC_AUDIT_ENABLED=true
FEATURE_AUDIT_FALLBACK_TO_FILE=true
FEATURE_ANOMALY_DETECTION_ENABLED=false
FEATURE_ALERTING_ENABLED=false
```

## OIDC アイデンティティプロバイダ連携

プロバイダそのもの（issuer、client id、シークレット、受け入れルール）は管理 UI で設定し、データベースに保存されます。
ここに置かれているのは、デプロイ層が決めなければならない 3 つの設定だけです。

SSO を有効にする前に、運用上の前提条件が 2 つあります（全文は `docs/QUICKSTART.md` にあります）。

1. **ローカルの管理者アカウントを少なくとも 1 つ残してください。**解封（`KEK_PROVIDER=ui`）と初期管理者の認可は
   ローカルの資格情報しか受け付けません。これらはシステムが完全に立ち上がる前に行われる操作であり、外部 IdP では
   完了できないためです。すべての管理者を外部化してしまうと、シールされたシステムを解封できる人間が誰もいなく
   なります。そのアカウントには強固なパスワードを設定し、MFA を有効にしてください（最後のローカル管理者を削除
   できないよう、不変条件がすでに防いでいます）。

2. **IdP 側でユーザーを無効化しても、進行中のプロトコルセッションは切断されません。**本バージョンにバックチャネル
   ログアウトはなく、確立済みの SSH／RDP／VNC セッションは資格情報を参照しなくなっているため、アイドルタイムアウト
   または最大セッション長に達するまで存続します。発行済みのアクセストークンも有効期限（15 分）までは有効なままです。
   IdP 側での停止は、**次回のログイン**を拒否するだけです。アクセスを直ちに遮断するには、本システムの管理 UI で
   アカウントまたはプロバイダ全体を無効化してください。どちらの操作も、資格情報の失効、セッションの終了、監視
   フィードの切断を行います。

### `PUBLIC_BASE_URL`

```
PUBLIC_BASE_URL=
```

公開ベース URL です。IdP へ渡す `redirect_uri` と、コールバックの戻り先アドレスの組み立てに使用します。リクエストの
`Host` からは導出しません。多段のリバースプロキシの背後では導出は必ず誤りとなり、誤った値が `redirect_uri` に入って
利用者を別のホストへ送ってしまうためです。未設定のあいだ、有効化されたプロバイダは不完全としてマークされ、ログイン
画面から隠されます（フェイルクローズ）。本番では https でなければなりません（例: `https://bastion.example.com`）。

### `OIDC_DEDICATED_ISSUERS`

```
OIDC_DEDICATED_ISSUERS=
```

専用 issuer の宣言です（カンマ区切り）。未知の issuer は**共有**アイデンティティドメインとしてフェイルクローズに扱われ、
その受け入れルールには組織条件（テナント id またはホステッドドメイン）が必須となります。Okta やセルフホストの IdP
などはそのようなクレームを発行しないため、この宣言がないと自動プロビジョニングを構成できません。ここに issuer を
宣言することは「この issuer は自組織のみにサービスを提供している」と述べることであり、これはデプロイ担当者にしか
下せない判断です。管理者向けの UI に露出していないのはそのためです。組み込みの共有リスト（Google、Microsoft の
マルチテナントエンドポイントなど）が優先され、ここから上書きすることはできません。変更が有効になるのは、全レプリカを
ローリング再起動した後です。

例: `OIDC_DEDICATED_ISSUERS=https://acme.okta.com,https://idp.internal.example`

### `OIDC_ALLOWED_INTERNAL_HOSTS`

```
OIDC_ALLOWED_INTERNAL_HOSTS=
```

外向き通信の宛先として許可する内部ホスト名です（カンマ区切り）。IdP への外向き呼び出しは、既定ではループバック、
リンクローカル（クラウドのメタデータアドレスを含みます）、プライベート範囲へ解決されることを拒否します。したがって
内部 IdP はここに明示的に列挙する必要があります。アドレス検査を無効化する真偽値のスイッチは存在しません。`release`
モード以外では、ここに列挙されたホスト名には http でも到達できます。開発用の IdP ターゲットはこれを必要とします。

## LDAP 認証（シードのみ。実行時設定ではありません）

以下の `LDAP_ENABLED` から `LDAP_SKIP_TLS_VERIFY` までのキーは、データベースへ一度だけ書き込まれます。書き込まれるのは、
初回起動時にテーブルが空で、かつ `LDAP_ENABLED=true` の場合だけです。それ以降は、管理 UI の「アイデンティティ管理 →
LDAP ディレクトリ」が唯一の正となり、このファイルを編集しても効果はありません（システムは評価済みマーカーを記録する
ため、行を削除しても再度シードされることはありません）。本節の最後のキーである `LDAP_ALLOWED_LOOPBACK_ENDPOINTS` は
この集合に含まれません。こちらは実行時の外向き通信ポリシーで、このファイルから読み続けられます。

古いバージョンへダウングレードする前に、現在の管理 UI の設定を bind パスワードも含めてこのファイルへ書き戻して
ください。詳細は `docs/QUICKSTART.md` を参照してください。

### `LDAP_ENABLED`

```
LDAP_ENABLED=false
```

既定では無効です。開発環境で LDAP を試す場合は `LDAP_ENABLED=true` にしてください。以下の値は同梱の `ldap-test`
サービスに合わせてあります。本番では `LDAP_URL` を実在のディレクトリサーバーに向け、対応する DN とパスワードを記入して
ください。

### `LDAP_URL`

```
LDAP_URL=ldap://ldap-test:1389
```

同梱の開発用テストサービスです。本番では実在のサーバーを指定してください（`ldap://` または `ldaps://`）。

### `LDAP_BIND_DN`

```
LDAP_BIND_DN=cn=admin,dc=example,dc=org
```

### `LDAP_BIND_PASSWORD`

```
LDAP_BIND_PASSWORD=adminpass
```

`[secret]` 開発テスト用の値です。本番では必ず置き換えてください。

### `LDAP_BASE_DN` / `LDAP_USER_FILTER` / `LDAP_ATTR_EMAIL` / `LDAP_ATTR_FULLNAME`

```
LDAP_BASE_DN=ou=users,dc=example,dc=org
LDAP_USER_FILTER=(uid=%s)
LDAP_ATTR_EMAIL=mail
LDAP_ATTR_FULLNAME=cn
```

検索の基点 DN、ユーザー検索フィルタ、メールアドレス属性、氏名属性です。いずれも上記の値は同梱の開発用テスト
サービスに合わせたものです。

### `LDAP_SKIP_TLS_VERIFY`

```
LDAP_SKIP_TLS_VERIFY=false
```

自己署名のテスト証明書を使う場合に限って使用します。本番では常に `false` にしてください。

### `LDAP_ALLOWED_LOOPBACK_ENDPOINTS`

```
LDAP_ALLOWED_LOOPBACK_ENDPOINTS=
```

外向き通信の宛先として許可するループバックエンドポイントです（カンマ区切り、`host:port` の完全一致、ワイルドカードは
使えません）。LDAP の接続は、既定ではループバック、リンクローカル（クラウドのメタデータアドレスを含みます）、
未指定アドレス、マルチキャストアドレスを拒否します。一方でプライベート範囲は許可されます。ディレクトリは通常、内部
ネットワーク上に存在するためです。アドレス検査を無効化する真偽値のスイッチは存在しません。ディレクトリが同一ホスト上で
動作している場合は、そのエンドポイントをここに列挙してください（例: `127.0.0.1:1389`）。

## シール状態機械と解封エンドポイント（`KEK_PROVIDER=ui` のときに有効）

ここにあるキーはすべて空欄のままにでき、その場合は組み込みの安全な既定値が適用されます。KEK 素材は解封 API を通じて
のみメモリへ到達するため、この節は全体がレート、送信元、リスナーに関するノブであり、鍵素材は一切含みません。シール期間の
ジャーナルは監査ログのディレクトリへ書き出されます。両方の compose ファイルがコンテナ内に
`AUDIT_LOG_PATH=/var/log/custodexa/audit` を設定し、ホスト側の `${DATA_PATH}/audit` を bind mount しているため、
ジャーナルはそこにあります。書き出し先を指定する専用のキーはありません。

**以下の 4 つの `*_SECONDS` ノブは、共通の解析ルールに従います。**空欄または数値として解釈できない文字列は、各キーに
記載された既定値へフォールバックします。しかし 1〜86400 の範囲外の**数値** — ゼロ、負値、過大な値 — は、値を丸めずに
起動を拒否します。指定した値が黙って無視されるレート制限は、レート制限がないことよりも悪いためです。同様に、上限
（ceiling）が基準（base）を下回る場合も起動を拒否します。

### `SEAL_UNSEAL_BACKOFF_BASE_SECONDS`

```
SEAL_UNSEAL_BACKOFF_BASE_SECONDS=
```

送信元ごとのバックオフの基準（秒）です。空欄または数値でない文字列の場合は 2 となります。

### `SEAL_UNSEAL_BACKOFF_MAX_SECONDS`

```
SEAL_UNSEAL_BACKOFF_MAX_SECONDS=
```

送信元ごとのバックオフの上限（秒）です。空欄または数値でない文字列の場合は 300 となります。バックオフの増大には上限が
必要です。そうしてはじめて「待てばまた試せる」という性質が、どのような攻撃強度のもとでも成り立ちます。

### `SEAL_UNSEAL_COOLDOWN_THRESHOLD`

```
SEAL_UNSEAL_COOLDOWN_THRESHOLD=
```

全体クールダウンを発動させる、誤った鍵による連続した解封試行の回数です。カウントはすべての送信元をまたいで通算され、
一度でも解封に成功するとゼロへ戻ります。これは時間ではなく回数であるため、上記の `*_SECONDS` ノブと比較できる値では
ありません。1 人の管理者が現実に犯しうる連続ミスの回数より十分に大きい値を設定してください。そうすれば、鍵を
打ち間違えてもその本人が送信元ごとの待ち時間を負うだけで済み、エンドポイント全体をクールダウンに入れて他の全員を
足止めすることにはなりません。空欄の場合は 20 となります。

**このキーの解析ルールは、上記の `*_SECONDS` ノブとは異なります。**空欄以外で、1〜1048576 の整数として解釈できない値は
（数値でない文字列も含めて）すべて起動を拒否し、既定値へフォールバックすることはありません。

### `SEAL_UNSEAL_COOLDOWN_SECONDS`

```
SEAL_UNSEAL_COOLDOWN_SECONDS=
```

全体クールダウンの基準（秒）です。空欄または数値でない文字列の場合は 60 となります。クールダウンは必ず自然に解除され
ます。クールダウンからの復帰にプロセスの再起動が必要になることはありません。

### `SEAL_UNSEAL_COOLDOWN_MAX_SECONDS`

```
SEAL_UNSEAL_COOLDOWN_MAX_SECONDS=
```

全体クールダウンの上限（秒）です。空欄または数値でない文字列の場合は 900 となります。

### `TRUSTED_PROXIES`

```
TRUSTED_PROXIES=
```

信頼するプロキシの一覧です（IP または CIDR、カンマ区切り）。未設定のあいだ、IP ごとのバックオフは全体バックオフへ縮退
します。合意されたプロキシチェーンがなければ、レート制限のキーが転送ヘッダによって汚染され得るためであり、迂回できる
防御は大雑把な防御よりも悪いからです。

### `SEAL_UNSEAL_BIND_ADDR`

```
SEAL_UNSEAL_BIND_ADDR=
```

解封エンドポイント専用の待ち受けアドレスです（例: `127.0.0.1:8081`）。空欄の場合は本体サービスのリスナーを共有します。

### `SEAL_UNSEAL_ALLOWED_CIDRS`

```
SEAL_UNSEAL_ALLOWED_CIDRS=
```

解封エンドポイントへの到達を許可する送信元の範囲です（CIDR または素の IP、カンマ区切り）。空欄の場合は制限しません。
管理ネットワークと組み合わせて指定してください。認証のないエンドポイントでは、どのようなレート制限の仕組みをもってしても
管理者が必ず通過できることを保証できないためです。
